# 用车报价服务平台 · 开发需求

Oct 6, 2026 · @LUCAS

## 文档说明

本系统是用车业务的**报价与服务底层（服务端）**：平台统一维护车型、城市、地点和坐标等主数据；多个供应商作为租户各自配置商品和报价规则；所有配置和报价能力都通过 API 开放给销售端对接。本文档是给开发团队的需求说明，覆盖接送机、点对点、包车三类商品。

**三类角色**

| 角色 | 是谁 | 做什么 | 入口 |
| --- | --- | --- | --- |
| 平台 | 我方运营 | 维护统一主数据（国家城市、机场/车站/POI 坐标、车型目录、附加服务目录等），开通租户，分配销售端 | 平台运营后台 |
| 租户（供应商） | 车队，如 NOZOMI、Relaxcar | 建区域、建商品、设服务规则和报价规则、管库存、接单派单 | 租户后台 + 租户配置 API |
| 销售端 | 自有官网、OTA、旅行社、分销平台 | 查询主数据、请求报价、下单、取消、接收订单状态推送 | 销售端开放 API |

**范围**

- 本期：主数据、租户后台（区域、商品、服务规则、价格规则、调价规则、库存、上架校验、商品详情模版）、报价引擎、租户配置 API、销售端 API（报价到订单状态推送）。
- 不在本期：司机端 App、派单算法、支付收银、财务结算。订单建好后推送给租户现有的调度系统。

**参考依据**

- 迪达（Dida）供应商后台的区域与商品创建规则（另有 PRD 整理），本系统沿用其区域、四步建商品、计价模型和调价规则的设计。
- 在迪达基础上的改进：包车同一区域同一车型允许多个套餐（如 5 小时和 10 小时）；增加草稿态；增加商品详情模版（日语、中文等多语言）；所有规则可经 API 读写。

## 系统架构

系统分三层：开放 API 网关、四个核心服务、两类数据。租户后台本身也走 `/tenant/v1`，没有绕过 API 的内部入口，保证后台能做的事 API 都能做。

&#91;embedded content: 系统架构 · 4 个核心服务，2 类数据\]

报价引擎是核心：它读平台主数据和租户配置，输出带快照的报价；订单服务只认报价快照，并向销售端和租户调度系统推送状态。

- **多租户隔离**：共享数据库、按 `tenant_id` 隔离，并用行级安全兜底；大租户以后可单独拆库。
- **缓存**：主数据和已上架商品的规则放缓存；租户改规则发事件，1 分钟内刷新。
- **空间计算**：点是否在多边形内用 PostGIS 空间索引，热点区域可在内存里算。

## 统一主数据（平台级）

主数据由平台唯一维护、所有租户和销售端共用同一套编码；租户只能引用，不能新建或修改。这样同一个「羽田机场 T3」「商务 7 座」在所有租户、所有销售端都是同一个 ID，销售端可以拿一次请求同时问多个租户的价。

| 主数据 | 编码规则 | 关键字段 | 说明 |
| --- | --- | --- | --- |
| 国家 | ISO 3166-1 alpha-2（JP、KR） | 多语言名称、默认币种 | — |
| 城市 | `CTY-` + 国家码 + 序号（CTY-JP-TYO） | 多语言名称、时区（IANA，如 Asia/Tokyo）、中心坐标、边界多边形 | 所有时间规则按城市时区计算 |
| 机场 | IATA 三字码（HND） | 多语言名称、所属城市、坐标、航站楼列表（每个航站楼单独坐标和上车点） | 接送机的 POI |
| 车站 | `STN-` + 国家码 + 序号（可映射各国铁路站码） | 多语言名称、类型（新干线/铁路/地铁）、坐标、出口列表 | 接送站与接送机共用一套 POI 逻辑 |
| POI（其他地点） | `POI-` + 序号 | 类型（酒店/景点/港口/商场）、多语言名称、坐标、地址 | 常用点位，销售端也可以直接传坐标 |
| 车型组 | `VG-` + 等级 + 座位（VG-BIZ-7） | 等级（经济/舒适/商务/豪华）、代表车型（如丰田埃尔法）、动力（燃油/EV）、可选「人数/行李数」组合 | 报价、库存、订单都按车型组，不按具体车牌 |
| 附加服务 | `ADD-` + 代码（ADD-CHILD\_SEAT） | 适用品类、计费方式（按次/按个/按人/按时长）、多语言名称和说明 | 迪达的目录说明见「租户端功能」 |
| 语言 | ISO 639-1（ja、zh、en） | — | 司机语言、商品详情多语言 |
| 币种 | ISO 4217（JPY、CNY） | 小数位（JPY 0，CNY 2） | 金额按币种小数位存储和取整 |
| 节假日日历 | 国家 + 日期 | 名称、类型 | 调价规则可以直接选「日本法定假日」 |

**坐标与地图规范**

- 全部坐标用 WGS84（经度、纬度，小数点后 6 位），多边形用 GeoJSON 存储，导入时支持 WKT。
- 中国大陆地图的 GCJ-02 坐标入库前转成 WGS84，输出时按销售端要求转换。
- 主数据每条带版本号和更新时间，销售端可以增量同步（`updated_since`）。
- 主数据只做停用，不做物理删除，保证历史订单和规则的引用不失效。

**汇率中心**

跨币种比价和对外报价都用汇率中心的中央汇率，它是平台主数据的一部分，租户和销售端都不能自己设汇率。

- **数据源**：先接免费汇率源（如欧洲央行每日参考汇率，或免费档汇率 API），以后可换付费实时源，按一个基准币种（建议 USD）存各币种汇率，任意两种币种用交叉汇率换算。具体服务商在开发前选定。
- **刷新**：按数据源的更新频率（每日或每小时）拉取，放缓存；数据源不可用时继续用最近一次有效汇率，超过 48 小时未更新则暂停跨币种报价并告警。
- **快照**：报价快照记录所用汇率和取数时间；订单按快照里的汇率结算，不随之后的汇率变动。
- **存储**：`fx_rate`（base、quote、rate、source、fetched\_at），保留全部历史，用于对账。
- **接口**：`GET /master/fx-rates?base=JPY`（租户和销售端只读）；平台后台可查历史曲线和更新状态。

## 租户端功能（供应商后台）

租户按「区域 → 商品四步 → 商品详情 → 上架」配置；后台每个按钮背后都是一个租户配置 API，后台能做的事租户也能用 API 做。

### 1. 区域管理（前置）

- 区域 = 一组营运多边形 + 一组禁行多边形，挂在一个城市下；商品和价格规则只引用区域。
- 字段：名称（多语言）、城市、业务类型（接送机/点对点/包车/通用）、归属（平台预设/租户自建）。
- 多边形来源：地图手绘、粘贴 WKT/GeoJSON、选平台预设区域（同一区域内每个预设只能加一次）。
- 区域规则：禁行优先（起点或终点落入禁行区就不报价）；点对点两端都要在营运区；接送机只校验非机场一端；包车只校验上车点（比迪达严一点，可配置关闭）。
- 被上架商品引用的区域不能删除；改多边形要提示影响的商品数。

### 2. 商品 · ① 基础信息

| 字段 | 适用品类 | 规则 | 创建后可改 |
| --- | --- | --- | --- |
| 子品牌（含币种） | 全部 | 租户下的品牌，决定商品所有金额的币种 | 否 |
| 国家 / 城市 | 全部 | 引用主数据 | 否 |
| 品类 | — | 接送机 / 点对点 / 包车 | 否 |
| 接送点（POI） | 接送机 | 一个商品一个机场或车站，引用主数据 | 否 |
| 服务区域 | 全部 | 多选，只显示本城市、品类匹配或「通用」的区域 | 是 |
| 车型组 | 全部 | 多选主数据车型组，每个选一个「人数/行李数」组合 | 是 |
| 调度人 | 全部 | 姓名 + 电话，可多个；随订单推送 | 是 |

商品状态：草稿 → 未上架 → 已上架 → 已下架。商品 ID：`PRD` + 日期时间 + 流水号，全平台唯一。

### 3. 商品 · ② 服务规则

服务规则是商品级配置，不分区域和车型。

| 规则 | 字段 | 说明 |
| --- | --- | --- |
| 预订规则 | 下单有效期（日期区间）、服务时间（每日 HH:mm–HH:mm）、提前预订时长（小时）、备注 | 用车时间须在服务时间内 |
| 加急预订 | 开关、每日加急库存、阶梯（提前 N 小时内 → 加收 X） | 允许在提前预订时长内下单，取最小的命中 N 一档 |
| 夜间加价 | 时段（可跨天）、金额、计费方式（按次 / 按小时） | 接送机一般按次，包车按与夜间时段重叠的小时数 |
| 免等 | 接送机：接机/送机各一项；包车：一项；每项「无限」或「有限 N 分钟」 | 平台统一默认值：国际线 90 分钟、国内线 60 分钟、接站 30 分钟、其他 15 分钟、包车 0；租户只能设得更长 |
| 取消规则 | 阶梯（出发前 N 小时以前取消 → 扣款 M%） | 第五轮起由平台按品类和车型级别统一设置，租户只读（付款前客人不知道中标租户，政策必须一致） |
| 附加服务 | 从主数据目录选，每项开关 + 单价；0 = 免费提供；座椅类可设「首个免费」 | 司机语言为多行「语言 + 单价」 |
| 附加费支付 | 服务后线上补款（扣 Stripe 保存的支付方式，客人 48 小时内可提异议）；平台订单不收现金 | 用于超时、超公里等履约后费用 |

### 4. 商品 · ③ 价格规则与调价规则

**价格规则** = 区域 × 车型组 ×（接送机：服务方向；包车：套餐时长）× 生效日期 的一条报价，带启停状态。

| 计价模型 | 适用品类 | 字段 |
| --- | --- | --- |
| 固定一口价 | 接送机、点对点 | 基础价 |
| 里程 + 时长 | 接送机、点对点 | 起步价、起步里程、起步时长、超出每公里单价、超出每分钟单价、最低消费 |
| 小时/公里套餐 | 包车 | 套餐时长、套餐公里、套餐价、超时单价（/小时）、超公里单价（/公里） |

- 唯一性：同一商品内「区域 + 车型组 + 方向或套餐时长」的生效日期不能重叠。包车把套餐时长加入唯一键，所以同一车型可以同时卖 5 小时和 10 小时。
- 「接送通用」和「接机」同时存在时，以更具体的「接机」为准。

包车的超时费、超公里费只在价格规则里设置；附加服务目录不再提供「车辆超时费」，避免两处设置互相冲突。

**调价规则**（可选）：名称、出行日期范围、周期（每天 / 每周指定星期 / 指定日期 / 节假日日历）、适用区域（空 = 全部）、适用车型（空 = 全部）、适用方向或套餐、适用时段（可跨天）、策略步骤（金额或百分比，可为负数，可多步）、优先级顺序、启停。后台提供「价格日历」视图：按区域、车型、套餐显示每天的最终价和命中的规则，在日历上框选日期即可新建调价规则。

### 5. 商品 · ④ 库存

- 模式：无限（默认）/ 有限。有限时按「商品 × 日期」设每日可售单数；预留按「商品 × 日期 × 车型组」的字段，二期开放。
- 批量设置：日期范围 + 数量；不填 = 清除。日历视图点日期直接改。
- 下单时预占，支付确认后扣减，取消或超时未支付自动释放；切回无限需二次确认。

### 6. 商品 · ⑤ 商品详情（本系统新增）

- 多语言标题、路线、简介、包含/不含列表、行程路线（包车）、接机指引（接送机，必填）。
- 使用条款、取消政策、附加费用等文字由**固定模版**自动生成，数字取自服务规则和价格规则，避免文字与实际规则不一致。模版由平台维护，按语言各一份。
- 销售端可用 API 取回渲染好的文字，也可取结构化数据自己渲染。

### 7. 上架校验

| 校验项 | 必须 | 通过条件 |
| --- | --- | --- |
| 基础信息 | 是 | 必填齐全，至少 1 个区域、1 个车型组 |
| 服务规则 | 是 | 必填齐全，取消阶梯合法 |
| 价格规则 | 是 | 至少 1 条启用且未过期 |
| 商品详情 | 是 | 至少一种对外语言的标题；接送机另需接机指引 |
| 调价规则、库存 | 否 | — |

所有增删改记录操作日志（操作人、来源是后台还是 API、时间、前后值）。

### 8. 订单与履约

租户有两种接单方式：有自己调度系统的用 Webhook 收单、用 API 回传派车和履约状态；没有的直接在后台手工派车。两种方式写入同一张订单。

| 功能 | 说明 |
| --- | --- |
| 订单列表 | 按用车日期、状态、品类、是否已派车筛选；顺序按用车时间；超过派车截止时间未派车的单置顶标红 |
| 订单详情 | 支付后可见乘客姓名、电话、航班号、上下车地点、附加服务、结算价（不显示销售端的对外价） |
| 订单指派 | 选司机 + 车辆；系统校验车型组、座位、司机语言、金牌司机、新车等是否符合订单要求；司机和车辆在当天同一时段已有订单时提示冲突 |
| 改派 | 服务开始前可换司机、换车，每次改派都重新推送 `order.assigned`（带 `change=true`）并通知客人 |
| 履约回传 | 已出发 → 已到达 → 已接到客人 → 已完成；完成时填实际时长和公里 |
| 附加费用 | 超时、超公里按商品规则自动计算；停车费等实报实销的费用必须上传凭证照片 |
| 客人未出现 | 司机提交 no-show 申请和证据，平台审核后按规则收费 |

**履约规则（已确认）**

| 规则 | 建议 |
| --- | --- |
| 派车截止时间 | 用车前 24 小时必须派车；下单时距用车不足 24 小时的，支付后 2 小时内派车 |
| 超时未派车 | 过截止时间告警租户调度人和平台运营；用车前 6 小时仍未派车升级告警。用车前 6 小时仍未派车则自动进入救援改派，按违约金阶梯扣款，并计入履约评分 |
| 客人未出现 | 接机：航班实际到达后等满免等时长（国际线 90 分钟、国内线 60 分钟）；其他品类：约定时间后等满免等时长。司机「已到达」定位距上车点 ≤ 300 米，期间至少联系客人 3 次，上传举牌照片，并在 H5 申请离开由客服确认；用车后 24 小时内提交，审核通过后按全额收费 |
| 改派和换车 | 自动通知客人和销售端；只能换同级或更高级的车型组，升级不加价，系统拦截降级 |
| 履约时间点 | 用车前 1 小时仍未「已出发」时提醒租户；服务结束后 24 小时内必须提交完成和附加费用 |

**落地时间**：取客人「我已落地」的时间；没有则取司机在 H5 填写的时间，填写时必须拍到达屏；都没有则取计划到达时间。客人和司机不一致时取较晚者；提交后不能改。航班延误 6 小时内顺延且不加收费用。

**声明无法履约**：订单详情页新增按钮，点击前显示本单会被扣的金额档位；提交后订单变为只读。租户也会收到其他租户的「救援单」，这是唯一需要主动接单的订单（15 分钟内不接顺延下一家）。

### 9. 司机管理

- 字段：姓名、手机、照片、会说的语言（主数据语言代码）、驾照到期日、驾龄、是否金牌司机、状态（在职 / 停用）。
- 金牌司机按平台标准审核：驾龄 10 年以上、从业 5 年以上、连续 3 年无主动责任事故。
- 驾照到期前 30 天提醒，到期后不能被派单。
- 只展示给客人：姓名、照片、语言、联系电话（用车前 24 小时起）。

### 10. 车辆管理

- 字段：车牌、车型组（主数据）、品牌车型、颜色、座位数、累计里程、营业牌照类型、保险到期日、车检到期日、状态（可用 / 维修 / 停用）。
- 在日本经营收费载客必须用营业牌照车辆（绿牌），非营业牌照车辆不能被派单。其他国家按当地要求配置。
- 里程小于 5 万公里的车自动标记为「新车」，用于校验新车附加服务。
- 保险、车检到期前 30 天提醒，到期后不能被派单。

### 11. 账号、权限与 API 设置

| 角色 | 可以做什么 |
| --- | --- |
| 管理员 | 全部，包括账号、资质、API 密钥 |
| 商品价格 | 区域、商品、服务规则、价格、调价、库存、上下架 |
| 调度 | 订单、指派、履约回传、司机、车辆 |
| 财务 | 订单（只读）、对账、发票 |
| 只读 | 全部只读 |

- 子账号用邮箱邀请，可停用；管理员至少保留一个。支持两步验证。

## 报价引擎

一次报价 = 找商品 → 校验服务规则 → 区域校验 → 命中价格规则 → 算基础价 → 叠加调价、加急、夜间、附加服务 → 校验库存 → 生成报价快照。所有符合条件的租户都参与比价：每个车型组（包车再按套餐）只返回一个价，按对外价（结算价 × (1 + 加价比例)，加价比例可按渠道和租户分别设置）排序，与最低价相差 3% 以内时评分高者为中标租户；预订后订单直接转给中标租户，自动确认。

1. **入参**：品类、城市、起点和终点（主数据 ID 或坐标）、用车时间（当地时间）、人数、行李数、方向（接送机）、套餐时长（包车）、附加服务、可选的车型组；销售端身份（`channel_id`）决定加价比例。
2. **找商品**：销售端被授权的所有租户中，同城市、同品类、已上架的商品（接送机还要同 POI）。
3. **服务规则**：下单有效期、每日服务时间、提前预订时长；不足时开了加急走加急，没开就不报价。
4. **区域校验**：禁行优先；接送机校验非机场一端，点对点起终点都要在营运区，包车校验上车点。一个点落在同一租户多个区域时，每个区域都算一遍价，取最低；点对点起、终点在不同区域时，两端区域的价格规则都算，取最低。
5. **命中价格规则**：区域 × 车型组 × 方向或套餐，启用且用车日期在生效期内；人数或行李超过车型组合的不报。
6. **基础价**：按计价模型公式；里程 + 时长模型的里程和时长用谷歌地图 Routes API 预估，按预估报价。
7. **调价**：筛出匹配的调价规则，按优先级顺序链式执行，后一步以前一步结果为基数。
8. **加急费**、**夜间费**、**附加服务**：各自独立计算后相加，不参与调价，得到该租户的**结算价**。
9. **库存**：有限库存时当日剩余 > 0；加急单另查加急库存。
10. **选中标租户**：同一车型组（包车同一套餐）在所有租户中取对外价（结算价 × (1 + 该租户适用的加价比例)）最低者为基准（观察期租户按对外价 × 1.05 参与排序）。排序价不超过基准 × (1 + δ) 的租户中，评分高者中标，评分相同比已完成订单数，再相同取排序价低者；δ 由渠道配置，0–5%，默认 3%。客人支付中标租户自己的对外价。不同币种按汇率中心的实时中央汇率折算到销售端的结算币种后再比较。
11. **对外价**：结算价 × 汇率 × (1 + 汇率缓冲) × (1 + 加价比例)，按币种取整；客人支付币种与租户结算币种不同时汇率缓冲为 1.5%，相同时为 0；加价比例不得低于渠道下限（默认 10%）。
12. **报价快照**：生成 `quote_id`，记录中标租户、结算价、加价比例、对外价和当时的规则版本，有效期 30 分钟；下单以快照为准。
13. **下单转单**：带 `quote_id` 下单并确认支付后，订单直接转给中标租户，自动确认，通过 Webhook 推送到租户调度系统；租户不能拒单。中标租户临时无法出车时先自己找车；确实无法履约时尽早点「声明无法履约」，由平台救援改派，差价和违约金按阶梯从其账单扣除（用车前 ≥ 24 小时只扣差价，2–24 小时加扣结算价 30%，< 2 小时或司机未到加扣 100%）。其他情况平台不改派。中标租户名称只在支付成功后对销售端可见。

**计价公式**

固定一口价：

```latex
P_{base} = \text{基础价}
```

里程 + 时长（D 为预估里程，T 为预估时长，来自谷歌地图 Routes API；按预估报价，不按实际里程结算）：

```latex
P_{base} = \max\Big(P_{min},\; P_{start} + \max(0, D - D_{start}) \cdot p_{km} + \max(0, T - T_{start}) \cdot p_{min}\Big)
```

包车套餐（报价时 H = 套餐时长，超时超公里在履约后按实际结算）：

```latex
P_{base} = P_{pkg} + \max(0, H - H_{pkg}) \cdot p_{hour} + \max(0, D - D_{pkg}) \cdot p_{km}
```

总价：

```latex
P_{total} = \mathrm{Adjust}(P_{base}) + F_{urgent} + F_{night} + \sum F_{addon}
```

中标与对外价（m 为该渠道对该租户适用的加价比例，FX 为换算到客人支付币种的汇率）：

```latex
P_{sell,t} = P_{total,t}\cdot FX\cdot(1+b)\cdot(1+m_t),\qquad R_t = P_{sell,t}\cdot(1+0.05\cdot[observation_t]),\qquad winner = \arg\max_{t:\,R_t\le(1+\delta)\min R}(score_t,\ completed_t,\ -R_t)
```

**取整规则**：每一步用高精度小数计算，只在最后按币种小数位四舍五入；租户可另设取整单位（如 JPY 取整到 100）。价格明细的各项之和必须等于总价，尾差计入调价项。

**时区**：服务时间、夜间时段、出行日期、加急小时数都按服务城市当地时间计算；跨天时段（22:00–06:00）要单独处理。

**性能**：单次报价 P95 ≤ 300 ms；价格规则和区域多边形要缓存，租户改规则后 1 分钟内生效。

## API 通用约定

API 分三组：平台管理 `/platform/v1`、租户配置 `/tenant/v1`、销售端 `/sales/v1`；三组共用一套约定，全部先写 OpenAPI 3.1 规格再开发，并提供沙箱环境。

| 项目 | 约定 |
| --- | --- |
| 协议与格式 | HTTPS、REST、JSON，UTF-8；字段名 snake\_case |
| 版本 | 路径带大版本 `/v1`；只加字段不升版本，删改字段升 `/v2` 并保留旧版至少 12 个月 |
| 鉴权 | 服务对服务用 OAuth 2.0 Client Credentials 换 Bearer Token（有效 2 小时）；另支持 API Key + HMAC-SHA256 签名（`X-Timestamp` + `X-Signature`，5 分钟防重放） |
| 租户隔离 | 租户端 Token 内含 `tenant_id`，服务端强制按它过滤，请求体里的 tenant\_id 一律忽略；销售端 Token 内含 `channel_id`，只能看到平台授权给它的租户 |
| 权限范围 | 按 scope 分配：`master.read`、`area.write`、`product.write`、`pricing.write`、`inventory.write`、`quote`、`order.write`、`order.read` |
| 幂等 | 所有创建类 POST 必须带 `Idempotency-Key`（24 小时内同一 key 返回同一结果） |
| 并发修改 | 资源带 `version`；PUT/PATCH 用 `If-Match` 传版本，不一致返回 409 |
| 分页 | 游标分页：`limit`（≤ 200）+ `cursor`，返回 `next_cursor` |
| 增量同步 | 列表接口支持 `updated_since`（ISO 8601） |
| 时间 | 接口里的时间一律 ISO 8601 带时区偏移；用车时间另带当地时间和时区名 |
| 金额 | 对象 `{amount: "98000", currency: "JPY"}`，金额用字符串避免浮点误差 |
| 多语言 | 请求头 `Accept-Language`；多语言字段返回 `{ja, zh, en}` 对象或按请求语言返回单值 |
| 限流 | 按 Token：报价 50 次/秒，其他 10 次/秒；超限 429 + `Retry-After` |
| 追踪 | 每个返回带 `X-Request-Id`，日志可按它查全链路 |

**错误格式**：HTTP 状态码 + `{"error": {"code": "PRICE_RULE_CONFLICT", "message": "...", "details": [...], "request_id": "..."}}`。

| 业务错误码 | HTTP | 含义 |
| --- | --- | --- |
| `VALIDATION_FAILED` | 422 | 字段校验失败，details 列出字段 |
| `PRICE_RULE_CONFLICT` | 409 | 同区域同车型同套餐日期重叠 |
| `FIELD_LOCKED` | 409 | 修改了创建后不可改的字段 |
| `PUBLISH_CHECK_FAILED` | 409 | 上架校验未通过，details 列出失败项 |
| `AREA_IN_USE` | 409 | 区域被上架商品引用 |
| `OUT_OF_SERVICE_AREA` | 422 | 地址不在营运区或在禁行区 |
| `LEAD_TIME_TOO_SHORT` | 422 | 不足提前预订时长且未开加急 |
| `SOLD_OUT` | 409 | 库存不足 |
| `QUOTE_EXPIRED` | 410 | 报价快照过期，需重新报价 |
| `ORDER_STATE_INVALID` | 409 | 当前订单状态不允许该操作 |

## API · 销售端接口（/sales/v1）

销售端的主流程是「询价 → 平台按最低结算价选中标租户并加价报价 → 下单 → 直接转给中标租户 → 状态推送」，只看得到平台授权给它的租户和已上架商品。

| 模块 | 方法 路径 | 说明 |
| --- | --- | --- |
| 主数据 | `GET /master/{type}` | 同租户端，支持 `updated_since` 增量同步 |
| 地点搜索 | `GET /places/search?q=&city=` | 搜机场、车站、POI，也支持坐标反查 |
| 商品列表 | `GET /products?city=&category=` | 已上架商品、可选车型和套餐、起价 |
| 商品详情 | `GET /products/{id}?lang=ja` | 渲染好的多语言详情 + 结构化规则 |
| 价格日历 | `GET /products/{id}/price-calendar` | 每日起价和可售状态，用于前台日历 |
| 报价 | `POST /quotes` | 每个车型组（包车按套餐）只返回最低价的一个候选，每个带 `quote_id` 和价格明细 |
| 报价查询 | `GET /quotes/{quote_id}` | 下单前确认报价仍有效 |
| 下单 | `POST /orders` | 必须带 `quote_id` 和 `Idempotency-Key`；预占库存 |
| 确认支付 | `POST /orders/{id}:confirm-payment` | 销售端收完款后调用，扣减库存、推给租户 |
| 退款试算 | `GET /orders/{id}/cancel-fee` | 按取消阶梯算应扣金额 |
| 取消 | `POST /orders/{id}:cancel` | 返回扣款和退款金额 |
| 修改 | `PATCH /orders/{id}` | 只允许改乘客信息、航班号、备注；改时间或车型 = 取消重下 |
| 查单 | `GET /orders/{id}`，`GET /orders?updated_since=` | 含司机车辆信息、履约后费用 |
| 状态推送 | Webhook 到销售端地址 | 事件见下表 |

**订单状态**：`pending_payment` 待支付 → `confirmed` 已确认（支付后自动确认并推送中标租户）→ `assigned` 已派车 → `in_service` 服务中 → `completed` 已完成；服务开始前可到 `cancelled`（按取消阶梯扣款）。租户不能拒单。

| Webhook 事件 | 触发 |
| --- | --- |
| `order.confirmed` | 租户接单或自动确认 |
| `order.rejected` | 不使用（租户不能拒单） |
| `order.assigned` | 填了司机和车辆（姓名、电话、车牌、车型） |
| `order.in_service` | 司机接到客人 |
| `order.completed` | 服务完成，含实际时长和里程 |
| `order.extra_charged` | 产生超时、超公里等费用 |
| `order.cancelled` | 任一方取消，含扣款金额 |
| `product.changed` | 商品上下架或规则变更，销售端用来刷新缓存 |

Webhook 用 HMAC 签名；销售端 5 秒内未返回 2xx 就重试，间隔 1–5–30 分钟、2–6–24 小时；事件带 `event_id` 供去重。

## 数据模型

平台表不带 `tenant_id`，所有租户表都带 `tenant_id` 并建在复合索引最前面；建议 PostgreSQL + PostGIS，租户表开启行级安全（RLS）作为第二道隔离。

## 非功能需求、分期与已确认决策

**非功能需求**

| 项目 | 要求 |
| --- | --- |
| 可用性 | 报价和下单接口月可用率 ≥ 99.9% |
| 性能 | 报价 P95 ≤ 300 ms；下单 P95 ≤ 800 ms |
| 容量 | 首期按 100 个租户、各 500 个商品、报价峰值 200 次/秒设计 |
| 安全 | 密钥只存哈希；乘客电话、邮箱加密存储，租户只在订单确认后可见；支持 IP 白名单 |
| 审计 | 所有配置变更和订单状态变更可追溯，保存 3 年 |
| 观测 | 报价失败原因统计（按错误码、租户、城市），便于发现缺价的区域和车型 |
| 多语言 | 后台中文、英文；对外内容至少日语、中文、英文、韩语 |

**分期建议**

1. **一期**：主数据（日本、韩国主要城市和机场）、租户后台、包车和接送机的完整链路、租户配置 API、销售端报价和下单 API、Webhook、自有官网作为第一个销售端接入。
2. **二期**：点对点、里程+时长计价（接谷歌地图 Routes API）、按车型的库存、履约后费用结算、对接第一个外部分销平台。
3. **三期**：全部 100 个空港城市的主数据、销售端加价规则、对账结算。

**已确认的决策**

| 问题 | 决策 |
| --- | --- |
| 销售端与租户的价格关系 | 租户报结算价，销售端按百分比加价 |
| 租户接单 | 默认自动确认，租户不能拒单 |
| 一个点落在同一租户多个区域 | 每个区域都算价，取最低 |
| 点对点起终点在不同区域 | 两端区域都算价，取最低；多租户同样取最低 |
| 包车超时费设置位置 | 只保留价格规则里的超时单价，去掉附加服务「车辆超时费」 |
| 里程+时长模型 | 用谷歌地图预估里程和时长，按预估报价 |
| 租户调度系统对接 | Webhook 推送订单 |

接单流程：客户询价 → 所有符合区域条件的租户报结算价 → 平台取最低价租户并加价后报给客户 → 客户预订后订单直接转给中标租户。

**第二轮决策**

| 问题 | 决策 |
| --- | --- |
| 结算价相同时谁中标 | 先比履约评分，再比已完成订单数，多者中标 |
| 中标租户临时无法出车 | 中标租户自己找车；订单不退回，平台不重新派单 |
| 销售端是否看到中标租户 | 显示名称，但只在支付成功后显示；报价和待支付阶段不显示 |
| 跨币种比价的汇率 | 新建汇率中心，用实时中央汇率换算（见「统一主数据」） |

履约评分的算法（如准时率、投诉率、客户评价的权重）还没定，一期可先用「已完成订单数」单独排序。

**第三轮决策**（详见《平台运营端与渠道对接 · 开发需求》）：先用自有官网实验，暂无 OTA；多币种不设单一本位币；不向租户收费、不收保证金，月结次月 20 日付款；评分低于 4.0 观察、低于 3.5 暂停；加价比例可按租户单独设置，比价按对外价取最低；不接航班数据和短信，付款用 Stripe，汇率用免费源。

**第四轮决策**：给租户付款用银行转账；租户专属加价比例对租户不可见，租户端页面和 `/tenant/v1` 接口都不返回对外价和加价比例。

**第五轮决策**：对照同类平台后做规范化修正。① 新增救援改派兜底，违约金阶梯 0 / 30% / 100%；② 中标改为 3% 价格带内评分高者中标，观察期 +5%；③ 落地时间以客人确认优先，no-show 须 5 项证据；④ 取消政策平台统一；⑤ 事后加收走 Stripe 保存的支付方式；⑥ 跨币种 1.5% 汇率缓冲、渠道最低加价 10%。细则见《平台运营端与渠道对接》的「履约保障与服务标准」。
