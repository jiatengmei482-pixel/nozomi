## 十三、需求规格：包车「途经景点区域加价」

### 13.1 背景

- NearMe 的线路价 = 同时长小时价 + 按目的地远近的档位附加费（镰仓 +¥10,500、富士山 / 日光 +¥17,500 等），同样 10 小时，去不同地方价格不同。
- NOZOMI 现状：包车下单只有上车点和下车点，区域加价也只有「上车加价」「下车加价」。客人从新宿出发、去富士山转一圈又回新宿，平台只看到「新宿→新宿」，只报市内价；只有把下车点设在富士山才会加价。
- 目标：客人在下单时加上途经景点，平台按景点所在区域加价，得出一口总价。

### 13.2 核心规则

1. 包车订单增加「途经景点」，选填，每单最多 10 个，每个带经纬度。
2. 供应商在「区域加价」里给每个加价区域多填一栏「途经加价」，和上 / 下车加价一样按「车型组 × 套餐」填。
3. 每个途经景点先匹配区域：落在哪个加价区域，就归哪个区域。
4. **同一区域只算一次**：多个途经景点落在同一区域，只加一次该区域的途经加价。
5. 不同区域各自累加：同一单去了镰仓和箱根，就加镰仓 + 箱根。

**总价公式**

> 总价 = 套餐价 + 上车加价 + 下车加价 + Σ（每个被途经景点命中、且没有因上 / 下车已计价的区域的途经加价），再过调价规则和平台加价。

### 13.3 边界规则（建议值，需产品确认）

| 情况 | 建议规则 | 原因 |
|---|---|---|
| 途经景点在商品的服务区域内（如东京市） | 不加价 | 与上 / 下车规则一致 |
| 途经区域与上车或下车是同一个区域 | 不再加途经加价，只按上 / 下车加价算 | 避免「下车在河口湖 + 途经河口湖」重复收费 |
| 一个景点同时落在多个重叠的加价区域 | 只归一个区域：取途经加价最高的那个（或按区域排序优先） | 避免一个点被收两次 |
| 途经景点不在任何区域（既不是服务区域也不是加价区域） | 不在线报价，转客服人工报价 | 与现有「地址没有在线报价」一致 |
| 没填途经景点 | 按现有规则报价 | 保持兼容 |
| 下单后客人改途经景点 | 重新报价，补差或退差 | 价格跟行程走 |
| 当天临时去了新区域 | 司机走现有「服务后加收」流程，按该区域的途经加价提交，客人 48 小时内可异议 | 不增加新流程 |

### 13.4 算例（按当前新商品配置，结算价）

假设「富士山地区-01」途经加价 ¥10,000、「镰仓」区域途经加价 ¥6,000（待建），经济 7 座 10 小时套餐 ¥55,000：

| 行程 | 命中区域 | 结算价 | 客人价（×1.1） |
|---|---|---|---|
| 新宿 → 五合目 → 河口湖 → 忠灵塔 → 新宿 | 富士山（3 个点，只算 1 次） | ¥55,000 + ¥10,000 = ¥65,000 | ¥71,500 |
| 新宿 → 鹤冈八幡宫 → 镰仓大佛 → 新宿 | 镰仓（只算 1 次） | ¥55,000 + ¥6,000 = ¥61,000 | ¥67,100 |
| 新宿 → 镰仓大佛 → 河口湖 → 新宿 | 镰仓 + 富士山 | ¥55,000 + ¥6,000 + ¥10,000 = ¥71,000 | ¥78,100 |
| 新宿 → 五合目 → 河口湖站（下车） | 下车已在富士山，途经不再加 | ¥55,000 + ¥10,000（下车） = ¥65,000 | ¥71,500 |
| 新宿 → 浅草 → 新宿 | 均在服务区域 | ¥55,000 | ¥60,500 |

### 13.5 界面改动

**客人下单页（包车）**

- 上车点下方增加「途经景点（选填）」：搜索或地图选点，可拖动排序，可删除。
- 车型报价卡片里展示价格明细：套餐价、上 / 下车加价、「途经 富士山地区 +¥xx」。
- 提示文字：「价格按您填的途经景点计算；当天临时去其他区域可能会加收」。

**供应商后台（价格规则 → 区域加价）**

- 表格在「上车加价」「下车加价」后增加「途经加价」列；批量设置弹窗同步增加这一项。
- 「这一行的意思」提示增加途经规则的说明和例子。

**订单与司机端**

- 订单详情保存途经景点列表和价格明细，发给调度和司机。

### 13.6 数据结构（草案）

- 区域加价记录：增加 `waypoint_surcharge`（按车型组 × 套餐）。
- 订单：增加 `waypoints[]`（顺序、名称、经纬度、命中区域 ID）和 `price_breakdown[]`（类型：套餐 / 上车 / 下车 / 途经，区域 ID，金额）。
- 报价算法：每个途经点 → 匹配加价区域（重叠时取加价最高）→ 得到区域集合并去重 → 去掉服务区域和已因上 / 下车计价的区域 → 累加途经加价。

### 13.7 与「推荐线路」结合（对标 NearMe 线路页）

- 在商品详情里维护结构化的「推荐线路」：名称、建议套餐、按顺序的途经景点（带坐标）、示例时刻表。
- 客人点「按这条线路预订」，自动带入套餐和途经景点，走同一套算法出价，效果等同 NearMe 「线路价 = 小时价 + 附加费」，但客人还能自己增减景点。

### 13.8 建议先画的加价区域（参照 NearMe 档位）

| 区域 | NearMe 附加费（客人价） | 我方途经加价建议（结算价） |
|---|---|---|
| 横滨 / 川崎 | +¥3,500 | ¥3,000 |
| 镰仓·江之岛 | +¥10,500 | ¥6,000–¥9,000 |
| 箱根 | —（NearMe 无此线） | ¥8,000–¥10,000 |
| 富士五湖 / 富士山 | +¥17,500 | ¥10,000–¥15,000 |
| 日光 | +¥17,500 | ¥10,000–¥15,000 |
| 轻井泽 | +¥17,500（推算） | ¥15,000（现有） |
| 川越 | +¥0 | 不加 |

现有「富士山地区-01」的多边形画得较大，上线前建议拆成「富士五湖」「箱根」等小区域，分别定价。

### 13.9 验收用例

1. 3 个途经点都在富士山区域 → 只加 1 次。
2. 途经镰仓 + 富士山 → 两个区域各加 1 次。
3. 下车在富士山、途经也在富士山 → 只加下车加价。
4. 途经点在东京市内 → 不加价。
5. 途经点不在任何区域 → 不出在线价，转人工。
6. 一个点落在两个重叠区域 → 只按加价最高的那个收 1 次。
7. 不填途经点 → 报价与现在完全一致。
8. 下单后删除一个途经区域 → 重新报价并退差。

## 十四、为支持途经加价，产品框架需要的调整

### 14.1 现有框架（按后台实际结构整理）

| 层 | 现状 | 对途经加价的限制 |
|---|---|---|
| 区域 | 属于一个城市；业务类型（通用 / 接送机 / 点对点 / 包车）；用途（运营 / 报价 / 运营+报价） | 只有「能不能接」和「按什么价」两种含义，没有「去了要加钱」的目的地含义 |
| 商品 | 城市、品类创建后不可改；服务区域 + 车型组 | 客人上车点所在城市必须等于商品城市（河口湖属山梨，东京商品接不到） |
| 价格 | 基础价（区域 × 车型 × 套餐）+ 区域加价（上车 / 下车两栏）+ 调价规则 | 加价触发点写死为上车和下车；多区域时取最低价 |
| 订单 / 报价 | 上车点、下车点、时长、人数；报价 30 分钟有效 | 没有途经点字段，价格没有明细 |
| 内容 | 行程路线是自由文本 | 无法把「推荐线路」变成可下单的行程 |
| 履约 | 服务后 24 小时内提交超时、超公里加收 | 临时去新区域没有对应的加收类型 |

### 14.2 调整一：区域增加「目的地加价区」用途，允许跨城市

- 区域用途从 3 种变为 4 种：运营 / 报价 / 运营+报价 / **加价区**。
- 加价区只用来「判断去没去、加多少」，不决定能不能接单、不带基础价。
- 加价区**不受城市限制**：东京的包车商品可以引用山梨的「富士五湖」、栃木的「日光」、长野的「轻井泽」。
- 区域库做成平台公共库（后台已有「从共享库引用」入口），景点区域由平台统一画，各供应商只填价，避免每家画的边界不一致。

### 14.3 调整二：包车商品从「城市」改为「出发城市 + 可达范围」

- 商品的「城市」含义改为**出发城市**（车队所在地，决定时区和币种）。
- 新增**可达范围** = 服务区域 + 加价区的合集：上车、下车、途经点都在可达范围内，这个商品才参与报价。
- 报价时不再用地址的行政城市来筛商品，而是用「坐标是否落在商品的可达范围」来筛。这样既能解决途经点，也能解决现在河口湖上车报不出价的问题。
- 「上车点必须在服务区域」是否放宽为「可以在加价区」，由供应商在商品里开关控制（默认允许，按上车加价收费）。

### 14.4 调整三：价格模型从「上 / 下车两栏」改为「加价项 + 触发点」

每条区域加价记录由「区域 × 车型组 × 套餐」下的三个金额组成：

| 触发点 | 触发条件 | 去重 |
|---|---|---|
| 上车加价 | 上车点在该区域 | — |
| 下车加价 | 下车点在该区域 | — |
| 途经加价（新增） | 任一途经点在该区域 | 同一区域只计一次；该区域已因上 / 下车计价则不再计 |

- 计价引擎改为输出**价格明细**（套餐、各区域加价、调价、平台加价），而不是只给一个总数。
- 计价顺序固定：套餐价 → 上 / 下车加价 → 途经加价 → 调价规则 → 平台加价（现为 ×1.1）。
- 「多区域取最低价」只用于基础价（服务区域之间）；加价区重叠时，一个点只归一个区域（取加价最高或按优先级）。
- 长期可加第二种策略：等「路线预估」上线后，按包含途经点的预估公里提前算超公里费。两种策略由供应商二选一，初期只做区域加价。

### 14.5 调整四：订单从「两个点」改为「有序行程点列表」

- 包车订单的行程 = 上车点 → 途经点 1…N → 下车点，每个点记录名称、坐标、命中区域。
- 报价时把行程点和价格明细一起锁定 30 分钟；下单后保存当时用到的规则快照，以后改价不影响已下的单。
- 改行程 = 重新报价，按明细差额补收或退款。
- 接送机、点对点沿用同一个行程点结构（点对点未来的「经停点」也能复用）。

### 14.6 调整五：新增平台级「线路库」

- 线路 = 名称 + 出发城市 + 建议套餐 + 有序途经点 + 图文和示例时刻表 + 多语言内容。
- 放在**平台级**，不放在单个商品里：客人付款前不知道是哪家供应商，线路页只是「带好途经点的下单入口」，价格由各供应商的加价规则实时算出，取最低价成交。
- 线路页同时是 SEO 落地页，对标 NearMe 的 tours/plans 页。商品详情里的「行程路线」自由文本可以逐步下线。

### 14.7 调整六：履约与加收

- 司机端和调度单显示完整行程点。
- 「服务后加收」增加一种类型：**新增途经区域**。司机选区域，金额按商品的途经加价自动带出，不允许手填，减少争议。

### 14.8 改动量与分期

| 阶段 | 内容 | 依赖 |
|---|---|---|
| 第一期 | 区域加价增加「途经加价」列；下单页增加途经点；订单保存行程点和价格明细；去重规则 | 无，沿用现有区域和商品 |
| 第二期 | 「加价区」用途和跨城市引用；报价按可达范围筛商品；平台公共景点区域库 | 报价匹配逻辑改造 |
| 第三期 | 平台线路库 + 线路落地页；服务后加收新增「途经区域」类型；路线预估公里策略 | 路线预估功能 |

第一期即可让「新宿 → 富士山 → 新宿」按富士山加价出价；不填途经点的订单报价与现在完全一致。
