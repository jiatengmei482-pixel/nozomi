# NOZOMI 包车报价逻辑规格（开发版）

Nov 14, 2026 · @中村

## 一、结论：总价公式与三层区域

包车总价由四部分相加，各算各的，互不抵消。车辆一律从东京市区出库、回东京市区归库，所以上车加价 = 出库空驶费，下车加价 = 归库空驶费。

```latex
\text{总价} = \text{套餐价} + \sum_{\text{经停涉及的每个行程区域}} \text{行程加价} + \text{上车加价} + \text{下车加价} + \text{超公里费} + \text{司机语言等附加}
```

以上都是结算价；前台售价 = 结算价 × 1.1。超时费不在下单时收，由供应商服务后提交。

| 层 | 是什么 | 用什么点判断 | 收费规则 |
| --- | --- | --- | --- |
| ① 基础价区域 | 东京市内、羽田机场等「按套餐价就能接」的范围 | 上车点、下车点 | 在这里上下车不加钱。套餐价整单只算一次，就是东京市内价格，显示多少就是多少 |
| ② 行程区域 | 富士山、箱根、镰仓等景区 | 经停点 | 每个区域一单只收一次；不同区域叠加；**上车或下车在同一区域也照收，不抵消** |
| ③ 上下车加价区域 | 离东京市区远、需要空驶的范围 | 上车点、下车点 | 上车点在区域内收一次上车加价，下车点在区域内再收一次下车加价；上下车在同一区域也各收一次 |

### 四个标准场景（10 小时包车）

| 场景 | 公式 | 加价合计 |
| --- | --- | --- |
| 东京往返富士山 | 东京市内 10h 套餐价 + 富士山行程 | 10,000 |
| 东京上车 → 富士山下车 | 套餐价 + 富士山行程 + 富士山下车 | 20,000 |
| 富士山上车 → 富士山游玩 → 富士山下车 | 套餐价 + 富士山行程 + 富士山上车 + 富士山下车 | 30,000 |
| 富士山上车 → 箱根游玩 → 富士山下车 | 套餐价 + 箱根行程 + 富士山上车 + 富士山下车（不收富士山行程） | 30,000 |

第四个场景说明：行程加价只看**经停点**在哪个区域，不看上下车点。富士山只是上下车地点，游玩在箱根，所以只收箱根行程。

## 二、报价流程

[embedded content: 包车报价流程 · 6 步]

商品匹配只看上车点和下车点；行程加价只看经停点；三层加价各自算完后相加，互不抵消。

## 三、各步规则

### 步骤 1：匹配商品（决定用哪个城市的套餐价）

- 一个商品参与报价的条件：**上车点和下车点都落在该商品的①基础价区域或③上下车加价区域内**。
- 不再用「上车点所属城市」来筛商品。例：河口湖在东京包车的富士山上下车加价区域内，就应由东京包车报价，套餐按东京市内价。
- 经停点不影响匹配，只影响行程加价；但经停点不在任何①②③区域内时，该商品不报价（转人工）。
- 多个商品都能报时，平台展示同一车型下**总价最低**的一个。

### 步骤 2：算预计用时 T 和全程公里 D

- 路线：上车点 → 各经停点（按客人填的顺序）→ 下车点，用地图路径接口算每段行驶时间和公里。不含出库、归库空驶（空驶由上下车加价覆盖）。
- T = 行驶时间 + 各经停停留时长 + 经停数 × 每站默认占用（建议 15 分钟）+ 整单缓冲（建议 60 分钟）。默认占用和缓冲做成商品级配置。
- 经停数量不设业务上限，只受路径接口技术上限约束。

### 步骤 3：选套餐

- 候选：该商品中时长 ≥ T 的所有套餐（T 超过最大套餐时，候选只有最大套餐）。
- 对每个候选算：套餐价 + max(0, D − 套餐含公里) × 超公里单价，**取最低的**。不要只按时长取最小套餐。
- 客人可以手动改成更长的套餐，不能改成短于 T 的。
- 不同商品各自选自己的套餐、各自算总价，再比价（现在平台是先统一定一个套餐时长，只有含这一档的商品才能比价，需要改）。

### 步骤 4：算三层加价

按下面的伪代码。每个点在同一层里**只会落在一个区域**（后台保证同层不重叠，见第四节）。

```
// ③ 上下车加价：上、下车各算各的，同一区域也各收一次
function 上下车加价(点, 方向):
    if 点 在任一 ①基础价区域: return 0          // 基础价区域优先
    区 = 点所在的 ③上下车加价区域
    if 区 不存在: 商品不报价
    return 区.加价[方向]                         // 方向 = 上车 | 下车

// ② 行程加价：只看经停点，同区域一单一次，与上下车无关
已收区域 = 空集合
行程加价 = 0
for 经停点 in 所有经停:
    if 经停点 在任一 ①基础价区域: continue    // 市内经停不加价
    区 = 经停点所在的 ②行程区域
    if 区 不存在: 商品不报价
    if 区 不在 已收区域:
        行程加价 += 区.加价
        已收区域.add(区)
    // 注意：不要因为上车点或下车点也在这个区域就跳过

// 下车点行程加价：没有市外经停时，下车点所在行程区域算一次经停（商品级开关，默认开）
if 商品.下车点行程加价开关 and 已收区域 为空:
    if 下车点 不在任一 ①基础价区域:
        区 = 下车点所在的 ②行程区域
        if 区 存在: 行程加价 += 区.加价          // 不看上车点

总加价 = 上下车加价(上车点, 上车) + 上下车加价(下车点, 下车) + 行程加价
```

- 下车点行程加价（已确认）：如果本单没有落在基础价区域以外的经停点（没填经停点，或者经停点都在东京市内这类基础价区域里），并且下车点落在某个行程区域内，就把这个行程区域算作一次经停，收一次行程加价。只看下车点，不看上车点。每个商品可以单独开关，默认打开。原因：只按「没填经停」判断，客人加一个浅草这样的市内经停就能少付；上车点不算，是因为从景区上车回东京基本等于单程接送，上车加价已包含空车开过去的成本。规格场景「河口湖上车 → 芦之湖 → 河口湖下车」不受影响：芦之湖是市外经停，照旧不收富士山行程加价。
- 价格明细逐项列出：套餐 / 上车加价（区域名）/ 下车加价（区域名）/ 行程加价（区域名，第几个经停）/ 超公里费。

### 步骤 5：超限提醒

- T > 12 小时或 D > 360 公里：在行程时间表下提醒客人缩减行程、减少经停，仍可下单。
- T > 13 小时：不允许在线下单，转客服（司机日勤拘束时间法定 13 小时以内）。
- 两个阈值做成商品级配置。提醒文案见《NOZOMI 包车开发需求》需求四。

### 不变的业务规则

- 包车从预约上车时间开始计时，占用全部时长，没有免费等待。
- 不设航班号字段、不校验航班，需要时写在备注。
- 报价含高速费、停车费，服务后不再另收。

## 四、区域数据模型与后台校验

把「区域在商品里当什么用」从现在的两种（服务区域 / 区域加价）改成三种，每种单独配置。

### 1. 商品里的区域角色

| 角色 | 后台入口 | 填什么 | 空值含义 |
| --- | --- | --- | --- |
| ① 基础价区域 | 基础信息 → 服务区域（现有） | 不填加价；套餐价按商品统一 | — |
| ② 行程区域 | 价格规则 → 行程加价（新） | 行程加价（可按车型组） | 经停在此不报价 |
| ③ 上下车加价区域 | 价格规则 → 上下车加价（现有「区域加价」改名） | 上车加价、下车加价（可按车型组） | 在此上下车不报价 |

- ②和③是两张独立的表：同一个地理区域（如「富士山」）可以同时加入两张表，金额各自填；也可以只加一张。
- 也允许②和③用不同的地理区域：②用小范围景区（华严瀑布、河口湖），③用按距离划的大范围。
- 当前「区域加价」里的「途经加价」列迁移到②行程加价表。
- 套餐价不再按「服务区域 × 车型组 × 套餐」填，改为按「车型组 × 套餐」填一次（处处都是东京市内价）。现在每个服务区域都要重复填，漏填就报不出价。

### 2. 保存和上架时的校验

1. **同一商品、同一层的区域不能重叠**：①与①、②与②、③与③。重叠时保存拦下，提示重叠的区域名和面积。
2. **①与③不能重叠**（上下车点只能有一个答案）。①与②、②与③可以重叠。
3. **同一区域不能既是①又是③**：现在东京包车出过这种配置，导致保存卡在「有 N 条未保存」。
4. **上架检查增加「覆盖检查」**：可配置一份城市热门景点坐标清单，上架前列出不在任何区域的景点。
5. **加价表有空格时提示**：空格 = 不报价，容易是漏填。

### 3. 区域编辑器建议

- 提供「从本区域减去另一个区域」的操作，用来切掉重叠。现在只能手工粘贴坐标切割。
- 「在地图上看全部」页面按商品和层筛选，并把重叠部分标红。
- 区域详情显示「在哪些商品里当什么用」（①/②/③）。
