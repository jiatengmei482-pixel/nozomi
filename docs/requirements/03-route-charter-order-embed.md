# 线路式包车、统一订单格式、嵌入预订组件 · 开发需求

- 来源：业主 2026-11-13 的新需求（下面「业主原话」逐字保留），**优先级高于其他 roadmap 项**。
- 技术方案：ADR 0087（`docs/adr/0087-route-charter-order-format-embed.md`）。可行性结论（报价接口能不能直接收总时长和总公里）写在 ADR 第一节。
- 与另两份需求的关系：《用车报价服务平台》（01）、《平台运营端与渠道对接》（02）的规则全部继续有效；本文只**增加**销售端（官网）的入口和订单上的记录，不改报价引擎、价格规则、比价、结算、取消政策。两份文档末尾的「第 N 轮决策」与本文冲突时，以本文末尾「待业主确认」的业主答复为准，答复前按推荐项做。
- 进度：roadmap 里程碑 M9（线路包车与嵌入预订）。

## 业主原话

> 【新需求·业主已确认，优先级高于其他 roadmap 项】原则：后台报价逻辑不改，销售端收集条件→换算成报价引擎现有输入→原样展示引擎价格→标准化下单，全部在主站框架内。① 线路式包车：客人填出发时间、上车点、途经点（每点停留时长必填，30 分钟一档）、下车点、人数行李；Google 路线算各段行驶时间和公里；总时长=行驶+停留，总公里=各段之和；途经点只算距离和时间，不加钱、不触发区域加价，加价只看上车点和下车点；交给现有包车产品报价（时段套餐、含公里、价格、超时价、超公里价、上车点加价、下车点加价）出每个车型最终价，显示明细和行程时间表；超范围转人工报价；后台可配模型线路（预填地点和停留时长）；先确认报价接口能否直接收总时长和总公里，不能就只在销售端用引擎规则单价拼总价，引擎不改。② 统一订单格式：主站 /book、模型线路、嵌入组件共用，含地点列表、停留时长、锁定报价编号、渠道来源。③ 嵌入组件：一行脚本 + NozomiBooking.init({key, root, lang, services, redirectUrl})，区间/包车两个 tab，Shadow DOM 隔离样式，提交跳主站 /book；嵌入码绑定域名白名单，后台生成嵌入代码（参照 Good Journey widget.js 用法：一个容器+脚本+init，提交后跳完整预订页）。顺序：先写需求/ADR 走独立审查，再分 PR：订单格式→线路包车→嵌入组件；每步 PR→独立审查→合并→部署→测试站验收。验收：三个入口同条件报价与引擎一致；在演示站 embed-demo.moveglobal.io（MoveGlobal 工厂站点 ID 73，需加入白名单；该站 Good Journey 企业 ID 是占位值）嵌入组件，区间和包车各用 Stripe 测试卡完整下一单；非白名单域名被拒。

## 总原则（所有部分都适用）

| 编号 | 原则 | 怎么检验 |
| --- | --- | --- |
| P1 | 报价引擎（`packages/domain/src/quote.ts`、`pricing.ts` 的计算）一行不改；价格规则、调价、比价、中标、加价、汇率、取整都不改 | 现有报价兼容样例（`quote-compat`，888 个）逐分一致；引擎文件在 M9 的 PR 里没有改动（代码审查核对 diff） |

## 第一部分：线路式包车

### 1.1 客人填什么

在主站 `/book` 的「包车」标签里新增「按行程」方式（现有的「按时长」选套餐方式保留，见待确认 Q6）。

| 字段 | 规则 |
| --- | --- |
| 出发时间 | 城市当地日期 + 时间（`YYYY-MM-DDTHH:mm`），沿用现有包车的日期时间输入 |
| 上车点 | 必填；地址框同现有（输入即提示、地图选点），得到名称 + 坐标 |
| 途经点 | 0～8 个（上限见 Q3）；每个有名称 + 坐标 + **停留时长（必填）** |
| 停留时长 | 30 分钟一档：30、60、90 …… 480 分钟（上限见 Q3）；不能为空、不能是 0、不能不是 30 的倍数 |
| 下车点 | 必填（同现有包车，ADR 0073） |
| 人数、行李 | 同现有（人数 1–60，行李 0–60） |
| 附加服务 | 同现有（原样交给引擎） |

### 1.2 系统怎么算（销售端换算，引擎不改）

1. **各段路线**：上车点 → 途经点 1 → … → 下车点，每相邻两点一段，用现有路线预估（谷歌 Routes，ADR 0042：不按实时路况、坐标取整到 3 位小数缓存 7 天、每日上限 `GOOGLE_ROUTES_DAILY_LIMIT`）。每段得到米数、分钟数（四舍五入到分钟，ADR 0042）。
2. **总行驶时间** = 各段分钟数之和；**总停留时间** = 各途经点停留之和；**总时长 T** = 两者相加（分钟）。
3. **总公里 D** = 各段米数之和（米，整数）；显示时向上取整到 0.1 公里（同 ADR 0073 的写法）。
4. **选套餐时长 H**：这个城市官网能卖的包车套餐时长（`GET /site/v1/cities/{id}/charter-packages` 的同一口径）里，**满足 H × 60 ≥ T 的最小那个**。例：可选 4、8、10 小时，T = 310 分钟 → H = 8；T = 480 分钟 → H = 8（正好等于也算）；T = 481 分钟 → H = 10。
5. **询价**：把「上车点、下车点、出发时间、H、人数、行李、附加服务」原样交给现有包车询价（和 `POST /site/v1/quotes` 同一个内部流程）。**途经点不交给引擎**，所以途经点不参与区域判断、不触发区域加价、不受禁行区影响；加价只看上车点和下车点（ADR 0073 的现有规则）。
6. **某个车型组在 H 报不出（这个车型的供应商没有 H 这个套餐，原因 `NO_PRICE_RULE`）**：这个车型组按更大的下一个套餐再询一次，最多再试 2 个更大的套餐；每个车型卡片写明自己用的套餐时长。
7. **对外价**：每个车型显示引擎给的对外价，不加不减（P2）。这就是客人现在付的钱。
8. **超公里预估**（显示方式见 Q1，按推荐项 A 写）：中标价格规则的套餐含公里数 K；预计超出公里 Z = max(0, ⌈(D − K × 1000) ÷ 1000⌉)（向上取整到 1 公里，同 ADR 0073 的 `overKm`）；**预计另收** = Z × 超公里对外单价（对外单价按这一单的汇率、缓冲、加价比例单独换算、单独四舍五入，同 ADR 0073 `over_km_per_km` 的口径）。只是预估，不收款；服务后按实际公里由供应商提交、走现有服务后加收流程（ADR 0029：先通知、48 小时可异议、Stripe 保存的支付方式扣款）。
9. **超时**：因为 H 是覆盖 T 的最小套餐，预计超时永远是 0；卡片上只写超时对外单价「超出套餐时长按每小时 ¥X 服务后收取」。

### 1.3 页面显示

每个能报价的车型卡片：

- 对外价（一口价，大字），「已含高速费、停车费」（ADR 0070 的现有说法）；含区域加价时写「含区域加价」（ADR 0073，不写金额）。
- 套餐：「8 小时套餐 · 含 150 公里」。
- 本行程：「约 5 小时 10 分（行驶 2 小时 40 分 + 停留 2 小时 30 分）· 约 120.3 公里」。
- 预计另收（只在 Z > 0 时）：「预计超出 34 公里 × ¥440 ≈ ¥14,960，服务后按实际公里收取」；Z = 0 时写「本行程预计不超出套餐公里」。
- 服务后价格：「超时 ¥5,500 / 小时 · 超公里 ¥440 / 公里」（对外单价）。

页面另有「行程时间表」（所有车型共用）：

| 序号 | 地点 | 到达 | 停留 | 出发 | 下一段 |
| --- | --- | --- | --- | --- | --- |
| 1 | 上车点 | — | — | 09:00 | 40 分 · 25.1 公里 |
| 2 | 途经点 1 | 09:40 | 60 分 | 10:40 | 70 分 · 60.0 公里 |
| 3 | 途经点 2 | 11:50 | 90 分 | 13:20 | 50 分 · 35.2 公里 |
| 4 | 下车点 | 14:10 | — | — | — |

- 时间都是城市当地时间；过了午夜的写「次日 01:10」（跨两天写「第 3 天 …」）。
- 时间表下注明「行驶时间按谷歌路线预估，不含实时路况；实际以司机安排为准」。

### 1.4 转人工报价（「超范围」）

以下任一情况不给在线价，显示现有的「这个地址暂时没有在线报价，请联系客服」+ 人工报价留资表单 + WhatsApp 按钮（ADR 0076）：

| 情况 | 原因代码（给页面） |
| --- | --- |
| T 大于这个城市能卖的最大套餐时长（例：最大 10 小时，T = 601 分钟） | `ROUTE_TOO_LONG` |
| 这个城市没有任何能卖的包车套餐 | `NO_PRODUCT`（现有） |
| 任一段谷歌说没有可行驶的路线 | `NO_ROUTE`（现有） |
| 路线服务暂时不可用（超时、到了每日上限等） | `TEMPORARILY_UNAVAILABLE`（现有；页面同时提供「稍后再试」） |
| 引擎所有车型都报不出（上车点或下车点不在区域等，现有原因） | 现有原因 |

人工报价留资带上途经点和停留时长（放在已加密的行程内容里，ADR 0076 的加密口径，不加明文列）。

### 1.5 下单

- 客人选一个车型 → 进入现有的填写信息、付款（Stripe）流程；下单接口仍是 `POST /site/v1/orders`，带这个车型的报价编号。
- 服务端按报价编号找到这次询价时保存的行程（客人不能在下单时改途经点、停留、时间表）；订单记录统一订单格式（第二部分）。
- 订单页、确认邮件、运营订单详情、供应商订单详情、司机页、给供应商的 Webhook：都显示地点列表、停留时长和计划时间表。供应商、司机看到的没有对外价和预计另收金额（P5）。
- 改期（ADR 0029）：时间可以改，按同一个商品、同一套餐时长重新报价（现有规则）；时间表按新出发时间整体平移。途经点、停留不能在线改：联系客服或取消重下（同 `PATCH` 订单的现有限制）。

### 1.6 模型线路（后台配置）

| 项 | 规则 |
| --- | --- |
| 在哪个后台 | 平台运营后台，菜单「内容运营 → 包车模型线路」（02 文档「主数据与内容运营」一节）。供应商后台没有这项 |
| 谁能配 | 运营、超级管理员：新增、编辑、上下线；客服、只读：只能看。权限动作 `route_template.read`、`route_template.manage` |
| 字段 | 编码（链接里用，3–40 位小写字母、数字、连字符，唯一，建好后不能改）；名称（中文必填，日文、英文选填，各 ≤ 60 字）；城市；上车点、途经点（0–8 个，每个停留 30–480 分钟、30 分钟一档）、下车点（名称 + 坐标，地址框同官网）；建议出发时间（选填，HH:mm）；简介（中 / 日 / 英，选填，各 ≤ 500 字）；排序号；状态（草稿 / 已上线 / 已下线） |
| 不含 | 价格。模型线路只预填地点和停留，价格永远在客人询价时由引擎现算 |
| 客人怎么用 | `/book` 包车「按行程」上方列出这个城市已上线的模型线路（按排序号）；点一条 → 预填地点和停留，客人选日期时间、人数后询价，预填内容可以改；链接 `/book?mode=charter&route=<编码>` 直接打开 |
| 改动 | 版本号 + `If-Match`，并发修改 409；每次改动写审计 |
| 停用 | 下线后链接打开时提示「这条线路已下线」，不预填；已经下的订单不受影响（订单里存的是地点本身） |

## 第二部分：统一订单格式

三个入口交给 `/book` 的「预订条件」和订单上存的「订单行程」用同一套结构（字段清单见 ADR 0087 第四节）。

### 2.1 预订条件（入口 → `/book`）

| 字段 | 说明 |
| --- | --- |
| 版本 | `v: 1` |
| 标签 | `transfer`（区间）/ `charter`（包车） |
| 包车方式 | `route`（按行程）/ `package`（按时长，带套餐时长） |
| 出发时间 | 城市当地 `YYYY-MM-DDTHH:mm` |
| 地点列表 | 有顺序；第一个是上车点（区间是出发地），最后一个是下车点（区间是目的地），中间是途经点；每个有名称、纬度、经度；途经点带停留分钟 |
| 人数、行李 | 整数 |
| 模型线路 | 编码，可空 |
| 来源凭证 | 嵌入组件给的签名凭证，可空（第三部分） |
| 语言 | `zh` / `ja` / `en`，可空 |

- **不带任何价格、报价编号**：价格只在 `/book` 上由引擎现算。
- 链接参数：`/book?d=<预订条件的 base64url JSON>`，最长 4,000 个字符；旧参数（`from`、`to`、`date`、`time`、`pax`、`bags`、`mode`）照旧可用。
- `/book` 对预订条件**逐项校验**：不合格的那一项不预填、页面不报错（同现有链接参数的做法）；整个解不开（不是 base64url、不是 JSON、超长、版本不认识）时整份忽略。

### 2.2 订单行程（存在订单上）

| 字段 | 说明 |
| --- | --- |
| 方式 | `transfer` / `charter_package` / `charter_route` |
| 地点列表 | 同上，另加每点的计划到达、计划出发（当地时间） |
| 各段 | 每段米数、分钟数 |
| 合计 | 行驶分钟、停留分钟、总分钟、总米数 |
| 套餐 | 包车的套餐时长和含公里数 |
| 预计超出 | 超出公里数、超出分钟数（只有数量） |
| 锁定报价编号 | 下单用的 `quote_id`（订单本来就有，这里不重复存，接口里一起给出） |
| 来源 | `entry`：`book`（直接打开主站）/ `route_template`（模型线路）/ `embed`（嵌入组件）；模型线路编号；嵌入码编号和来源域名 |

- 订单行程里**没有金额**。预计另收的对外金额只存在平台侧（运营和官网可见），超时 / 超公里的结算单价存在结算价明细里（供应商可见自己的）。
- **所有新的官网订单**（区间、按时长包车、按行程包车）都写订单行程；M9 之前的订单、`/sales/v1` 渠道订单为空，显示照旧。
- 来源只是记录，**不改渠道、不改加价**：三个入口都属于官网渠道，同样的价格（P3）。

### 2.3 统一格式的验收

| # | 条件 | 操作 | 结果 |
| --- | --- | --- | --- |
| F1 | 官网区间单（成田机场 → 东京站） | 下单 | 订单行程方式 `transfer`，地点 2 个、停留都为空，来源 `book` |
| F2 | 按时长包车 8 小时 | 下单 | 方式 `charter_package`，套餐 8 小时，地点 2 个 |
| F3 | M9-02 上线前已有的订单 | 打开官网订单页、运营 / 供应商订单详情 | 订单行程为空，页面与上线前截图一致 |
| F4 | `/book?d=` 带合法预订条件（2 人 1 件、2026-12-01 09:00） | 打开 | 自动预填并询价；价格等于手填同样条件的价格 |
| F5 | `d=` 里途经点停留 45 分钟 | 打开 | 这个途经点的停留不预填，提示「停留时长按 30 分钟一档」；其余预填 |
| F6 | `d=` 不是 base64url / 超过 4,000 字符 / `v: 2` | 打开 | 整份忽略，页面正常显示空表单，没有报错弹窗 |
| F7 | 租户 A 的令牌 | 读租户 B 订单的行程 | 404（集成测试） |
| F8 | `/tenant/v1` 订单详情、给供应商的 Webhook | 读按行程包车单 | 有地点、停留、时间表；没有任何对外金额和加价比例字段（集成测试扫全部键） |
| F9 | 同一个 `Idempotency-Key` 并发提交两次 | 下单 | 只有一张单，两次应答相同；订单行程只写一次 |

## 第三部分：嵌入预订组件

### 3.1 合作网站怎么放

运营后台生成的代码（容器 + 脚本 + init，参照 Good Journey widget.js 的用法）：

```html
<div id="nozomi-booking"></div>
<script src="https://<主站域名>/embed/v1/widget.js"></script>
<script>
  NozomiBooking.init({ key: "nze_…", root: "#nozomi-booking", lang: "ja", services: ["transfer", "charter"] });
</script>
```

### 3.2 init 参数

| 参数 | 必填 | 规则 |
| --- | --- | --- |
| `key` | 是 | 嵌入码（`nze_` 开头的公开标识，**不是密钥**，写在网页源代码里本来就公开） |
| `root` | 是 | CSS 选择器或 DOM 元素；找不到时在浏览器控制台报一条错误，不渲染 |
| `lang` | 否 | `zh` / `ja` / `en`，默认用后台给这个嵌入码设的默认语言；其他值按默认语言 |
| `services` | 否 | `["transfer"]`、`["charter"]` 或两个都有（顺序就是标签顺序）；默认用后台设的；不认识的值忽略，忽略后一个都不剩时按后台设的 |
| `redirectUrl` | 否 | 付款完成后订单页上「返回原网站」链接的地址（含义见 Q7）；必须是这个嵌入码白名单里的域名下的 https 地址，否则忽略 |

### 3.3 组件长什么样、做什么

- 两个标签：「区间」（出发地、目的地、日期、时间、人数、行李）、「包车」（上车点、途经点 + 停留、下车点、日期、时间、人数、行李）。地址框有输入即提示（经主站代调，见 ADR 0087 安全一节）。
- 样式放在 Shadow DOM 里：合作网站的 CSS 影响不到组件，组件的样式也不漏到合作网站（验收用一个把 `div`、`input`、`button` 全部改成红色的页面检验）。
- 「查询价格」按钮 → 浏览器**整页跳转**到主站 `/book?d=<预订条件>`（同一个标签页），报价、选车、填写、付款都在主站完成。组件本身**不询价、不下单、不显示价格**。
- 宽度自适应容器：容器 320 px 时不横向滚动；无障碍：标签、输入框有可读的名称，键盘能走完全部操作（axe 无严重问题）。
- 脚本大小：gzip 后 ≤ 60 KB；不加载任何第三方脚本、字体、图片（只连主站）。

### 3.4 嵌入码与域名白名单（后台）

| 项 | 规则 |
| --- | --- |
| 在哪 | 运营后台「渠道 → 嵌入组件」 |
| 谁能管 | 超级管理员、运营、渠道经理：新建、改白名单、停用；只读：只看。权限动作 `embed.read`、`embed.manage` |
| 字段 | 名称（≤ 60 字）、白名单域名（1–20 个）、默认语言、默认标签、状态（启用 / 停用）、备注 |
| 域名格式 | 写成来源（origin）：`https://` + 主机名（可带端口），不带路径；统一小写；国际化域名存 punycode；不支持通配符；正式环境只收 `https://`；测试环境另外允许 `http://localhost:<端口>`、`http://127.0.0.1:<端口>`（本机调试） |

| 生效 | 改白名单、停用后 60 秒内生效（组件的配置最多缓存 60 秒） |

### 3.5 白名单防什么、不防什么（安全边界）

- **防的是**：别人把我们的组件放到没有授权的网站上（例如仿冒的旅行社网站）。浏览器里的组件第一步向主站取配置，主站只对白名单里的来源（浏览器自动带的 `Origin` 请求头，网页脚本改不了）给出允许跨域读取的应答；不在白名单的网站读不到配置，组件只显示一行「此网站未获授权使用预订组件」，不显示表单。
- **不防的是**：不是浏览器的程序可以伪造 `Origin`、`Referer`，拿到组件配置（里面没有任何秘密，只有标签、语言）。这没有危害：组件能做的事，任何人直接打开主站 `/book` 也都能做。
- **真正的下单安全**仍是主站 `/book` 和 `/site/v1` 的现有校验：报价有效期、库存、下单信息校验、限速、Stripe 付款；嵌入组件没有绕开任何一项。
- **来源记录**：组件取配置时拿到一张主站签名的「来源凭证」（嵌入码 + 来源域名 + 2 小时有效期），跳转时带到 `/book`，下单时由服务端核对签名，核对通过的订单记来源 `embed` 和来源域名；凭证缺失、过期、被篡改、嵌入码已停用或域名已移出白名单时，订单照常下，来源记 `book`，不报错。
- 嵌入码是公开标识：页面、日志里出现都没关系；要禁止某个网站用，就把它移出白名单或停用嵌入码。

## 待业主确认

答复前一律按「推荐」做；业主改答复时只改对应的常量或显示，不影响其余部分。

| # | 问题 | 选项 | 推荐 |
| --- | --- | --- | --- |
| Q1 | 预计超出的公里怎么算钱 | A. 付款金额 = 引擎价；预计超公里单列「预计另收约 ¥Y，服务后按实际收取」，另写「预计合计约 ¥X+Y」。B. 把预计超公里算进付款总价、锁定，服务后不再收这部分：订单金额就不等于报价快照，要改下单、付款、结算、取消、改期、救援差价，超出「后台不改」。C. 销售端把几个套餐（8、10 小时……）各算「引擎价 + 预计超公里」，替客人选预计合计最低的那个；付款仍按 A | **A**：完全符合「原样展示引擎价格」，钱的流程不动，金额整数；C 可以以后加 |
| Q2 | 总时长超过最大套餐 | A. 转人工。B. 按最大套餐报价 + 预计超时另收 | **A**（业主原话「超范围转人工报价」） |
| Q3 | 途经点数量、停留时长的上限 | 途经点 ≤ 8 个；停留 30–480 分钟 | 按推荐；每多一个途经点多一次谷歌路线调用 |
| Q4 | 途经点要不要在供应商的服务范围、禁行区里校验 | A. 不校验（原话「途经点只算距离和时间」）。B. 途经点也要在运营范围内 | **A**；供应商不愿意去的地方由「超公里」和人工客服把关。业主如担心远途，可加「总公里超过套餐含公里 2 倍转人工」（另定） |
| Q5 | 行驶时间要不要加缓冲（谷歌时间不含堵车） | A. 不加。B. 每段 +10% | **A**：与点对点、接送机的现有路线预估一致；页面写明「不含实时路况」 |
| Q6 | 包车标签的两种方式 | A. 「按时长」（现有）和「按行程」（新增）并存，客人切换。B. 只留「按行程」 | **A**：不打断现有包车客人；没有途经点的「按行程」等于「从 A 到 B 用的时间」 |
| Q7 | `redirectUrl` 是什么 | A. 付款完成后订单页「返回原网站」的链接，必须在白名单域名下。B. 预订页的地址（可以指到别处） | **A**：B 会让任何人把客人带到别的「预订页」（钓鱼风险）；预订页固定是主站 `/book` |
| Q8 | 组件和预订页的语言 | 组件 `zh` / `ja` / `en`；主站 `/book` 目前是中文，带 `lang` 参数待多语言上线后生效 | 按推荐；韩语随主站多语言一起做 |
| Q9 | 演示站接哪个环境 | A. 测试环境 `https://nozomi.moveglobal.io`（Stripe 测试模式）。B. 正式环境 | **A**：验收要用 Stripe 测试卡；正式环境另生成一个嵌入码 |
| Q10 | 演示站上现有的 Good Journey 组件（企业 ID 是占位值） | A. 去掉。B. 保留，和我们的组件并排 | **A**：占位 ID 的组件不能用，留着会让验收的人点错；需要业主在 MoveGlobal 工厂后台（站点 ID 73）操作 |
| Q11 | 嵌入组件来的订单要不要单独的渠道、单独加价 | A. 同官网渠道、同价，只记来源。B. 每个合作网站一个渠道 | **A**（验收要求三个入口同价）；以后要给合作网站分佣再单独定 |
| Q12 | 线路式包车开不开放给 `/sales/v1` 渠道接口 | A. 本期不开放。B. 开放 | **A**（原话「全部在主站框架内」）；接口只加字段，以后开放不影响已接入的渠道 |
| Q13 | 中标供应商要不要考虑「预计超公里」 | A. 不考虑（按套餐价比价，引擎现有规则）。B. 考虑 | **A**：B 要改引擎的比价，违背「引擎不改」；后果是偶尔中标的供应商超公里单价较高，客人在卡片上能看到单价 |
| Q14 | 嵌入组件跳转到 `/book` 还是 `/book/new` | `/book`；M8-05（`/book` 切到新页面）还没做之前，`/book` 收到预订条件 `d=` 时转到新页面 | 按推荐：合作网站的代码以后不用改 |
