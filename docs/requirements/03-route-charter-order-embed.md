# 线路式包车、统一订单格式、嵌入预订组件 · 开发需求

- 来源：业主 2026-11-13 的新需求（下面「业主原话」逐字保留），**优先级高于其他 roadmap 项**。同日业主口径纠正（监工转达）：「算出全程需要多少时间、多少公里数，给出最终报价」——客人按最终报价付款。
- 技术方案：ADR 0087（`docs/adr/0087-route-charter-order-format-embed.md`）。可行性结论（报价接口能不能直接收总时长和总公里）写在 ADR 第一节，最终价的算法和核对代码的结论在第二节。
- 与另两份需求的关系：《用车报价服务平台》（01）、《平台运营端与渠道对接》（02）的规则全部继续有效；本文不改报价引擎、价格规则、比价规则、取消政策，只在官网报价服务层把包车规则里已有的超时价、超公里价算进最终报价，并增加入口和订单上的记录。两份文档末尾的「第 N 轮决策」与本文冲突时，以本文末尾「待业主确认」的业主答复为准，答复前按推荐项做。
- 进度：roadmap 里程碑 M9（线路包车与嵌入预订）。

## 业主原话

> 【新需求·业主已确认，优先级高于其他 roadmap 项】原则：后台报价逻辑不改，销售端收集条件→换算成报价引擎现有输入→原样展示引擎价格→标准化下单，全部在主站框架内。① 线路式包车：客人填出发时间、上车点、途经点（每点停留时长必填，30 分钟一档）、下车点、人数行李；Google 路线算各段行驶时间和公里；总时长=行驶+停留，总公里=各段之和；途经点只算距离和时间，不加钱、不触发区域加价，加价只看上车点和下车点；交给现有包车产品报价（时段套餐、含公里、价格、超时价、超公里价、上车点加价、下车点加价）出每个车型最终价，显示明细和行程时间表；超范围转人工报价；后台可配模型线路（预填地点和停留时长）；先确认报价接口能否直接收总时长和总公里，不能就只在销售端用引擎规则单价拼总价，引擎不改。② 统一订单格式：主站 /book、模型线路、嵌入组件共用，含地点列表、停留时长、锁定报价编号、渠道来源。③ 嵌入组件：一行脚本 + NozomiBooking.init({key, root, lang, services, redirectUrl})，区间/包车两个 tab，Shadow DOM 隔离样式，提交跳主站 /book；嵌入码绑定域名白名单，后台生成嵌入代码（参照 Good Journey widget.js 用法：一个容器+脚本+init，提交后跳完整预订页）。顺序：先写需求/ADR 走独立审查，再分 PR：订单格式→线路包车→嵌入组件；每步 PR→独立审查→合并→部署→测试站验收。验收：三个入口同条件报价与引擎一致；在演示站 embed-demo.moveglobal.io（MoveGlobal 工厂站点 ID 73，需加入白名单；该站 Good Journey 企业 ID 是占位值）嵌入组件，区间和包车各用 Stripe 测试卡完整下一单；非白名单域名被拒。

## 第一部分：线路式包车

### 1.1 客人填什么

在主站 `/book` 的「包车」标签里新增「按行程」方式（现有「按时长」保留，见 Q6）。

| 字段 | 规则 |
| --- | --- |
| 出发时间 | 城市当地日期 + 时间（`YYYY-MM-DDTHH:mm`） |
| 上车点 | 必填；地址框同现有（输入即提示、地图选点），名称 1–240 字 + 坐标 |
| 途经点 | 0～8 个（Q3）；每个有名称 + 坐标 + **停留时长（必填）** |
| 停留时长 | 30 分钟一档：30、60 …… 480 分钟（Q3）；不能为空、不能是 0、必须是 30 的倍数 |
| 下车点 | 必填（同现有包车，ADR 0073） |
| 人数、行李、附加服务 | 同现有（原样交给引擎） |

### 1.2 最终报价怎么算（服务层换算，引擎不改；细节和代码依据见 ADR 0087 第二节）

1. **各段路线**：相邻两点一段，用现有谷歌路线预估（ADR 0042），每段米数、分钟数。
2. **总时长 T** = 各段行驶分钟 + 各途经点停留；**总公里 D** = 各段米数之和（显示时向上取整到 0.1 公里）。
3. **试哪些套餐**：城市能卖的套餐时长里，先按供应商规则预筛：超时不超过 2 小时（T − H × 60 ≤ 120 分钟，Q2），并且至少有一条这个时长的规则含公里的 2 倍不小于 D（Q4）；再从小到大取 4 个。某车型 4 个都报不出而还有更大的套餐时，为它补试，总共最多 6 轮。一个都没有 → 转人工（`ROUTE_TOO_LONG` 或 `ROUTE_TOO_FAR`）。
4. **每个套餐报一次**：把「上车点、下车点、出发时间、H、人数、行李、附加服务」交给现有包车询价，得到每个车型组每个供应商、每个商品的套餐部分价格（含上 / 下车加价、调价、加急、夜间、附加服务）；同一供应商的几个商品分别参加，不在算超时超公里之前按套餐价去掉。**途经点不交给引擎**：不参与区域判断、不触发区域加价、不受禁行区影响。
5. **每个候选加上超时、超公里**（用这个供应商这条包车规则自己的单价）：超时费 = 每小时单价 × max(0, T − H × 60) ÷ 60；超公里费 = 每公里单价 × max(0, D − 含公里 × 1000 米) ÷ 1000——与引擎包车公式同一个函数，按分钟、按米成比例（Q1）。两项结算价相加后按商品取整单位四舍五入一次；对外价按这个供应商的汇率、缓冲、加价比例从整数结算价换算、四舍五入一次。
6. **总公里过远**：某个候选 D 超过它含公里的 2 倍（Q4）时这个候选不参加；某车型所有候选都不参加 → `ROUTE_TOO_FAR`，转人工。
7. **比价**：同一车型把所有套餐、所有供应商的候选按**最终价**排序，用现有的比价规则（3% 价格带内评分高者中标、观察期 +5%）选出一个；卡片上写中标的套餐时长。订单就落在这个按最终价中标的供应商、商品和套餐时长上（可能和只看套餐价时的中标不同）。最终价超过平台金额上限的候选不参加。已知限制：一个商品的几个区域都能报时，引擎按套餐价取最低的区域，不看各区域的超公里单价不同（罕见）。
8. **最终报价**就是客人付的钱。只有当天客人自己延长停留、改线路，实际超出锁定的时长 / 公里，超出部分才服务后补收（1.6）。

### 1.3 页面显示

每个能报价的车型卡片：

- **最终报价**（大字），「已含高速费、停车费」（ADR 0070）；含区域加价时写「含区域加价」。
- 明细（对外价）：「8 小时套餐 ¥55,000 · 超时 40 分 ¥3,666 · 超公里 0 公里 ¥0 = ¥58,666」；明细各项之和等于最终报价。
- 套餐说明：「8 小时套餐 · 含 150 公里」；本行程：「约 8 小时 40 分（行驶 … + 停留 …）· 约 120.3 公里」。
- 当天超出的说明：「当天如延长停留或改变线路，超出本行程的时间按每小时 ¥5,500、超出的公里按每公里 ¥440 服务后收取」。

页面另有「行程时间表」（所有车型共用）：

| 序号 | 地点 | 到达 | 停留 | 出发 | 下一段 |
| --- | --- | --- | --- | --- | --- |
| 1 | 上车点 | — | — | 09:00 | 40 分 · 25.1 公里 |
| 2 | 途经点 1 | 09:40 | 60 分 | 10:40 | 70 分 · 60.0 公里 |
| 3 | 途经点 2 | 11:50 | 90 分 | 13:20 | 50 分 · 35.2 公里 |
| 4 | 下车点 | 14:10 | — | — | — |

- 城市当地时间；过午夜写「次日 01:10」（跨两天写「第 3 天 …」）。注明「行驶时间按谷歌路线预估，不含实时路况」。

### 1.4 转人工报价

不给在线价，显示现有的「这个地址暂时没有在线报价，请联系客服」+ 人工报价留资 + WhatsApp 按钮（ADR 0076）：

| 情况 | 原因代码 |
| --- | --- |
| T 超过最大套餐 + 2 小时（例：最大 10 小时，T = 721 分） | `ROUTE_TOO_LONG` |
| 某车型所有候选的 D 都超过各自含公里的 2 倍 | `ROUTE_TOO_FAR`（只影响那个车型；所有车型都这样时整页转人工） |
| 城市没有能卖的包车套餐 | `NO_PRODUCT` |
| 任一段谷歌说没有路线 | `NO_ROUTE` |
| 路线服务暂时不可用 | `TEMPORARILY_UNAVAILABLE`（另有「稍后再试」） |
| 引擎所有车型都报不出（现有原因） | 现有原因 |

人工报价留资带上途经点和停留（放在已加密的内容里，ADR 0076）。

### 1.5 下单、取消、改期

- 下单仍是 `POST /site/v1/orders` 带报价编号；**订单总价 = 这个报价编号锁定的最终价**（含超时、超公里明细），Stripe 收这个数。客人不能在下单时改途经点、停留。
- 取消：现有平台取消政策按订单对外价和结算价的百分比算（ADR 0029），订单价就是最终价，所以取消费按最终价算。
- 改期：按同一商品、同一套餐时长重新报价（ADR 0029）；行程不变，所以超时分钟、超出公里不变，单价按同一商品当前规则重读；新旧最终价的差额走现有改期补差价 / 退差价。时间表整体平移。途经点、停留不在线改：联系客服或取消重下。
- 救援改派：接手的供应商也按最终价（含它自己规则的超时、超公里）排序，差价按最终结算价算。
- 渠道接口 `/sales/v1` 不受影响（不提供按行程报价）。
- 订单页、确认邮件、运营订单详情、供应商订单详情、司机页、供应商 Webhook：都显示地点、停留、时间表；供应商看到的是结算价（含超时、超公里两项），没有对外价。

### 1.6 事后补收（只补超出锁定的部分）

- 能补收的只有：实际时长超过 max(套餐时长, T) 的部分、实际公里超过 max(含公里, D) 的部分。
- 走现有服务后加收（ADR 0029）：供应商在服务结束 24 小时内提交，客人 48 小时内可提异议，到期用 Stripe 保存的支付方式扣款；单笔超过对外价 50%、无凭证或有异议转人工审核。
- 供应商后台提交事后加收时，按行程的单显示锁定的 T、D、套餐时长、含公里和两项结算单价，并写明「只收超出锁定部分」。
- 按行程的单的超时、超公里加收**一律转人工审核**（新审核原因「按行程锁定用量」），不在异议期后自动扣款；运营审核页显示锁定的 T、D、套餐时长、含公里、两项单价，以及按供应商填的实际量算出的可补的量和参考金额。
- 「付款链接、客人不付现场收现金」现有流程没有（ADR 0069 第二批确认 ② 只是方案，随受阻的 M8-07 做），本期不做，见 Q15。

| 项 | 规则 |
| --- | --- |
| 在哪个后台 | 平台运营后台「内容运营 → 包车模型线路」；供应商后台没有 |

## 第二部分：统一订单格式

三个入口交给 `/book` 的「预订条件」和订单上的「订单行程」用同一套结构（字段清单见 ADR 0087 第三、四节）。

### 2.1 预订条件和预订草稿

| 字段 | 说明 |
| --- | --- |
| 版本 | `v: 1` |
| 标签、包车方式 | `transfer` / `charter`；`route`（按行程）/ `package`（按时长，带套餐时长） |
| 出发时间 | 城市当地 `YYYY-MM-DDTHH:mm` |
| 地点列表 | 2–10 个，有顺序：上车点、途经点（带停留）、下车点；名称 1–240 字、坐标 |
| 人数、行李、语言 | 整数；`zh` / `ja` / `en` |

- **不带价格、报价编号、任何客人个人信息**（姓名、电话、邮箱在 `/book` 填，不进预订条件）。
- **嵌入组件**：先把预订条件交给主站暂存成「预订草稿」，再跳 `/book?draft=<草稿编号>`。草稿编号是 256 位随机数（不可猜、不可枚举）；草稿 2 小时有效（Q16），有效期内可以反复打开（刷新、退回再进），过期后 `/book` 显示「链接已过期，请重新填写」和空白表单。草稿内容总大小 ≤ 16 KB；每个嵌入码每分钟最多建 60 个、同时有效的最多 5,000 个；过期草稿定时删除。已知限制：地点名称是自由文本，客人可能把电话等填进去；不做识别，靠 2 小时过期删除兜底，地址框提示「只填地点」。来源（哪个嵌入码、哪个网站、返回地址）由主站在建草稿时记下，客人改不了。
- **主站自己的入口**（`/book` 页内、模型线路）不建草稿，直接用页面内状态，同一套结构和校验。
- 不改测试服务器的 nginx（共用、不能 SSH）；链接只带短编号。
- 旧链接参数（`from`、`to`、`date`、`time`、`pax`、`bags`、`mode`）照旧。

### 2.2 订单行程（存在订单上）

| 字段 | 说明 |
| --- | --- |
| 方式 | `transfer` / `charter_package` / `charter_route` |
| 地点列表 | 同上，另加每点的计划到达、计划出发 |
| 各段、合计 | 每段米数、分钟；行驶、停留、总分钟、总米数 |
| 套餐、锁定量 | 套餐时长、含公里；锁定的 T、D |
| 锁定报价编号 | 订单本来就有的 `quote_id` |
| 来源 | `book` / `route_template` / `embed`；模型线路编号；嵌入码编号、来源网站、返回地址 |

- 订单行程里没有金额；最终价的组成在结算价明细（供应商可见结算价）和平台侧对外明细（官网、运营可见）。
- 所有新的官网订单都写订单行程；M9 之前的订单、`/sales/v1` 渠道单为空，显示照旧。
- 来源只是记录，不改渠道、不改加价；来源 `embed` 能被非浏览器程序伪造，**只用于统计**，不作分佣或金额依据（Q11）。来源字段只给官网订单应答和运营后台，`/tenant/v1` 和供应商 Webhook 不给。

## 第三部分：嵌入预订组件

### 3.1 合作网站怎么放

```html
<div id="nozomi-booking"></div>
<script src="https://<主站域名>/embed/widget-v1.js"></script>
<script>
  NozomiBooking.init({ key: "nze_…", root: "#nozomi-booking", lang: "ja", services: ["transfer", "charter"] });
</script>
```

### 3.2 init 参数

| 参数 | 必填 | 规则 |
| --- | --- | --- |
| `key` | 是 | 嵌入码（`nze_` 开头的公开标识，**不是密钥**） |
| `root` | 是 | CSS 选择器或 DOM 元素；找不到时控制台报错、不渲染 |
| `lang` | 否 | `zh` / `ja` / `en`，默认用后台设的；其他值按默认 |
| `services` | 否 | `["transfer"]`、`["charter"]` 或两个（顺序即标签顺序）；不认识的忽略，忽略后为空按后台设的 |
| `redirectUrl` | 否 | 付款完成后订单页「返回原网站」的地址（Q7）。≤ 2,000 字符；按 URL 解析，只收 https（测试环境另收 localhost）；不能带用户名密码；origin 必须完全等于白名单某一项、并且等于当前网站；下单时再对当前白名单核一次。不合格就忽略（不报错，没有返回链接）。全文见 ADR 0087 第六节第 2 小节 |

### 3.3 组件做什么

- 两个标签：「区间」（出发地、目的地、日期、时间、人数、行李）、「包车」（上车点、途经点 + 停留、下车点、日期、时间、人数、行李）；地址经主站代调输入即提示。
- 样式在 Shadow DOM 里，和合作网站互不影响。
- 点「查询价格」：先向主站建预订草稿，成功后整页跳到主站 `/book?draft=<编号>`；建草稿失败（未授权、太频繁、网络）就在组件里提示，不跳转。组件不询价、不下单、不显示价格。
- 容器 320 px 不横向滚动；键盘可走完；axe 无严重问题。脚本 gzip 后 ≤ 60 KB，不加载任何第三方资源。

### 3.4 嵌入码与域名白名单（后台）

| 项 | 规则 |
| --- | --- |
| 在哪 | 运营后台「渠道 → 嵌入组件」 |
| 谁能管 | 超级管理员、运营、渠道经理；只读只看。权限 `embed.read`、`embed.manage` |
| 字段 | 名称（≤ 60 字）、白名单域名（1–20 个）、默认语言、默认标签、状态、备注 |
| 域名格式 | origin：`https://` + 主机名（可带端口），不带路径；小写；punycode；不支持通配符；正式环境只收 https；测试环境另收 `http://localhost:<端口>`、`http://127.0.0.1:<端口>` |
| 生成代码 | 详情页显示 3.1 的代码和「复制代码」 |
| 生效 | 改白名单、停用后 60 秒内生效 |
| 审计 | 新建、改白名单、停用都写审计 |

### 3.5 白名单防什么、不防什么

- **防的是**：组件被放到没有授权的网站上。浏览器自动带的 `Origin` 网页脚本改不了；主站只对白名单来源（完全相等，`null` 和缺失都拒）放行跨域读取和建草稿；不在白名单的网站上组件只显示「此网站未获授权使用预订组件」。
- **不防的是**：非浏览器程序能伪造 `Origin`，拿到公开配置、建一个 2 小时的草稿（受限速和大小上限）——和直接用主站一样。所以来源记录只作统计。
- **真正的下单安全**仍是主站 `/book` 和 `/site/v1` 现有的校验。
- 嵌入码是公开标识；草稿编号不可猜、不可枚举，过期和不存在不区分。伪造 `Origin` 刷草稿受每个来源地址、每个嵌入码的限速和每个嵌入码 5,000 个有效草稿的上限约束。

## 待业主确认

答复前一律按「推荐」做；改答复时只改对应的常量或显示。

| # | 问题 | 选项 | 推荐 |
| --- | --- | --- | --- |
| Q1 | 超时、超公里怎么计费 | A. 按分钟、按米成比例（引擎包车公式本身）。B. 超时向上取整到整小时、超公里向上取整到整公里 | **A**：「超时价 / 超公里价」在引擎里就是这个公式；以后事后补收自动算建议金额也用它，两边一致 |
| Q2 | 超范围阈值 | 每个套餐最多超时 2 小时（T ≤ 最大套餐 + 2 小时）；按规则预筛后试 4 个套餐，报不出的车型补试，总共最多 6 轮 | 按推荐；超出就转人工；P95 目标 1.2 秒 |
| Q3 | 途经点数量、停留上限 | 途经点 ≤ 8 个；停留 30–480 分钟 | 按推荐 |
| Q4 | 途经点的地理范围 | A. 不限。B. 途经点必须在本城市运营范围内（运营范围是各供应商各自的，要在引擎外另做判断）。C. 总公里超过该供应商含公里的 2 倍时这家不报（全都不报转人工） | **C**：不用对途经点做区域判断，符合「途经点只算距离和时间」；远途必然体现在总公里上；倍数是常量 |
| Q5 | 行驶时间要不要加缓冲（谷歌不含堵车） | A. 不加。B. 每段 +10% | **A**：与现有路线预估一致；当天路况慢不另收，只有客人自己延长停留 / 改线路才补收 |
| Q6 | 包车标签的两种方式 | A. 「按时长」和「按行程」并存。B. 只留「按行程」 | **A** |
| Q7 | `redirectUrl` 是什么 | A. 付款后订单页「返回原网站」的链接，必须在白名单域名下。B. 预订页地址 | **A**：B 有钓鱼风险 |
| Q8 | 组件和预订页语言 | 组件 zh / ja / en；`/book` 目前中文 | 按推荐；韩语随主站多语言 |
| Q9 | 演示站接哪个环境 | A. 测试环境 `https://nozomi.moveglobal.io`。B. 正式环境 | **A**：用 Stripe 测试卡验收 |
| Q10 | 演示站现有的 Good Journey 占位组件 | A. 去掉。B. 保留 | **A**：需业主在 MoveGlobal 工厂后台（站点 ID 73）操作 |
| Q11 | 嵌入组件的单要不要单独渠道 / 加价 | A. 同官网渠道同价，只记来源。B. 每个合作网站一个渠道 | **A**；来源可伪造，只作统计；以后分佣先重新设计来源证明，另写 ADR |
| Q12 | 线路式包车开不开放给 `/sales/v1` | A. 本期不开放。B. 开放 | **A** |
| Q13 | 多个供应商时按什么比价 | A. 按最终价（含超时、超公里），比价规则不变。B. 按引擎套餐价，中标后再加超时超公里 | **A**：客人拿到最低的最终价；不改引擎（ADR 0087 第二节第 3 小节核对了代码） |
