### 规则（监工 2026-11-15）

- 互不冲突、CI 全绿、没有迁移的 PR，可以连续合并后只部署一次。
- 带迁移的 PR 要单独合并、单独部署。
- 需要在测试站验收的 PR，要等它的部署成功后再合下一个。部署只部署 main 最新的提交，前一个还没部署完就合下一个，前一个就不会单独部署了。

### 脚本

脚本在原 Codespace 的 `~/nozomi-wt/tools/` 下，不在仓库里。云端看不到，下面写出逻辑，需要时可以照着重写。

- **`merge_chain.sh <PR...>`：** 逐个处理：
  - 等 GitHub 算出能不能合并；
  - 冲突只在 `docs/progress/roadmap.json` 时，开一个临时 worktree 合并 main，用 `roadmap_merge_logs.py` 合并日志，跑 `node scripts/check-roadmap.mjs`，再推回 PR 分支；
  - 冲突不只在 roadmap 时报出来并跳过；
  - 然后等 `gh pr checks` 全部完成，三项都 pass 才执行 `gh pr merge --merge`。
- **`merge_deploy.sh <PR...>`：** 每个 PR 先走 merge_chain，然后：
  - 等合并提交在 main 上的 CI（workflow「CI」）跑完；
  - 再等在那之后创建的 `deploy.yml` 运行完成，打印各个 job 的结果；
  - 然后才处理下一个。
- **`merge_batch.sh <PR...>`：** 逐个走 merge_chain，最后只等一次部署。

停工时，后台还有几条串起来的等待脚本在跑（依次执行上面的顺序）。Codespace 一停，它们就会断掉。
