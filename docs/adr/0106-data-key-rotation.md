# ADR 0106：更换数据加密主密钥（多密钥读取和重新加密）

- 状态：已采纳（2026-11-22，M4-35）
- 依据：ADR 0057「换主密钥」一节。那一节写明：明文清掉（M4-25，ADR 0055 第 6 步）之后只认一把密钥，换密钥会让乘客信息读不出来，所以清明文之前必须先做多密钥读取。本篇就是它，同时把其他用这把密钥的数据一起纳入。
- 编号：main 上最大 0104；0103 被 PR #330 占用，0105 留给同时在做的 M4-23（备份和恢复到任意时间点），本篇用 0106。
- 负责人不参与：不新增要负责人填的密钥，平时什么都不用做。只在怀疑密钥泄露、要换的时候由开发按 `docs/deploy.md`「更换数据加密密钥」操作。

## 问题

`DATA_ENCRYPTION_KEY` 加密了这些数据：

| 数据 | 存在哪 | 密文带密钥标记 |
| --- | --- | --- |
| 乘客姓名、电话、邮箱和三个盲索引（ADR 0057） | `orders`、`order_changes`、`webhook_deliveries`、`notifications` | 有 |
| 改乘客邮箱、补发查看链接时等审核的地址 | `passenger_email_changes`、`view_link_requests` | 有 |
| 人工报价申请的联系方式、地点和客服备注（ADR 0076） | `manual_quote_requests`、`manual_quote_request_events` | 有 |
| 供应商的 Webhook 签名密钥（ADR 0027） | `tenant_webhooks` | 没有 |
| 平台员工的两步验证密钥（ADR 0030） | `platform_users` | 没有 |
| 运营后台填写的第三方密钥（ADR 0041） | `integration_secrets` | 没有 |
| 供应商的收款账号（ADR 0051） | `payout_accounts` | 没有 |

以前只认一把密钥：换了以后，上面所有数据都解不开。明文还在时乘客信息可以从明文重新加密，其余几种没有办法。

## 决定

### 1. 换的那段时间带着两把密钥

- 新增可选配置 `DATA_ENCRYPTION_KEY_PREVIOUS`（只经 `packages/config` 读取）：换密钥时把原来的 `DATA_ENCRYPTION_KEY` 放到这里，`DATA_ENCRYPTION_KEY` 换成新生成的。配置校验：要有新密钥、至少 32 个字符、不能和新密钥或登录签名密钥相同。日志打码，`config:check` 和 `/health` 只显示「正在换密钥」，没有原文。
- `SecretBox` 加密、算指纹只用新密钥；解密先试新的，再试旧的。所以重启那一刻起，所有旧密文照常能读，业务代码不用改。
- 乘客信息按密文前面的密钥标记选钥匙：新密钥的标记用新密钥解，旧密钥的标记用旧密钥解，都不报警；别的标记仍按「密钥换过」处理（有明文读明文）。
- 盲索引查找（官网查订单、运营按乘客筛选、人工报价按联系方式查）新旧两把各算一个去查，所以还没换的行照样查得到。
- `passenger-backfill --verify` 仍然只认新密钥：旧密钥的行算「解不开」。没换完就不能说「全部一致」，也就不能清明文、不能删旧密钥。

### 2. 用命令把旧密文换成新密文

`pnpm data-key:rotate`（服务器上是 `bin/compose.sh run --rm data-key-rotation`）：

- 默认 dry-run：每张表还有几行是旧密钥、几行新旧两把都解不开。`--execute` 逐行用旧密钥解开、用新密钥加密，乘客信息和人工报价的盲索引一起按新密钥重算。最后再数一遍，全部为 0 才提示可以删旧密钥。
- **用迁移账号（表的所有者）连库**：收款账号的密文列平台角色改不了（迁移 0160 的触发器，保证两人复核不被绕过）。不为它新开一个「以所有者身份执行」的数据库函数：那会让能用平台角色执行 SQL 的人改掉生效账户的密文，削弱两人复核；只在服务器上手工运行的命令才拿得到迁移账号。所以这个命令在单独的 `data-key-rotation` 容器里运行（`tools` 配置组，平时不启动），只拿迁移账号的连接串和新旧两把数据加密密钥，没有登录签名密钥和第三方密钥。
- 每张表一批一个短事务，`for update skip locked`，更新条件里再比一次旧密文：业务刚改过、锁着的行这一轮跳过，不会被旧内容覆盖。可以中断，可以反复运行。
- 带标记的表按前缀在库里选；不带标记的四种行数很少（每家供应商最多几行），逐行试解。
- 人工报价申请的去重键不重算：它是联系方式加行程要点算出的指纹，原料没有全部存下来，只在 24 小时内防重复提交有用。代价：换密钥前后 24 小时内同一个人重复提交同一行程，会多记一条。
- 输出只有表名和数量。

### 3. 不做的

- 不做后台自动换：换密钥一年也不一定有一次，手工运行、看着数量更稳妥；后台任务每小时一轮的乘客信息回填照旧（明文还在时它也会把旧密钥的行重新加密）。
- 不做「三把以上」：一次只能在换一把。上一轮没换完（旧密钥的行不为 0）不能开始下一轮。
- 不改登录签名密钥（`AUTH_JWT_SECRET`）、数据库密码的更换方式。

## 顺序和回退

1. 改 `.env`：`DATA_ENCRYPTION_KEY_PREVIOUS=<原来的>`，`DATA_ENCRYPTION_KEY=<新生成的>`，重新部署（或重启 API）。
2. `data-key-rotation`（dry-run）看数量 → `--execute` → 提示「全部换成新密钥」。
3. `passenger-backfill --verify` 全部一致。
4. 删掉 `.env` 里的 `DATA_ENCRYPTION_KEY_PREVIOUS`，重启。

回退：第 4 步之前随时可以把两行换回去（新的放回 PREVIOUS、旧的放回 KEY），再跑一次命令换回旧密钥，数据不丢。第 4 步之后旧密钥就用不到了，但**和那段时间的数据库备份一起保管到备份过期**：用备份恢复时要用备份当时的密钥。

## 测试

- 单元：`SecretBox` 带旧密钥时旧密文能解、新加密只用新密钥、`openCurrent` 只认新密钥；乘客信息按标记选钥匙、查找用的盲索引新旧各一个、核对只认新密钥；配置校验和命令的配置。
- 集成（真实 PostgreSQL）：明文不再写（第 6 步前半）的单，换上新密钥、带着旧密钥时 reveal、官网查订单、运营按邮箱筛选、人工报价按联系方式查都正常、不报警；dry-run 数得出、不改数据；`--execute` 之后乘客信息、人工报价、Webhook 签名密钥、收款账号都只用新密钥就解得开，重复运行没有可换的；删掉旧密钥后照常读和查。
- 部署结构：`data-key-rotation` 服务只在手工运行时启动，环境变量只有那三项。
