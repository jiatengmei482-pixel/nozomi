# ADR 0008：登录、令牌与会话、密码

- 状态：已采纳（2026-10-07，M0-06；同日第二轮修订：暂停租户不影响登录、增加密码找回、增加按来源地址的限速）

## 决定

### 两套账号、两套入口

- 平台员工（`platform_users`）和租户用户（`tenant_users`）是两套账号，各有一套登录接口：`/platform/v1/auth/*`、`/tenant/v1/auth/*`。同一个邮箱可以在两边各有一个账号，互不相通。
- 本期只有邮箱 + 密码登录。公司 SSO 和两步验证不在本任务范围，代码里没有它们的半成品。
- 租户用户的邮箱全平台唯一（一个邮箱只属于一个租户的一个账号），所以登录时不用选租户。

### 访问令牌 + 服务端会话

- 登录成功后签发一个访问令牌：HS256 签名的 JWT，放在 `Authorization: Bearer` 里。自己实现（`apps/api/src/auth/token.ts`，只用 `node:crypto`），不引入 JWT 库。
- 令牌分两类受众：`platform` 和 `tenant`。签名密钥由 `AUTH_JWT_SECRET` 按受众分别派生（HKDF），所以平台令牌在租户接口上连验签都过不了，反过来也一样；验签后还会再核对受众，以及「租户令牌必须带租户编号、平台令牌不能带」。
- 令牌内容：受众、用户编号、会话编号、租户编号（租户令牌）、角色、签发和过期时间。
- 令牌只是会话的凭证。每次登录在数据库里建一行会话（`platform_sessions` / `tenant_sessions`），**每个请求都回数据库核对**：会话还在且没过期、账号是「在用」。任何一项不满足都是 401。
- 因此：退出登录（删会话）、停用账号（删该账号的全部会话）、凭重置令牌改密码（删该账号的全部会话）之后，已经发出的令牌**立即失效**，重新启用后旧令牌也不会复活。
- **租户被暂停不影响它的用户登录，也不影响已有会话。** 需求文档「租户状态」规定暂停 = 商品不参与比价、已有订单继续履约，所以暂停的租户必须还能登录后台。登录响应和 `/tenant/v1/auth/me` 里的 `tenant.status` 让前端显示「已暂停」。完整的租户状态机属于 M4-01。
- 令牌的签名只接受签发时的那一种 base64url 写法（加补位、换字母表、改末位无效比特的变体都拒绝），所以一个会话只有一个合法的令牌串。
- 权限判断用数据库里的当前角色，不用令牌里的角色（令牌里的角色只给前端显示用）。改角色立即生效，不用重新登录。
- 会话 8 小时过期（需求文档对平台会话的要求；租户会话取相同的值）。**没有刷新令牌**：过期后重新登录。

### 密码

- 哈希用 Node 内置的 `crypto.scrypt`，不加原生依赖。参数 N=2^15、r=8、p=3（OWASP 给出的等强度组合之一，单次约 32MB 内存、约 0.15 秒）。
- 存储格式 `scrypt$<参数版本>$<盐>$<哈希>`。以后调高强度时新增一个版本，旧哈希仍按自己的版本验证。
- 密码先做 Unicode NFKC 归一化再哈希。
- 强度规则在 `packages/domain/src/password-policy.ts`：12 ~ 128 个字符；小写、大写、数字、其他字符至少占三类；至少 6 个不同字符；不能包含邮箱名。
- 登录失败不暴露邮箱是否存在：邮箱不存在、密码错误、账号没激活，返回完全相同的 401；邮箱不存在时也做一次同样耗时的哈希计算。只有密码正确时才会告知「账号已停用」。

### 防暴力破解

- 规则在 `packages/domain/src/login-throttle.ts`。15 分钟的固定窗口内，三个维度同时限制，超过返回 429 和 `Retry-After`：
  1. **同一来源地址（不分邮箱）最多 50 次失败**。挡住同一个地址轮换邮箱无限触发密码哈希计算、灌满审计日志。登录成功的那一次会退还，所以很多人共用一个出口地址正常登录不受影响。平台入口和租户入口各算各的。
  2. 同一邮箱 + 同一来源地址最多 5 次。登录成功后清零。
  3. 同一邮箱（不分来源）最多 20 次。登录成功后清零。
- 来源地址这一层最先检查；被它拦下的请求不再占用邮箱维度的次数（否则已经被拦下的攻击者还能继续把别人邮箱的计数顶满）。
- **被任何一层拦下的请求都不验证密码（不做哈希计算）、不写审计日志**。每一次真正验证了密码的失败都有审计记录。
- 50 这个阈值的依据：一次失败约占 0.15 秒 CPU 和一条审计记录，一个地址 15 分钟最多 50 次，即最多约 8 秒 CPU、每天最多 4800 条审计记录；而一个办公室里的人 15 分钟内输错 50 次密码基本不会发生。
- 计数存在数据库（`login_throttles`），多实例部署也有效。计数方式是「先占用一次，再验证密码」，在一条 SQL 里原子完成，并发请求绕不过去。
- 表里只存「入口 + 邮箱 + 地址」的 SHA-256，没有邮箱和地址原文。不存在的邮箱同样计数，表现与存在的邮箱一致。
- 来源地址取自连接；服务前面有反向代理时，由 `TRUST_PROXY_HOPS` 指定信任几层 `X-Forwarded-For`。默认 0：完全不看 `X-Forwarded-For`、`X-Real-IP`、`Forwarded`，伪造这些请求头换不了来源地址，也绕不过限速（`input-hardening.itest.ts` 有测试）。
- 已登录用户改密码时核对当前密码，用同一套限速（单独一组计数），防止拿着别人的会话去猜密码。

### 邀请（新账号怎么拿到密码）

- 本期不接邮件服务。创建账号（平台员工、租户的第一个管理员、租户子账号）时，接口**只在这一次响应里**返回一次性邀请令牌；数据库只存它的 SHA-256。本人凭令牌在 `accept-invite` 接口设置密码，账号从「待激活」变成「在用」。
- 令牌 7 天过期、只能用一次。对一个从未激活过的邮箱再次邀请会换发新令牌，旧令牌作废。
- 平台上第一个账号只能用命令行创建：`pnpm admin:create --email … --name …`，创建的是超级管理员。密码在终端里交互输入（不回显）或从标准输入读，不接受命令行参数。

### 密码找回（不依赖邮件）

- **自己改密码**：`POST /platform/v1/auth/change-password`、`POST /tenant/v1/auth/change-password`。要提供当前密码；新密码要过强度规则且不能与当前密码相同；成功后该账号的**其他**会话全部失效，当前会话保留。
- **忘了密码：管理员发一次性重置令牌**，本人凭它在 `auth/reset-password` 设置新密码。谁能给谁发：
  - 平台超级管理员 → 平台员工（`POST /platform/v1/staff/{id}/password-reset`）；
  - 有 `tenant.create` 权限的平台员工 → 租户的**管理员**（`POST /platform/v1/tenants/{id}/admin-password-resets`），用于租户里没有别的管理员能帮忙的情况；
  - 租户管理员 → 本租户的用户（`POST /tenant/v1/users/{id}/password-reset`）。
- 重置令牌的机制与邀请令牌相同：原文只在发出的那一次响应里返回，数据库只存 SHA-256，一次性；有效期 **24 小时**（比邀请短，因为它能改掉一个正在使用的账号的密码）。再发一次，上一个作废；停用账号、本人自己改了密码，没用掉的令牌也作废。
- **发出重置令牌不改变现有密码，也不让现有会话失效**——否则这个功能可以被用来把别人锁在门外。只有本人真的凭令牌设了新密码，旧密码和全部会话才失效。
- 只能发给「在用」的账号：待激活的走重新邀请，已停用的先启用。
- 租户用户的重置令牌里带着租户编号（不是秘密），兑换时直接进入那个租户的数据库事务去查，不需要跨租户查询，也不需要全平台唯一的索引（ADR 0009）。
- 令牌不存在、已用过、已过期、账号已停用，返回同一个错误 `RESET_TOKEN_INVALID`。
- **最后一个超级管理员忘了密码**：在服务器上执行 `pnpm admin:reset-password --email …`，直接重设密码（交互输入不回显，或从标准输入读；不接受命令行参数）。只对在用的超级管理员有效；该账号的全部会话失效；审计日志记为「系统 / 命令行」。选择「直接重设」而不是「在终端打印一个重置令牌」，是因为打印出来的令牌会留在终端回滚和日志里。
- 以上每一步都写审计日志：`change_password`、`request_password_reset`（谁给谁发的）、`reset_password`（本人完成，或命令行）。

### 角色与权限

- 角色清单是系统定义的常量，来源是需求文档。代码里在 `packages/domain/src/access.ts`，数据库里是 `platform_roles`、`tenant_roles` 两张表（迁移写入，集成测试核对两边一致）。
- 权限模型做到「角色 → 允许的操作」，接口层每个接口声明自己需要的操作并强制检查。自建角色、数据范围留到 M4。
- 「至少保留一个」：租户在用的管理员、平台在用的超级管理员都不能减到 0（改动前锁住相关行，并发也不会出错）。
- 租户管理员可以查本租户的操作日志（`GET /tenant/v1/audit-logs`，操作 `audit_log.read`）。只包含本租户用户的操作和针对本租户账号的登录失败；平台员工对这个租户做的操作（创建、暂停及原因、代发邀请 / 重置）是平台内部记录，不给租户看。
- 修改账号的姓名也算敏感操作，写审计日志（前后姓名）。

## 理由

- 用「签名令牌 + 每次请求查会话」而不是纯无状态令牌：平台员工能看到所有租户的数据，停用账号必须立即生效，这比省一次数据库查询重要。每个请求多一次按主键的查询，代价很小。
- 仍然用签名令牌而不是不透明的会话编号：伪造的令牌在验签阶段就被拒绝，不会打到数据库；令牌里的受众和租户编号让租户请求在查会话之前就能进入该租户的数据库上下文（ADR 0009）。
- 不做刷新令牌：8 小时的会话足够覆盖一个工作日，少一类需要保护的长期凭证。以后要做「记住我」再新增 ADR。
- scrypt 是 Node 内置的、抗 GPU 的算法；不用 bcrypt / argon2 是因为它们需要原生依赖（ADR 0001「少依赖」）。

## 已知限制

- 重置令牌要由管理员当面或通过别的可信渠道交给本人（没有邮件服务）。拿到令牌的人就能设置这个账号的密码，所以有效期只有 24 小时，并且每次发出都有审计记录。
- 按邮箱限速意味着有人可以故意输错密码，让某个邮箱在 15 分钟内无法从**同一来源地址**登录；要让它从所有地址都无法登录，需要 15 分钟内 20 次请求。按来源地址的限速意味着同一出口地址后面如果有人在恶意尝试，同一地址的其他人在窗口内也登录不了。这些是防暴力破解的常见代价，全站级的限流（需求文档「限流」）另做。
- 自己改密码时「当前密码不对」的尝试不写审计日志（有限速）。
- 过期的会话行在该账号下次登录时清理，没有定时清理任务。
