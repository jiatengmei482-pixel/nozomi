## 二、业主需求原文（需求文档第一节，2026-11-14）

> 1. 后台套餐配置新增字段
>    - 套餐场景：单选 普通 / 机场开始 / 机场结束（默认普通，已有套餐全部为普通）
>    - 绑定机场区域：场景为机场时必填，可多选，只能选业务类型为"接送机"或"通用"的机场区域（如羽田、成田）
>    - 套餐价：按"套餐 × 绑定机场 × 车型组"单独填写；也可选"继承普通套餐价 + 区域加价"
>    - 含公里 / 超时费 / 超公里费：默认与普通套餐相同，可单独覆盖
>    - 前台名称：如"成田机场接机 + 5 小时包车""5 小时包车 + 羽田送机"
> 2. 下单页
>    - 包车模式增加快捷入口"机场接机开始""机场送机结束"，点击后上车点（或下车点）只能选机场，按航站楼列出
>    - 不走快捷入口、直接把机场填为上车点或下车点时，也要自动匹配机场场景套餐
>    - 不增加航班号字段，备注栏提示"如需司机知道航班号，请填在这里"
>    - 价格明细的套餐行显示场景名
> 3. 报价匹配规则
>    - 上车点落在套餐绑定的机场区域 → 可用"机场开始"套餐
>    - 下车点落在绑定的机场区域 → 可用"机场结束"套餐
>    - 两者都不满足 → 只用普通套餐
>    - 机场→机场：取两类套餐里价格较低的
>    - 选"继承"定价时，按普通套餐价加机场区域上车或下车加价计算；单独填价时已含机场部分，该机场区域不再重复加价

需求文档第〇节（「保持不变，不需要开发」）和规格「不变的业务规则」一致：包车按购买时长计、从预约上车时间开始计时、**没有免费等待**、**不设航班号字段**、不校验航班、航班延误由客服在下单前联系确认。

验收用例（需求文档第六节 P1，东京商品、经济 7 座，结算价）：
- 成田上车，「机场开始 5 小时」选继承 → 显示「成田机场接机 + 5 小时包车」，33,000 + 14,000 = 47,000；
- 同上，单独填价 45,000 → 报 45,000，成田不再加 14,000；
- 新宿上车、羽田下车 → 匹配「机场结束」套餐；
- 上下车都不在机场 → 只匹配普通套餐；
- （「服务区域含成田又设加价保存卡住」已由 ADR 0093 第七节改为保存前拦截，归 M9P-07，不在本篇。）

和规格冲突的地方（以规格为准）：需求文档写「超时费」在下单时收——规格已改为下单不收（ADR 0091 第三节），本篇的超时单价覆盖只作为服务后提交超时费的单价；「只能选接送机或通用区域」——见第三节第 2 条。

## 三、设计

### 1. 方案比较

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A「场景是套餐的属性」 | 每个套餐（时长）一行配置：场景、绑定区域、继承 / 单独定价、前台名称 | 字面最接近需求文档 | 「套餐」现在不是实体（只是价格规则上的时长），要新建套餐表并把整商品套餐价挂上去，改动 M9P-05 刚做完的结构；同一时长要拆成普通 / 机场开始 / 机场结束三行 | 不选 |
| **B「机场绑定 + 机场套餐价表」** | 商品级「机场绑定」：哪个场景 × 哪个机场（主数据）× 用哪个区域判断；价格页多一张「机场套餐价」表（场景 × 机场区域 × 车型组 × 套餐时长），**有格 = 单独定价，空格 = 继承** | 不改现有套餐价结构；价格规则的生效期、启停、版本、导入导出、审计、租户隔离全部沿用（同 ADR 0093 ②的做法）；没配的商品逐字不变 | 「继承 / 单独」是按格而不是按套餐整体选——见第十二节 Q3 | **推荐** |
| C「只靠区域加价表达」 | 不做场景，让供应商把成田的③加价改小 | 零开发 | 做不出「单独填价不含加价」「显示场景名」「快捷入口」，不满足需求 | 不选 |

### 2. 机场绑定（商品级）

- 新表 `charter_airport_bindings`（迁移 0520）：`tenant_id`、`product_id`、`scenario`（`airport_start` 机场开始 / `airport_end` 机场结束）、`place_id`（主数据里的机场，`places.type = 'airport'`）、`area_id`（用哪个区域判断「点落在这个机场」）、`created_at`。主键 `(tenant_id, product_id, scenario, place_id)`；同一商品同一场景里 `area_id` 唯一。RLS 按租户（规则 2）。
- **保存校验**（后端，前端保存前提示）：
  1. 只有包车、且 `charter_layout = 'three_layer'` 的商品能配（否则 400 `CHARTER_LAYOUT_NOT_MIGRATED`，同 ADR 0093 第一节）。
  2. `area_id` 必须是**这个商品的①基础价区域，或有启用的③上下车加价规则的区域**——规格步骤 1：上 / 下车点不在①③里根本不参与报价，绑一个①③以外的区域永远不会生效。需求文档写的「业务类型为接送机或通用」改为这一条（包车商品本来只能用「通用」「包车」类型的区域，`products.ts:72`；业主选的成田、羽田区域在东京包车里就是③ / ①）。见 Q2。
  3. `place_id` 是启用的机场，且机场坐标落在 `area_id` 的营业多边形里（防止把「成田市」误当成田机场绑定）。错误码 `AIRPORT_NOT_IN_AREA`。
  4. 一个商品一个场景最多绑 10 个机场（防误操作，够用）。
- 接口：`GET/PUT /tenant/v1/products/{id}/charter-airports`（整组替换，带商品 `version` 做乐观锁，成功后商品 `version` 加一、记审计）；运营后台 `GET /platform/v1/products/{id}/charter-airports` 只读。租户 A 读不到、改不了 B 的集成测试（规则 2）。
- 区域被删除 / 停用、或从商品里移除、③规则全停用：绑定不删，报价时这条绑定不生效（点不在①③就不匹配），商品页标红「绑定的区域已不在本商品里」；上架检查给提醒，不拦。

### 3. 机场套餐价（价格规则新价格方式）

- `price_rules` 加价格方式 **`charter_airport_package`**：`area_id` = 绑定的机场区域（必填）、`direction` = `pickup`（机场开始）/ `dropoff`（机场结束）（必填）、`package_hours` 必填、车型组、生效期、启停照旧。
- `params = { packagePriceMinor, packageKm?, overKmPerKmMinor?, overtimePerHourMinor? }`：只有套餐价必填；其余三项**没填 = 用同一车型组同一时长的普通套餐价那一行的值**（需求文档「默认与普通套餐相同，可单独覆盖」）。
- **有这一格 = 单独定价**；**没有这一格 = 继承**（普通套餐价 + 这一端的③加价）。需求文档「也可选继承」按格表达：价格页这张表的空格显示灰字「继承：普通 33,000 + 上车加价 14,000」，不是「空 = 不报价」（和②③不同，见 Q3）。
- 只有迁移过三层区域、且这个区域 × 方向有绑定的商品能建这种行（400 `AIRPORT_BINDING_REQUIRED`）。冲突键：区域 × 方向 × 车型组 × 套餐 × 生效日期。
- 价格导入导出：多一个工作表「机场套餐价」（M9P-22，和 M9P-07 的三张表同一做法）。

### 4. 报价匹配和计价（引擎）

对每个商品、每个车型组、每个候选套餐时长 H（自动选档、手动、锁定三种口径都一样）：

1. **找场景**（只在商品有绑定时）：
   - 上车点落在某个「机场开始」绑定的 `area_id` 里 → 候选场景 S（机场开始，记下机场和区域）；
   - 下车点落在某个「机场结束」绑定的 `area_id` 里 → 候选场景 E；
   - 都没有 → 普通套餐，**和今天逐字一样**。
   - 一个点落在同一场景的多个绑定区域里（过渡期重叠）：取③加价最高的那个区域对应的绑定（和 `endCharge` 的 `prefer: "highest"` 同一口径），一样时取绑定先建的。
2. **算场景 S 在 H 的价**：
   - 套餐价：有 `charter_airport_package`（这个区域、`pickup`、车型组、H、在生效期、启用）→ 用它的 `packagePriceMinor`，含公里 / 超公里 / 超时单价没填的取普通套餐行；**单独定价**。没有 → 用普通套餐价；**继承**。
   - 单独定价时普通套餐行不存在、而机场行又没填齐三项单价 → 这一档报不出（`NO_PRICE_RULE`），和今天缺套餐价一样。
   - 上车加价：**单独定价 → 0**（明细记 `areaId` = 机场区域、`amountMinor: 0`、`includedInPackage: true`）；**继承 → 照 `endCharge` 算**（成田 14,000；羽田在①里 0）。
   - 下车加价、行程加价、下车点行程加价：**完全照 ADR 0093 第二节**，场景不影响。
   - E 对称（下车那一端）。
3. **选档**：S / E 各自按 ADR 0093 第四节选档——候选 ≥ T，比「（场景下的）套餐价 + 超公里费」取最低；加价不参与（规格步骤 3）。
4. **场景替换普通**：有 S 或 E 时**不再和普通套餐比**——单独定价的机场价就是这个商品在这个机场的价（哪怕比「普通 + 加价」贵，比如含举牌接机），继承时两者本来相等。见 Q4。
5. **机场 → 机场**（S、E 都有，含同一个机场上下车）：S、E 各自选档算出结算总价，取**结算价低的**，一样时取 S（需求文档「取两类套餐里价格较低的」）。不叠加两个机场的单独定价。见 Q5。
6. 比价：各商品各自算完，照 `rankCandidates`（包车同价区间 0）。

#### 和三层区域的关系（逐条）

| 问题 | 结论 |
| --- | --- |
| 机场开始算不算③的上车？ | **算**。机场开始就是「上车点在机场」：继承时照收③上车加价（成田 14,000），单独定价时免的就是这一项。①里的机场（羽田）上车加价本来是 0，继承 = 普通价，只是多了场景名。 |
| 单独定价免哪些？ | 只免**场景那一端**的③加价。机场开始 → 只免上车加价；下车加价、行程加价照收（成田上车 → 箱根下车仍收箱根下车加价）。 |
| 规则 A：成田外围（成田机场 14,000 ∩ 成田市 / 千叶超远 12,000）重叠处上车 | 点在成田机场区域里 → 匹配机场开始。继承 → 收 14,000（规则 A 本来的结果）；单独定价 → 这一端**整个**免掉，**不退回**收千叶超远的 12,000（规则 A 的意思是重叠处归机场，机场的钱已含在单独价里）。将来按 A 切掉成田市、千叶超远的包车副本后结果相同。 |
| ②行程区域里有机场（经停在成田）？ | 经停不触发场景，行程加价照收；场景只看上 / 下车点。 |
| 下车点行程加价（ADR 0093 C） | 不受场景影响。机场结束且单独定价、下车点同时在某个②里时，下车点行程加价照规则收（单独价只含③）。东京的成田机场区域迁移后也在②里（业务方已定 B：途经加价 14,000 原样进②），所以「新宿 → 成田下车、不填经停」在机场结束单独定价时仍会收成田的下车点行程加价——**照收**，单独价只含③（Q6）。 |
| ①优先（M9P-06） | 场景判断用绑定区域的几何，不受①优先影响；加价仍按①优先（羽田在①里 = 0）。 |

#### 结算价明细、快照、订单

- 结算价明细加可选键 `charterScenario: { kind: "airport_start" | "airport_end", placeId, areaId, pricing: "own" | "inherit", priceRuleId: string | null }`（`own` 时是机场套餐价那一行；`inherit` 时为 null，套餐价规则照旧记在 `priceRuleId`）。没有场景时**不出现这个键**（golden 不变）。
- `areaSurcharge.pickup / dropoff` 加可选键 `includedInPackage: true`（单独定价免掉的那一端）。不改已有键名（同 ADR 0093「明细逐项」的理由）。
- 对外 `price_breakdown` 的套餐项加可选 `scenario`（kind、`airport_id`）和中文 `label`（「成田国际机场接机 + 5 小时包车」）；OpenAPI 同步。渠道 `/sales/v1` 同口径。
- 快照（含 `charterScenario`）就是订单记录场景的地方，**订单表不加列**。供应商、运营订单详情、司机行程页、客人订单页的套餐行按快照显示场景名。
- **改期**（M9P-16 锁加价）：加价照锁定（单独定价那一端锁的是 0）；套餐价按快照里的场景现算——快照有 `charterScenario.pricing = "own"` 时强制找同一区域 × 方向 × 车型组 × H 的机场套餐价，找不到（供应商删了）就报不出、按现有改期报不出流程转人工；不重新匹配场景、不退回普通价（否则锁定的 0 加价 + 普通价会少收）。`inherit` 照普通套餐价现算。
- **救援**：照 M9P-16——客人价锁定，候选按现行规则报价（候选商品有自己的机场套餐就用，没有就普通 + 加价），原供应商扣款基准不变。
- 回放（ADR 0086）：询价日志的 `request` 不变（场景由几何和商品配置决定）；回放读当时的绑定和价格规则即可重现。

### 5. 名称

- 前台名称**自动生成**，不让供应商填自由文本（文案进 i18n、M11 统一翻译；供应商自由文本做不了多语言）：
  - 机场开始：「{机场简称}接机 + {H} 小时包车」；机场结束：「{H} 小时包车 + {机场简称}送机」。
  - {机场简称} 用主数据机场的中文名（`places.name.zh`，如「成田国际机场」「羽田机场」）；主数据没有中文名时用日文名。见 Q7。
- i18n key（新文案只做中文，M11-01）：`charter.scenario.airportStart`（`{airport}接机 + {hours} 小时包车`）、`charter.scenario.airportEnd`（`{hours} 小时包车 + {airport}送机`）、`book.charter.quickAirportStart`（「机场接机开始」）、`book.charter.quickAirportEnd`（「机场送机结束」）、`book.charter.pickTerminal`（「选择航站楼」）、`book.charter.quickExit`（「改填其他地点」）、`book.notes.flightHint`（「如需司机知道航班号，请填在这里」）、`book.charter.airportTimingHint`（「包车从预约的上车时间开始计时，没有免费等待；航班可能延误时请预留时间，或下单前联系客服」）、`tenant.charterAirport.*`（后台的表头、空格灰字、校验提示）。M11-01 的 i18n 模块在 #258 合并前还没有：实现时先用它；若 M9P-22 开工时仍未合并，在 `apps/web/src/lib` 放一个只含中文的同名 key 表，M11 时并入。

### 6. 航班号、免费等待、航班延误

- **不加航班号字段、不给免费等待、不接航班状态**——需求文档第〇节和规格「不变的业务规则」是业主明文，ADR 0097 也写明包车不变。机场开始的包车虽然很像接机，但计费是「从预约上车时间起占用整段时长」，不是接机的「落地后免费等 X 分钟」。
- 页面上：
  - 第 3 步备注框的占位 / 提示改为「如需司机知道航班号，请填在这里」——**只在上车点或下车点是机场（匹配到了机场场景）时**显示，普通包车不变。
  - 选了机场开始时，第 1 步时间下面加一行提示（`book.charter.airportTimingHint`）：从预约时间开始计时、没有免费等待、延误请预留时间或联系客服。
- 航班延误：照需求文档「客服在客人下单前联系确认」，系统不做。若以后业主要「填航班号 → 自动顺延开始时间」，可复用 ADR 0097 的 `normalizeFlightNo` 和 M9E-29 的航班数据，另开任务（见 Q8）。

### 7. 官网 `/book/new` 和嵌入页

- **快捷入口**：包车模式在上车点上方两个按钮「机场接机开始」「机场送机结束」。点了以后上车点（或下车点）变成「选择航站楼」下拉：按机场分组、列出航站楼（`places` 里机场的子节点 `terminal`；机场没有航站楼的列机场本身）；只列**能报机场套餐的机场**（新接口 `GET /site/v1/charter-airports?scenario=airport_start|airport_end`：渠道范围里已上架、迁移过三层区域的包车商品的绑定机场，按城市分组，坐标取航站楼 / 机场的主数据坐标）。旁边「改填其他地点」退出快捷入口，回到普通地址输入。
- **不走快捷入口**直接输入机场或航站楼地址：引擎按几何自动匹配，页面不需要额外判断（需求文档「也要自动匹配」）。
- 价格明细套餐行显示场景名（`price_breakdown` 套餐项的 `label`）；单独定价时不出现那一端的上车 / 下车加价行，继承时照常显示「上车加价（成田机场）」。
- 套餐时长下拉、自动选档、经停、地图（M9P-20）全部不变。
- **嵌入页**：预订页（ADR 0095，`booking-shell`）和主站共用组件，快捷入口、提示、明细一起生效；入口小程序（widget）这次不加快捷入口（它只收起终点，客人在预订页再选），见 Q9。

### 8. 后台

- **供应商后台**：
  - 商品编辑页（包车、迁移过三层区域）加一块「机场套餐」：两组「机场开始」「机场结束」，每组多选机场（下拉只列「落在本商品①或③区域里的机场」，选中后自动带出所在区域，多个时让供应商选），保存即整组替换。没迁移过的商品这一块显示「迁移三层区域后可用」。
  - 价格页（M9P-07 的三张表之后）第四张表「机场套餐价」：行 = 场景 × 机场 × 车型组，列 = 套餐时长；格子填单独价，空格灰字显示继承后的价；格子可展开填含公里、超公里、超时单价（不填 = 同普通套餐）。
  - 上架检查：绑定的区域不在本商品①③里 → 提醒。
- **运营后台**：商品详情只读显示机场绑定和机场套餐价（结算价）。
- 租户看不到对外价和加价比例（规则 4）：这些接口只有结算价。

## 四、数据模型和迁移（0520）

只做加法，不含任何数据：

```sql
-- price_rules：新价格方式 charter_airport_package（area_id、direction、package_hours 必填，direction 只能 pickup / dropoff）
alter table price_rules drop constraint price_rules_model_check;  -- 加 'charter_airport_package'
alter table price_rules drop constraint price_rules_package_matches_model; -- charter_airport_package 时 package_hours not null
alter table price_rules add constraint price_rules_airport_package_shape check (
  pricing_model <> 'charter_airport_package' or (area_id is not null and direction in ('pickup', 'dropoff')));

create table charter_airport_bindings (
  tenant_id uuid not null references tenants (id),
  product_id uuid not null,
  scenario text not null check (scenario in ('airport_start', 'airport_end')),
  place_id uuid not null references places (id),
  area_id uuid not null,
  created_at timestamptz not null,
  primary key (tenant_id, product_id, scenario, place_id),
  unique (tenant_id, product_id, scenario, area_id),
  foreign key (tenant_id, product_id) references products (tenant_id, id) on delete cascade,
  foreign key (tenant_id, area_id) references areas (tenant_id, id) on delete cascade
);
-- RLS：同租户（nozomi_app）；平台只读（nozomi_platform select，同 0016 的做法）
```

- `price_rules_area_required`（0450）不用改：新价格方式 `area_id` 必填。
- 报价读商品时（`apps/api/src/repos/quotes.ts` `loadQuoteCandidates`）多读一次绑定，`QuoteProduct` 加可选 `airportBindings`（第五节）。

## 五、对外接口和代码接口（加什么）

- domain：`QuoteProduct.airportBindings?: readonly { scenario: "airport_start" | "airport_end"; placeId: string; areaId: string; placeName: LocalizedText }[]`；`Pricing` 联合类型加 `CharterAirportPackagePricing`；`SettlementBreakdown.charterScenario?`；`AreaSurchargeEnd.includedInPackage?`。新文件 `packages/domain/src/charter-airport.ts`：`airportScenarios(product, pickup, dropoff)`（找 S / E）、`airportPackagePricing(rules, query)`（找机场套餐价并补齐默认单价）。`quote.ts` 只在 `quoteAtHours` 取套餐价和 `endCharge` 两处调用它，`selectPackages` 外面包一层「S / E 各选一次取低」；没有绑定时走原路径（改动集中、和并行的 M9P-10 警告函数、M9P-20 不冲突）。

## 六、验收标准

1. 没配机场绑定的商品：包车 golden、itinerary golden 0 条变化；回放比对 0 变化。
2. 需求文档 P1（东京包车、经济 7 座、结算价，5h = 33,000，成田③上 / 下车加价 14,000，羽田在①）：
   - 成田航站楼上车（机场开始，继承）→ 套餐行「成田国际机场接机 + 5 小时包车」，33,000 + 上车加价 14,000 = **47,000**；
   - 同上，机场套餐价 5h 填 45,000 → **45,000**，明细没有上车加价；
   - 新宿上车、羽田下车 → 「5 小时包车 + 羽田机场送机」，= 普通价（羽田①，加价 0）；
   - 上下车都不在机场 → 只有普通套餐，明细逐字同今天。
3. 机场 → 机场（成田上车、羽田下车）→ S、E 取结算价低的；一样时取机场开始。
4. 规则 A：成田外围重叠处上车——继承收 14,000；单独定价收 0（不收千叶超远 12,000）。
5. 机场开始单独定价 + 箱根下车 → 下车加价照收；经停在②照收行程加价。
6. 自动选档按场景价比较（候选 ≥ T，场景套餐价 + 超公里费取最低）；手动升档、13 小时拦截不变。
7. 改期：单独定价的单改期后仍按机场套餐价、上车加价仍为 0；供应商删了那格 → 改期报不出、转人工。
8. 后台：没迁移过的商品不能配（400）；绑定区域不在①③里 → 400；机场不在区域里 → 400 `AIRPORT_NOT_IN_AREA`；租户隔离集成测试。
9. `/book/new` 和嵌入预订页：快捷入口只列能报机场套餐的机场、按航站楼列；直接输入航站楼地址也匹配；匹配到机场时备注提示航班号；没有航班号字段、没有免费等待文案。
10. 新文案只有中文、全部走 i18n key（M11-01）。
11. 单元、集成（真实 PostgreSQL）、组件、端到端（主站 + 嵌入页，chromium + webkit）；独立审查、合并、部署后测试站验收（并入 M9P-11 加 4 条机场用例）。

## 八、风险

1. **机场区域画得太大**：区域里的酒店也会匹配「机场接机」并免掉加价。缓解：绑定时校验机场在区域里；价格页提示「机场区域请只画航站楼周边」；运营可以另画一个小的「成田机场（包车）」③区域用于绑定。
2. **单独价比「普通 + 加价」贵**时客人付得更多：按需求文档单独价是供应商对机场的定价，接受；价格页空格 / 填格并排显示继承价，供应商自己看得到。
3. **改期找不到机场套餐价**：报不出转人工（第三节第 4 小节），不悄悄降价。
4. **航班延误**：包车从预约时间计时，延误的风险由客人承担，靠页面提示和客服（业主明定）；客诉风险在 Q8 记录。
5. **与并行车道冲突**：`quote.ts` 只改两处取值点 + `selectPackages` 外层，和 M9P-10（超限提醒函数）、M9P-20（经停顺序）各自独立；迁移号 0520 和 M9P-07 / M9P-13 车道（0500～0510）错开。

## 十一、和其他 ADR 的关系

- ADR 0093：不改任何一条；本篇在它的第二节（`endCharge`）和第四节（选档）外面加「场景」一层。0093 第九节 M9P-09 一行由本篇落实。
- ADR 0091：T 的定义不变；机场开始**不加**额外缓冲（见 Q10）。
- ADR 0096：地图编号、经停顺序不变；场景只看上 / 下车点，和经停顺序无关。
- ADR 0097：包车不加航班类型、免费等待，0097 第二节「包车不变」继续成立。

## 十二、待确认项（按监工常设规则：先按推荐答案实施，监工可以改）

| # | 问题 | 采用的答案（一句话） |
| --- | --- | --- |
| Q1 | 没迁移三层区域的商品能不能配机场套餐？ | 不能，只有 `charter_layout = 'three_layer'` 的商品能配（旧表按区域套餐价和机场单独价会混在一起，正式站迁移后再开）。 |
| Q2 | 需求文档要求「只能选接送机或通用类型的机场区域」，但包车商品只能用通用 / 包车类型的区域，怎么办？ | 改为「只能选本商品的①基础价区域或有启用③规则的区域、且机场坐标在区域里」——规格步骤 1 下其他区域永远匹配不上。 |
| Q3 | 「继承 / 单独定价」按套餐整体选，还是按格选？ | 按格：机场套餐价表里填了的格是单独价，空格是继承（普通价 + 这一端③加价），不是「空 = 不报价」。 |
| Q4 | 匹配到机场场景、单独价比「普通价 + 加价」贵时，要不要取低？ | 不取低，场景替换普通套餐（单独价是供应商对机场的定价，可能含举牌等服务）。 |
| Q5 | 机场 → 机场能不能两端都用单独价、两端加价都免？ | 不能，按需求文档取机场开始、机场结束两者结算价低的一个，一样时取机场开始。 |
| Q6 | 机场结束单独定价时，下车点所在②的「下车点行程加价」免不免？ | 不免，单独价只含③那一端的加价，②照 ADR 0093 第二节收（需求文档只说「该机场区域不再重复加价」指上 / 下车加价）。 |
| Q7 | 前台名称自由填写还是自动生成？ | 自动生成「{机场中文名}接机 + {H} 小时包车」「{H} 小时包车 + {机场中文名}送机」，供应商不填（便于 M11 多语言）。 |
| Q8 | 机场开始要不要加可选航班号字段或免费等待？ | 不加，按业主明定写在备注里，匹配到机场时备注框提示「如需司机知道航班号，请填在这里」，另加「从预约时间开始计时、没有免费等待」提示。 |
| Q9 | 嵌入入口小程序要不要也加快捷入口？ | 这次不加，嵌入预订页和主站共用组件已经有；小程序以后另开任务。 |
| Q10 | 机场开始要不要在 T 里多加缓冲（出关时间）？ | 不加，T 的公式按规格 / ADR 0091 不变，出关时间由客人选的上车时间覆盖。 |
| Q11 | 单独定价时成田外围重叠处，免掉 14,000 后要不要退回收千叶超远 12,000？ | 不退回，整端免掉（规则 A：重叠处归机场）。 |
| Q12 | 一个商品一个场景能绑几个机场？ | 最多 10 个，同一场景同一区域只能绑一个机场。 |
