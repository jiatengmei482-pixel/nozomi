## 二、业主需求原文（需求文档第一节，2026-11-14）

> 1. 后台套餐配置新增字段
>    - 套餐场景：单选 普通 / 机场开始 / 机场结束（默认普通，已有套餐全部为普通）
>    - 绑定机场区域：场景为机场时必填，可多选，只能选业务类型为"接送机"或"通用"的机场区域（如羽田、成田）
>    - 套餐价：按"套餐 × 绑定机场 × 车型组"单独填写；也可选"继承普通套餐价 + 区域加价"
>    - 含公里 / 超时费 / 超公里费：默认与普通套餐相同，可单独覆盖
>    - 前台名称：如"成田机场接机 + 5 小时包车""5 小时包车 + 羽田送机"
> 2. 下单页
>    - 包车模式增加快捷入口"机场接机开始""机场送机结束"，点击后上车点（或下车点）只能选机场，按航站楼列出
>    - 不走快捷入口、直接把机场填为上车点或下车点时，也要自动匹配机场场景套餐
>    - 不增加航班号字段，备注栏提示"如需司机知道航班号，请填在这里"
>    - 价格明细的套餐行显示场景名
> 3. 报价匹配规则
>    - 上车点落在套餐绑定的机场区域 → 可用"机场开始"套餐
>    - 下车点落在绑定的机场区域 → 可用"机场结束"套餐
>    - 两者都不满足 → 只用普通套餐
>    - 机场→机场：取两类套餐里价格较低的
>    - 选"继承"定价时，按普通套餐价加机场区域上车或下车加价计算；单独填价时已含机场部分，该机场区域不再重复加价

需求文档第〇节（「保持不变，不需要开发」）和规格「不变的业务规则」一致：包车按购买时长计、从预约上车时间开始计时、**没有免费等待**、**不设航班号字段**、不校验航班、航班延误由客服在客人下单前联系确认。

验收用例（需求文档第六节 P1，东京商品、经济 7 座，结算价）：
- 成田上车，「机场开始 5 小时」选继承 → 显示「成田机场接机 + 5 小时包车」，33,000 + 14,000 = 47,000；
- 同上，单独填价 45,000 → 报 45,000，成田不再加 14,000；
- 新宿上车、羽田下车 → 匹配「机场结束」套餐；
- 上下车都不在机场 → 只匹配普通套餐；
- （「服务区域含成田又设加价保存卡住」已由 ADR 0093 第七节改为保存前拦截，归 M9P-07，不在本篇。）

和规格冲突的地方（以规格为准）：需求文档写「超时费」在下单时收——规格已改为下单不收（ADR 0091 第三节），本篇的超时单价覆盖只作为服务后提交超时费的单价。

## 三、设计

### 1. 方案比较

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A「场景是套餐的属性」 | 每个套餐（时长）一行配置：场景、绑定区域、继承 / 单独定价、前台名称 | 字面最接近需求文档 | 「套餐」现在不是实体（只是价格规则上的时长），要新建套餐表并把整商品套餐价挂上去，改动 M9P-05 刚做完的结构；同一时长要拆成普通 / 机场开始 / 机场结束三行 | 不选 |
| **B「机场绑定 + 机场套餐价表」** | 商品级「机场绑定」：哪个场景 × 哪个机场（主数据）× 用哪块「机场区域」判断；价格页多一张「机场套餐价」表（场景 × 机场 × 车型组 × 套餐时长），**有格 = 单独定价，空格 = 继承** | 不改现有套餐价结构；价格规则的生效期、启停、版本、导入导出、审计、租户隔离全部沿用（同 ADR 0093 ②的做法）；没配的商品逐字不变 | 「继承 / 单独」是按格而不是按套餐整体选（Q3） | **推荐** |
| C「只靠区域加价表达」 | 不做场景，让供应商把成田的③加价改小 | 零开发 | 做不出「单独填价不含加价」「显示场景名」「快捷入口」，不满足需求 | 不选 |

### 2. 机场绑定（商品级）

- 新表 `charter_airport_bindings`（迁移 0520）：`tenant_id`、`product_id`、`scenario`（`airport_start` 机场开始 / `airport_end` 机场结束）、`place_id`（主数据里的机场，`places.type = 'airport'`）、`area_id`（用来判断「点在这个机场」的**机场区域**）、`short_name_zh`（可选的中文简称，最多 20 字，第 5 小节）、`created_at`。主键 `(tenant_id, product_id, scenario, place_id)`；同一商品同一场景里 `area_id` 唯一。RLS 按租户（规则 2）。
- **机场区域只用来判断「点在不在机场」（2026-11-15 按推荐，待监工复核；审查必改第 3 条）**：按业主原文，机场区域是和包车计价区域分开的一块区域，业务类型可以是**接送机、通用、包车**任一种；它**不是**商品的区域，不进 `product_areas`，不受 `areaUsableByCategory` 限制，也不参与①②③的同层不重叠校验。所以供应商可以只画航站楼周边，不必把整个成田③（含外围酒店）当机场。免的仍是这一端③（或①的 0）的加价，金额从③表取。
- **保存校验**（后端，前端保存前提示）：
  1. 只有包车、且 `charter_layout = 'three_layer'` 的商品能配（否则 400 `CHARTER_LAYOUT_NOT_MIGRATED`，同 ADR 0093 第一节）。
  2. 机场区域必须**被本商品的①∪③（有启用③规则的区域）完全覆盖**——否则会出现「匹配到机场场景、却因为上 / 下车点不在①③报不出价」。用 M9P-06 的同一套几何（`findAreaOverlaps` 用的多边形运算）算「机场区域 − (①∪③)」的面积，大于 0（容差 1 平方米）→ 400 `AIRPORT_AREA_NOT_COVERED`，`details` 给出没被覆盖的面积。之后①③改动让覆盖不再成立时：不拦那次改动，绑定照留，商品页标红「机场区域有部分不在本商品的报价范围里」、上架检查提醒（报价时那部分照规格步骤 1 报不出）。
  3. 机场（`place_id`）是启用的机场，**机场本身和它下面所有启用航站楼的坐标都落在机场区域里**（审查必改第 4 条）；不在 → 400 `AIRPORT_NOT_IN_AREA`，`details` 列出不在区域里的航站楼。主数据以后新加的航站楼落在区域外时，站点接口不列它（第 7 小节），商品页提醒。
  4. 机场区域是本租户启用中的区域（别的租户的按 404）。
  5. 一个商品一个场景最多绑 10 个机场，同一场景同一区域只能绑一个机场（Q12）。
- **机场区域被删除、停用**（审查必改第 6 条）：外键 `on delete restrict`——绑定着的区域**不能删**，删区域时 409 `AREA_IN_USE`（指出是哪个商品的机场绑定），先解绑再删；停用区域不拦，报价时停用的区域不生效（`locateInAreas` 跳过停用区域），商品页标红「机场区域已停用」、上架检查提醒。机场主数据停用同样：绑定不生效、标红。
- 接口：`GET/PUT /tenant/v1/products/{id}/charter-airports`（整组替换，带商品 `version` 做乐观锁，成功后商品 `version` 加一、记审计）；运营后台 `GET /platform/v1/products/{id}/charter-airports` 只读。租户 A 读不到、改不了 B 的集成测试（规则 2）。

### 3. 机场套餐价（价格规则新价格方式）

- `price_rules` 加价格方式 **`charter_airport_package`**：`area_id` = 绑定的机场区域（必填）、`direction` = `pickup`（机场开始）/ `dropoff`（机场结束）（必填）、`package_hours` 必填、车型组、生效期、启停照旧。
- `params = { packagePriceMinor, packageKm?, overKmPerKmMinor?, overtimePerHourMinor? }`：只有套餐价必填；其余三项**没填 = 用同一车型组同一时长的普通套餐价那一行的值**（需求文档「默认与普通套餐相同，可单独覆盖」）。
- **有这一格 = 单独定价**；**没有这一格 = 继承**（普通套餐价 + 这一端的机场加价，第 4 小节）。价格页这张表的空格显示灰字「继承：普通 33,000 + 上车加价 14,000」，不是「空 = 不报价」（和②③不同）。**继承的格不能单独覆盖含公里、超公里、超时单价**——要覆盖就填单独价（Q3，有意的取舍：一格只有一种来源，明细和回放说得清）。
- 单独价高于同一格继承价时，价格页把这一格标黄提醒（Q4）。
- 只有迁移过三层区域、且这个区域 × 方向有绑定的商品能建这种行（400 `AIRPORT_BINDING_REQUIRED`）。冲突键：区域 × 方向 × 车型组 × 套餐 × 生效日期。
- 它不是「基础定价」：上架检查、缺价统计、调价检查都不把它当普通套餐价。**区分它用单独的判断 `isAirportPackageModel`，不用 `isSurchargeModel`**（它不是加价，不能走加价那一支的区域检查）。
- **区域校验单独一支（#259 复核）**：这种价格规则的 `area_id` 是机场区域——不在本商品的 `product_areas` 里，业务类型可能是接送机。所以它**不走**商品区域（`services/prices.ts:350` `AREA_NOT_IN_PRODUCT`）、业务类型（`surchargeAreaIssues`，`prices.ts:429` `AREA_NOT_USABLE`）、区域用途（`areaRoleCanPrice`）这三项检查，**只查「这个区域 × 方向在本商品有机场绑定」**，没有 → 400 `AIRPORT_BINDING_REQUIRED`（区域不是本租户的仍按 404）。机场区域的用途（ADR 0075 的运营 / 报价 / 两者）都可以用，它只用来判断场景。
- 只读商品区域的两处**按绑定把它带上**：取整单位改动的影响预览（`apps/api/src/repos/prices.ts` `listBrandSellablePrices`，要求区域在 `product_areas` 里）和导入导出的区域判断（`apps/api/src/services/import-export.ts:440`）——机场套餐价行的区域只要在本商品的机场绑定里就算本商品的。
- **导入导出**（审查建议，统一归属）：价格表多一列「机场场景」（填「机场开始 / 机场结束」的行就是机场套餐价，同一张表，M9P-21 实现定稿）；**后端（M9P-21）**负责解析、校验、冲突检查和导出，**前端（M9P-22）**只负责价格页上的展示和上传入口。

### 4. 报价匹配和计价（引擎）

对每个商品、每个车型组、每个候选套餐时长 H（自动选档、手动、锁定三种口径都一样）：

1. **找场景**（只在商品有绑定时）：
   - 上车点落在某个「机场开始」绑定的机场区域里 → 候选场景 S（记下机场和机场区域）；
   - 下车点落在某个「机场结束」绑定的机场区域里 → 候选场景 E；
   - 都没有 → 普通套餐，**和今天逐字一样**。
   - 一个点落在同一场景的多个机场区域里：按绑定的先后取第一个（一般不会发生：同一场景的机场区域画在不同机场）。
2. **算场景 S 在 H 的价**（E 对称，换成下车那一端）：
   - 套餐价：有 `charter_airport_package`（这个机场区域、`pickup`、车型组、H、在生效期、启用）→ 用它的 `packagePriceMinor`，含公里 / 超公里 / 超时单价没填的取普通套餐行；**单独定价**。没有 → 用普通套餐价；**继承**。
   - 单独定价时普通套餐行不存在、而机场行又没填齐三项单价 → 这一档报不出（`NO_PRICE_RULE`），和今天缺套餐价一样。
   - **「这一端的机场加价」**（单独定价免掉、继承照收的那几项，2026-11-15 按推荐，待监工复核；审查必改第 2 条）：
     - 场景那一端的③上 / 下车加价（点在①里时本来就是 0）；
     - 机场结束时，另加**下车点行程加价**那一项（`fromDropoff`，ADR 0093 C）——下车点就是机场，这一项收的就是机场所在②的钱，业主原文「该机场区域不再重复加价」包括它。
     - 单独定价 → 上面几项都是 0（明细记 `includedInPackage: true`）；继承 → 照 ADR 0093 第二节算。
   - 另一端的上 / 下车加价、经停的行程加价：**完全照 ADR 0093 第二节**，场景不影响（成田上车 → 箱根下车仍收箱根下车加价）。
3. **选档**（审查必改第 1 条）：S / E 各自按 ADR 0093 第四节选档——候选 ≥ T（且 ≥ 最低套餐），比较的钱是 **「场景套餐价 +（继承的档才加）这一端的机场加价 + 超公里费」**，取最低，一样时取短的。规格让加价不参与选档，是因为加价对所有档都一样；机场场景里单独定价的档已含机场加价、继承的档要另付，加价随档变，所以把这一项算进比较。其他加价（另一端、经停）照规格不参与。
   - 例：成田上车，T = 4h30m，5h 单独价 45,000，6h 空格继承（普通 38,000，成田上车加价 14,000）：比 45,000 和 52,000，选 5h、报 45,000。
   - 可选时长：普通套餐价的时长 ∪ 这个机场区域 × 方向 × 车型组有机场套餐价的时长（只填了机场价、普通价没有这一档时也能选，三项单价要填齐）。
4. **场景替换普通**（Q4）：有 S 或 E 时**不再和普通套餐比**——单独定价的机场价就是这个商品在这个机场的价（可能含举牌接机等服务），继承时两者本来相等。价格页对单独价高于继承价的格标黄提醒供应商。
5. **机场 → 机场**（S、E 都有，含同一个机场上下车）：S、E 各自选档算出结算总价，取**结算价低的**，一样时取 S（需求文档「取两类套餐里价格较低的」）。不叠加两个机场的单独定价（Q5）。
6. 比价：各商品各自算完，照 `rankCandidates`（包车同价区间 0）。

#### 和三层区域的关系（逐条）

| 问题 | 结论 |
| --- | --- |
| 机场开始算不算③的上车？ | **算**。机场开始就是「上车点在机场」：继承时照收③上车加价（成田 14,000），单独定价时免的就是这一项。①里的机场（羽田）上车加价本来是 0，继承 = 普通价，只是多了场景名。 |
| 单独定价免哪些？ | 只免**场景那一端**的机场加价：③那一端的加价；机场结束另加下车点行程加价（**2026-11-17 业主定 Q13：机场结束不再加，见第十四节**）。另一端的③、经停的②照收。 |
| 规则 A：成田外围（成田机场 14,000 ∩ 成田市 / 千叶超远 12,000）重叠处 | 机场区域现在单独画（第 2 小节）：重叠处的酒店**不在**只画航站楼周边的机场区域里，不匹配场景，照规则 A 收 14,000。若供应商把机场区域画到了重叠处、单独定价：这一端**整个**免掉，**不退回**收千叶超远的 12,000（规则 A 的意思是重叠处归机场，Q11）。 |
| 继承时成田下车是多少？ | **新宿 → 成田下车、不填经停、机场结束继承（5h）= 33,000 + 成田下车加价 14,000 + 成田下车点行程加价 14,000 = 61,000**（ADR 0093 B：成田机场途经加价 14,000 原样进②；C：下车点行程加价），**不是**需求文档那条公式算出的 47,000。这是 C 带来的结果，本篇不改 C，列为待确认 Q13 交监工。单独定价 45,000 → 报 45,000（两项都免）。 | **（2026-11-17 业主已改为 47,000，见第十四节）**
| 成田上车继承是多少？ | 新宿下车（①）时 = 33,000 + 14,000 = **47,000**，和需求文档一致（下车点行程加价只看下车点）。 |
| ①优先（M9P-06） | 场景判断只看机场区域的几何，不受①优先影响；加价仍按①优先（羽田在①里 = 0）。 |
| 经停在机场 | 经停不触发场景，行程加价照收；场景只看上 / 下车点。 |

#### 结算价明细、快照、订单

- 结算价明细加可选键 `charterScenario: { kind: "airport_start" | "airport_end", placeId, areaId, pricing: "own" | "inherit", priceRuleId: string | null, name: string }`（`name` 是前台名称里的机场名：中文简称，没填用主数据中文名）（`own` 时 `priceRuleId` 是机场套餐价那一行；`inherit` 时为 null，套餐价规则照旧记在明细的 `priceRuleId`）。没有场景时**不出现这个键**（golden 不变）。
- `areaSurcharge.pickup / dropoff` 和 `waypoints` 里 `fromDropoff` 那一项加可选键 `includedInPackage: true`（单独定价免掉的，金额 0）。不改已有键名（同 ADR 0093「明细逐项」的理由）。
- 对外 `price_breakdown` 的套餐项加可选 `scenario`（`kind`、`airport_id`、`airport_name`），**不带拼好的中文 `label`**：场景名「成田机场接机 + 5 小时包车」由前端用 i18n key（第 5 小节）拼（M9P-21 实现定稿，#261 审查建议 4）；OpenAPI 同步。渠道 `/sales/v1` 同口径。供应商 / 运营订单详情的包车区域加价另带 `charter_scenario`（`kind`、`airport_id`、`airport_name`、`pricing`）和免掉那一项的 `included_in_package: true`。
- 快照（含 `charterScenario`）就是订单记录场景的地方，**订单表不加列**。供应商、运营订单详情、司机行程页、客人订单页的套餐行按快照显示场景名。
- **改期**（M9P-16 锁加价）：加价照锁定（单独定价免掉的项锁的是 0）；套餐价按快照里的场景现算——快照有 `charterScenario.pricing = "own"` 时强制找同一机场区域 × 方向 × 车型组 × H 的机场套餐价，找不到（供应商删了）就报不出、按现有改期报不出流程转人工；不重新匹配场景、不退回普通价（否则锁定的 0 加价 + 普通价会少收）。`inherit` 照普通套餐价现算。
- **救援**：照 M9P-16——客人价锁定，候选按现行规则报价（候选商品有自己的机场套餐就用，没有就普通 + 加价），原供应商扣款基准不变。
- 回放（ADR 0086）：询价日志的 `request` 不变（场景由几何和商品配置决定）；回放读当时的绑定和价格规则即可重现。

### 6. 航班号、免费等待、航班延误

- **不加航班号字段、不给免费等待、不接航班状态**——需求文档第〇节和规格「不变的业务规则」是业主明文，ADR 0097 也写明包车不变（0097 的 `isFlightArrival` 对包车返回 false，`BookNewPage` 包车模式不出现航班号字段）。机场开始的包车虽然很像接机，但计费是「从预约上车时间起占用整段时长」，不是接机的「落地后免费等 X 分钟」。
- 页面上：
  - 第 3 步备注框的提示改为「如需司机知道航班号，请填在这里」——**只在匹配到机场场景时**显示，普通包车不变。

```sql
create table charter_airport_bindings (
  tenant_id uuid not null references tenants (id),
  product_id uuid not null,

  place_id uuid not null references places (id),
  area_id uuid not null,

-- RLS：同租户（nozomi_app）；平台只读（nozomi_platform select，同 0016 的做法）
```

## 六、验收标准

1. 没配机场绑定的商品：包车 golden、itinerary golden 0 条变化；回放比对 0 变化。
2. 需求文档 P1（东京包车、经济 7 座、结算价，5h = 33,000，成田③上 / 下车加价 14,000、成田②14,000，羽田在①；成田绑定填简称「成田机场」）：
   - 成田航站楼上车、新宿下车（机场开始，继承）→ 套餐行「成田机场接机 + 5 小时包车」，33,000 + 上车加价 14,000 = **47,000**；
   - 同上，机场套餐价 5h 填 45,000 → **45,000**，明细没有上车加价；
   - 新宿上车、羽田下车 → 「5 小时包车 + 羽田机场送机」，= 普通价（羽田①，加价 0）；
   - 上下车都不在机场 → 只有普通套餐，明细逐字同今天。
3. 成田下车（机场结束）：继承 = 33,000 + 14,000 + 下车点行程加价 14,000 = **61,000**（Q13；2026-11-17 业主改为 **47,000**，见第十四节）；单独 45,000 → **45,000**（两项都免）。
4. 选档混合：成田上车，T = 4h30m，5h 单独 45,000、6h 继承（38,000 + 14,000）→ 选 5h、报 45,000。
5. 机场 → 机场（成田上车、羽田下车）→ S、E 取结算价低的；一样时取机场开始。
6. 机场开始单独定价 + 箱根下车 → 箱根下车加价照收；经停在②照收行程加价。
7. 自动选档按第三节第 4 小节第 3 步比较；手动升档、13 小时拦截不变。
8. 改期：单独定价的单改期后仍按机场套餐价、免掉的项仍为 0；供应商删了那格 → 改期报不出、转人工。
9. 后台：没迁移过的商品不能配（400）；机场区域没被①∪③完全覆盖 → 400 `AIRPORT_AREA_NOT_COVERED`；机场或航站楼不在区域里 → 400 `AIRPORT_NOT_IN_AREA`（列出航站楼）；绑定着的区域删不掉（409）；新价格方式没有绑定 → 400 `AIRPORT_BINDING_REQUIRED`；租户隔离集成测试；迁移测试（每种价格方式都插得进去）。
10. `/book/new` 和嵌入预订页：快捷入口只列能报机场套餐的机场、只列区域里的航站楼；直接输入航站楼地址也匹配；匹配到机场时备注提示航班号；没有航班号字段、没有免费等待文案；价格页单独价高于继承价的格标黄。
11. 新文案只有中文、全部走 i18n key（M11-01）。
12. 单元、集成（真实 PostgreSQL）、组件、端到端（主站 + 嵌入页，chromium + webkit）；独立审查、合并、部署后测试站验收（并入 M9P-11 加第 2–6 条机场用例）。

## 八、风险

1. **机场区域画得太大**：区域里的酒店也会匹配「机场接机」并免掉加价。缓解：机场区域和计价区域分开、可以只画航站楼周边（第三节第 2 小节）；保存时校验机场和航站楼在区域里；商品页提示「机场区域请只画航站楼周边」。
2. **单独价比继承价贵**时客人付得更多：按需求文档单独价是供应商对机场的定价，接受；价格页标黄提醒供应商（Q4）。
3. **继承时成田下车 61,000**（C 带来的下车点行程加价）：业主可能以为是 47,000；列为 Q13 交监工，确认前按 ADR 0093 现行规则算。 **业主 2026-11-17 定为 47,000，见第十四节。**
4. **改期找不到机场套餐价**：报不出转人工，不悄悄降价。
5. **航班延误**：包车从预约时间计时，延误的风险由客人承担，靠页面提示和客服（业主明定）。
6. **与并行车道冲突**：`quote.ts` 改动集中在第五节列的 4 处，和 M9P-10（超限提醒函数）、M9P-20（经停顺序）各自独立；迁移 0520 按当时 main 最新列表重建约束、并有迁移测试兜底。

## 十四、补记（2026-11-17）：机场结束不加下车点行程加价（Q13 定案）

- **业主决定**：终点是机场的套餐不加下车点行程加价——套餐价已含去机场的路程。
- **规则**：机场结束场景（单独定价、继承都一样）的「下车点行程加价」（ADR 0093 C，`fromDropoff`）记 0、标 `includedInPackage`，不进总价、不进明细。继承照收这一端的③下车加价（业主原文「继承 = 普通套餐价 + 机场区域加价」不变）。机场开始场景、没有场景的普通包车不受影响，仍按 ADR 0093 C。
- **例**：新宿 → 成田下车（5h，不填经停）：继承 = 33,000 + 下车加价 14,000 = **47,000**（原 61,000）；单独 45,000 → 45,000。成田上车 → 成田下车：机场结束继承 = 33,000 + 14,000 + 14,000 = 61,000（原 75,000）。
- **已下的单**：改期按下单时锁定的加价（M9P-16），不重算。
- **改动**：`packages/domain/src/quote.ts` 一行条件；价格页第四张表继承灰字去掉「下车点行程加价」一项，价格页不再为此读取服务规则。
