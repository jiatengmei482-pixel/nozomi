# ADR 0024：机场的中文名、日文名从 GeoNames 导入

- 状态：已采纳（2026-10-18，M1-15）
- 补充 ADR 0012（主数据、机场从 OurAirports 导入）和 ADR 0014（城市从 GeoNames 导入）。不改变其中的决定；数据来源、署名、下载、事务、咨询锁、版本核对、严格 UTF-8 的做法和城市导入相同，下面只写不同的地方。

## 背景

OurAirports 只有英文名，导入的机场要由平台逐个补上中文名、日文名，供应商在接送点里输入「成田」才找得到成田机场。GeoNames 里有机场的多语言名称，城市导入已经在用它（CC BY 4.0）。

## 决定

### 数据来源：同一个国家的两个文件

- `https://download.geonames.org/export/dump/<国家码>.zip`：这个国家的全部地理名称记录（19 列，和城市文件同一种格式；日本约 5MB）。
- `https://download.geonames.org/export/dump/alternatenames/<国家码>.zip`：各语言的名称（城市导入用的同一个文件）。语言一栏是 `iata` 的行就是机场的三字码，`ja`、`zh…` 是日文、中文名。
- 只用名称文件不够：同一个三字码也挂在城市、街区上（2026-10-18 的日本文件里，NRT 同时挂在成田机场和成田市上，HND 同时挂在羽田机场和「羽田」这个街区上，TYO、OSA 挂在东京、大阪上）。所以先用国家文件认出类型是机场（`S` / `AIRP`）的记录，只看这些记录的三字码和名称。
- 没有用全世界的文件（allCountries，压缩后约 400MB）：命令只支持 `--country`，按国家下载。
- 按 2026-10-18 的文件：日本有 133 条机场记录，其中 96 条有三字码，没有一个三字码挂在两条机场记录上。

### 按三字码对应

- 库里类型是机场、编码就是三字码的地点（从 OurAirports 导入的和平台手工建的都算），只看 `--country` 所选国家的。
- 下面这些不填，在命令输出里列为「需要人工处理」：
  - 同一个三字码挂在数据源里好几条机场记录上（分不清是哪一个）；
  - 数据源里这个机场在另一个国家；
  - 两边的坐标相差超过 **10 公里**（两个数据源给同一个机场的坐标一般相差不到 3 公里，10 公里以上多半是三字码挂错了记录）。
- 库里有、数据源里找不到三字码的，单独列出来。

### 选哪个名称

同一种语言有多个名称时的取舍（`packages/domain/src/geonames-airports.ts`）：

1. 历史名称、俗称不取；空白、只有不可见字符、超过 200 字的不取。
2. **日文**：只取标签是 `ja` 的，而且必须有汉字或假名——数据源里标成 `ja` 的有不少是罗马字（「Kansai Kokusai Kūkō」「Tōkyō Kokusai Kūkō」）。中文名同样必须有汉字。名称里夹着字母、数字的（「JR…」）照样取。
3. **中文只要简体**：
   - 标签优先级：`zh-CN` > `zh-Hans` > `zh-SG` > `zh`（和城市导入同一个顺序）；
   - `zh-Hant`、`zh-TW`、`zh-HK`、`zh-MO`（繁体）、`yue`（粤语）、`wuu`（吴语）不取；
   - 只标了 `zh` 的在日本的机场里大多是繁体（「松本機場」「東京國際機場」），所以任何一条中文名里出现繁体专用字（機、場、國、際、東、島……，只收了地名里常见的、在简体里一定写成另一个字的约一百个字）就不要它；
   - 只有繁体的，中文名**留空**，在输出里列出「数据源里只有繁体中文名」，由平台在后台填简体。不做繁简转换（没有可靠又不引入第三方库的转换表）。
4. 剩下的里面：「首选的简称」>「简称」>「首选」> 其余；还一样就取数据源里编号最小的那条（最早录入的，一般是正式名称）。
   不用「最短的」：关西机场的候选里有「関空」，比正式名称短，但不适合做名称。

由此羽田的日文名是「東京国際空港」而不是「羽田空港」（两个都没有标首选，前者编号小）；中文名只有繁体，留空。

### 只填空着的，不覆盖人工修改

- 只填空着的语言（没有这种语言，或者只有空白）。已经有名称的，不管是平台填的还是以前导入的，一律不改；数据源后来改了名，也不更新——要更新请平台在后台改。
- 「人工改过」的判断和城市导入是同一个思路：**记下导入写进去的是什么，以后拿它和现在的值比**。城市用的是一个 `source_overridden` 标记，机场不能直接用它：地点上原有的 `source` / `source_overridden` 记的是 OurAirports 管的英文名和坐标，平台改中文名不会、也不应该把它标成「改过」（否则以后 OurAirports 的坐标更新也被挡住）。所以新增一列 `places.name_sources`（迁移 `0022_place_name_sources.sql`），按语言记下数据源、数据源编号和当时填的文字：
  - 以前由导入填过、现在空了 → 平台在后台删掉了，**不再补回去**；
  - 现在的值和导入写的不一样 → 平台改过，不覆盖；
  - 平台在后台改名称时不需要动这一列，比较就能认出来。
- 这一列只在数据库和审计日志里，不出现在接口的应答里（前端的接口约定测试钉住了 `Place` 的字段）。
- 填名称是一次真正的修改：版本号加一、更新时间改为现在、写审计日志（操作者「系统」、入口「命令行」，`after` 里记 `name_source`：数据源、编号、填了哪几种语言）。不改启用状态、所属城市、英文名和坐标。
- 每次写入核对版本号：导入运行期间平台在后台改过的机场不填，列为需要人工处理。同一时间只允许一次机场名称导入（咨询锁）；整次导入在一个事务里。

### 命令

```
pnpm masterdata:import-airport-names --country JP,KR [--dry-run]
pnpm masterdata:import-airport-names --country JP --file JP.zip --names-file alternatenames/JP.zip   # 不联网
```

- `--file`（国家文件）和 `--names-file`（名称文件）要一起给，都可以给多次（每个国家一个），`.zip` 或解压好的 `.txt` 都行。zip 里取和文件名同名的 `.txt`（两个下载下来都叫 `JP.zip`，放在不同目录即可）。
- 要先有机场：先运行 `pnpm masterdata:import-airports`。可以反复运行。

### 署名

和城市导入相同的位置：每个填进去的名称在 `places.name_sources` 里记着来源和编号，审计日志里也记；命令输出的第一行写明来源和许可；代码、本 ADR、根 `README.md`、`openapi.yaml` 的说明。

**面向用户的页面**：凡是展示机场名称的页面（运营后台的地点页、供应商后台的接送点选项、以后的官网），署名那一行要包含机场名称——例如「城市数据和机场的中文、日文名称来自 GeoNames（geonames.org），CC BY 4.0」。这一条是许可的条件，由前端在下一个涉及这些页面的任务里改（M1-15 只做了后端）。

### 在真实文件上试跑（2026-10-18，日本，`--dry-run`）

在临时的测试 schema 里先导入 OurAirports 的 82 个日本机场，再试运行：82 个全部对上，没有需要人工处理的；将给 71 个机场填名称（日文 70 个、中文 41 个），另外 11 个数据源里没有这两种语言；20 个只有繁体中文名、中文名留空（含羽田、中部、神户、松山、新潟）。成田：日文「成田国際空港」、中文「成田国际机场」；羽田：日文「東京国際空港」，中文留空。

## 没有做的

- 韩文名：`MASTER_DATA_LANGUAGES` 里有 `ko`，但这个任务只要求中文、日文；要导入只需把 `ko` 加进 `AIRPORT_NAME_LANGUAGES`。
- 繁简转换、给繁体名单独存一种语言。
- 航站楼的名称：数据源里没有。
- 数据源后来改名时提示「可以更新」：现在只在输出里列出「以前导入的，数据源后来改了」，不自动更新。

## 补充：搜索别名（M8-47，2026-11-22）

M8-06 验收时在官网输入「羽田」「羽田空港」，平台的羽田机场不在候选里：它的日文名是正式名称「東京国際空港」、中文名因只有繁体留空、英文名里的「Haneda」是字母，名称里没有「羽田」两个字。GeoNames 里其实有「羽田空港」这一条（日文、非俗称），按上面「同一种语言取一个」的规则被舍掉了。

只做加法，不改上面的任何规则（名称怎么挑、只填空着的、怎么认人工修改都不变）：

- 迁移 0680 给 `places` 加 `search_names`（`text[]`，默认空数组，最多 20 个）。
- 这个导入同时把数据源里这个机场所有用汉字、假名写的日文、中文写法（标签 `ja`、`zh*`、`yue`、`wuu`；俗称也收，历史名称不收；繁体也收）记成搜索别名，按数据源编号排、去重。只在对上了（国家、坐标核对过）的机场上写，每次按数据源整份替换；和 `municipality` 一样不算修改（版本号、更新时间不变，不写审计日志），不出现在任何接口的应答里，不显示。
- 只有官网地址搜索、输入即提示找平台的机场、航站楼（连同所属机场的别名）时用（`@nozomi/domain` 的 `platformPlaceSuggestions`）。候选里显示的仍是名称（羽田显示「東京国際空港」）。
- 上线后在每个环境运行一次 `pnpm masterdata:import-airport-names --country <已导入机场的国家>`，已有的机场就补上别名；不运行时行为和以前一样。

## 补充（M12-06，2026-11-25）：GeoNames 之后还空着的名称，用仓库里的核对表补

业主 2026-11-25 要求机场主数据每个机场都预先填好日文、简体中文、英文名称。GeoNames 导入后仍有空着的（数据源只有繁体中文名的 21 个、数据源里没有日文 / 中文名的若干个），改用**仓库里一张人核对过的表**补：`apps/api/masterdata/airport-names-reviewed.json`。

- 每一条写明来源：GeoNames 繁体名逐字转简体（「機場 / 飛行場」统一写「机场」，业主 2026-11-25 在 #288 确认 21 个）、维基数据（Wikidata，CC0 公有领域）的日文、简体中文标签、机场官方的民航名称（维基数据给的是自卫队名称时，如茨城「百里飛行場」）。
- 写入规则和 GeoNames 导入相同：只填空着的语言，已有的不改；以前导入填过、后来平台删掉的不补回去；按三字码 + 国家对应；不动搜索别名。来源记进 `name_sources`（`source` 是 `nozomi-reviewed`，`ref` 是表里写的来源说明），每次写入都有审计日志。
- 表在读入时校验：简体名里出现常见繁体 / 日文字形（维基数据的「简体」标签偶尔就是繁体，如仁川）、日文名里没有汉字或假名、没写来源，整张表不用。
- 命令 `pnpm masterdata:import-airport-names-reviewed --country <国家码> [--dry-run]`；测试环境经主数据导入工作流的 `airport-names-reviewed` 运行（默认试运行）。表要改就改这个文件、走 PR。

## 补充（M12-06b，2026-11-25）：机场 / 航站楼的固定地址、集合地点说明和航站楼核对表

业主 2026-11-25 要求每个机场预先填好固定地址、每个航站楼的集合地点说明。原来 `places` 只有地标能填地址（迁移 0007 的约束），没有集合地点这一项，测试站一个航站楼都没登记。这一段只定结构和导入机制；内容（地址、集合地点文字、航站楼坐标）由监工审过后另一个 PR 填进核对表。

### 结构（迁移 0700，只改结构、不写数据）

- `places.address`：地标、机场、航站楼能填（填了就不能只有空白，最多 300 字），车站、出口不能填。机场、航站楼的地址写日文、含邮编（核对表里检查，平台手工录入时不强制）。
- `places.meeting_point`：集合地点说明，`{zh, ja, en}`，只有机场、航站楼能填；至少一种语言，每种最多 1000 字，不认识的语言不收。运营后台和核对表要求中文必填，接口只要求至少一种。数据库里有同样的检查约束兜底。
- 挂在哪：**单航站楼的机场挂在机场上，多航站楼的挂在各航站楼上**。这是录入约定，数据库和接口不强制（机场下有航站楼时也能在机场上写一段总的说明）；核对表里强制（列了航站楼的机场不能在机场上写，没列航站楼的必须在机场上写）。
- `places.content_sources`：地址、集合地点是哪次导入填的（`{address | meeting_point: {source, ref, value}}`），用法和上面的 `name_sources` 一样——以前导入填过、现在空了，就是平台删掉了，再导入不补；现在的值和导入写的不一样，就是平台改过，不覆盖。只在数据库和审计日志里，不进接口应答。
- 接口：平台主数据地点的新增、修改收 `address`、`meeting_point`（权限、`If-Match`、审计日志和别的字段一样），平台和租户的读接口都返回。**租户看得到集合地点和地址**：供应商要按它安排司机在哪里等客人；这两项不是对外价和加价比例（规则 4 不涉及）。

### 航站楼核对表

- 表：`apps/api/masterdata/airport-terminals-reviewed.json`。每个机场：`code`、`country`、`address {text, source}`、`meetingPoint {zh, ja?, en?, source}`（只有不列航站楼的机场写）、`terminals [{suffix, names {ja, zh, en}, lat, lng, coordSource, flightScope?, address? {text, source}, meetingPoint {zh, ja?, en?, source?}, sources [...]}]`。航站楼集合地点没写 `source` 时用这个航站楼的 `sources`。
- **来源只用机场官网、政府资料和维基数据（CC0）**，不用谷歌数据（谷歌地图平台的条款限制把它的内容长期存进自己的数据库，监工 2026-11-25 要求）。每一项写明来源，写入时记进 `name_sources` / `content_sources` 和审计日志。
- 读表时校验，任何一处不合格整张表不用：三字码、国家码；日本的地址要有汉字或假名、要带邮编；集合地点中文必填、简体里不能有常见繁体 / 日文字形（同上面名称核对表的那张字表）；航站楼后缀 1 到 6 位大写字母或数字、同一机场不重复；航站楼名称三种语言都要有（日文要有汉字或假名、中文是简体）；坐标在范围内；每一项都写了来源。
- 写入（`planReviewedAirportTerminals` 算计划，纯函数）：
  - 按三字码 + 国家对应库里的机场；库里没有的机场列出来、不管。
  - 机场：填空着的地址、集合地点。
  - 航站楼编码是「三字码-后缀」。库里没有就新建：类型航站楼、挂在机场下、城市和国家跟机场；机场启用（有城市）时是启用的，机场停用时建成停用的（启用的航站楼必须有城市、上级必须启用，ADR 0012），等机场启用后由平台启用。新建时用表里的名称、坐标、国际 / 国内属性、地址、集合地点。
  - 已有的航站楼只填空着的地址、集合地点、名称语言（名称的来源记进 `name_sources`，和机场名称一样），坐标、国际 / 国内属性不动。
  - **航站楼坐标和机场相距超过 5 公里的不用**（新建和填写都不做），列出来交给人看；一般航站楼离机场参考点 1～3 公里，5 公里以上多半是坐标抄错了。同编码的航站楼挂在别的机场下的，也不动。
  - 每次写入核对版本号（运行期间平台改过的不覆盖）；整次在一个事务里；同一时间只允许一次（咨询锁）；新建和填写都写审计日志（操作者「系统」、入口「命令行」，`after.fill_source` 记来源）。同一张表可以反复运行，第二次什么都不做。
- 命令 `pnpm masterdata:import-airport-terminals-reviewed --country <国家码> [--file <表>] [--dry-run]`，不联网；测试环境经主数据导入工作流的 `airport-terminals-reviewed` 运行（默认试运行）。要先导入机场。表要改就改这个文件、走 PR。
