# ADR 0105：WAL 归档、恢复到任意时间点和异地备份

- 状态：已采纳（2026-11-22，M4-23 不依赖负责人的部分）
- 补充：ADR 0007「部署到自有 VPS」的「影响」一节（每日备份达不到「恢复到任意时间点」，上线前要补 WAL 归档）和「已知限制」里的「备份只在本机」。ADR 0007 的其余内容不变；每日的 `pg_dump`（`backup.sh` / `restore.sh`）照旧保留。
- 依据：需求文档 02「备份与恢复」：数据库每日全量备份 + 实时日志，可恢复到任意时间点；每季度演练一次恢复。roadmap M4-23 的验收标准：「备份存到另一个地方，演练过恢复」「补 WAL 归档」。M4-25（清除乘客明文，不可逆）要等这里的异地备份和恢复演练。

## 背景

现在每天一份 `pg_dump`，加上部署前、恢复前各一份，全部在同一台服务器上，保留 14 天。两个缺口：

1. **只能回到「某一份备份那一刻」**：误删、错误的数据迁移、程序缺陷写坏数据之后，最近一份每日备份可能是二十多个小时之前的，中间的订单和付款全丢。
2. **服务器整台坏掉（硬盘、服务商、被入侵）时备份跟着一起没了。**

异地存储用哪一家、正式环境的服务器都要负责人决定，还没有。本 ADR 把不依赖这两样的部分全部做完，异地那一段做成「填好 `.env` 就生效、不填也照常工作」。

## 决定

### 1. 工具：PostgreSQL 自带的归档 + restic 做异地

| 环节 | 用什么 |
| --- | --- |
| 连续归档 WAL | PostgreSQL 自带的 `archive_mode` / `archive_command`：压缩后写进本机的 `pitr` 数据卷 |
| 基础备份 | PostgreSQL 自带的 `pg_basebackup`（tar + gzip，带备份期间的 WAL），每天一次 |
| 恢复到时间点 | PostgreSQL 自带的 `recovery_target_time`，在一个**临时数据库容器**里恢复 |
| 异地 | [restic](https://restic.net/)（固定版本的官方镜像）：把 `pitr` 卷加密后同步到任意 **S3 兼容**的对象存储 |

**为什么不用 pgBackRest 或 WAL-G**：两者都很成熟，但都要装进数据库容器里运行（`archive_command` 在数据库进程里执行）。我们的数据库用的是官方 `postgres:16` 镜像、不在 CI 里构建；用它们就得多出第三个自建镜像（构建、推送、拉取、回退、清理全部多一份，ADR 0007 的镜像规则都要改）。而本机这一段 PostgreSQL 自带的功能已经够用；异地这一段 restic 是独立的容器，不碰数据库镜像。

**为什么异地选 restic，而不是直接把归档目录同步上去**：

- **加密在本机完成**（AES-256），对象存储里只有密文；不依赖服务商的加密。
- **S3 兼容的都能用**：Cloudflare R2、Backblaze B2、AWS S3、Wasabi、各家云的对象存储都行；以后换服务商只改 `.env`。
- **保留规则、完整性检查、断点续传、去重压缩都是现成的**（`forget --prune`、`check`），不用自己写。
- 单个静态程序、官方镜像、用户多、文档全。

### 2. 本机：WAL 归档和基础备份

- 数据库容器加两项设置：`archive_mode=on`、`archive_timeout=60`（WAL 不满一段时最多 60 秒也归档一次）。改动在 `deploy/compose.yml` 的 `db.command`；容器入口先以 root 建好 `/pitr/wal`、`/pitr/base` 并交给 postgres，再交回官方入口。
- **归档命令**：压缩后写临时文件 → 落盘 → 改名，不留半截文件；同名文件已经在（上次归档到一半数据库重启了）时内容一致算成功、不一致算失败，**永不覆盖**。
- **按数据库实例分目录**：`/pitr/wal/<系统标识>/`。系统标识是 PostgreSQL 实例建立时生成的编号。换了服务器、数据卷重建过的新实例，WAL 文件名会从头开始、和旧实例撞名；分目录之后从异地取回的旧实例的 WAL 和新实例自己的 WAL 互不干扰（CI 演练里专门验证了这一点）。
- **基础备份**（`bin/pitr-backup.sh`）：每天 03:47 由定时任务做一次，带 `--checkpoint=fast`（不等定期检查点）。另外每次部署成功后，如果最近一次基础备份已经超过 20 小时（或者还没有）也做一次——兜底那些还没重新运行初始化、没装上新定时任务的服务器（比如现在的测试环境）。失败不影响部署结果，只记一行日志。
- **本机保留**：最近 7 天的基础备份，外加比这更早的最近一份（这样 7 天里任何时间点都有起点）；比最早留下的那份更早的 WAL 一起删掉；没有基础备份再引用的旧实例的 WAL 目录整个删掉。新备份做完并确认可读之后才清理，失败时不删任何东西。
- `pitr` 卷和数据库在同一块硬盘上：它防的是「数据被改坏」，防不了「硬盘坏了」——后者靠异地。

### 3. 恢复到时间点（`bin/pitr-restore.sh`）

- **默认不碰正在运行的数据库**：选「在目标时间之前已经完成」的最近一份基础备份，在临时容器 `pitr-restore` 自己的数据卷里解开，按归档重放到目标时间，然后让它可读写。人进去看对不对（`compose.sh exec pitr-restore psql …`）。
- **时间必须带时区**（`+09:00` 或 `Z`），不带的拒绝：服务器、数据库、看日志的人可能各在一个时区。
- **开始前先让正在运行的数据库把当前的 WAL 段归档**（`pg_switch_wal()` 并等归档完），所以「刚才那一分钟」的改动也恢复得到。
- **确认后替换正式数据**（`--apply`，要输入环境名确认）：把临时库整库导出到 `backups/`（标签 `pitr`），交给已有的 `restore.sh`——和用每日备份恢复是同一条路：停 API、恢复前再备份一次当前库、清空、导入、迁移、启动并等健康、应用账号仍是最小权限。不在物理层面替换数据目录：那样要停数据库、动 `db-data` 卷，出错的代价大得多，而几 GB 的库导出导入只要几分钟。最后再做一次基础备份。
- `latest`：恢复到归档里最后的时刻，用于数据库坏了、数据卷没了。
- `--system <系统标识>`：只用某个数据库实例的备份。换了服务器之后，新服务器首次部署时已经给新的（空）实例做了基础备份，`latest` 默认会选到它；取回旧实例的数据要带上旧实例的标识（`pitr-offsite.sh fetch` 取回后会打印要用的命令）。
- 时间晚于最后一次提交时 PostgreSQL 没法确认停在哪里，会拒绝（「recovery ended before configured recovery target was reached」）；脚本把它翻译成「换一个稍早的时间，或用 latest」。

### 4. 异地（`bin/pitr-offsite.sh`）

- **配置**：服务器 `.env` 里四项，**由负责人自己填**，不经过聊天、GitHub 和仓库：

  | 变量 | 内容 |
  | --- | --- |
  | `OFFSITE_BACKUP_REPOSITORY` | `s3:https://<服务商给的 S3 地址>/<存储桶>/<环境名>` |
  | `OFFSITE_BACKUP_ACCESS_KEY_ID` | 对象存储的访问密钥 ID（只给这一个存储桶读写权限） |
  | `OFFSITE_BACKUP_SECRET_ACCESS_KEY` | 对应的密钥 |
  | `OFFSITE_BACKUP_PASSWORD` | 加密口令，至少 32 个字符。**负责人另外自己保管一份**（密码管理器）：服务器整台没了时，没有它异地备份谁也解不开 |
  | `OFFSITE_BACKUP_REGION`（可选） | 有的服务商要求填区域 |

- **没配（四项都空）**：什么都不传，日志和状态检查明确写「备份只在这台服务器上」；测试环境照常工作。**只配了一部分、口令太短**：报错。**正式环境没配**：状态检查算「异常」。
- **频率**：每 15 分钟同步一次（restic 只传新增的部分）；每天基础备份之后再按保留规则清理旧快照、检查仓库完整性。同一时间只有一个 restic 在操作仓库（`flock`）。
- **异地保留**：最近 2 天的快照全留，之后每天一份留 35 天。每份快照里都有当时本机的 7 天，所以异地至少能恢复到最近 35 天里的任何时间点。
- **快照按数据库实例区分**：快照的主机名是 `nozomi-<环境>-<系统标识>`。换了服务器之后，新服务器（空库）的同步不会盖掉旧实例「最后的那一份」；保留规则按主机名分组各自套用，旧实例的快照最多也只留 35 份每日的。
- **取回**（`pitr-offsite.sh fetch`）：把异地里**别的**数据库实例（换服务器之前的那个）各自最后的快照取回到 `pitr` 卷，并打印恢复要用的命令（`pitr-restore.sh latest --system <旧实例的标识>`）。
- restic 容器以数据库容器里 postgres 的用户号（999）运行、文件系统只读、去掉全部特权，只接一个专用的、能出外网的网络 `offsite`（不在数据库所在的内部网络里）。它的配置只给它自己，别的容器的环境里没有。

### 5. 监控

- **`bin/pitr-status.sh`**：检查归档开着、没有在失败、没有积压（等着归档的 WAL ≤ 5 个）、最近一次基础备份 ≤ 26 小时、异地最近一次成功 ≤ 60 分钟。每 15 分钟由定时任务运行，结果写进系统日志（标签 `nozomi-pitr`），异常时以 1 退出。
- **提醒到人**：`.env` 里可选的 `BACKUP_HEARTBEAT_URL`——监控服务（Healthchecks、Better Stack、Uptime Kuma 等都支持的「心跳 / 推送」检查）给的地址。全部正常时才访问它一次；监控服务在约定时间（建议 30 分钟）内收不到就通知负责人。这样归档停了、定时任务没跑、整台服务器宕机，都会被发现。没配时只有系统日志（需要有人去看）。

### 6. 目标（RPO / RTO）

| 情况 | 最多丢多少数据（RPO） | 多久恢复（RTO） |
| --- | --- | --- |
| 数据被改坏、误删（服务器还在） | **0**：恢复前先归档当前 WAL，任何已提交的时刻都能回到 | 先在临时库里看：几 GB 的库约 5–15 分钟；确认替换再加约 10–20 分钟（网站这段时间不可用） |
| 服务器整台没了 | **约 16 分钟**：异地每 15 分钟同步 + 归档最多等 60 秒 | 约 2 小时：开新服务器、初始化、部署（约 30–60 分钟）+ 取回 + 恢复 + 替换 |
| 只配了本机、服务器整台没了 | 全部（本机副本跟着没了） | — |

### 7. 演练

- **CI 每次都跑**（`deploy/ci/pitr-drill.sh`，只用容器）：写数据 → 基础备份 → 再写 → 记下时间 → 再写、删一行 → 记下时间 → 再写；分别恢复到两个时间点（一个用东京时间写）和 latest，行数**正好**是那一刻的；正在运行的数据库一行没变；写错的时间被拒绝。异地：用一个 S3 兼容服务（rclone serve s3）代替对象存储，只配一部分报错、口令太短报错、配齐后同步、口令不对读不了；然后删掉数据库和 `pitr` 两个数据卷、起一个空数据库并做一次基础备份（和新服务器首次部署一样），从异地取回，再恢复到时间点、恢复旧实例的 latest，行数都正好；新旧实例的 WAL 各在各的目录，新实例归档不失败。
- **部署冒烟**（`deploy/ci/smoke.sh`，两种入口模式）：首次部署后状态检查正常（部署脚本做了第一次基础备份）；在完整的系统上恢复到两次写之间的时间点并 `--apply`，正好剩前一行，服务健康、管理员能登录、应用账号仍是最小权限。
- **每季度演练一次**（需求文档 02）：在测试环境按 `docs/deploy.md`「恢复到任意时间点」恢复到一个时间点看一遍（不加 `--apply`，不影响测试环境），正式环境有了之后同样做；结果记在验收记录里。

## 理由（摘要）

- 不新增自建镜像、不改镜像流水线；本机部分全是 PostgreSQL 自带功能，出问题时任何 PostgreSQL 文档都适用。
- 异地服务商还没定：restic 支持所有 S3 兼容存储，加密在本机，负责人以后选哪家都只是填 `.env`。
- 恢复默认进临时库、替换走已经验证过的 `restore.sh`：最危险的那一步（动正式数据）沿用同一条路，有确认、有恢复前备份。

## 影响

- **部署这个版本时数据库会重启一次**（compose 里数据库的启动参数变了，容器重建），几秒到十几秒；之后照常。回退到更早的版本时数据库又会按旧参数重启、归档停掉——状态检查会报异常，重新部署新版本即恢复。
- **磁盘**：本机 `pitr` 卷约为「压缩后的库 × 8 + 7 天的 WAL」。库很小时（测试环境）每天的 WAL 主要是每分钟一个的空段，压缩后每个约几十 KB。
- **测试环境不需要任何新变量**：不配异地照常工作。新的定时任务（每天基础备份、每 15 分钟状态检查）要重新运行一次「服务器初始化」才装上；在那之前由部署兜底做基础备份。
- 需要负责人做的：选对象存储并在 `.env` 填四项（加密口令自己另存一份）；可选地开一个心跳监控；提供正式环境的服务器。见 `docs/deploy.md`「恢复到任意时间点」。

## 已知限制

- 本机 `pitr` 卷不加密（和数据库的数据卷同一块盘、同样的权限边界）；只有异地副本是加密的。
- 异地只有一份（一家服务商）。需要「两家互为备份」时再加。
- 状态检查只看「备份在不在、新不新」，不证明「能恢复」；能恢复靠 CI 演练和每季度的人工演练。
- 恢复替换正式数据是逻辑导出导入：库到几十 GB 以上时会变慢，到时再考虑物理替换。
