# ADR 0065：运营代改乘客邮箱也要双人复核

- 状态：已采纳（2026-11-02，M4-31）。负责人只收最终结果，取舍按「安全、保守、可回退」定，全部写在这里。
- 补充 ADR 0060「运营代改、代处理」：运营代客人改单（`PATCH /platform/v1/orders/{id}`）时改了乘客邮箱，这一项不再直接生效，另走双人复核；同一次提交的其余字段按 ADR 0060 照常拆分。
- 补充 ADR 0061：「已知缺口：运营代客人改单可以一个人改掉乘客邮箱」由本篇补上。核实方式沿用 `VIEW_LINK_VERIFICATIONS`。
- 补充 ADR 0023：新增复核类别 `order.passenger_email`。
- 补充 ADR 0030：不新增操作。审核用 ADR 0061 的 `order.view_link_review`（角色勾选表「订单链接重发 · 审核」那一格），发起用现有的 `order.manage`。
- 编号：写这篇时 main 上最大是 ADR 0061，0062、0063 给 M4-28，0064 给 M4-32；这里用 ADR 0065。迁移：M4-30 用到 0231，这里用 0235（空出 0232–0234 给并行的任务）。

## 背景

M4-30 让「把订单链接发到核实后的新邮箱」必须另一位同事批准：收到链接的人能看、改、取消这张单，等于把订单交给他。

但运营和客服「代客人改单」能一个人直接改掉乘客邮箱（M3-03 / M4-29 起就是这样：乘客信息属于联系信息，直接生效）。改完以后，带订单管理链接的通知（订单修改、取消、派车、事后加收……）都发到新地址，效果和「发到新邮箱」一样，却绕过了复核。社会工程最容易得手的就是「客服一个人接电话、一个人决定」这一步。

## 决定

### 1. 什么时候要复核

只在**平台员工代改**（`PATCH /platform/v1/orders/{id}`）且**改了乘客邮箱**时：

- 新邮箱和订单上的邮箱按盲索引的口径（NFKC、不分大小写、去首尾空白，`normalizeEmailForIndex`）比较，是同一个地址就不算改，直接生效（只是写法不同，收件箱是同一个）；
- 订单上原来没有邮箱、现在加一个，同样要复核（一样是把通知交给这个地址）；
- 不区分官网单和渠道单：渠道的单平台不给客人发信，但邮箱仍然是订单的联系信息、之后可能被别的流程用到，按保守处理一律复核。

不经过复核的（不变）：

| 谁改 | 为什么 |
| --- | --- |
| 客人自己在官网用订单链接改（`PATCH /site/v1/order`） | 拿着链接的人本来就能看、改、取消这张单，改邮箱没有多交出什么 |
| 渠道替客人改（`PATCH /sales/v1/orders/{id}`） | 渠道是客人的代理，客人的通知本来就由渠道发；平台没法替渠道核实 |

### 2. 一次提交里怎么拆

在 ADR 0060 的拆分之上再拿出一项：

| 部分 | 处理 |
| --- | --- |
| 乘客邮箱（改了的话） | 发起复核 `order.passenger_email`；订单上的邮箱不变 |
| 其余联系信息（姓名、电话、即时通讯、备注） | 直接生效，通知供应商和已派的司机（ADR 0060） |
| 履约字段（时间、地址、航班号、人数行李） | 生成修改申请，等供应商确认（ADR 0060） |

- 三者在**同一个事务**里：校验、报价、容量任一失败，整个回滚，复核也不会发起。补差价被拒（402）是在事务提交之后，这时联系信息已生效、复核已发起，和 ADR 0060「联系信息和差价无关」同一个理由，有意不回滚。
- 联系信息那一行里的乘客对象，邮箱保持原来的；通知（`order.changed`）在这时照旧发到**原来的**地址。
- 邮箱的复核不挡别的：等审核期间其余字段照常能改（包括再提履约字段，只受 ADR 0060 的 `CHANGE_IN_PROGRESS` 约束）；只是不能再发起一次改邮箱（409 `PASSENGER_EMAIL_REVIEW_PENDING`，`details.approval_id`）。
- 只改了邮箱：没有改单记录，应答 **202** `{ change: null, email_review }`；有别的改动时 200 `{ change, email_review }`（`change` 和以前一样，两类都有时是待确认的那一行）。

### 3. 接口

`PATCH /platform/v1/orders/{id}` 的请求体（`PlatformOrderChangeRequest`）在 `OrderChangeRequest` 之上：

- `passenger` 可以只给要改的那几项（至少一项）。运营后台只看得到打码后的乘客信息（ADR 0055），要求三项都给就得先「查看」再原样抄回去；只给要改的那几项，没给的按订单上现在的。渠道、官网的请求体不变（三项必填）。
- 新增 `email_review: { verification, reason }`：改了邮箱时必填（没写 400，`/email_review` REQUIRED），没改邮箱却写了 400 NOT_APPLICABLE。核实方式和「发到新邮箱」同一套（回拨下单电话、用下单邮箱来信、核对订单细节、核对付款信息、其他）；原因最多 500 字，进复核的发起说明。

运营订单详情 `GET /platform/v1/orders/{id}` 多一项 `pending_email_review`（等审核的那一条，只有打码地址、核实方式、发起人、时间），没有时 null。

### 4. 复核 `order.passenger_email`

- 发起：`order.manage`（运营、客服，和代改单同一批人）。写一条复核（摘要「把订单 NZ… 的乘客邮箱改成 打码地址」，内容只有订单编号、订单号、打码后的新旧地址、核实方式）和发起审计。
- 审核：`order.view_link_review`（超级管理员、运营）。客服发起、运营审核；两位运营互审，或超级管理员审。发起人不能批自己发起的（通用规则，`APPROVAL_SELF_REVIEW`）。限定了数据范围的员工只看得到、审得了范围内的单（`orderScoped`）。
- 批准时（审核人的事务里，先锁订单、后锁这条记录）再核对一遍：
  - 订单还能改乘客信息（服务没开始，`orderChangeStillApplicable`）；
  - 没脱敏；
  - 订单上的邮箱还是发起时的那个（按同一口径比）——审核期间客人用订单链接、或渠道改过的，批准会 409 `APPROVAL_STALE`（`details.reason = EMAIL_CHANGED_SINCE_REQUEST`），审核人驳回即可。审核人批的是「从旧地址改成新地址」，不能覆盖客人后来自己填的。
  核对通过后按**一次直接生效的联系信息改动**处理（`order_changes` 记一行，发起人是代改的那位员工）：写订单、通知供应商和已派的司机、`order.changed` 告诉客人（这时收件人已是新地址，链接在发信时新签发）、写审计（审核人）。
- 驳回、撤回：订单不动，不发任何信。
- 为什么用 `order.view_link_review` 而不新增操作：两件事审的是同一个问题「这个新邮箱是不是客人本人的」，审核人是同一批人；新增操作要在角色勾选表加一格，已有的自建角色要么没人能审、要么被动多出权限（ADR 0052、0060 同样的考虑）。勾选表那一格的说明改为「审核把订单链接发到新邮箱、代客人改乘客邮箱」。

### 5. 新邮箱存在哪

`passenger_email_changes`（平台表，迁移 0235）。只有等审核期间留着**新邮箱**和**发起时订单上的邮箱**（批准时比对用），都按乘客信息加密（`sealRecipient`，发起时这单的供应商的密钥，两份密文的附加数据各带编号，互换位置解不开），有结论（批准、驳回、撤回）后马上清空；数据库约束保证只有 `pending_review` 的行能有地址、等审核的行一定有新邮箱、批准的行一定记着生效的那次改单。同一张单同时只有一条在等（部分唯一索引）。

复核记录（`approvals.payload`）、审计、应答、订单详情里只有打码后的地址。改单记录（`order_changes` 的前后值）和以前一样存完整乘客信息（加密，ADR 0057），审计写入时打码（ADR 0055）。

已知限制（和 ADR 0061 一样）：等审核期间换了乘客信息的密钥，这一行解不开，批准会失败，审核人驳回后重新发起即可。等审核期间订单被脱敏（用车后 180 天），批准会 409，驳回即可；这一行的密文到有结论时才清，不加进脱敏任务（行数极少、正常几分钟到几小时就有结论）。

### 6. 页面

- 订单详情「代客人改单」框新增「乘客的新邮箱」（留空不改）。填了以后出现提示「改乘客邮箱需要另一位同事批准……批准前订单上的邮箱不变，通知照旧发到原来的邮箱；同一次提交的其他内容照常处理」，以及必填的「怎么核实的客人身份」「原因」。保存后的提示把两件事都说清楚（如「已改好，已通知供应商和司机；乘客邮箱改成 xx***@… 需要另一位同事在「待审核」里批准，批准前订单上的邮箱不变」）。
- 有等审核的改邮箱时：订单详情「乘客」下面显示「改成 打码地址 在等另一位同事批准（某某 发起）……」和「去待审核」；改单框里不再显示新邮箱输入框，说明处理完之前不能再改。
- 批准、驳回、撤回沿用现有的「待审核」页：类别名「代客人改乘客邮箱」，变更列出订单号、乘客邮箱（旧 → 新，打码）、核实方式；批准按钮上方写明「批准后之后带订单链接的通知都发到新地址，等于把订单交给这个邮箱的主人……审核期间客人自己改过邮箱的，批准会失败，请驳回」。

## 回退

- 接口和页面一起回退即可：新表、复核类别都是加法；回退后等审核的那几条在「待审核」里批不了（类别不认识），驳回或直接留着都不影响订单。
- 回退后运营代改邮箱回到「直接生效」，即恢复 ADR 0061 写的缺口。

## 不做

| 内容 | 为什么 |
| --- | --- |
| 发起时给原来的邮箱发一封「有人申请改邮箱」 | 要加通知事件和模板；客人多半就是因为原邮箱用不了才来电。复核已挡住一个人的社会工程，需要时再加 |
| 批准后给原来的邮箱发「邮箱已更改」 | 同上 |
| 审核人看新邮箱全文 | 和 ADR 0061 一致：复核里只有打码地址，审核人看的是核实方式和原因 |
| 渠道、客人改邮箱也复核 | 见第 1 节：他们本来就有权改 |
| 改电话也复核 | 电话不决定通知发到哪；平台的通知只发邮箱 |

## 测试

- 单元（`packages/domain/src/passenger-email-review.test.ts`）：同一个地址的不同写法不用复核、原来没有邮箱要复核；批准时的拒绝原因（已脱敏、审核期间被改过）。
- 集成（`apps/api/src/passenger-email-review.itest.ts`，真实 PostgreSQL + 本机假 SMTP）：原来一个人能改掉的请求现在 400；没写核实方式 400 且什么都不改；同一次提交的姓名直接生效、邮箱不变、新地址收不到信、旧地址收到修改通知；复核记录、应答、订单详情、审计里只有打码地址；新旧两个地址加密存、有结论清空；客服（发起人和别的客服）不能批、运营发起的自己批 409；批准后邮箱改了、新地址收到带链接的通知且能打开订单；驳回和撤回不改不发、可以重新发起、同一张单只能有一条在等；履约字段等确认、备注直接生效、邮箱进复核三者互不阻塞；只改邮箱 202、没有改单记录；同一个收件箱的不同写法直接生效；客人用订单链接改邮箱照旧直接生效、审核期间客人改过的批准 409；渠道改邮箱照旧直接生效；财务、风控、只读 403，租户令牌 401，接单的供应商看不到新邮箱和复核、别家供应商读不到这张单，数据范围外的自建角色 404、范围内的能批。
- 页面（`apps/web/src/pages/platform/passenger-email-review.test.tsx`）：填了新邮箱才提示、核实方式和原因必填、提交内容、结果说法、等审核状态和「去待审核」、待审核页的类别名和变更。
