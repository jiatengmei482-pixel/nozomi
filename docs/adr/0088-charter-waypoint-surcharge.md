# ADR 0088：包车途经加价（第一期，最小改动）

- 状态：已采纳（2026-11-13，PR #187 独立审查两轮通过）。
- 依据：业主「日本时间制包车产品策划方案」第十三、十四节（`docs/requirements/charter-waypoint-surcharge.md`）。本篇只做第一期的最小改动；第二、三期不在本篇。
- 补充 ADR 0073（包车区域加价）、ADR 0020（报价引擎）；沿用 M8-38「重叠取最高、大区不盖小加价区」。

## 范围

**做**：途经加价规则、包车报价和订单带有序经停点、引擎累加途经加价、官网价格明细、下单页编辑经停点、订单详情和司机端显示行程。

**不做**：按时长自动选套餐（不按行程计价时套餐仍由客人选；按行程计价见 ADR 0089）、预收超公里（不选「按行程计价」时，超时、超公里仍按现有服务后加收；按行程计价见 ADR 0089）、`/sales/v1` 开放经停点、嵌入组件、预订草稿、模型线路、在线改经停点（客服或取消重下）。

## 决定

### 1. 价格规则

包车区域加价规则（价格方式 `charter_area_surcharge`）的 `price_rules.params` 加可选整数 `waypointSurchargeMinor`（「途经加价」，≥ 0，按车型组 × 套餐，商品币种，上限沿用 `PRICE_LIMITS`）。**没设 = 这个区域对经停点没有规则**（不当 0；要不加钱就明填 0）。不加列、不迁移；已有规则含义不变。`/tenant/v1` 价格规则接口、导入导出加这一项（旧模板照旧导入），供应商后台「区域加价」表加「途经加价」列和批量设置。

### 2. 经停点

- 包车报价请求（`POST /site/v1/quotes`，`category: charter`）加可选 `waypoints: [{ name, lat, lng, stay_minutes }]`，有顺序，最多 10 个；其他品类给了 400 `NOT_APPLICABLE`。引擎的 `QuoteRequest` 加可选 `waypoints: [{ lat, lng }]`（只用坐标）；名称和停留分钟只存在报价快照的 `snapshot.request.waypoints`（`[{ name, lat, lng, stay_minutes }]`），引擎不看。
- 经停点随报价快照的 `snapshot.request` 锁定，价格明细随结算价明细（`orders.settlement`，租户可读）锁定。
- **订单加一列 `waypoints jsonb`（一个迁移，可空，不回填）**，下单时从 `snapshot.request.waypoints` 写入。原因：报价快照所在的 `quotes`、`order_sales` 只授权给平台账号（迁移 0020、0024），供应商订单详情和司机端走租户事务读不到；救援改派后的新供应商同样读不到原报价；改授权会把报价快照里的对外价暴露给租户（违反规则 4）。供应商、司机、官网、运营都从 `orders.waypoints` 读；这一列加进订单现有的「不可改列」触发器（迁移 0031、0035 等里的 before update of 触发器），下单后谁都不能改。
- 改期重新报价用 `quote.request`（展开），自动带上经停点；**救援改派（`rescues.ts` 第 372 行起逐个字段传给 `previewPlatformQuote`）要显式加上 `waypoints`**。

### 3. 引擎（在现有上 / 下车加价之后）

每个车型组：

1. 每个经停点过和上 / 下车同样的运营判断、禁行判断（落在商品报价区域的禁行区 → 整个商品不报，同 M8-36）。
2. 经停点落在加价区域里：`areaSurchargeFor` 加第三种端点 `waypoint`，取 `waypointSurchargeMinor`；**在挑规则（`sameCombo`）这一步就把没有 `waypointSurchargeMinor` 的规则过滤掉**（没设 = 这个区域对经停点没有规则，不能当 undefined 去比大小）；用 `prefer: "highest"` **归到途经加价最高的那一个区域**（重叠取最高）。
3. 经停点在商品自己的区域里、且不在任何有可用途经规则的加价区域里 → 不加。经停点同时在商品区域和有途经规则的加价区域里 → 按 M8-38 收加价区域的途经加价（待确认第 1 条）。
4. 经停点落在加价区域里、但这些区域对这个车型组 × 套餐都没有可用的途经规则（没设、停用、未生效），而且点不在商品区域里 → **这个车型组不报**（同现有上 / 下车那一端报不出的口径，`quote.ts` 第 732 行），原因代码沿用上 / 下车那一端的现有原因（`NO_PRICE_RULE` / `PRICE_RULE_DISABLED` / `PRICE_NOT_IN_EFFECT`）。经停点**哪个区域都不在**（既不在商品区域也不在任何加价区域）→ 这个车型组不报，新原因 `WAYPOINT_NOT_PRICED`，官网转人工报价并指出是第几个经停点。
5. **同一区域只加一次**；**已因上 / 下车计价的区域不再加**——「已计价」只认上车、下车各自最终选中的那个加价区域（明细里的 `pickup.areaId` / `dropoff.areaId`）；那一端只在商品区域里（`areaId` 为 null）就没有已计价区域。选中区域的加价金额为 0 也算已计价（待确认第 2 条）。
6. 剩下各区域的途经加价相加，**并进现有的 `surchargeMinor`**，`tripPrice` 不改，调价照旧作用在合计上。顺序：套餐 → 上下车加价 → 途经加价 → 调价 → （加急、夜间、附加服务、司机语言，现有）→ 平台加价。
7. 结算价明细 `areaSurcharge` 加 `waypoints: [{ areaId, priceRuleId, amountMinor, stopSeqs }]`，**只在带经停点时写**。

**不带经停点时，报价、明细、快照与现在完全一致。**

### 4. 官网价格明细

`/site/v1` 报价应答加简单的 `price_breakdown`（对外价；**只增字段**——不带经停点的报价也会多出这一项，但原有字段、价格、快照不变）：套餐、上车、下车、各途经区域、调价、其他费用。各项用现有 `sellEquivalentMinor` 换算，**套餐项倒算**（= 对外总价 − 其余各项），吸收尾差，各项之和等于总价。`/tenant/v1` 只给结算价明细（规则 4）。

### 5. 页面

- 官网包车下单页：上车点下面「途经景点（选填）」，复用现有地址框，可排序、删除，最多 10 个，每个填停留分钟；提示「价格按您填的途经景点计算；当天临时去其他区域可能会加收」；报价卡片显示 `price_breakdown`。
- 订单详情（官网、运营、供应商）和司机端显示行程：上车 → 经停点 → 下车（名称、停留）；司机端不显示任何价格。

## 最终报价公式

「按行程计价」（超公里费、超时费预收、按总时长选套餐、服务器算全程路线）见 **ADR 0089**；它取代本篇「不预收超公里」那一句。

## 验证

- **PR-0 回放摘要**：给 M8-34 的只读回放报告（`area-role-preview` 接口）加：
  - 固定截止时间参数 `until`：前后两次用同一个 `until` 和天数，回放的是同一批询价日志（不受窗口滑动影响）；
  - 结果摘要 `resultDigest`（每条日志 × 每个候选商品的报价结果按固定顺序序列化后的哈希）和条数，另给逐条摘要（日志 × 商品），出现差异能定位到具体哪条；
  - 状态摘要 `stateDigest`：回放用到的商品、价格规则、区域的当前状态哈希。**两次的 `stateDigest` 不同就判这次比对无效**（期间有人改了价格或区域），要重跑。
  
  引擎改动部署前、后各跑一次，**状态摘要相同且结果摘要相同 = 不带经停点逐分不变**。回放只覆盖 domain 层的报价计算；API 层的报价快照和应答不变由集成测试保证。

- 策划方案 13.9 的 8 条（第 8 条「下单后删除途经区域退差」本期按「取消重下」验证）和 13.4 的 5 个算例做成测试，例如：富士山地区途经加价 10,000、10 小时套餐 55,000，「新宿 → 五合目 → 河口湖 → 忠灵塔 → 新宿」结算价 65,000、对外 71,500；下车在富士山时只收下车加价。

## 补充（2026-11-13，M9W-06）

- 修改包车区域加价（`PUT /tenant/v1/products/{id}/price-rules/{ruleId}`、批量 `update`）时，请求里**没有** `waypoint_surcharge` 这个键 = 保留原来的途经加价；显式传 `null` 才清掉。和导入没有「途经加价」列的旧模版同一口径，防止旧页面、旧对接方改上 / 下车加价时把途经加价清掉。
- 按行程计价先核城市（不存在或停用 400 `UNKNOWN_CITY`，和普通询价一致）、再查这个城市能选的套餐（没有就直接 `NO_PRODUCT`），最后才逐段估路线；城市不对、没有套餐时不调谷歌。
- 上一条按规则 id 沿用：省略这个键的同时改了 `area_id`，原来的途经加价跟着这条规则走到新区域（和导入旧模版同一口径）；要换区域又不想带过去，请显式传值或 null。
- 没有能选的套餐时不估路线，应答里没有 `itinerary_route`（OpenAPI 里本来就是可选），页面不显示「按行程预计…」。

## 补充（2026-11-13，M9W-10）：经停点报不出时对外的原因

第 3 节第 4 条：经停点落在加价区域里、但那些区域对这个车型组 × 套餐都没有可用的途经规则（没设、停用、未生效），且点不在商品区域里 → 这个车型组不报，原因码沿用上 / 下车那一端的（`NO_PRICE_RULE` / `PRICE_RULE_DISABLED` / `PRICE_NOT_IN_EFFECT`）。这条**在引擎和平台内部不变**；本补充只改**对外**怎么说：

- 引擎：只有经停点那一端报不出（上车、下车两端都报得出）时，拒绝里另带 `stopSeq`（第一个报不出的经停点，从 1 起），原因码照旧。上 / 下车有一端报不出时和以前完全一样，不带 `stopSeq`（去掉经停点也报不出，不能叫客人去掉经停点）。
- 对外（`sales-quotes.ts`，官网和渠道共用）：凡带 `stopSeq` 的拒绝一律报 `WAYPOINT_NOT_PRICED`，`waypoint_stop_seqs` 指出是第几个经停点——和「经停点哪个区域都不在」同一个说法，官网转人工报价并指出是哪个点。以前这种情况落到默认分支变成 `NOT_AVAILABLE`，页面叫客人「换一个时间」，对客人是误导。
- 平台内部（询价日志 `quote_logs.rejects`、未覆盖需求的 `refusal_counts`、报价试算）仍是原始原因码，方便运营找到是哪个区域缺了途经加价。平台端询价日志接口 `GET /platform/v1/channels/{id}/quote-logs` 另给每条拒绝的商品、车型组和原始原因码（`rejects`）；`/tenant/v1` 没有询价日志。
- **只影响对外的原因，不影响价格**：报得出的报价、明细、快照逐分不变；不带经停点的询价报价和原因都不变（golden、`area-surcharge.test.ts`、`charter-waypoints.itest.ts` 原样通过）。
- 通用原因 `NOT_AVAILABLE`（供应商内部原因：没设价、停用、价格超限、汇率取不到等）的页面文案改为「这个行程暂时无法在线报价，请联系客服人工报价，或调整行程后再试。」，不再让客人换时间——真的和时间有关的各有各的原因（`OUTSIDE_SERVICE_TIME`、`LEAD_TIME_TOO_SHORT`、`SERVICE_TIME_PASSED`、`SOLD_OUT`）。
