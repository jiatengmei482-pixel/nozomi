# ADR 0082：订单的举牌姓名、乘车人姓名和电话（正式字段）

- 状态：已采纳（业主 2026-11-11 定，M8-32 实施）。
- 取代 ADR 0079 第 4 节「先写在给司机的备注最前面」的临时做法（M8-27）；ADR 0081（M8-33）里「航班号写进备注」只保留给改用点对点商品报价的接送机行程。
- 补充 ADR 0055、0057（乘客信息打码、脱敏、加密）。
- 编号：写这篇时 main 上最大是 ADR 0081（M8-33），这里用 0082。

## 业主定的规则（roadmap M8-32 为准）

1. 订单新增「举牌姓名、乘车人姓名、乘车人电话 / WhatsApp」三项，**只做新增**，不删不改旧数据。
2. 新订单写入这三项；旧订单保留原来的备注，不改写。
3. 司机页、供应商后台、运营后台都单独显示这三项。
4. 修正订单页「为他人预订」时把预订人标成乘车人的问题。

## 决定

### 存在哪里：乘客对象里的 `rider`

- 存进订单已有的乘客对象（`orders.passenger` 和它的密文 `passenger_enc`）：`{ name, phone, email, rider?: { signName, name, phone } }`。**不加新列、不做迁移。**
- 理由：这三项和联系人一样是个人信息。放在同一个对象里，现有机制自动覆盖它们，不用另写一套，也就不会漏：
  - 加密：整个对象一起加密（ADR 0057）；
  - 明文占位：不写明文时整个对象换成占位，`rider` 只留在密文里；
  - 脱敏：保存期满后整个对象换成 `[已脱敏]`，`rider` 随之清除（ADR 0055）。
- 三项都没有时不存 `rider` 这个键。旧订单原样，读出来是「没有乘车人」。
- 盲索引（查订单用）不变，只按联系人的邮箱、电话、姓名。

### 接口

- 下单 `POST /site/v1/orders` 新增选填的 `sign_name`、`passenger_name`、`passenger_phone`：
  - 姓名和电话要么都给、要么都不给；
  - 电话要国际格式；
  - 超长报 `TOO_LONG`。
  - 联系人 `passenger` 仍是预订人，确认邮件发给他。
  - 渠道下单接口（`/sales/v1`）这次不加。
- 订单的应答（渠道、官网订单页、供应商、运营）：`passenger` 只有联系人三项，另加顶层的 `rider`（`{ sign_name, name, phone }`，没有为 null）。司机页的 `order.rider` 同样如此。OpenAPI 新增 `OrderRider`。

### 打码、脱敏、改单

- 运营后台默认打码：`rider` 的姓名、举牌姓名按姓名规则打码，电话按电话规则（`maskOrderValues` 认 `rider` 键）；手写内容里出现的乘车人姓名也会打码。点「查看」（`POST /platform/v1/orders/{id}/passenger/reveal`）返回 `rider` 原文，审计的字段名多一项 `rider`。
- 推送内容、改单前后值的副本：
  - 不写明文时 `rider` 换成 null（`replacePassengers`）；
  - 脱敏时同样换成 null（`scrubOrderValues`）。
- 改乘客信息（运营代改、渠道改单）只改联系人三项。改单记录里只记联系人；生效时这一单原来的 `rider` 原样带上，不会丢。

### 客人页（`/book/new`、订单页）

- 第 3 步的举牌姓名、为他人预订的乘车人姓名和电话改成单独提交，不再拼进备注。
- 订单页：为他人预订时，联系人那几项标为「预订人」，另显示「乘车人」「乘车人电话 / WhatsApp」；有举牌姓名时显示「举牌姓名」。

## 不做的

- 不改旧订单：M8-27 以来写在备注最前面的「举牌姓名：/ 乘车人：」原样保留。
- 不给渠道接口加这三项（以后渠道要时另议）。
- 工单详情的打码按「这一单用过的姓名」找，暂时不含乘车人姓名（`listPassengerNames` 读的是联系人和改单前后的姓名）。工单里提到乘车人姓名的很少，记为后续改进。
