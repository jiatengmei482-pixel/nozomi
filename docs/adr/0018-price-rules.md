# ADR 0018：价格规则与调价规则——计价、调价链、取整、唯一性、节假日日历

- 状态：已采纳（2026-10-09，M1-04）
- 接上 ADR 0016 里留给本任务的三件事：上架校验的「价格规则」一项改为真实判断（商品从此可以经接口上架）、「调价规则」一项的判断、子品牌的取整单位。

## 背景

M1-04 做商品的第 ③ 步：价格规则（一口价 / 里程 + 时长 / 包车套餐）、调价规则、价格日历。需求见《用车报价服务平台》「4. 商品 · ③ 价格规则与调价规则」和「报价引擎」的计价公式、调价、取整规则；页面规范见 `docs/design/pages/tenant-prices.md`。完整的报价引擎是 M2-01，这里只实现它里面「命中价格规则 → 基础价 → 调价 → 取整」这一段，并保证以后的报价和现在的价格日历用同一个函数。

## 决定

### 表

迁移 `0014_price_rules.sql`：

| 表 | 内容 |
| --- | --- |
| `price_rules`（租户表） | 商品、区域、车型组、方向（接送机）、套餐时长（包车）、计价方式、`params`（jsonb，各种计价方式自己的几个数）、生效日期、启停 |
| `adjust_rules`（租户表） | 商品、名称、出行日期范围、周期（jsonb）、时段（jsonb）、适用的区域 / 车型组 / 方向 / 套餐（数组，空 = 全部）、步骤（jsonb）、`position`（顺序）、启停 |
| `holidays`（平台表） | 国家、日期、各语言的名称 |
| `brands.rounding_unit` | 子品牌的取整单位，默认 1 |

- 两张租户表带 `tenant_id`、开行级安全、只授权给租户角色；外键都带着 `tenant_id`（接不到别的供应商的商品和区域上）。平台角色碰不到它们。
- 商品删除时价格和调价跟着删；区域删除时它的价格跟着删（被已上架商品用着的区域本来就删不掉）。
- **唯一性没有用数据库的排他约束**（需求文档的数据模型写的是排他约束）：按「组合 + 日期范围」做排他约束要装 `btree_gist` 扩展，而本项目的做法是不依赖数据库扩展（ADR 0002），集成测试又是每个测试一个 schema、扩展装不到每个 schema 里。改为在应用里检查，并且可靠：价格的每次写入都先锁住商品那一行，同一个商品的写入因此排成了队，检查和写入之间插不进别人的修改。

### 版本号和幂等

价格规则、调价规则属于商品，沿用 ADR 0016 的「一个版本号」：每次修改都用商品的版本号做 `If-Match`，成功后商品的版本号加一，应答带回新的版本号。创建类接口（新增一条、批量保存、新增调价规则）另带 `Idempotency-Key`。例外：调价规则的启用 / 停用不要求 `If-Match`（列表里的开关）。

### 价格规则

一条价格 = 区域 × 车型组 ×（接送机：方向；包车：套餐时长）× 生效日期 + 计价方式和它的几个数 + 启停。

| 计价方式 | 品类 | 字段 |
| --- | --- | --- |
| `fixed` 固定一口价 | 接送机、点对点 | 基础价 |
| `mileage_time` 里程 + 时长 | 接送机、点对点 | 起步价、起步里程（米，100 的整数倍）、起步时长（分钟）、超出每公里单价、超出每分钟单价、最低消费（可不设） |
| `charter_package` 包车套餐 | 包车 | 套餐公里、套餐价、超时单价（每小时）、超公里单价（每公里）；套餐时长在组合里 |

- 金额是子品牌币种的最小货币单位整数（ADR 0004），不采用需求文档示例里的 `{ amount, currency }` 写法（同 ADR 0016）。
- 区域、车型组必须是这个商品现在选的。后来被商品去掉的区域 / 车型组的价格仍然保留、返回，可以改（不换区域 / 车型组的话）、可以删，但不计入「该有价格的组合」。
- **生效日期看的是城市当地的用车日期**，两端都含；开始必填，结束可以不填 = 一直有效。需求文档只写了「生效日期」。
- **唯一性**（需求文档）：同一商品内「区域 + 车型组 + 方向或套餐时长」的生效日期不能重叠。落地时定下的细节：
  - 两头的日期都算：「到 03-31」和「从 03-31」是重叠的。
  - 计价方式不在组合里：同一个组合同一天只能有一条价格。
  - 「接送通用」和「接机」「送机」是三个不同的组合，可以同时存在；命中时以更具体的为准（需求文档）。
  - 停用的价格也占着日期（否则一启用就撞上）。
  - 违反时 409 `PRICE_RULE_CONFLICT`，`details.conflicts[]` 列出每一条被拒绝的规则和它撞上的那些。
- **批量保存**（需求文档的 `price-rules:batch-upsert`，路径按 ADR 0016 的习惯写成 `/price-rules/batch`）：新增、修改、删除一次提交，合计最多 500 条，全部成功或全部失败。重叠按保存之后的样子判断，所以一批里「删旧的、加新的」同一个组合不算冲突。单条的新增 / 修改 / 删除走的是同一段代码。
- 里程 + 时长的计价方式现在就可以填（需求文档的分期把它放在二期，等谷歌地图路线预估）。配了它的商品能上架；路线预估上线前，报价引擎拿不到里程和时长，价格日历按「不超出起步」显示。要不要在路线预估上线前先不开放，由负责人定（页面规范 15.1）。

### 基础价（需求文档的计价公式）

`packages/domain/src/pricing.ts` 的 `basePrice`：

- 固定一口价：P = 基础价。
- 里程 + 时长：P = max(P_min, P_start + max(0, D − D_start) × p_km + max(0, T − T_start) × p_min)。
- 包车套餐：P = P_pkg + max(0, H − H_pkg) × p_hour + max(0, D − D_pkg) × p_km；报价时 H = 套餐时长。
- 里程按米、时长按分钟传入，换算成公里、小时**不凑整**（超出 500 米收 0.5 公里的钱，超时 30 分钟收半小时的钱）。需求文档没有写超出部分按什么粒度计。

### 调价规则

- 字段同需求文档：名称、出行日期范围、周期（每天 / 每周指定星期 / 指定日期 / 节假日日历）、适用区域、车型组、方向或套餐（空 = 全部）、适用时段、策略步骤、顺序、启停。
- **链式执行**（需求文档）：筛出匹配的规则，按顺序逐条执行，后一条以前一条的结果为基数；一条规则里的几步也是链式的。百分比步：× (1 + 基点 / 10000)；金额步：直接加减。都可以为负，不能为 0。
- **顺序即优先级**：排在前面的先执行。新增的排在最后；`PUT …/adjust-rules/order` 整体重排。
- **时段**：从开始（含）到结束（不含），结束可以写 `24:00`。结束不含是为了让相邻的两个时段（06:00–22:00 和 22:00–06:00）不会在交界的那一分钟同时命中。注意这和服务规则里服务时间的「两端都含」（ADR 0016）不同。需求文档示例里的 `00:00`–`23:59` 请写成不填时段（全天）或 `00:00`–`24:00`。
- **跨午夜的时段算在开始的那一天头上**（需求文档只说「可跨天」）：「每周五 22:00–06:00」是周五 22:00 到周六 06:00；出行日期范围和周期都按归属的那一天判断，所以范围到 12-31 的规则，元旦凌晨 01:00 仍然生效。
- 百分比的范围：下调不到 100%（−9999 基点），上调最多 1000%。步骤最多 10 步，指定日期最多 366 个，一个商品最多 100 条调价规则。
- **调完不大于 0 的规则存不了**：启用的规则单独作用在它碰得到的、启用且没过期的价格上（按那条价格能报出的最低数算），结果不大于 0 → 400 `ADJUST_RESULT_NOT_POSITIVE`。价格后来降了导致已有的规则变成这样：价格照样能存，上架校验的「调价规则」一项指出来（不拦上架）；真到报价时算出不大于 0 的不报价。
- 「调得很多」（高于基础价 4 倍或低于一半）只提供判断函数 `adjustRuleIsUnusual` 给页面做二次确认，后端不拦。

### 取整（需求文档「取整规则」）

- 中间结果用分数精确保留（`ExactAmount`，分子分母是 bigint）：里程单价 × 米数 ÷ 1000、百分比连乘都不丢精度，不出现浮点数。
- **只在最后取整一次**：调价全部执行完之后，按子品牌的取整单位四舍五入（正好一半远离零，`money.ts` 的 `roundFractionToUnit`）。取整单位为 1 就是取整到最小货币单位。
- **没有调价规则命中时也取整**：基础价 20050、取整单位 100，报 20100。
- 取整管的是「基础价 → 调价」算完的那个数。加急费、夜间费、附加服务是填好的整数，由报价引擎（M2-01）直接相加，不再取整（需求文档：这三项独立计算、不参与调价）。
- **价格明细之和等于总价，尾差计入调价项**（需求文档）：明细里的基础价 = 基础价四舍五入到最小货币单位，调价项 = 取整后的结果 − 基础价。
- 取整单位存在子品牌上（需求文档的 `brand.rounding_unit`），可选的值由币种决定：没有小数的币种 1 / 10 / 100 / 1000，两位小数的币种 0.01 / 0.1 / 1 / 10 / 100（存成 1 到 10000 的最小货币单位）。只有管理员能改（`brand.manage`），对这个子品牌下所有商品立即生效。
- 取整单位没有放进子品牌的应答（`Brand`）里，而是单独一个接口 `PUT /brands/{id}/rounding-unit`，读取从价格规则、调价规则、价格日历的应答里拿：前端的接口约定测试把 `Brand` 的字段逐个钉住了，后端单方面加字段会让它失败。

### 时区

价格过没过期、调价的日期和时段，都按商品所在城市的当地日期和时刻判断（`service-time.ts` 的 `instantToLocal`），和服务器、浏览器在哪个时区无关。单元测试覆盖了跨日、夏令时开始和结束的那一夜。

### 价格日历

`GET …/price-calendar`：一个组合在一段日期里（最多 62 天）每天的结算价和命中的规则。一天按调价规则的时段切成几段，每段算一次，相邻的、命中同一批规则的并在一起。用的是 domain 的 `tripPrice`——以后的报价引擎也用它，所以日历上看到的就是会报出去的结算价（不含加急、夜间、附加服务）。数据量：一个商品的价格规则最多 2000 条、调价规则最多 100 条，一次请求把它们全部取出来在内存里算，62 天 × 每天至多 201 段。

### 缺价的组合

「该有价格的组合」：接送机 = 区域 × 车型组 × 接 / 送；点对点 = 区域 × 车型组；包车 = 区域 × 车型组 × 套餐（套餐 = 这个商品现有价格里出现过的套餐时长）。一个组合「有价格」= 有一条启用、还没过期的价格（方向是它自己或「接送通用」）；以后才开始生效的也算，另外标出哪天起。`GET …/price-coverage` 逐个给出；价格规则的应答里带概况。**缺价不是错**：不拦保存，也不拦上架（供应商可以有意不做某个组合）。

### 上架校验

| 检查项 | 必须 | 现在 |
| --- | --- | --- |
| `price_rules` | 是 | 至少 1 条启用且未过期的价格（结束日期不早于城市当地的今天）。不通过的原因：`NO_ACTIVE_PRICE_RULE`（一条都没有）、`ALL_PRICE_RULES_DISABLED`、`ALL_PRICE_RULES_EXPIRED` |
| `adjust_rules` | 否 | 可以没有。有启用中的规则会把某条价格调到不大于 0 时不通过（`ADJUST_RESULT_NOT_POSITIVE`），不影响能不能上架 |
| `inventory` | 否 | 功能在 M1-05，恒通过 |

商品从此可以经接口真正上架。已上架的商品改价格、删价格之后必须仍然通过校验，否则这次修改被拒绝（409 `PUBLISH_CHECK_FAILED`）。接口不再返回 `FEATURE_NOT_AVAILABLE`（domain 的 `publishCheck` 在不知道价格条数时仍会给出它，前端预览其余各项时用）。

### 节假日日历

调价规则的周期可以选「节假日」。**没有预置任何节假日数据**（CLAUDE.md 规则 1）：没有找到带明确许可、同时覆盖日本和韩国、可以稳定下载的公开数据源（日本内阁府有官方的 CSV，韩国的官方数据要申请接口密钥）。所以做成平台主数据，由平台在后台逐条登记（`PUT /platform/v1/holidays/{国家}/{日期}`，写审计日志），租户只读。没有登记数据的国家，选了「节假日」也不会生效；租户接口返回「哪些国家有数据」，页面据此提示。从官方来源批量导入（并注明来源和许可）是后续任务。

### 首页和列表上的数量

没有改 `GET /dashboard/summary` 和商品列表项的结构（前端的接口约定测试把它们的字段钉住了）。另设 `GET /tenant/v1/price-overview`：每个商品有没有启用且未过期的价格、价格和调价的条数，外加首页用的两个数（只数草稿和已上架的商品）。

### 权限（需求文档 §11）

价格规则、调价规则、价格日历沿用 `product.read`（管理员、商品价格、只读）和 `product.manage`（管理员、商品价格）；取整单位用 `brand.manage`（只有管理员）；节假日租户侧用 `master_data.read`，平台侧用 `master_data.read` / `master_data.manage`。没有新增操作。

### 规则 4

价格规则是供应商的结算价。这些接口的任何返回里都没有对外价和加价比例（那是渠道一侧的事，M2-04），有测试逐个接口核对。

### 页面规范提出后补的（`tenant-prices.md` 14.3）

- 精确值的主单位写法：domain 的 `formatExactMajor(amount, currency)`（按币种小数位挪小数点，整数运算）。接口里的 `base` / `delta` / `after` / `unrounded` 仍是最小货币单位的十进制字符串，页面用它换。
- 方向的中文名按接送点类型取：`priceDirectionNames(placeType)`，车站是「接站 / 送站」。
- 批量保存的 400：每条问题的 `detail` 带 `ref`（新增的）或 `id`（修改、删除的）。上架校验「调价规则」一项的原因在 `detail` 里带 `rule_id`、`name`（在接口层加的，domain 的 `PublishIssue.detail` 仍然只有数字）。
- `price-overview`：每个商品带城市和缺价概况 `coverage { total, missing }`；`summary=1` 只返回两个数。缺价概况一次取回整个供应商的区域、车型组、价格（三条查询），在内存里按商品算。
- 价格日历的 `vehicle_group_id` 可以给多个（逗号分隔，最多 20 个），应答的 `groups` 里每个各一份；`days` 仍是第一个的。
