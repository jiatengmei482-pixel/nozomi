# ADR 0062：价格表导入第 1 阶段——写入工具、客人价倒算、批次与撤回

- 状态：已采纳（2026-11-02，M4-28）
- 接着 ADR 0059（第 0 阶段只读报告）。执行 ADR 0059 末尾「2026-11-02 补记：写入前的决定」A–E 和生效日期，不改变它们。
- 不改变 ADR 0012、0015、0016、0018、0020、0023 的任何规则：写入全部走现有的服务函数，校验、审计、行级安全和后台操作一样。
- 没有新增迁移。

## 背景

业主的价格表（表名「官网」费率）要先导入日本「机场↔地区」这一批（决定 D），挂在「NOZOMI 自营车队」下一个新的子品牌里，全部草稿（决定 B）。
表上的价是官网原价，也就是客人价（决定 A）；价格规则存的是供应商结算价，官网显示的对外价由渠道加价算出（ADR 0020、0023），所以要倒算。
地区只有名字，范围（中心点 + 半径）由我们出草稿、业主核对后才导（决定 E）。业主补充：地区按「机场服务的主要城市」归属，归属只用于分组和显示，不影响价格。

## 决定

### 命令 `pnpm price-sheet:import`

| 用法 | 连库 | 写 |
| --- | --- | --- |
| 离线计划：`--file --expect-sha256 --mapping --batch --out` + `--target <导出.json>` | 否 | 只写 `--out` 里的 plan.md、anomalies.md、plan.json |
| 离线估算：同上，把 `--target` 换成 `--assume-pricing 加价bp,下限bp,最低毛利,取整单位` | 否 | 同上；不核对主数据，只估偏差 |
| 连库 dry-run（默认）：`--tenant <编号> --channel <官网渠道编号>` | 读 | 不写数据库 |
| 写入：再加 `--apply` | 读写 | 只建这一批 |
| 撤回：`--revert --tenant --batch`，加 `--apply` 才删 | 读写 | 只删这一批 |
| `--print-target-sql`：打印目标环境只读导出用的 SQL | 否 | 否 |

- **默认只读**：不带 `--apply` 什么都不写；`--apply` 只能和 `--tenant`、`--channel` 一起用。
- **目标租户只来自参数**，工具不猜、不默认；所有写入都在这个租户的租户事务里（行级安全兜底）。
- 输出含价格：`--out` 在 git 仓库里拒绝运行，文件权限 600，终端只打印数字（同 ADR 0059）。
- 价格表要核对 sha256；价格表、映射、导出的写法不对整份拒绝，数据库不动。

### 写入只走现有的服务函数

- 子品牌 `createBrand`、区域 `createArea`（圆，ADR 0015 的 64 边形）、商品 `createProduct` / `updateProduct`、价格 `savePriceRules`（每次最多 500 条，和接口一样）、撤回 `deleteProduct` / `deleteArea`。不拼写入的 SQL，不绕过任何校验。
- 命令行没有登录用户：服务层的写入者（`ProductWriter`、`AreaWriter`）多一种 `SystemTenantPrincipal { tenantId, user: null }`，审计记为 `system` / `cli`（和主数据导入命令一样），不借用任何人的账号。接口层的写入者仍然只来自令牌，类型上也只有命令行能构造它。
- 这些服务函数原来要整个 `AppContext`，实际只用 `pool` 和 `now`；改成 `DbContext = Pick<AppContext, "pool" | "now">`，命令行不用起整个应用。接口层不受影响。
- **工具不建平台主数据**（城市、机场、车型组）：缺了、停用、机场还没指定城市、车型组没有表里的「人数 / 行李」组合，列为「拦住写入的原因」，整批不写，由平台按现有流程在后台建好再跑。

### 批次：认得出、能重跑、能撤回

- 批次号 `--batch`：字母、数字、短横线，3–24 位。
- 子品牌名 `价格表导入 <批次号>`，币种日元，取整单位 1。子品牌名在供应商下不重名，所以它就是「这一批建过没有」的依据。
- 这一批建的区域：营运区圆的备注名写 `价格表导入 <批次号>`（40 字以内），名称是表里的地区名。撤回时按它认。
- 商品：每个机场一个，按「这一批的子品牌 + 接送点」认；只建草稿，**从不上架**。
- 价格：一口价，开始日期 2026-11-01，不设结束日期；按「区域 × 车型组 × 方向 × 开始日期」认。
- **重跑**：已有的不再建；表里多出来的地区、车型补到已有的商品后面（不去掉已有的）；已有的价格和这次算出的不同（价、方向、日期、状态任何一项），或者同一区域车型组上方向重叠（通用和接机 / 送机），列为冲突，**整批不写**——不覆盖有人改过的东西。
- **不碰别的**：同城市里已有同名、但不是这一批建的区域，不动它也不建同名的，整批不写（ADR 0015 的同城不重名）。这一批的商品不是草稿了（被人上过架），整批不写。
- 中途失败：每一步是各自的事务，已提交的会留下；重跑同一批从断点接着做，或者撤回。
- **撤回**：删这一批子品牌下的全部商品（价格随商品删除）和这一批的区域。任何一个商品不是草稿、任何一个区域被这一批以外的商品选了（删区域会连带删掉那个商品在这个区域的价格），整批不动，列出原因。
  子品牌留下：没有删除子品牌的接口，数据库也没给应用账号删除子品牌的权限（ADR 0016）；空的子品牌没有商品，不参与报价。再导同一批时接着用它。

### 倒算：客人价 → 结算价（决定 A）

正向（报价引擎第 7、11 步，没有调价规则、加急、夜间、附加服务时）：

1. 结算价 = 一口价按子品牌的取整单位四舍五入（这一批是 1，即不取整）；
2. 对外价 = `sellPrice`：结算价 × (1 + max(加价比例, 渠道下限))，不足最低毛利补到最低毛利，渠道对外价取整单位大于 1 时向上取整、等于 1 时四舍五入到日元（ADR 0023）。
   加价比例按渠道的五级规则匹配（`resolveMarkup`：这一批的租户 × 机场所属城市 × 接送机 × 车型组）。

倒算（`inverseSitePrice`，`packages/domain/src/price-import.ts`）：

- 不另写一套公式。每个候选结算价都用上面同一个 `sellPrice` 正向算一遍；显示价随结算价单调不减，二分查找**显示价不超过表上价的最大结算价**。
- 正好等于表上价：导入。同一个显示价对应一段结算价时取最大的——实际加价最接近渠道设定的比例。
- 对不上：**不硬凑**（不加调价规则、不改取整），取低一档导入（显示价比表上价低，客人不会多付），列进偏差清单：表上价、倒算结算价、正向显示价、差额、高一档的显示价、原因（渠道取整单位、子品牌取整单位、加价步长跳过、低于最低可报价）。
- 连最小的结算价都超过表上价（最低毛利比表上价高）：不导入。
- 只看**不带日期**的加价规则：价格从生效日起一直有效。带日期的（促销）期间显示价会不同，命中的规则单独列出提醒。
- 子品牌、官网渠道、客人支付币种必须都是日元：跨币种的显示价随汇率每天变，倒算没有意义，渠道币种不是日元时拦下。
- 业主之后给草稿补夜间费、附加服务、调价规则，显示价会跟着变（那是业主的设置，不是导入的偏差）。

### 归属：只影响分组，不影响价格

- 「机场服务的主要城市」现有框架能表达：机场在主数据里的**所属城市**（`places.city_id`）就是平台的城市划分（ADR 0012：成田机场算东京），不是所在的行政市。商品的城市必须等于接送点的城市（ADR 0016），所以**商品的城市 = 机场的所属城市**，工具直接读这个字段，不另存归属，也不改主数据。
- 区域只能被同城市的商品选（ADR 0016），所以地区的圆建在机场所属的城市下面；同一个地区被几个城市的机场服务，就在每个城市下各建一个同样的圆。同一城市的几个机场共用一个。
- 地区自己的「归属主要城市」（京都地区→京都）框架里没有字段，只写在给业主的草稿里；要在系统里用它分组见 ADR 0063。
- 价格只由机场、地区、车型组、方向、表上价决定。单元测试固定：换机场的归属，价格规则（区域 × 车型组 × 方向 × 金额）一条不变；城市有单独的加价比例时，结算价随倒算变，官网显示价仍等于表上价。

### 范围和方向（决定 C、D、E）

- 只取日本表里的「机场↔地点」路线。地点名里有滑雪、码头、邮轮、港口，或以「港」结尾（空港、香港除外）的不导——宁可少导，确认后再补。
- 机场在前的一行是接机，机场在后的是送机。只列一个方向、说明页写了「反向同价」：接送通用；两个方向都列：同价通用，不同价拆成接机 + 送机，只有一边有价的原样只导那一边（进异常清单）；同一方向几行价格不一致：这一格不导。
- 映射文件（`--mapping`，不进仓库）：表里的机场名 → IATA 码；地区名 → `{ lat, lng, radius_m }`（半径 100 米到 100 公里，和区域的圆一样），待定的写 null；车型列名 → 车型组编码，不写时用第 0 阶段的建议编码，名字里没有座位数的必须写（或写 null 不导）。
  建议编码只给等级在现有四个里的列；Premium、Bus、Van、SUV、EV 这些等级要业主定的列不写进映射就不导（原因「等级不在现有四个里」），见文末补记。
- 机场的编码规定是 IATA 三字码（ADR 0012）：没有三字码的机场现在建不成接送点，这一批不导。

### 目标环境的只读导出

- 连不上的环境（staging）由有权限的人执行 `--print-target-sql` 打印的 SQL（`apps/api/src/repos/price-import.ts`，只有 select；参数是租户编号、官网渠道编号、国家码 JP），把结果（一行 JSON）存成文件交给 `--target`。
  内容：租户（编号、名称、状态）、渠道的定价参数、没删除的加价规则、日本的城市和机场（含所属城市、状态）、全部车型组（含组合）。
- 连库时工具执行的是同一条 SQL，由 domain 的 `parsePriceImportTarget` 解析；集成测试经它跑，导出和连库不会走两套口径。

## 2026-11-02 补记：第 2 阶段（测试环境写入日本第一批）前的规则

负责人授权代业主审定的最终表（地区 73 个、机场 28 个，「第二批」「不导」都不进映射或写 null）。对工具规则的影响只有两处，都先写了测试（`packages/domain/src/price-import.test.ts`）：

- **度假小镇按普通地区**：二世古、喜乐乐、留寿都名字里没有「滑雪」，按普通地区导入；范围判定不变——只有名字里写了滑雪（或港口、码头、邮轮、以「港」结尾）的才排除。测试固定这三个名字不被排除。
- **车型的等级要明写**：建议编码只给 Economy、Comfort、Luxury、Business 这四个现有等级的列。Premium、Bus、Van、SUV、EV 不在其中，归哪个等级、导不导是业主的决定，**映射文件必须写明**：写编码就按编码导（这一批 Premium → 豪华级 `VG-LUX-座位数`），写 null 就不导（这一批 Bus 14 / Bus 22 都写 null，改进方案见 ADR 0063 第 7 项）；没写的不导，列为「等级不在现有四个里」。以前没写时会按 `VG-PRM-5`、`VG-BUS-14` 这类建议编码去找车型组，找不到才拦住；现在直接不导，不会因为平台碰巧建了同名车型组就导进去。
- 「黑部立山水坝 / 雪墙」最终决定不导（车开不到水坝），映射写 null；工具把它列为「地区范围待定」，原因文字以最终表为准。


### 在测试环境执行的方式（2026-11-02）

- 平台主数据由平台账号经后台接口建好（车型组、给机场指定城市并启用），工具仍然不建主数据。
- 命令在测试环境用 api 服务自己的配置临时起一个容器执行（`bin/compose.sh run --rm --no-deps api node apps/api/src/cli/price-sheet-import.ts …`），连的是应用账号，不重启、不改任何常驻服务，命令行和文件里没有密钥。
  这一批的代码还没合并进部署的镜像，所以把分支的 `apps/api/src`、`packages/domain/src` 只读挂进这个临时容器（依赖和部署的镜像相同，分支先合并了部署的版本）；价格表、映射放在服务器的临时目录，用完删除。合并部署后直接用镜像里的命令。
- 顺序：只读导出 → `--target` 离线计划 → 连库 dry-run（无拦截才继续）→ `--apply` → 只读核对（新建的全是草稿、负责人原有的行逐行哈希不变、官网询价前后一致）→ `--revert` 的 dry-run。

## 2026-11-02 补记：改用业主的多边形围栏（第 3 步，批次 JP-2026-11-B3）

业主提供了他 2.0 调度后台导出的围栏（GeoJSON，每个地区一块不带洞的多边形，名字带「JP-」前缀）。地区范围改为以它为准，第 1、2 步的圆（中心点 + 半径）作废。不改框架：区域本来就支持多边形（ADR 0015）。

- **映射支持多边形**：地区可以写 `{ "polygon": [[经度, 纬度], …], "source", "note" }`，和圆二选一。围栏文件是不可信输入：解析映射时逐点检查坐标，按区域保存时的同一套规则整理（`normalizeRing` 去掉相邻重复点、统一成逆时针）并校验（`areaShapeIssues`：点数、共线、自相交、跨 180° 经线），有一块不合法整份拒绝。写入时来源记为 `pasted`（和在后台粘贴进来的图形一样），批次标记照旧写在备注名里，撤回方式不变。
- **范围**：围栏里名字对得上的地区都用围栏，原来「待定」的地区有围栏的移进第一批；业主定了不导的（八尾机场、港口、滑雪场、黑部立山）照旧不导。围栏里多出来、价格表没有的不导。
- **机场本身的多边形不导**：接送机的报价按客人选的接送点（机场）匹配，商品的接送点就是机场，不需要机场的区域。
- **重叠比价**：一个地址落在几个区域里时报价取结算价最低的（ADR 0020 第 4 步），没有优先级；业主的预期是更小、更具体的区域优先。所以写入前对同一机场商品下所有互相重叠的地区逐对比较：同一车型组、同一方向（通用的一格两个方向都算），大区域（按面积）的结算价比和它重叠的小区域低时，重叠处会报出比预期低的价——**跳过大区域的那一格**（通用的整格），列进 `overlap.md`。只去掉格子，不会产生新的冲突。domain 的 `priceImportOverlapCheck`，单元测试和集成测试都覆盖。
  这是临时方案，正式的「区域优先级」见 ADR 0063 第 8 项。
- 新批次 `JP-2026-11-B3`（不复用 B1，审计更清楚）。B1 撤回后它的子品牌是空的，按本文「撤回」的规定留下；B3 另建一个子品牌。
- **两块围栏校验不过（2026-11-02）**：「JP-名古屋-吉普力」「JP-名古屋市周边」自相交，没有导入；原始 GeoJSON 文件一律不改，修正只放在映射文件里。
  - 「JP-名古屋-吉普力」（11 个点）：第 9 点已经回到起点（首尾闭合），后面又多了第 10 点（离起点约 0.78 米）和第 11 点（又回到起点）。这是导出时多出来的一个尖刺：来回两条边重合在一起，围住的面积是零，客人地址不可能落在这不到 1 米的线上。只去掉第 10、11 两个点，前 9 个点一个不动，所以不算改形状（面积和边界都没变），按负责人确认用 B3 重跑补导，只新增这一个地区和它的价格。
  - 「JP-名古屋市周边」：第 16–17 点和第 28–29 点的边真的交叉，改了就是改形状，等业主在 2.0 后台修好再导。
