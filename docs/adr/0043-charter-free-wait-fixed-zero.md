# ADR 0043：包车的免费等待由平台固定为 0

- 状态：已采纳（2026-10-26，M4-10）
- 补充 ADR 0016「商品」的服务规则：包车的免等（`free_wait.general`）不再由供应商设置，只能是 0 分钟。
- 补充 ADR 0020「报价引擎」：报价时包车的免等一律按 0 分钟算。
- 不新增迁移（编号说明：0042 已被别的分支使用）。

## 背景

需求《平台运营端与渠道对接》「免费等待与 no-show」表：

| 场景 | 免费等待 | 起算时间 |
| --- | --- | --- |
| 包车 | 0（从约定开始时间计入套餐时长） | 约定开始时间 |

M1 的商品配置把包车当作「平台规定最少 0 分钟，供应商可以设得更长」，于是可以填 15 分钟、甚至不限时，官网上就显示「免费等待 15 分钟」（M3 验收发现）。包车按时长计费，开始时间到了就计入套餐，另给免费等待会和套餐时长重复计算。

## 决定

1. **规则在 `@nozomi/domain`**：`fixedFreeWaitMinutes(category)`（包车 0，其他品类 null），`effectiveFreeWait(category, value)`（报价、下单用的值），`fixedFreeWaitIssues(rules, category)`（保存时的校验）。
2. **保存时拒绝**：`PUT /tenant/v1/products/{id}/service-rules` 给包车填了 0 以外的值（含「不限时」）返回 400 `VALIDATION_FAILED`，原因 `FIXED_BY_PLATFORM`，`detail.minutes = 0`。
3. **已有数据不改**：不写迁移去改库里已经存下的非 0 值。原因：服务规则是供应商的数据，改它要留审计、要提示供应商；而它对客人和结算的影响只在报价那一刻，报价按 0 算就够了。
   - 报价（`quoteProduct`）一律用 `effectiveFreeWait`：从这一版起，包车的新报价、新订单的免等都是 0。
   - **上架检查不拦**：`fixedFreeWaitIssues` 不并入 `serviceRuleIssues`（后者也用于上架检查），以前存了 15 分钟的已上架包车不会因此变成「不能上架」。
   - 供应商后台打开这一步时显示「0 分钟 · 平台统一 · 不能修改」，有旧值时说明「以前存的是 15 分钟，报价时已经按 0 分钟算；保存这一步时会改成 0」，点保存就存成 0。
4. **已经下了的单不变**：订单里的 `free_wait_minutes` 是下单时的快照，旧的包车单照旧（官网照存下的分钟数显示）。
5. 客人看到的说法：包车写「不另计免费等待（从约定的开始时间起计入包车时长）」。

## 影响

- 供应商后台「服务规则」里包车没有免等的输入框。
- 集成测试：`site-categories.itest.ts`（保存被拒；库里留着 15 分钟时报价、下单都是 0）、`products-openapi.itest.ts`（`FIXED_BY_PLATFORM` 写进了接口说明并能触发）。单元测试：`products.test.ts`、`quote.test.ts`。
