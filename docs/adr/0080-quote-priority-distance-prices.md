# ADR 0080：报价优先级——接送机 / 点对点 一口价 → 一口价 + 区域外里程费 → 计程价；包车 服务城市 → 上下车加价区域

- 状态：已采纳（业主 2026-11-11 确认最终优先级；M8-30 实施）。
- **部分取代 ADR 0075 第二部分**（增强版 B）：0075 规定「点在运营区域里、但不在商品勾选的报价区域里 → 这个商品不报价，不退回基础价」。
  本篇之后，对**接送机、点对点**，这句话只在商品**没有设计程价**时成立；设了计程价的按下面的优先级报。**包车不变**（仍按 0075 / 0073）。
  0075 的其余部分（运营区域与报价区域分开、运营判断、`NO_PRICING_AREA`、未覆盖需求、迁移）全部继续有效。
- 补充 ADR 0073（区域价、线路价、含公里数、包车区域加价）、ADR 0018（价格规则）、ADR 0020（报价引擎第 4～7 步）。
- 编号：写这篇时 main 上最大是 ADR 0079（M8-27），这里用 0080。

## 业主定的规则（roadmap M8-30 为准）

**接送机 / 点对点**，每个商品依次：

1. 两端都在这个商品的报价区域里 → 原来的一口价（区域价 / 线路价 / 含公里数），和今天一模一样。
2. 只有一端在 → 在区域里那一端所在区域的一口价 + 区域外里程费。区域外公里 = 路线距离 − 一口价含的公里数（没设为 0），不足 1 公里按 1 公里；里程费 = 区域外公里 × 这个商品的计程价的每公里单价。没设计程价 → 这个商品不报。
3. 两端都不在 → 计程价：按车型组的起步价 + ⌈路线公里⌉ × 每公里单价，不挂区域。
4. 否则这个商品不报。路线距离用现有的路线服务；取不到时 2、3 不报。

**包车**：服务城市要对上；上车点、下车点都要在商品本身的区域（加 0）或它的某个加价区域里 → 基础价 + 上车加价 + 下车加价（和今天一样）；否则不报。不用计程兜底。

**不变的**：运营区域仍是「这一端能不能接单」的上限（任一端不在供应商的运营范围里 → 这个商品不报）；城市匹配 80 / 150 公里不变；一个都报不出 → 现有的人工报价流程 + 未覆盖需求。**今天报得出的价一分不变**；只有今天报不出的请求可能新报出。

## 一、数据：计程价单独一张表

`distance_prices`（迁移 0330）：`tenant_id`、商品、车型组、`start_minor`、`per_km_minor`（结算价，子品牌币种的最小货币单位整数）、生效日期、启停。行级安全只放行当前租户，平台角色只读（比价用）。

- 为什么不用 `price_rules` 加一种 `distance_only` 计价方式：`price_rules.area_id` 是非空外键，价格日历、缺价统计、上架检查、导入导出、调价规则的检查、价格影响评估都以「区域 × 车型组」为键。让 `area_id` 可空要改动所有这些地方，风险集中在「今天报得出的价一分不变」上。单独一张小表只被报价引擎读，现有路径一行不动。
- 沿用价格规则的口径（不是另造一套）：生效日期两端都含、`valid_to` 为空 = 一直有效、停用的也参与冲突判断（`dateRangesOverlap`、`priceRuleCoversDate`）；同一车型组的生效日期不能重叠（409 `DISTANCE_PRICE_CONFLICT`），在锁住商品那一行之后检查；每次修改商品版本号加一、写审计（`resource` = `distance_price`）；原因代码同价格规则（`NO_PRICE_RULE` / `PRICE_NOT_IN_EFFECT` / `PRICE_RULE_DISABLED`）。
- 不按方向分（接送机的接 / 送用同一条）：业主说的是「按车型的起步价 + 每公里」。以后要分方向再加列。
- 只有接送机、点对点能设（包车 400 `DISTANCE_PRICE_NOT_ALLOWED`）；车型组要是商品选的。计程价不是上架条件。

接口（`/tenant/v1`，`tenant_id` 只来自令牌，规则 4：只有结算价）：

| 方法 | 路径 |
| --- | --- |
| GET / POST | `/tenant/v1/products/{id}/distance-prices` |
| PUT / DELETE | `/tenant/v1/products/{id}/distance-prices/{ruleId}` |
| POST | `/tenant/v1/products/{id}/distance-prices/{ruleId}/enable`、`/disable` |

## 二、引擎（`packages/domain/src/quote.ts` 的 `transferAreas`）

- 先跑今天的 `serviceAreas`。报得出区域 → 情形 1，后面的计算和今天是同一段代码。
- 报不出时，只有同时满足这三条才进入情形 2、3：商品设了计程价、商品带着运营范围（做运营判断）、不是 `legacyAreaRules`（只读回放用的「M8-30 之前的口径」）。否则原样返回今天的原因。
- 每一端先过运营判断；有一端不在运营范围里 → 不报，**原因和今天一样**（不改报不出时的原因，包括两端都在报价区域里、只是区域都被禁行区排除的情形）。
- 点对点只有一端在 → 情形 2：用这一端所在的报价区域（另一端落在某个区域的禁行区里时，那个区域不算，同今天的禁行区口径）。
- 接送机只看非机场一端（机场一端不看区域，同今天）：非机场一端不在报价区域里 → **情形 3**（计程价）。没有情形 2：机场一端没有报价区域，说不清「哪个区域的一口价」，不替供应商挑。

### 金额（结算价，精确值、只在最后取整一次，`money.ts`）

| 情形 | 基础价 | 调价 |
| --- | --- | --- |
| 2 一口价 + 区域外里程费 | 区域的固定一口价 + ⌈(路线米数 − 含公里 × 1000) ÷ 1000⌉ × 计程价的每公里单价（`overKm`，M8-11 同一个函数） | 和包车区域加价一样，作用在「一口价 + 里程费」的合计上，按那个区域匹配 |
| 3 计程价 | 起步价 + ⌈路线米数 ÷ 1000⌉ × 每公里单价 | 只有适用全部区域（`area_ids` 为空）的调价规则作用在它上面；挂了区域的不作用（计程价不挂区域） |

- 情形 2 只认固定一口价：区域的价是「里程 + 时长」的，本来就按整段路线算钱，不再叠加里程费，这个区域报 `NO_PRICE_RULE`（**提案**：如果业主希望「里程 + 时长」也能和区域外里程费组合，另开任务定口径）。
- 情形 2 里一口价设了「含 X 公里 + 超出每公里 Y」的：区域外公里扣掉 X，按计程价的每公里单价收；Y 不再另算（同一段路不收两次）。
- 情形 2 只用区域价，不找线路价（线路价要求两端都在区域里）。
- 加急、夜间、附加服务、司机语言、库存、取整、上限、`PRICE_NOT_POSITIVE` 都和今天一样。
- 报价明细加两个只在新情形出现的字段：`pricingBasis`（`one_price_outside_km` / `distance_only`）和 `mileage`（计程价编号、路线米数、含公里、计费公里、起步价、每公里、里程费），路线预估记进 `usage`，改期重算用同一段路线（ADR 0029）。按计程价报的 `areaId` 为 null，`priceRuleId` 是那条计程价的编号。一口价的报价、订单没有这两项（golden 对比逐字节一样）。
- 只有设了计程价的商品才会为它调路线服务（`needsRoute`），其余商品不多调一次。

## 三、对外显示

- `/site/v1` 报价、订单，`/sales/v1` 报价、订单多一个字段 `pricing_basis`（`one_price` / `one_price_outside_km` / `distance_only`）：只说方式，不给计程的单价和金额（钱已含在总价里）。渠道接口只加字段。
- 客人页的说法（业主定）：`one_price_outside_km` →「含里程费」，`distance_only` →「按里程计价」，包车区域加价照旧「含区域加价」。文字在 `packages/domain/src/distance-price.ts` 的 `pricingBasisNote`，页面只调用它。
- 供应商试算（`/tenant/v1/.../quote-preview`）和运营试算的结算价明细多 `pricing_basis`、`mileage`（结算价，规则 4 不变）。

## 四、验证

1. **golden 对比**（`quote-compat.test.ts`）：全部样例（三个品类、多区域、禁行区、停用区域、调价、夜间、加急、附加服务）在接送机、点对点商品加上计程价后，今天报得出的每一个价逐项 `deepEqual`，按车型组报不出的原因不变；`legacyAreaRules` 的结果和 golden 一样；新报出的只出现在今天因区域原因报不出的样例上，而且都带 `pricingBasis`。
2. **只读回放**：`pnpm areas:role-preview` 多一段「M8-30 报价优先级」——最近 30 天询价日志里的请求，对每个候选商品用 M8-30 之前的口径和现在各算一遍：之前报得出的价（车型组、区域、线路、规则、结算价、币种）有变化的必须 0 处（否则退出码 2）；之前报不出、现在新报出的按计价方式计数。M8-20 那一段对比两边都按 M8-30 之前的口径算，只看区域用途的影响。测试环境、正式环境部署前各跑一次，结果写进验收记录。
3. 集成测试：计程价接口（幂等、If-Match、冲突、校验、包车不能设、启停、审计、规则 4）、三种情形经官网和供应商试算、运营区域上限、路线取不到、订单锁定计价方式、回放；租户隔离（甲读不到、改不了乙的计程价，数据库层面也一样）。

## 六、M8-30c 补充：订单详情和确认邮件

- 运营订单详情（`GET /platform/v1/orders/{id}`）、供应商订单详情（`GET /tenant/v1/orders/{id}`）多两个顶层字段：`pricing_basis`（M8-30 之前的单是 `one_price`）和 `mileage`（`OrderMileage`：`route_meters`、`included_km`、`km`、`start_price`、`per_km`、`fee`，金额写成 `{ amount, currency }`，订单上锁定的**结算价**；一口价、旧单为 null）。两边形状一样；运营的计程对外价参考没加（页面不用，要时再加），规则 4 照旧。
- 客人确认邮件：已付金额后面接 `pricing_basis_note`（「（含里程费）」/「（按里程计价）」，文字用 `pricingBasisNote`；一口价为空，那一行和以前一样）。不写计程的单价和金额；供应商邮件不加。
