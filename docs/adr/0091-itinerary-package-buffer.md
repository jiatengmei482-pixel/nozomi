# ADR 0091：按行程计价自动选套餐时加「经停点默认占用」和「整单缓冲」；商品最低套餐；客人可升套餐

- 状态：草案（2026-11-14，待独立审查）。实施任务 M9W-11。
- 依据：业主正式需求文档 `docs/requirements/charter-airport-packages-2026-11-14.md`（PR #217）第二节「需求二：自动选套餐时加缓冲时间」和第六节验收用例 P0 三条。开发顺序按文档第五节：需求二 → 需求一 → 需求四 → 需求三，本篇只管需求二。
- 修改 ADR 0089 第 3 节「选套餐（服务层）」：选套餐用的时长从「行驶 + 停留」改为下面的 T；其余（公式、路线、订单）不变。需求四（按「套餐价 + 超公里费」取最低）以后另写 ADR，会再改这一节的「取最小」。
- 业主硬要求：**现有报价结果完全不变**（golden 和测试站 1,368 行回放比对必须一致）。

## 依据（文档第二节原文）

> 现状：只按"行驶时间 + 停留时长"选套餐，路线短时 5 小时会被换成 4 小时，实际跑下来又超时
> 公式：T = 行驶时间 + Σ停留时长 + 经停点数量 × 经停点默认占用 + 整单缓冲
> - 取不小于 T 的最小套餐；超过最大套餐（12 小时）时，按最大套餐加超时费报价
> - 商品级配置：经停点默认占用（建议 15 分钟）、整单缓冲（建议 60 分钟，设 0 即关闭）、最低套餐（可设为 5 小时，默认不限）
> - 客人可手动升到更长的套餐，但不能选低于计算结果的套餐
> - 价格明细显示"预计用时 X 小时 Y 分钟（含缓冲）"

## 一、商品配置（三项）

| 项 | 含义 | 取值 | **默认（没填）** | 业主建议值 |
| --- | --- | --- | --- | --- |
| 经停点默认占用 `stopOccupancyMinutes` | 每个经停点额外算的时间（停车、步行、上下车），和客人填的停留分开 | 整数分钟 0–120 | **0** | 15 |
| 整单缓冲 `bufferMinutes` | 整单额外加的时间；0 = 关闭 | 整数分钟 0–240 | **0** | 60 |
| 最低套餐 `minPackageHours` | 这个商品最短卖几小时 | 1–`PRICE_LIMITS.maxPackageHours` 的整数，或不限 | **不限** | 5（可选） |

- **默认值取「行为不变」的那一组（0 / 0 / 不限），不取业主建议值。** 理由：业主要求现有报价完全不变；默认取建议值会让部署当天所有按行程计价的报价（以及「最低套餐 5 小时」会让不带经停点的 4 小时报价）变化，回放比对也就失去意义。建议值在部署、回放比对通过之后，由业主（或运营代业主）在供应商后台的商品「服务规则」里填；页面上用灰色提示写出建议值（「建议 15 分钟」「建议 60 分钟，填 0 关闭」「可设为 5 小时」），不预填。
- 只对包车商品有效；别的品类给了 400 `NOT_APPLICABLE`。

### 存在哪里（改进方案，超出现有框架，请审查确认）

推荐放进商品现有的 `products.service_rules` jsonb（领域类型 `ServiceRules`）里新加一个可选键 `charterItinerary: { stopOccupancyMinutes, bufferMinutes, minPackageHours }`，**不加列、不写迁移**：

- 它和免等、加急一样是「这个商品怎么服务」的规则，跟着商品版本走；改了商品 `version` 加一，报价快照里本来就记商品版本，审计、并发控制（If-Match）都现成；
- 没有这个键的旧数据读出来就是默认值（0 / 0 / 不限），不需要回填；
- 回放的状态摘要 `stateDigest` 里有商品的 `version`：只要没人改服务规则，部署前后状态摘要不变；**有人填了这三项，版本变、状态摘要变，回放比对按 ADR 0086 判无效**——所以要先比对、后填值（第五节）。

不推荐另开列或另开表：要迁移、要改「商品不可改列」之类的触发器和导入导出，收益只是能单独建索引，这里用不到。

接口：`GET / PUT /tenant/v1/products/{id}/service-rules` 加 `charter_itinerary: { stop_occupancy_minutes, buffer_minutes, min_package_hours }`（`min_package_hours: null` = 不限）。PUT 里**没有这个键 = 保留原值**（同 ADR 0088 补充里 `waypoint_surcharge` 的口径，防旧页面保存服务规则时把它清掉）；显式给值才改。`/platform/v1/products/{id}` 只读带上。供应商后台「服务规则」页加三个输入框。新字段要有「租户 A 读不到、改不了租户 B」的集成测试（规则 2）。

## 二、T 和选套餐

### 1. 公式

```
T = 行驶分钟（逐段之和，ADR 0089 第 4 节） + Σ 客人填的停留分钟
  + 经停点个数 × 经停点默认占用
  + 整单缓冲
```

- 经停点个数 = 客人填的经停点个数（上车点、下车点不算）；没有经停点时这一项为 0。
- `itinerary_route.total_minutes` 仍是「行驶 + 停留」（原样，不含占用和缓冲），T 另给（第三节）。

### 2. 选套餐

每个车型组：在这个城市官网能选的套餐时长里，**取 ≥ T 且 ≥ 最低套餐的最短一档**；所有档都 < T 时，**按最长那一档加超时费**（和 ADR 0089 现有的退路一致）。

### 3. T 是按商品算的——这是现有框架的第二处改动（请审查确认）

三项配置在商品上，同一城市里不同商品的 T 可以不同；而现在的选套餐在服务层按「城市的套餐档次」逐档询价、引擎每次只拿到一份用量（`routeUsage`），服务层没法按商品分别判断。改进方案：**让引擎按商品判断**（只加不改）：

- 引擎 `QuoteRequest` 加可选 `itineraryStops: number`（经停点个数）和 `allowShortPackage: boolean`（只有服务层的退路询价才给 true）。**不给 `itineraryStops` 时，引擎和现在逐字一样**（golden、旧日志回放、旧快照的改期都走这条路）。
- 给了时，包车商品各自算 `T_p = routeUsage.minutes + itineraryStops × 占用_p + 缓冲_p`：
  - `packageHours < 最低套餐_p` → 这个商品不报，新原因 `BELOW_MIN_PACKAGE`；
  - `packageHours × 60 < T_p` 且没给 `allowShortPackage` → 不报，新原因 `PACKAGE_TOO_SHORT`；
  - 报出来的超时费按 `max(0, T_p − 套餐分钟)` 算（见第六节待确认第 1 条），结算价明细 `itinerary` 多记 `stops`、`stopOccupancyMinutes`、`bufferMinutes`、`estimatedMinutes`（= T_p）——**只在占用或缓冲不为 0 时写**，三项都是默认值时明细逐字和现在一样。
- **最低套餐不限于按行程计价**：不带经停点、客人自己选时长的包车询价（`package_hours`）也按商品的最低套餐拦（`BELOW_MIN_PACKAGE`）。理由：验收用例 P0 第 2 条「市内短线路 T=2h → 选 5 小时，不能选 4 小时」，没有经停点的市内包车在 `/book/new` 上本来就是客人选时长，不拦就等于没设。默认「不限」时不拦，行为不变。
- 服务层 `itineraryQuotes`：第一轮按城市的档次**从短到长**逐档询价（带 `itineraryStops`，跳过 `< 行驶 + 停留` 的档——任何商品的 T 都不会比它小），每个车型组取第一个报得出的档；还有车型组没报出时，第二轮**从长到短**对 `< 那一档` 的档次带 `allowShortPackage` 询价（同现在的退路）。三项都是默认值时，引擎对每一档的判断和现在服务层按 `total_minutes` 的判断完全相同，所以选中的档、价格、快照都不变。
- 比价：同一档里，T 已覆盖的商品照常比价；T 没覆盖的商品不参加这一档。结果是「每个车型组取最短的、至少有一个商品能卖的档」——不同商品配置不同时，客人拿到的是能卖最短档的那个商品。这是按商品配置的自然结果，写在这里供审查。

## 三、接口和页面

### 1. 询价应答

- 每个按行程计价的报价加 `estimated_minutes`（中标商品的 T）、`includes_buffer`（占用或缓冲不为 0）、`min_package_hours`（这个车型组自动选出的那一档 = 客人能选的最短档）。
- `POST /site/v1/quotes` 的 `itinerary_pricing: true` **现在可以带 `package_hours`**（以前 400 `NOT_APPLICABLE`，现在是只加不改的放宽）：表示客人手动选的档，服务层只询这一档、不给 `allowShortPackage`；比这个车型组的 T 或最低套餐短的，按上面的原因不报（页面不让选，这里是服务端兜底）。

### 2. 页面（官网 `/book/new`；嵌入组件跳过来后同样生效）

- 价格明细的套餐行下面一行：「**预计用时 X 小时 Y 分钟（含缓冲）**」——`includes_buffer` 为 false 时不写「（含缓冲）」。X、Y 由 `estimated_minutes` 换算，不四舍五入到小时。
- 套餐时长下拉：默认「自动（N 小时）」；可选项只列这个城市 ≥ `min_package_hours` 的档；选了更长的档就带 `package_hours` 重新询价，按那一档报价（P0 第 3 条：6 小时升到 8 小时）。不列比自动结果短的档。
- 嵌入组件有经停点时不选时长（ADR 0090），不用改。

## 四、对已有决定和数据的影响

- **ADR 0089 第 3 节**：选套餐的时长由「行驶 + 停留」改为 T，「能覆盖的最小套餐」的判断从服务层移到引擎按商品做（第二节第 3 小节）；退路不变。第 4 节 `itinerary_route` 不变。
- **已下订单**：不变（快照锁定）。**改期**：按快照的 `request` 和订单原来的套餐重算；新快照里带 `itineraryStops` 的按当时商品的配置算 T（缓冲改了，改期价可能变，和价格规则改了一样处理）；不重新选档。**救援改派**：照传 `itineraryStops`。
- **回放（ADR 0086）**：询价日志的原始请求多记 `waypoint_count`；旧日志没有这一项，回放时不给 `itineraryStops`，走旧路径，结果不变。部署前后用同一个 `until`、天数各跑一次：在没人改服务规则的前提下，`stateDigest` 相同、`resultDigest` 必须相同；1,368 行逐行摘要一致。`replay-digest.ts` 的 `offerParts` 不改。
- **golden**：引擎改动前在 main 上生成「按行程计价、三项默认值」的 golden（各档、退路、超时），改后逐字段一致；现有 golden 和 `area-surcharge.test.ts` 原样通过。

## 五、测试与验收

- domain 单元：T 的公式；`BELOW_MIN_PACKAGE`、`PACKAGE_TOO_SHORT`、`allowShortPackage`；默认值时与不给 `itineraryStops` 的结果逐字相同；边界：T 正好等于套餐分钟时选这一档。
- 集成（真实 PostgreSQL，测试数据在测试代码里构造、测试后清理，不进迁移和种子）：服务规则新字段的读写、保留原值、租户隔离；按文档第六节 P0 三条（东京商品、经济 7 座的价格规则在测试里构造）：
  1. 行驶 2 小时 + 3 个经停点共停留 1.5 小时，占用 15 分钟、缓冲 60 分钟 → T = 5 小时 15 分，选 **6 小时**，明细「预计用时 5 小时 15 分钟（含缓冲）」；
  2. 最低套餐 5 小时，市内短线路 T = 2 小时 → 选 **5 小时**；带 `package_hours: 4`（按行程或不带经停点）→ 不报 `BELOW_MIN_PACKAGE`；
  3. 第 1 条的行程客人带 `package_hours: 8` → 按 8 小时报价；带 `package_hours: 5` → 不报 `PACKAGE_TOO_SHORT`。
- 端到端：`/book/new` 的明细文字、时长下拉只列 ≥ 自动结果的档、升档后价格变化。
- 测试站验收（部署后）：① 先跑回放比对（同一 `until`、天数，摘要一致）；② **再**请业主在「东京包车」服务规则里填 15 / 60（最低套餐按业主意愿）；③ 用 `/book/new` 走 P0 三条，截图写进 PR。
