# ADR 0025：汇率人工锁定——按币种锁定、必须带到期时间、双人复核、快照里记明

- 状态：已采纳（2026-10-18，M2-06）
- 实现 ADR 0022「没有做的」里的「人工锁定某个汇率（双人复核）」；用 ADR 0023 的通用复核机制登记两类 `ApprovalKind`。
- 补充 ADR 0020：报价快照里的汇率（`FxQuote`）多一项可选的 `lock`；`fxQuoteUsable` 认得锁定。
- 补充 ADR 0010：一张新的平台表 `fx_locks` 的授权。
- 编号说明：ADR 按任务安排用 0025；迁移用 0023（0022 留给同时在开发的 M1-15）。

## 背景

需求：《平台运营端与渠道对接》「汇率中心运维」——「人工锁定：极端行情时可临时锁定某个汇率（双人复核）」；「敏感操作双人复核：发起人和审核人不能是同一人」。
roadmap 的验收标准：极端行情时可临时锁定某个汇率，一人提交、另一人批准后生效；锁定期间报价用锁定值，快照里记明是锁定汇率；解锁同样双人复核；全部操作留审计。

## 决定

### 锁定的粒度：按币种锁「1 USD = ?」

锁定的是**某一个币种相对基准 USD 的汇率**（和 `fx_rates` 的存法一样），不是某一对币种。任意两种币种之间照常用交叉汇率，锁定的一边用锁定值、另一边用数据源的值。

理由：

- 极端行情通常是某一个币种在动（日元急贬、人民币管制）：锁住它一个，它和其余 6 种币种之间的 12 个方向就都稳住了；按币种对锁，要锁 12 对，还会互相矛盾（锁了 JPY→CNY、JPY→USD，USD→CNY 却没锁，三者对不上，就有了无风险套利的口子）。
- 存法、校验、48 小时规则、3% 跳变都已经是按币种（相对 USD）做的，锁定沿用同一个口径，结果可以用同一套精确分数复算。
- USD 是基准（恒等于 1），不能锁定。要锁「美元对日元」，就是锁 JPY。

交叉汇率在一边锁定时：1 个 A = (1 USD 的 B 数) ÷ (1 USD 的 A 数)，锁定的那一边换成锁定值，照常先用精确分数算、再四舍五入到 12 位小数（`fxQuoteWithLocks`，`packages/domain/src/fx-lock.ts`）。

### 锁定值：十进制字符串，正数，和中央汇率比偏离

- 接口里 `rate` 是**字符串**（`"151.2"`），不收 JSON 数字（JSON 数字在解析时就变成浮点数了）。只认普通十进制写法：没有正负号、指数、千分位、空格，必须大于 0，整数、小数各最多 12 位；在字符串上规范（`0151.20` → `151.2`），存进不限精度的 `numeric`（`parseLockRate`）。
- 和**发起那一刻**的中央汇率（现在用的那批里这个币种的值）比，精确分数比较：
  - 偏离**超过 3%**（严格大于，和「单次变动超过 3% 挂起」同一个口径）：必须写原因（`REASON_REQUIRED`）；
  - 偏离**超过 20%**：不允许（`DEVIATION_TOO_LARGE`）——多半是输错了数量级或币种（把 0.0067 写成 151.2、把 KRW 当成 JPY）。真要锁一个离谱的值，说明数据源本身出了大问题，应该先处理数据源。
- 还没有任何汇率时不能锁定（409 `FX_RATE_UNAVAILABLE`）：没有可比对的中央汇率。

### 必须带到期时间，最长 72 小时，到期自动失效

- `expires_at` 必填：发起时离现在至少 30 分钟（太短的锁定来不及有人审核就到期了）、最多 72 小时（从发起算；批准得晚，剩下的时间就短）。后台表单让人选「锁定多久」（1–72 小时），提交时换成到期时刻。
- **到期那一刻起不再用（不含这一刻）**：报价时按报价时刻判断（`fxLockActive`），不依赖定时任务有没有跑到；进程内的缓存只缓存锁定本身，用的时候再按时刻判断，所以到期精确到毫秒。
- 定时任务（`FxCenter.tick`，每分钟）把到期的改成 `expired`，每一条记一条审计（`fx_lock` / `expire`，操作者「系统」，入口 `job`）和服务日志（warn，`event: fx.lock_expired`）。几个服务进程同时跑也只记一次（同一把锁）。
- 为什么必须有到期：锁定是临时的应急手段，忘了解锁会让报价长期偏离市场。72 小时覆盖一个周末（周五晚锁到周一早上）。要更久，到期前再发起一次（「改锁定值」），同样要另一人批准。
- 数据库约束兜底：`expires_at > locked_at` 且不超过 `locked_at + 72 小时`。

### 锁定期间数据源照常、48 小时规则

- 数据源新拉到的一批**照常入库、照常生效**（其余币种用），只是锁定的币种报价不用它。看板上「数据源（中央汇率）」一列照常更新，方便判断什么时候可以解锁。
- 「单次变动超过 3% 挂起」照旧和**数据源上一批**比，不和锁定值比：挂起是在拦数据源的错，锁定不改变这件事。
- **锁定期间不因数据源停更而暂停这个币种**：只涉及锁定币种和 USD 的（或两边都锁定的）汇率不看 48 小时；另一边还用数据源的，那一边照旧受 48 小时约束——例如锁了 JPY、数据源停更超过 48 小时：JPY↔USD 照常报价，JPY↔CNY 暂停（CNY 的数据过期了）。
  这条规则写在报价引擎的 `fxQuoteUsable` 里（`lock.usesSource` 为 false 时不看取数时间、只看锁定是否到期），汇率中心和报价引擎两处的判断一致。
- 首页、汇率页的「已过期」提示条上加一句：锁定的币种和美元之间照常报价。

### 快照里记明是锁定汇率

`FxQuote` 多一项可选的 `lock`（没有锁定时不出现，原有的快照、测试不变）：

```ts
lock?: { legs: { currency, rate /* 1 USD = ? */, lockId, expiresAt }[]; usesSource: boolean }
```

- `rate` 仍是交叉后的 12 位小数（对外价按它算），`asOf` 仍是现在用的那批数据源的时间；`lock.legs` 写明哪一边用了锁定值、锁定值多少、是哪一条锁定、到什么时候。
- 报价快照（`quotes.snapshot`）原样存 domain 的对象，自然带上 `lock`；平台试算接口的候选 `fx.lock`（没有为 null）；后台试算页的明细里写「用了人工锁定的汇率：1 USD = 151.2 JPY（锁定到 …）」。
- 销售端（`/sales/v1`）的应答**不加**锁定的细节：照旧只给汇率和取数时间。锁定是平台内部的风控手段，渠道不需要知道。

### 双人复核：两类，批准时再核对一次

- 登记两类：`fx_lock.create`（锁定，或给已锁定的币种改锁定值 / 到期时间——批准后新的取代旧的，旧的记为 `replaced`）、`fx_lock.release`（解锁）。复核记录的 `resource` 是 `fx_lock`，`resource_id` 是币种。
- **批准时的「过时」判断（参照 M2-04 的 `APPROVAL_STALE`）**：复核的对象是「这个币种的锁定状态」。发起时记下当时生效的那条锁定（`replaces_lock_id`，没有为 null；解锁记 `lock_id`），批准时这个币种的锁定状态变了——别的复核先批了一条锁定、被解锁了、到期了——就是 409 `APPROVAL_STALE`，记录仍是待审核，审核人驳回、发起人按现在的情况重新发起。
  **中央汇率变了不算过时**：数据源每天更新，不是同事的改动；锁定本来就是要盖过数据源。批准时按**那一刻**的中央汇率重新核对偏离（超过 3% 要有原因、超过 20% 拦截），已经过了到期时间的不能生效。
- **并发**：批准锁定 / 解锁、处理到期都在事务级咨询锁（`:nozomi.fx_lock`，锁名带 schema）里做，再看「这个币种现在有没有生效中的锁定」。两条同一币种的锁定同时批准，第二条看得到第一条的结果，按 `APPROVAL_STALE` 拒绝；同一条复核两个人同时批准，复核机制本身的行锁让第二个拿到 `APPROVAL_NOT_PENDING`。数据库另有「同一币种最多一条 active」的唯一索引兜底。
- **缓存**：批准生效后作废本进程的汇率缓存——在事务**提交之后**（复核机制新增的可选钩子 `ApprovalKind.afterApply`）；在事务里作废，别的请求会在提交前把旧数据读回缓存。别的服务进程最晚 30 秒后用上（和数据源新批次一样，ADR 0022）。

### 权限

| 操作 | 角色 |
| --- | --- |
| 看锁定状态、锁定记录、待审核的锁定申请（`master_data.read`） | 每个平台角色（和看汇率一样） |
| 发起锁定、改锁定值、发起解锁（`fx.manage`，沿用 ADR 0022） | 主数据运营、超级管理员 |
| 审核（`fx.review`，新增） | 主数据运营、超级管理员；**不能是发起人**（复核机制本身保证）。两位主数据运营互审；只有一位时由超级管理员审 |
| 待审核队列（`approval.read`） | 新给主数据运营（原来没有）：要在队列里审汇率锁定。队列只列各人看得到的那几类，主数据运营仍看不到渠道的复核（没有 `channel.read`） |

渠道经理有 `approval.read` 和 `master_data.read`，能在队列里看到汇率锁定的申请，但没有 `fx.review`，不能审（403）。

### 租户

`GET /tenant/v1/fx-rates` **不受锁定影响**：给的仍是数据源的中央汇率，也不说有没有锁定；租户角色对 `fx_locks` 没有任何权限。理由：

- 锁定是平台对客人报价的风控手段，和汇率缓冲、加价一样属于平台内部（规则 4 的精神）；
- 租户的结算价是自己的币种，客人支付的币种换算发生在平台一侧，租户看不到对外价，也就用不到锁定值；
- 少一张对租户开放的表，少一处要证明「租户看不到原因、经手人」的地方。

### 表（迁移 `0023_fx_locks.sql`）

| 表 | 内容 | 平台 | 租户 |
| --- | --- | --- | --- |
| `fx_locks` | 币种、锁定值（`numeric`）、原因、到期时间、生效时刻、批准时的中央汇率和那批的时间、偏离（基点）、锁定的复核、发起人、批准人、状态（active / released / replaced / expired）、结束时刻、解锁或取代的复核和批准人 | 读、增、改 | 无 |

没有 `delete`；保留全部记录。约束：币种不是 USD、锁定值和中央汇率为正、批准人不是发起人、最长 72 小时、结束了的有结束时刻（解锁 / 取代还要有复核和批准人）、同一币种最多一条 active。

### 审计

| 事件 | `resource` / `action` | 操作者 |
| --- | --- | --- |
| 发起锁定 / 解锁 | `approval` / `request` | 发起人 |
| 批准、驳回、撤回 | `approval` / `approve`、`reject`、`withdraw` | 审核人（撤回是发起人） |
| 锁定生效 | `fx_lock` / `lock`（`after` 有锁定值、到期、原因、批准时的中央汇率和偏离、复核编号、发起人） | 批准人 |
| 解锁、被新的锁定取代 | `fx_lock` / `unlock`（`after.status` 是 `released` / `replaced`） | 批准人 |
| 到期 | `fx_lock` / `expire` | 系统（入口 `job`；批准新的锁定时顺手处理的，入口是后台） |

### 运营后台

- 汇率页「人工锁定」卡片：生效中的锁定（币种、锁定值、批准时的中央汇率和偏离、到期时间、发起 / 批准、原因）、待审核的申请（能审的人有「去待审核处理」，发起人看到「要等另一位同事」）；有 `fx.manage` 的有「发起锁定」「改锁定值」「解锁」。
- 发起表单：币种、锁定值（实时显示和中央汇率的偏离）、锁定多久（到期时刻）、原因（偏离超过 3% 时必填）。和后端同一套解析和比较（domain），服务器拒收的原因按字段放回表单。
- 汇率表里锁定的值标 `*`（读屏读「用了人工锁定的汇率」），另列「数据源（中央汇率）」；互换表里用到锁定的格子同样标 `*`。页底「锁定记录」。
- 待审核队列：这两类显示「锁定汇率」「解除汇率锁定」，改了什么写锁定值、到期时间、偏离，链接去汇率页。

## 没有做的

| 内容 | 原因 / 去向 |
| --- | --- |
| 到期前提醒（如到期前 2 小时） | 没有通知渠道（第三轮决策）；通知中心做出来以后接 `fx.lock_expired`，并加「即将到期」 |
| 按币种对锁定 | 见「锁定的粒度」 |
| 锁定 USD（改基准） | USD 是存储的基准；要锁美元对某个币种，锁那个币种 |
| 租户看到锁定值 | 见「租户」 |
| 销售端应答里说明锁定 | 平台内部的风控手段；快照里有 |

## 待定事项（先按推荐做了，需要负责人确认）

| # | 问题 | 选的方案 | 理由 |
| --- | --- | --- | --- |
| 1 | 锁定最长多久 | 72 小时，必须填到期时间 | 覆盖一个周末；忘了解锁也会自动恢复 |
| 2 | 偏离中央汇率多少要写原因、多少拦截 | 超过 3% 写原因，超过 20% 拦截 | 3% 和挂起的口径一致；20% 以上几乎都是输错 |
| 3 | 发起后中央汇率变了，复核要不要作废 | 不作废，批准时按新的中央汇率重新核对偏离；锁定状态变了才作废 | 数据源每天更新，不是同事的改动；锁定本来就要盖过数据源 |
| 4 | 谁能审 | 主数据运营、超级管理员（不是发起人） | 汇率归主数据运营；只有一位时超级管理员审 |
| 5 | 租户看到的汇率受不受锁定影响 | 不受，给中央汇率 | 锁定是平台风控手段；租户用不到 |
