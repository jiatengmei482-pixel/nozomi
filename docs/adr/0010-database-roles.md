# ADR 0010：数据库账号分离——迁移账号与应用账号

- 状态：已采纳（2026-10-07，M0-10）
- 取代：ADR 0009 中的这几处——
  - 「决定」里 `withSystemTx` 的定义（用连接本身的账号执行，不受行级安全限制）和「不需要第二个连接串，不新增环境变量」；
  - 「对数据库账号的要求」一节；
  - 「理由」里「相比应用用另一个非所有者账号连接」和「平台操作……直接用所有者身份」两条；
  - 「已知限制」里后两条（能注入 SQL 的攻击者可以 `reset role`；绕过 `withTenantTx` 直接用连接池查询不受保护）。
  - 「验证」一节里「连接账号是超级用户」这一前提：测试里的应用代码现在用应用账号连接。
  - ADR 0009 的其余内容不变：租户事务切换到 `nozomi_app`、策略怎么写、有意的例外、新增租户表的做法、验证方式，全部照旧。

## 背景

ADR 0009 让服务进程用建库时的那个账号连接数据库（表的所有者，Docker Compose 下还是超级用户），只在租户事务里临时切换到 `nozomi_app`。测试角色在 M0-06 指出这留下三个洞：

- 行级安全只在 `withTenantTx` 里生效；`withSystemTx` 和任何直接用连接池的查询都以所有者身份执行，不受保护。
- 审计日志的「只能追加」只防误操作：所有者可以关掉触发器，超级用户可以 `set session_replication_role = replica`，然后随意删改。
- 一旦出现 SQL 注入或连接串泄露，对方拿到的是整个库：读全部租户、抹审计、删表。

## 决定

### 两个登录账号

| | 迁移账号 | 应用账号 |
| --- | --- | --- |
| 环境变量 | `DATABASE_MIGRATION_URL` | `DATABASE_URL` |
| 是谁 | 表的所有者（Compose 下是建库时的 `nozomi`） | 专用账号（Compose 下是 `nozomi_api`） |
| 谁用它 | 只有 `pnpm db:migrate`、`pnpm db:provision`、备份和恢复 | 服务进程、`pnpm admin:create`、`pnpm admin:reset-password` |
| 权限 | 建表、改结构、建角色 | 能登录；`NOSUPERUSER NOCREATEROLE NOCREATEDB NOBYPASSRLS NOREPLICATION NOINHERIT`；不拥有任何表；**自己对任何表都没有权限** |

应用账号只是下面三个权限角色的成员，而且不自动继承它们的权限（`NOINHERIT`）：不切换角色时，它一张表都读不了。

- 服务进程的环境里只有 `DATABASE_URL`，没有迁移账号的连接串和密码。两个连接串写成同一个账号时，配置校验直接报错。
- 管理员命令行（`admin:create`、`admin:reset-password`）是业务写入，用应用账号、走平台角色，和后台操作受同样的约束。

### 三个权限角色

都不能登录、没有密码、不拥有任何表，由迁移创建，权限由迁移按表授予。`apps/api/src/db/context.ts` 的三个入口各对应一个，事务开头 `set local role` 切换过去，事务结束自动恢复：

| 入口 | 角色 | 用在哪 | 能做什么 |
| --- | --- | --- | --- |
| `withTenantTx` | `nozomi_app` | 租户请求（ADR 0009，不变） | 行级安全把读写限定在当前租户 |
| `withPlatformTx`（原 `withSystemTx`） | `nozomi_platform` | `/platform/v1` 的操作、管理员命令行 | 平台账号与会话；租户主体和租户用户（可跨租户）；审计日志只能追加和读 |
| `withPreAuthTx`（新增） | `nozomi_preauth` | 还不知道请求方是谁的时候：登录限速、租户登录 / 接受邀请时定位用户、匿名的登录失败记录、`/health` 读迁移记录 | 见下 |

**平台角色不是所有者，也不绕过行级安全**：`tenants`、`tenant_users`、`audit_logs` 上各有写明 `to nozomi_platform` 的放行策略；对 `audit_logs` 只有 `insert` / `select` 两种权限和对应的两条策略。它碰不到租户会话（`tenant_sessions`）和登录限速（`login_throttles`），也没有任何表的 `delete`（平台会话除外）、`truncate` 权限。

**登录前角色尽量小**（这是对原方向的进一步收窄）：

- 它读不了 `tenant_users`、`tenants`、`platform_users`、`audit_logs`。
- 租户登录时只有邮箱、接受邀请时只有令牌，要在知道租户之前定位到用户（ADR 0009 的例外）。这一步改成调用两个数据库函数 `locate_tenant_user_by_email` / `locate_tenant_user_by_invite_token`：以所有者身份执行（`security definer`），查找路径固定在本库的 schema，**只返回（租户编号，用户编号）**，只有 `nozomi_preauth` 能执行。之后的读写照旧回到那个租户的事务里做。
- 对 `audit_logs` 只能追加「不属于任何租户、操作者是匿名」的行（策略写死了这个条件），不能读。
- 平台员工登录要读平台账号的密码哈希，那是平台数据，所以平台登录走平台角色，不放进登录前角色。

原有的四条租户策略（没有写角色，对所有角色生效）改成只对 `nozomi_app` 生效：每个角色能看到什么，只由写明给它的策略决定。

### 应用账号由谁创建

应用账号带密码，**迁移 SQL 里不能出现密码**，所以它不在迁移里创建，由 `pnpm db:provision` 创建：

- 用迁移账号执行；应用账号的名字和密码取自 `DATABASE_URL`。只从环境变量读，没有命令行参数，只打印账号名。
- 密码不以原文发给数据库：命令在本地算出 SCRAM-SHA-256 校验值再写进 `create role` / `alter role`，数据库的语句日志里只会出现校验值。
- 可以反复运行：账号不存在就建；存在就把密码、属性、成员关系改成应有的样子（多出来的成员关系会被收回）。
- 不会去降级一个已有的超级用户、带特殊属性或拥有表的账号——那多半是连接串填错了，直接报错。
- 三个权限角色不存在时一并创建（迁移也会创建，谁先执行都可以）；已存在的权限角色不做任何改动。

各环境的做法完全一样，只是谁来运行它不同：本地是 `docker compose up -d` 之后手工运行一次；CI 是工作流里的一步；服务器上是每次部署、每次恢复时由脚本运行。

### 自检：权限过大的账号不能运行服务

`apps/api/src/db/identity.ts` 用一条只查系统目录的 SQL 判定当前登录账号是不是最小权限：不是超级用户、没有 `CREATEROLE` / `CREATEDB` / `BYPASSRLS` / `REPLICATION`、不是数据库和任何表的所有者（也不属于某个所有者角色）、恰好是三个权限角色的成员、不自动继承、三个权限角色本身没有危险属性。用在三处：

1. **进程启动时**：不合格就拒绝启动（退出码 1），列出每一条原因和处理办法。
2. **每条数据库连接第一次被事务使用之前**：不合格的连接直接销毁，一条业务 SQL 都不执行。所以即使启动时数据库连不上（此时照常启动、`/health` 报 503，这是 M0-05 定下的行为）、之后才连上，权限过大的账号也用不了。
3. **`/health` 的数据库探测**：连得上但账号不合格算数据库不可用，`database.errorCode` 是 `DB_ROLE_UNSAFE`。部署脚本以健康检查为准，所以这样的版本不会被当成部署成功。

**所有环境规则相同，local / ci 不放宽**：本地和 CI 跑的就是线上的权限，不会出现「本地能跑、线上才暴露权限不足」。代价是本地第一次要多运行一条 `pnpm db:provision`。

### 部署

- 服务器 `.env` 多一项 `POSTGRES_APP_PASSWORD`（应用账号的密码），自动生成，负责人不用管。初始化脚本会生成；在此之前初始化过的服务器，下一次部署时由部署脚本自动补上（已有的值绝不改动）。
- `deploy/compose.yml`：`api` 容器只拿到应用账号的连接串。新增不常驻的 `migrate` 服务（带 profile，`up` 不启动它），只有它拿得到迁移账号的连接串，而它拿不到登录签名密钥和第三方密钥。
- 部署：起数据库 → 备份 → **建 / 核对应用账号** → 迁移 → 启动新版本 → 健康检查。
- 恢复：停 API → 备份 → 删库重建 → **建 / 核对应用账号和权限角色** → 导入（`--no-owner`：表全部归迁移账号；备份里的授权原样恢复）→ 迁移 → 启动。角色和账号属于整个数据库实例，不在备份里，所以要在导入之前确保它们存在。
- 备份用迁移账号（应用账号读不了全部数据）。

## 验收标准 2 的严格含义

「应用账号无法绕过行级安全读到其他租户的数据」分三层说清楚：

1. **应用账号本身（不切换角色）**：对任何表都没有权限，什么都读不到。它不是所有者、没有 `BYPASSRLS`，也关不掉行级安全。
2. **切到 `nozomi_app`**：受行级安全约束，只读得到 `app.tenant_id` 指定的那个租户；不设租户时一行都读不到。
3. **切到 `nozomi_platform`**：可以跨租户读写租户主体和租户用户。这**不是绕过**行级安全，而是策略明确放行——平台员工的工作就是跨租户（ADR 0003），没有这个权限平台功能做不了。

所以正常的代码路径里，租户请求只走第 2 层，读不到别的租户。

## 剩余风险

- **能执行任意 SQL 的攻击者（SQL 注入、应用账号的连接串泄露）可以自己 `set role nozomi_platform`**，于是能跨租户读写租户主体和租户用户（包括密码哈希、邀请和重置令牌的哈希）、读全部审计日志、读写平台账号。也可以设任意的 `app.tenant_id` 后以 `nozomi_app` 读写任何一个租户。数据库层面区分不了「服务代码切换角色」和「攻击者切换角色」。
- 这仍然比原来好得多，因为他**做不到**的事情变多了：
  - 改不了、删不了、清不掉审计日志，关不掉保护它的触发器，也设不了 `session_replication_role`——他做过的事情抹不掉；
  - 删不了表、改不了结构、关不掉行级安全、改不了策略和函数；
  - 提不了权：不能建角色、不能改自己的属性、不能切到迁移账号；
  - 读不了操作系统上的文件、执行不了系统命令（那是超级用户才有的能力）；
  - 删不了租户、租户用户、平台账号（没有 `delete` 权限）。
- 防注入仍然靠全部查询使用参数化；防连接串泄露靠密钥只放在服务器 `.env`（ADR 0005、ADR 0007）。
- 进一步收窄（例如把平台事务换成第二个登录账号、第二个连接池，让租户请求所在的连接根本切不到平台角色）会让攻击面再小一圈，但要多一套密码和连接池，而平台登录和租户登录在同一个进程里，收益有限。等平台后台和对外 API 拆成独立进程时再做，届时新增 ADR。
- 两个定位函数会告诉调用者「这个邮箱 / 邀请令牌对应哪个租户的哪个用户」。能调用它们的攻击者可以枚举邮箱是否注册过，但拿不到任何账号内容。
- 应用账号可以建临时表（PostgreSQL 默认给所有账号这个权限）。两个定位函数的查找路径固定且临时表排在最后，同名临时表骗不了它们（有测试）。
- 迁移账号在 Compose 下仍是超级用户。它只出现在迁移和备份恢复时，不在服务进程里。

## 以后新增表时要做的事

在迁移文件里（和建表同一个迁移）：

1. **默认谁都没有权限**：新表建出来时三个角色都碰不到它，这是安全的默认状态。不要 `grant … to public`。
2. **租户表**：照 ADR 0009 做（带 `tenant_id`、开行级安全），策略写明 `to nozomi_app`，`using` 和 `with check` 都是 `tenant_id = app_tenant_id()`；按需要 `grant` 给 `nozomi_app`。
3. **平台也要访问这张租户表时**：再 `grant` 给 `nozomi_platform`，并加一条写明 `to nozomi_platform` 的策略。只给用得到的权限；不给 `delete` / `truncate`，除非业务确实要删。
4. **平台表**（不带 `tenant_id`）：不开行级安全，只 `grant` 给 `nozomi_platform`。
5. **登录前角色**：原则上不给任何新表的权限。确实需要在登录前查的东西，用只返回最少字段的 `security definer` 函数，并固定 `search_path`、收回 `public` 的执行权。
6. **不要把任何权限直接给应用账号**：迁移里不知道也不应该知道它的名字。
7. 更新 `apps/api/src/schema-structure.itest.ts` 里的三张清单：`ROLE_GRANTS`（每个角色在每张表上的权限）、`PLATFORM_TABLES`（平台表）、`CROSS_TENANT_POLICIES`（不限定在当前租户的策略）。清单和库里的实际情况有任何出入，测试都会失败：漏了行级安全、多给了权限、把权限给了清单外的账号、多了一条跨租户策略、多了一个 `security definer` 函数。

## 验证

- `apps/api/src/db-roles.itest.ts`：用应用账号的真实连接逐条尝试，全部被数据库拒绝——不切换角色读写每一张表；切到租户角色读别的租户、关行级安全；切到登录前角色读账号数据、冒充别人写审计；在不切换角色和三个角色下分别对审计日志 `update` / `delete` / `truncate` / `drop`、关触发器、删触发器、改触发器函数、`session_replication_role`、改表结构、换所有者；给自己提权、建对象、切到迁移账号。把迁移账号或其他权限过大的账号配给服务进程和管理员命令行：拒绝启动 / 拒绝执行。
- `apps/api/src/schema-structure.itest.ts`：三个角色的权限清单精确匹配；所有表属于迁移账号；应用账号和三个角色的属性；`security definer` 函数只有登记过的两个。
- `apps/api/src/db-roles-upgrade.itest.ts`：停在迁移 0004 并已有数据的库升级到 0005。
- `apps/api/src/db/provision.itest.ts`：建账号、重复运行、换密码、把被改歪的账号改回来、拒绝降级特权账号。
- 其余全部接口测试的应用代码都用应用账号连接（`apps/api/src/testing/db.ts`），直接摆数据和核对结果才用迁移账号。
- `deploy/ci/smoke.sh`：真实容器里，`api` 的环境里没有迁移账号的密码，数据库看到的 API 连接全部来自应用账号，用它的连接串越权全部被拒绝；备份恢复后登录照常可用，应用账号仍是最小权限。

## 理由

- **为什么是「一个应用账号 + 切换角色」，而不是三个登录账号、三个连接池**：只多一个密码；现有「每个事务一个入口」的结构不用变；连接池不会被分成三份各自吃紧。代价见「剩余风险」第一条。
- **为什么平台角色不用 `BYPASSRLS`**：那会让它对以后新增的每一张租户表自动有效，新表默认就对平台敞开。写明的策略让「平台能碰哪些租户表」成为每张表的显式决定，并且能被结构测试核对。
- **为什么登录前单独一个角色**：登录、接受邀请这些接口不需要登录就能调用，是最容易被探测的入口；让它们运行在读不到任何账号数据的角色下，代码写错时能泄露的东西最少。
- **为什么自检不只在启动时做**：数据库连不上时服务照常启动是既定行为，只在启动时检查会留下「启动时没查成、之后一直没查」的空档。
- **为什么本地和 CI 不放宽**：权限问题只有在真实的最小权限下才测得出来；放宽等于让全部集成测试继续以所有者身份运行。

## 对迁移账号的要求

- 需要能创建角色（超级用户或 `CREATEROLE`）。Compose 的默认账号是超级用户。
- 用没有这些权限的托管数据库账号时，迁移和 `pnpm db:provision` 会失败并说明原因；需要数据库管理员先建好三个权限角色和应用账号。
