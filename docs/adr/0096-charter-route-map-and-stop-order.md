# ADR 0096：包车行程地图（编号 1、2、3…）与经停顺序优化

- 状态：**草案第一稿**（2026-11-15），待独立审查和业主确认第十节。
- 工作项：**M9P-20**（roadmap 已登记，受阻于本篇采纳和 M9P-04）。
- 依据：业主需求（监工 2026-11-15 转达，要点 a–f 见下）；ADR 0042（路线预估）、0072（静态路线图）、0088 / 0089（经停、按行程计价）、0091（缓冲 T）、0093（三层区域，含 M9P-16 改期锁价）、0094 第七节（地图与谷歌条款）、0095（嵌入页）。
- 编号：main 上最大是 0095；0087（#186）、0092（#219）被未合并的 PR 占用，其余开着的 PR 不新增 ADR，这里用 0096。
- **只加不改**：
  - 点对点（接送机）的路线图、报价都不变。
  - 不带新字段的包车询价逐字不变，golden 0 条变化。
  - 经停顺序只影响路线里程、时长（从而影响选档、超公里），**不改区域加价算法**（第五节第 3 小节）。

业主需求要点：

| # | 要点 |
| --- | --- |
| a | 包车报价页（主站和嵌入页）像点对点一样显示地图，用 1、2、3… 标先后：上车 = 1，经停依次，下车 = 最后；旁边的行程列表同样编号，每段显示时长和公里 |
| b | ≥ 2 个经停时固定起终点、算最优顺序（Routes API `optimizeWaypointOrder`）；省 ≥ 5 公里或 ≥ 10 分钟（阈值可配）时提示「建议顺序，可省 X 公里、Y 分钟、Z 円」，并排显示两条路线、两个报价；不自动改，可一键采用，也可拖动调整，数字即时重排；指定了到达时间的经停不参与重排 |
| c | 按最终顺序报价；订单保存顺序，给司机调度用 |
| d | 商品级开关，默认开 |
| e | 顺序变化不影响区域加价 |
| f | 只在经停变化时调用接口，并且要缓存 |

## 〇、结论摘要

1. **地图**：主站和嵌入页都先用**谷歌静态地图**画多点路线和编号（扩展 ADR 0072 的后端代调），不用 Leaflet。
   - 这样和 ADR 0094 第七节、ADR 0095 Q11 的条款结论一致，也不用等 M10-01 和浏览器 key。
   - 静态图出不来时**只显示行程列表**（列表本来就有全部信息），包车不加 Leaflet 后备图。
   - M10-01 / ADR 0094 P2 把主站改成 Google Maps JS 以后，主站换成可交互地图，数据接口不变；嵌入页按 ADR 0094 继续用静态图。
2. **顺序优化**：新增接口 `POST /site/v1/charter/order-suggestion`，只在**经停点集合**变了时由页面调用。
   - 服务器按「固定点」把行程切段，每段 ≥ 2 个可动经停时调一次 Routes `computeRoutes` + `optimizeWaypointOrder: true`。
   - 这一次按 **Compute Routes Pro** 计费：$10 / 千次，每月免费 5,000 次。
   - 结果按「顺序无关」的键缓存，拖动、改停留不再调用；优化调用单设每日上限。
3. **两个报价**：只有按建议顺序算出的里程、时长达到阈值时，服务器才多算一次按行程计价的报价。
   - 两个报价各有自己的报价编号和 30 分钟有效期。
   - 「一键采用」直接换用建议顺序那份报价，不再询价。
4. **到达时间**：现有经停数据（`name / lat / lng / stay_minutes`）**没有**到达时间。
   - 新增可选的 `arrive_by`（当地时间 HH:MM，「最晚到达」）。
   - 填了的经停固定位置、不参与重排；进报价快照、订单、司机页。
   - 首期不按预计到达时间校验，只在晚于指定时间时提示。
5. **区域加价与顺序无关**：
   - 上下车加价看的是上、下车点，起终点固定。
   - 行程加价是「去重后的区域集合」。
   - 下车点行程加价看「已收区域为空」，等价于「有没有①外经停」，是集合成员关系，与顺序无关。
   - 唯一随顺序变的是明细里「第几个经停」的标注（`stopSeqs`），金额不变。
   - 顺序变化带来的价格差只来自路线里程、时长：选档、超公里、调价跟着变，这正是要提示给客人的「省 Z 円」。
6. **订单**：`orders.waypoints` 本来就按数组顺序保存、下单后不可改（迁移 0370 的触发器），司机页本来就按这个顺序列「经停 1、2…」。
   - 本篇只补编号的一致性（上车 = 1）和 `arrive_by`。
   - 改期、救援（M9P-16）**沿用订单里的顺序，不重新优化**。
7. **开关**：`products.service_rules.charterItinerary.suggestStopOrder`（布尔，默认开），和 M9P-01 的「下车点行程加价」同一个键、同一套读写；服务规则页（M9P-04）上加一个勾选框。
8. **阈值**放平台配置（运营可调、对所有商品一样），默认「省 ≥ 5,000 米**或** ≥ 10 分钟」。
9. **工作量**：三期合计约 **17–23 人日**（第九节）。

## 一、现状（对照代码）

### 1. 点对点（接送机）的地图

- **画法**：右侧栏 `RouteBlock`（`apps/web/src/pages/book/new/CheckoutParts.tsx:32`）→ `RoutePicture`（`StaticRouteMap.tsx`）。
  - 先请求 `GET /site/v1/route-map?from_lat…&to_lng…`（ADR 0072）：后端从 Routes 取折线，代调**谷歌 Maps Static API**，起点 `label:A`、终点 `label:B`，灰色底图 + 品牌色路线。
  - 图片存在库表 `static_map_images` 里 1 天，浏览器也缓存 1 天。
- **后备**：静态地图返回 `NOT_ENABLED` 时，`RouteMap.tsx` 用 **Leaflet + 可配置的非谷歌瓦片**画谷歌 Routes 的折线；其他失败只显示「约 X 分钟 · Y 公里」。
- **用了谷歌数据**：
  - 折线、时长、里程来自 Routes API（`ROUTE_PREVIEW_FIELD_MASK = routes.distanceMeters,routes.duration,routes.polyline.encodedPolyline`，`apps/api/src/integrations/google-maps.ts:140`）；
  - 地点候选来自 Places（后端代调）。
- 只在 `draft.mode === "transfer"` 时显示（`BookNewPage.tsx:1262`）。

### 2. 包车现在没有地图

- 包车页没有任何地图，只有一张行程时间表：`scheduleRows`（`apps/web/src/lib/charter-itinerary.ts:214`）列「上车 / 经停 N / 下车」、停留时长和每段行驶分钟。
  - **每段没有公里**；
  - 编号是「经停 1、2…」，上车、下车不编号。
- 经停输入 `WaypointsField.tsx`：
  - 最多 `MAX_WAYPOINTS = 10` 个，停留 30 分钟一档、最多 8 小时；
  - 已有「上移 / 下移 / 删除」按钮和 Alt + ↑ / ↓，移动后焦点跟着走，读屏播报「X 现在排第 N，共 M 个」；
  - **没有拖动**。

### 3. Routes API 怎么调、限额、缓存

| 项 | 现状 |
| --- | --- |
| 报价用的路线 | `computeRoutes`，`DRIVE`、`TRAFFIC_UNAWARE`、不要备选，字段掩码 `routes.distanceMeters,routes.duration`（Essentials）。按行程计价时**逐段两两调用**：上车 → 经停 1 → … → 下车（`itineraryRoute`，`apps/api/src/services/site.ts:606`），各段并行，每段受报价外部调用时限 |
| 路线缓存 | 库表 `route_estimates`（迁移 0110），键 = 起终点各取整到 3 位小数（`routeCacheKey`，约 100 米），**有向**（A→B 与 B→A 是两个键）；成功的存 7 天，没有路线的存 1 天（`ROUTE_RULES`，`packages/domain/src/route-estimate.ts`）；同一键并发只调一次 |
| 折线 | `RoutePreviewer.preview`：进程内 10 分钟、最多 500 条，不存库 |
| 每日上限（东京日期） | 路线 `GOOGLE_ROUTES_DAILY_LIMIT` 默认 **1,000**；地点 `GOOGLE_PLACES_DAILY_LIMIT` **500**；静态地图 `GOOGLE_STATIC_MAPS_DAILY_LIMIT` **300**（`packages/config/src/index.ts:194-198`）。每次真正发请求前在库里占名额，并发不超；记不了数就不调 |
| 失败 | 冷却（配额 / 密钥 60 秒，超时等 15 秒）；按行程计价某段取不到 → 422 `ITINERARY_ROUTE_UNAVAILABLE`（`details.leg`） |
| `optimizeWaypointOrder`、`intermediates` | **代码里都没有用过** |

### 4. 报价请求里的经停

- 官网 `POST /site/v1/quotes`：包车 + `itinerary_pricing: true` + `pickup` + `dropoff` + `waypoints: [{ name, lat, lng, stay_minutes }]`（有序数组）。
- 服务层类型 `SiteWaypoint`（`site.ts:501`）原样进报价快照 `snapshot.request.waypoints`。
- 应答 `itinerary_route.legs[{ minutes, meters }]` 已经**按段给了时长和米数**，页面目前只用了分钟。

### 5. 订单和司机端

- `orders.waypoints jsonb`（迁移 0370）：下单时从快照抄过来，按顺序保存。
  - 检查约束只限 1–10 个元素；
  - 列进「供应商不能改的列」，另有触发器挡住平台账号（改经停 = 取消重下）。
- 司机页 `DriverTripPage.tsx:327`：`<ol aria-label="经停点">` 按顺序列「经停 N · 名称 · 停留 · 导航到经停 N」，上车、下车各一行；`orderItineraryText` 显示全程。
- 改期：用快照的 `request`（含 `waypoints`、`routeUsage`）重算；M9P-16（#250）起加价按下单时锁定（`lockedAreaSurcharge`）。
- 救援：候选按快照的 `waypoints` / `routeUsage` 显式询价（`rescues.ts:469`）。

### 6. 谷歌条款现状（ADR 0094 第七节已定论）

- 《服务专用条款》19.2：Routes 内容不得与非谷歌地图一起使用。14.2（Places）、6.2（Geocoding）同理。
- 所以：
  - 主站的 Leaflet 后备路线图（`RouteMap.tsx`）和 Leaflet 地图选点（`SiteMapPicker.tsx`）有违约风险，由 **M10-01** 核实整改；
  - 嵌入页（ADR 0095）本来就不带 Leaflet。

## 二、地图方案

### 1. 三个选项

| | 甲：谷歌静态地图（扩展 ADR 0072）**推荐首期** | 乙：Google Maps JavaScript API | 丙：等 M10-01 再做地图 |
| --- | --- | --- | --- |
| 条款 | 合规：谷歌自己的地图，路线、标记都画在谷歌底图上 | 合规 | — |
| 前置条件 | 无：Maps Static 已开通（ADR 0072 待确认第 1 项） | 业主新建**浏览器 key**（只开 Maps JS、限官网域名）填进后台；CSP 放行谷歌域名；修订 ADR 0017（ADR 0094 第七节第 2 小节） | M10-01 完成 |
| 密钥进不进浏览器 | 不进（后端代调） | 浏览器 key 进浏览器（受域名限制） | — |
| 嵌入页 | 可直接用（ADR 0095 Q11 业主要「至少和主站一样的路线摘要图」） | ADR 0094 定为「嵌入组件只放静态缩略图」 | — |
| 交互 | 只能看；每换一次顺序重出一张图 | 可缩放、点标记联动 | — |
| 计费 | Static Maps $2 / 千次，每月免费 10,000 | Dynamic Maps $7 / 千次，每月免费 10,000 | — |
| 本篇采用 | **首期主站、嵌入页都用** | 第二期只换主站，在 M10-01 / ADR 0094 P2 之后 | 不采用：需求 a 可以不等 |

**结论**：

- 首期两边都用甲。
- 包车**不加 Leaflet 后备图**：静态地图 `NOT_ENABLED` 或其他失败 → 不显示地图，只显示行程列表。新功能不增加新的条款风险，也不让嵌入页和主站分叉。
- 点对点现有的 Leaflet 后备图照旧，由 M10-01 处理。
- 主站换 Maps JS 时，用同一份「有序点 + 每段折线」数据，前端换组件即可。

### 2. 后端：多点静态路线图

新增 `GET /site/v1/itinerary-map`，不改 `/site/v1/route-map`：

| 参数 | 规则 |
| --- | --- |
| `p` | 重复 2–12 次（上车 + 最多 10 个经停 + 下车），每个 `lat,lng`，按行程顺序 |
| `theme`、`width`、`height`、`scale` | 同 ADR 0072 |

**出图步骤**：

1. 每个点按 `routeCacheKey` 的规则取整。
2. **折线**：调一次 `computeRoutes`，经停作 `intermediates`、`via: false`，字段掩码 `routes.polyline.encodedPolyline,routes.legs.polyline.encodedPolyline`。
   - ≤ 10 个中间点，按 Essentials 计费（见第三节第 2 小节出处）。
   - 折线是经纬度，按条款 19.3 可以缓存不超过 30 天；本篇存库 7 天，和路线缓存一致。
   - 缓存键 = 有序点列（取整后）。
3. **图**：
   - `path` 用品牌色；
   - `markers` 逐点编号：1–9 用谷歌内置的 `label`（只支持单个字符 A–Z / 0–9）；
   - 10–12 用本站提供的**自定义图标**（`icon:https://<官网域名>/map-markers/10.png`；谷歌限每个请求最多 5 种自定义图标，10–12 只用 3 种）；
   - 上车、下车标记用另一种形状，或者深浅区分；
   - 图例由页面上的列表承担。
4. **缓存与上限**：同 ADR 0072，库里 1 天、浏览器 1 天，计入 `GOOGLE_STATIC_MAPS_DAILY_LIMIT`。
   - 图片缓存键 = 样式版本 + 主题 + 尺寸 + 倍率 + 有序点列；
   - 折线调用计入 `GOOGLE_ROUTES_DAILY_LIMIT`。
5. **失败**：503 `ROUTE_MAP_UNAVAILABLE`，原因分类同 0072；页面一律只显示列表。
6. 网址超过 15,000 字符时按 0072 的抽稀办法逐段抽稀，点位不动。

**为什么折线不逐段两两调用**：

- 两两调用 11 段要 11 次，而且折线只在进程内 10 分钟。
- 一次带中间点只要 1 次。
- 报价仍用现有的逐段估算和缓存，**不改报价口径**。地图上的折线和报价里程可能有几十米的差别，只影响画线，不影响列表里的数字。

> M9P-10 放开经停上限后（> 10 个中间点）：折线调用进入 Pro 计费档（11–25 个中间点）；编号 > 12 时自定义图标超过 5 种，13 起不标数字，列表照常编号。到时在 M9P-10 里处理。

### 3. 页面：编号、列表联动、每段时长和公里

- **编号**：上车 = 1，经停依次 2…N+1，下车 = N+2。
  - 地图标记和列表**用同一个函数**生成（`stopNumbers(points)`），编号只来自顺序，不另存。
  - 现有 `scheduleRows` 的「经停 1」改为「2 · 经停」这种「编号 + 类型」写法，具体文案由美工定。
- **每段时长和公里**：列表两行之间显示「↓ 约 35 分钟 · 28.4 公里」。
  - 取报价应答 `itinerary_route.legs[i]`（报价同一口径）；公里用 `kmText`（M9W-09 的取整规则）。
  - 没有经停、按自选时长报价时（不估路线），取地图折线那次调用的 `routes.legs` 里程、时长，只作展示。
  - 取不到就不显示这一行。
- **联动**：
  - 首期静态图不能点；列表行悬停、聚焦时只高亮列表本行，不重出图。
  - 第二期换 Maps JS 后，列表行和地图标记双向高亮。
- **换顺序时**：
  - 列表数字立刻重排；
  - 地图在顺序停止变化 800 毫秒后才请求新图，等图期间旧图盖一层「路线更新中」，避免旧编号和新列表对不上，也避免拖动时每一步都出一张图。
- **手机（≤ 640px）**：
  - 地图在上（宽度占满，高度不超过 40vh）、列表在下；
  - 两条路线对比改成分段切换「当前顺序 / 建议顺序」，不并排；
  - 360px 宽不横向滚动（`docs/design/03-layout.md`）。
- **嵌入页**：
  - 同一个组件，图宽按框宽；
  - 不加载 Leaflet、不加载 Maps JS（ADR 0095 的「一个 JS、一个 CSS」和 CSP 不变）；
  - 自定义标记图标走主站域名，不需要嵌入页另外放行。
- **无障碍（地图不是唯一信息来源）**：
  - 图是 `<img>`，`alt` 写全程摘要：「路线图：1 新宿 → 2 河口湖 → 3 箱根 → 4 新宿，约 6 小时 10 分钟 · 312 公里」；
  - 有序列表 `<ol>` 本身带全部点、编号、每段时长和公里；
  - 建议顺序用文字完整写出来，读屏能读到；
  - 颜色不是唯一区分：上车、下车除颜色外还有形状或文字。

## 三、顺序优化

### 1. 什么时候调用

- **页面**：经停**点集合**（不看顺序、不看停留分钟）或固定点（第 5 小节）变了，防抖 800 毫秒后调 `POST /site/v1/charter/order-suggestion`。
  - 拖动、上移下移、改停留只重新询价，**不调优化**。
  - 这是需求 f 的「只在经停变化时调用」。
- **服务器**：先算「可动经停」。
  - 起终点和带 `arrive_by` 的经停是固定点，把行程切成几段，每段内部的可动经停只在段内重排，不跨过固定点（跨过就可能改变到达固定点之前要去的地方）。
  - 只有某段里 ≥ 2 个可动经停时才调用谷歌；
  - 所有段都 < 2 个可动经停 → 不调用，应答 `suggestion: null`（`reason: "NOT_APPLICABLE"`）。
- **商品开关**：这次上下车点匹配到的商品**全部关了** `suggestStopOrder` 时不调用（第六节）。

### 2. 请求和计费（出处见文末参考）

- 每段一次 `computeRoutes`：
  - `origin`、`destination` = 段的两端，`intermediates` = 段内可动经停，`optimizeWaypointOrder: true`；
  - `DRIVE`、`TRAFFIC_UNAWARE`（和报价同口径；优化不能用 `TRAFFIC_AWARE_OPTIMAL`，也不能有 `via` 点）；
  - 字段掩码 `routes.optimizedIntermediateWaypointIndex`；只有一段时加 `routes.polyline.encodedPolyline`，同一次顺带拿建议路线的折线，省一次地图调用。
- 谷歌按行驶**时间**优化，同时考虑距离和转弯数。
- **计费**：
  - 设了 `optimizeWaypointOrder` 的请求按 **Routes: Compute Routes Pro** 计（$10.00 / 千次，每月免费 5,000 次）；
  - 一次请求只按一个最高档计；
  - 不带优化、≤ 10 个中间点的请求是 Essentials（$5.00 / 千次，每月免费 10,000 次）；
  - 每个请求最多 25 个中间点。
- **单设每日上限** `GOOGLE_ROUTES_OPTIMIZE_DAILY_LIMIT`，默认 **150 次 / 天**（东京日期）：
  - 150 × 31 ≈ 4,650，落在每月 5,000 次免费额度内；
  - 和路线的 1,000 分开计：优化用多了不挡报价；
  - 到了上限 → `suggestion: null`（`reason: "UNAVAILABLE"`），页面不提示，报价照常。
- 冷却、并发不超、记不了数就不调：照搬 ADR 0042。

### 3. 缓存键

```
opt:v1:<上车键>|<下车键>|<段1：固定端键 + 段内可动经停键排序后拼接>|<段2…>
```

- 可动经停的键**排序后**再拼：同一组点不管客人现在排成什么顺序，命中同一条缓存。所以拖动、上移下移都不会再调谷歌。
- 存什么：建议顺序本身，存成**按建议顺序排好的取整后坐标列表**；查到后按坐标映射回客人的经停。
- 保留多久：**24 小时**（库表 `route_order_suggestions`，平台表）。
  - 条款 19.3 只明说经纬度可以缓存最长 30 天；
  - 《服务条款》3.2.3(b) 不允许缓存其他谷歌内容，除非服务专用条款明确允许。
  - 这里存的就是经纬度，所以不超过 30 天；取 24 小时更保守，足够覆盖一个客人反复改顺序的时间。
  - 见第八节风险 3。
- 没有可行路线：缓存 1 天，同路线缓存的 `negativeTtlMs`。

### 4. 建议成不成立、多算一次报价

1. 拿到建议顺序后，用**现有逐段估算** `routes.estimate`（报价同一口径、同一个 7 天缓存）算两种顺序的行驶米数、分钟。
   - 当前顺序通常已在缓存里；建议顺序最多多 N+1 段新的两两路线，计入路线每日上限。
   - 省多少不用谷歌优化应答里的数，避免和报价对不上。
2. **成立条件**：
   - 省的米数 ≥ `minSavedMeters`（默认 5,000）**或**省的行驶分钟 ≥ `minSavedMinutes`（默认 10）；
   - 而且另一项不变差超过 1 公里或 3 分钟（防止「省 10 分钟、多 20 公里」也提示）。
   - 停留分钟两种顺序一样，不计。
3. 成立才**多算一次报价**：按建议顺序调现有 `itineraryQuotes`（和普通询价同一套：商品匹配、自选套餐、区域加价、调价、对客价），写询价日志。
   - 不成立不算，应答 `suggestion: null`（`reason: "BELOW_THRESHOLD"`）。
4. **Z 円**：
   - 按车型对应：建议报价里同一车型组的最低对客价 − 当前报价里同一车型组的最低对客价；
   - 标题行用客人当前选中的车型，没选时用当前最便宜的那张卡片；
   - Z ≤ 0：价格不变或建议更便宜，照常提示，文案「价格不变」或「可省 Z 円」；
   - Z > 0：建议顺序反而更贵（理论上不会，路线短了套餐、超公里不会变贵，但调价规则可能不对称）→ 不提示。
5. **应答**：`suggestion: { order: [当前经停的下标…], saved_meters, saved_minutes, itinerary_route, quote_result }`。
   - `quote_result` 和 `POST /site/v1/quotes` 的应答同一结构，含各自的报价编号和 `expires_at`。

### 5. 报价有效期（锁价）

- 两份报价各自独立，各有 30 分钟有效期，都写进 `quotes` 表、各有快照。
- **一键采用**：页面把经停按 `order` 重排，直接改用 `quote_result`，不再询价。前端把这份结果按新顺序的请求键放进报价缓存，避免重排触发一次重复询价。
  - 已过期 → 按新顺序正常重新询价（只有路线缓存，不调优化）。
- **拖动调整**：和现在一样，顺序变了就是新的询价请求，按最终顺序报价。
- **下单**：只认客人最后选的那份报价的 `quote_id`；订单的经停顺序来自那份快照的 `request.waypoints`。服务器不需要另外核对顺序，快照就是按顺序锁定的。
- 没被采用的那份 30 分钟后自然过期，和 ADR 0089 第 3 节多档询价同样的处理。

### 6. 指定到达时间的经停

- **现状**：`SiteWaypoint`、快照、`orders.waypoints`、人工报价（迁移 0380）都**没有**到达时间。
- **新增**：可选 `arrive_by`（字符串 `HH:MM`，用车当地时间，和用车日期同一天），含义「最晚到达」。
  - 进 `SiteWaypoint` → 快照 `request.waypoints` → `orders.waypoints`。jsonb 里多一个可选键；检查约束只限个数，**不需要改约束**；不带它的请求、旧单逐字不变。
  - 报价不用它：不影响价格、选档，golden 不变。
  - 页面：经停行加「指定到达时间（选填）」；
    - 填了的行显示锁形图标，不能拖动；
    - 上移 / 下移仍可用：客人自己有权改，改了固定点的位置会重新切段、重新调优化（属于「固定点变了」）。
  - 首期**只提示不拦截**：按当前顺序预计到达时间（用车时间 + 逐段分钟 + 停留 + 每站占用）晚于 `arrive_by` 时，在该行显示「预计 14:20 到，晚于指定的 14:00」。
  - 司机页：该经停加一行「须在 14:00 前到达」。
  - OpenAPI：`SiteWaypoint`、订单视图的经停加 `arrive_by`（`/sales/v1` 本期不开，见第十节第 7 条）。
- **要不要新增**：需求 b 明确要「指定了到达时间的经停不参与重排」，没有这个字段做不到。推荐新增（第十节第 3 条）。

### 7. 拖动排序的无障碍

- **保留现有键盘做法**（`WaypointsField.tsx`）：
  - 每行「上移」「下移」按钮（`aria-label` 带地点名），焦点在行内按钮上时 Alt + ↑ / ↓；
  - 移动后焦点跟到同一行；
  - `aria-live="polite"` 播报「河口湖 现在排第 3，共 5 个」，编号按新口径（含上车）。
- **新增指针拖动**：
  - 用 Pointer Events 自己实现，不引第三方库：HTML5 原生拖放在触屏上不可用；新库会让嵌入页的包更大。
  - 每行一个拖动把手（`aria-hidden`；键盘用户用上移下移，把手本身不进 Tab 顺序）；
  - 拖动中目标位置有插入线；
  - 尊重 `prefers-reduced-motion`（不做位移动画）；
  - 触屏长按 300 毫秒开始拖，避免和页面滚动冲突。
- 起终点行不能拖，也没有移动按钮。
- **「采用建议顺序」按钮**：采用后播报「已按建议顺序排列：…」；另给「恢复原来的顺序」按钮（只在本页这次采用后出现）。

## 五、报价和订单

### 1. 按最终顺序报价

不改引擎：

- 按行程计价本来就逐段估路线：上车 → 经停按数组顺序 → 下车；
- 全程米数、行驶分钟进 `routeUsage`，再按 ADR 0093 第四节自选套餐、算超公里。

顺序就是 `waypoints` 数组的顺序。

### 2. 订单快照、司机端

- 快照 `request.waypoints` 是有序数组；下单抄进 `orders.waypoints`，下单后不能改。现状已满足需求 c 的「订单保存顺序」。
- 司机页、供应商订单详情、运营订单详情、官网订单页：
  - 统一按「1 上车、2…N+1 经停、N+2 下车」编号；
  - 经停行加 `arrive_by`；
  - 每段公里、分钟取结算价明细 `settlement.itinerary`。现在 `itinerary` 只有合计，逐段在快照 `routeUsage.legs` 里；
  - 订单视图加只读的 `itinerary.legs`（只有量没有金额，和 ADR 0089 第 5 节同样的可见性）。
- 司机页「导航到经停 N」改成按新编号；另加「在谷歌地图打开全程」链接：谷歌地图网址带中间点，不调 API、不收费。

### 3. 区域加价与顺序（对照 ADR 0093 第二节伪代码）

| 部分 | 看什么 | 与顺序的关系 |
| --- | --- | --- |
| 上车加价、下车加价 | 上车点、下车点各自所在的③ | 起终点固定，优化和拖动都不动它们 → **无关** |
| 行程加价 | 遍历经停，跳过①内的；`已收区域` 去重，同一个②一单只收一次 | 结果是「①外经停所在的②的集合」各收一次。集合与遍历顺序无关 → **金额无关** |
| 下车点行程加价 | `商品开关 and 已收区域为空`，且下车点不在①、在某个②里 | 「已收区域为空」在 M9P-06 之后等价于「没有①外经停」：这是集合成员关系，与顺序无关；下车点固定 → **无关** |
| 过渡期（M9P-06 之前） | ①里的经停如果同时落在设了途经加价的③里，照现行规则收途经加价、进已收区域 | 仍按「每个经停各自落在哪」判断，与顺序无关 |
| 迁移前的商品（`charter_layout` 为空） | 查③行里的途经加价 `waypointSurchargeMinor`，同区域去重 | 同上，**无关** |

**会随顺序变的只有明细标注**：

- 某个②由「第一个落在它里面的经停」记 `stopSeqs`。顺序变了，「行程加价（富士山，第 2 个经停）」可能变成「第 3 个经停」，金额不变。
- 页面明细、订单明细按新顺序显示，符合客人看到的列表。

**价格差从哪来**：路线米数、分钟 → 自动选档（ADR 0093 第四节）、超公里费、预计用时 T（ADR 0091）→ 调价作用在合计上。这些随顺序变是有意的，就是 Z 円。

**测试保证**（第七节）：任取 golden 商品和带经停的样例，对经停做全排列（≤ 4 个经停全排列，更多随机抽 50 种），`areaSurcharge` 的上车、下车金额和行程加价合计**逐分相等**。

### 4. 改期、救援（M9P-16 锁价）

- **改期**：用快照 `request` 重算。经停及其顺序、`routeUsage`（逐段量）都来自下单时，加价用 `lockedAreaSurcharge`。
  - **不重新优化、不提示建议顺序**：改期只改日期时间。
  - 要换顺序 = 改经停 = 取消重下，和现在一样（`orders_waypoints_immutable`）。
- **救援**：候选供应商按快照的 `waypoints`（订单顺序）和 `routeUsage` 询价（`rescues.ts:469`）。
  - 原供应商扣款按 M9P-01 救援 B 基准，与顺序无关；
  - 不调优化。
- `arrive_by` 随快照带到改期、救援：只给司机看，不参与报价。

## 六、商品级开关

- **位置**：`products.service_rules.charterItinerary.suggestStopOrder`（布尔），**默认开**。
  - 不存键 = 开（`normalizeServiceRules` 只存和默认不同的项）；PUT 不带键 = 保留原值；只有包车能设。
  - 和 `dropoffItinerarySurcharge` 同一个结构（`CharterItineraryRules`，`packages/domain/src/products.ts`）、同一套读写。

  - 它是「这个商品愿不愿意被建议重排」的服务规则，和缓冲、下车点行程加价同类；

  - 关 = 这个商品的报价卡片不显示建议顺序和建议价；
  - 匹配到的商品全关 → 服务器不调优化；
  - 关了不影响这个商品接受「客人自己排的任何顺序」的报价：客人采用建议顺序后，所有商品照常按新顺序报价。
- **和 M9P-04 的配合**：
  - M9P-04 在服务规则页做缓冲三项和「下车点行程加价」开关；
  - 本任务在同一块「包车行程」里加一个勾选框「经停顺序建议」，说明写「客人填 2 个以上经停时，提示更省路程的顺序」；
  - 依赖 M9P-04 先把这一块做出来，所以 M9P-20 `blockedBy` M9P-04。
- **阈值**：不放商品里，放平台配置（第十节第 2 条）。
  - `packages/config`：`CHARTER_ORDER_SUGGEST_MIN_METERS`（默认 5000，0–100000）、`CHARTER_ORDER_SUGGEST_MIN_MINUTES`（默认 10，0–600）；
  - 不是密钥，改了重新部署生效。
  - 如果运营要在后台改，再挪进平台设置页（另开任务）。

## 七、测试和验收

### 1. 单元（domain / web lib）

- `stopNumbers`：0、1、10 个经停的编号；上车 = 1、下车 = 最后。
- 切段：
  - 没有固定点 / 固定点在头、中、尾 / 相邻两个固定点；
  - 每段 < 2 个可动时不调用；
  - 段内重排不跨固定点。
- 缓存键：同一组点不同顺序同一个键；固定点位置不同则键不同；取整规则同 `routeCacheKey`。
- 阈值判断：
  - 刚好 5,000 米 / 10 分钟成立，4,999 / 9 不成立；
  - 一项省、另一项变差超出容差不成立。
- Z 円按车型对应、Z > 0 不提示。
- **区域加价顺序无关**：对 `charter-golden` / `itinerary-golden` 里所有带经停的样例做排列，`areaSurcharge` 三项金额逐分相等；只有 `stopSeqs` 可以变。
- 静态图参数：1–9 用 `label`、10–12 用自定义图标且 ≤ 5 种；抽稀不动点。
- `arrive_by` 格式校验；预计到达晚于指定时间的提示计算（含每站占用）。
- `charterItinerary.suggestStopOrder` 读写：默认开、不存键、PUT 不带键保留、非包车 400。

### 2. 集成（真实 PostgreSQL + 本机假谷歌，从不调用真实谷歌）

- `order-suggestion`：
  - 请求体带 `optimizeWaypointOrder: true`、`TRAFFIC_UNAWARE`、字段掩码含 `optimizedIntermediateWaypointIndex`；
  - 成立时应答两份报价、各有编号和有效期；
  - 不成立不多询价，询价日志只多 0 条。
- 缓存：同一组点换顺序第二次请求，假谷歌**收到 0 次**；24 小时后过期再调。
- 每日上限：`GOOGLE_ROUTES_OPTIMIZE_DAILY_LIMIT` 到了不调、并发不超、上限 0；和路线上限分开计。
- 商品开关：全关不调；一关一开时只有开的那家卡片带建议价。
- 采用建议后下单：订单 `waypoints` 顺序 = 建议顺序；司机视图、供应商视图编号一致；`arrive_by` 带到订单和司机页。
- 改期：顺序和 `arrive_by` 不变，不调优化，加价锁定（沿用 M9P-16 用例）。救援候选询价用订单顺序。
- `itinerary-map`：编号、缓存、上限、失败分类；密钥不外泄（按值核对）。
- 租户隔离：本篇不新增租户接口；服务规则开关沿用现有商品接口的隔离测试，加一条「租户 A 改不了 B 的开关」。
- 不带新字段的询价：golden 0 条变化；回放比对 0 变化（ADR 0086）。

### 3. 端到端（chromium + webkit，主站和嵌入页各一套）

- 填 3 个经停 → 列表编号 1–5、每段时长和公里 → 地图图片请求带 5 个点。
- 打乱顺序 → 出现建议块 → 「采用」→ 编号即时重排、价格换成建议价、没有多发询价请求。
- 键盘：Tab 到「下移」→ Alt + ↓ → 读屏播报文本正确 → 焦点仍在该行。
- 指针拖动（含触屏模拟长按）。
- 带 `arrive_by` 的行不能拖、不参与建议。
- 静态图失败 → 只显示列表、不加载 Leaflet（嵌入页核对请求列表里没有 Leaflet 的包）。
- 手机 360px 不横向滚动；建议块是切换而不是并排。

### 4. 测试站验收步骤（M9P-11 之后，用 QA 测试供应商，ADR 0077）

1. 包车：新宿上车、新宿下车，经停依次填「河口湖站、横滨站、箱根汤本站」（故意绕路），各停 1 小时。
   - 看到地图编号 1–5 与列表一致，每段有分钟和公里。
2. 出现「建议顺序」提示，记下 X 公里、Y 分钟、Z 円和建议顺序。
   - 两张图、两个价格并排（手机上可切换）。
   - 截图留证。
3. 点「采用建议顺序」：编号即时重排，价格等于建议价；浏览器网络面板没有新的 `order-suggestion` 请求。
4. 用键盘把第 2 个经停下移一位：重新报价，没有新的 `order-suggestion` 请求；运营后台系统状态里优化调用次数不变。
5. 把横滨站设「指定到达时间 11:00」：它固定在原位，建议只在它前后各自重排；预计晚到时有提示。
6. 下单 → 司机页、供应商订单详情的经停顺序、编号、「须在 11:00 前到达」与下单时一致。
7. 嵌入页（演示宿主页）重复第 1–3 步。
8. 供应商后台关掉该商品的「经停顺序建议」→ 第 1 步不再出现提示，报价照常。
9. 运营后台系统状态：`routes_optimize` 今日次数、上限、被挡下次数可见。

## 十、待业主 / 监工确认（未答复按推荐做，不停工）

| # | 问题 | 推荐 | 理由 |
| --- | --- | --- | --- |
| 1 | 地图用什么 | **首期主站和嵌入页都用谷歌静态地图**（后端代调，不加 Leaflet 后备）；M10-01 / ADR 0094 P2 后主站换 Maps JS | 条款合规、不用等浏览器 key；嵌入页本来就定为静态图（ADR 0094、0095 Q11） |
| 2 | 阈值放哪 | 平台配置，默认「省 ≥ 5 公里**或** ≥ 10 分钟」，另一项变差不超过 1 公里 / 3 分钟 | 是对客体验参数，和单个商品的定价无关；放商品里每家都要配一遍 |
| 3 | 指定到达时间 | 新增可选「最晚到达时间」（HH:MM），只固定位置、首期只提示不拦截，给司机看 | 需求 b 要用；现在数据里没有；拦截要定「多晚算不行」，先不做 |
| 4 | 商品开关关掉的含义 | 只是不给这家的卡片显示建议；客人采用建议后，这家照常按新顺序报价 | 商品本来就接受客人任意排的顺序 |
| 5 | 优化调用每日上限 | 150 次 / 天，单独计 | 落在 Pro 档每月 5,000 次免费额度内 |
| 6 | 缓存时长和条款 | 建议顺序 24 小时、折线 7 天（都是经纬度，在 19.3 的 30 天内）；**现有里程、时长 7 天缓存是否合规，并入 M10-01 核实** | 3.2.3(b) 原则上不许缓存，只有经纬度有明文例外 |
| 7 | 渠道 API（`/sales/v1`） | 本期不开放建议顺序和 `arrive_by`，渠道传什么顺序就按什么顺序报 | 先在官网验证效果；渠道接口改动要通知对接方 |
| 8 | 价格不变时是否提示 | 提示（「可省 X 公里、Y 分钟，价格不变」） | 对客人仍有价值（少坐车） |
| 9 | 编号文案 | 「1 上车 · 新宿」「2 经停 · 河口湖」…「5 下车 · 新宿」，由美工定稿 | 和地图标记一一对应 |
