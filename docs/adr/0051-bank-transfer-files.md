# ADR 0051：银行转账批量文件、供应商收款账户与流水号回填

- 状态：已采纳（2026-11-01，M5-02）
- 文中「待负责人确认」的项已由 ADR 0053 落定（2026-11-01）。
- 补充 ADR 0040：付款批次的 `closed → paid` 在这里实现；账单多一列 `bank_reference`。补上它「本期不做」表里的转账文件、流水号回填、记为已付款、推 `payout.paid`、结算账户号加密存储和变更审核。
- 补充 ADR 0023：双人复核新增两类 `payout_account.activate`（启用收款账户）、`bank_file.generate`（生成转账文件）。
- 补充 ADR 0027：供应商 Webhook 多一种事件 `payout.paid`。
- 补充 ADR 0028：资质里的「结算账户证明」仍是证明文件；账号本身存在这里的收款账户表（ADR 0028 说「账户号和付款一起在财务任务做」）。
- 补充 ADR 0004：`money.ts` 的 `CURRENCIES` 增加 SGD（见「币种」）。
- 编号说明：ADR 0049、0050 和迁移 0140、0150 被 M4-08、M4-06 占用；这里用 ADR 0051、迁移 0160。

## 背景

需求：《平台运营端与渠道对接》「财务结算」（给租户付款：生成付款批次 → 双人复核 → 银行转账，导出批量付款文件，付款后回填银行流水号；**结算账户变更需租户管理员两步验证 + 平台审核**）；「风控」（租户结算账户变更：二次验证、延迟付款）；数据模型 `payout`（statement_id、amount、currency、bank_ref、status、approved_by）；《用车报价服务平台》「12. 资质认证」（账户号加密存储）；新增事件 `payout.paid`。

负责人决定（2026-10-27）：按国际汇款惯例自定范例格式（CSV / Excel），SWIFT 字段包括收款人名称 / 地址、银行名称 / 地址、SWIFT/BIC、账号 / IBAN、币种、金额、付款参考 / 用途、费用承担 OUR / SHA / BEN；支持 SGD 等多币种，以后可按银行模板调整；供应商收款账户在后台维护，真实账号不进代码、文档、测试。

这笔钱一旦转错很难追回，设计上防三件事：**有人改账号骗款**、**同一笔付两次**、**完整账号外泄**。

## 决定

### 分层

| 层 | 在哪里 | 做什么 |
| --- | --- | --- |
| 纯规则 | `packages/domain/src/bank-transfer.ts` | IBAN、SWIFT/BIC、账号、SWIFT 文字的校验；打码；费用承担；账单能不能进文件；模板（列定义集中在一处）；生成行、合计行和 CSV 文本；流水号格式 |
| 取数 | `apps/api/src/repos/payout-accounts.ts`、`repos/bank-files.ts` | 账户、文件、文件条目 |
| 流程 | `services/payout-accounts.ts`、`services/bank-files.ts` | 提交、复核、文件生成、下载、回填、作废 |
| 接口 | `routes/bank-files.ts` | 见「接口」 |

### 1. 文件内容和格式

**列定义集中在一处**（`BANK_FILE_TEMPLATES`）：一个模板是列表（列头 + 取值函数）加 CSV 选项（BOM、换行、合计行）。以后对接某家银行的模板就加一项，流程和数据不动。文件记下用的哪个模板（`bank_files.template`），重新下载时内容不变。现在只有一个模板 `swift-generic-v1`：

| 列头 | 内容 | 对应 SWIFT MT103 |
| --- | --- | --- |
| `Seq` | 序号（1 开始） | — |
| `Beneficiary Name` | 收款人名称 | 59 |
| `Beneficiary Address` | 收款人地址 | 59 |
| `Bank Name` | 收款银行名称 | 57 |
| `Bank Address` | 收款银行地址 | 57 |
| `SWIFT/BIC` | SWIFT/BIC | 57A |
| `Account No/IBAN` | 账号或 IBAN（规范化后：大写、无空格无连字符） | 59 |
| `Currency` | 币种 | 32A |
| `Amount` | 金额（字符串） | 32A |
| `Value Date` | 付款日 YYYY-MM-DD | 32A |
| `Payment Reference` | `NOZOMI <账单号> SETTLEMENT <周期>` | 70 |
| `Charges` | `OUR` / `SHA` / `BEN` | 71A |

- **一条账单一行**，不合并同一家的多张账单（付款参考能精确对到账单、流水号回填按条做）。同一家同币种同批次有两张账单时会转两笔、多一次手续费（**待负责人确认 2**）。
- **合计行**：最后一行 `Seq` 列写 `TOTAL`，`Currency`、`Amount` 写币种和合计，`Payment Reference` 写 `<条数> PAYMENTS`。银行模板不接受合计行时，模板里关掉即可。Excel 另有一张 `Summary` 工作表（文件号、付款日、币种、笔数、合计、费用承担、模板、生成时间），方便核对。
- **金额**：`formatMajor` 从最小单位整数按字符换算成字符串（JPY `12000`、SGD `1234.50`，没有千分位和货币符号），合计用 `sumMinor` 做整数加法。全程不用浮点。Excel 里金额、账号都写成**文字单元格**（账号开头的 0 不丢、长数字不变科学计数）。
- **CSV**：RFC 4180；UTF-8 **带 BOM**（Excel 打开不乱码）；换行 CRLF；只有含逗号、引号、换行的字段才加引号。因为名称和地址限定为 SWIFT 字符集（见下），正文实际只有 ASCII，BOM 去掉后也是合法 ASCII；银行系统不接受 BOM 时，模板里关掉。
- **公式注入**：以 `=`、`+`、`-`、`@`、制表符、回车、换行（以及全角的 `＝＋－＠`）开头的单元格前面加单引号；CSV 和 Excel 都防（Excel 复用 `integrations/xlsx.ts` 的 `guardFormula`，单元格本身是行内文字，不是公式）。
- **Excel 不加新依赖**：仓库已有 `integrations/xlsx.ts` 的写入器（ADR 0019，内存里生成，zip 时间固定，同样内容逐字节相同）。
- **提醒**：把 CSV 用 Excel 打开再保存，Excel 会吃掉账号开头的 0。页面写明：查看用 Excel 文件，交给银行用原始下载的 CSV，不要另存。

### 2. 收款账户

**谁维护、谁审核**：供应商的**管理员**在供应商后台提交（`company.manage`，只有管理员有），平台财务核对后发起复核（`statement.manage`），**另一位**财务批准（`statement.review`）才生效。全程三个人。批准前旧账户继续有效。平台不代填（**待负责人确认 3**）：账号由供应商自己提交，平台员工没有改账号的入口，少一条内部骗款路径。

**一种币种一个生效账户**：账户带 `currency`，账单按自己的币种找账户，不回退到别的币种的账户（`payout_accounts_active_key`、`payout_accounts_pending_key` 两个部分唯一索引：同一家同一币种最多一个生效、一个待审核）。

**数据库层的状态机**（纵深防御）：新账户只能是待审核；只允许 待审核 → 生效 / 驳回 / 撤回、生效 → 已被替换，已被替换的不能退回生效（触发器 `payout_accounts_status_machine`）。生效的账户必须有属于它自己的已批准复核，提交时检查（延迟约束触发器 `payout_accounts_active_approved`：批准的事务里先生效、后写复核结论）。

**变更通知**（负责人决定 2026-11）：提交、批准、驳回发邮件给这家的管理员（通知中心，事件 `payout_account.submitted` / `approved` / `rejected`）。只有账号末 4 位，没有对外价和加价比例；调度不收。账号被盗用时，管理员能从这封邮件发现异常提交。撤回不发。

**不可变**：账户的内容不能改（数据库触发器拦截，只能改状态和审核字段）。修改就是提交一条新记录，批准后旧的变成「已被替换」。每一次改动都留痕，审计日志只记末 4 位。

状态：`pending` 待审核 →（双人复核批准）`active` 生效 →（新账户生效）`superseded` 已被替换；`pending` →（财务驳回，原因必填）`rejected`；`pending` →（供应商撤回）`withdrawn`。复核被驳回、撤回时账户仍是待审核，由财务决定再发起或驳回给供应商。待审核时再提交同币种：409，先撤回。

**提交时的身份确认**：需求要求两步验证，但供应商账号现在没有两步验证（只有平台员工有，ADR 0030）。先要求**重新输入当前密码**，和改密码共用失败限速（`reserveLogin`）。供应商有第二因素后换成它（**待负责人确认 1**，和需求有差距）。

**敏感数据**：
- 账号用 `SecretBox` 加密（用途 `payout-account`，附加数据 `<租户编号>:<账户编号>`，密文搬到别的行解不开），库里只有密文 `account_sealed` 和末 4 位 `account_last4`。没配 `DATA_ENCRYPTION_KEY` 时不能提交（503）。
- 接口只返回 `account_masked`（`•••• 1234`），没有任何接口返回完整账号；**只有下载文件时解密**。
- 审计、复核内容、日志、错误信息都没有完整账号。校验函数只返回原因代码，不回显输入。
- 其余字段（名称、地址、银行、SWIFT/BIC）明文存放：不是能单独动钱的数据，审核要看。

**校验**（`bank-transfer.ts`，提交时校验，发起生成和批准时再校验一次）：
- 账号、BIC 的规范化只转 ASCII 字母：`ß`、`ı`、`ſ`、`ﬁ` 不会被改写成别的字母，校验直接拒绝。
- IBAN：国家 + 长度（ISO 13616 登记表）+ 校验位只接受 02–98 + mod-97。
- SWIFT/BIC：ISO 9362，8 或 11 位，第 5–6 位是国家代码。
- 其他账号：规范化后 4–34 位字母数字（SWIFT 59 栏上限 34）。
- 名称、地址：只能是 SWIFT X 字符集（`A-Za-z0-9 /-?:().,'+`）；收款人和银行名称最长 70（35 × 2）、地址最长 105（35 × 3），不能以 `-`、`:`、`/` 开头。中文、`&` 会被拒绝并提示写英文（**待负责人确认 4**）。

**风控「延迟付款」**：账户替换了旧账户、且批准不到 7 天的，预览里标「账户最近变更」提醒财务核实，**不拦截**（**待负责人确认 5**）。

**审核时只看得到末 4 位**：财务按结算账户证明核对户名、银行、SWIFT、币种和末 4 位，不看完整账号。

### 3. 批次和状态

**按「付款批次 + 币种」出文件**。付款批次（ADR 0040）是一个付款日一个、可含多币种，而一个转账文件只能一种币种（银行按付款币种分账户），合计也不能跨币种。所以一个批次里每种币种各出文件；账户有问题的账单补好后，可以给同一批次同一币种再出一个文件，只包含剩下的。

**前提**：批次必须已锁定（`closed`），否则 409 `BATCH_NOT_CLOSED`。锁定后不再进新账单，核对的内容才不会变。

**能进文件的账单**（`statementFileIssue`，按顺序判断）：

| 代码 | 情形 |
| --- | --- |
| `NOT_APPROVED` | 不是「已复核通过，待付款」（`in_payout` 且有复核记录） |
| `NON_POSITIVE_AMOUNT` | 金额 ≤ 0 |
| `CURRENCY_UNSUPPORTED` | 平台不支持的币种（算不出小数位） |
| `ACCOUNT_MISSING` | 这种币种没有账户 |
| `ACCOUNT_PENDING` | 账户还在审核，没有生效的 |
| `ACCOUNT_INVALID` | 生效账户的字段现在不合规则 |
| `ACCOUNT_UNREADABLE` | 账号解不开（只在发起生成时检查：预览不解密） |

**金额为 0 或负数**：ADR 0040 已经分流——复核通过时合计 0 记「无需付款」、合计为负（违约金扣减后）转入下一期，都不进付款批次，数据库约束 `statements_outcome_total` 把关。这里再把关两层：`NON_POSITIVE_AMOUNT`、`bank_file_items_amount_positive`。

**不静默跳过**：预览（`GET …/bank-file-preview`）按币种列出可进文件的、有问题的（供应商、账单号、金额、原因）、已在文件里的。发起生成时有问题的账单必须明确确认：不传 `allow_exclusions: true` 就 409 `BANK_FILE_EXCLUSIONS` 并列出；确认后这份名单写进复核内容和文件记录（`bank_files.excluded`），审核人看得到。没有一张能进的 409 `BANK_FILE_EMPTY`。

**发起时才发现账号解不开**：预览不解密（完整账号只在必要时取），发起时才解。这时 `BANK_FILE_EXCLUSIONS` / `BANK_FILE_EMPTY` 的 `details.excluded` 把这些账单列回来，对话框列出名单和确认项，确认后发出 `allow_exclusions`；一张都进不了的只说明原因，不让再提交。

**批准时也解密校验**：解不开、不合规则、末 4 位对不上就不生成（409 `BANK_FILE_ACCOUNT_UNREADABLE`，复核仍是待审核，由审核人驳回），不会产生永远下载不了的文件。

**不支持的币种**：预览不报错，按 `CURRENCY_UNSUPPORTED` 列出，金额写最小单位。

**条目币种等于文件币种**：外键 `bank_file_items_file_currency_fkey` 保证。

**不重复付款（数据库保证）**：`bank_file_items_active_key` 是 `(tenant_id, statement_id) where voided_at is null` 的部分唯一索引，一张账单同时只能在一个未作废的文件里。作废文件时把未付款的条目标记作废，账单释放。

**生成走双人复核**：财务发起（`statement.manage`），复核内容是每一笔的供应商、户名、SWIFT、账号末 4 位、金额，以及排除名单；另一位批准（`statement.review`），**文件在批准的事务里生成**。没有「待复核的文件」这种状态，驳回、撤回不留任何东西。批准时重新核对：批次版本、每张账单的状态、账户还是发起时那一个；变过就 `APPROVAL_STALE`，改账户不会把未审核的账号带进文件。同一批次同一币种同时只有一条待审核（409 `BANK_FILE_REVIEW_PENDING`）。ADR 0040 的账单复核审的是「该不该付」，这里审的是「付到哪里」，两者不重复。

**快照**：批准时把账户字段和密文复制到文件条目。之后供应商再改账户，文件内容不变（审过的就是这个账号）；详情标「账户已变更」，财务自行决定是否作废重出。

**文件状态**：`generated` 已生成 →（第一次下载）`downloaded` 已下载 →（全部回填）`paid` 已付款；`generated` / `downloaded` →（作废，原因必填）`void`。

**回填流水号**：只有已下载的文件能回填；一次可以回填多笔，可以分多次；同一流水号可以用在多笔上（有的银行一个文件一个流水号）。每笔：条目记流水号，账单 → `paid`、写 `bank_reference`，写账单经过和审计，推 `payout.paid`。全部回填后文件 `paid`；批次里所有账单都 `paid` 后批次 `paid`。同一笔同一流水号再提交原样返回（幂等），不同流水号 409 `BANK_FILE_ITEM_ALREADY_PAID`，防止手滑改掉记录。回填单人操作（钱已经转了，只是记账），全部进审计。

**部分退汇**：已回填过部分条目的文件作废时，只作废未付款的条目（账单释放，可进新文件），文件记为 `paid`，不会把已付的账单退回去。作废的对话框提醒：**文件如果已经交给银行，先到银行撤销**，否则重新生成会重复付款。

### 4. 下载和审计

- `POST /platform/v1/bank-files/{id}/download`，`{ "format": "csv" | "xlsx" }`。用 POST：下载会改状态、写审计，不能被预取或缓存。
- 权限：`statement.manage`（财务、超级管理员），只读角色不能下载。数据范围：限定了范围的 403（和整个财务结算一样）。只有 `generated`、`downloaded` 的文件能下载。
- **不落盘**：库里不存文件，也不写磁盘。每次下载从条目快照在内存里生成。解密失败返回 409 `BANK_FILE_ACCOUNT_UNREADABLE`，不会给出一份缺账号的文件。
- **内容基准**：批准生成时算一个 HMAC（主密钥派生，改库的人重算不了）记在 `bank_files.content_digest`，CSV 和 Excel 共用。覆盖文件号、币种、模板、手续费、笔数、合计，以及每一笔的账单、账户编号、账号密文的哈希、末 4 位、金额、收款人和银行。
- **每次下载都核对**，不依赖「第一次下载」：账号解得开 → 解出的末 4 位等于快照的末 4 位 → 笔数、合计等于条目之和 → 内容基准一致 → 已记过的 SHA-256 一致。任何一项不过都拒绝（`BANK_FILE_INTEGRITY` / `BANK_FILE_ACCOUNT_UNREADABLE`），不改状态、不计次数。
- **拒绝也留记录**：下载的事务回滚后，另开事务写一条审计（`bank_file` / `integrity_failed`：谁、格式、原因，没有账号），并记错误日志（`bank_file.integrity_failed`）。
- **文件指纹**：内容是确定的（来自快照，时间取生成时间，zip 时间固定）。第一次下载某种格式时记 SHA-256，给人核对；写过就不能改（触发器 `bank_files_sha_once`），基准列平台角色改不了（`bank_files_platform_columns`）。
- **账户换过之后下载要确认**（负责人决定 2026-11）：文件生成后这家这种币种的生效账户换过、这笔还没付款时，接口要 `acknowledge_account_changed: true`，否则 409 `BANK_FILE_ACCOUNT_CHANGED`；页面先弹确认。审计的 `account_changed_acknowledged` 记下这次是确认后下载的。文件内容不变，仍是批准时的账号。
- **审计**：每次下载一条（`bank_file` / `download`）：谁、IP、格式、SHA-256、笔数、合计、币种、第几次。没有账号，也没有条目内容。
- **响应头**：`Cache-Control: no-store`（`/platform/` 下的接口统一带）、`Pragma: no-cache`、`X-Content-Type-Options: nosniff`、`Content-Disposition: attachment`。
- **文件名**：`nozomi-bank-transfer-<付款日>-<币种>-<文件号>.csv`，没有供应商名和账号。

### 5. 租户隔离和规则 4

- 账户表、文件条目表带 `tenant_id`，开行级安全。供应商接口的租户编号只来自令牌；读在租户事务里，提交、撤回在平台事务里按「令牌里的租户 + 编号」找，别的供应商的 404；请求体带 `tenant_id` 被拒绝（400）。
- 租户角色对 `payout_accounts` 只有 `select`，没有写权限；文件条目表、文件表租户角色没有任何权限。
- 供应商读账户的查询不取密文列，`account_sealed` 不出现在 `/tenant/v1` 的任何返回里（项目规定不用列级授权，见 `schema-structure.itest.ts`；密文本身也解不开）。
- 账户和文件都只有结算价一侧的数，`/tenant/v1` 没有对外价和加价比例，集成测试扫描字段名。

### 币种

`CURRENCIES` 增加 SGD（2 位小数）。`FX_CURRENCIES` 由它推出，汇率中心、子品牌币种、汇率锁定会一起支持 SGD：不加的话，SGD 的账单无法显示金额，也不可能有 SGD 的子品牌。上线后：
- 汇率源必须带 SGD，否则整批拒收（`FX_SOURCE_MISSING_CURRENCY`）；**拒收时就告警**（负责人决定 2026-11：通知中心 `fx.alert`，`kind: source_rejected`，同一天一次），不等 48 小时过期。现在用的公开汇率源带 SGD；集成测试和端到端的假数据源已补上。
- 上线前的汇率批次里没有 SGD，下一次拉取之后才有。这期间没有 SGD 的子品牌，没有影响。
- EUR 等其他币种仍不支持。要加同样是在 `CURRENCIES` 里加一项。

### 费用承担

**由财务在发起生成时选，默认 `SHA`**（各付各的，国际汇款最常见），整个文件一个值，写进复核内容。不让供应商选：选 `OUR` 意味着平台付全部手续费，是商务条款（**待负责人确认 6**）。

## 已知限制（有意不修）
