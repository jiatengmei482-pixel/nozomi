# ADR 0077：测试环境专用的 QA 测试供应商（`pnpm qa:tenant-ensure`）

- 状态：已采纳（2026-11-10；M8-16 实施）。
  - 业主 2026-11-09：「Tokyo-Taxi」（原「验收专用车队」，`qa-tenant@`）按真实供应商对待，验收永远不用它；需要供应商端写入实测时，用项目自己的脚本在测试环境另建一个名字带「QA 测试」的供应商，不上架、不参与官网比价（roadmap M8-16 的验收标准）。
- 补充 ADR 0028（供应商入驻和状态机）、ADR 0008（账号和登录）、ADR 0013（命令行建账号、密码不进命令行参数）。**都不改**：正常供应商的入驻、资质审核、双人复核、上架条件一条都没有放宽。
- 编号：写这篇时 main 上最大是 ADR 0076；0075 由 M8-20 占用。迁移用 0300（main 上最大 0280，M8-20 占用 0290）。

## 背景

验收角色要在测试环境做供应商端的写入实测（区域、商品、价格规则、加价、导入导出、试算）。测试环境里现有的供应商都要按真实供应商对待，不能拿来写测试数据；规则 1（没有演示数据）又不允许迁移或代码预置一家供应商。需要一个**显式运行才会建**、**永远不会被卖出去**的测试供应商。

## 决定

### 1. 用已有的状态机挡住「卖出去」，加一个明确的标记做兜底

ADR 0028 已经规定：申请中、审核中、已签约的供应商能建区域、商品、价格，**不能上架**（`tenantCanPublish`，409 `TENANT_NOT_ONBOARDED`），**不参与比价**（`tenantBids`：官网、销售端询价和下单、救援都只认试运营和正式）；供应商自己的试算不看供应商状态（`forOwner`），照常能用。所以 QA 测试供应商就停在「申请中」，验收要用的写入全都能做。

只靠状态不够：运营可能顺手把它签约、开始试运营。所以加一个明确的标记 `tenants.is_test_tenant`（迁移 0300），并在三层把住：

| 层 | 做法 |
| --- | --- |
| 数据库 | 检查约束 `tenants_test_tenant_never_sells`：带标记的供应商只能是申请中、审核中、已签约、已清退。任何代码出错要把它改成试运营、正式、暂停，数据库都拒绝。部分唯一索引 `tenants_one_test_tenant`：全平台最多一家（清退了也占着位置） |
| 业务逻辑 | 唯一的状态写法 `applyTenantChange` 和状态机的一步 `transitioned` 先检查：进入这几种状态以外的状态 409 `TEST_TENANT_NOT_FOR_SALE`（运营点「开始试运营」看到的是这条中文说明）。清单在 `@nozomi/domain` 的 `TEST_TENANT_STATUSES`，和约束一致，有单元测试 |
| 已有的 | 上架要求试运营以后（`tenantCanPublish`）；询价、下单、官网城市和机场列表只认试运营、正式（`tenantBids`） |

不在报价目录的查询里另加 `where not is_test_tenant`：供应商自己的试算走同一个查询（要能看到自己没上架的商品），而状态这一关已经由约束保证，再加一道只会让两条路径不一致。集成测试直接在库里把它的商品改成「已上架」，证明官网城市、机场、询价和销售端询价都和没有它时一样（`qa-tenant.itest.ts`）。

### 2. 只用命令行建：`pnpm qa:tenant-ensure`

`pnpm qa:tenant-ensure --email <管理员邮箱> [--name <姓名>] [--reset-password]`（`apps/api/src/cli/qa-tenant-ensure.ts`，逻辑在 `services/qa-tenant.ts`）：

- **只允许 `APP_ENV` 是 staging**（以及本机 `local`、CI 的 `ci`，自动测试用）。production 直接拒绝：先读配置、判断环境，不读密码、不连数据库，说明「当前环境是 production……」。
- **不是迁移，也不是预置数据**：部署、迁移、服务启动都不会建这一行，只有运维显式运行这条命令才会。
- **可以重复运行**：
  - 还没有：建供应商「QA 测试供应商（验收专用）」（申请中、`is_test_tenant`）和一位**在用**的管理员（角色管理员，密码就是给的这个，不是临时密码，不用先改密码）。
  - 已经有、邮箱是它的账号：只核对并报告（名称还带不带「QA 测试」、是否已清退、账号是不是在用的管理员），**什么都不改**，也不读密码；有问题时退出码 2，不自动修复。
  - 已经有、邮箱不是它的账号：409 `QA_TENANT_EMAIL_MISMATCH`，说出已有的那家和它的管理员邮箱，不建第二家、不加账号。
  - 加 `--reset-password`：从标准输入读新密码，重设这位管理员的密码，他已有的登录全部失效（`admin:reset-password` 同样的做法）。账号不是在用状态时不改（409 `ACCOUNT_NOT_ACTIVE`）。
- **密码**：和 `admin:create` 一样，只从标准输入读（终端里交互输入两遍、不回显；管道 / 重定向时读一遍，去掉末尾一个换行）。不接受命令行参数（`--password` 和位置参数都是用法错误），不从环境变量读。按平台的密码强度规则校验；数据库只存哈希；不打印、不进日志。
- **审计**：记为「系统 / 命令行」（`actor_type = system`、`source = cli`、没有 IP）：建供应商（`tenant` / `create`，`after` 只有名称、状态、`is_test_tenant`）、建管理员（`tenant_user` / `create`，邮箱、姓名、角色、状态）、重设密码（`tenant_user` / `reset_password`，`after` 为空）。审计里没有密码。
- 建供应商和管理员在平台事务里做（和运营后台「新建供应商」一样）；重设密码在这家供应商自己的租户事务里做（会话表只有租户角色能删），租户编号来自刚找到的那一家 QA 测试供应商，不来自参数。

**为什么不走正常流程**：正常的新供应商由招商在后台建、管理员凭邀请链接自己设密码，签约、试运营要资质审核和双人复核。QA 测试供应商不需要也不应该走这些：它永远不签约、不试运营。用命令行直接建出在用的管理员，是业主批准的唯一入口（M8-16）；它绕开的只是「邀请邮件」这一步，审核、复核规则对正常供应商一条都没变，对它也没有放宽（它根本进不了需要审核的那几步之后的状态）。

### 3. 接口和后台

- 供应商主体（`Tenant`，运营后台和供应商自己看到的同一份）多一个字段 `is_test_tenant`（布尔，必有）。它不是对外价、加价比例（规则 4 不受影响）。
- 运营后台的供应商列表、详情据此显示「测试」标记——页面由前端任务 M8-24 做，这里先在接口里提供。

### 4. 凭据放在哪里

- 测试环境 QA 测试供应商管理员的密码只存在运维机器上的文件 `~/.ssh/nozomi/qa-staging-tenant-password`（权限 600），由协调者在本机随机生成，经管道传给命令；不进仓库、聊天、日志、命令行参数和提交记录。
- 管理员邮箱不是密钥，记在同目录的说明文件里（`docs/secrets.md`「测试环境的 QA 测试供应商」）。
- 验收角色在测试环境做供应商端写入实测时用这家；永远不用 `qa-tenant@` / 「Tokyo-Taxi」。

## 测试

- `packages/domain/src/tenants.test.ts`：QA 测试供应商能处在的状态里没有能上架或比价的。
- `apps/api/src/services/qa-tenant.test.ts`：只允许 staging、local、ci。
- `apps/api/src/cli/qa-tenant-ensure.itest.ts`（真的启动命令）：production 拒绝且什么都不建；参数里的密码被拒绝；弱密码不建；staging 第一次建好并能登录、审计记系统 / 命令行；重复运行什么都不改（不读密码）；换邮箱不建第二家；核对发现问题时退出码 2；`--reset-password` 后旧密码和旧登录失效；输出、审计、服务日志里都没有密码。
- `apps/api/src/qa-tenant.itest.ts`（真实接口）：管理员能登录、建品牌、区域、商品、价格规则、调价规则、试算；上架 409；运营开始试运营 409 `TEST_TENANT_NOT_FOR_SALE`；数据库拒绝改成试运营、正式、暂停和第二家；商品被直接改成已上架时官网城市、机场、询价和销售端询价不变；租户隔离不变。
