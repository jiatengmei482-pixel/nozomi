# ADR 0032：官网下单页与订单页——官网专用的公开接口 `/site/v1`、客人查看订单的链接、限速

- 状态：已采纳（2026-10-26，M3-05）
- 补充 ADR 0023：官网是一个普通的自营渠道，但浏览器不能持有渠道的 API 密钥，所以官网不经 `/sales/v1`，而是经本文的 `/site/v1` 由服务端以「配置里指定的那个 API 客户端」的身份调用**同一套**询价、下单、取消、改单、落地、异议的业务流程。
- 补充 ADR 0026：Stripe 没配置时，官网下单照样建单（待支付，30 分钟后由超时检查自动取消、释放库存），页面写明「付款暂未开放」；不伪造付款成功。`/sales/v1` 的行为不变（仍是 503 `PAYMENT_NOT_CONFIGURED`）。
- 补充 ADR 0005：新增普通配置 `SITE_CLIENT_ID`（不是密钥）。
- 编号说明：迁移 0045、0046（任务指定从 0045 起）。
- 「官网只卖接送机」（待定事项 4）已由 ADR 0034 修订：M3-10 起官网也卖点对点和包车，并加了不依赖外部服务的地址输入辅助。

## 背景

需求：《平台运营端与渠道对接》「渠道与自营的关系」（NOZOMI 官网是一个普通的自营渠道，走同样的比价和结算规则）、「接入方式」（自营：直接调用 `/sales/v1`）、「客人通知」（订单页免登录链接；订单页始终显示客服热线）、「航班信息」（客人在订单页点「我已落地」）、「服务后加收费用」（48 小时内可提异议）；
《用车报价服务平台》「API · 销售端接口」（报价和待支付订单都不返回中标租户）。文末决策：第二轮（付款前不显示中标租户）、第五轮 ③④⑤（客人确认落地优先、取消政策平台统一、事后加收走保存的支付方式）。
roadmap 的验收标准：客人可点「我已落地」。

## 决定

### 为什么不是浏览器直接调 `/sales/v1`

`/sales/v1` 用 Client Credentials 换令牌（ADR 0023）。浏览器里的任何东西客人都看得到：把 `client_secret` 放进前端，等于把渠道的身份交给所有人，任何人都能以官网渠道的名义询价、下单、查这个渠道下的**所有**订单（渠道令牌按渠道授权，不按客人）。所以官网需要一层「按客人授权」的接口，而渠道身份留在服务端。

考虑过的另一种做法是另起一个官网后端（BFF）进程持有密钥、经 HTTP 调 `/sales/v1`：多一个要部署、要监控的进程，多一跳网络，还要在 BFF 里再做一遍客人授权和限速。本项目只有一个 API 进程，直接在里面加一组路由、调同一批 service 更简单，也保证不会出现两份业务逻辑。

### `/site/v1`：官网专用的公开接口

- 只做「客人授权 + 校验 + 限速 + 调 service + 序列化」。询价调 `createSalesQuotes`，下单调 `createSiteOrder`（和 `createSalesOrder` 共用同一个内部流程，只在「没配 Stripe」时不同，见下），取消、退款试算、改单、落地、异议分别调 `cancelForChannel`、`previewCancellation`、`changeForChannel`、`reportGuestLanding`、`disputeExtraCharge`。应答在 `salesOrderJson` 的基础上加时间线和名称，**同样没有中标租户（付款前）、结算价、加价比例**；落地信息里去掉司机到达屏照片的文件编号 `driver_photo_file_id`（照片只给平台和供应商核对，客人既打不开也用不上；定义里是单独的 `SiteOrder` / `SiteOrderLanding`）。
- 官网只卖**接送机**（页面按需求先做接送机）：询价请求是「城市、机场、方向、另一端的坐标、城市当地的用车时间、人数、行李」，币种固定为渠道的结算币种。点对点和包车以后在同一组接口里加。
- 城市、机场列表只列「这个渠道能卖、且有已上架接送机商品」的（城市 / 机场启用、渠道授权范围里的供应商、渠道授权的城市和品类）：列出买不到的城市只会让客人询价后看到「没有可用车型」。

### 官网用哪个渠道：`SITE_CLIENT_ID`

任务建议的是 `SITE_CHANNEL_ID`。改为指定**渠道的一个 API 客户端**（`SITE_CLIENT_ID=nzc_…`，就是运营后台「API 客户端与密钥」里显示的 client_id，公开值，不是密钥）。理由：

1. 询价日志 `quote_logs.api_client_id`、订单的 `order_sales.api_client_id` 都是非空的（ADR 0023 / 0026：每一次询价、每一张单都要追溯到发起它的客户端）；只给渠道编号就要么改约束（失去追溯），要么在代码里随便挑一个客户端（不确定）。
2. 运营后台现有的开关直接管用：**吊销这个客户端或暂停渠道 = 官网立即停止接单**，「最近使用」照样更新。
3. 不需要密钥：服务端不拿 `client_secret` 换令牌（那是给外部调用方的），按 client_id 在库里核对客户端在用、渠道没暂停。运营给官网发客户端时显示的那一次密钥可以不保存。

没配置 `SITE_CLIENT_ID`、客户端不存在或已吊销、渠道暂停：`GET /site/v1/config` 返回 `open: false`，页面显示「暂未开放」；其余接口 503 `SITE_NOT_OPEN`。**已经下了的单照样能查看、取消、点「我已落地」、提异议**（订单接口只要求配置了客户端，不要求渠道在卖）：停止接单不能让客人连自己的订单都看不到。

### 客人怎么看到自己的订单：查看链接

- 下单成功时服务端生成一个查看令牌 `nzo_<32 字节随机数 base64url>`，**库里只存它的 SHA-256**（`site_order_links`，和 M3-02 司机链接同一做法），原文只在这一次应答里给。页面跳到 `/book/order#<令牌>`：`#` 后面不会发给服务器、不进访问日志、不随来源页泄露；前端把它放进 `Authorization: Bearer` 调 `/site/v1/order…`。接口路径里没有订单编号：一个链接只对应一张单，换不到别人的单。
- 链接丢了：用「订单号 + 下单时的邮箱或手机号」找回（`POST /site/v1/orders/lookup`），对上了发一个新的链接。联系方式先做 Unicode NFKC 规范化（全角的数字、字母、`＠`、`＋`、`－`、全角空格转成半角——日文 / 中文输入法常见；页面提交前做同样的转换，后端再做一次，两边同一口径），再比较：邮箱不分大小写、去掉首尾空白；手机号去掉空格、括号、连字符、点后比较。订单号不做全角转换（不分大小写、去首尾空白，格式不对 400；页面同样只认半角）。订单号不存在、联系方式对不上、不是官网的单，一律同一个 404 `ORDER_NOT_FOUND`，不让人借此确认某个订单号存在。
- 有效期：用车时间后 30 天（覆盖事后加收的 24 小时提交期 + 48 小时异议期、投诉的 14 天）；至少到发链接之后 1 天。过期的一律 401 `ORDER_LINK_INVALID`，页面引导用订单号重新找。
- 有效期**每次查看时按订单现在的用车时间算**（`greatest(orders.service_at + 30 天, 发链接时间 + 1 天)`），不看发链接时记下的 `expires_at`：改期把用车时间往后推，已经发出的链接（包括以后邮件里的）跟着顺延；往前提就跟着提前。考虑过「改期时去顺延这张单的所有链接」：要在改单的事务里多改一张表，而且以后任何改用车时间的地方（运营改单、供应商确认改期）都得记得改，漏一处就出现「行程还没开始链接却失效」；按查询时算只有一处。`site_order_links.expires_at` 仍然写（发链接那一刻算出的值，下单 / 找回应答里的 `expires_at` 就是它，供排查），不再作为判断依据。
- 以后通知中心发确认邮件时，邮件里放的就是这个链接（发邮件时另生成一个，不复用页面上那个）。

### 限速（防刷）

和 `/sales/v1` 同一种机制（`sales_rate_limits`、`evaluateFixedWindow`，计数在库里、多实例有效），按**来源地址**计（地址只存哈希）；不占渠道自己的额度（官网的所有客人共用一个渠道，按渠道计会让一个人刷满就挡住所有人）：

| 接口 | 额度 |
| --- | --- |
| 询价 | 每个地址每分钟 30 次 |
| 下单 | 每个地址 10 分钟 10 次 |
| 找回订单 | 每个地址 15 分钟 10 次（成功、失败都算）；**每个订单号**每小时 10 次**失败**（不存在、对不上都算；联系方式对上的那次不受这一层限制，见「已知限制」）；**硬上限**：每个订单号滚动 24 小时失败满 100 次后，对上的也挡。计数先单独提交 |
| 其余（配置、城市、机场、订单页的读写） | 每个地址每分钟 120 次 |

超限 429 `RATE_LIMITED` + `Retry-After`，页面告诉客人等多少秒。

### 输入校验

- 请求体一律 `.strict()`：不认识的字段 400（`channel_id`、`tenant_id`、`currency`、`markup_bp` 都传不进来）。
- 用车时间按城市当地时间 `YYYY-MM-DDTHH:mm` 传，服务端按城市时区换成时刻（不存在的当地时间 400）；人数 1–60，行李 0–60；坐标在合法范围内；机场必须属于这个城市；姓名、电话、邮箱、航班号、地址的规则就是下单的 `orderDetailsIssues`（和 `/sales/v1` 同一份）。
- 下单要带 `Idempotency-Key`（页面每次「提交」生成一个，网络失败重试用同一个），重复提交得到同一张单和一个新的查看链接。

### Stripe 没配置时

- `createSiteOrder`：建单、占库存、写销售端一侧和收款记录（`creating`），**不调收款服务**；应答里 `payment: null`。订单停在待支付，到付款期限由现有的超时检查取消、释放库存（`order-jobs` 对「还没建付款」的单本来就就地取消）。页面写「付款暂未开放：订单已保留到 HH:mm，未付款将自动取消」。
- 为什么还要建单而不是在询价页就挡住：负责人要在测试环境走完「询价 → 下单 → 订单页」，确认下单信息、库存预占、超时释放都对；付款打开后同一张页面只多一个付款区块。
- Stripe 配置后：`GET /site/v1/config` 给出 `publishable_key`（只有它，`sk_` / `whsec_` 永远不下发），下单应答和 `GET /site/v1/order/payment` 给 `client_secret`，页面用 Stripe Elements 确认付款。付款结果只认 Stripe 的通知（ADR 0026），页面付完只显示「正在确认付款」并刷新订单。
- 前端的接入点是 `PaymentDriver` 接口（挂付款表单、确认付款、拆掉）；组件测试用替身。**现在的默认实现不加载 Stripe.js**（挂表单时直接告诉客人「在线付款还在接入中」）：前端有一条守则——不加载任何站外脚本、站外地址只登记在 `lib/external-links.ts`（`styles.edge.test.ts`），放开它属于安全策略的改动，和 Stripe 上线一起做。**上线时要做**（新任务）：写 Stripe Elements 的实现换掉默认值；内容安全策略放行 `https://js.stripe.com`（script-src、frame-src）、`https://api.stripe.com`（connect-src）、`https://hooks.stripe.com`（frame-src，3DS），并相应调整那条守则；用测试卡在测试环境走一遍（ADR 0026「拿到 Stripe 测试密钥后的验证步骤」）。

### 表（迁移 0045、0046）

| 表 | 层级 | 内容 | 平台 | 租户 |
| --- | --- | --- | --- | --- |
| `site_lookup_failures`（0046） | 平台 | 找回失败的记录：订单号的 SHA-256、失败时间（一次一行，算滚动 24 小时；超过 24 小时的写入时顺手删，每个订单号最多留 100 行） | 读、追加、删过期行 | 无 |
| `site_order_links` | 平台 | 订单、令牌的 SHA-256（唯一）、怎么来的（下单 / 找回）、生成时间、发链接时算出的有效期（只追加；是否有效按订单现在的用车时间判断，见上） | 读、追加 | 无 |

### 页面（`apps/web`，`/book` 路由组）

面向客人的独立外观：不用后台的菜单壳，单栏、内容最宽 `layout-reading-max-width`、控件用大尺寸，主操作按钮吸在屏幕底部（留出 `safe-area-inset-bottom`），亮暗两套令牌。

1. `/book`：询价（城市、接机 / 送机、机场、地址文字 + 坐标、当地日期时间、人数、行李）→ 各车型组的对外价、免费等待、取消政策摘要。不显示供应商、结算价、加价比例（接口里本来就没有）。
2. `/book/checkout`：乘客、航班号（接机必填）、地址、即时通讯、备注、同意保存支付方式 → 提交。
3. `/book/order#<令牌>`：状态时间线、行程、付款、司机和车辆（派车后）、「我已落地」（接机、付款后、计划到达前 3 小时起；点之前页面内确认，点过后显示确认的时间）、取消（先显示按政策退多少，页面内确认）、改单（M3-03 允许的字段）、事后加收和异议。没有令牌时显示「用订单号查找」。
4. 展示城市、机场名称的页面带 GeoNames、OurAirports 署名。

## 已知限制

### 找回按订单号限速：只记失败（已采用方案 A，2026-10-26）

原来「每个订单号每小时 10 次」成功失败都算：知道某个订单号的人（截图、转发、同行的人）用错的联系方式试满 10 次，这一小时里真客人用正确的邮箱 / 手机号也会被 429 挡住。考虑过的方案：

| 方案 | 做法 | 结论 |
| --- | --- | --- |
| A | 订单号这一层只记失败的尝试，联系方式对上的那次不受这一层限制（地址那一层照旧都计数） | **采用** |
| B | 订单号额度按「订单号 + 联系方式的哈希」计，再加一个更宽的总额度 | 规则更复杂，效果和 A 相近 |
| C | 超过额度后要求人机验证（如 Turnstile） | 要接外部服务、改内容安全策略、多一个密钥；以后需要时再加 |
| D | 确认邮件 / 短信里直接带链接，找回只做兜底 | 依赖通知中心任务，和 A 不冲突 |

做法：先按订单号找单、核对联系方式；对上了直接发链接，不碰订单号的计数。没对上（包括订单号不存在、不是官网的单）才记一次订单号的失败——计数单独提交，超过额度回 429，否则回 404。不存在和对不上走的是同一条路（同样先查、同样记一次失败、同样的 404 / 429），所以照旧不能借应答或限速区分订单号存不存在。

**加硬上限（2026-10-26）**：只用 A 的话，订单号额度满了以后猜错回 429、猜对回 200，这一层就不再限制「猜联系方式的总次数」，只剩每个地址 15 分钟 10 次。所以再加一层：

- 每个订单号**滚动 24 小时**里失败满 100 次后，联系方式对上的也回同一个 429（`RATE_LIMITED`），直到最早的那些失败滑出 24 小时、剩下的少于 100 次。滚动窗口用 domain 的 `evaluateRollingWindow` 判断，失败一次一行记在 `site_lookup_failures`（固定窗口的计数器做不到滚动：窗口交界处能连续猜 200 次）。上限满了以后不再记，所以每个订单号最多 100 行。
- 被挡时不论联系方式对没对上、订单号存不存在，正文和 `Retry-After` 都一样：都按「这一次如果算失败」算，等待时间取每小时那一层和硬上限中较长的。
- 正好记满 100 次的那一次写一条服务日志 `site_lookup_ceiling_reached`（带订单编号，订单号不存在时为空；只带订单号哈希的前 16 位，不带订单号原文和联系方式），供运营留意是否有人在猜。还没接进运营后台的告警，告警以后由通知中心任务接。
- 页面：找回被 429 时提示「尝试次数过多，请 N 小时 / 分钟后再试，或联系客服」。客服热线还没登记（待定事项 6），登记后在这里显示号码。
- 代价：被别人刷满 100 次的订单号，真客人最长要等 24 小时才能自己找回，这段时间只能找客服。这是有意的取舍：不加上限，猜测次数就没有上限。人机验证（方案 C）可以把等待去掉，需要时再做。
