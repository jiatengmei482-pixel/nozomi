# ADR 0102：区域分类（平台共享 / 供应商独立）与三层区域重叠清理

- 状态：**已采纳（2026-11-18，业主决定「直接清理」，监工在 #288 转达）**。
- 工作项：区域分类、停用 / 归档核对、测试站清理与回放对比（拆分见第五节）。
- 依据：业主 2026-11-18 的说明（#288 监工评论）；ADR 0083（区域共享库）、ADR 0093（包车三层区域）、ADR 0075（区域用途）。

## 一、背景

1. 区域创建后不能删除（只能停用），所以测试站有重复、重叠的旧区域。三层迁移试跑报告里有 32 处重叠。
2. 价格表导入时建了一批名称带「·通用」的区域（测试站前 300 个区域里有 121 个，业务类型都是「通用」）。业主说明：这类多供应商共用的「·通用」区域和供应商自己画的区域**不算重叠**，必须分开。
3. 现在的重叠检查（区域页提示、上架检查、包车三层保存校验）不分这两类，把它们之间的覆盖都当成重叠。

## 二、决定：区域分两类

- `areas.sharing`（迁移 0630，只加列，默认 `own`）：
  - `shared` = **平台共享**：「·通用」这类多家供应商可用的区域；
  - `own` = **供应商独立**：供应商自己画的区域。
- 业主 2026-11-18【需业主决定】按推荐 A：分类是区域上的明确字段，不靠名称判断（改个名分类不该变）。第一次由测试站清理脚本把名称带「·通用」的标成共享；之后由平台运营修改（另开任务）。
- 区域接口（列表、详情、区域地图）多一项 `sharing`，供应商后台区域列表多一列「分类」。

## 三、决定：重叠只在同一分类里算

- 重叠检查只在**同一分类、同一供应商、同一层**里报。区域都属于各自的供应商，各检查本来就按商品（同一供应商）、按层分开算。
- 实现：`@nozomi/domain` 的重叠计算（`findAreaOverlaps`，以及在它之上的 `charterLayerOverlaps`）判断两个区域是否「互相竞争」时，除业务类型外再要求分类相同。区域页提示、上架检查、包车三层保存校验、三层迁移报告共用这一处，口径一致。
- 共享和独立重叠**不报错**。

## 四、决定：报价时供应商独立优先

- 同一层里一个点同时落在平台共享和供应商独立的区域：只算供应商独立的，共享的不算。点只落在共享区域里时照常按共享区域报价。
- 「落在」包括营运区和禁行区：独立区域的禁行区盖住这个点时不报（共享区域的营运区不能把它救回来）；共享区域的禁行区挡不住独立区域。
- 实现：`locateInAreas`（报价第 4 步判断点落在哪些区域）。调用方每次只给同一层的区域（①商品区域、②行程加价、③上下车加价、运营范围各判一次），所以优先规则按层生效，不会跨层。
- 没有标记共享的数据（正式站、迁移刚执行时）行为和以前完全一样。

## 五、实施拆分

1. 本篇 + 分类字段 + 重叠口径 + 报价优先（本 PR）。
2. 停用 / 归档：核对并补齐「停用的区域不参与报价、不参与重叠检查」；已被订单引用的区域照常保留，订单照常显示；运营后台按分类、状态筛选。
3. 测试站清理脚本（和三层迁移同样的做法：先试跑、再执行，业主设一次环境变量）：
   - 清理前把每个区域的形状、分类、状态和全部关联（商品、各层、价格行）存进备份表；
   - 标出共享区域；
   - 停用重复的旧区域；
   - 剩下的真重叠用「从本区域减去另一个」切掉。
4. 清理前后各跑一次询价回放（1,629 条），逐条列出价格变化。
5. 上架检查的重叠数为 0 后在 #288 回报。只动测试站；正式站等业主看过测试站结果再定。
