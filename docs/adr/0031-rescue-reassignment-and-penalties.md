# ADR 0031：救援改派与违约金——4 种触发、救援单、改派后订单转给救援供应商、违约金和救援差价记账、不可抗力

- 状态：已采纳（2026-10-26，M3-04）
- 补充 ADR 0026 / 0027：订单状态加「已转给救援供应商」`rescued`；`rescue_pending` 只去 `rescued` 或 `cancelled`（原来写的「救援 → 已确认 / 已派车」由本文取代，见「改派」）。
- 补充 ADR 0027：发出 `rescue.offered`、`order.rescued_away`（M3-02 定下了名字）；订单定时任务多做救援的事；平台角色可以吊销司机链接（只改吊销的两列）。
- 补充 ADR 0029：救援改派中的单取消时供应商应得为 0；无人可接按「供应商原因」全额退款不用复核。
- 补充 ADR 0023：双人复核登记一类 `rescue.manual_assign`。
- 用到 ADR 0020（报价引擎：按原报价条件找候选、算各自的结算价）。
- 编号说明：ADR 0031；迁移 0035（0033、0034 留给正在开发的别的分支）。

## 背景

需求：《平台运营端与渠道对接》「履约保障与服务标准」（4 种触发情形与违约金阶梯、救援差价、不可抗力、救援流程 5 步、计入评分）、「订单中心 · 异常队列」（超时未派车：用车前 6 小时仍未派车自动进入救援改派；司机未到达：到点 15 分钟仍未到达且联系不上，启动救援改派或请客人自行打车凭票报销）、「人工介入能力」（救援改派只在 4 种情形下可用，客人价格不变，差价和违约金从原租户账单扣除）、「财务结算 · 一单的账务分录」（履约失败：应付租户 − 结算价 − 违约金）、「第五轮新增接口」（`:rescue`、`:assign-rescue`（双人复核）、`:force-majeure`）。
文末决策：第五轮 ①（平时不改派；4 种情形启动救援改派，客人价格不变，差价和违约金 0 / 30% / 100% 由原租户承担）。
roadmap 的验收标准：4 种触发情形；违约金阶梯 0 / 30% / 100%。

### 4 种触发情形

| 情形 | 谁、怎么识别 | 违约金（基数：原结算价） |
| --- | --- | --- |
| 供应商声明无法履约 | 供应商后台「声明无法履约」或接口 `POST /tenant/v1/orders/{id}/declare-unable`（`order.dispatch`，**原因必填**）；运营也可以替它登记（供应商打电话来） | 用车前 ≥ 24 小时 0；2–24 小时 30%；< 2 小时 100% |
| 用车前 6 小时仍未派车 | **系统自动**：订单定时任务每分钟扫「已确认、还没派车、过了 max(用车前 6 小时, 派车截止时间)」的单 | 100% |
| 司机未到 | 到点 15 分钟（含那一刻）仍未「已到达」：定时任务记下提醒（`arrival_overdue_at`）、客人可以在订单页报告（`POST /sales/v1/orders/{id}/driver-missing`），都进运营后台的**救援队列**；运营联系司机、联系不上后发起（`driver_no_show`）。不让系统自动触发：「联系不上」要人判断 | 100% |
| 供应商被暂停 | 运营对暂停中的供应商**批量发起**（`POST /platform/v1/tenants/{id}/rescue`），名下已确认 / 已派车 / 司机已出发、用车时间还没到的单逐张触发 | 按触发时距用车时间套用前 3 行（0 / 30% / 100%） |

- 每次触发：订单进入「救援改派中」、**原来的司机链接立即作废**、没有结论的改单作废（补收的差价退回）、记违约金（应扣款项）、订单流水（`RESCUE_TRIGGERED`，带情形和比例）、给原供应商推 `order.status_changed`、审计（供应商 / 运营 / 系统）、服务日志 `order.rescue_triggered`（警告级别，通知运营；邮件 / LINE 在通知中心任务）。
- **原供应商不能再操作这一单**：派车、回传履约、改期确认都按状态拒绝（409 `ORDER_STATE_INVALID`）；数据库里租户角色本来就不能把状态改出 `rescue_pending`（ADR 0027 的行级触发器），也不能改新加的几列（语句级触发器）。可以查看。
- 阶梯按**毫秒**：正好 24 小时算 0，少 1 毫秒 30%；正好 2 小时算 30%，少 1 毫秒 100%（和 ADR 0029 的取消阶梯同一个口径）。
- 「到点」：用车时间；接机的航班晚点、已经取定了比用车时间晚的实际落地时间时，从落地时间算（免费等待也从落地起算，ADR 0027）。
- 付款时离用车已不足 6 小时的单，派车截止时间是付款后 2 小时（ADR 0027）：未派车的自动触发从截止时间起算，不会一付款就触发。
- **并发只建一条**：触发先锁订单再看状态和有没有没结论的救援；`order_rescues_open_key`（一张单只能有一条没结论的）兜底。供应商声明、运营登记、定时任务同时到，只有一个成功（集成测试覆盖）。
- 「暂停」本身不自动发起：ADR 0028（M4-01）定了暂停后已有订单继续履约，需求写的也是「运营批量发起」。M4-01 合并后如果某种暂停原因要自动发起，在状态变化的地方调 `rescueSuspendedTenant`（同一个函数）。

### 候选和救援单

- **按原报价条件重新比价**：下单用的报价快照里的请求，换成这一单现在的用车时间、人数行李，只比这一单的车型组；走 `previewPlatformQuote`（同一个渠道的加价规则和授权范围、现取现算；里程 + 时长的用下单时的路线预估）。所以候选天然是「同城、同品类（接送机同一个接送点）、能接这个车型组、没被暂停、报得出价」，排序就是中标排序（价差 3% 内评分高者，ADR 0020）。
- 排除这一单以前和现在的供应商、这次救援已经发过的。报不出价的列在 `excluded` 里（报价引擎的原因代码），运营看得到为什么没有某一家（比如离用车太近，提前预订时长不够——没开加急的供应商这时报不出，见待定事项 3）。
- 结算价是候选**这一次的报价**（需求「结算价为其当前报价」），不是原结算价。
- **救援单是唯一要供应商主动接的订单**：运营在救援队列选一家发出（不指定就是第一名），期限 15 分钟、发出时离用车不足 2 小时的 5 分钟（正好 2 小时仍是 15 分钟）；拒绝、超时就**自动顺延**给剩下的第一名（重新比价）；一家都没有了 → 「候选都不接」，服务日志 `order.rescue_exhausted`。同一时刻只有一张待接的（唯一索引）。
- 救援单推 `rescue.offered`：只有行程（没有乘客的姓名、电话、邮箱和航班号）、它的结算价和期限。接单前供应商后台也只看得到这些；接了单在订单里看乘客。
- 救援单的对外价、加价比例、汇率、名次放在平台表 `order_rescue_quotes`，不在救援单那张租户表里（规则 4 在数据库层的保证）。

### 改派（订单转给救援供应商）

订单表的主键是 `(tenant_id, id)`，订单的子表（流水、派车记录、照片、司机链接、推送……）都带着 `tenant_id` 外键指向它。改派时：

1. 原供应商的那一行改成 `rescued`（终态，记 `rescued_at`），它的流水、派车记录、照片都留在原地——原供应商还看得到自己那一段，救援供应商看不到；
2. 照着它给救援供应商**另起一行，同一个订单编号、同一个订单号**：行程、乘客、即时通讯、备注、免费等待（客人下单时的承诺）、取消阶梯（下单时的平台政策）、客人确认的落地时间照抄；商品、结算价和明细用救援供应商的；从「已确认」开始，确认时间 = 改派时间（派车截止时间按它算，但至少留 30 分钟——到点之后才改派的单按普通规则截止时间已经过了，`rescuedDispatchDeadline`）；派车、履约、司机填的落地时间从头开始；版本号接着原来的往上加；
3. `order_sales.supplier_tenant_id` 换成救援供应商——客人付的钱（`sell_minor`）不变；
4. 库存：原供应商释放已售，救援供应商的商品是限量的就占一个（订满了接不了，409 `RESCUE_SOLD_OUT`）。

「现在的」那一行：没转出的那一行。`orders_current_key`（`id` 唯一，不含 `rescued`）和订单号的唯一索引同样排除 `rescued`；平台侧按编号找订单（`findOrderForPlatform`）只取现在的那一行，所以渠道、运营后台、取消、改单、加收、退款都自然作用在救援供应商那一行上；原供应商的请求按「令牌里的租户 + 编号」找到的是它自己转出的那一行（状态 `rescued`），什么都做不了。
推给供应商的 Webhook 按「供应商 + 编号」取它自己的那一行（原供应商收到的 `order.rescued_away` 里是它那一行）。

为什么不改 `tenant_id`：子表的外键会跟着断，搬过去又会把原供应商的司机、照片、联系记录交给救援供应商看。为什么不建一张新编号的订单：渠道、客人手里的订单编号和订单号都要变，客人就不是「无感」了。

推送：原供应商 `order.rescued_away`；救援供应商 `order.confirmed`（`data.rescue = true`，和普通新订单同一个处理入口）。流水：原供应商那一行 `rescue_pending → rescued`（`RESCUED`），救援供应商那一行 `null → confirmed`（`RESCUE_ASSIGNED`）；都不写对方是谁。

### 违约金和救援差价（只记账）

- 应扣款项 `tenant_deductions`（租户表，供应商只读自己的）：触发时记违约金（比例为 0 也记一条，看得到「用车前 ≥ 24 小时声明，0」）；改派成功时记救援差价。现在**只记账**，实际扣款在 M5 结算时从当期或下一期账单里扣（需求「记入原租户下一期账单」），M5 加「已扣」状态和账单关联。
- 违约金 = 原结算价 × 比例，最小单位四舍五入（`portionBasisPoints`）。
- **救援差价 = 救援结算价 − 原结算价（按快照汇率换算，为负时记 0）**。两家结算币种不同：救援结算价按**救援报价快照**的汇率换到客人支付的币种，再按**原订单快照**的汇率换回原结算币种——两边各用各自报价时记下的汇率，不用现在的汇率；全程精确分数，只在最后四舍五入一次。同币种直接相减。救援发生过两次（救援供应商也没履约）时，第二次的「原结算价」和汇率是第一次救援记下的。
- 「原租户承担」= 原供应商被扣差价；平台按救援供应商的结算价付给救援供应商，客人付的不变——平台先垫付（需求「由平台先垫付，记入原租户下一期账单」）。
- 救援中取消（无人可接全额退款、客人自己取消）：违约金照记（原供应商没有履约）；原供应商的「取消应得」为 0（需求「履约失败：应付租户 − 结算价 − 违约金」），客人被扣的取消费（客人自己取消时）全归平台。
- 司机未到的「+ 报销金额」：客人凭票报销替代交通在投诉 / 赔付任务（工单）里做，到时记一条报销的应扣款项。

### 不可抗力

- 大雪封路、机场关闭、政府管制：运营认定（`rescue.manage`，`POST …/rescue/force-majeure`），**单人认定、说明必填、写审计**；这一单最近一次救援的应扣款项（违约金、救援差价）全部免除（`waived`，免除原因就是说明），之后才记的差价也直接免除。供应商看得到「已免除」和说明。
- 为什么单人：需求的「敏感操作双人复核」清单（改加价、改结算条款、付款给租户、人工退款超过阈值、停用租户或渠道）里没有它，第五轮新增接口里只给 `:assign-rescue` 标了「双人复核」，`:force-majeure` 没标；需求原文是「经运营确认」。它影响的是向供应商扣不扣钱（对供应商有利），不让客人多付或平台多付出去。
- 「客人全额退款」走取消（原因选 `FORCE_MAJEURE`），多退了钱的照 ADR 0029 复核——两件事分开：认定不可抗力不自动退款，退款不自动免违约金。

### 人工指定（双人复核）

- 「全部候选都不接，运营可人工指定租户（双人复核）」：运营（`rescue.manage`）发起，选供应商、它的一个商品（同城同品类、同一个接送点、有这一单的车型组）、**电话谈好的结算价**和说明；另一位有 `rescue.review`（运营、超级管理员）的同事批准时才改派（`rescue.manual_assign`，发起人不能批）。
- 结算价由运营填：人工指定多半就是因为它报不出价（离用车太近、库存设满了）。明细只有基础价一项。结算币种和客人支付币种不同时，**发起时**取一次汇率记进复核内容，批准时按它换算救援差价（快照汇率）。
- 还有待接的救援单时不能发起；批准时还有待接的（复核期间又发了一张）一并收回。复核期间订单被接走或取消 → `APPROVAL_STALE`。

### 救援中的取消

`cancelPaidOrderInTx` 遇到 `rescue_pending`：救援记为「已取消订单」、待接的救援单收回（`withdrawn`）、供应商应得 0。按「供应商原因」（`SUPPLIER_FAULT`）的全额退款不用复核（需求定好的结果，不是人工多退）；别的原因照 ADR 0029。

### 运营后台、供应商后台

- 运营后台「救援」队列：没有结论的救援（待处理、救援单待接、候选都不接，按用车时间）；司机未到的提醒；暂停中还有未来订单的供应商。每一条可以看候选和差价、发救援单、人工指定、认定不可抗力、取消退款。订单详情显示全部救援记录、救援单、违约金和差价。
- 供应商后台：订单详情「声明无法履约」（显示按现在的时间会落在哪一档违约金）；「救援单」页（待接的、接 / 拒、倒计时）；「违约金与扣款」页（自己的应扣款项，只看自己的，没有对外价、加价比例、救援供应商是谁）；订单详情里原供应商看到触发和违约金，救援供应商只看到「这是救援单」。

## 待定事项（需求没写清；先按推荐做了）

| # | 问题 | 选的方案 | 理由 |

| 1 | 救援单是按排序自动依次发，还是运营选一家 | 运营选第一家（默认第一名），之后拒绝 / 超时自动顺延 | 需求写「依次向候选发救援单」；运营先看一眼候选和差价再发，能避开明显不合适的（比如差价很大）；之后不用人盯着 |
| 2 | 不可抗力单人还是双人 | 单人认定、说明必填、审计 | 见「不可抗力」 |
| 3 | 离用车很近时（比如 < 24 小时），没开加急的供应商报不出价，候选很少 | 照报价引擎的规则（「结算价为其当前报价」）；报不出的列出原因，运营可以人工指定（谈好价、双人复核） | 不绕过供应商自己设的提前预订时长；真要接的供应商可以在电话里答应，走人工指定 |
| 4 | 救援供应商的免费等待按谁的 | 按原订单（客人下单时看到的） | 客人「无感」；救援单上写着这一单的行程，接单的供应商接受这个条件 |
| 5 | 救援中原供应商取消费的分成 | 0（客人被扣的取消费归平台） | 需求「履约失败：应付租户 − 结算价 − 违约金」 |
| 6 | 候选只看同一个车型组还是也看更高级的 | 同一个车型组 | 报价是按车型组比的；升级车型要另算价，第一版不做 |
| 7 | 司机未到要不要系统自动触发 | 不自动：系统记提醒、客人可以报告，由运营判定「联系不上」后触发 | 需求「到点 15 分钟仍未到达**且联系不上**」，后半句要人判断；司机可能只是忘了点「已到达」 |
| 8 | 救援发生后能不能撤销（触发错了） | 不能；可以取消订单全额退款，或照常改派 | 撤销要把原供应商的司机链接、改单都恢复，容易出错；需求没有这一步 |

## 本期不做

| 内容 | 去向 |
| --- | --- |
| 应扣款项实际扣款（从账单里扣）、账务分录 | M5 结算 |
| 司机未到的凭票报销（上限对外价 1.5 倍）及报销的应扣款项 | 投诉 / 赔付任务（工单） |
| 通知运营、通知客人新的司机（邮件 / LINE） | 通知中心任务（现在：服务日志 + 救援队列；客人在订单页和渠道接口看到新的司机） |
| 推给渠道的 `order.rescue_started`、`order.rescued` | 接入第一个外部分销商时（自营官网用订单接口） |
| 暂停的某些原因自动发起救援 | 需要时在 ADR 0028 的 `applyTenantChange` 里调 `rescueSuspendedTenant`（现在按需求由运营批量发起） |

## 补充：接上 M4-01（2026-10-26，合并 ADR 0028 之后）

- **计入评分**：改派成功、或救援中订单取消时，在同一个事务里给原供应商记一次履约失败（`recordPerformanceEvent`，`kind = failure`；情形是司机未到的记 `driver_no_show`——30 天内 2 次观察、3 次暂停的依据，其余记 `rescue`）。同一单同一个供应商只记一次。只触发、还没有结论的不记。
- **「被暂停或解约」按 ADR 0028 的状态机认**：`suspended`（不管有几个暂停原因）、`terminated`（`tenantOutOfService`）。观察期只是试运营 / 正式身上的标记，不算暂停，不能按这种情形救援。救援队列「暂停中还有未来订单」同样包括已清退的。
- **能接救援单、能被人工指定的**：和参加比价同一个条件（`tenantBids`：试运营、正式，观察期照样可以），`tenantCanRescue`；候选本来就由报价引擎按这个条件和试运营每日上限筛过，接单、人工指定时再核对一次。
- 人工暂停现在走双人复核（ADR 0028）；批准生效后运营再在救援队列批量发起。
