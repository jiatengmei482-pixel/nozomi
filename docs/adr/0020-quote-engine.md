## 背景

M2-01 做报价引擎。需求见《用车报价服务平台》「报价引擎」（13 步、计价公式、取整规则、时区、性能）、文末各轮决策（轮次大的优先），
《平台运营端与渠道对接》的「加价规则」「中标排序（修正版）」「汇率缓冲与加价下限」。roadmap 的验收标准：与需求文档的计价公式逐项对应的单元测试。

路线预估（M2-02）、汇率（M2-03）、渠道和加价规则（M2-04）、评分（M4-01）、订单（M3-01）都还没有。本任务把引擎做完，这几样各留一个接口。

## 决定

### 分层

| 层 | 在哪里 | 做什么 |
| --- | --- | --- |
| 纯计算 | `packages/domain/src/quote.ts` | 一个商品对一次用车的结算价和明细（`quoteProduct`）、对外价（`sellPrice`）、选中标（`rankCandidates`）、多个供应商合起来比并生成快照（`compareQuotes`）。不碰数据库和网络 |
| 取数 | `apps/api/src/repos/quotes.ts` | 找候选商品，把报价要看的事实一批取回（每类数据一条查询） |
| 业务流程 | `apps/api/src/services/quotes.ts` | 核对请求、取数、估路线、调 domain、取加价 / 汇率 / 评分 |
| 接口 | `apps/api/src/routes/quotes.ts` | 平台侧、租户侧两个试算接口 |

### 报价的步骤（和需求文档的 13 步对应）

| 文档 | 做法 |
| --- | --- |
| 1 入参 | 品类、城市、起点 / 终点坐标、用车时间（城市当地时间 `YYYY-MM-DDTHH:mm`）、人数、行李数、方向、套餐时长、附加服务、司机语言、可选的车型组。接送机机场那一端不用给坐标（用接送点的）。`channel_id` 等渠道做了再加 |
| 2 找商品 | 同城市、同品类、已上架（接送机还要同一个接送点）；城市、接送点要是启用中的。供应商被暂停、子品牌停用的商品在结果里给出原因，不参加比价 |
| 3 服务规则 | `checkBookingWindow`：下单有效期（看下单那天）→ 服务时间 → 提前预订时长；不足时开了加急取最小的够用的一档 |
| 4 区域校验 | 接送机只看非机场一端，点对点两端都看，包车只看上车点。每个要看的点都要落在某个区域的营运区里且不在**那个区域**的禁行区里。一个点落在几个区域、或点对点起终点在不同区域：这些区域的价都算，取结算价最低的；一样低取商品里排在前面的区域 |
| 5 命中价格 | `tripPrice`：区域 × 车型组 × 方向或套餐，启用且用车日期在生效期内，具体方向优先于接送通用。人数或行李数超过车型组合的不报 |
| 6 基础价 | 三个公式（ADR 0018）。里程 + 时长的用路线预估；取不到预估就报不出（`ROUTE_UNAVAILABLE`），一口价和包车套餐不受影响。包车报价时 H = 套餐时长、不看路线预估 |
| 7 调价 | 匹配的规则按顺序链式执行（ADR 0018） |
| 8 加急、夜间、附加服务 | 各自独立，不参与调价，见下一节 |
| 9 库存 | 限量时当日剩余 > 0（`hasInventory`）；走加急的另查每日加急库存 |
| 10 选中标 | `rankCandidates`，见「比价和中标」 |
| 11 对外价 | `sellPrice`，见「对外价」 |
| 12 快照 | `QuoteSnapshot`，见「报价快照」 |
| 13 下单转单 | 订单任务（M3-01） |

### 结算价和明细

`P_total = Adjust(P_base) + F_urgent + F_night + ΣF_addon`。全程精确分数，**只在最后按子品牌的取整单位取整一次**——不是「调价后先取整、再加各项费用」。
明细各项（基础价、调价、加急、夜间、附加服务、司机语言）之和恒等于结算价，取整的尾差计入调价项。
夜间费（按小时）、附加服务（按时长）按比例算出来可以带小数：结算价用它们的精确值，明细里显示的是各自四舍五入到最小货币单位的数（附加服务另给每项和合计的精确值 `amount_exact`、`exact.addons`）。

调价后的精确值不大于 0 的不报（`PRICE_NOT_POSITIVE`）——ADR 0018「调完不大于 0 的不报价」，不靠加急、夜间、附加服务把它补成正数；
调价后精确值大于 0、只是单独取整会变成 0 的照常往下算，只看最后合在一起取整的结算价，它不大于 0 时同样是 `PRICE_NOT_POSITIVE`。

价格日历（ADR 0018）显示的是「调价后单独取整」的数；有加急、夜间、附加服务时，报价的结算价是合在一起取整的，两者可以差不到一个取整单位。这是需求文档「只在最后取整」的直接结果。

需求文档没写细、这里定下来的：

- **夜间费**。夜间时段是「开始含、结束不含」（22:00–06:00，06:00 整不算夜间）。按次：用车开始的时刻在夜间时段里收一次。按小时：金额 × 与夜间时段重叠的分钟数 ÷ 60，不足一小时按比例；用车多长——包车是套餐时长，其他品类是路线预估的时长；取不到时长的（一口价商品、没有路线预估）按一次算，开始时刻在夜间时段里收一小时的钱。
- **附加服务**。请求里要的东西商品不提供（没选、关着、被平台停用、不适用这个品类）→ 整个商品不报（`ADDON_NOT_OFFERED`），不是悄悄不带。计费：按次收一次；按个 = 单价 × 个数（首个免费时减一个）；按人 = 单价 × 人数；按时长 = 单价 × 小时数（时长的取法同夜间费，取不到按一小时）。司机语言同理：不提供就不报（`DRIVER_LANGUAGE_NOT_OFFERED`），提供就加它的单价。
- **每日加急库存**的已用量要有了订单才数得出来：现在按 0 算（`QuoteMoment.urgentUsed` 留着）。
- **免费等待**不影响价格，带在明细里：这个方向用哪一项、供应商设的值、平台规定的最小值。国际线 90 / 国内线 60 的区分要知道航班，报价入参里没有，留给订单。
- **区域里的禁行区**只管它所在的那个区域（ADR 0015）：点落在 A 区域的禁行区里、同时在 B 区域的营运区里，B 可以接。所有区域都接不了时，只要有一个区域说它在禁行区里，原因就是 `IN_FORBIDDEN_AREA`，否则是 `OUT_OF_SERVICE_AREA`。
- **点对点有一端落在某个区域的禁行区里**：这个区域不参与这一单的报价，即使另一端在它的营运区里（按推荐选项定的）。例：起点只在 A 的营运区、终点在 A 的禁行区里又在 C 的营运区里——只用 C 的价，不用 A 的。
  这样排除之后一个区域都不剩，原因是 `IN_FORBIDDEN_AREA`。
- **请求里同一个车型组写了几次**只算一次：一个车型组只出一个价。

### 报不出价的原因

每个原因一个代码（`QUOTE_REFUSALS`），接口另给中文说明。商品层面的（对所有车型组都一样）：
`PRODUCT_NOT_PUBLISHED`、`TENANT_SUSPENDED`、`BRAND_DISABLED`、`SERVICE_RULES_INCOMPLETE`、`INVALID_SERVICE_TIME`、`OUTSIDE_SALE_PERIOD`、`OUTSIDE_SERVICE_TIME`、`SERVICE_TIME_PASSED`、
`LEAD_TIME_TOO_SHORT`、`URGENT_SOLD_OUT`、`OUT_OF_SERVICE_AREA`、`IN_FORBIDDEN_AREA`、`ADDON_NOT_OFFERED`、`DRIVER_LANGUAGE_NOT_OFFERED`、`SOLD_OUT`。
车型组层面的：`VEHICLE_GROUP_NOT_OFFERED`、`VEHICLE_GROUP_DISABLED`、`CAPACITY_EXCEEDED`、`NO_PRICE_RULE`、`PRICE_NOT_IN_EFFECT`、`PRICE_RULE_DISABLED`、`ROUTE_UNAVAILABLE`、`PRICE_NOT_POSITIVE`、`PRICE_OVER_LIMIT`。
比价时才有的：`FX_RATE_UNAVAILABLE`、`SELL_PRICE_OVER_LIMIT`。

需求文档的三个错误码 `OUT_OF_SERVICE_AREA`、`LEAD_TIME_TOO_SHORT`、`SOLD_OUT` 原样用。几条同时不满足时报先查到的那一条（顺序同上面的步骤）；一个车型组在几个区域各有各的原因时，报离「报得出」最近的那个。

### 对外价

`对外价 = 结算价 × 汇率 × (1 + 汇率缓冲) × (1 + 加价比例)`，精确分数，最后按客人支付币种的小数位四舍五入一次。

- 客人支付币种和结算币种相同：汇率 1、缓冲 0。不同：要有汇率，缓冲 1.5%（取配置 `FX_BUFFER_PERCENT`，默认 1.5）；没有汇率就报不出。
- 汇率用十进制字符串传进来、换成精确分数，不经过浮点数；最小货币单位之间的换算按两种币种的小数位挪。
  `packages/domain/src/fx.ts`（M0 留下的）的汇率是浮点数、`convertMinor` 走浮点取整，报价引擎不用它；汇率中心（M2-03）做的时候把它改成同一种精确写法或删掉。
- 汇率超过 48 小时没更新就不用（「汇率中心」：超过 48 小时未更新则暂停跨币种报价）：`compareQuotes` 自己按汇率的取数时间再查一遍（`fxQuoteUsable`，正好 48 小时还能用），
  过期的当作没有汇率，原因同样是 `FX_RATE_UNAVAILABLE`。汇率中心自己也该停掉过期的汇率、并告警；引擎这一道保证不管汇率从哪里来，过期的都进不了报价。
  取数时间比现在晚 5 分钟以内（两台机器的钟差）照常用；晚得更多的也不用——那是数据源或时钟出了错，不拦的话一个写成明年的取数时间会让汇率永远不过期。
- 加价比例不得低于下限（默认 10%）：给的比下限低就按下限算，快照里记实际用的那个。
- 渠道的「对外价取整规则」「最低毛利金额」是渠道配置（M2-04），现在没有。

### 比价和中标（第五轮决策 ②）

1. 每个报价算出对外价，换到客人支付的币种；
2. 同一个租户在同一个车型组有几个报价（几个商品）时只留排序价最低的——每个车型组每个租户只出一个价；
3. 排序价 R = 对外价，观察期租户 × 1.05（只用于比较）；最低的 R 是基准；
4. R ≤ 基准 × (1 + δ) 的进同价区间，δ 默认 3%（渠道可配 0–5%）；恰好等于也算在里面，用精确值比，不取整；
5. 区间内：评分高者 → 已完成订单数多者 → 排序价低者中标；区间外的按排序价排在后面；
6. 客人支付的是中标租户自己的对外价。

评分是百分之一分的整数；完成不足 20 单、或还没有评分的用默认 4.5。**全都一样时**（评分、单量、排序价都相同）按「租户编号、商品编号」的字典序定先后——保证同一次询价不管怎么取数结果都一样；这个顺序没有业务含义。

包车「每个车型组再按套餐」：一次询价只带一个套餐时长，所以结果里每个车型组一组。

### 报价快照

`QuoteSnapshot`（domain）：创建时间、有效期（30 分钟，到点的那一刻失效）、原始请求、客人支付的币种、价格带；中标的租户 / 商品 / **商品版本号** / 用的区域和价格规则 / 完整的结算价明细 / 加价比例 / 汇率和缓冲 / 对外价；
以及**全部候选**的排序依据（结算价、对外价、加价比例、评分、单量、是否观察期、排序价、是否在区间里、名次）——《平台运营端》「自营中立」要求每次报价保存全部候选的排序依据。

- 「规则版本」用商品的版本号：商品下面任何规则（服务规则、价格、调价、库存模式）变了都会加一（ADR 0016 / 0018 / 0019）。快照里另有结算价的完整明细，下单时不重新算，直接以快照为准；对账时拿明细核对。
- 快照是纯数据，能原样存成 JSON。**本任务不建 `quote` 表、不生成 `quote_id`**：现在没有会拿着快照下单的调用方，两个试算接口不该产生可以下单的报价。表、`quote_id`、询价日志和 `/sales/v1/quotes` 一起在 M2-04 做。

### 两个试算接口

| 接口 | 谁用 | 返回 |
| --- | --- | --- |
| `POST /platform/v1/quotes/preview` | 平台员工（新操作 `quote.preview`：超级管理员、运营、招商、渠道经理、客服） | 每个车型组的中标和全部候选（结算价、对外价、加价比例、汇率、排序依据、明细），每个没报出价的商品 / 车型组的原因 |
| `POST /tenant/v1/products/{id}/quote-preview` | 供应商（`product.read`） | 自己这一个商品的结算价和完整明细；没上架的也能试算，被暂停时也能试算 |

- 都是只读：不写库、不留审计日志、不占库存。
- **租户侧绝不返回对外价和加价比例**（规则 4）：这条路径在租户事务里只读本租户的数据，代码里根本不调 `sellPrice`、不取加价和评分，应答的结构（连同 openapi 的定义）里没有这些字段。集成测试逐层扫描字段名。
- 试算可以带 `assume_route`（假定的里程和时长）：路线服务没接上之前，里程 + 时长的商品靠它试算；接上之后也可以用来看某个里程下的价。
- 财务、风控、主数据运营、技术、只读角色不给 `quote.preview`：应答里有各供应商的结算价和加价比例。
- **正式的询价接口 `/sales/v1/quotes` 不在本任务**：它要渠道鉴权（API 客户端、`channel_id`、授权的租户、限流 50 次 / 秒），属于 M2-04。到时走的是这里同一个函数（`previewPlatformQuote` 的 `fresh: false` 路径加上渠道参数）。

### 留给别的任务的接口（`apps/api/src/services/quote-deps.ts`）

| 接口 | 给谁 | 现在的默认实现 |
| --- | --- | --- |
| `RouteEstimator.estimate({ from, to, departAt })` → `{ meters, minutes }` 或 null | M2-02（谷歌 Routes） | 恒返回 null：里程 + 时长的报不出，别的不受影响。候选里没有用得到路线的规则时不调用 |
| `FxRates.quote(from, to, at)` → `{ rate（十进制字符串）, asOf }` 或 null | M2-03（汇率中心） | 恒返回 null：只有同币种的能报。超过 48 小时没更新的引擎不用（见「对外价」） |
| `MarkupRules`：`markupBp({ tenantId, cityId, category, vehicleGroupId })`、`floorBp`、`bandBp` | M2-04（渠道和加价规则） | 加价比例取配置 `QUOTE_DEFAULT_MARKUP_BP`（默认 1000 = 10%，不是密钥），下限 10%，价格带 3% |
| `TenantStandings.load(db, tenantIds)` → 评分、已完成订单数、是否观察期 | M4-01（评分），已完成订单数来自 M3-01 | 都是默认：没有评分（按 4.5）、0 单、不在观察期。所以现在同价区间里实际按排序价低者中标 |

这四样挂在 `AppContext.quote` 上，`buildApp` 可以替换；集成测试用可以改的替身把跨币种、路线、评分、观察期各走了一遍。

**外部调用出问题时**（`services/quotes.ts` 的 `callExternal`）：路线预估、汇率每次调用最多等 `QuoteDeps.externalTimeoutMs`（默认 2 秒，`QUOTE_EXTERNAL_TIMEOUT_MS`）。
超时或抛异常都当作「取不到」：用得到路线的商品报 `ROUTE_UNAVAILABLE`，跨币种的报 `FX_RATE_UNAVAILABLE`，其余照常——一个外部服务出问题不让整次比价失败。
每次记一条警告日志（依赖名 + 异常，异常走统一的脱敏序列化，不含密钥和连接串）。M2-02 / M2-03 的模块自己还要有更短的超时、重试和错误码，这里是报价这一层的兜底。
外部调用都在数据库事务之外：先在一个只读事务里把商品、规则、库存、节假日、评分取齐，提交之后再并行调路线预估和汇率，最后纯计算——不占着连接等外部服务。

**停用的城市、机场 / 车站**：平台侧试算返回 409 `MASTER_DATA_NOT_READY`（`details.reason` 是 `CITY_DISABLED` / `PLACE_DISABLED`），说明为什么报不了；租户侧原来就是 409 `CITY_OR_PLACE_DISABLED`。

### 取数和权限

比价要把所有供应商的商品放在一起算。迁移 `0016` 给平台角色加了这几张租户表的**只读**权限和策略：`brands`、`areas`、`area_polygons`、`product_areas`、`price_rules`、`adjust_rules`、`inventory_days`
（原来就能读 `products`、`product_vehicle_groups`）。不能写；调度人不给。结构测试的三张清单同步更新。

以后 `/sales/v1` 用渠道身份询价时，也应当走平台角色（或一个专门的只读角色）读这些表，再按「渠道被授权的租户」过滤——这一层在 M2-04 定。

### 缓存和性能

需求：单次报价 P95 ≤ 300 ms；价格规则和区域多边形要缓存，租户改规则后 1 分钟内生效。

- 缓存的是「候选商品连同它们的区域图形、价格、调价、服务规则」，按「城市 + 品类 + 接送点」分开存，在进程内存里（`QuoteCatalogCache`），不引入外部缓存组件。
- 有效期 30 秒，不做主动失效：供应商改了规则，最迟 30 秒后按新规则算；多个实例各有各的缓存，留一倍余量仍在 1 分钟以内。供应商被暂停、商品下架也在这 30 秒里生效。
- **不缓存**：库存（差一单就是超卖）、节假日、评分、汇率（各有自己的来源和刷新）。
- 试算接口不用缓存里的旧数据（现取现算），取到的新数据顺手更新缓存：运营和供应商要看的是现在的规则。
- 取数是每类数据一条查询取回这一批商品的，不逐个商品查；查询都带着这批商品所属的租户编号，走得上以 `tenant_id` 开头的索引。

基准（`apps/api/src/quotes-benchmark.itest.ts`，真实 PostgreSQL）：300 个供应商，每个 1 个已上架的接送机商品、3 个区域共 6 块图形（营运区 60 个顶点）、2 个车型组、18 条价格、5 条调价规则；对同一次用车请求比价（每个供应商两个车型组各算两个区域）。开发机上的结果：

| 情况 | P50 | P95 |
| --- | --- | --- |
| 现取现算（试算接口，每次从库里取全部规则） | 约 200 ms | 约 264 ms |
| 目录在缓存里（正式询价的常态） | 约 42 ms | 约 82 ms |

上面是单独跑这一个测试的结果。和全部集成测试一起跑时（几十个测试文件同时跑，机器有时还和别的任务共用）数字会大得多：
见过现取现算 P95 485 ms、1290 ms，缓存命中 P95 143 ms、476 ms（后一组是机器负载 11 的时候）。

所以这个测试平时（`pnpm check`、CI）**不断言耗时**，只断言与机器负载无关的事：结果算得对、300 个供应商都参加了比价、连续 31 次询价只去库里取了一次目录；量到的数记在测试的诊断信息里。
要按需求断言时单独跑这一个文件并打开开关：`QUOTE_BENCH_ASSERT=1 node --env-file-if-exists=.env --test apps/api/src/quotes-benchmark.itest.ts`，这时断言缓存命中 P95 ≤ 300 ms。
**是否达到需求的 P95 ≤ 300 ms，以单独跑的结果为准**：缓存命中约 82 ms，达到；现取现算约 264 ms，只用于试算。
需求的容量是 100 个租户，300 个供应商同时在一个城市的一个机场都有商品已经是三倍。生产机器上的实际数字要等部署后再量。

还没做的优化（数据量再大时）：按请求的坐标用区域图形的外接矩形先筛商品（`area_polygons` 存着外接矩形）；缓存里把图形、规则预先整理成查找表。
