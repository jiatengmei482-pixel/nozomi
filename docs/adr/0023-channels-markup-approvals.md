# ADR 0023：渠道与加价规则、敏感操作双人复核、`/sales/v1` 的鉴权与正式询价

- 状态：已采纳（2026-10-17，M2-04）
- 由 ADR 0033 补充（2026-10-26，M3-07）：「复核生效前试算对近 30 天订单的毛利影响」已做——发起前可以试算，发起时存进复核记录（`impact`），审核人批准前看并可以再算一次；报价快照的候选多记汇率和缓冲、渠道多记结算币种的汇率。本文其余决定不变。
- 实现 ADR 0020 留下的 `MarkupRules`：带渠道的报价改为按渠道的五级规则匹配，并加上渠道的下限、价格带 δ、最低毛利、对外价取整；ADR 0020 的待定事项 9、15、16 在这里定。
- 实现 ADR 0020「本期不做」里的 `/sales/v1/quotes`、`GET /quotes/{quote_id}`、渠道鉴权、限流、`quote` 表和 `quote_id`、询价日志。
- 补充 ADR 0008：渠道的 API 客户端与访问令牌（第三种受众 `sales`）。补充 ADR 0010：九张新的平台表的授权。
- 双人复核做成通用机制：ADR 0022 留下的「汇率人工锁定」以及之后的结算条款、付款、退款、停用租户都用它。
- 由 ADR 0034 补充（2026-10-26，M4-02）：登记 `compensation_table.update`、`ticket.decision` 两类；`ApprovalKind` 多一个可选的 `onDismiss`（驳回、撤回时在同一个事务里恢复对象）。

## 背景

需求：《平台运营端与渠道对接》「渠道管理」（类型、配置项、授权范围、加价规则五级匹配、日期范围、修改需双人复核）、「敏感操作双人复核」、「汇率缓冲与加价下限」（每个渠道设最低加价比例，默认 10%；加价规则低于下限时系统拦截）、「平台账号、安全与审计」（密钥后台只显示后 4 位）、数据模型；
《用车报价服务平台》「API 通用约定」（OAuth 2.0 Client Credentials、Bearer Token 2 小时、限流 报价 50 次/秒 其他 10 次/秒、429 + Retry-After）、「API · 销售端接口」、报价引擎第 10–12 步。文末各轮决策优先：第四轮（租户端不返回对外价和加价比例）、第五轮 ②⑥（价格带、渠道最低加价 10%）。
roadmap 的验收标准：租户端任何接口不返回对外价和加价比例。

## 决定

### 表（迁移 0019、0020，全是平台表）

| 表 | 内容 | 平台角色 |
| --- | --- | --- |
| `channels` | 类型（自营 / API 分销商 / OTA / 线下代理）、状态（测试 / 启用 / 暂停）、公司和联系人、结算币种、付款方式和额度（只存配置）、授权范围（租户：全部 / 白名单 / 黑名单；城市：全部 / 指定；品类）、定价参数（默认加价、下限、价格带、最低毛利、对外价取整）、付款后是否展示中标租户名、`version`、`pricing_version` | 读、增、改 |
| `channel_tenants`、`channel_cities` | 授权范围里的租户名单、城市名单 | 读、增、删（整体替换） |
| `markup_rules` | 五级之一的维度、加价比例、用车日期范围、备注、版本；软删除 | 读、增、改 |
| `approvals` | 双人复核：类别、对象、一句话说明、要改成什么、改之前是什么、发起时的版本、状态、发起人 / 审核人和时间、说明 | 读、增、改 |
| `channel_api_clients` | client_id、名称、密钥的 SHA-256 和后 4 位、密钥代次、轮换前的密钥和宽限期、状态 | 读、增、改 |
| `quote_logs` | 每次询价：渠道、客户端、请求、币种、候选数、报出几个、全部候选的排序依据（`bids`）、没报出价的原因（`rejects`）、耗时、是否下单 | 读、追加 |
| `quotes` | 每个 `quote_id`：中标租户 / 商品 / 版本、对外价、结算价、加价比例和命中的规则、完整快照、有效期 | 读、追加 |
| `sales_rate_limits` | 限流计数 | 读、增、改 |

- **租户角色对这九张表没有任何权限**（结构测试的清单里登记了；`sales.itest.ts` 逐张在租户事务里查，全部被数据库拒绝）。这是规则 4 在数据库层的保证：租户代码里即使写错了也读不到加价比例和对外价。
- 指向租户的列叫 `supplier_tenant_id`、`winner_tenant_id`，**不叫 `tenant_id`**：这些行是平台的配置和交易记录，不属于那个租户；叫 `tenant_id` 会被结构测试当成租户表、要求开行级安全并让租户读到自己那几行——那正是不能发生的。
- 数据库约束兜底：渠道下限不低于 10%、默认加价不低于下限、价格带 0–5%、加价规则不低于 10%、五级的维度组合、审核人不能是发起人（`approvals_two_people`）。「不低于**渠道**下限」由业务层在发起和批准时检查（渠道下限会变）。
- 没有预置任何渠道。第一个渠道（自营官网）由运营在后台建（规则 1）。

### 加价规则：五级匹配

| 级 | 维度 | 例子 |
| --- | --- | --- |
| 1 | 租户 × 城市 × 品类 × 车型组 | 官网 · Relaxcar · 东京 · 包车 · 商务 7 座 = 12% |
| 2 | 租户 | 官网 · Relaxcar = 15% |
| 3 | 城市 × 品类 × 车型组 | 官网 · 东京 · 包车 · 商务 7 座 = 12% |
| 4 | 城市 × 品类 | 官网 · 东京 · 接送机 = 8% |
| 5 | 渠道默认 | 渠道的 `default_markup_bp`；或带日期范围的全渠道规则（促销） |

- 纯函数 `resolveMarkup`（`packages/domain/src/channels.ts`）：从第 1 级往下，**命中第一级就停**。都没命中用渠道默认。
- **日期范围**（促销期）是**用车日期**（城市当地），两端都含。同一级里，用车日期落在范围内的带日期规则优先于不带日期的；同一组维度上不带日期的最多一条、带日期的不能重叠（保存时拦截，`MARKUP_RULE_CONFLICT`），所以每级最多命中两条，结果是确定的。
- 不带日期的全渠道规则不允许（那就是渠道默认）；第 5 级的规则必须带日期。
- 带日期的第 5 级（全渠道促销）**不会**压过第 1–4 级的规则：「命中第一条即停」按级别，促销要覆盖某个城市或租户，就在那一级也加一条带日期的规则。
- **低于下限拦截**：发起时 `markupRuleIssues` 检查（`VALIDATION_FAILED`，原因 `BELOW_FLOOR`，`detail.floor_bp`），批准时按那一刻的下限再查一次。
- **调高渠道下限**时，还在用（没结束）的规则有低于新下限的，发起就拦（409 `RULES_BELOW_FLOOR`，列出规则）：否则规则表上写 8%、实际按 12% 算，运营看到的和客人付的对不上。
  「还在用」按规则自己的当地日期判断（用车日期的口径，和匹配一致）：有城市的规则用那个城市的当地日期；没有城市的规则（第 2 级供应商、第 5 级全渠道）在哪个城市都可能用到，
  要在世界上最晚的时区（UTC−12）也过了结束日期才算结束——宁可多挡几个小时，也不让一条还在某个城市生效的低比例规则漏过去。发起和批准两处都这样判断。询价时再遇到低于下限的（理论上走不到）仍按下限算（ADR 0020 待定事项 9）。

### 对外价：渠道的价格带、下限、最低毛利、取整

`sellPrice` 多了可选的渠道规则（不给时和 ADR 0020 完全一样，原有测试不变）：

1. 对外价 = 结算价 × 汇率 × (1 + 缓冲) × (1 + max(加价比例, 下限))，精确分数；
2. **最低毛利**：加价部分（上式减去结算价 × 汇率 × (1 + 缓冲)）不足最低毛利时补到最低毛利。最低毛利是渠道结算币种的金额；客人付别的币种时按中央汇率（不加缓冲）换过去，要换却没有可用的汇率（没有或超过 48 小时）时这个报价报不出（`FX_RATE_UNAVAILABLE`）——不能在不知道够不够最低毛利的情况下卖；
3. **取整**：客人支付币种在渠道的取整表里、取整单位大于 1 时**向上**取整到这个单位（ADR 0020 待定事项 15：只往上取，往下会让实际加价低于下限）；否则照旧四舍五入到最小货币单位。需求文档的例子 108,900 × 1.1 = 119,790 → 119,800 由此得到。
4. 比价（排序价、价格带）用的是最后的对外价；价格带 δ 用渠道的。

快照里每个候选的 `sell.channel` 记取整单位、换算后的最低毛利、是否补过最低毛利、最低毛利换币种用的汇率。

### 敏感操作双人复核（通用机制，`apps/api/src/services/approvals.ts`）

- 每一类登记成一个 `ApprovalKind`：`kind`、`resource`、看（`readAction`）、发起（`requestAction`）、审核（`reviewAction`）三个权限，和批准时让改动生效的 `apply`。登记表在 `services/approval-kinds.ts`。
- **发起**：在业务事务里写一条 `pending` 的记录和一条审计（`approval` / `request`）。发起之前先按现在的数据校验一遍，明显不对的（低于下限、日期重叠、和现在一样）直接拦，不进队列。
- **审核**：锁住记录；发起人不能批准、驳回自己发起的（409 `APPROVAL_SELF_REVIEW`，数据库也有约束）；没有这一类的审核权限 403；看不到这一类当作不存在 404。批准时在**同一个事务里**调 `apply`：按那一刻的数据再校验；发起时记下的版本（`base_version`）和对象现在的版本对不上 409 `APPROVAL_STALE`；任何一步失败整个回滚，记录仍是待审核，审核人看到原因后驳回。
- **撤回**：只有发起人自己能撤回待审核的。批准、驳回、撤回之后不能再改。
- **审计**：复核记录的发起、批准、驳回、撤回各一条；改动生效时被改的对象再记一条，操作者是审核人，`after` 里带复核编号和发起人。
- 「定价参数」的复核核对渠道的 `pricing_version`（定价参数、加价规则、状态任何一个变了都加一）；规则的修改、删除核对规则自己的 `version`；新增规则和暂停不核对版本（批准时按当时的规则重查冲突）。所以一个渠道上同时挂着的几条定价复核，批了一条，其余的会变成 `APPROVAL_STALE`，按现在的数重新发起——宁可多发起一次，也不按过时的「改之前」生效。
- 现在登记的五类：`channel.pricing`（改定价参数）、`channel.pause`（停用渠道）、`markup_rule.create` / `update` / `delete`。
- **以后加一类**（汇率人工锁定、结算条款、付款、人工退款超过阈值、停用租户）：写一个 `ApprovalKind`（`apply` 里自己校验、改数据、写对象的审计），加进登记表；发起接口里调 `requestApproval`。队列页面、审核接口、审计都不用改。openapi 里 `Approval.kind` 的枚举加一项。

**「生效前试算对近 30 天订单的毛利影响」没有做**：现在没有订单（M3-01）。询价日志（`quote_logs.bids`）里已经存着每次中标的结算价、加价比例和命中的规则，订单做出来以后，试算就是「把近 30 天成交的那些单按新规则重算加价部分、汇总差额」。建议拆成新任务（排在 M3-01 之后），复核详情页上显示试算结果。

### 哪些操作走复核

| 操作 | 怎么做 | 理由 |
| --- | --- | --- |
| 新建渠道（含初始定价参数） | 直接生效，状态是「测试」 | 新渠道还没有在卖；把新建也放进复核会让第一个渠道迟迟建不起来。建好后改定价走复核 |
| 改基本信息、授权范围 | 直接生效（`If-Match`），写审计 | 需求的复核清单里没有它们 |
| 改定价参数（默认加价、下限、价格带、最低毛利、取整） | 双人复核；只给要改的几项，没给的保持现在的值（合并后再校验，`sell_rounding` 给了就整体替换） | 「修改渠道加价比例」 |
| 新增 / 修改 / 删除加价规则 | 双人复核 | 「修改加价规则需双人复核」 |
| 暂停渠道 | 双人复核 | 「停用租户或渠道」 |
| 启用渠道（测试 → 启用、暂停 → 启用） | 直接生效 | 需求只要求停用复核；启用不会让客人多付钱 |
| 发 API 密钥、轮换、吊销 | 直接生效，写审计 | 不在清单里；吊销要能立即做（泄露时） |

### 权限

| 操作 | 角色 |
| --- | --- |
| `channel.read`（看渠道、规则、API 客户端、询价日志） | 除主数据运营外的每个平台角色：运营、招商看渠道卖哪些供应商；客服处理订单要知道是哪个渠道；财务对账；风控看价格；技术管连接器和接口日志；只读 |
| `channel.manage`（新建、改基本信息和授权、发密钥、**发起**定价 / 规则 / 暂停的复核、启用） | 渠道经理、超级管理员 |
| `channel.review`（审核渠道这一类的复核） | 渠道经理、超级管理员。两位渠道经理可以互相审核；只有一位时由超级管理员审 |
| `approval.read`（待审核队列） | 有 `channel.read` 的角色；列表只列自己能看的那几类 |
| `tenant.read`（只读看供应商） | 新给渠道经理：设置渠道卖哪些供应商、按供应商设加价规则，要看得到供应商名单。仍然不能新建、暂停供应商 |

里面有加价比例：这是平台内部的配置，规则 4 只限制 `/tenant/v1`。运营后台的菜单和首页卡片按这几个操作显示。

### API 客户端与访问令牌

- **凭据**：`client_id`（`nzc_` + 24 位十六进制，公开）+ `client_secret`（`nzs_` + 32 字节随机数）。密钥原文**只在新建、轮换的那一次应答里出现**；库里存 SHA-256（密钥是高熵随机数，不需要慢哈希；和邀请令牌同一做法）和后 4 位。审计日志只有 client_id、名称、后 4 位和代次。
- **换令牌**：`POST /sales/v1/oauth/token`（`grant_type=client_credentials`，JSON 或表单）→ 2 小时的访问令牌：HS256 的 JWT，签名密钥由 `AUTH_JWT_SECRET` 按受众 `sales` 派生（和平台、租户令牌互不通用）。令牌里有客户端编号、**渠道编号**、密钥代次。密钥不对、客户端不存在或已吊销都是同一个 401 `INVALID_CLIENT`；渠道暂停 403 `CHANNEL_PAUSED`（密钥正确时才说）。比较哈希用等时比较。
- **每个请求**：验签后回数据库核对客户端在用、渠道没暂停、令牌的密钥代次有效。所以吊销、暂停立即生效。
- **轮换**：新密钥（代次加一）；被换下的那一代默认还能用 24 小时（宽限期，让渠道有时间换上），宽限期里用旧密钥换的令牌在宽限期过后失效；选「立即作废」（泄露时）所有旧代和用它们换的令牌马上失效。
  - **每一代各自算宽限期**（测试发现的缺陷后改的，迁移 0021）：旧代存成一个数组（代次、哈希、失效时刻），宽限期里再轮换一次，之前那几代照旧各自从被换下的时刻起保留 24 小时——
    运营没保存好新密钥又轮换一次时，渠道还在用的那把不会被顶掉。同时最多保留 5 代，再多就作废最早的一代（反复轮换不会攒下一串都能用的旧密钥）；过期的在下一次轮换时清掉；吊销时全部清空。
  - 令牌里记的是换令牌时用的那一代；那一代还在宽限期里（或就是当前代），令牌才有效。
- 换令牌接口按来源地址限流（每秒 10 次），失败的也计数（计数在单独的事务里先提交）。
- 需求里的「API Key + HMAC-SHA256 签名」「IP 白名单」「Webhook 地址」本期没做：自营官网用 Client Credentials 就够；见「本期不做」。

### `/sales/v1` 的渠道和数据权限

- 渠道编号**只来自令牌**。请求体不认识的字段一律 400（`channel_id`、`tenant_id`、`markup_bp` 都传不进来）。
- 用平台角色读写（ADR 0020 留的「这一层在 M2-04 定」）：渠道、规则、报价都是平台表；比价要读所有供应商的商品（ADR 0020 迁移 0016 给平台角色的只读）。读取在只读快照事务里，按渠道的授权范围过滤租户。没有为销售端单独建一个数据库角色：它需要的权限和平台试算完全一样，多一个角色只是多一份要维护的授权清单；等销售端拆成独立进程时再考虑（ADR 0010 剩余风险）。
- 别的渠道的报价和不存在一样 404。

### 正式询价（`POST /sales/v1/quotes`）

- 走 `previewPlatformQuote` 同一个函数，带渠道、`fresh: false`：候选商品和规则用 30 秒内的目录缓存（ADR 0020），渠道的配置和加价规则每次现查（改了立即生效），库存、节假日、评分现查。
- 城市或品类不在授权范围里：422 `CHANNEL_SCOPE_DENIED`。渠道不卖的租户不参加比价，询价日志里记 `NOT_IN_CHANNEL_SCOPE`。
- 请求：城市、品类、接送机的机场 / 车站和方向、起终点（坐标，或主数据的地点编号——用地点的坐标，ADR 0020 待定事项 16）、带时区的用车时间（按城市时区换成当地时间）、人数、行李、套餐时长、附加服务、司机语言、车型组、客人支付的币种。
- 每个车型组（包车按套餐）一个 `quote_id`（`QT` + 日期 + 10 位随机字母数字），有效期 30 分钟。快照（domain 的 `QuoteSnapshot` + quote_id + 渠道的参数 + 命中的规则和级别）原样存进 `quotes.snapshot`，常用的几项另抄成列；询价日志一行，带全部候选的排序依据和没报出价的原因。集成测试核对应答、quote 表的列、快照、询价日志四者一致。
- **应答**：quote_id、有效期、车型组、套餐、用车日期、是否加急、对外价（`{ amount: "119800", currency: "JPY" }`，主单位的十进制字符串）、跨币种时的中央汇率和取数时间、免费等待分钟数。**没有中标租户、结算价、加价比例**——需求文档报价返回示例里的 `settlement`、`markup_percent` 不给：「付款前不显示中标租户」「参与比价的租户和它们的报价只在平台内部记录」，有结算价和加价比例就能反推出供应商的报价。
- 没报出价的车型组在 `unavailable` 里，原因只给面向客人的几种（`NO_PRODUCT`、`OUT_OF_SERVICE_AREA`、`LEAD_TIME_TOO_SHORT`、`SOLD_OUT`、`OUTSIDE_SERVICE_TIME`、`SERVICE_TIME_PASSED`、`CAPACITY_EXCEEDED`、`ADDON_NOT_OFFERED`、`DRIVER_LANGUAGE_NOT_OFFERED`、`NOT_AVAILABLE`）；供应商内部的原因（暂停、子品牌停用、缺价格、汇率）归为 `NOT_AVAILABLE`。完整原因在询价日志里。
- `GET /sales/v1/quotes/{quote_id}`：本渠道的报价，有效期内 200，到点那一刻起 410 `QUOTE_EXPIRED`。

### 限流

- 「按项目现有限流机制」：和登录限速（ADR 0008）同一种做法——固定时间窗、计数在数据库里（多实例有效）、「先占用一次再判断」在一条 SQL 里原子完成；判断规则是 domain 的 `evaluateFixedWindow`（登录限速的 `evaluateThrottle` 改为调用它）。
- 按**渠道**计：报价每秒 50 次，查报价每秒 10 次（需求写「按 Token」；一个渠道发几个客户端不能把额度翻倍）。换令牌按来源地址每秒 10 次。超限 429 `RATE_LIMITED` + `Retry-After`。被拦下的请求不生成报价、不记询价日志。
- 每次请求多一次按主键的写。需求的容量是全平台报价峰值 200 次/秒，单行 upsert 的开销在这个量级可以接受；量大以后改成进程内令牌桶 + 定期汇总时新增 ADR。

### 运营后台

- 菜单「渠道」（`channel.read`）：列表（状态、类型、结算币种、默认加价）、新建、详情（基本配置、授权范围、定价参数、加价规则表、API 客户端与密钥、询价日志、这个渠道的复核记录）。改定价、规则、暂停的按钮发起复核，页面提示「已提交，等另一位同事审核后生效」。
- 菜单「待审核」（`approval.read`）：待审核队列和历史；每条显示改什么、改之前和之后、发起人和说明；按 `can` 显示批准 / 驳回 / 撤回。
- 首页：「渠道」卡片（渠道数、启用中的）、「待审核」卡片（待审核数）——按权限显示，数用列表接口的 `total`（ADR 0021 同样的做法，不改首页统计接口）。
- 报价试算页加「选渠道」：选了按该渠道的规则试算（候选上显示命中第几级、是否补了最低毛利；渠道不卖的供应商单独列出）。

## 补充（2026-10-25，M1-18）：API 客户端的「最近使用」

验收发现：运营后台「API 客户端与密钥」里的「最近使用」只在换令牌时更新。令牌有效 2 小时，渠道换一次令牌后一直在调接口，页面上却停在两小时前，看不出这个客户端是不是还在用（决定能不能吊销旧客户端时要看这一项）。

- **用令牌调用 `/sales/v1` 的任何接口也算使用**：通过了鉴权（令牌有效、客户端在用、渠道没暂停、没被限流）就更新；令牌无效、被拒的不算。
- **按分钟节流**：鉴权时本来就要按主键读这一行，顺带读出 `last_used_at`；离现在不到 1 分钟就不写，满 1 分钟才写一次。写的语句本身也带条件（`last_used_at` 为空或早于 1 分钟前），同一分钟里并发的几个请求只有一个真正改到这一行，时钟回拨时也不会往回改。
  - 不节流的话，报价峰值时每个请求都要多改一次同一行（同一渠道的请求排队等这一行的行锁，还多写 WAL）；限流计数已经是每个请求一次写（见「限流」），不再加一次。
  - 代价：页面上的「最近使用」最多晚 1 分钟。这一项只用来判断客户端还在不在用，分钟级足够；需要精确的调用记录看询价日志。
- 换令牌照旧每次都记（换令牌本身按来源地址限流，量很小）。
- 集成测试（`sales.itest.ts`）：换令牌后 1 分钟内调用不写这一行（行版本不变），满 1 分钟后下一次调用（查报价也算）更新到那一刻，令牌无效的请求不更新。
