# ADR 0027：派车、司机 H5、落地时间取证、no-show 证据、推送给供应商的 Webhook

- 状态：已采纳（2026-10-25，M3-02）
- 补充 ADR 0026：订单状态和转换表扩展（「订单状态」一节）；租户角色对订单加「改」；付款确认时排 `order.confirmed` 推送。ADR 0026 的其余决定不变。
- 由 ADR 0029 补充（2026-10-25，M3-03）：发出 `order.changed`、`order.cancelled`；照片多一种 `receipt`（事后加收的票据，司机 H5 或供应商后台上传）。本文其余决定不变。
- 补充 ADR 0005：新增一把服务器自动生成的密钥 `DATA_ENCRYPTION_KEY`（「签名密钥怎么存」一节）。
- 补充 ADR 0022「定时任务和多实例」：第三个进程内定时任务（Webhook 投递），订单定时任务加履约提醒。
- 编号说明：迁移 0025（司机、车辆）、0026（派车和履约）、0027（Webhook）。

## 背景

需求：《用车报价服务平台》「8. 订单与履约」（订单指派、改派、履约回传、客人未出现、落地时间、两种接单方式）、「履约规则（已确认）」（派车截止时间、超时未派车、客人未出现、改派和换车、履约时间点）、
「9. 司机管理」「10. 车辆管理」「11. 账号、权限与 API 设置」（Webhook：填地址、选订阅事件、查看投递记录和失败原因、手动重发、发送测试事件）、「14. 补充功能」（实际落地时间登记、司机 H5）、
「API · 租户配置接口」（订单指派、履约状态、司机、车辆、可用资源、Webhook 记录）、「API 通用约定」（HMAC-SHA256、X-Timestamp + X-Signature、5 分钟防重放）、
「API · 销售端接口」（Webhook 5 秒未 2xx 重试，间隔 1–5–30 分钟、2–6–24 小时；事件带 event_id）、「数据模型」（driver、vehicle、assignment、order_evidence、webhook_subscription / webhook_delivery）；
《平台运营端与渠道对接》「航班信息」「免费等待与 no-show」「订单中心 · 人工介入」（手工重发租户推送）、「异常队列」；第五轮决策 ③（落地时间以客人确认优先，no-show 须 5 项证据）。
roadmap 的验收标准：推送失败自动重试；落地时间取证规则。

### 订单状态（扩展 ADR 0026）

| 状态 | 含义 | 谁让它进入 |
| --- | --- | --- |
| `assigned` 已派车 | 填了司机和车辆 | 供应商（后台或调度系统） |
| `departed` 司机已出发 | | 司机 H5 / 调度系统 |
| `arrived` 司机已到达 | 到了上车点（带定位时记下距上车点多少米） | 同上 |
| `in_service` 服务中 | 接到了客人 | 同上 |
| `completed` 已完成 | 包车必须带实际时长和里程 | 同上 |
| `no_show_claimed` 客人未出现（待审核） | 司机提交 no-show，5 项证据齐全 | 司机 H5 |
| `no_show` 客人未出现 | 平台审核通过（按全额收费） | 运营（M4-02） |

转换（`orderTransitionAllowed`）：已确认 → 已派车 / 已取消 / 救援；已派车 → 已出发 / 已取消 / 救援；**已出发 → 已派车（改派）** / 已到达 / 已取消 / 救援；已到达 → 服务中 / 客人未出现（待审核）/ 已取消；
服务中 → 已完成；客人未出现（待审核）→ 客人未出现 / 已取消（审核驳回 = 客人全额退款，M4-02）；救援 → 已确认 / 已派车 / 已取消。已完成、客人未出现、已取消是终态。
履约不能跳步（没出发不能到达，没到达不能接到），重复也不行：409 `ORDER_STATE_INVALID`（`details.status`、`details.action`）。改派在状态流水里记「已派车 → 已派车」（`REASSIGNED`）。

**数据库兜底**：租户角色对 `orders` 有了「改」，但语句级触发器只许改派车和履约的列（行程、乘客、结算价、付款、确认 / 取消、截止时间、客人确认的落地时间都只有平台能改）；
行级触发器只许状态从「已确认 / 已派车 / 已出发 / 已到达 / 服务中」变成「已派车 / 已出发 / 已到达 / 服务中 / 已完成 / 客人未出现（待审核）」——供应商不能在库里把单取消、确认或复活（42501，和没有权限一样）。

### 司机、车辆

- 司机：姓名、国际格式的电话（客人来自不同国家）、会说的语言（主数据语言代码，至少一种）、驾照到期日、驾龄（选填）、金牌司机、在职 / 停用。同一个供应商里一个电话一位司机。
- 车辆：车牌（空白归一后唯一）、车型组（主数据）、品牌车型、颜色、座位、里程（< 5 万公里为新车）、营业牌照 / 非营业牌照、保险和车检到期日、可用 / 维修 / 停用。**非营业牌照的车不能设为可用**（检查约束 + 校验）。
- 不删除（订单引用着它们），「删除」= 停用。证件到期前 30 天在列表里提示「快到期」（按今天 UTC）；能不能派单按用车日判断。司机照片不在本期（见「本期不做」）。
- 权限：看 `fleet.read`（管理员、调度、只读）；新增、修改、停用 `fleet.manage`（管理员、调度）。新增带幂等键，修改带 If-Match，内容没变不加版本不写日志，写审计日志。

### 派车（`POST /tenant/v1/orders/{id}/assign`）

- `order.dispatch`（管理员、调度）。必须带订单的 If-Match：两个人同时派同一张单只有一个成功（另一个 409 `VERSION_CONFLICT`）。
- **硬性条件**（不满足 422 `ASSIGNMENT_MISMATCH`，`details.issues[]` 逐项 `code` + `message`）：司机在职、驾照在用车日有效、会说客人要求的司机语言；车辆可用、营业牌照、保险和车检在用车日有效、
  车型组同级或升级（等级不低且座位不少；需求「只能换同级或更高级，升级不加价，系统拦截降级」）、座位不少于订单车型组。
- **同一时段的提示**：每单占用「用车前 1 小时 ～ 用车后（套餐时长或 2 小时）+ 1 小时」；这位司机或这辆车在重叠的时段已有派着的单：409 `ASSIGNMENT_CONFLICT` 列出那几单，
  调度确认后带 `confirm_conflicts: true` 再派（需求是「提示冲突」，不是禁止；派车记录里记下 `conflict_confirmed`）。判断之前先拿司机和车辆的事务级咨询锁，两张单同时派给同一位司机时后到的一定看得到先到的。
- 成功：派车记录（`order_assignments`，只追加）、状态流水（`ASSIGNED` / `REASSIGNED`，`detail` 里有司机、车辆、操作人）、审计日志（`order` / `assign`、`reassign`）；旧的司机链接立即作废，发新的；
  给中标供应商自己的 Webhook 排 `order.assigned`（改派 `change: true`）。同一位司机、同一辆车再派一次什么都不变。
- 可派资源（`GET /orders/{id}/assignable`）：在职的司机、可用的车辆，各自带不符合的原因和同一时段的单——比「排除掉」更好用：调度看得到为什么不能派。
- 「通知客人」：改派后客人在订单页（M3-05）和渠道的订单接口（`GET /sales/v1/orders/{id}` 的 `driver`、`vehicle`）看到新的司机；邮件在通知中心任务里接。

### 派车截止时间和提醒

- 截止时间（`dispatchDeadline`，需求「履约规则」原文）：用车前 24 小时；付款时距用车已不足 24 小时的，付款后 2 小时（不晚于用车时间）。付款确认时算好存进订单。
- 订单的定时任务（同一个进程内任务，每分钟）：过了截止时间还没派车 → 订单上记下发现的时间（`dispatch_overdue_at`）、服务日志 `order.dispatch_overdue`（警告）；用车前 1 小时仍未出发 → `departure_overdue_at`、`order.departure_overdue`。
  每张单只提醒一次（一条条件更新「找出来 + 记下」，`skip locked`，多实例也只提醒一次）。
- 供应商后台的订单列表能筛「超时未派车」并标红；订单里有 `dispatch.overdue`、`escalation_at`（用车前 6 小时：仍未派车即进入救援改派，M3-04 实现）。邮件 / LINE 通知在通知中心任务。

### 司机链接（司机不需要账号）

- 派车 / 改派时生成；令牌 `nzd_<租户编号>.<32 字节随机数 base64url>`，**库里只存整个令牌的 SHA-256**，原文只在派车 / 重新生成的那一次应答里。租户编号不是秘密，带着它是为了直接进入那个租户的事务（和租户的重置令牌一样，ADR 0008），全程在行级安全之内。
- 有效期：用车结束（包车加套餐时长）后 24 小时（需求「链接用车后 24 小时失效」）。改派、重新生成（`POST …/driver-link`）、手动吊销（`DELETE …/driver-link`）都立即作废旧链接。
  这三种操作都先锁订单再改链接；司机的每个请求先按令牌找到链接，锁住订单之后**再读一次链接**再核对，所以和吊销同时到的司机请求排在吊销之后、读到的是已吊销（401），不会用已作废的链接成功一次。
- 链接写成 `/driver#<令牌>`：`#` 后面不会发给服务器，不进反向代理的访问日志，也不随来源页泄露。前端把令牌放进 `Authorization: Bearer` 调 `/driver/v1/…`。
- 令牌不存在、被吊销、过期、令牌里的租户被换掉、不再是这一单现在的司机：一律 401 `DRIVER_LINK_INVALID`，应答完全一样。一个链接只对应一张单（接口路径里没有订单编号）。

### 司机 H5（`/driver/v1/trip…`）

- 看这一单：乘客姓名和电话、航班号、上下车点（接机给机场坐标，一键导航）、时间、人数行李、附加服务（名字）、备注、调度电话、车辆；履约时间点、落地时间、免费等待、联系记录、照片、5 项证据的核对。
  **没有任何价格**（结算价、对外价、加价比例都不给；也没有客人的邮箱）。
- 操作：出发 / 到达 / 接到客人 / 完成（和调度系统的 `POST /tenant/v1/orders/{id}/events` 同一套规则）、出发后每分钟上报定位、上传照片、填落地时间、记联系客人、申请离开、提交 no-show。
- 时间一律用系统收到的时间，不认手机时钟。
- 「一键导航」用 `geo:纬度,经度` 链接交给手机自带的地图应用（本站代码只允许链到 `lib/external-links.ts` 登记过的站外地址，不链谷歌地图网页），旁边同时显示上车点坐标。
- 页面是独立的路由 `/driver`（不在两个后台里，不需要登录），手机宽度可用。

### 落地时间（验收标准「落地时间取证规则」，第五轮决策 ③）

规则是 `effectiveLanding` 纯函数，逐条单元测试：

1. 司机填写的时间只有**附了到达屏照片**才算数（「填写时必须拍到达屏」）；
2. 客人和司机都有：取**较晚者**（一样时记为客人确认）；
3. 只有客人的：取客人的（「客人确认优先」）；只有司机的：取司机的；
4. 都没有：取计划到达时间——接机单的用车时间（下单时按航班的计划到达时间填）。

- 客人：`POST /sales/v1/orders/{id}/landed`（官网订单页在 M3-05 调），时间是系统收到的时间；司机：先上传 `arrival_screen` 照片，再 `POST /driver/v1/trip/landing`（`landed_at` + `file_id`）。
- **各自提交后不能改**（409 `LANDING_ALREADY_REPORTED`；有争议走工单）。时间不能晚于现在（5 分钟误差）、不能比计划到达早 3 小时以上；客人在计划到达前 3 小时以上点也拒绝（`LANDING_TOO_EARLY`）。
- 只有接机（接送机 + 接机方向 + 有航班号；下单时机场接机必填航班号、车站不能填）记落地时间；其余 409 `LANDING_NOT_APPLICABLE`。
- 每次有人提交都按规则重新取定，结果写入订单（`landed_at`、`landed_source`），原始的两份记录也都保留（`guest_landed_at`、`driver_landed_at` + 照片）。供应商后台、运营后台、司机页面、渠道看到的是同一个结果，还有延误分钟数和「是否在 6 小时顺延范围内」。「是否在 6 小时顺延范围内」按毫秒比较：延误恰好 6 小时算在内，多 1 毫秒就不算；延误分钟数向下取整，只用于显示，不参与判断。
- 接机的免费等待从实际落地时间起算（需求「免费等待与 no-show」），其他从用车时间起算。

### 客人未出现（no-show，第五轮决策 ③ 的 5 项证据）

`noShowChecklist` 纯函数，逐项：

1. 免费等待开始前（含那一刻）点了「已到达」，且当时的定位距上车点 ≤ 300 米（接机的上车点是主数据里机场的坐标）；
2. 免费等待内至少 3 次联系记录（电话或即时通讯，可附截图；时间是系统收到的时间）；
3. 到达之后拍的举牌照片（`signboard`；照片的「系统时间」= 系统收到它的时间）；
4. 免费等待结束后点了「申请离开」，并且已经过了 10 分钟（客服 10 分钟内没处理视为同意；客服反对的流程在 M4-02）；
5. 用车后 24 小时内提交。

- 5 项都满足才能提交（422 `NO_SHOW_EVIDENCE_INCOMPLETE`，`details.missing[]`）——证据不全的申请提交上去也必然被驳回，不如在现场就告诉司机还差什么；司机页面实时显示这张核对表。
- 提交后订单变成 `no_show_claimed`，记一条 `order_no_show_claims`（提交时逐项的核对结果、免费等待的起止），给供应商推 `order.status_changed`。审核在 M4-02。
- 无限免等的单不能申请离开（免费等待永远不结束），也就不能 no-show——这种单要联系调度处理。

### 照片存在哪里

存在 PostgreSQL（`order_files.data`，`bytea`），不存本机文件、也不接对象存储：

- 项目现状是单机 Docker Compose，以后可能多实例：本机文件在多实例之间不共享，还要另外挂卷、另外备份；库里的照片随每日数据库备份（ADR 0007）一起备份、一起恢复，和证据记录在同一个事务里写入。
- 量不大：每单几张照片，每张最大 5 MB（建议手机端压缩到 1–2 MB）。照片多到影响备份时间时，按同一个接口换对象存储（新增 ADR）。
- 格式按文件开头的字节判断（JPEG、PNG、WebP、HEIC），和声明的 `Content-Type` 不一致、不是这四种都拒绝（415）；超过 5 MB 413。请求体是原始字节（不引入 multipart 依赖）。
- 取回时原样返回，带 `X-Content-Type-Options: nosniff` 和 `Content-Security-Policy: default-src 'none'; sandbox`：伪装成图片的内容不会被浏览器当页面执行。
- 「带系统时间水印」：水印的时间就是系统收到照片的时间，后台查看时叠加显示；不在图片像素里烧录（要引入图像处理的原生依赖，ADR 0001「少依赖」）。

### 推送给供应商的 Webhook

**设置**（`/tenant/v1/webhooks`，一个供应商一个接收地址）：地址、订阅的事件、推送 / 暂停。设置、换密钥、删除、发测试事件、手动重推只归管理员（`webhook.manage`）；看设置和投递记录 `webhook.read`（管理员、调度、只读）。

**事件**：`order.confirmed`（新订单：付款后自动确认的**同一个事务里**排队，确认了就一定会推）、`order.assigned`（派车和改派，`data.change`）、`order.status_changed`（出发、到达、接到、完成、客人未出现，`data.from_status`、`data.to_status`）；
`order.changed`、`order.cancelled` 在 M3-03 发出，`rescue.offered`、`order.rescued_away` 在 M3-04 发出——名字先定下来，供应商可以先订阅。另有不可订阅的 `webhook.test`。

**请求**：`POST` 到接收地址，请求体 `{ event_id, type, created_at, tenant_id, data }`，`data.order` 是**发送时**订单的当前内容（就是 `GET /tenant/v1/orders/{id}` 的那份：行程、乘客、结算价、派车、履约、落地时间；**没有对外价、加价比例、渠道**，规则 4）。
请求头 `X-Event-Id`、`X-Event-Type`、`X-Timestamp`（秒）、`X-Signature: v1=<HMAC-SHA256(签名密钥, "<X-Timestamp>.<请求体原文>") 的十六进制>`、`X-Delivery-Attempt`。
接收方：算签名定长比较；时间戳和自己的时钟相差超过 300 秒拒绝（防重放）；同一个 `event_id` 只处理一次（重试、手动重推、偶尔的重复投递都是同一个编号）。参考实现 `verifyWebhookSignature`；格式写在 openapi.yaml 的 `webhooks.tenantOrderEvent`。

**签名密钥怎么存（为什么不是哈希）**：推送时平台要用密钥**原文**算 HMAC，哈希还原不出原文，所以只能加密存储：

- 密钥由平台生成（`nzwh_` + 32 字节随机数），**只在新建设置和换密钥的那一次应答里出现**；后台之后只显示末 4 位。换密钥后旧的立即作废。
- 库里是 AES-256-GCM 密文：每次随机 IV，附加数据是租户编号（密文搬到别的租户的行里解不开），格式 `v1.<IV>.<标签>.<密文>`。
- 加密用的密钥从新配置 `DATA_ENCRYPTION_KEY` 按用途（HKDF-SHA256，`info = nozomi.tenant-webhook-secret.v1`）派生；**不复用登录签名密钥**（ADR 0026「本期不做」里同样的理由：一把泄露不连累另一把，换登录密钥不会让所有供应商的 Webhook 失效）。
  以后乘客电话、邮箱的库级加密用同一把主密钥的另一个用途名派生。
- `DATA_ENCRYPTION_KEY` 只经 `packages/config` 读取：production 必须配置；其他环境不配时不能设置 Webhook（503 `WEBHOOK_ENCRYPTION_NOT_CONFIGURED`，`/health` 和 `pnpm config:check` 显示「数据加密密钥：未配置」）。
  服务器上由初始化脚本生成（32 字节十六进制），更早初始化的服务器由部署脚本补上；**不能修改**（改了库里的密文就解不开，供应商要各自换密钥；这种情况下投递记为 `WEBHOOK_SECRET_UNAVAILABLE`）。主密钥的轮换（多把并存）以后需要时新增 ADR。

**排队和投递**：

- 投递（`webhook_deliveries`）在改订单的同一个事务里插入；没设置、暂停、没订阅的不排。库里不存请求体（里面有乘客的姓名和电话），只存事件编号、类型、订单、少量事件信息；请求体在发送时按订单的当前内容现生成。
- 投递任务跑在 API 进程里（ADR 0022 的做法）：启动后 5 秒第一次，之后每 5 秒一轮，一轮最多 20 条、同时 4 条。只有服务进程启动它；测试直接调 `tick()`。
- 多实例：一个短事务里用 `for update skip locked` 取到期的投递并「租下」（下一次时间改成 60 秒后的租约到期时间），发送在事务之外，再一个短事务记结果。同一条同一时刻只有一个实例在发；
  进程在发送中途退出时租约到期后别的实例接着发，所以是「至少一次」，接收方按 `event_id` 去重。没有用咨询锁：`skip locked` 让每个实例各取各的，比一把全局锁吞吐高。
- 租约令牌（迁移 0028 的 `lease_token`）：每次租下都写一个新令牌，记结果（以及「不发了、记为最终失败」）时核对令牌并清掉。卡住超过租约、已被别的实例接手的那一方发完后对不上令牌，什么都不记（服务日志 `webhook.lease_lost`）；
  先核对令牌再记尝试，加上 `webhook_attempts (tenant_id, delivery_id, attempt_no)` 唯一，同一条推送不会出现两个「第 N 次」。
- **同一张订单按排队的先后依次投**：前一条没投完（含在等重试），后一条这一轮不取——接收方不会先收到「改派」再收到「新订单」。代价是一张单的推送卡住时，这张单后面的推送也等着（别的单不受影响）。

**失败重试（验收标准「推送失败自动重试」）**：

- 5 秒（含解析、连接、TLS、等应答）内没回 2xx 算失败：超时、连不上、TLS 失败、解析失败、非 2xx（记状态码）、**3xx 不跟随**（`WEBHOOK_REDIRECT_NOT_FOLLOWED`）。
- 第一次失败后按 **1 分钟、5 分钟、30 分钟、2 小时、6 小时、24 小时**重试（需求「销售端接口」的间隔，供应商沿用同一套），**最多 7 次**（约 32.6 小时）；第 7 次仍失败就是**最终失败**：
  状态 `failed`，供应商后台和运营后台的投递记录里都能筛出来（`?status=failed`）、看到每次尝试的时间、耗时、状态码、错误码；服务日志记一条 `webhook.delivery_failed`（错误级别）。完整的异常队列在 M4-02。
- **手动重推**：供应商管理员（`POST /tenant/v1/webhooks/deliveries/{id}/retry`）、运营后台（`POST /platform/v1/webhook-deliveries/{id}/retry`，`order.resend`：超级管理员、运营、客服；需求「人工介入：手工重发租户推送」）。
  最终失败的、在等重试的都可以：马上投一次（同一个 `event_id`），结果在应答里；已成功的 409；测试事件不能重推。写审计日志。
  **推送任务正在发这一条（租约中）时什么都不做**：不改时间、不收回租约、不写审计，应答 200、`result: "in_flight"`，页面提示「正在发送，稍后刷新查看结果」；发完的结果在推送记录里。
  租约已到期（进程中途退出）的视同等重试，重推时收回租约马上投。手动重推本身也先租下再发（同一套令牌），和推送任务互不重复。供应商和运营后台的重推是同一条路径。
  应答的 `result`：`sent` 发了一次（成败看投递状态）、`in_flight`、`not_configured`（设置已删除或暂停，没发，记为最终失败）。手动重推失败、次数已经用完时直接回到最终失败（不再自动排重试）。
- 每次尝试记一行 `webhook_attempts`：时间、耗时、状态码、错误码、目标主机、请求体的大小和 SHA-256。**不存请求体和应答的原文**（应答最多读 64 KB 就丢弃）。
- 设置删除或暂停后，已经排着的推送不再发，直接记为最终失败（`WEBHOOK_NOT_CONFIGURED`，不算一次尝试）。
- 发送测试事件：马上发一条 `webhook.test`，结果直接返回，记一条投递，不重试。

**防 SSRF**（接收地址是供应商自己填的）：

1. 保存时（`webhookUrlIssue`）：只认 `https://`；不能带账号密码、不能带 `#`；主机不能是 IP 写法的内网 / 回环 / 链路本地 / 元数据 / 组播 / 广播 / 文档 / 保留地址，不能是 `localhost`、`.local`、`.internal` 这类只在内网解析的名字或没有点的单标签名字，也不能是十进制 / 八进制 / 十六进制写的「数字地址」。
2. 发送前：解析域名，**解析到的每一个地址**都必须是公网地址（`ipAddressClass` 纯函数，含 IPv4 映射的 IPv6、NAT64、6to4 里嵌着的 IPv4；AWS 的 `fd00:ec2::254`、`169.254.169.254` 都拒绝），有一个不是就整体拒绝（`WEBHOOK_TARGET_FORBIDDEN`）。
3. 连接时只连第 2 步检查过的那个地址（自己提供 `lookup`），不解析第二次——防 DNS 重绑定；TLS 证书仍按域名校验。
4. 不跟随重定向；总时限 5 秒；应答最多读 64 KB；不复用连接。
- 集成测试的接收方是本机的假服务器：测试给发送器打开 `allowLocalTargets`（只放行 http 和回环地址，其余检查不变），服务进程从不打开；SSRF 的检查本身在单元测试里逐项测，另有一个集成测试用真实的发送器验证「解析到内网地址就拒绝」。

## 待定事项（需求没写清；先按推荐做了）

| # | 问题 | 选的方案 | 理由 |
| --- | --- | --- | --- |
| 1 | 供应商的 Webhook 重试间隔和次数 | 沿用需求给销售端的 1–5–30 分钟、2–6–24 小时，共 7 次 | 需求只给了一套；供应商也是系统对接，同样的节奏够用 |
| 2 | 签名密钥存哈希还是加密 | 加密（AES-256-GCM），新配置 `DATA_ENCRYPTION_KEY`，服务器自动生成 | 签名要原文；不复用登录签名密钥 |
| 3 | 照片存哪里 | PostgreSQL | 随数据库备份、多实例共用、和证据同一个事务；量不大 |
| 4 | 证据不全能不能提交 no-show | 不能（逐项列出还差什么） | 不全的必然被驳回；现场提示司机补齐 |
| 5 | 冲突是禁止还是提示 | 提示，确认后可派 | 需求原文「提示冲突」 |
| 6 | 改派后旧司机的链接 | 立即作废 | 避免两个司机同时操作一张单 |
| 7 | 接送机、点对点的「用车结束」 | 按用车时间算（没有约定时长），链接用车后 24 小时失效 | 需求「链接用车后 24 小时失效」 |
| 8 | 落地时间报得多早算填错 | 比计划到达早 3 小时以上拒绝 | 航班提前到达一般不超过 1 小时，留足余量 |
