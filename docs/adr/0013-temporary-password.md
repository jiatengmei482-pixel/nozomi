# ADR 0013：临时密码与首次登录强制修改密码

- 状态：已采纳（2026-10-07，M0-12）。是对 ADR 0008 的补充，不改变其中的决定。
- 补充了 ADR 0008 的两处：
  - 「邀请」一节里「平台上第一个账号只能用命令行创建……密码在终端里交互输入或从标准输入读」——现在多一种方式：让命令生成临时密码。
  - 「密码找回」一节里「最后一个超级管理员忘了密码」——`admin:reset-password` 同样多一种方式。原来的两种输入方式都还在，不带新开关时行为完全不变。

## 背景

负责人不在服务器前、由别人代为执行 `pnpm admin:create` 时，原来的做法要求执行的人替负责人想一个密码，这个密码之后就一直是负责人的密码。需要一种方式：执行的人拿不到长期有效的密码，本人第一次登录就必须换掉它。

## 决定

### 「必须先修改密码」标记

- `platform_users`、`tenant_users` 各加一列 `must_change_password`（非空，默认 false，迁移 0006）。数据库约束：没设过密码的账号（待激活）不能带这个标记。
- 标记什么时候变：

  | 操作 | 标记 |
  | --- | --- |
  | 命令行带 `--temporary-password` 创建 / 重设超级管理员 | true |
  | 命令行不带开关创建 / 重设（操作人自己输入的密码） | false |
  | 本人 `auth/change-password` 成功 | false |
  | 本人凭邀请链接、重置链接设置密码 | false |
  | 发出重置链接、停用、启用、退出登录 | 不变 |

- 两张表都有这一列、接口两侧都强制，但**本期只有平台超级管理员有生成临时密码的途径**。平台给租户用户发邀请 / 重置走的是令牌链接（ADR 0008），本来就由本人自己设密码，不需要临时密码。租户一侧的标记是为以后（例如平台代租户重置）留的，现在只能通过直接改库出现；强制逻辑两侧都有测试。
- 权限（ADR 0010）不用调整：三个权限角色的授权都是表级的，`nozomi_platform` 对两张表、`nozomi_app` 对 `tenant_users` 已有读写；`nozomi_preauth` 仍然读不到这两张表。

### 临时密码长什么样、怎么生成

- 规则在 `packages/domain/src/temporary-password.ts`（纯函数，随机源由调用方传入）：4 组、每组 5 个字符、连字符隔开，如 `aB3de-Fg4hJ-k5LmN-6pQrS`。字符取自去掉了易混字符（`0 O o 1 l I i`）的小写、大写、数字共 55 个，20 个随机字符约 115 比特。
- 一定同时含小写、大写、数字（连字符是第四类），并且通过给这个邮箱的全部现有密码强度规则（`checkPasswordStrength`，含「不含邮箱名」）。不满足的候选整个丢弃重抽，不做会破坏均匀分布的修补。
- 命令行用 `crypto.randomInt`（密码学安全、没有取模偏差）作随机源。

### 命令行

- `pnpm admin:create --email … --name … --temporary-password`、`pnpm admin:reset-password --email … --temporary-password`。
- 带开关时不读标准输入（管道里送进来的内容被忽略，不会成为密码）。开关不接受值；`--password` 和位置参数照旧是用法错误。
- 账号写进数据库**之后**才显示临时密码。只写标准输出、只写一次、单独占一行，行首固定是 `临时密码：`，后面紧跟密码、没有别的内容：

  ```
  已创建超级管理员：owner@example.com（编号 …）
  下面这一行是临时密码，只显示这一次，请现在就交给本人：
  临时密码：aB3de-Fg4hJ-k5LmN-6pQrS
  用它登录后必须先修改密码，改完之前不能使用其他功能；改完后这个临时密码作废。
  ```

- 标准错误、审计日志、应用日志里都没有它；数据库只存哈希。失败时（邮箱已被使用、不是在用的超级管理员、参数不对）标准输出为空，生成了但没用上的临时密码不会显示。
- `admin:reset-password --temporary-password` 和不带开关时一样让该账号的全部会话失效。
- 审计：`create` 的 `after` 多一项 `temporary_password: true`；`reset_password` 的 `after` 是 `{ temporary_password: true }`。不带开关时这两条记录和以前一模一样（没有这一项）。

### 接口

- 登录照常成功。登录应答和 `auth/me` 的**顶层**多一个必有的布尔字段 `must_change_password`。它不在账号对象（`PlatformUser` / `TenantUser`）里，所以不会出现在账号列表、邀请 / 重置应答等别人能看到的地方——「谁还在用临时密码」只有本人知道。访问令牌里也没有它，每个请求以数据库为准。
- 标记为 true 时，需要登录的接口里只有三个可用：`GET auth/me`、`POST auth/change-password`、`POST auth/logout`。其余一律 403，错误码 `PASSWORD_CHANGE_REQUIRED`。平台和租户两侧规则相同。
- 判断顺序：401（没登录、会话失效、账号停用）→ 403 `PASSWORD_CHANGE_REQUIRED` → 403 `FORBIDDEN`（角色权限）→ 参数校验。也就是说被拦的请求不暴露「你本来有没有这个权限」，也不产生任何效果。
- `auth/change-password` 成功后标记清除，**当前令牌继续可用**，不用重新登录；该账号的其他会话失效（原有行为），临时密码随即作废。新密码不能和当前（临时）密码相同——原有的 `PASSWORD_UNCHANGED` 规则已覆盖，补了测试。
- 强制改密完成沿用原有的 `change_password` 审计记录。

### 在哪里强制

- 在鉴权函数里统一判断（`authenticatePlatform` / `authenticateTenant`），不靠每个接口自己记得。规则本身是 `packages/domain` 里的纯函数 `passwordChangeRequiredFirst`。
- 鉴权函数的默认用途是 `general`（被拦）；只有三个接口显式声明 `self_service`（路由文件里的 `authenticateSelfService`）。**新接口不用做任何事就默认被拦**；要放行必须显式写出来。
- `password-change-required.itest.ts` 遍历全部已注册的路由：每个路由要么在 openapi.yaml 里声明为不需要登录，要么是那三个接口，要么必须返回 403 `PASSWORD_CHANGE_REQUIRED`。以后新增的接口如果先做了参数校验再鉴权、或者忘了鉴权却没在定义里标成公开，这个测试会失败。不在 `/platform/v1`、`/tenant/v1` 下的需要登录的新入口（例如以后的 API 密钥）也会让它失败，逼着当时做出明确决定。

## 理由

- **为什么这次可以把密码打印出来**：ADR 0008 不在终端打印重置令牌，是因为它会留在终端回滚和日志里。临时密码同样会留在那里，但它只能用来做一件事——改成一个只有本人知道的密码；改完即作废。在此之前账号什么功能都用不了，所以留在回滚里的临时密码泄露后，后果限于「别人抢先改了密码」，本人会立刻发现登录不上，再用 `admin:reset-password` 恢复（会话全部失效，有审计）。需要更谨慎的场合，原来的交互输入方式仍然可用。
- **为什么是顶层字段而不是账号对象的字段**：账号对象会出现在列表和别人的操作应答里；这个标记只对本人有意义，放在账号对象里等于向所有能看账号列表的人公开谁的密码还是临时的。
- **为什么是 403 而不是 401**：令牌是有效的，重新登录解决不了问题；前端要据此跳到改密页而不是登录页。用单独的错误码而不是 `FORBIDDEN`，前端不用猜原因。
- **为什么不单独签发一种「只能改密码」的令牌**：现有模型是「令牌只是会话的凭证，每个请求回数据库核对」（ADR 0008）。标记放在账号上、每次核对，改完密码当前令牌立即恢复正常，也不会出现「标记已经清了但手里还是受限令牌」的状态。
- **为什么 `auth/me` 放行**：前端刷新页面后要靠它知道当前是谁、是否仍需改密码。它只返回本人信息。

## 已知限制

- 临时密码没有单独的有效期：一直有效到本人改掉或被再次重设。创建后长期没人登录的账号，临时密码也就一直有效；审计里能看到哪些账号是用临时密码创建 / 重设的。需要有效期时再新增 ADR。
- 临时密码会留在执行命令的终端回滚里（见「理由」第一条）。把命令的标准输出重定向到文件时，文件里也会有，由执行的人负责删除。
- 强制只发生在接口层。前端要在 `must_change_password` 为 true 时只显示改密页（M0-12 的前端部分）。

## 验证

- `packages/domain/src/temporary-password.test.ts`：形状、强度、不含易混字符、不重复、坏随机源不会给出弱密码或死循环；放行规则。
- `apps/api/src/password-change-required.itest.ts`：遍历全部路由；平台和租户两侧的登录、拦截（且不产生效果）、改密、恢复、临时密码作废；判断顺序；邀请 / 重置链接清标记；标记不出现在列表、审计、别人的应答里；租户隔离不受影响；数据库约束。
- `apps/api/src/cli/admin-temporary-password.itest.ts`：真的启动两个命令，标准输出和标准错误分开核对；拿打印出来的临时密码走完「登录 → 被拦 → 改密 → 恢复 → 旧密码失效」。
- `apps/api/src/must-change-password-upgrade.itest.ts`：停在迁移 0005 且已有账号的库升级到 0006；三个权限角色对新列的读写情况。
- `apps/api/src/schema-structure.itest.ts`：新列的形状和约束，授权清单不变。
