# ADR 0054：运营审核 no-show 时看得到证据

- 状态：已采纳（2026-11-01，M4-20）
- 补充 ADR 0027（no-show 证据）、ADR 0034（工单）、ADR 0052（乘客联系方式打码）。
- 编号说明：其他分支已用到 ADR 0053，这里用 0054。本任务没有迁移。

## 背景

验收报告 M3-06 第二轮缺陷 1：运营的订单详情和工单详情看不到 5 项证据、照片、联系记录、到达距离、落地时间，工单只写「已在提交时核对，请审核」，运营等于盲判。需求：《平台运营端》「订单详情一页看全」「免费等待与 no-show」。

## 决定

### 显示

- 组件 `NoShowEvidenceSection`，运营订单详情和工单详情共用。显示 5 项逐条结果和背后的事实、到达时间和距离、免费等待时段、落地时间和来源、联系记录、照片、司机定位记录（折叠）。缺什么写明，不留空白。
- 工单详情放在「处理」下面，和判定按钮同一栏。判定对话框会盖住页面，所以对话框里另有 5 项简表。对 no-show 审核的申诉工单同样显示。
- 数据来自现有的订单详情接口，没有新接口。

### 5 项的结果以提交时存下的为准

页面不重新判断。5 项是后端提交时核对后存下的，里面没有的项写「没有核对记录」，不当作满足。提交之后落地时间变了（客人后来才点「我已落地」），页面提醒「核对结果是按提交那一刻算的」，并写出现在的免费等待。**是否据此改判由运营决定**，系统不自动改。

### 权限和数据范围

沿用现有规则：看工单 `ticket.read`，看证据 `order.read` 和订单的数据范围。工单页只有 `ticket.read` 的员工不会多看到东西，页面写明「没有查看订单的权限」。范围外写明看不到。

### 证据没看到就不能判定（产品决定，协调人定：拦截）

原来只有页面提示，看不到证据的员工仍可以判定，等于盲判。判定直接决定客人退不退款、供应商拿不拿钱，所以拦下：

- **后端强制**：判定 no-show 审核和对它的申诉（`ticketDecisionNeedsEvidence`）另外要 `order.read`，没有的 403（`details.required` = `order.read`）；订单不在数据范围的 404。没判定就关掉这样的申诉同样要 `order.read`，因为关掉等于驳回。其他类型的工单不变。
- **权限矩阵**：`ticket.manage` 的说明里写明（`access.ts`）。内置角色（超级管理员、运营、客服）都同时有两项，不受影响；只有只勾「工单 · 编辑」没勾「订单 · 查看」的自建角色受影响。
- **页面**：没有权限、范围外的员工看不到「判定」按钮（申诉工单的「关闭」也不显示），写明原因和可以交给同事。证据还在加载时对话框写「加载中」，失败时写明并给「重新加载」，两种情况确认按钮都不能点，直到证据加载出来。**不提供「未看证据也判」的选项。**
- **页面只拦「证据数据没加载出来」**：单张照片取失败不拦，5 项结果旁边提醒，每张有重新取的按钮。理由：照片解不出来时（HEIC）运营可以下载原图看，不应该让一张坏照片卡住审核的 24 小时时效。
- **代价**：证据接口故障时不能判定，审核可能超时。这是偏向不误判的方向；24 小时时效里接口恢复即可继续。

### 照片和审计

- 走现有文件接口 `GET /platform/v1/orders/{id}/files/{fileId}`（带令牌取回，没有公开地址）。这个接口原来没有审计，现在每次取到照片记一条（`order` / `view_evidence_file`，记订单号、照片编号、种类，不含内容，`tenant_id` 为空，供应商看不到）。
- 审计和取照片在同一个事务里，记不下来就不给照片。没有权限、范围外、不存在的不记。
- **取照片的时机（保守选择，减少看到个人信息的机会）**：
  - 提交过 no-show 的单：举牌、到达屏打开页面就取，判定要用。
  - 没提交 no-show 的单：不是在审核，点了才取，不让日常打开订单详情就产生审计和访问。
  - 联系截图、票据：一律点了才取，截图可能带着客人的联系方式。页面写明查看会记入操作记录。
- 只记运营的访问。供应商看自己的照片不记（不是平台访问，和原来一样）。
- HEIC 很多浏览器显示不了：解不出来时写明并给下载链接，不让运营以为没有照片。

### 照片画在 canvas 上，不放宽内容安全策略

端到端测试发现：原来供应商后台用 `<img src="blob:…">` 显示照片，而全站内容安全策略的 `img-src` 不放行 `blob:`（`deploy-web.test.ts` 明确禁止），所以**任何环境里照片都显示不出来**，供应商后台也一样。

- 决定：取回图片后用 `createImageBitmap` 解码，画到 `canvas`（`role="img"`，带说明文字）。不需要改内容安全策略，也不产生公开地址。供应商后台用同一个组件，一起修好。下载原图仍是 `blob:` 链接（下载不受 `img-src` 管）。
- 没选放行 `blob:`：策略是全站的（官网付款页也在内），为了这一处放宽所有页面不划算，而且改了之后要新增 ADR 推翻原来的约束。
- 没选带签名的图片地址：地址一旦外传就成了公开地址，也绕过了「每次访问记审计」。
- 缩略图改成完整显示（`object-fit: contain`），不裁切，判定要看到全图。
- **极端尺寸**：canvas 有尺寸上限（Chrome 单边 32767），超过时什么都画不出来也不报错。所以解码后最长边超过 2048 的按比例缩小再画，并释放原图的解码内存；画完缩成一小块检查有没有不透明的像素。解不出来、缩不了、画不出来的都写「显示不了」并给下载链接（原图不缩）。

### 乘客联系方式

- 接口里的乘客信息继续打码（ADR 0052），证据区不提供查看入口。
- **新增**：司机手写的联系备注现在显示在运营页面上，可能抄了客人的电话、邮箱、姓名。订单详情接口返回给运营时打码（`maskContactsInText`）。没有查看全文的入口，要全文可以点乘客的「查看联系方式」对照。供应商看到的仍是原文（付款后本来就看得到）。

打码规则：

- **电话**：7 位以上的数字串留末 4 位。分隔认空白（含全角）、括号、点、斜杠、各种连字符（U+2010、U+2011、U+2013、U+2014、U+2212、U+FF0D、长音 ー ｰ）。不认冒号，所以时间不会连起来；连写的日期可能被打码，宁可多打。
- **邮箱**：`@` 和全角 `＠`；`/` 相连的多个地址分别打码。
- **姓名**（不区分大小写，忽略半角和全角空格）：

| 写法 | 什么时候打码 |
| --- | --- |
| 全名 | 满足下面的长度规则就打码，空格有无、段的顺序不影响（顺序反过来时按各段打） |
| 姓名的一段（只写姓、只写名） | 拉丁字母至少 3 个字母，且前后不连着字母（否则 Li 会打到 line 里）；中日文至少 2 个字 |
| 1 个字的段（姓「王」） | **只在紧跟敬称时**：先生、女士、小姐、太太、老师、さん、さま、様、氏、君、ちゃん。否则「王府井」「田里」都会被打 |
| 没有空格的中日文名（3 个字以上，分不出姓和名） | 后 2 个字按名打码；第 1 个字、前 2 个字只在紧跟敬称时打码 |

少打和多打都有代价。名字里的 2 个字恰好是普通词时（姓名「王东京」和地名「东京」）会多打，只影响备注的可读性；短于上述长度的拉丁段（如 Li、Wu）不打，会漏。

**还没解决**：`maskContactsInText` 只认这几种形式，LINE 编号等认不出；联系截图和照片里的内容无法打码，只能靠点了才取和审计。

### 接口定义修正

`no_show_claim.status` 在 OpenAPI 里只写了 `pending_review`，实际审核后还有 `approved`、`rejected`，审核过的订单详情不符合定义。一起修了。

## 本期不做

- 司机轨迹只有文字列表，没有地图。
- 没提交 no-show 的单不做「现在满足几项」的试算（运营要判的都已提交）。
