# ADR 0097：接机免费等待按航班定——国际 90、国内 60，下单时按航班锁定

- 状态：**已采纳**（2026-11-15：第五节 Q1–Q5 由监工替业主确认按推荐，Q2 补充一条文案）。实施任务 M9E-28；按航班号查航班数据另立 M9E-29。
- 依据：业主反馈（M9E-27 第 2 部分）、监工替业主 2026-11-15 的决定：
  1. 按航班定：客人填了航班号时，按国际 / 国内航班给 90 / 60 分钟；
  2. 没填航班号或判断不出时，文案写「国际线最长 90 分钟、国内线最长 60 分钟」；
  3. 下单确认时按航班锁定；
  4. 订单记下最终给的分钟数，供应商看得到。
- 与 #253（M9E-27）的关系：#253 改的是「还没报价时不写死 60」的前端提示（按认出的机场写 90 / 60，认不出不写分钟数）。本篇实施后，接机还不知道航班类型时一律写「国际线最长 X 分钟、国内线最长 Y 分钟」，#253 的那段取值由本篇的取代（M9E-28 的 PR 基于 #253）。

## 一、现状（2026-11-15 main，本篇实施前）

- **没有航班数据来源**。代码里没有查航班的接口、没有航班时刻表，也没有配置航班服务的密钥（`packages/config`、`apps/api/src/services` 里都没有）。航班号只做格式规范化（`packages/domain/src/orders.ts` 的 `normalizeFlightNo`）后存进订单；实际落地时间靠客人或司机上报（ADR 0027、`driver-trip.ts` 的 `landingChange`）。
- 国际 / 国内只看**机场**的主数据字段 `places.flight_scope`（international / domestic / mixed / 空），只用于供应商保存服务规则时的最少值校验（`minimumFreeWaitMinutes`：机场只走国际线的最少 90，其他最少 60）和前台还没报价时的提示（#253）。
- 实际作数的是**商品自己设的**分钟数：报价时 `quote.ts` 直接取 `product.serviceRules.freeWait.pickup`，下单时 `services/orders.ts` 抄进 `orders.free_wait_minutes`。平台不会按航班把它往上补。
- `products.ts` 里 `minimumFreeWaitMinutes` 的注释说「报价时再按实际航班取 90 和供应商设的值里较大的」，但代码里**没有实现**。
- 机场主数据本身也不准：成田标的是国际线，但成田也有国内航班；羽田在测试环境没标。

## 二、规则

最终分钟数 = 按航班类型取下限，再和供应商设的值取较大的（`packages/domain/src/arrival-free-wait.ts` 的 `lockArrivalFreeWait`）：

| 航班类型 | 最终分钟数 |
| --- | --- |
| 国际航班 | max(供应商设的, 90) |
| 国内航班 | max(供应商设的, 60) |
| 航班类型未确认（Q2） | max(供应商设的, 60)，订单标「航班类型未确认」 |
| 供应商设了「不限时」 | 不限时（不压低） |

- 只用于**接机**：接送机商品的机场接机，以及认出机场、改用点对点商品报价、带了航班号的接机单（Q5，`isFlightArrival`）。接站、送机、其他点对点、包车不变。
- 报价阶段（还不知道航班）不改价格、不改报价快照里商品自己的值。给客人看的文案：选了航班类型写那一种的分钟数；没选、判断不出写「国际线最长 X 分钟、国内线最长 Y 分钟」（X = max(商品, 90)、Y = max(商品, 60)；还没报价时按 90 / 60）；商品不限时写不限时。

## 三、下单时锁定动到的字段

- `orders.free_wait_minutes`（已有）：接机存第二节算出的**最终值**，不再直接抄商品的值。履约（`freeWaitWindow`）、no-show 证据、付费等待都读它，不用改。
- 新增（迁移 **0540**；原定 0480，合并时 main 已到 0520，按迁移顺序检查改成 0540）：
  - `orders.flight_kind`：客人选的 `international` / `domestic`；没选、不是接机为 null；
  - `orders.free_wait_basis`（jsonb）：锁定依据 `{ flight_kind, base, floor_minutes }`——按哪种航班取的下限（null = 未确认）、商品自己设的值（`base`，取下限前的底数）、取的下限。以前的单、不是接机的单为 null，不回填。
  - 两列加进 `orders_tenant_columns`（供应商不能改）。订单没有列出 `free_wait_minutes` 的视图，不用重建。
- 报价快照 `settlement.freeWait` 不改。下单时在 `services/orders.ts` 的 `createOrder` 里算出最终值。
- 接口：下单（`/sales/v1/orders`、`/site/v1/orders`）和改单（`PATCH` 订单）多一个可选的 `flight_kind`；订单视图（渠道、官网、供应商、运营、司机）多 `flight_kind`、`free_wait_basis`。点对点单可以带 `flight_no`（带了就按接机定免费等待，Q5）。

## 四、给谁看、在哪里看

- 客人：新预订页第 3 步在航班号下面选「航班类型」（必选，每个选项后面写这种航班免费等多久）；第 1 步接机提示、第 2 步「一口价包含」、旧下单页车型列表在没选之前写「国际线最长 X 分钟、国内线最长 Y 分钟」；第 4 步核对写航班类型和最终分钟数；订单页「免费等待」后面注明航班类型；订单页改单可以改航班类型。
- 供应商后台订单详情「免费等待」：如「90 分钟（国际航班；商品设 60 分钟，按平台规定补到 90 分钟）」「60 分钟（航班类型未确认，按国内线）」。
- 司机行程页：同一写法。
- 渠道（OTA）：订单里的 `free_wait_minutes`、`flight_kind`、`free_wait_basis`；报价里的 `free_wait_minutes` 仍是商品设的值，接口说明里写清楚。

## 五、确认结果（2026-11-15 监工确认按推荐）

- **Q1 怎么从航班号判断国际 / 国内**——**2026-11-15 监工确认按推荐**：先做 B，客人填航班号时选「国际航班 / 国内航班」（官网必选；渠道接口可以不给，按 Q2）。A（接航班数据服务，选服务商、算费用要业主拍板）另立任务 **M9E-29**。C（按号段推断）不做。
  - 当时写的「机场只走国内线的不让选国际」没有做：机场主数据的航线类型本身不准（见第一节），按客人选的为准。
- **Q2 判断不出时锁多少**——**2026-11-15 监工确认按推荐**：锁 max(商品值, 60)，订单标「航班类型未确认」。**补充（监工 2026-11-15）**：判断不出时给客人看的文案也写「国际线最长 90 分钟、国内线最长 60 分钟」，和没填航班号时一致。
- **Q3 下单后改航班号 / 航班类型**——**2026-11-15 监工确认按推荐**：派单前（以供应商同意的那一刻为准，见五之二 S1；已确认、还没派司机）改的，供应商同意生效时重新锁定，`order.changed` 推送和通知里带 `free_wait_minutes: { before, after }`；派单后改的，航班号和航班类型照改，免费等待和锁定依据不变。改航班号、航班类型都要供应商同意（和以前改航班号一样）。
- **Q4 已有订单**——**2026-11-15 监工确认按推荐**：不回头改。**待办（平台不代发）**：「国际国内都有」的机场上设了 60 的商品，接国际航班时要多等 30 分钟，这是供应商义务的变化，由运营另行通知供应商；本次不发系统通知。
- **Q5 改用点对点商品报价的接机订单**——**2026-11-15 监工确认按推荐**：也按 90 / 60。这种单的航班号、航班类型作为正式字段提交（以前航班号写在备注里）；改用点对点商品报价的送机仍写进备注。

## 五之二、独立审查后的补充（2026-11-15 按推荐，监工转达；PR #255 审查意见）

- **供应商邮件写明免费等待改了多少（必须改 1）**：派单前改航班重新锁定时，`order.changed` 给供应商的邮件在「改动的内容」后面写「免费等待 60 → 90 分钟（按客人的航班重新锁定，请按新的时长安排司机等候）」（变量 `free_wait_change`，可为空的后缀）。供应商邮件只有中文模板，没有日文、英文版本，所以只改中文这一份。
- **S1「派单前」按什么时候算——2026-11-15 按推荐**：以供应商**同意、改单生效的那一刻**有没有派司机为准。供应商审批页在这条改单下面提示「同意后免费等待 60 → 90 分钟」或「已派车：同意后免费等待不变」，供应商同意前就知道后果。
- **S2 以前的单——2026-11-15 按推荐**：M9E-28 之前下的单（没有锁定依据），派单前改航班号 / 航班类型也按新规则重新锁定、补写依据。改航班是新发生的事，不算回头改旧单（Q4 说的是不主动批量改已有订单）。
- **S3 点对点接机清掉航班号——2026-11-15 按推荐**：派单前清掉航班号，单子不再按航班定：免费等待回到商品自己设的值，依据清空，和清空的航班类型对得上。
- **S4 点对点接机在官网订单页改航班——2026-11-15 按推荐**：下单时带了航班号的点对点单，客人在订单页也能改航班号和航班类型（以前只有接送机能改）。
- **S5 改单表单的提示——2026-11-15 按推荐**：航班类型选项后面的分钟数按商品自己设的值算 max（商品设 120 就写 120）；已派车的单注明「已派车，免费等待不再变化」。
- **S6 派单后客人订单页——2026-11-15 按推荐**：写「按派单时的国际航班锁定 90 分钟」（未确认写「按派单时航班类型未确认（按国内线）锁定 60 分钟」），客人派单后改了航班类型也不会误以为按新选的算。
- **S7 商品没设免费等待——2026-11-15 按推荐**：供应商看到的依据写「商品没设，按平台规定补到 N 分钟」，不写「商品设 0 分钟」。
- **S8 渠道接入说明——2026-11-15 按推荐**：OpenAPI 下单接口（`createSalesOrder`）的说明里强调「点对点单填了 `flight_no` 就表示从机场接人，会按接机补到 60 / 90；送机、市内点对点不要填，送机的航班号写在 `notes` 里」。

## 六、`products.ts` 的注释

`minimumFreeWaitMinutes` 上面的注释改为：供应商保存服务规则时每一项最少要设多少（接机：机场只走国际线的 90，其他 60；接站 30；送机 / 送站、点对点 15；包车 0）；这只是保存时的下限，接机客人实际得到的分钟数在下单时按航班定（`lockArrivalFreeWait`）。和实现在同一个 PR 里改。
