# ADR 0097：接机免费等待按航班定——国际 90、国内 60，下单时按航班锁定

- 状态：**草案**（2026-11-15）。第五节的待确认问题定下来以后才开工（实施任务 M9E-28）。
- 依据：业主反馈（M9E-27 第 2 部分）、监工替业主 2026-11-15 的决定：
  1. 按航班定：客人填了航班号时，按国际 / 国内航班给 90 / 60 分钟；
  2. 没填航班号或判断不出时，文案写「国际线最长 90 分钟、国内线最长 60 分钟」；
  3. 下单确认时按航班锁定；
  4. 订单记下最终给的分钟数，供应商看得到。
- 与 #253（M9E-27）的关系：#253 只改「还没报价时不写死 60」的前端提示，不依赖本篇，单独合并。

## 一、现状（2026-11-15 main）

- **没有航班数据来源**。代码里没有查航班的接口、没有航班时刻表，也没有配置航班服务的密钥（`packages/config`、`apps/api/src/services` 里都没有）。航班号只做格式规范化（`packages/domain/src/orders.ts` 的 `normalizeFlightNo`）后存进订单；实际落地时间靠客人或司机上报（ADR 0027、`driver-trip.ts` 的 `landingChange`）。
- 国际 / 国内现在只看**机场**的主数据字段 `places.flight_scope`（international / domestic / mixed / 空）。它只用于：
  - 供应商保存服务规则时的最少值校验（`minimumFreeWaitMinutes`）：机场只走国际线的最少 90，其他最少 60；
  - 前台还没报价时的提示（#253）。
- 实际作数的是**商品自己设的**分钟数：报价时 `quote.ts:959` 直接取 `product.serviceRules.freeWait.pickup`，下单时 `orders.ts:332` 抄进 `orders.free_wait_minutes`。平台不会按航班把它往上补。
- `products.ts:200–207` 的注释说「报价时再按实际航班取 90 和供应商设的值里较大的」，但代码里**没有实现**。
- 机场主数据本身也不准：成田标的是国际线，但成田也有国内航班；羽田在测试环境没标。

## 二、规则（推荐，监工已建议）

最终分钟数 = 按航班类型取下限，再和供应商设的值取较大的：

| 航班类型 | 最终分钟数 |
| --- | --- |
| 国际航班 | max(供应商设的, 90) |
| 国内航班 | max(供应商设的, 60) |
| 判断不出 | 见第五节 Q2 |
| 供应商设了「不限时」 | 不限时（不压低） |

- 只用于**接机**（行程是接机，含 M8-33「认出机场、改用点对点商品报价」的订单，见第五节 Q5）。接站、送机、点对点、包车不变。
- 报价阶段（还不知道航班）不改价格、不改报价快照里商品自己的值；页面文案按决定第 2 条写「国际线最长 90 分钟、国内线最长 60 分钟」。如果商品设得比下限还长，文案写商品的值。

## 三、下单时锁定会动到的字段

- `orders.free_wait_minutes`（已有）：改为存第二节算出的**最终值**，不再直接抄商品的值。履约（`freeWaitWindow`）、no-show 证据、付费等待都已经读它，不用改。
- 新增 `orders.flight_kind`（`international` / `domestic` / 空 = 判断不出）和 `orders.free_wait_basis`（jsonb：商品设的值、按哪种航班取的下限、判断依据），这样供应商和客服能看到「为什么是 90」。迁移编号 **0480**（main 已到 0460，#249 占了 0470；其他开着的 PR 都没有迁移）。0370 之后订单相关的视图如果列出了 `free_wait_minutes`，也要在同一个迁移里重建并加上新列。
- 报价快照 `settlement.freeWait` 不改（报价时还不知道航班）。下单时在 `services/orders.ts:297–332` 算出最终值。
- 下单以后改航班号（`order-changes.ts:177–184`）：见第五节 Q3。

## 四、供应商在哪里看到

- 供应商后台订单详情 `apps/web/src/pages/orders/OrderPages.tsx:453`「免费等待」：改成「90 分钟（国际航班；商品设 60）」这种写法。
- 司机行程页 `apps/web/src/pages/driver/DriverTripPage.tsx:361`：已经按 `free_wait_minutes` 显示，值变了以后跟着变。
- 派单列表、平台订单详情 `PlatformOrderPages.tsx`、供应商 webhook 的订单内容：同一个字段。
- 销售接口（OTA）`routes/sales.ts:89` 报价里的 `free_wait_minutes`：报价阶段不改，接口文档里注明「下单时按航班可能补到 90 / 60」。

## 五、待确认（定下来才开工）

- **Q1 怎么从航班号判断国际 / 国内？** 现在没有数据来源，三种做法：
  - A 接入航班数据服务（例如 AeroDataBox、FlightAware AeroAPI、Cirium）。按航班号和日期查出发、到达机场，再比国家：最准，但要选服务商、要付费，密钥由业主自己填进设置页，还要处理查不到、超时的情况。
  - B 客人填航班号时同时选「国际航班 / 国内航班」（必选）。不用外部数据、马上能做，但靠客人自己选；选成国际航班能多等 30 分钟，有选错或故意选错的风险。机场只走国内线的不让选国际。
  - C 按航空公司代码和航班号段推断：日本各航空公司的号段不统一，**不推荐**。
  - 推荐：先做 B，A 另立任务（选服务商、算费用要业主拍板）。
- **Q2 下单时判断不出（OTA 订单没给航班号、A 方案查不到）锁多少？** 推荐 max(商品值, 60)，订单标「航班类型未确认」，司机按航班实际情况可以多等、提交付费等待时客服核对；另一个选择是按 90 锁（对客人宽、供应商吃亏）。
- **Q3 下单后客人改航班号**（`order-changes`）：重新判断、重新锁定，还是保持下单时的值？推荐派单前改的重新锁定并通知供应商，派单后改的保持不变。
- **Q4 已有订单**不回头改（推荐）。另外，国际航班取 max(商品值, 90) 会让「国际国内都有」机场上设了 60 的商品，接国际航班时要多等 30 分钟，这是供应商义务的变化：要不要先通知供应商？
- **Q5 改用点对点商品报价的接机订单**（M8-33：订单是点对点，航班号写在备注里）：也按本规则给 90 / 60 吗？推荐给（行程本身是接机），这样就需要 B 方案在这种订单里也收航班类型。

## 六、`products.ts` 的注释怎么改

`minimumFreeWaitMinutes` 上面的注释（`packages/domain/src/products.ts:200–207`）改成：

> 供应商保存服务规则时，接机免费等待最少要设多少（按商品所在机场：只走国际线的 90，其他 60；接站 30；送机 / 送站、点对点 15；包车 0）。
> 这只是保存时的下限。客人实际得到的分钟数在下单时按航班定：国际航班 max(商品值, 90)、国内航班 max(商品值, 60)（ADR 0097、M9E-28）。

开工以前不改注释，免得注释说的和代码做的又对不上。
