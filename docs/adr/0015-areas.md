# ADR 0015：区域——图形怎么存和判断、幂等键、地图底图与内容安全策略

- 状态：已采纳（2026-10-08，M1-02）
- 修订 ADR 0002 中「形状以 GeoJSON 多边形或『中心点 + 半径』存」「圆按真圆判断」两点（见「圆」一节）；ADR 0002 的其余内容（区域判断在应用层、暂不依赖 PostGIS、存外接矩形粗筛）不变。
- 修订 ADR 0007「前端接入部署」和 ADR 0011 中「图片只认同源」这一条（见「地图底图」一节）；其余安全响应头不变。

## 背景

M1-02 是第一个租户业务功能：供应商在后台画区域（营运区 + 禁行区），之后的商品、价格规则、报价都引用它。需求见《用车报价服务平台》「1. 区域管理」；页面规范见 `docs/design/pages/tenant-areas.md`。下面是落地时定下的事。

## 决定

### 表

- `areas`（区域）和 `area_polygons`（一块图形一行），迁移 0011。都是租户表：带 `tenant_id`、主键和索引以它开头、开行级安全、策略只放行当前租户（ADR 0009、ADR 0010）。
- 只授权给租户角色 `nozomi_app`（增删改查）。**平台角色本期没有任何权限**：运营后台还没有看区域的页面；等有了（排查报价问题时要看）再按需要给只读并加一条写明 `to nozomi_platform` 的只读策略。
- 区域可以**真的删除**（和主数据「只停用不删除」不同）：它是供应商自己的配置，删除前的完整内容记在审计日志里。被已上架商品引用时不能删、不能停用（409 `AREA_IN_USE`）——这条检查随商品（M1-03）一起加，现在没有商品，不会触发。
- 没有做需求文档例子里的区域编号（`AREA-TYO-23`）：区域用 `id`（uuid）引用，给人看的是名称。

### 负责人已定的三件事（由协调人转达）

- 区域有「停用 / 启用」（需求文档只写了删除）。停用 = 暂时不用，图形保留；停用期间可以修改、可以自测。
- **禁行区只管它所在的那一个区域**：位置落在区域甲的禁行区里，只是区域甲不报价；它同时在区域乙的营运区里（且不在乙的禁行区里）时，乙照常报价。
- 同一个供应商在同一个城市里区域不能重名。口径：每种语言的名称去掉首尾空白、全角半角归一、不分大小写后比较，**不要求是同一种语言**（「东京 23 区」写在中文名里和写在日文名里，列表上看起来一样）。不同供应商之间、同一供应商的不同城市之间可以同名。违反时返回 409 `AREA_NAME_TAKEN`。

### 图形

- 一个区域 = 若干块营运区 + 若干块禁行区；每一块是**一个不带洞的简单多边形**。「洞」不单独存在：要在营运区中间挖掉一块，就在那里画一块禁行区。
- 保存时每一圈点整理成：6 位小数、去掉闭合点后再闭合、统一成逆时针（第一个点保持是第一个点）。接口返回的就是整理后的。
- 每块图形有一个类内序号 `seq`（「营运 1」里的 1），由后端分配：新图形 = 这一类保存前的最大序号往上数；删掉的序号不再用；保留的图形编号（`id`）和序号不变。
- 上限（`@nozomi/domain` 的 `AREA_LIMITS`）：一个区域 50 块、一个多边形 1000 个点、合计 5000 个点、最少 3 个点；圆的半径 100 到 100000 米；名称每种语言 100 个字、备注名 40 个字。
- 数据库里另存每块图形的外接矩形（ADR 0002 的粗筛）和顶点数。

### 圆：存成多边形，圆心半径只为再编辑

- 一个圆在数据里 = 一个 64 边的正多边形（顶点都在圆上）+ 一份「它原本是圆」的记录（圆心、半径）。
- **报价、自测、对外的接口全部只认那个多边形**；圆心和半径只有一个用途：再次打开编辑页时还能按「圆」来改。
- 前端提交的是「圆心 + 半径」，后端用 `@nozomi/domain` 的 `circleToRing` 算出多边形；前端画预览用的是同一个函数。记录的圆和实际判断用的多边形永远对得上。
- 这改变了 ADR 0002 的两点：不再以「中心点 + 半径」作为判断依据；`geo.ts` 里按真圆判断的分支（`kind: "circle"`）区域不用。原因：一种形状一种判断，前端画出来的就是判断用的；64 边形比真圆略小（边的中点近约 0.12%，半径 30 公里时约 36 米），远小于地址定位本身的误差。

### 规则放在 `@nozomi/domain`，前后端同一份

`packages/domain/src/areas.ts`（纯函数，不依赖 Node 的模块，浏览器里也跑）：圆变多边形、整理一圈点、一圈点的合法性（坐标、点数、相邻重复、跨 180° 经线、共线、边交叉并指出是哪两条边）、整个区域的合法性和三条提醒、点在区域的哪里、解析 WKT / GeoJSON / 坐标行、上限常量、业务类型的枚举和中文名、重名的判断键。

- 检查函数只返回**原因代码**和位置，不返回句子；接口把代码放在 `details.issues[].reason` 里，前端按代码显示自己的定稿文字。
- 交叉、共线、方向用整数（百万分之一度）精确计算，不受浮点误差影响。
- 「点在不在里面」沿用 `geo.ts` 的规则：正好压在边线上的算在里面。**自测接口和以后的报价用的是同一个函数 `locatePoint`。**
- 跨过 180° 经线的图形不支持（一条边两端的经度差超过 180° 即判定）。这条判定有两个有意接受的后果：
  - 经度 180 和 -180 被当成两个不同的位置（平面上相差 360°），连它们的边就是「跨经线」；不做「其实是同一条线」的换算。
  - 一条边在平面上横跨超过 180° 经度的多边形（宽度超过半个地球）同样被判成跨 180° 经线并拒绝，哪怕它的本意是绕远的那一边。
    城市级的区域到不了这个尺度；以后要做跨日期变更线的地区（斐济、阿留申）时再把图形拆成两块或换算经度，届时另写 ADR。
- 圆能不能保存用 `circleIssues(center, radiusM)`：圆心、半径各自报，再把算出来的多边形过一遍上面的检查，所以贴着 180° 经线或盖住极点的圆报 `CROSSES_ANTIMERIDIAN`。前端保存前、后端保存时调的是同一个函数。
- 解析粘贴的文字（`parseShapeText`）用时和长度成正比：数字的正则写成每个位置只有一种拆法（测试发现原来的写法遇到几千位的数字会回溯几十秒），坐标行先去掉首尾空白再匹配；总长度超过 1000 万个字符的不解析，按 `UNRECOGNIZED` 报。单个数字不另设长度上限——超长的数字照常读出来，由坐标范围的检查拒绝（`COORDINATE_OUT_OF_RANGE`）。机场、城市导入里校验坐标的正则有同样的写法，一并改了。
- GeoJSON 语法错时的行号由 `jsonErrorOffset` 自己找（不递归、每个字符只看一遍），不依赖运行环境报错里带不带位置；行号按用户贴进来的原文数（前面的空行也算）。

### 空间计算：本期不用 PostGIS

需求文档写的是「点是否在多边形内用 PostGIS 空间索引」。本期仍按 ADR 0002 在应用层算：

- 引入 PostGIS 要换数据库镜像（本地、CI、测试服务器、备份恢复都要跟着换），而现在的量用不上：一次报价先按城市和品类筛出少量商品，每个商品的区域是个位数到几十个，先用外接矩形粗筛，再逐个做点在多边形内判断，是微秒到毫秒级。
- 更重要的是「同一份规则」：浏览器里的实时校验和自测必须和后端一致，这只有纯函数做得到。
- **以后报价量上来后的优化**：外接矩形列上建索引、已上架商品的区域放进内存；单城市区域数量超过 1 万或区域判断让报价 P95 超过 100 毫秒时再评估 PostGIS（ADR 0002 的重新评估条件），届时新增 ADR，并保证它和 `locatePoint` 的结果一致（边界上的点怎么算）。

### 所属城市

- 区域属于一个城市，创建后不能改（409 `FIELD_LOCKED`）。新增和启用时城市必须是平台**启用中**的城市（409 `MASTER_DATA_NOT_READY` / `CITY_DISABLED`）。
- **城市后来被平台停用**：区域原样保留，状态不跟着变，照常能看、能改、能停用、能自测，只是不能再启用；接口的应答里带着城市的当前状态。平台停用城市时**不检查**有没有供应商的区域在用它（供应商的配置不应挡住平台的运营动作）。
- 这意味着以后报价时要自己判断：**城市已停用的区域不参与报价**（M2-01 实现时照此做）。

### 暂停的供应商

供应商被平台暂停后，账号照常能登录（需求文档：暂停 = 商品不参与比价，已有订单继续履约），**也照常能看和改自己的区域**。暂停只影响比价，不冻结配置——这样恢复之前可以先把配置改好。

### 权限

`TENANT_ACTIONS` 加 `area.read`、`area.manage`。依据需求文档「11. 账号、权限与 API 设置」：管理员、商品价格两个都有；只读只有 `area.read`；调度、财务都没有。自测只需要 `area.read`。

### 幂等键（通用实现）

需求文档要求所有创建类 POST 带 `Idempotency-Key`，24 小时内同一个键返回同一结果。此前的创建接口都没有实现；这次做了通用的（`services/idempotency.ts` + 表 `idempotency_keys`），`POST /tenant/v1/areas` 是第一个用它的，以后的创建类租户接口都用它。

- 键的记录和业务写入在**同一个事务**里：先占位，做业务，存应答，一起提交。业务失败则整体回滚，键没有被占用，修好以后可以带同一个键重试。
- 同一个键同时来两次：后到的那次等前一次的事务结束，然后原样返回存好的应答——业务只做一次。
- 同一个键、内容不同：422 `IDEMPOTENCY_KEY_REUSED`。内容按校验后的请求算指纹，对象键的先后不同不算不同。
  这个键上一次已经建成了东西时，`details.created = { id, version }` 带着那一条的编号和**当时**的版本号。用途：第一次其实成功了但应答没收到，用户改了内容再保存——调用方凭它取到那一条（`GET`），把现在的内容存成对它的修改（`PUT` + `If-Match`），不用让人刷新后重画。那一条之后可能被改过或删掉，以 `GET` 的结果为准。
- 幂等回放的应答是从 jsonb 里读出来的，字段的先后和第一次不一定相同（内容相同）。JSON 对象本来就不保证顺序，不处理。
- 键只在「同一个租户 + 同一个接口」里有意义：两个供应商用同一个键互不相干（表是租户表，有行级安全）。
- 存的是当时的应答：之后那条记录被改了、删了，带同一个键再来仍然返回当时的应答，不会再建一个。
- 没带键：400 `VALIDATION_FAILED`（`/idempotency-key`）。已有的创建接口（邀请账号、主数据新增）没有补上强制要求：它们靠邮箱、编码唯一防重复，补上会让现有前端全部报错；等各自下次改动时再接入。
- 平台侧（`/platform/v1`）的创建接口以后要用时，给平台角色加一张同样的表或把这张表扩成两用，届时再定。

### 审计

区域的新增、修改、停用、启用、删除都写审计日志（`resource` = `area`，`tenant_id` 是该供应商）。修改只记变了的那几项的前后值；图形变了就记前后两份完整的图形（顶点坐标）——区域改动不频繁，而「谁把边界改成了什么」正是出了报价争议时要查的。

### 首页数量

`GET /tenant/v1/dashboard/summary`：任何已登录的供应商账号都能调，按模块裁剪（和平台的同名接口同一个思路）；本期只有 `areas: { active, disabled }`，没有 `area.read` 的角色拿到 null。

### 地图底图

区域页面要显示地图。前端把地图库（Leaflet）打包进产物，不从 CDN 加载；底图是栅格瓦片（一张张图片）。

**配置从哪来**：瓦片地址按环境不同，不能在构建时写进前端。放在环境配置里（`packages/config`），经 `GET /tenant/v1/map/config` 下发；没配置时返回 `tiles: null`，页面按「没有底图」工作。

| 环境变量 | 含义 | 默认 |
| --- | --- | --- |
| `MAP_TILE_URL_TEMPLATE` | 瓦片地址模板，`https://主机/…{z}/{x}/{y}…` | 不配 = 没有底图 |
| `MAP_TILE_ATTRIBUTION` | 版权署名，`文字|链接`，多条用 `;;` 隔开 | 配了地址就必须配 |
| `MAP_TILE_DARK_URL_TEMPLATE` | 暗色主题的瓦片地址 | 无（前端用滤镜压暗） |
| `MAP_TILE_REFERRER_POLICY` | 请求瓦片图片时的来源页策略 | `strict-origin` |
| `MAP_TILE_MIN_ZOOM` / `MAP_TILE_MAX_ZOOM` | 缩放范围 | 3 / 19 |
| `MAP_TILE_SIZE` | 瓦片边长 | 256 |

**这些不是 CLAUDE.md 规则 5 说的「密钥」**：它们的值本来就要发给浏览器，任何打开页面的人都看得到。付费底图常把服务商的密钥写在瓦片地址里——那是「发给浏览器用、靠限制域名来保护」的公开密钥，不是服务器密钥，可以这样下发；但它的值仍然只放在各环境的配置里（服务器的 `.env`），不进仓库。服务器端的密钥（如谷歌地图算里程用的 `GOOGLE_MAPS_API_KEY`）永远不经这个接口下发。

**内容安全策略**：此前全站 `img-src 'self'`。现在只多放行瓦片的那一个来源（协议 + 主机 + 端口）；`script-src`、`style-src`、`connect-src`、`font-src` 都不动，不放行 `data:`、`blob:`、通配符。

- 策略里的来源和接口下发的地址必须是同一个值，否则地图会悄悄变成一片灰。做法：**同一个环境变量算出两边**。
  - 策略仍在构建前端镜像时生成（`apps/web/build/edge-config.ts`），但 `img-src` 里留一个 Caddy 的环境变量占位 `{$MAP_TILE_CSP_SOURCES}`；
  - `deploy/bin/compose.sh`（服务器上所有 compose 调用的唯一入口）每次从 `.env` 的 `MAP_TILE_URL_TEMPLATE`（和暗色地址）取出来源，作为 `MAP_TILE_CSP_SOURCES` 交给反向代理；API 容器拿到的是同一个 `.env` 里的地址。
  - 没配底图时这个变量是空的，策略就是原来的只认同源。
- 来源的取法在 `packages/config`（`mapTileOrigin`）和 `compose.sh` 里是同一条规则，有测试核对两边一致；地址写错（不是 `https://`、带引号空格分号、通配符）时两边都拒绝：API 启动报配置错误，`compose.sh` 直接停下，不会把奇怪的字符拼进策略。
- `compose.sh` 读 `.env` 的方式比 docker compose 窄（只认顶格的 `变量名=值`，值原样使用），而 API 拿到的值是 docker compose 读出来的。为了不出现「API 下发了地址、`img-src` 却没放行，地图悄悄变灰」，瓦片地址的两个变量只要有一行不是标准写法（行首 `export`、行首空白、等号两边有空格、`变量名: 值`）`compose.sh` 就停下并说明，不去猜 docker compose 会怎么读；带引号、行尾空白或注释的值过不了地址校验，同样停下。同一个变量写了多行时两边都取最后一行。调用方环境里的同名变量先清掉。校验规则和 `packages/config` 逐条相同：三个占位符 `{z}`、`{x}`、`{y}` 都要有；只配暗色地址、没配主地址也停下。`apps/api/src/deploy-map-tiles-qa.test.ts` 用一批写法（含真实的 `docker compose config`）核对两边结论一致。
- 同一份镜像仍然可以原样部署到底图不同的测试、正式两个环境。

**来源页（Referer）**：全站 `Referrer-Policy: no-referrer` 不改。OpenStreetMap 的瓦片使用政策要求请求带有效的来源页，多数付费服务也靠它认域名，所以**只给瓦片图片**单独设来源页策略（前端在瓦片图层上设 `referrerPolicy`，值来自 `map/config` 的 `referrer_policy`，默认 `strict-origin`）：对方只收到我们的域名，不含路径和参数。

**测试环境用 OpenStreetMap 官方栅格瓦片**（`https://tile.openstreetmap.org/{z}/{x}/{y}.png`，不要密钥）。它的使用政策（<https://operations.osmfoundation.org/policies/tiles/>）要求：显示版权署名（所以配置里署名是必填）、带来源页、不批量下载、不保证可用。只适合测试环境。使用它意味着用户的浏览器直接向 OpenStreetMap 的服务器请求图片，对方能看到用户的 IP 和我们的域名。

**正式环境用哪家底图**还没有定，需要负责人决定（页面规范 13.6 列了选项：付费的同类瓦片服务 / 谷歌的瓦片接口 / 自己托管）。换一家只改这几个环境变量；选谷歌的话要另做「换会话令牌」的后端步骤，届时新增 ADR。
