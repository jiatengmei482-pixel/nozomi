# ADR 0061：官网查订单改成把链接发到下单邮箱

- 状态：已采纳（2026-11-02，M4-30）。负责人只收最终结果，取舍按「安全、保守、可回退」定，全部写在这里。
- 修改 ADR 0032「客人怎么看到自己的订单：查看链接」：查订单不再在页面上直接发链接、打开订单；「找回按订单号限速：只记失败」和硬上限整节作废（见「旧的找回限速」）。查看链接本身（令牌格式、只存哈希、有效期按订单现在的用车时间算）不变。
- 补充 ADR 0049：新增事件 `order.view_link`（只发客人）；运营核实后发到新邮箱的那一封收件人是审核过的地址，不按订单上的邮箱改写。
- 补充 ADR 0050「防枚举」：同一种做法（应答前只做和账号 / 订单无关的事，其余放后台任务）；后台任务的管理从 `email-login.ts` 抽到 `services/background.ts`，两处共用，`app.backgroundIdle()` 取代 `app.emailLoginIdle()`。
- 补充 ADR 0030：新增操作 `order.view_link_resend`、`order.view_link_review`，角色勾选表新增单独一格「订单链接重发」。
- 补充 ADR 0023：新增复核类别 `order.view_link_email`。
- 编号：写这篇时所有分支上最大是 ADR 0060（M4-29）、迁移 0230（M4-29）；这里用 ADR 0061、迁移 0231。

## 背景

负责人决定（2026-11-02）：

1. 官网查订单不再在页面直接打开订单，改成把管理链接发到下单邮箱。
2. 页面统一提示「如信息匹配，链接已发送到下单邮箱」，不透露订单号是否存在。
3. 只留了手机号、或邮箱填错的客人：页面提示联系客服，由管理员核实后重发。运营后台要有入口，有权限和审计。
4. 已经发出去的订单邮件里的管理链接继续有效。

原来的查订单是「订单号 + 邮箱或手机号 → 对上了 200 带新令牌，否则 404」。即使有限速，200 / 404 本身就是一个「猜对没有」的结论；为了让真客人不被别人刷满额度挡住，又加了「只记失败」和 24 小时硬上限两层，规则复杂、真客人最长要等 24 小时。改成发邮件之后，应答里没有任何结论，这两层都不需要了。

## 决定

### 1. 接口：`POST /site/v1/orders/lookup`

请求 `{ order_no, email }`（不再收 `contact`，手机号格式不对 400）。成功一律 **202 `{ status: "accepted" }`**。

**应答之前只做和订单无关的事**，依次：

1. 来源地址的额度（校验请求之前占，和官网其余接口一样；格式不对的请求也算）；
2. 校验格式：订单号 `NZ` + 16 位；邮箱 NFKC（全角转半角）、去首尾空白（含制表符、换行）、小写，中间有空白或控制字符、没有 `@` 和点、超过 320 字的 400（domain 的 `viewLinkLookupEmail`）；
3. 官网配没配置（没有 503 `SITE_NOT_OPEN`）、邮件能不能发（没配置 503 `ORDER_LINK_EMAIL_UNAVAILABLE`，页面请客人联系客服）——都和订单无关；
4. 订单号、邮箱的额度（见下）。

然后排一个后台任务，立刻回 202。后台任务：按渠道和订单号找单（同 ADR 0032：只认官网渠道、不认已转出的那一行）→ 没脱敏 → 比下单邮箱（先比盲索引再解密，ADR 0057；对得上却解不开的抛出、记日志，客人收不到信，和对不上一样）→ 都过了才往通知中心排一条 `order.view_link`。对不上什么也不做、不记失败。

所以「对上 / 邮箱不对 / 订单号不存在 / 别的渠道的单 / 已脱敏」五种，状态码、正文、应答头一样；耗时也一样到「同一段代码路径」为止（ADR 0050 同样的口径，数据库和网络本身的抖动不处理）。集成测试在订单表被锁住时发「对上」的请求，照样马上 202，证明应答之前不碰订单。

**为什么手机号不能查**：链接只发邮箱。用手机号查，再发到订单上的邮箱，技术上可以，但「只留了手机号」的客人订单上本来就没有能用的邮箱，页面说「已发送」会让他白等；负责人的决定是这些客人联系客服。页面上手机号直接提示「只留了手机号的，请联系客服」。

### 2. 限速（domain 的 `VIEW_LINK_REQUEST_LIMITS`）

| 维度 | 额度 | 防什么 |
| --- | --- | --- |
| 来源地址（IPv6 按 /64，ADR 0045） | 15 分钟 10 次 | 沿用原来的地址额度 |
| 订单号 | 每小时 3 次、每天 6 次 | 换着地址拿一张单的邮箱当靶子；枚举订单号 |
| 邮箱 | 每小时 3 次、每天 10 次 | 拿这个功能轰炸一个邮箱（一个客人可能有几张单） |

- 计数存在 `sales_rate_limits`（固定窗口，和官网其余额度一样），订单号、邮箱只存哈希。
- **不管订单存不存在、对没对上都计**，被前面拦下的不占后面的（地址 → 订单号 → 邮箱）。所以 429 本身也不透露任何东西：存在和不存在的订单号被挡时正文、`Retry-After` 一样（测试对比过）。
- 一个邮箱一天最多收 10 封这种信，一张单一天最多 6 封。攻击者能做的最坏的事是把某张单的额度刷满，让真客人这一小时 / 这一天发不了——页面提示等多久或联系客服。
- 运营重发另有一份：同一张单每小时 5 次（`staff_view_link`，连点保护）。

**按地址的额度窗口仍然最长 15 分钟**（ADR 0045 的说法）：订单号、邮箱、运营重发的几份不按地址，`ipv6-rate-limit-qa.itest.ts` 的清单已更新。

### 3. 链接：复用现有的查看令牌

- 邮件里的链接在通知中心**发信那一刻**新签发（`newSiteLink`，`issued_via = 'email'`，库里只有哈希），和确认邮件、派车邮件里的链接完全是同一套（ADR 0049「不存正文」）。查订单本身不签发任何令牌。
- 有效期按订单现在的用车时间算（ADR 0032），至少到签发后 1 天。
- **不吊销旧链接**（负责人第 4 条）：下单时的、之前邮件里的链接继续有效。测试核对过：同一张单查两次，三条链接都能打开。
- 通知中心的事件 `order.view_link`：只发客人；只有订单号和链接，**没有姓名、电话、行程、金额**（收件人可能只是被人填了这个邮箱）；写明「以前收到的链接仍然可以使用」「如果不是您本人申请的，可以忽略」。有效期 24 小时（客人是刚在页面上申请的，晚一天才到的那封不如让他再申请一次）；订单状态变了照发（取消了的单客人也要能看退款）。
- 发件箱 `notification_events.data` 只有 `via`、`target`、`request_id`，没有邮箱；日志不写邮箱和令牌。

### 4. 运营核实后重发（订单详情「官网订单链接」）

`GET /platform/v1/orders/{id}/view-link`（`order.read`）：能不能发、下单邮箱（打码）、在等审核的那一条、最近 20 条记录。不是官网的单页面上不显示这一块。

`POST /platform/v1/orders/{id}/view-link/resend`（`order.view_link_resend`），`{ target, email?, verification, reason }`。**核实方式和原因必填**：

| 核实方式 `verification` | 说明 |
| --- | --- |
| `callback_phone` | 回拨下单时留的电话，本人确认 |
| `email_from_order_address` | 客人用下单邮箱来信 |
| `order_details` | 核对订单细节（行程、用车时间、人数、航班号） |
| `payment_details` | 核对付款信息（卡号末 4 位、付款时间、金额） |
| `other` | 其他（原因里写清楚） |

- `target: original`（发到下单邮箱）：直接排进通知中心，收件人是订单上现在的邮箱。审计 `order` / `send_view_link`（核实方式、原因、打码地址）。
- `target: new_email`（发到核实后的新邮箱）：**发起双人复核** `order.view_link_email`，另一位有 `order.view_link_review` 的同事在「待审核」里批准时才排进通知中心。发起人不能批自己发起的（通用规则）。同一张单同时只有一条在等审核（唯一索引，409 `VIEW_LINK_REVIEW_PENDING`）。批准时再核对一遍（还是官网的单、没脱敏），审计 `send_view_link` 记审核人、发起人、复核编号。
- 拒绝：不是官网的单 409 `NOT_SITE_ORDER`（客人的通知由渠道发）；已脱敏 409 `PASSENGER_ANONYMIZED`；发到原邮箱但订单上没有邮箱 409 `NO_EMAIL_ON_FILE`（这时可以走新邮箱）；新邮箱和下单邮箱一样 409 `SAME_AS_ORDER_EMAIL`（那就是发到原邮箱，不用复核）。
- 限定了数据范围的员工（ADR 0030）对范围外的单 404；租户的令牌进不来，供应商那边没有这些接口。

**为什么发到新邮箱要双人复核**：收到链接的人能看、改、取消这张单，等于把订单交给他。现有体系里「把东西交给另一个人」类的操作（收款账户生效、两步验证重置、多退给客人）都是双人复核；客服一个人接电话、一个人决定，社会工程最容易得手的就是这一步。代价是客人要等另一位同事批准，属于有意的取舍。

**为什么不改订单上的邮箱**：改邮箱会让之后所有通知都发到新地址，影响面比「发一封链接」大；客人打开链接后可以自己改（改单规则照旧，联系信息直接生效）。所以复核只批准「发这一封」。

**新邮箱存在哪**：`view_link_requests`（平台表，迁移 0231）。只有等审核期间留着，按乘客信息加密（`sealRecipient`，按发起时这单的供应商的密钥，ADR 0057），有结论（批准、驳回、撤回）后马上清空；数据库约束保证只有 `pending_review` 的行能有地址。复核记录（`approvals.payload`）、审计、应答里只有打码后的地址。复核的发起说明（原因）属于订单相关复核的手写内容，打码和脱敏按 ADR 0055 的现有规则。
- 已知限制：等审核期间换了乘客信息的密钥（轮换），这一行解不开，批准会失败，审核人驳回后重新发起即可（不加进回填和校验任务：行数极少、存活时间短）。

**谁有权限（按现有角色的惯例）**：

| 操作 | 角色 | 理由 |
| --- | --- | --- |
| `order.view_link_resend`（发到原邮箱、发起发到新邮箱） | 超级管理员、运营、**客服** | 官网让找不回订单的客人联系客服，接电话的是客服；和 `order.resend`、`notification.retry` 同一批人 |
| `order.view_link_review`（批准发到新邮箱） | 超级管理员、运营 | 和 `ticket.review`、`rescue.review` 一样：客服发起、运营审核；两位运营互审，或超级管理员审 |

角色勾选表单独一格「订单链接重发」（查看 = 订单查看，编辑 = 重发，审核 = 审核新邮箱）：放进「订单 · 编辑」的话，已有的自建角色会没人审核就多出这个权限（同 ADR 0052、0060 的做法）。

### 5. 页面（`/book/order`，没有令牌或令牌失效时）

- 标题「查订单」；说明「输入订单号和下单时填的邮箱，我们会把订单链接发到这个邮箱」。
- 字段：订单号、下单时的邮箱（`type=email`、`autocomplete=email`）；按钮「发送订单链接」。提交后不管对没对上都显示「如信息匹配，链接已发送到下单邮箱。请查收邮件（也看看垃圾邮件），打开邮件里的链接查看订单。」（`role=status`），不跳转、不打开订单。
- 「收不到邮件？」一节：只留了手机号、邮箱填错、十几分钟没收到的，联系客服核实后重发。客服电话（`SITE_SUPPORT_PHONE`）登记了才显示 `tel:` 按钮，没登记时这一节照常显示文字。
- 限速：「尝试次数过多，请 N 分钟后再试，或联系客服。」；邮件没配置：「暂时发不了邮件，请联系客服找回订单。」
- 下单成功页、付款回跳取不回令牌、链接失效的说法同步改成「在查订单填订单号和邮箱，我们把链接发到您的邮箱」。

### 6. 旧的找回限速

- `site_lookup_order` 额度、`site_lookup_failures` 的读写、`SITE_LOOKUP_CEILING`、`peekRateSlot`、服务日志 `site_lookup_ceiling_reached` 都删掉：它们是为「200 / 404 能猜」设计的，现在应答里没有结论。
- `site_lookup_failures` 表留着不删（没有新数据写入；删表要另一个迁移，好处只是少一张空表）。`site_order_links.issued_via` 的 `lookup` 值留给历史数据，之后不再产生。
- 通知事件 `site.lookup_ceiling` 和它的模板留着（通知中心可能还有历史记录要显示），之后不再产生。

## 已知缺口（没在这里改，见负责人待决定）

**运营「代客人改单」可以一个人改掉乘客邮箱**：`PATCH /platform/v1/orders/{id}`（`order.manage`，运营、客服）改乘客信息直接生效，之后的 `order.changed` 客人邮件（带查看链接）发到新地址。效果和「发到新邮箱」差不多，却不用复核。这是 M3-03 / M4-29 就有的行为，改它会影响现有的改单流程和测试，不在本任务范围；推荐另开任务：运营代改乘客邮箱也走双人复核（或改邮箱那一次的通知只发旧地址）。

## 回退

- 页面和接口一起回退即可：新增的表、事件、权限都是加法。回退后旧代码会重新写 `site_lookup_failures`（表还在）。
- 已经发出去的 `order.view_link` 邮件里的链接是普通的查看链接，回退后照样能用。

## 不做

| 内容 | 为什么 |
| --- | --- |
| 用手机号查、发短信 | 负责人决定只发邮箱；短信要接新服务 |
| 人机验证（Turnstile 等） | 应答里没有结论，限速已足够；要接外部服务、改内容安全策略，需要时再加 |
| 发到新邮箱时顺带吊销旧链接 | 负责人第 4 条：已发出的链接继续有效。邮箱填错时旧链接可能在陌生人手里，见负责人待决定 |
| 运营看到新邮箱全文再审核 | 复核里只有打码地址；审核人看的是发起人的核实方式和原因。要看全文得加「查看」和审计，以后需要再加 |
| 多语言邮件 | 模板只有中文，和 ADR 0049 一样 |

## 测试

- 单元（`packages/domain/src/view-link.test.ts`、`notifications.test.ts`、`access.test.ts`）：邮箱的认法、限速顺序和上限、拒绝原因、模板没有个人信息和有效期、权限归属和勾选表。
- 集成（`apps/api/src/view-link-email.itest.ts`，真实 PostgreSQL + 本机假 SMTP）：五种情况应答一致、订单表锁住时照样马上应答、只有对上的收到信；邮件链接能打开、旧链接仍有效、邮件里没有个人信息、库里和日志里没有令牌和邮箱；三个维度的限速和被挡时应答一致；格式不对 400；邮件没配置、官网没配置 503；已脱敏；运营重发的权限、核实必填、审计、不是官网的单、租户进不来；发到新邮箱的复核（发起人不能批、客服不能批、批准后才发、新邮箱清掉、订单邮箱不改）、驳回和撤回；连点保护。旧的测试按新行为改（`site*.itest.ts`、`passenger-*.itest.ts`、`ipv6-rate-limit*.itest.ts`）。
- 页面（`site.test.tsx`、`site.qa.test.tsx`、`order-money.test.tsx`）：统一提示、手机号提示、客服电话有无、限速和邮件不可用、运营的重发对话框。
- 端到端（`apps/web/e2e/site-lookup-email.spec.ts`）：官网下单 → 查订单 → 假 SMTP 收到 → 打开邮件里的链接看到订单；对不上的同一句提示、不发信；亮暗主题、手机宽度、无障碍。
