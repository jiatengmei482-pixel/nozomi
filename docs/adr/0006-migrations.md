# ADR 0006：数据库迁移与集成测试的数据库隔离

- 状态：已采纳（2026-10-07）

## 决定

### 迁移

- 迁移是 `apps/api/migrations/` 下的纯 SQL 文件，文件名 `NNNN_snake_case.sql`，按编号从小到大执行。
- 用自己写的执行器（`apps/api/src/db/migrate.ts`，约 150 行），不引入第三方迁移库。命令：`pnpm db:migrate`。
- 已执行的迁移记在 `schema_migrations` 表（编号、名称、内容的 SHA-256 校验和、执行时间）。
- 每个迁移在一个事务里执行，失败整体回滚。为了让这一条真的成立，迁移文件里不允许出现事务控制语句（`begin`、`start transaction`、`commit`、`end`、`abort`、`rollback`、`prepare transaction`）：执行器在读取文件时就检查，发现就报 `MIGRATION_TRANSACTION_CONTROL`，一条语句都不执行。`savepoint` / `rollback to savepoint` 允许。
- 记录表建在连接的当前 schema，执行器全程用带 schema 的完整表名读写它，所以迁移文件里用 `set local search_path` 不影响记录。
- 扩展名是 `.sql`（不分大小写）的文件都必须符合命名规则，写成 `.SQL` 之类会报错而不是被跳过；其他扩展名的文件和子目录忽略。
- 迁移不受连接池默认查询时限的约束（迁移可能很慢，也可能要排队等锁）：`pnpm db:migrate` 用不设时限的连接池，执行器在自己的会话里关掉 `statement_timeout`，结束时恢复。
- 用 PostgreSQL 的 advisory lock 保证同一时间只有一个进程在迁移；等锁超过 60 秒报错退出。
- 只进不退：没有「回滚迁移」。要撤销就新增一个迁移。
- 已执行的迁移文件被修改、删除，或新迁移的编号小于已执行的最大编号，执行器一律报错并且不动数据库。
- 服务启动时**不**自动迁移。迁移是部署流程里单独的一步；`/health` 会报告迁移是否执行完，没执行完返回 503。
- 迁移只建结构，不写任何预置业务数据（CLAUDE.md 规则 1）。

### 集成测试的数据库隔离

- 集成测试（`*.itest.ts`）连真实 PostgreSQL。每个测试新建一个随机名字的 schema，连接的 `search_path` 只指向它，测试结束后整个删除。
- 因此集成测试可以直接连本地开发库或 CI 的库，不读也不留任何数据。
- 单元测试（`*.test.ts`，`pnpm test`）不需要数据库；集成测试（`pnpm test:integration`）连不上数据库时直接失败，不跳过。`pnpm check` 两者都跑。

## 理由

- 需要的功能很少（顺序执行、记录、校验和、加锁），自己写比引入一个库更容易看懂和排查，符合 ADR 0001「少依赖」的取向；纯 SQL 文件也方便以后写行级安全策略（ADR 0003）。
- 「哪些要执行、记录对不对」是纯函数（`migration-plan.ts`），有单元测试；真正执行的部分有连真实数据库的集成测试（空库从头执行、重复执行、篡改、中途失败、并发、锁超时）。
- 启动时不自动迁移：多实例同时启动、迁移失败时的表现都更可控，出问题时也能明确知道是哪一步失败。

## 已知限制

- 因为每个迁移包在事务里，不能使用 `create index concurrently` 这类不允许在事务中执行的语句。等数据量大到需要时，再新增 ADR 支持「不包事务」的迁移。
- 事务控制语句的检查是对 SQL 文本的静态扫描（跳过注释、字符串、带引号的标识符、`$$…$$` 函数体和 `begin atomic … end` 函数体），不是完整的 SQL 解析。它拦得住写在文件顶层的 `commit` 等语句；极端写法如果被误判，报错会指出文件和关键字。
- 校验和按文件内容计算（换行统一为 LF）。给已执行的迁移文件补注释也会被视为改动，这是有意的。
