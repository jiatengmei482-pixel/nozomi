# ADR 0045：按来源地址的限流对 IPv6 按 /64 网段计数

- 状态：已采纳（2026-10-26，M4-11）
- 补充 ADR 0008「登录与会话」（防暴力破解的「同一来源地址」「同一邮箱 + 同一来源地址」两层）、ADR 0023「渠道」（换令牌按来源地址限流）、ADR 0032「官网」（`/site/v1` 按来源地址限速）：「来源地址」一律先换成本文的**限流键**再计数。各处的额度、窗口、计数方式都不变。
- `TRUST_PROXY_HOPS` 取来源地址的规则（ADR 0007、0008）不变：先按它定出来源地址，再换成限流键。

## 背景

原来按来源地址计数时，计的是地址原文（的哈希）。IPv4 下一个用户通常只有一个出口地址；IPv6 下运营商一般给每个用户（每条宽带、每台手机）一个 /64 或更大的网段，网段里的 2^64 个地址都归他用，系统还会定期自动换临时地址（RFC 8981）。按单个地址计数时，同一个人每次请求换一个地址就能无限绕过官网询价、找回订单、换令牌、登录的「同一来源地址」限制。

## 决定

### 「来源地址 → 限流键」：domain 的 `rateLimitKeyOf`（`packages/domain/src/rate-limit-key.ts`）

所有按来源地址计数的地方都先过这一个纯函数，再拿结果去算哈希、计数。以后新增按来源地址的限流（包括 M3-12 官网地址搜索）也必须用它。

| 来源地址 | 限流键 |
| --- | --- |
| IPv4 | 原样（规范写法），如 `203.0.113.5`。**不按网段合并**，和原来一样 |
| IPv4 映射的 IPv6（`::ffff:203.0.113.5`、`::ffff:cb00:7105`） | 对应的 IPv4，如 `203.0.113.5`（和 IP 白名单同一口径，ADR 0030） |
| IPv6 | 前 64 位的规范压缩写法加 `/64`，如 `2001:db8:1:2::/64`（小写、去前导 0、最长一段连续 0 压成 `::`，RFC 5952）。大小写、零压缩、前导 0、末尾用点分写法的不同写法得到同一个键 |
| 带外壳的写法 | 先去掉首尾空白、方括号（`[2001:db8::1]`）、端口（`[2001:db8::1]:443`、`203.0.113.5:8080`；有的代理会把端口写进 `X-Forwarded-For`）、区域标识（`fe80::1%eth0`、`fe80::1%25eth0`）再按上面换 |
| 解析不了的 | `raw:` 加原文 |

- 解析复用 IP 白名单的 `parseIpAddress` / `formatIpAddress`（ADR 0030），两处对「什么是合法地址、映射地址算谁」的判断一致。
- **解析不了的不合并成一个桶**：如果所有解析不了的来源共用一个键，一个人刷满就挡住所有同类来源。`raw:` 加原文让不同的原文各算各的；`raw:` 前缀保证它不会和任何合法地址的键相同（把 `2001:db8:1:2::/64` 当来源地址传进来，得到的是 `raw:2001:db8:1:2::/64`，碰不到真实网段的计数）。实际上来源地址取自连接本身或我们信任的那一层代理写的值，客户端控制不了，解析不了的情况基本不会出现。

### 接到哪里

| 限流 | 位置 | 说明 |
| --- | --- | --- |
| 官网 `/site/v1` 全部按地址的额度：询价、下单、找回订单（地址那一层）、其余读接口（含官网订单页上客人看、提交工单的接口，`routes/order-center.ts` 同样走 `takeSiteSlot`） | `services/site.ts` 的 `takeSiteSlot` | 找回订单按**订单号**的那一层与地址无关，不变 |
| 对外接口换令牌（每个地址每秒 10 次） | `services/sales-auth.ts` 的 `ipBucket` | `/sales/v1` 其他接口按渠道计，不变 |
| 登录限速：「同一来源地址」「同一邮箱 + 同一来源地址」两层 | `services/login-guard.ts` 的 `reserveLogin` | 平台、租户登录，自己改密码，两步验证输码都经这里；「同一邮箱」那一层与地址无关，不变 |

### 不改的

- **库表结构不改、不需要迁移**：`login_throttles`、`sales_rate_limits` 本来就只存「入口 / 范围 + 地址」的 SHA-256，没有地址原文；现在哈希的是限流键。上线那一刻，IPv6 来源（以及写成映射形式的 IPv4 来源）在当前窗口里的计数会从零开始——窗口最长 15 分钟（官网找回、登录），影响可以忽略。
- 审计日志、服务日志里的来源地址照旧记连接给出的完整地址（排查、追责要用到具体地址），不改成网段。
- IP 白名单（ADR 0030）照旧按单个地址匹配名单里的地址段。
- `TRUST_PROXY_HOPS`：默认 0 完全不看 `X-Forwarded-For` 等请求头；设为 n 时取代理链从右往左第 n 跳。伪造请求头换不了来源地址，自然也换不了网段。

## 为什么按 /64

- /64 是 IPv6 里「一个子网」的最小单位：无状态地址自动配置（SLAAC）要求子网是 /64，所以运营商分给一个用户的至少是一个 /64（家庭宽带常见 /56、/48，手机常见每台设备一个 /64，RFC 6177、RIPE-690 的建议）。同一个用户在自己的 /64 里随意换地址的成本是零，按 /64 计才挡得住。
- 不选 /128（原来的做法）：上面说的，换个地址就绕过。
- 不选 /56 或 /48：一个用户拿到的 /56、/48 里能换出 256、65536 个 /64，按 /64 计他的额度确实会被放大；但也有运营商（尤其是手机网络、部分机房）从同一个 /56、/48 里给**不同用户**各分一个 /64，按更大的网段计会把互不相干的人算在一起。现在的额度（找回 15 分钟 10 次、询价每分钟 30 次、登录 50 次失败）是按「一个人」定的，选 /64 和 IPv4 下「一个出口地址」的粒度最接近。如果以后观察到有人拿整个 /48 轮换来刷，再加一层「同一 /48 的更宽额度」，在本函数旁边加一个 `/48` 的键即可，新增 ADR。

## 后果

- **共享 /64 的网络**：少数网络让很多用户共用一个 /64——公共 Wi-Fi、酒店、校园网、公司网（一个网段里所有设备都在同一个 /64 里），以及给多个客户分同一个 /64 的个别机房。这些用户现在共用一份额度：其中一人刷满，同一网络的其他人在窗口内会被 429（官网页面提示等多少秒，登录提示稍后再试）。这和 IPv4 下同一个出口地址（运营商级 NAT、公司出口）后面的人共用一份额度是同一种代价，ADR 0008、0032 已经接受；额度本来就留了余量（登录成功的那次退还，正常客人一分钟不会询价 30 次）。
- IPv4 映射写法和 IPv4 写法现在是同一个键：同一个客户端在双栈服务上以两种写法出现时不能再各算各的（原来理论上可以多一倍额度）。
- 每次请求多一次纯函数换算，开销可以忽略。

## 测试

- 单元（`packages/domain/src/rate-limit-key.test.ts`）：IPv4 原样、带端口 / 方括号；映射地址的点分 / 十六进制 / 大写写法；同一 /64 的各种写法（全写、大写、前导 0、零压缩、末尾点分）；方括号、端口、区域标识（含 `%25`）；第 64 位与第 65 位的边界；规范写法；解析不了的各自一个键且不撞合法键。
- 集成（真实 PostgreSQL，`apps/api/src/ipv6-rate-limit.itest.ts`）：官网找回、询价、读接口，换令牌，登录的「同一地址」「同一邮箱 + 同一地址」两层——同一 /64 里每次换地址和写法，到上限 429；别的 /64 不受影响；IPv4 相邻地址各算各的、映射写法和 IPv4 同一个；`TRUST_PROXY_HOPS=0` 伪造 `X-Forwarded-For` / `X-Real-IP` / `Forwarded` 绕不过；`TRUST_PROXY_HOPS=1` 伪造最左边的地址无效、按最后一跳的 /64 计。
