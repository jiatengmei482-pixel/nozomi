# ADR 0034：官网也卖点对点和包车；不依赖外部服务的地址输入辅助

- 状态：已采纳（2026-10-26，M3-10）
- 修订 ADR 0032 的「官网只卖接送机」（待定事项 4）和「本期不做」里的「点对点、包车」一行；ADR 0032 的其余内容（`/site/v1` 的授权、查看链接、限速、Stripe 没配置时的做法）不变。
- 不新增表、不新增迁移、不新增配置。

## 背景

roadmap M3-10 的验收标准：「点对点和包车也能在官网下单」「地图选点 / 地址搜索」「确认邮件里带订单查看链接（依赖通知中心）」。

需求《用车报价服务平台》的三种品类：接送机、点对点、包车（包车按小时套餐，超时、超公里服务后加收）。《平台运营端与渠道对接》：官网是普通的自营渠道，走同样的比价和结算规则。查下来，报价引擎、`/sales/v1/quotes`、下单、取消、改单、加收早就支持三种品类（M2-01、M2-04、M3-01、M3-03）；只有官网这一层（`/site/v1` 的询价请求、城市列表、页面）只认接送机。

## 决定

### 询价：同一个接口，按 `category` 填各自的字段

`POST /site/v1/quotes` 加 `category`（不填 = 接送机，M3-05 的请求照旧能用）：

| 品类 | 要填 | 不能填 |
| --- | --- | --- |
| 接送机 | `airport_id`、`direction`、`address` | `pickup`、`dropoff`、`package_hours` |
| 点对点 | `pickup`、`dropoff`（坐标） | `airport_id`、`direction`、`address`、`package_hours` |
| 包车 | `pickup`（坐标）、`package_hours` | `airport_id`、`direction`、`address`、`dropoff` |

该给的没给 400 `REQUIRED`，不该给的给了 400 `NOT_APPLICABLE`（和 `/sales/v1`、报价引擎同一种说法），每一项都有中文说明。

考虑过的另一种写法是 `oneOf` 三种请求体（按 `category` 区分）：定义更严，但 zod 的判别联合对「不填 `category`」不友好，前端契约测试也要改成逐个分支比对；三个品类的字段只有六个，一个对象加一张「谁填什么」的表更好读，校验集中在 `siteTripOf` 一处。

服务端照旧调 `createSalesQuotes`：接送机把地址那一端放进 `pickup` / `dropoff`；点对点两端都放；包车只放 `pickup`、带 `packageHours`。询价日志的 `request` 多记一项 `category`。渠道没授权这个品类时报价引擎照旧回 422 `CHANNEL_SCOPE_DENIED`。

### 报价多一项 `package`

包车的报价带 `package: { hours, km }`：套餐时长和含的公里数（`km` 取中标那条价格规则的 `packageKm`；读不到时为 null）。只是套餐的条件，不是钱，不涉及结算价和加价比例。客人要知道「8 小时含 150 公里」才知道超出部分会另收。超时、超公里的单价**不**给：那是供应商的结算口径，换成客人币种要按这一单的加价比例算，等于把比例透露出去；服务后的加收照旧在订单页按客人要付的金额显示、可提异议（ADR 0029）。其他品类 `package` 为 null。

### 城市带能订的品类；包车的套餐时长单独一个接口

- `GET /site/v1/cities` 的每个城市多一项 `categories`：这个城市能在官网订哪几种（城市和品类都在渠道授权里、有渠道卖的供应商上架了这个品类的商品），顺序固定为接送机、点对点、包车。页面按它显示「服务」单选。
- `GET /site/v1/cities/{id}/charter-packages`：渠道卖的供应商上架的包车商品里，启用、到城市当地今天还没过期的价格规则的套餐时长（去重、从短到长）。包车询价必须给一个时长，客人不可能自己猜；这里只列「有价格规则」的时长，某个时长某一天能不能报出价（库存、提前量、服务时间）照旧由询价判断。城市或包车不在渠道授权里、城市不存在时为空列表。

### 地址输入辅助：只用平台的主数据

地址搜索、地图选点要谷歌地图（M2-02，等负责人提供密钥）或定下正式环境的底图（ADR 0015「正式环境用哪家底图」，等负责人决定）。本期不接任何外部服务，做一个不依赖它们的辅助：

- `GET /site/v1/cities/{id}/places`：这个城市里启用的机场、车站、地标（平台维护的主数据；航站楼、出口挂在上级下面，不单独列），带名称（各语言）、编码、地标的地址、坐标；按种类、编码排，最多 500 个。城市不存在或停用时为空列表。
- 页面每个要填地址的地方上面多一个组合框「从常用地点选上车 / 下车地点（选填）」：按名称（各语言）、编码、地址筛选（和后台选接送点同一套匹配规则 `placeQueryMatches`），选一个就把「名称（地标的地址）」和坐标填进下面的地址、坐标栏；之后手改地址或坐标，选择随之清掉。不在列表里的照旧自己写地址、粘贴坐标。城市里一个常用地点都没有时不显示这个组合框；读不出来时组合框里说明，不挡住填写。
- 这是临时方案：接入地点搜索（`/places/search`）和底图后，换成搜索 + 地图选点（roadmap M3-10 的「地图选点 / 地址搜索」仍未完成）。

### 页面

`/book`（标题改为「预订用车」，顶栏入口同名）：

```
城市            [东京            ▾]
服务            (●) 接送机  机场和酒店、地址之间
                ( ) 点对点  市内两个地点之间
                ( ) 包车    按小时包一辆车，司机全程陪同
── 接送机 ──    接机还是送机、机场、[常用地点] 地址、坐标（同 M3-05）
── 点对点 ──    [从常用地点选上车地点] 上车地址、上车坐标
                [从常用地点选下车地点] 下车地址、下车坐标
── 包车 ──      包车时长 [8 小时 ▾]（超出套餐的时长和公里服务后按实际收取）
                [从常用地点选上车地点] 上车地址、上车坐标
用车日期 / 上车时间（当地）；接机仍是航班到达日期 / 计划到达时间
人数、行李
[              查询价格              ]
```

- 城市只有一种服务时不显示「服务」单选；换城市时如果新城市没有现在这种服务，换成它有的第一种。城市只有一种包车时长时替客人选上；没有可选时长时在原位置显示空状态「暂时没有可选的包车时长」，读不出来时显示错误状态 +「重试」。
- 报价卡：包车多一行「包车套餐：8 小时，含 150 公里」；免费等待只有接机写「从航班落地起算」，其余「从约定的上车时间起算」。结果上方的价格说明：接送机、点对点「按车计价的一口价，已含高速费和停车费」；包车「按车计价的套餐价。超出套餐的时长和公里、高速费、停车费服务后按实际收取：先通知您，48 小时内可以在订单页提异议」（加收类型里高速费、停车费只有包车有，ADR 0029）。包车报不出价时多一句「也可以换一个包车时长试试」。
- `/book/checkout`：行程区块按服务写（点对点「上车地址 → 下车地址」；包车「包车套餐」和「包车上车点」）；只有接送机有航班号；地址栏按服务（接送机一栏、点对点两栏、包车一栏），从询价页带过来。
- `/book/order`：行程按服务写（包车「包车：8 小时」「上车地点」）；只有接机单有「我已落地」（不变）；修改订单只列这一单有的地址栏，非接送机不出航班号。

上面这些说法需要美工并入 `docs/design/pages/site-booking.md`（官网页面规范，在 M3-09 的分支上，尚未合并）。

## 本期不做

| 内容 | 原因 / 去向 |
| --- | --- |
| 地址搜索、地图选点 | 需要谷歌地图密钥（M2-02）和正式环境底图（负责人决定）；拿到后在本任务或新任务里做 |
| 确认邮件里带订单查看链接 | 依赖通知中心和发邮件的服务账号（负责人提供）；查看链接的生成方式见 ADR 0032 |
| 附加服务、司机语言、多币种、点对点的途经点 | 官网后续任务 |
| 超时、超公里单价给客人看 | 见上「报价多一项 `package`」 |
