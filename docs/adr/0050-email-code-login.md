# ADR 0050：邮箱验证码登录

- 状态：已采纳（2026-11-01，M4-06）；标「待负责人确认」的几项先按推荐做
- 由 ADR 0061 补充（2026-11-02，M4-30）：官网查订单用同一种防枚举做法；后台任务的管理抽到 `services/background.ts` 两处共用，`app.emailLoginIdle()` 改名 `app.backgroundIdle()`。
- 文中「待负责人确认」的项已由 ADR 0053 落定（2026-11-01）。
- 取代 ADR 0030「本期不做」里的「公司 SSO 登录」：负责人决定（2026-10-27）不接 SSO，改为邮箱验证码。
- 补充 ADR 0008：多一种登录方式，会话、令牌、停用、限速的规则不变；密码登录**继续可用**。
- 补充 ADR 0030：验证码只代替「密码」这一步，后面的两步验证、IP 白名单、必须先改密码一步不少。
- 补充 ADR 0010：`nozomi_preauth` 多一张表 `email_login_codes`（和 `login_throttles` 同理：还不知道请求方是谁时就要读写；表里没有邮箱、没有账号编号）。
- 使用 ADR 0048 的 `sendMail`（不抛错）。迁移 0150。

## 背景

负责人要的流程：输入邮箱 → 收到 6 位验证码 → 登录，不用密码；有有效期、次数限制、防暴力；两步验证、IP 白名单照常生效。

现实的约束：测试环境还没填 SMTP，发不出邮件；平台账号和自动化验收的 QA 账号都靠「密码 + 两步验证」登录。所以这个任务上线本身不能改变任何人现在的登录方式。

## 决定

### 1. 不能把人锁在外面（最重要）

规则集中在 `@nozomi/domain` 的 `resolveLoginMethods`：

| 邮件发送（ADR 0048 生效的那份） | `PASSWORD_LOGIN_DISABLED` | 验证码登录 | 密码登录 |
| --- | --- | --- | --- |
| 没配置 | 不填 / `false`（默认） | 不可用 | 可用 |
| 已配置 | 不填 / `false`（默认） | 可用 | 可用 |
| 没配置 | `true` | 不可用 | **仍然可用**（宁可开着，不能把人锁在外面） |
| 已配置 | `true` | 可用 | 关闭（403 `PASSWORD_LOGIN_DISABLED`） |

- **部署上线不改变任何人的登录**：迁移不动账号；默认不关闭密码；没配置邮件时登录页和今天一模一样。
- **验证码登录随邮件配置自动可用**：负责人在运营后台填好 SMTP，下一次打开登录页就能用；清空 SMTP 就消失，不用重启。
- **关闭密码只有一个入口**：服务器 `.env` 的 `PASSWORD_LOGIN_DISABLED=true`，改完重启服务。没有后台开关：运营后台的账号被盗不应该能把所有人的密码入口关掉，而且后台开关一旦把人锁在外面，就回不到后台去开了。代码、迁移、部署脚本都不会自动设置它。
- **SMTP 配好了但实际发不出去**（密码错、服务商封了）：应用只有发信时才知道。密码没关闭时，登录页有「改用密码」，不受影响；发送失败写审计和错误日志。
- **密码已关闭、邮件又坏了**：在服务器上去掉 `PASSWORD_LOGIN_DISABLED` 并重启，或者在运营后台（已登录的会话）清空 SMTP，密码立即恢复。
- **应急命令全部照旧**：`pnpm admin:reset-password`、`admin:reset-2fa`、`admin:clear-ip-allowlist`、`admin:create` 不依赖邮件。`admin:reset-password` 设的新密码要在密码开着时才能用来登录，所以密码已关闭时先按上一条打开。
- **待负责人确认：何时关闭密码**。默认不关闭。建议的条件：正式环境 SMTP 稳定运行、所有员工都用验证码登录成功过至少一次、QA 账号改好之后，由负责人明确说一声，再改 `.env`。
- 关闭只影响「用密码登录」这一个接口。邀请设密码、改密码、重置密码等接口保留原样（数据不丢，随时可以重新打开）；彻底去掉密码是另一个任务，要新写 ADR。

### 2. 适用范围

| 谁 | 现在怎样 | 本任务后 |
| --- | --- | --- |
| 平台员工 | 密码 → 两步验证 | 密码**或**验证码 → 两步验证（同一个待验证会话，ADR 0030） |
| 租户员工（供应商后台） | 密码（没有两步验证） | 密码**或**验证码（验证码通过即得到正常会话） |
| 司机 H5 | 派单链接里的令牌，没有账号、不登录（ADR 0027） | **不变**，不在负责人决定的范围内 |
| 渠道 API 客户端、官网客人 | 客户端密钥、订单令牌 | 不变 |

账号怎么开通不变：只能邀请。验证码登录不会创建账号；还没接受邀请的账号收不到验证码。

### 3. 接口

每个入口（`/platform/v1`、`/tenant/v1`）各三个，都不要令牌：

| 接口 | 应答 |
| --- | --- |
| `GET …/auth/login-methods` | `{ email_code: bool, password: bool }`：登录页据此显示。只暴露「邮件配了没有」，`/health` 本来就公开这一点 |
| `POST …/auth/email-code/request` `{ email }` | 202 `{ expires_in_seconds, resend_after_seconds }`，**不管账号存不存在**；邮件没配置 503 `EMAIL_CODE_UNAVAILABLE`（和邮箱无关）；超限 429 `TOO_MANY_LOGIN_ATTEMPTS` |
| `POST …/auth/email-code/verify` `{ email, code }` | 成功和密码登录的应答完全一样；邮箱不存在、没发过码、码错、过期、用过、次数用尽，一律 401 `EMAIL_CODE_INVALID`；超限 429 |

验证码通过之后才可能出现 403 `ACCOUNT_DISABLED`、403 `IP_NOT_ALLOWED`（同密码登录：能拿到验证码的人本来就知道这个邮箱存在）。

租户入口的 `tenant_id` 只来自账号定位，请求里没有这个字段；同一个邮箱平台、租户两边的验证码互不相通（密钥派生和键都带入口）。

### 4. 验证码的安全

- **生成**：`crypto.randomInt` 取 000000–999999。
- **存储**：表 `email_login_codes` 一个邮箱一行。`code_hash` = HMAC-SHA256（密钥由 `AUTH_JWT_SECRET` 用 HKDF 按用途派生，消息含入口、邮箱、验证码）。不用裸 SHA-256：6 位数字只有一百万种，库被拖走后一秒就能穷举；HMAC 的密钥不在库里。不用 scrypt：登录前的接口不该每次都做慢计算，熵靠次数限制补。`email_key` 同样是 HMAC，表里没有邮箱原文。
- **有效期 10 分钟**；过期的行在下一次发码时清掉。
- **单码最多试 5 次**，用尽作废（查询条件里排除，数据库检查约束保证计数不超过 5）。
- **发新码时旧码作废**：一个邮箱只有一行（主键 `email_key`），发新码就是覆盖。
- **用过即作废，并发只成功一次**：
  1. 计数和读取在一条 `update … where attempt_count < 5 and expires_at > now returning` 里完成，行锁排队，并发猜码绕不过 5 次；
  2. 恒定时间比较（`timingSafeEqual`；没有这一行时比一个随机值，路径一样）；
  3. 通过的请求再 `delete … where email_key = $1 and code_hash = $2`，**只有影响到一行的请求算成功**。同一个码并发提交，数据库保证只有一个成功。
- **限速**（都按邮箱和来源地址的哈希计数，存在 `login_throttles`，邮箱不存在一样计数；来源地址按 ADR 0045 的 `rateLimitKeyOf`）：

  | 动作 | 维度 | 上限 |
  | --- | --- | --- |
  | 发码 | 同一地址 | 15 分钟 20 封 |
  | 发码 | 同一邮箱 | 60 秒 1 封 |
  | 发码 | 同一邮箱 | 15 分钟 5 封 |
  | 发码 | 同一邮箱 | 24 小时 20 封 |
  | 校验 | 同一邮箱 + 地址 | 15 分钟 5 次 |
  | 校验 | 同一邮箱 | 15 分钟 20 次 |
  | 校验 | 同一地址 | 15 分钟 50 次（`LOGIN_MAX_ATTEMPTS_PER_IP`，同 ADR 0030） |

  校验沿用 `reserveLogin`（入口 `platform-email-code`、`tenant-email-code`，和密码互不影响）；成功后校验的邮箱维度清零、地址退还，发码的 15 分钟计数清零；**发码的 24 小时计数不清零**：否则攻击期间本人每登录一次，攻击者就多一轮额度（代价见「已知限制」）。
- **暴力破解的上限**（2026-11-01 协调人确认用固定窗口，不改滑动窗口）：每个固定 24 小时窗口不超过 20 封、100 次猜测；跨窗口的短时峰值可到两倍（卡着交界不到 3 小时 40 个码、200 次），长期平均仍是每天 100 次。猜中概率：单个窗口 0.01%；短时峰值 0.02%；长期按每天 0.01% 累积，持续攻击一年约 3.6%（攻击期间审计里有成串的失败记录）。20 封同样是「拿这个系统轰炸别人邮箱」在一个窗口里的上限。租户账号没有两步验证，所以这个数字要算清楚；平台账号后面还有 TOTP。
- **限速按入口分开计**（保持现状）：平台、租户两个入口的计数互不相通，所以实际上限是同一地址 15 分钟 40 封（两个入口各 20），同一邮箱在两边都有账号时每天 40 封（各 20）。两边是两套账号、两个码，猜测的上限也按账号各算各的；合并计数要多一层键，而这个差别不影响单个账号的安全。
- **限速表里的邮箱键是不加密钥的 SHA-256**（保持现状）：和现有的 `login_throttles` 一致（ADR 0008）。`platform_users`、`tenant_users` 表本身就有邮箱原文，拿到这张计数表的人不会多知道什么，不增加泄露面。`email_login_codes` 不同，它的 `code_hash` 必须加密钥，否则一百万种验证码可以直接穷举。
- **SMTP 清空后，已发出的码在有效期内仍能登录**（保持现状）：校验不看邮件配置。清空 SMTP 是「以后发不了信」，不是「撤销已经发出去的信」；码的持有人已经证明能收这个邮箱的信，最多再有效 10 分钟；让校验也依赖配置，反而会让正在输码的人在配置切换时失败。

### 5. 防枚举

- **发码接口的应答和耗时与账号无关**：请求里只做参数校验、查邮件配置、占限速计数（都和账号无关），然后立刻 202。查账号、写库、发信全部放到应答之后的后台任务。发信最长 15 秒（ADR 0048），不会影响应答时间。
- **校验的路径也一样**：不存在的邮箱、停用的账号、待激活的账号，发码时同样写一行（`code_hash` 是一个随机值，任何验证码都对不上，也不发信）。所以之后校验时走的 SQL 完全相同，「有没有这一行」看不出账号是否存在。失败的审计也在后台写（要先查账号才知道归到哪个租户）。
- 后台任务丢了（进程在这一刻重启）：用户收不到信，重新发送即可。服务关闭时等后台任务结束（有发信的 15 秒时限兜底）。
- 后台任务的数量不用另外设上限：不存在的邮箱只有几条 SQL；要发信的只能是真实账号，每个账号受上面的限速。

### 6. 两步验证、IP 白名单和现有限制

验证码通过之后，走和密码登录**同一段代码**建会话，所以：

- 平台员工：会话是「待验证」的（15 分钟），`second_factor.status` 要求输入动态码或先绑定；此前除 `auth/me`、`auth/logout`、两步验证本身外一律 403 `MFA_REQUIRED`。
- IP 白名单：验证码通过后检查，不在名单里 403 `IP_NOT_ALLOWED`（验证码已消耗），之后每个请求也照旧检查。
- 必须先修改密码：标记不变，改密码仍要提供当前密码（临时密码就是本人手上的那个）。
- 账号停用：发码时不发；发出后才被停用的，校验时 403 `ACCOUNT_DISABLED`，不建会话。建会话前锁住账号再核对一次状态。
- 租户暂停、清退：和密码登录一样（暂停能登录，清退只读，ADR 0028），由鉴权函数判断。

### 7. 审计和日志

| 动作（审计 `resource` 是 `platform_user` / `tenant_user`） | 什么时候 | `after` |
| --- | --- | --- |
| `email_code_request` | 每次通过限速的发码请求 | `{ email: 打码, outcome }`，`outcome` 是 `sent` / `send_failed` / `no_account` / `not_active`；`send_failed` 多一个 `error`（ADR 0048 的错误分类） |
| `email_code_failed` | 校验失败 | `{ email: 打码, reason }`，`reason` 是 `invalid` / `exhausted`（这一次把 5 次用完） |
| `login` | 登录成功 | `{ method: "email_code" }`（密码登录仍是 null） |
| `login_failed` | 验证码对了但账号停用、不在 IP 白名单 | `{ email: 打码, reason, method: "email_code" }` |

- 验证码在任何地方都不出现：审计、日志、数据库、应答。上表 `after` 里的邮箱都打码，形如 `a***@example.com`；日志里没有邮箱。
- **例外：登录成功的 `login` 审计，`actor_email` 是完整邮箱**，和密码登录一致（操作人列表要认得出是谁，这时账号已经确认）。匿名的 `email_code_request`、`email_code_failed`、`login_failed` 的 `actor_email` 为空。
- **限速命中只写日志，不写审计**（`warn`，事件名 `email_code.rate_limited`，只有入口和阶段）：和 ADR 0008「被拦下的不写审计」一致，否则攻击者可以灌满审计表。
- 发送失败额外写 `error` 级日志（事件名 `email_code.send_failed`，只有错误分类）。
- 租户相关的审计写进租户自己的事务，租户管理员在操作日志里能看到；账号定位不到的 `tenant_id` 为 null，只有平台能看到。

### 8. 邮件

纯文本中文，主题「NOZOMI 登录验证码」（**主题里没有验证码**，手机通知栏和邮件列表不露出）；正文有验证码、哪个后台、10 分钟有效、不要告诉任何人、不是本人操作请忽略；**没有链接**。

直接调 `sendMail`，不经通知中心（M4-08）：通知中心的发件箱会把正文落库，验证码不能落库明文。

### 9. 登录页（docs/design/pages/login.md 第 6 节）

- 过渡期默认仍显示密码表单，邮件可用时多一个次要按钮「改用邮箱验证码」。**待负责人确认**：推荐先这样，密码关闭时页面自动变成只有验证码。理由：登录页不能依赖 `login-methods` 这个请求才显示（请求失败时必须还能用密码登录，也不闪屏），密码管理器的填充也不受影响。要改成「邮件可用时默认验证码」只是页面上的一处默认值。
- 验证码这一步：邮箱 →「发送验证码」→ 输入 6 位数字（`autocomplete="one-time-code"`，手机可一键填入）→ 登录；有重新发送的倒计时、「换一个邮箱」、「改用密码」。文案不说邮箱是否存在：「如果这个邮箱有账号，验证码已经发过去了」。
- `login-methods` 请求失败时按「只有密码」处理。

## 已知限制

- **知道邮箱的人可以消耗对方的额度**：连续请求发码（24 小时 20 封用完；每次发码还会顶掉本人正在等的那个码）或连续猜错（烧掉当前的码、15 分钟 20 次），本人当天或这 15 分钟内用不了验证码。过渡期本人还有密码；关闭密码之前要先评估这一点（第 1 节的「待确认」）。
- **一封邮件的安全等于邮箱的安全**：拿下邮箱就拿下租户账号。平台账号还有两步验证。
- **第一次绑定之前谁先登录谁绑定**（ADR 0030 已知限制）对验证码同样成立，但前提从「知道密码」变成「能收这个邮箱的信」。
- **登录成功不清零 24 小时发码计数**：本人一天发满 20 封（或被攻击者用掉）后，到窗口结束前发不了验证码，只能用密码或等窗口结束。这是为了不给攻击者续额度，取舍见第 4 节。
- **发码后账号被停用又重新启用，没用过的旧码在 10 分钟内仍然有效**：停用期间校验会被拒并消耗掉这个码；没有人试过的话，码还在，启用后可用。持有人能收这个邮箱的信，窗口很短，不为它加一条作废逻辑。
- 改密码、重设密码不作废已发出的验证码（它们属于「能收这个邮箱的信」的人，10 分钟后自然失效）。
- 耗时对齐是到「同一段代码路径」为止，数据库和网络本身的抖动不处理。
