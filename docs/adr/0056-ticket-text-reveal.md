# ADR 0056：工单详情的「查看原文」只给工单文字

- 状态：已采纳（2026-11-01，M4-24）
- 补充 ADR 0055 决定一「看原文」。

## 背景

ADR 0055 规定看原文只有一条路：`POST /platform/v1/orders/{id}/passenger/reveal`。工单详情也走它，于是：

- 工单没有任何打码内容时也显示「查看原文」，点了白记一条审计；
- 接口把这单的联系方式、备注和所有手写内容都传给浏览器，页面再滤出这张工单的（多传了原文）；
- 审计固定写 `fields: [name, phone, email, messaging, notes]`，看不出这次其实是在工单页看工单文字。

## 决定

1. **新接口** `POST /platform/v1/tickets/{id}/texts/reveal`：只返回 `{ texts }`，只有这张工单确实被打了码的文字，没有联系方式、没有别的工单。要 `ticket.read` 和 `order.read`，数据范围检查和工单详情相同。选新接口而不是给旧接口加参数，是因为响应形状不同（`passenger` 必填）；ADR 0055 的「只有一条路」修订为：订单详情一条、工单详情一条，都是打码内容的来源，都记审计。
2. **`texts_masked`**（工单详情响应）：工单文字里有没有打码内容。判断直接比这次响应打码前后的文字（`maskedTicketTexts`），不另算规则；看原文的接口用同一段代码取内容。所以「页面有按钮」和「点了有内容」来自同一份输入，内容里别处带的姓名（复核内容里的旧姓名）也算在内。
3. **没有内容不记审计**：`texts` 为空（没打码、脱敏过）时不写审计。页面过期或直接调接口同样如此。
4. **审计**：新动作 `view_ticket_text`（对象仍是 `order`，订单的审计历史里看得到），`after` 写 `viewed: "ticket_text"`、工单编号和号码、条数、来源，不写内容，也不列联系方式字段。订单详情的 `view_passenger` 不变：那里确实给了 5 个字段。
5. 脱敏过的单 `texts_masked` 为假。

## 限制

工单详情里还有几处打码但不在这个接口里：应扣款项的 `waive_reason`、关联复核的说明（走复核页）。ADR 0055 的 reveal 也不给 `waive_reason`。这几处只有它们被打码时，不显示「查看原文」。
