# ADR 0052：运营代租户回传履约状态

- 状态：已采纳（2026-11-01，M4-18）
- 补充 ADR 0027：履约回传多一个来源「平台代传」；状态机、包车完成必填、状态流水、Webhook、通知仍是 `applyFulfilmentEvent` 这一份代码。ADR 0027「时间一律用系统收到的时间」对司机和供应商不变，代传带报告时间（见「时间」）。
- 补充 ADR 0023：双人复核新增两类 `order.proxy_pick_up`、`order.proxy_complete`。
- 补充 ADR 0030：新增操作 `order.proxy_fulfilment`（发起）、`order.proxy_review`（审核），角色勾选表新增单独一格 `order_proxy`（代传履约）。
- 补充 ADR 0028：派车、到达两类评分事件从这里开始有人写（见「评分」）。
- 补充 ADR 0029、0034：事后加收窗口、投诉 14 天的起点改成系统记录完成的时间（见「时限」）。
- 编号说明：写这篇时 main 上最大是 ADR 0051、迁移 0160；迁移用 0170。
- 修订（2026-11-01，测试角色发现的缺陷，协调人决定）：「接到客人」改走复核、最早时间收紧、评分、时限、审核权限、原因的内容都按这个版本。

## 背景

需求：《平台运营端与渠道对接》「人工介入能力」（代租户回传履约状态，租户系统故障时，全部留审计）、接口表 `POST /orders/{id}/events（代回传）`；《用车报价服务平台》接口表 `departed / arrived / picked_up / completed，带时间和定位`。
验收报告 M3-06 缺陷 1：接口 404、页面没有入口，供应商系统故障时运营没有办法处理。

## 决定

### 接口

`POST /platform/v1/orders/{id}/events`，请求头 `If-Match` 带订单版本，请求体 `{ type, occurred_at, reason, actual? }`（严格，多余字段拒绝）。

| 事件 | 结果 |
| --- | --- |
| `departed`、`arrived` | 200，直接生效 |
| `picked_up`、`completed` | 202，发起一条双人复核；另一位同事批准时才生效 |

**不接受定位**：运营不在现场，给不出真实定位。

### 和现有规则的关系

- 状态机、包车完成必填、状态流水、供应商 Webhook、通知都走 `applyFulfilmentEvent`，没有第二份规则。不能跳步、不能重复（409 `ORDER_STATE_INVALID`）。
- **没付款、已取消**：状态机本来就不放行，这里先单独判断并写明。**救援改派中、已转出**：不能代传（原供应商已不能操作；救援流程不被绕开）。**待派车**（`confirmed`）：不能代传，因为不能跳过派车；本任务不做运营代派车（见「本期不做」）。
- **并发**：和供应商、司机的回传一样先锁订单这一行，再判断状态。同时到的同一事件只有一个成功，另一个 409，流水只有一条。先判状态再比版本（和派车同样的顺序）。
- **If-Match**：运营是看着页面上的状态做决定的。这期间供应商改派、改单都会让判断过时，版本不一致一律 409 `VERSION_CONFLICT`，要刷新后重新看。比供应商的接口更严（调度系统是机器连续上报，运营是人隔一段时间才提交）。

### no-show 不能借这个接口绕开

no-show 不在这个接口里（`type` 不认它）。`no_show_claimed` 状态下代传一律 409。代传的「已到达」没有定位，所以 `arrival_distance_m` 为空，no-show 第 1 项（定位距上车点 ≤ 300 米）不满足：

- 代传不能给 no-show 提供证据，把到达时间往前填也没有用；
- **代价**：运营代传了「已到达」后，这一单司机不能再提交 no-show（`NO_SHOW_EVIDENCE_INCOMPLETE`）。这是偏向客人的方向，页面在确认框里写明。司机还能用 H5 时，应该让司机自己点。

### 时间

代传的事常在事后才补，用系统收到的时间会让履约记录失真。所以 `occurred_at` 必填，写进订单的履约时间和状态流水；系统收到的时间另存为 `recorded_at`，两者都看得到。校验（`proxyFulfilmentTimeIssue`，400 `VALIDATION_FAILED`）：

| 原因 | 规则 |
| --- | --- |
| `IN_FUTURE` | 不能晚于现在。不留误差：将来的时间会让之后司机按系统时间上报的事件排在它前面 |
| `BEFORE_PREVIOUS` | 不能早于上一个履约节点（派车 / 出发 / 到达 / 接到），流水的时间不会倒退。页面只填到分钟而节点带秒，所以同一分钟不算早，写入时按上一个节点的时间算 |
| `TOO_EARLY` | `departed`、`arrived` 不能早于用车时间前 24 小时；`picked_up`、`completed` 不能早于用车时间前 3 小时（`PROXY_FULFILMENT_RULES.reviewedEarliestHoursBeforeService`，可调）。接到客人不可能比用车时间早这么多。只限代传，不管司机和供应商自己上报 |
| `TOO_OLD` | 不能早于现在之前 7 天：异常队列 24 小时内催，再久的补录应走工单 |

发生时间写进履约记录和状态流水；**不影响**准时到达率（代传不计入，见「评分」）和加收、投诉时限（见「时限」）。试运营和评分的完成单数按流水的发生时间计。靠操作留痕和供应商可见防滥用，见下。

### 接到客人、完成要双人复核（决定和理由）

**`picked_up`、`completed` 走双人复核，`departed`、`arrived` 不走。不做撤销功能。**

`picked_up` 把订单推进服务中：状态机只能再到 `completed`，客人和运营都不能再取消，no-show 也不能再提交。这是不可逆的后果，单人不能造成（测试发现：离用车 20 小时，一位运营就能把单推进服务中，客人从此退不了款）。

`completed` 直接动钱，而且改不回来：

1. **进账单**：`billing.ts` 里已完成的单按结算价进供应商应付，一个人能让平台为没跑的单付钱，这正是双人复核要防的（需求把「付款给租户」列为敏感操作）。
2. **是终态**：`in_service → completed` 之后状态机没有出路，只能走工单和调账。
3. **打开向客人收钱的窗口**：已完成之后供应商才能提交事后加收，从客人保存的卡上扣款。
4. **计入评分和试运营转正**：`loadTrialProgress`、评分窗口都按完成事件计数。

`departed`、`arrived` 不产生这些后果（改派、取消都还能挽回），而且故障时运营要跟着行程实时操作，每一步都等复核就没法用了。

- 发起要 `order.proxy_fulfilment`，审核要 `order.proxy_review`。发起人不能审核自己的（通用规则和数据库约束都拦）。`orderScoped`：范围外的看不到也审不了。
- **待复核期间不改订单**，单子停在原来的状态。供应商或司机这时回传完全正常（他们恢复了就是最可信的来源）；之后批准得到 409 `APPROVAL_STALE`，只能驳回，不会生效两次。详情的 `pending_proxy_review` 只看下一步，这种旧复核不再挡着页面。
- 同一张单同一步同时只能有一条待复核（在订单行锁里查），重复发起 409 `PROXY_REVIEW_PENDING`。
- 批准时按当时的数据重新校验状态、发生时间和包车实际时长里程。

### 评分（ADR 0028 的写入一直没接）

测试发现：`recordPerformanceEvent` 的 `dispatch`、`arrival` 两类从来没人调用，按时派车率、准时到达率（各占 25%）永远是「没有数据」，这是 M4-18 之前就有的缺陷。这里接上：

| 指标 | 谁写 | 口径（需求《平台运营端》评分表） |
| --- | --- | --- |
| `arrival` | 供应商、司机自己回传「已到达」（`applyFulfilmentEvent`，事务内） | 「用车时间前到达上车点」：系统收到的时间不晚于用车时间算准时 |
| `dispatch` | 供应商第一次派车（`assignOrder`） | 「截止时间前派车」：`dispatchOverdue` 为假算按时；改派不算 |

- **平台代传的到达不写这条**（时间是运营填的，避免被刷）。派车没有代传入口，所以不需要排除；以后加运营代派车要同样排除。
- 接机单按用车时间（下单时的计划到达）判断，需求没有按实际落地顺延的说法，所以航班延误后司机等到落地才到，也算迟到。**待负责人确认**：要不要改成按实际落地时间算。
- **已有订单没有回填**：上线之前的派车和到达没有事件，评分窗口要约 90 天才都是新口径。上线后这两项开始有数据，供应商的分会变，比价排序也跟着变（完成不足 20 单的仍是默认分）。
- 权限：这两条在租户事务里写，给 `nozomi_app` 开 `insert`，策略只放开这两类，投诉和履约失败仍然只有平台能写。

### 时限

代传完成常是回填的。事后加收窗口（24 小时）和客人投诉（14 天）**从系统记录完成的时间起算**（`orders.completed_recorded_at`，代传时是批准生效的时间），不是运营填的发生时间，回填不能让供应商和客人丢权利。自己回传的两个时间相同；M4-18 之前完成的单没有记录时间，按 `completed_at`。

### 原因的内容

`reason` 去掉零宽、控制、双向控制、BOM、软连字符（以及空白、组合符号、显示成空白的字母）后必须有实际内容，否则 400（`validation.ts` 的 `visibleText`，可复用）。内容原样保存。

### 权限

- 发起 `order.proxy_fulfilment`：超级管理员、运营。**客服不给**（客服已有代取消、改单，但这个操作会写供应商的履约记录，影响评分和账单，先收紧；要放开改一行即可，或用自建角色）。只读、风控、财务都没有。
- 审核 `order.proxy_review`：超级管理员、运营、财务。需求说的「主管」没有单独的角色；这两个是已有审核职责里最接近的（财务管账单，运营互审工单和救援）。**不复用 `payment.manage`**，这样已有自建角色不会自动多出审批权。
- **角色勾选表单独一格 `order_proxy`**（查看 / 编辑 / 审核），不放进「订单」那一格：自建角色存的是勾选，放进去的话已有的自建角色会在没人审核的情况下自动多出这些权限。
- 数据范围：和其他订单接口一样先过 `assertPlatformOrderInScope`，范围外和不存在都是 404。

### 留痕和谁能看到什么

| 内容 | 运营后台 | 供应商（接口、页面、Webhook） |
| --- | --- | --- |
| 来源是平台代传 `source: platform_proxy` | 有 | 有 |
| 报告时间 `occurred_at`、系统收到的时间 `recorded_at` | 有 | 有 |
| 原因、发起人、批准人、复核编号（`proxy`） | 有 | **没有** |

- 审计日志：每次生效一条（`order` / `update`，含事件、报告时间、原因、发起人；完成另有批准人和复核编号）；发起完成复核时另有一条 `approval` / `request`。审计 `tenant_id` 为空（和代取消一样），供应商的操作日志里看不到。
- **供应商看不到原因（可回退的保守选择）**：原因是运营手写的自由文本，无法机器保证不含对外价、加价比例（规则 4）；操作人是平台内部分工（工单也不给供应商看是哪位客服）。需要解释时走工单。以后要开放，加一个字段即可；反过来，泄露出去就收不回来。页面确认框写明供应商看得到什么。
- 规则 4 不变：这里没有给 `/tenant/v1` 增加任何价格字段。

### 通知

通知和 Webhook 都在 `applyFulfilmentEvent` 里，`order.driver_arrived` 仍走 `enqueueNotification`，去重键不变，所以同一次到达不会重发。`order.status_changed` 的 `data` 对代传多带 `source`、`occurred_at`，调度系统恢复后能分清这一步不是自己上报的。

### 页面

运营订单详情（`order.proxy_fulfilment`，否则不显示）：「代供应商回传履约」按下一步显示一个按钮（状态只能向前走一步，所以没有选择），确认框含发生时间（城市当地时间）、必填原因、包车完成的实际时长和里程、要不要另一位审核、供应商看得到什么。复核中显示提示、不显示按钮。状态流水里标「平台代传」。供应商订单详情的状态流水同样标「平台代传」和系统记录时间。

### 乘客联系方式打码（M4-19）

需求《平台运营端》「个人信息保护」：乘客姓名、电话、邮箱列表里默认打码，点「查看」才显示全文并记日志。查下来运营后台完全没有落实，这里按范围修了：

- 运营的订单列表、订单详情（含改单的改前改后）、推送记录（订单详情里的、`/platform/v1/webhook-deliveries` 的）默认打码（`privacy.ts`），接口里就没有原文，不只是页面藏起来。
- 新接口 `POST /platform/v1/orders/{id}/passenger/reveal`（`order.read` + 数据范围）：给全文，每次记一条审计（`order` / `view_passenger`，不含联系方式本身）。只读员工一样走这里。
- 按乘客姓名、电话筛选（`passenger=`）照旧：要知道原文才筛得到。
- 供应商（付款后看得到，需求写明）、司机 H5 不变。

**还没落实**（比这个任务大，已汇报）：审计日志的改单前后值、工单和备注里手写的内容、待审核详情里的内容没有打码；姓名电话邮箱仍是明文存库（ADR 0026 待办）；订单完成 180 天后自动脱敏没有做。

## 本期不做

- **运营代派车**（`POST /platform/v1/orders/{id}/assign`，M3-06 报告同样提到 404）：不在 M4-18 范围。结果是：供应商系统在派车前就故障的单不能代传，只能走已有的救援改派。
- **代传 no-show**：见上。

## 回退

迁移 0170 只加列和权限，代码回退后留着不影响。代码回退后，已写入的代传事件仍是合法的流水（`detail` 多几个键，`actor` 本来就允许）。待审核的 `order.proxy_pick_up`、`order.proxy_complete` 要先驳回或撤回，否则代码回退后这一类不再登记。
