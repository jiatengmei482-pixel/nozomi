# ADR 0083：区域共享库——已有区域对所有供应商开放引用，引用即复制并记住来源和图形版本

- 状态：已采纳（M8-31 实施，按 roadmap M8-31 的验收标准；业主夜间计划 2026-11-11 授权）。
- 补充 ADR 0015（区域）、ADR 0075（区域用途）、ADR 0077（QA 测试供应商）。
- 编号：写这篇时 ADR 0082 已被 M8-32（PR #155，乘车人字段）占用，这里用 0083。

## 要解决的问题

每家供应商都要自己画「东京 23 区」「成田机场周边」这类区域，重复劳动，画得也不一样。业主要：已有的区域对所有供应商开放引用，系统没有的自己新建、新建的自动进共享库；只共享名称和形状，不显示创建者，不共享价格和加价；不悄悄改别人已引用的区域和报价；现有区域和报价一分不变。

## 决定

### 1. 共享库不是新表，就是各供应商启用中的「原创」区域

- 共享库 = `areas` 里 `status = 'active'`、`shared_source_area_id is null`（不是引用来的副本）的区域，所属供应商不是测试供应商（`tenants.is_test_tenant`）、没有清退。
- 所以「已有区域开放引用」「新建自动进库」不需要任何数据搬运：迁移 0340 只加列，不写数据（迁移规则不允许预置业务数据），现有区域上线即在库里。
- 读库走平台事务（迁移 0016 已给 `nozomi_platform` 读 `areas` / `area_polygons`），租户事务的行级安全不变：供应商仍然读不到别家的区域表，只能通过共享库接口看到名称和形状。
- 对外只给：编号、城市、名称、图形（种类 + 坐标）、图形版本、块数、更新时间。**不给**创建者（租户）、备注名、业务类型、用途、商品用量、价格、加价。自己建的区域不出现在自己看到的库里。

### 2. 引用 = 复制一份到自己名下，记住来源和图形版本

- `POST /tenant/v1/areas/from-shared`：在自己名下新建区域，城市、图形照抄来源现在的版本（只抄种类和坐标，算作「粘贴的」），名称默认用来源的、可以改，业务类型和用途自己定；`areas.shared_source_area_id` / `shared_source_shape_version` 记来源。新增区域的全部检查、幂等、审计照旧（同城重名 409）。
- 副本是引用方自己的区域：能改名、改图形、停用、删除，挂价格和加价都和自己画的一样；租户隔离不变。
- 副本不进共享库（否则同一块区域会出现很多份）。引用方把副本的图形改得面目全非也仍算副本——它的来源记录还在，这是有意的简化。
- 来源在别的租户名下，所以不加外键；来源被停用、删除后副本照旧可用，只是看不到新版本了。

### 3. 图形版本：只有图形变了才加一；别人的副本不会被悄悄改

- `areas.shape_version`：现有区域从 1 开始；修改区域时图形有任何变化才加一（改名、改业务类型、改用途、停用启用都不加）。共享库里的「版本」就是它。
- 来源改了图形 → 库里版本加一；**已经引用的副本一分不变**，它挂的报价也不变。区域列表、详情的 `shared_source.latest_shape_version` 告诉引用方库里有新版本，由引用方自己决定是否切换。
- `POST /tenant/v1/areas/{id}/sync-shared`（带 `If-Match`）：把副本的图形换成来源现在的，名称、业务类型、用途不动；走修改区域同一套检查（运营范围变小时报价区域不能多出「不在运营区域里」的部分等）和审计（审计里记来源版本从几到几）。来源已不在库里时 409 `SHARED_AREA_UNAVAILABLE`。
- 为什么不存历史版本：副本自己就保存了引用时的形状，库里只需要「现在的形状 + 版本号」就能判断有没有新版本；不用新表、不用搬数据。

### 4. 新建时提示相似区域

- `POST /tenant/v1/shared-areas/similar`：同一个城市里名称相同（`areaNameKeys` 归一后任意一种语言相同）或营运区和你画的营运区重叠（`ringsOverlap`）的共享区域，同名在前，最多 5 个。新建区域页在你填了名称、画了营运区后查一次，提示「共享库里已有相似区域」，可以直接引用。只是提示，不拦保存。

### 5. QA 测试供应商不进库

- 测试供应商的区域不出现在共享库（库的条件里排除）。测试供应商可以引用库里的区域（引用不改来源，不影响别人）。

## 不在这次做（记入 roadmap 后续）

- **平台编辑 / 合并重复区域**（验收标准第 2 条的后半句）：平台改的是某家供应商自己名下的区域，会直接改它的报价范围，需要业主定规则（改原创区域？还是只在库里隐藏重复的一份、把引用指向另一份？）。先写进 roadmap 待业主决定；本 ADR 的结构（来源编号 + 图形版本）两种做法都能接上。**已由 M8-31b 按业主选的 B 做完，见文末「补充」。**
- 共享库里的地图预览挑选（现在是按城市列出、按名称搜索、点开看形状）。

## 影响

- 迁移 0340：`areas` 加 `shape_version`（默认 1）、`shared_source_area_id` / `shared_source_shape_version`（成对为空）、共享库查询的部分索引。不写数据、不改已有行的内容（新列的默认值除外）。
- 区域的应答（列表、详情、区域地图、运营区域地图）多了 `shape_version`、`shared_source`；只增不改。
- 报价不读这些新列，现有报价一分不变。

## 补充（M8-31b，2026-11-13）：平台去重 = 在库里隐藏重复的一份，以后的引用指向另一份

业主 2026-11-13 在两种做法里选了 B：**只在共享库里隐藏重复的一份、以后的引用指向另一份；不动任何供应商现有的区域、已引用的副本和报价**。本节补充上面的决定，不推翻其中任何一条。

### 结构：一张平台标记表，不改 `areas`

- 迁移 0350 建平台表 `shared_area_duplicates`：被隐藏的区域 `area_id`、保留的区域 `keep_area_id`、原因、谁何时标的（`marked_by` / `marked_at`）、谁何时为什么撤销（`revoked_*`）。撤销不删行，留作历史；同一区域同时最多一条生效中的（部分唯一索引）。
- 两个区域都在供应商名下，和 `shared_source_area_id` 一样不加外键；在不在库里由服务层在标记时现查。只给 `nozomi_platform` 读、增、改，租户角色没有任何权限。
- `areas` 的行、图形、用途、版本一概不改：被隐藏的区域在它自己的供应商那里照常显示、照常报价，只是别家在库里看不到它。

### 库里的两种「在不在」

- **在库里**（第 1 节的条件）：已有副本看来源用它。被隐藏的仍「在库里」。
- **看得到**（在库里且没有被隐藏）：共享库列表、详情、查相似，以及以后的引用用它。

### 以后的引用：自动转到保留的那份

- `POST /tenant/v1/areas/from-shared` 传的是被隐藏的那份时，改为复制保留的那份，副本的 `shared_source` 记保留的那份（不是请求里的那份）。不报错的理由：业主原话是「以后的引用指向另一份」；页面停在旧列表上的供应商点「引用」也能顺利拿到同一块区域，不必刷新重来。
- 详情 `GET /tenant/v1/shared-areas/{id}` 对被隐藏的那份是 404（和列表一致，「不再出现」）。
- 实际要复制的就是引用方自己名下的区域时（典型：他引用的那份被隐藏，保留的正是他自己画的）不复制，409 `SHARED_AREA_IS_YOURS`，页面说「这块区域你名下已经有了」——不让它落到看不懂的「同城重名」上。引用被转走时，页面按应答里的来源和所选的不同提示「已改为引用…」。
- 不形成链：被隐藏的不能当保留的，保留的不能被隐藏（先撤销指向它的标记），所以最多转一次。保留的那份后来被它的供应商停用、删除时，引用被隐藏的那份是 404（不会悄悄去复制别的区域）；运营后台的列表会标出「保留的那份已不在库里」，由运营撤销或改指向。

### 已有副本的来源不改

- 已经从被隐藏那份引用的副本：来源编号、来源版本不变；来源改了图形照旧提示「库里有新版本」、照旧能切换（`sync-shared` 读来源时不看隐藏标记）。
- 理由：(1) 业主要求「不动任何供应商现有的区域、已引用的副本和报价」——把副本的来源改指向保留的那份，等于悄悄换掉它将来「切换」时会拿到的形状，切换一次报价范围就变了，违背第 3 节「别人的副本不会被悄悄改」；(2) 被隐藏的那份仍是一块真实、启用中的区域，引用它的供应商当初选的就是它，继续跟它的版本最符合供应商的预期；(3) 两份是不是「同一块」是平台的判断，可能撤销，副本跟着来回改来源反而难以解释。
- 标记期间转到保留那份的新副本，撤销后来源也不变（理由同上）。

### 平台接口、权限、审计

- `GET /platform/v1/shared-areas?city_id=`（`master_data.read`）：一个城市里在库里的全部区域（含隐藏中的，才能撤销），每项带疑似重复（同名或营运区重叠——和供应商新建时的相似提示同一个判断，提到 `@nozomi/domain` 的 `sharedAreaSimilarity`）、副本数、隐藏标记。仍不显示创建者：平台只按名称、形状、副本数决定留哪份。
- `POST /platform/v1/shared-areas/{id}/mark-duplicate`、`…/unmark-duplicate`（`master_data.manage`）：沿用主数据的权限——共享库是全平台共用的资料，维护它和维护城市、地点是同一批人（主数据运营、超级管理员）；不新加权限，角色矩阵不变。能不能标的规则在 `@nozomi/domain` 的 `duplicateMarkProblem`。标记、撤销用一把事务级咨询锁排队，两人同时反向标记时后一个被拦下（不会形成环）。
- 不走双人复核：不改任何供应商的区域、副本和报价，撤销即可完全恢复。每次标记、撤销写审计（对象 `shared_area_duplicate`，操作 `create` / `revoke`，前后值里有两个区域的编号和原因）。
- 规模上限：去重列表一个城市最多取 500 个区域（多取一条判断是否截断），疑似重复在内存里两两比对（每对先比名称、再比营运区图形），500 个时约 12.5 万对，对现在每城几十个区域的规模足够；哪天单城接近上限，再改成先按外包矩形筛候选。
- 和主数据、区域地图一样不按员工的城市范围筛（共享库是全平台的公共资料）。
- 运营后台页面：主数据分组下的「共享区域」（`/platform/master/shared-areas`，docs/design/pages/master-data.md 第 13 节）。

### 影响

- 迁移 0350 只建表和索引、授权，不含任何数据，不改 `areas` 的任何行。
- 供应商侧的接口只多了一种情况：被隐藏的那份不出现在库里、引用它时转到保留的那份；应答结构不变。报价不读这张表，现有报价一分不变（集成测试对同一个询价前后逐字段比对）。
