# ADR 0059：价格表导入第 0 阶段——只读 dry-run 工具和映射报告

- 状态：已采纳（2026-11-02，M4-28）
- 不改变 ADR 0012、0014、0015、0016、0018、0020 的任何决定。这里只定工具的边界，并记下要写入之前必须确认的事。

## 背景

业主有一份多 sheet 的价格表（说明、车型、10 个国家 / 地区的路线、里程价），希望导入平台。表的结构是「出发地 + 目的地 × 车型」，而现有框架的价格是「区域 × 车型组 × 方向」，两者不是一一对应。写入之前要先弄清楚：表里多少内容框架放得下，多少放不下，多少要业主决定。

## 决定

### 第 0 阶段只读，没有写入模式

- `pnpm price-sheet:report --file <xlsx> [--expect-sha256 <值>] [--master <json>] [--out <目录>]`。
- 不连数据库，不联网，不读配置和密钥，没有写入开关。写入功能等业主确认后另做，届时另写 ADR。
- 除了 `--out` 目录里的 `report.md`、`report.json`，什么都不写；任何一步失败都不创建目录。
- 主数据只通过 `--master` 文件输入，由有权限的人从 staging 只读导出；没给时只输出归一化后的待匹配清单。工具自己不连 staging。

### 真实价格不进仓库

- 价格表和报告都不提交。报告含价格举例，`--out` 落在 git 仓库里面时拒绝运行；不给 `--out` 时写到系统临时目录；文件权限 600；终端只打印统计数字。
- 测试只用测试里构造的虚构小表。本文也不写任何真实价格和路线。

### 文件是不可信的输入

- 复用 `apps/api/src/integrations/xlsx.ts`（ADR 0019）：文件大小、解压后大小、标签数、行列数都有上限，拒绝 DTD 和实体声明，不引入新依赖。
- 公式不取值，也不看缓存值，记为问题。价格只接受十进制正整数原文，不经过浮点数；文字、小数、科学计数、错误值、逻辑值都记为问题，不算价格，也不算空。
- 读取层在找不到指定名字时退回第一张表，所以逐张核对读到的表名。读取层不提供表的清单，工具另从 `xl/workbook.xml` 取名字，只用来报告多余和隐藏的表，不决定读什么。
- 结构不对（缺表、表头不对）拒绝生成报告；单元格层面的问题逐条列出，其余照常统计。
- 表里的名字放进 Map，不当对象的键；写进 Markdown 前转义。

### 不猜测

- 端点类型只看名字里明确的字（机场、空港、结尾的「站」、码头、邮轮、港口……），判断不了的算地点。以「港」结尾的既可能是港口也可能是城市，不据此改分类，和以「场」结尾、口岸一起列为存疑，由人看。
- 大类先看机场：一端是机场、另一端不是的都归「机场↔非机场」，其中机场↔车站、机场↔码头的结论不同，在小类里分开。
- 城市匹配：同一国家内，归一化（全半角、空白、大小写）后和某个语言的名称完全相同才算。不做繁简转换，不拆分，不去后缀，不模糊匹配。几个城市都相同的是歧义，不选。
- 同名的车型列保留两列，报告成歧义；重复行价格不一致的不选其中一行。
- 车型组编码按 `VG-等级-座位数` 给建议（用 `vehicleGroupCodeIssue` 校验）。名字里没有座位数、有不认识的词的不给。Premium、Bus、Van、SUV 不在现有四个等级里，等级留空。

### 分类的依据

| 表里的内容 | 现有框架 | 结论 |
| --- | --- | --- |
| 机场↔地点、车站↔地点 | 接送机：商品的接送点 + 区域 | 框架内 |
| 单向列出（说明页写明反向同价） | `direction=both` | 框架内；说明页没写就要确认 |
| 两个方向都列且价不同的接送机 | `pickup`、`dropoff` 各一条 | 框架内 |
| 两个方向都列、某车型只有一个方向有价 | 规则说的是「未列出的路线」 | 需业主确认 |
| 车站↔机场、车站↔车站 | 一条价只有一个接送点，另一端要当区域 | 需业主确认 |
| 码头↔任何地方 | 地点类型没有码头；接送点只能是机场或车站 | 框架外 |
| 地点↔另一地点、机场↔机场 | 点对点的价是「区域 × 车型组」，没有起点 + 终点的价；起终点在不同区域时两端的区域价都算、取最低（ADR 0020） | 框架外 |
| 地点↔同一地点 | 能放成同一区域内的点对点价，但跨区行程会按这些区内价取最低报出 | 需业主确认 |
| 里程价 | `mileage_time`：起步里程取说明页的公里数，起步时长和每分钟单价填 0 | 框架内；作为兜底怎么挂区域要确认 |

## 写入之前必须由业主确认的事

1. **价格的含义**：表里的价是供应商结算价，还是对外价？价格规则存的是结算价，对外价由加价算出。表名是「官网」费率，不确认就不能写入。
2. **挂在谁名下**：哪个租户、哪个子品牌。全表是日元，路线分布在 10 个国家 / 地区；金额按子品牌的结算币种存。
3. **区域图形**：价格挂在区域上，区域必须有营运区图形，表里只有名字。图形从哪里来。
4. **跨城路线**：商品的接送点和区域要在同一城市。机场到邻近城市的路线怎么归属。
5. **点对点**：地点到另一地点的起终点价框架放不下。是扩展框架（要新的 ADR），还是这部分不导入。同一地点的价要不要导入（见上表的风险）。
6. **码头、车站↔机场、机场↔机场**：要不要加地点类型或改模型。
7. **同名列**：同一 sheet 里同名、容量相同、价格不同的车型列分别是什么车型。
8. **车型组**：要新建哪些；Premium、Bus、Van、SUV 对应什么等级；没有座位数的车型座位数是多少；同名不同国家容量不同是不是同一个车型组。
9. **里程价当兜底**：同一组合同一天只能有一条价，几个区域都能报时取最低，「没有固定线路时才用」框架不能直接表达。
10. **生效日期**：表里没有，价格规则的开始日期必填。
11. **一个方向有价、另一方向没价**：是不卖，还是同价。
12. **跨国家 / 地区的端点**：同一个端点名出现在几个 sheet 里、跨境路线属于哪里。

这些问题不影响第 0 阶段。按负责人的长期指示，第 0 阶段只出报告，不替他决定。

## 没有做的

| 内容 | 什么时候 |
| --- | --- |
| 写入（区域、商品、车型组、价格规则） | 业主确认上面的事之后，另开任务、另写 ADR |
| 读 `places`（机场、车站）的匹配 | 写入阶段需要时再扩展 `--master`；现在只比较城市 |
| 区分表里的黑字和蓝字（原有价 / 补齐价） | 读取层不读样式；里程价有来源列，路线表要确认后再说 |
