# ADR 0069：预订页重新设计（M8）的开发方案

- 状态：方案（2026-11-09，M8-01）。A 类按本篇直接开做；B 类每一项等业主确认后再另写 ADR 开工。
- 依据：业主 2026-11-09 的设计方案（`/home/codespace/import/booking-redesign-spec.txt`，原 HTML 设计稿的文字版，不进仓库）。
- 相关：ADR 0020（报价引擎）、0032 / 0035（官网下单、点对点和包车）、0041（谷歌密钥由后台填）、0044（地址搜索后端代调谷歌）、0046（官网付款）、0063（价格表超出框架的改进方案）、0066（M6 设计规范）、0068（车型标识）。
- 规则：价格规则、订单、支付逻辑**不顺手改**；旧的「城市 → 接 / 送 → 机场」下拉框在新流程验收通过后才删。

## 设计方案要什么（摘要）

客人只填出发地、目的地两个地址 + 用车时间 + 人数（行李选填），系统自己判断机场、接机还是送机、落在哪个报价区域，列出坐得下的车型和一口价。三步：① 填行程（「接送 / 按小时包车」两个标签）→ ② 选车型（按价格从低到高，坐不下的隐藏，车型名 + 代表车型 + 最多几人几件 + 一口价 + 包含什么）→ ③ 填乘客信息并付款（右侧一直显示行程和价格，下方显示取消规则）。链接带 from / to / date / time / pax 参数，打开就报价。

## A 类：在现有框架内直接做（按批次）

### A1 后端：按两个坐标报价（M8-02）

新接口 `POST /site/v1/quotes/by-points`（只在官网渠道下，`/sales/v1` 不动，见 B7）：

- 请求：`pickup { name, lat, lng, kind? }`、`dropoff { 同 }`、`service_local`（当地时间）、`passengers`、`luggage?`；包车标签用现有的包车请求，不走这个接口。`kind` 是地址搜索给的类型（机场 / 其他），客人手填的地址没有类型。
- 认出机场：一端的 `kind` 是机场，或坐标离某个**启用**的机场（地点主数据）不超过 **3 公里**（业主已定）。几个机场都在 3 公里内取最近的。只认渠道授权范围里的城市的机场。
- 判断方向：出发地是机场 → 接机；目的地是机场 → 送机；两端都是机场 → 按出发地算接机；两端都不是 → 点对点。
- 然后按方向组装成**现有**的询价请求，调用现有的 `createSalesQuotes`（和 `POST /site/v1/quotes` 同一条路）：价格规则、区域判断、比价中标、30 分钟报价快照、询价日志全部照旧。
- 应答：`trip_type`、识别到的机场（编号、名称）、每个车型的报价（沿用现有 `SiteQuote`：车型组含 M7 的车型标识、一口价、免费等待、取消政策、`quote_id`）按价格从低到高排、`expires_at`；报不出时给现有的拒绝原因（时间太近给最早可订时间、人数太多、地址不在服务范围），由页面给出说法。
- 不新增表、不新增迁移；询价日志的 `request` 多记 `mode: by_points` 和识别结果。
- 测试：单元（3 公里边界、两端都是机场、取最近机场、方向判断）；集成（真实库：识别对了以后报价和 `POST /site/v1/quotes` 同一请求完全一致——**证明价格逻辑没变**；渠道授权外的机场不认；点对点；报不出价的几种原因）；OpenAPI 同步。

### A2 后端：地址搜索不用先选城市（M8-02）

`GET /site/v1/places/search` 加一种不带 `city_id` 的用法：按渠道授权的国家 / 地区做 `regionCode`，不限城市范围；应答每个候选多一个 `kind`（谷歌的 `primaryType` 是机场时为 `airport`，否则 `other`）。仍然是后端代调（密钥不进浏览器）、短时缓存、每日上限（ADR 0044 的做法不变）。同时把平台主数据里名字匹配的机场、车站排在最前（不依赖谷歌也能搜到机场，含航站楼）。

> 费用提示：搜索次数会比现在多（不用先选城市，客人更容易直接搜）。仍受 `GOOGLE_PLACES_DAILY_LIMIT` 每日上限保护，超过就降级为「从常用地点选」。

### A3 前端：新预订页第 1、2 步（M8-03）

- 新页面先放在 **`/book/new`**，旧页面 `/book` 不动，验收通过后再切换（A5）。
- 第 1 步：「接送 | 按小时包车」标签；出发地、目的地两个地址框（输入后出候选：平台的机场 / 车站在前，谷歌结果在后；谷歌不可用时只用平台地点和地图选点）；日期、时间、人数、行李（选填，默认按人数推算的规则写进页面说明）；一端识别为机场时时间栏改叫「航班落地时间（当地）」并提示「已识别为接机」；右侧（手机在下方）「一口价包含」用现有数据：专车、举牌、免费等待分钟数（来自报价）。
- 第 2 步：行程条（可修改）、「按价格从低到高 · 坐不下的已隐藏」、车型卡（车型名、M7 车型标识、一口价、选择）。手机底部固定「车型 · 一口价 [下一步]」。
- 链接参数：`from` / `to`（平台地点编码，或 `纬度,经度` 加可选名称）、`date`、`time`、`pax`、`bags`，打开即报价；参数不合法时只是不预填，不报错。
- 报不出价：按拒绝原因给说法；地址不在服务范围时显示「这个地址暂时没有在线报价，请联系客服」和现有的客服电话（不收集客人信息，留资见 B2）。
- 按 M6 设计规范；手机优先；亮暗、360px、axe、键盘。

### A4 前端：第 3 步填信息并付款（M8-04）

复用现有的下单和付款（`CheckoutPage` 的字段、校验、`POST /site/v1/orders`、Stripe 银行卡），只改排版：左边表单（乘客、联系方式、接机行程才显示航班号和举牌名、备注、取消规则），右边一直显示行程和价格；手机单栏。下单、付款、订单、通知逻辑一行不改。

### A5 切换和删旧（M8-05，验收通过后）

`/book` 换成新流程，旧的「城市 → 接 / 送 → 机场」下拉框删除；旧链接 `/book?...` 能识别的参数转到新页面。只有 A3、A4 验收通过后才做。

## B 类：超出现有框架（改进方案和风险，等业主确认）

| 编号 | 内容 | 方案 | 需要业主 / 风险 |
| --- | --- | --- | --- |
| B1 | 谷歌「输入即提示」（Places Autocomplete） | 后端代调 Autocomplete（New）+ 会话令牌，前端防抖 300ms；密钥仍只在后端 | 要在谷歌云后台**开通 Places API (New) 的 Autocomplete 并确认计费**；按会话计费，量大时费用明显高于现在。密钥只由业主填进后台「系统设置 → 第三方密钥」（只进 secrets，不进代码、不发聊天）。中国大陆打不开谷歌，降级到平台地点 |
| B2 | 人工报价留资 | 新对象「询价线索」（客人填的地址、时间、人数、联系方式），运营后台加队列和处理状态，通知客服 | 新表和迁移；联系方式是个人信息，要按 ADR 0057 加密、定保留期限；要定谁处理、多久回复 |
| B3 | 日文 / 英文 / 韩文界面，地点名按语言 | 官网文案全部抽成多语言、语言切换、邮件模板多语言；地点主数据加韩文名 | 工作量大（整个官网 + 邮件）；翻译要业主或专业译者审；韩文名要导入数据 |
| B4 | 支付宝、微信支付 | Stripe 的 Alipay / WeChat Pay | 要在 Stripe 后台**开通并通过审核**（按账户所在国和币种有限制）；它们**不能保存付款方式**，而服务后的超时、超公里加收（ADR 0029）靠保存的银行卡扣款——用这两种付款的订单加收只能另想办法（例如线下收或另发付款链接），要业主决定 |
| B5 | Apple Pay / Google Pay | Stripe 支付组件打开钱包 | 要在 Stripe 后台**验证官网域名**（Apple Pay），正式环境域名定了再做；风险小 |
| B6 | 车辆照片 | 车型组加图片（上传、存储、缩略图、内容安全策略放行图片来源） | 新的文件存储和后台上传；照片要有版权（业主提供或购买） |
| B7 | OTA、企业门户共用按坐标报价 | `/sales/v1` 加同样的接口（新增，不改旧的） | 对外接口的契约变化要提前通知对接方；可以在 A1 稳定后再做 |
| B8 | 跨城市行程 | 先写测试核对：机场商品能否用另一个城市的区域报价 | 区域和商品都挂在城市上；如果不支持，要改「区域属于哪个城市」的规则，影响供应商后台的区域和商品配置，单独评估 |
| B9 | 不在区域时按里程报价（兜底价） | ADR 0063 的兜底价方案 | 改报价引擎的选价规则，要业主定兜底价怎么设、谁设 |
| B10 | 巴士 / 分两辆车 | ADR 0063 第 7 项（车辆类别） | 主数据、报价、派单都要改 |

不在 B 类、业主列的几项已经有了：报价锁价 30 分钟、多供应商同车型合并（只显示中标价）、按车型级别的取消规则、点对点商品、按小时包车。

## 后果

- A 类不改价格规则、订单、付款、通知；新接口只是「替客人选好机场和方向」再走现有报价。集成测试用「同一请求两条路报价完全一致」证明。
- 新旧页面并存一段时间，旧页面验收后才删。
- B 类每一项确认后另写 ADR。
