# ADR 0069：预订页重新设计（M8）的开发方案

- 状态：方案（2026-11-09，M8-01）。A 类按本篇直接开做；B 类每一项等业主确认后再另写 ADR 开工。
- 依据：业主 2026-11-09 的设计方案（`/home/codespace/import/booking-redesign-spec.txt`，原 HTML 设计稿的文字版，不进仓库）和同日的**修正版 v2**（同一文件末尾，以修正版为准；本篇末节「修正版 v2」覆盖前文 A3、A4 的页面部分）。
- 相关：ADR 0020（报价引擎）、0032 / 0035（官网下单、点对点和包车）、0041（谷歌密钥由后台填）、0044（地址搜索后端代调谷歌）、0046（官网付款）、0063（价格表超出框架的改进方案）、0066（M6 设计规范）、0068（车型标识）。
- 规则：价格规则、订单、支付逻辑**不顺手改**；旧的「城市 → 接 / 送 → 机场」下拉框在新流程验收通过后才删。

## 设计方案要什么（摘要）

客人只填出发地、目的地两个地址 + 用车时间 + 人数（行李选填），系统自己判断机场、接机还是送机、落在哪个报价区域，列出坐得下的车型和一口价。三步：① 填行程（「接送 / 按小时包车」两个标签）→ ② 选车型（按价格从低到高，坐不下的隐藏，车型名 + 代表车型 + 最多几人几件 + 一口价 + 包含什么）→ ③ 填乘客信息并付款（右侧一直显示行程和价格，下方显示取消规则）。链接带 from / to / date / time / pax 参数，打开就报价。

## A 类：在现有框架内直接做（按批次）

### A1 后端：按两个坐标报价（M8-02）

新接口 `POST /site/v1/quotes/by-points`（只在官网渠道下，`/sales/v1` 不动，见 B7）：

- 请求：`pickup { name, lat, lng, kind? }`、`dropoff { 同 }`、`service_local`（当地时间）、`passengers`、`luggage?`；包车标签用现有的包车请求，不走这个接口。`kind` 是地址搜索给的类型（机场 / 其他），客人手填的地址没有类型。
- 认出机场：一端的 `kind` 是机场，或坐标离某个**启用**的机场（地点主数据）不超过 **3 公里**（业主已定）。几个机场都在 3 公里内取最近的。只认渠道授权范围里的城市的机场。
- 判断方向：出发地是机场 → 接机；目的地是机场 → 送机；两端都是机场 → 按出发地算接机；两端都不是 → 点对点。
- 然后按方向组装成**现有**的询价请求，调用现有的 `createSalesQuotes`（和 `POST /site/v1/quotes` 同一条路）：价格规则、区域判断、比价中标、30 分钟报价快照、询价日志全部照旧。
- 应答：`trip_type`、识别到的机场（编号、名称）、每个车型的报价（沿用现有 `SiteQuote`：车型组含 M7 的车型标识、一口价、免费等待、取消政策、`quote_id`）按价格从低到高排、`expires_at`；报不出时给现有的拒绝原因（时间太近给最早可订时间、人数太多、地址不在服务范围），由页面给出说法。
- 不新增表、不新增迁移；询价日志的 `request` 多记 `mode: by_points` 和识别结果。
- 测试：单元（3 公里边界、两端都是机场、取最近机场、方向判断）；集成（真实库：识别对了以后报价和 `POST /site/v1/quotes` 同一请求完全一致——**证明价格逻辑没变**；渠道授权外的机场不认；点对点；报不出价的几种原因）；OpenAPI 同步。

### A2 后端：地址搜索不用先选城市（M8-02）

`GET /site/v1/places/search` 加一种不带 `city_id` 的用法：按渠道授权的国家 / 地区做 `regionCode`，不限城市范围；应答每个候选多一个 `kind`（谷歌的 `primaryType` 是机场时为 `airport`，否则 `other`）。仍然是后端代调（密钥不进浏览器）、短时缓存、每日上限（ADR 0044 的做法不变）。同时把平台主数据里名字匹配的机场、车站排在最前（不依赖谷歌也能搜到机场，含航站楼）。

> 费用提示：搜索次数会比现在多（不用先选城市，客人更容易直接搜）。仍受 `GOOGLE_PLACES_DAILY_LIMIT` 每日上限保护，超过就降级为「从常用地点选」。

### A3 前端：新预订页第 1、2 步（M8-03）

- 新页面先放在 **`/book/new`**，旧页面 `/book` 不动，验收通过后再切换（A5）。
- 第 1 步：「接送 | 按小时包车」标签；出发地、目的地两个地址框（输入后出候选：平台的机场 / 车站在前，谷歌结果在后；谷歌不可用时只用平台地点和地图选点）；日期、时间、人数、行李（选填，默认按人数推算的规则写进页面说明）；一端识别为机场时时间栏改叫「航班落地时间（当地）」并提示「已识别为接机」；右侧（手机在下方）「一口价包含」用现有数据：专车、举牌、免费等待分钟数（来自报价）。
- 第 2 步：行程条（可修改）、「按价格从低到高 · 坐不下的已隐藏」、车型卡（车型名、M7 车型标识、一口价、选择）。手机底部固定「车型 · 一口价 [下一步]」。
- 链接参数：`from` / `to`（平台地点编码，或 `纬度,经度` 加可选名称）、`date`、`time`、`pax`、`bags`，打开即报价；参数不合法时只是不预填，不报错。
- 报不出价：按拒绝原因给说法；地址不在服务范围时显示「这个地址暂时没有在线报价，请联系客服」和现有的客服电话（不收集客人信息，留资见 B2）。
- 按 M6 设计规范；手机优先；亮暗、360px、axe、键盘。

### A4 前端：第 3 步填信息并付款（M8-04）

复用现有的下单和付款（`CheckoutPage` 的字段、校验、`POST /site/v1/orders`、Stripe 银行卡），只改排版：左边表单（乘客、联系方式、接机行程才显示航班号和举牌名、备注、取消规则），右边一直显示行程和价格；手机单栏。下单、付款、订单、通知逻辑一行不改。

### A5 切换和删旧（M8-05，验收通过后）

`/book` 换成新流程，旧的「城市 → 接 / 送 → 机场」下拉框删除；旧链接 `/book?...` 能识别的参数转到新页面。只有 A3、A4 验收通过后才做。

## B 类：超出现有框架（改进方案和风险，等业主确认）

| 编号 | 内容 | 方案 | 需要业主 / 风险 |
| --- | --- | --- | --- |
| B1 | 谷歌「输入即提示」（Places Autocomplete） | 后端代调 Autocomplete（New）+ 会话令牌，前端防抖 300ms；密钥仍只在后端 | 要在谷歌云后台**开通 Places API (New) 的 Autocomplete 并确认计费**；按会话计费，量大时费用明显高于现在。密钥只由业主填进后台「系统设置 → 第三方密钥」（只进 secrets，不进代码、不发聊天）。中国大陆打不开谷歌，降级到平台地点 |
| B2 | 人工报价留资 | 新对象「询价线索」（客人填的地址、时间、人数、联系方式），运营后台加队列和处理状态，通知客服 | 新表和迁移；联系方式是个人信息，要按 ADR 0057 加密、定保留期限；要定谁处理、多久回复 |
| B3 | 日文 / 英文 / 韩文界面，地点名按语言 | 官网文案全部抽成多语言、语言切换、邮件模板多语言；地点主数据加韩文名 | 工作量大（整个官网 + 邮件）；翻译要业主或专业译者审；韩文名要导入数据 |
| B4 | 支付宝、微信支付 | Stripe 的 Alipay / WeChat Pay | 要在 Stripe 后台**开通并通过审核**（按账户所在国和币种有限制）；它们**不能保存付款方式**，而服务后的超时、超公里加收（ADR 0029）靠保存的银行卡扣款——用这两种付款的订单加收只能另想办法（例如线下收或另发付款链接），要业主决定 |
| B5 | Apple Pay / Google Pay | Stripe 支付组件打开钱包 | 要在 Stripe 后台**验证官网域名**（Apple Pay），正式环境域名定了再做；风险小 |
| B6 | 车辆照片 | 车型组加图片（上传、存储、缩略图、内容安全策略放行图片来源） | 新的文件存储和后台上传；照片要有版权（业主提供或购买） |
| B7 | OTA、企业门户共用按坐标报价 | `/sales/v1` 加同样的接口（新增，不改旧的） | 对外接口的契约变化要提前通知对接方；可以在 A1 稳定后再做 |
| B8 | 跨城市行程 | 先写测试核对：机场商品能否用另一个城市的区域报价 | 区域和商品都挂在城市上；如果不支持，要改「区域属于哪个城市」的规则，影响供应商后台的区域和商品配置，单独评估 |
| B9 | 不在区域时按里程报价（兜底价） | ADR 0063 的兜底价方案 | 改报价引擎的选价规则，要业主定兜底价怎么设、谁设 |
| B10 | 巴士 / 分两辆车 | ADR 0063 第 7 项（车辆类别） | 主数据、报价、派单都要改 |

不在 B 类、业主列的几项已经有了：报价锁价 30 分钟、多供应商同车型合并（只显示中标价）、按车型级别的取消规则、点对点商品、按小时包车。

## 修正版 v2（2026-11-09，以此为准）

业主发来修正版，页面结构改了，后端（A1、A2）不变。下面覆盖前文 A3、A4 的页面部分；B 类在前表基础上增加。

### 页面结构

- **电脑端单页**：「你的行程」「选择车型」「怎么联系你」三块从上到下在同一页；右侧栏跟随滚动。**手机仍分步**：第 1 步填行程，第 2 步选车型，然后联系信息和付款；底部固定「车型 · 一口价 [下一步]」。
- **行程块**：接送 / 按小时包车、出发地、目的地、日期、航班落地时间（当地）、「乘客 / 行李」合并成一个栏（如「2 人 · 2 件」，点开分别加减）、航班号（选填，放在行程里，接机才显示）。识别为接机时提示「已识别为接机…落地后免费等 N 分钟」：**N 取报价里的免费等待分钟数**（各商品不同，测试环境有 60 分钟的），不写死 90。
- **车型块**：按价格从低到高、坐不下的不显示；默认显示前几个（电脑 4 个、手机 3 个），下面「显示全部 N 个车型 ▾」。选中的车型展开**车内俯视示意图**（见下）。
- **联系块**：乘车人姓名、邮箱、手机号（含国家区号）、微信 / LINE / WhatsApp（选填）、给司机的备注（选填）——都是现有下单接口已有的字段（`passenger`、`messaging`、`notes`），只是换位置。
- **右侧栏（A 部分）**：车费、合计（订单币种的一口价）、取消规则（**取平台按车型级别配置的现有规则显示**，设计稿里的「经济车型 24 小时以上免费…」是示例，实际条款由运营在后台「取消政策」里配置）、「去付款 →」、支付方式图标（现在只有银行卡，只显示银行卡的图标）。

### 车内俯视示意图（A）

- 前端按车型的**最多乘客 N、最多行李 M**（M7 车型标识，来自组合）自动画 SVG，不用照片：车身轮廓、司机位、蓝色乘客座位编号 1–N、橙色行李位编号 1–M，按座位数排成 2 / 3 列的若干排；颜色用设计令牌（乘客用主色系、行李用警告色系），亮暗两套都校验对比度；同时有文字说明「乘客座位 N 个 · 行李 M 件 · 人数少时空座位也可以放行李」，不只靠颜色（无障碍）。
- 示意图是**示意**，不代表实际车型的座位布局；图下注明「示意图」。
- 「按标准大号箱计，尺寸标准待定」：尺寸标准是 B13，确认前只写「行李 M 件」，不写尺寸。

### 「一口价包含」

| 条目 | 现状 | 处理 |
| --- | --- | --- |
| 专车不拼车 | 现在只卖专车 | A：可以写 |
| 举牌接机 | 不是平台统一的服务规则；是供应商在商品详情「包含」清单里自己写的一项（例如「举牌接机」） | A：按中标商品的「包含」清单显示，清单里没有的不写 |

- 地址输入即提示：后端 `GET /site/v1/places/autocomplete?q=&session=`（Places Autocomplete New，带会话令牌，选中后用 Place Details 取坐标和类型，同一会话按一次计费）；前端防抖 300 毫秒、至少 2 个字才查；平台自己的机场 / 车站先出。
- 路线和时间距离：后端在「按两个坐标报价」时用现有的路线预估（ADR 0042，Routes API）顺带算出 `minutes`、`meters` 和**路线折线**（`polyline`），随报价返回。
- 地图显示：用现有的底图（`MAP_TILE_*`，OpenStreetMap）和地图组件，把后端给的路线折线画上去。**不需要浏览器密钥**，内容安全策略不用为谷歌放行。若业主坚持要谷歌自己的地图样式，需要另建一把**限制了 HTTP 来源（只允许官网域名）**的浏览器密钥，现在没有，等业主决定。

### B15 → A：婴儿座椅、儿童座椅（价格按供应商报价）

**现有框架已经有完整的链路**，不用新加计价规则：

| 业主要求 | 现有框架 |
| --- | --- |
| 平台「附加服务」目录只定义项目 | 主数据「附加服务」（编码、名称、计费方式），测试环境现在是空的，要建「婴儿座椅」「儿童座椅」两条（计费方式：按单） |

| 客人看到的价格按车费现有的定价规则从供应商价算出 | 报价引擎：附加服务费加进结算价合计 `P_total = Adjust(P_base) + F_urgent + F_night + ΣF_addon`，对外价按渠道现有的加价规则从整单结算价算出（ADR 0020、0023）——附加服务和车费用**同一套**加价，不另定 |

| 供应商没报价的商品不显示该附加服务 | 客人选了某个附加服务时，没提供它的商品报价引擎直接不报（`ADDON_NOT_OFFERED`），比价只在提供的供应商之间进行 |
| 多供应商合并时以最终接单供应商为准 | 比价中标后，订单的报价快照里就是中标商品的附加服务单价 |

### B16 → A：按客人币种显示参考价

- 汇率来源：系统「汇率中心」（ADR 0022，`apps/api/src/integrations/fx-source.ts`）。数据源是 ExchangeRate-API 的免费地址 `open.er-api.com/v6/latest/USD`（配置 `FX_SOURCE_URL`，免密钥），**数据源每天更新一次**；系统每 60 秒检查一次、到数据源给的下次更新时间才拉；按 USD 存，任意两种币种走交叉汇率；拉取失败用最近一次有效汇率，超过 48 小时停掉跨币种报价并告警；涨跌超过阈值的那批先挂起，人工确认。所以它是「当天的汇率」，不是秒级实时。
- 显示：右侧栏合计下面「≈ 客人币种金额」，小字「按当前汇率换算，仅供参考，实际以支付金额为准」/「現在の為替レートで換算した参考額です。実際のお支払い金額が優先されます」/「Converted at the current exchange rate for reference only; the amount actually charged prevails」。客人币种：按浏览器语言地区推断，可手动切换（只影响参考价）。
- 汇率取不到、挂起或超过 48 小时时不显示参考价，不影响下单。只读汇率中心的「现在生效」的汇率，不改定价和收款逻辑。
- 后端：`GET /site/v1/fx/reference?to=`（只返回订单币种 → 客人币种的汇率和 `as_of`），或随报价返回；不新拉外部服务。

| 3 | 服务后加收（超时、付费等待等）：48 小时异议期后用保存的卡**离线扣款** | 钱包订单扣不了 | 钱包订单的加收改成「付款链接」：异议期后在订单页显示「去付款」并发邮件提醒；7 天未付转运营处理（工单）。供应商的应收不因客人没付而变（按现有规则由平台承担或另行追收，要业主定） |
| 4 | 取消、赔付退款原路退回 | 支付宝 90 天、微信 180 天后不能原路退 | 现在最多提前 30 天预订，取消退款都在期限内；工单赔付超过期限时，退款失败会收到 `refund.failed`（已处理），转运营线下退款 |
| 5 | 订单币种可以是 JPY 以外（别的国家的渠道） | 日本账户只能用 JPY、CNY | 只在订单币种是 JPY（或 CNY）时显示这两种方式 |
| 6 | 手机为主 | 微信支付不支持手机浏览器 | 手机上只显示支付宝；电脑上两种都显示（由 Stripe 支付组件按设备自动决定，再加一层判断） |
| 7 | 有拒付流程（`charge.dispute.created`） | 钱包没有拒付 | 不影响；客人找来时走退款 |
| 8 | 付款回跳（3D 验证整页跳转后回到订单页，`payment-return.ts`） | 支付宝跳转也走这条 | 复用现有回跳处理；补测试 |

## 业主 2026-11-09 第二批确认

### ① 包车也一口价全含（B12 补充）

业主：包车报价的高速费、停车费也包含在一口价里；新预订页、包车页面、邮件统一写「一口价包含所有费用」。

**现在的逻辑**（不顺手改）：包车可以事后加收 `toll` 高速费、`parking` 停车费（凭票实报，`packages/domain/src/extra-charges.ts` 的 `CHARTER_ONLY`、`RECEIPT_REQUIRED`；ADR 0029），官网包车说明写「高速费、停车费服务后按实际收取」。

**影响范围**

| 位置 | 影响 |
| --- | --- |
| 加收规则 `extra-charges.ts`、接口 `POST /tenant/v1/orders/{id}/extra-charges` | 包车不能再收 toll / parking；超时、超公里、付费等待、加停靠点、加附加服务不变 |
| 供应商后台「事后加收」表单、司机页上传票据 | 类型列表去掉高速费、停车费；票据上传仍保留给其他用途（举牌照片等不受影响） |
| 官网包车说明（`site-display.ts`）、`BookPage` 包车提示、订单页 | 改为「一口价包含所有费用；超出套餐的时长和公里服务后按实际收取」 |
| 供应商的包车价格 | **最大风险**：供应商现在的包车套餐价是按「高速、停车另收」定的，改了以后这部分要由供应商自己承担，可能要调高套餐价 |
| 已有订单 | 已经提交、还在异议期或待扣款的高速 / 停车加收，照旧处理（不追溯） |
| 结算、账单 | 不改：以后不会再产生这两类加收，账单里自然没有 |
| 邮件 | 「服务后费用待确认」邮件随加收类型；新增说法放在订单确认邮件的「一口价包含」里 |

**安全方案（等业主确认后再做，单独一个 PR）**

1. 定一个生效时间（例如通知供应商 14 天后）。**生效时间之后下单的包车订单**不能加收高速、停车费；之前下的照旧（按订单的下单时间判断，不追溯、不影响已报价的订单）。
2. 生效前通知所有有包车商品的供应商：报价要包含高速、停车费，请按需调整套餐价（供应商后台首页提示 + 邮件）。
3. 页面和邮件的说法和规则**同一天切换**：规则还允许另收时，页面不能先写「包含所有费用」（否则客人会被收到「已说包含」的钱）。
4. 不改价格规则、结算公式；只是从加收类型里按订单下单时间去掉两项。

### ② 钱包付款的订单事后补钱：先发付款链接，客人不付由司机现场收现金（B4 补充）

**和现有决定的冲突**：需求第五轮决策 ⑤ 和现有代码都写着「**平台订单不允许司机现场收现金**」（`extra-charges.ts` 第 9、12 行）。业主这次的决定改变了这一条，但**只限支付宝 / 微信付款的订单、只限事后加收客人不付的情况**。

**流程方案**

| 步骤 | 状态（现有 / 新增） |
| --- | --- |
| 供应商提交加收、48 小时异议期、平台审核 | 现有：`in_window`、`review`、`disputed`、`approved`（不变） |
| 银行卡订单：离线扣款 | 现有：`charging` → `charged` / `charge_failed`（不变） |
| **钱包订单**：异议期后不离线扣款，在订单页显示「去付款」并发邮件（付款链接 = 订单页上的当场付款，复用现有 Stripe 付款组件） | **新增** `awaiting_payment`（等客人付款） |
| 客人付了 | 现有 `charged` |
| 7 天没付 → 转为现场收现金：通知供应商 / 司机，下次服务或尽快向客人收现金 | **新增** `cash_pending`（待收现金） |
| 司机或供应商在后台记「已收现金」（金额、时间、谁收的、可上传收据照片） | **新增** `cash_collected`（已收现金）；客人订单页显示「已现金付清」 |
| 收不到 | 运营在后台标「放弃」，走现有 `withdrawn` 或新增 `written_off`（要业主定由谁承担） |

**结算上的风险（必须先定）**：现金在供应商手里，平台不能再把这笔钱付给供应商。方案：`cash_collected` 的加收**不进**平台给供应商的付款金额，只在账单里列一行「现金已由供应商收取」（金额 0 计入应付），平台的抽成 / 加价部分（如有）在下期账单扣回。这会碰月结账单（ADR 0040），所以单独评估，业主确认后再做。

需要新增的：加收状态 3 个（迁移改 check 约束）、供应商后台和司机页「记现金」操作（新权限归调度和管理员）、订单页和邮件说法、账单的一行。都要业主确认后做。

### ③ 支付宝 / 微信开关

业主：现在不用开，正式上线时业主自己在 Stripe 开启。代码里做成**配置开关，默认关闭**（例如 `SITE_WALLET_PAYMENTS=off`，不是密钥，放 `packages/config`）：关闭时付款方式只有银行卡，和现在完全一样。M8-07 不阻塞其他 M8 任务；改期补差价、加收的钱包路径（②）等业主确认后随 M8-07 一起做。

### 和方案有出入的地方

1. **短时缓存改回 10 分钟**：ADR 0053 曾把地址搜索的进程内缓存设为 0（谷歌条款只明确允许缓存地点 ID 和坐标）；本篇「B1 + B11 → A」业主确认「每个接口都有短时缓存（同一关键字 / 同一对坐标 10 分钟内不重复调）」，所以 `PLACE_SEARCH_RULES.cacheTtlMs` 改为 10 分钟，搜索、反查、输入即提示、取坐标都按它；路线折线只在进程内存 10 分钟（`ROUTE_RULES.previewCacheTtlMs`），不存库。仍只在内存、不存库；要严格按条款时把这两个常量改成 0。
2. **地址搜索说是机场时放宽到 10 公里**：方案写「`kind` 是机场，或 3 公里以内」。`kind` 是机场时仍要落到平台主数据的某个机场（接送机商品挂在机场上），所以定为「`kind: airport` 且离最近的启用机场不超过 10 公里」（`BY_POINTS_RULES.airportKindRadiusMeters`）；超过就不认，按普通地址处理。
3. **「只认渠道授权范围里的城市的机场」**按「城市在授权里、启用，且渠道能卖这个城市的接送机」理解：只卖点对点的渠道不会把机场附近的地址认成机场（否则询价会被 422 `CHANNEL_SCOPE_DENIED` 挡掉）。停用的机场不认。
4. **点对点选哪个城市**：方案没写。按出发地落在哪个「官网能订点对点的城市」（城市中心周围 80 公里，和地址搜索同一个范围）取最近的；都不在时不询价，`city: null`、原因 `OUT_OF_SERVICE_AREA`，也不算路线（不花钱），这种情况没有询价日志（`quote_logs` 要城市）。跨城市行程仍按出发地的城市（B8 待核对）。（M8-35 补充：出发地不在任何城市、目的地在时按目的地的城市，见 ADR 0084。）
5. **两端都是机场**：按方案算接机，目的地那个机场的坐标当作地址那一端，由出发地机场的商品按区域判断能不能接。
6. **「时间太近给最早可订时间」没做**：现有拒绝原因只有 `LEAD_TIME_TOO_SHORT`，没有「最早可订时间」；要给的话得从各候选商品的提前预订时长、服务时间算，属于报价引擎的新输出，留给 M8-03 一起看要不要（不改价格规则）。
7. **限速**：输入即提示每输入几个字就调一次，单设每个地址每分钟 60 次（`site_autocomplete`，取坐标合计），每天的额度和搜索、反查共用 300 次（`site_places_day`）；按两个坐标报价和询价共用每分钟 30 次。
8. **地址名称**：请求要 `name`（非空、单行、最多 300 字），只做校验，不进询价日志和快照；下单时照旧在订单里填地址文字。

## 实现补记：M8-02 第二部分（2026-11-09，后端 B15 附加服务、B16 参考汇率）

### 附加服务（B15）

- `POST /site/v1/quotes`、`POST /site/v1/quotes/by-points` 多一项 `addons: [{ addon_id, quantity }]`（最多 20 项，数量 1–20，默认 1），照原样交给现有报价引擎：没提供的商品不报（`ADDON_NOT_OFFERED`），比价只在提供的供应商之间进行；附加服务费进结算价合计、和车费走同一套加价。价格规则、加价都没改。询价日志的 `request` 多记 `addons`。
- 每个报价多 `available_addons`：参加这个车型组比价的候选商品里有供应商提供的（开着、目录里启用、适用这个品类）附加服务，只有目录信息（`id`、`code`、`name`、`charge_unit`），**不带供应商单价，也不带对外单价**——客人选了以后带 `addons` 重新询价看合计（避免单独算单价再加回去和整单取整差 1 日元）。服务层：`createSalesQuotes` 给每个报价算 `offeredAddonIds`（`/sales/v1` 的应答不输出它）。
- 下单：现有下单流程本来就从报价快照的 `request.addons` 写订单的 `addons`，金额只来自快照，**不用改**；集成测试核对订单的附加服务和报价一致、金额就是报价的对外价、中标供应商在 `/tenant/v1` 看得到附加服务看不到对外价（规则 4 不变）。
- 本次没做：方案第 4 条「司机页、供应商和运营订单详情、邮件显示附加服务名称」（司机页已有名称；其余随页面任务）。

### 参考汇率（B16）

- `GET /site/v1/fx/reference?to=`（`to` 是汇率中心支持的 8 种币种之一）：只读汇率中心「现在生效」的汇率（`ctx.fx.rates`，和报价同一个来源，含人工锁定），不拉外部服务。应答 `available`、`from`（官网渠道的结算币种，即订单币种）、`to`、`rate`、`as_of`、`reason`；同币种 `rate` 为 "1"。
- 不可用时 200 + `available: false`：`NO_RATE`（没有这两种币种的汇率）、`STALE`（超过 48 小时没更新）、`PENDING_REVIEW`（有一批涨跌超过阈值的汇率挂起待确认——方案写「挂起时不显示」，所以即使现在生效的那批还能用也不给）。按官网读接口限速（每个地址每分钟 120 次）。
- 汇率中心每个进程缓存 30 秒，所以拉到新汇率后最迟 30 秒生效（和报价一致）。

测试：`apps/api/src/site-addons-fx.itest.ts`（真实 PostgreSQL；汇率源、收款都是本机替身）。

## 实现补记：M8-09（2026-11-09，第二批确认 ① 包车一口价全含）

## 实现补记：M8-04 验收问题 1（2026-11-09）
