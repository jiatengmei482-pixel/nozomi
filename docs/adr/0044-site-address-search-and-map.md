# ADR 0044：官网的地址搜索与地图选点——后端代调谷歌、短时缓存、每日上限、降级

- 状态：已采纳（2026-10-26，M3-12）
- 补充 ADR 0035「不依赖外部服务的地址输入辅助」：「从常用地点选」**保留**（不依赖谷歌的入口），再加地址搜索和地图选点；三种方式的排布见 `docs/design/pages/site-booking.md` 3.6。
- 补充 ADR 0042「路线预估」：同一把谷歌密钥、同一套安全处理、冷却规则和每日上限的做法；**计数分开**。
- 补充 ADR 0015 / 0017「底图」：官网的地图用同一份底图配置（`MAP_TILE_*`）和同一个瓦片层（`QuietTileLayer`），不加载谷歌地图的脚本。
- 补充 ADR 0005「配置」：新增普通配置 `GOOGLE_PLACES_DAILY_LIMIT`（不是密钥），只给测试用的 `GOOGLE_PLACES_SEARCH_URL`、`GOOGLE_GEOCODE_URL`（只有 local / ci 能改）。
- 迁移 0120（0111–0119 留给别的任务）。

## 背景

roadmap M3-12 的验收标准：官网的地址可以在地图上选点、按关键字搜索；选出的地址带坐标，报价按坐标判断服务区。
需求《用车报价服务平台》「API · 销售端接口」有「地点搜索 `GET /places/search?q=&city=`：搜机场、车站、POI，也支持坐标反查」，这里先给官网做；`/sales/v1` 的同名接口另开任务（见「本期不做」）。

## 决定

### 密钥绝不进浏览器：后端代理两个接口

| 接口 | 做什么 | 谷歌那边 |
| --- | --- | --- |
| `GET /site/v1/places/search?city_id=&q=` | 关键字 + 城市 → 最多 5 个候选（名称、地址、坐标） | Places API (New) Text Search（`POST places:searchText`），字段掩码 `places.id,places.displayName,places.formattedAddress,places.location`，`locationRestriction` 为城市中心周围 80 公里的正方形，`languageCode=zh-CN`、`regionCode`=城市的国家，`pageSize=5` |
| `GET /site/v1/places/reverse?city_id=&lat=&lng=` | 坐标 → 地址文字（没有地址为 null） | Geocoding API 反查（`GET …/v4beta/geocode/location/纬度,经度`），字段掩码 `results.formattedAddress` |

- 不用谷歌地图的 JS（Maps JavaScript API、Places Autocomplete 小部件）：那要把密钥放进页面，还要给内容安全策略开谷歌的脚本、样式、图片、连接来源。
- 安全处理和路线预估相同：地址只认配置（staging / production 不能改）；密钥只在请求头 `X-Goog-Api-Key`，不进网址；不跟随重定向；应答边读边截，只读 64 KB；
  整次 3 秒、每次尝试 2 秒，连不上、超时、5xx 在剩余时间 ≥ 0.5 秒时再试 1 次，4xx（含 429）不重试；失败归类和「测试一下」共用（`classifyCode`）。
  比询价宽一点：客人在页面上等的就是这一个结果，不用和别的外部调用分 2 秒的预算。
- 应答清理：名称最多 120 字、地址最多 240 字（下单的地址栏上限 300），去控制字符、并空白；缺名称或坐标、坐标不合法、不在城市范围里的候选丢掉。
- 城市要在官网渠道的授权里、启用（否则 400 `UNKNOWN_CITY`）；反查的坐标要在城市中心周围 80 公里以内（否则 400 `OUT_OF_CITY`）——这个代理只为在这个城市用车服务，不当全球通用的地址查询。
- 关键字：Unicode NFKC、去控制字符、空白并成一个；规范化后 2–100 个字，其中字母、数字、汉字、假名至少 2 个（`TOO_SHORT` / `TOO_LONG`）。一个字、纯表情、纯符号搜不出有用的结果，白花一次钱。
- 反查的 `lat`、`lng` 留空或缺少：400 `VALIDATION_FAILED`（`REQUIRED`），不当成 0。
- 页面用不用地址搜索：`GET /site/v1/config` 多一项 `address_search`（官网开着、谷歌密钥配置了、每日上限不是 0）。不说密钥从哪来、是不是坏了。

### 缓存：只在进程内、10 分钟（按谷歌条款能缓存的范围）

谷歌地图平台的服务条款（Service Specific Terms，Places API 和 Geocoding API 同样）**只明确允许**：地点 ID 可以长期保存；坐标（lat / lng）可以临时缓存，最多连续 30 天。
名称、地址文字不在允许之列。所以：

| 项 | 规则 |
| --- | --- |
| 存哪里 | **只在服务进程的内存里**；库里不存谷歌返回的任何名称、地址（计数表只有次数和原因代码） |
| 多久 | 10 分钟（`PLACE_SEARCH_RULES.cacheTtlMs`），最多 500 条，先进先出 |
| 键 | 搜索：`search:城市:规范化后的关键字（小写）`；反查：坐标取整到小数点后 **4 位**（约 11 米）+ 国家，调谷歌也用取整后的坐标 |
| 缓存什么 | 成功的结果（含「没找到」「这里没有地址」）；谷歌说请求无效（`INVALID_REQUEST`）也记 10 分钟 |
| 不缓存 | 其他失败（超时、配额、密钥……），靠冷却 |
| 并发 | 同一个键正在查时，后来的直接等那一次（进程内） |

10 分钟的作用是挡住同一个客人在一次填写里的重复请求（改了别的字段、切换服务、来回返回），属于为了性能的临时保存；
它**不是**条款明文允许的项目，列在「待负责人确认」第 3 条：若要严格按条款，把常量改成 0，就只剩「并发只调一次」。

### 费用控制：每日上限（和路线分开计）

- 配置 `GOOGLE_PLACES_DAILY_LIMIT`，默认 **500 次 / 天**（搜索和反查合计），0 = 不调用，最大 100 万；按东京时间的日期计。
- 表 `place_api_usage`（迁移 0120）：和 `route_api_usage` 同样的列和同样的占名额方式（锁住今天那一行、读出已用次数、允许才加一；并发不超；记不了数就不调用）。
- **为什么不和路线共用一个计数**：路线预估决定能不能报价；客人搜地址用多了（或被刷）不能把报价也挡住。两个 API 的价格也不同（见下）。
- 为什么 500：Text Search 取名称要到 Pro 一档（按千次计费，比 Routes Essentials 贵），Geocoding 便宜一些；500 次 / 天在早期流量下够用，最坏的费用也有上限。
  也建议在 Google Cloud Console 给 Places API (New)、Geocoding API 各设每日配额，作为第二道保险。

### 冷却（同一把密钥，进程内）

和路线预估同一张表（`placeFailureCooldownMs`）：密钥、项目配置、配额、每日上限 60 秒；超时、连不上、对方出错、看不懂 15 秒；请求无效、没配置不冷却。
冷却按密钥的指纹记，超级管理员换了密钥立即用新的。冷却还记下所属的东京日期：0 点换了新的一天立即失效（前一天「到了上限」的冷却不挡新的一天，也不把新一天记成被挡下）；路线预估（ADR 0042）同样修正。搜索和反查共用一个冷却（同一把密钥、同一个项目）。

### 限流（按来源地址，防刷费用）

和官网其他接口同一种机制（`sales_rate_limits`，地址只存哈希）：搜索和反查**合计**每个地址每分钟 20 次、每天 300 次。超限 429 `RATE_LIMITED` + `Retry-After`。
每天一份额度是为了一个地址刷不光全站的每日上限（500 次里最多占 300 次，而且大部分会命中缓存）。
限流键用 ADR 0045 的 `rateLimitKeyOf`（经 `takeSiteSlot`，IPv6 按 /64 计）；这两个额度和 /64 的键同时上线，ADR 0045「上线时 IPv6 计数从零开始、窗口最长 15 分钟」的说法不涉及它们（每天的额度窗口是 24 小时）。

### 降级

谷歌没配置、到了每日上限、冷却中、出错、超时、应答看不懂：**不报 500**，200 + `available: false`。页面：

- 搜索框下面说「地址搜索暂时用不了，请从常用地点选，或在地图上点选、直接填写地址」，常用地点、地图、手填照常可用；
- 地图点选后反查失败：坐标照样填好，地址栏不动，提示「没有查到这个位置的地址，请在下面写上地址」。

日志：失败时 warn 一条，只有原因代码（`placeFailure`），没有密钥、关键字、坐标、谷歌返回的原文。

### 地图（前端）

- 底图来自 `GET /site/v1/config` 的 `map_tiles`（和供应商区域页同一份配置）；没有配置时**不显示地图**，只有搜索和常用地点。不加载谷歌地图的任何东西。
- 地图默认收起，点「在地图上选{上车}地点」展开（首屏仍然要看到地址区的开头，规范 3.1）。点地图或拖动标记 → 坐标填进坐标栏 → 反查地址填进地址栏。
- 键盘：地图本身可聚焦，方向键平移、`+` / `-` 缩放；中间有准星，按「选地图中间这个位置」完成选点——不用鼠标也能选；坐标栏照旧可以直接输入或粘贴。
- 搜索结果点选后：地址、坐标填好，地图（若展开）移到那里。
- 内容安全策略**不变**：瓦片来源早已在 `img-src` 里（ADR 0015）；搜索、反查走同源的 `/site/v1`，`connect-src 'self'` 足够。

### 报价按坐标判断服务区

`POST /site/v1/quotes` 本来就只收坐标（接送机的 `address`、点对点 / 包车的 `pickup`、`dropoff`），请求体是 `.strict()`，没有地址文字这一项；报价引擎按坐标判断营运区和禁行区。
服务区外照旧是 `OUT_OF_SERVICE_AREA`，页面现有的说法「这个地址不在服务范围内…」。地址文字只在下单时进订单，给司机看。

## 待负责人确认（都已按推荐值实现）

| # | 问题 | 推荐（现在的做法） | 理由 |
| --- | --- | --- | --- |
| 1 | 每日调用上限 | 500 次 / 天（`GOOGLE_PLACES_DAILY_LIMIT`，搜索和反查合计），和路线的 1000 次分开 | 客人搜地址不挡报价；最坏费用有上限 |
| 2 | 每个来源地址的额度 | 每分钟 20 次、每天 300 次 | 正常客人一次预订用不到 10 次；一个地址刷不光全站的上限 |
| 3 | 短时缓存 | 进程内 10 分钟，不存库 | 条款只明确允许缓存地点 ID 和坐标；10 分钟内存缓存是为性能的临时保存。要严格按条款就改成 0 |
| 4 | 搜索范围 | 城市中心周围 80 公里 | 覆盖成田（离东京站约 60 公里）这类远郊机场；不让代理变成全球地址查询 |
| 5 | 反查用的接口 | Geocoding API（`v4beta` 地址，支持把密钥放请求头） | 旧版 Geocoding 要把密钥放网址里，会进各种日志。**请在测试环境用真实密钥确认这个地址可用**；不可用时反查降级、页面照常 |
| 6 | 结果语言 | 中文（`zh-CN`） | 官网是中文页面；日本的地址谷歌会给日文写法 |

开通：Google Cloud Console 里同一个项目要启用 **Places API (New)** 和 **Geocoding API**（路线已启用 Routes API），密钥的 API 限制里加上这两个（`docs/secrets.md`）。

## 本期不做

- `/sales/v1/places/search`（需求「API · 销售端接口」的地点搜索，含平台的机场、车站、POI）：渠道接口另开任务；可以复用本文的服务层。
- 运营后台「系统状态」显示地址搜索的用量：表里已有数据（`place_api_usage`），页面另开任务。
- 搜索时边输边出候选（自动补全）：每个字都可能花一次钱；现在是按「搜索」或回车才查。
- 把搜到的地点存成平台的 POI（需求「从询价日志里的高频地址推荐新 POI」）：条款不允许长期保存谷歌的名称和地址，要另行设计。
