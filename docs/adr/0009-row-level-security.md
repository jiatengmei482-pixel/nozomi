# ADR 0009：行级安全（RLS）的落地方式

- 状态：已采纳（2026-10-07，M0-06）。是对 ADR 0003 的补充，不改变其中的决定。

## 背景

ADR 0003 决定用 PostgreSQL 行级安全作为租户隔离的第二道防线。落地时有一个坑：行级安全对**表的所有者**和**超级用户**默认不生效。本地、CI 和服务器上的 Docker Compose 数据库，应用用的都是建库时的那个账号（超级用户，也是表的所有者），直接开启行级安全等于没开；`force row level security` 只能管住所有者，管不住超级用户。

## 决定

- 迁移创建一个专门的数据库角色 `nozomi_app`：不能登录、没有密码、不是超级用户、不拥有任何表、没有 `BYPASSRLS`。
- 数据访问只有两个入口（`apps/api/src/db/context.ts`）：
  - `withTenantTx(pool, tenantId, fn)`：处理租户请求。事务开头执行 `set local role nozomi_app` 和 `set_config('app.tenant_id', <租户编号>, true)`。此后这个事务里的所有 SQL 都以 `nozomi_app` 的身份执行，策略只放行 `tenant_id` 等于当前租户的行。
  - `withSystemTx(pool, fn)`：平台员工的操作，以及登录前按邮箱 / 邀请令牌定位用户（那时还不知道租户）。用连接本身的账号执行，不受行级安全限制，SQL 必须自己带好条件。
- 角色和 `app.tenant_id` 都是事务级的（`set local`），事务结束即恢复，连接还回连接池不会残留。
- **不需要第二个连接串，不新增环境变量**：应用仍然用 `DATABASE_URL` 连接，只是在租户事务里切换角色。
- 每张租户表：开启行级安全；策略同时有 `using` 和 `with check`（读、改、写入都限定在当前租户）；按最小权限给 `nozomi_app` 授权。`nozomi_app` 对平台表（`platform_users`、`platform_sessions`、`login_throttles`、`schema_migrations`）没有任何权限，对 `tenants` 只能读自己那一行，对 `audit_logs` 只能追加自己租户的记录。
- 没有设置 `app.tenant_id` 时策略里的比较不成立，一行都看不到（默认拒绝）。
- 数据访问层的每个函数仍然显式接收 `tenantId` 并写在 `where` 里（ADR 0003 的第一道防线）。行级安全是兜底，不是替代。

### 以后新增租户表时要做的事

1. 表带 `tenant_id`，主键和索引以它开头。
2. `alter table … enable row level security`，建策略（`using` + `with check` 都是 `tenant_id = app_tenant_id()`）。
3. 按需要 `grant` 给 `nozomi_app`（只给用得到的权限）。
4. `rls.itest.ts` 的结构检查会自动发现没开行级安全、没有策略的租户表并失败；跨租户的接口测试加到 `tenant-isolation.itest.ts`（那里会核对每个 `/tenant/v1` 接口都被覆盖）。

### 有意的例外

- `tenant_users` 的邮箱唯一索引和邀请令牌唯一索引不以 `tenant_id` 开头：登录时只有邮箱、接受邀请时只有令牌，要在知道租户之前定位到用户，所以这两个值全平台唯一。对应的两个查询函数名字带 `AcrossTenants`，只返回（租户编号，用户编号），后续读写仍回到租户事务里做。
- `audit_logs` 是平台和租户共用的表（`tenant_id` 可以为空，表示平台级操作）：有以 `tenant_id` 开头的索引，也有供平台按人、按对象跨租户查询的索引。
- `tenant_roles` 是系统定义的角色清单，所有租户共用，不带 `tenant_id`。
- 密码重置令牌**没有**成为第三个例外：租户用户的重置令牌里带着租户编号，按（`tenant_id`，令牌哈希）查找，索引以 `tenant_id` 开头，兑换过程全程在租户事务里。

## 验证

`apps/api/src/rls.itest.ts`（连接账号是超级用户，正是行级安全默认不生效的情形）：

- 在租户事务里执行不带任何条件的 `select` / `update` / `delete`，只影响当前租户的行；按编号直接访问别的租户的行，一行都碰不到。
- 往别的租户写用户、会话、审计日志，或把自己的行改到别的租户名下，数据库拒绝。
- 应用角色访问平台表、修改租户主体、修改或删除审计日志、关闭行级安全，数据库拒绝。
- 没设置租户时一行都看不到；事务结束后角色和租户设置不残留。
- 结构检查：每张带 `tenant_id` 的表都开启了行级安全并有策略；应用角色不是超级用户、不能绕过行级安全、不拥有任何表。

## 对数据库账号的要求

- 迁移 0002 要创建角色 `nozomi_app` 并让迁移账号能切换到它。迁移账号是超级用户（Docker Compose 的默认情况）或有 `CREATEROLE` 权限时自动完成；两种情况都实测过。
- 如果用的是没有这些权限的托管数据库账号，迁移会失败并在报错里给出需要数据库管理员先执行的语句（`create role nozomi_app nologin; grant nozomi_app to <账号>;`）。
- 角色是整个数据库实例共用的：同一个实例上的多个库 / schema 共用同一个 `nozomi_app`，它本身没有任何权限，权限都是各库自己的迁移授予的。

## 理由

- 相比「应用用另一个非所有者账号连接」：不需要第二个连接串和密码，不需要在每个环境手工建账号，本地、CI、服务器的做法完全一致，测试里也能直接验证。
- 相比只用 `force row level security`：它管不住超级用户，而本地、CI、Docker Compose 部署用的正是超级用户。
- 平台操作不走行级安全而是直接用所有者身份：平台员工本来就要跨租户访问（ADR 0003），这些访问走单独的 `/platform/v1` 接口并写审计日志。

## 已知限制

- 事务进行中连接被数据库断开（重启、故障切换）时，只有这个请求失败，连接被销毁、连接池自己新建；切换角色这一步失败时也会先回滚再归还连接（`connection-reuse.itest.ts`）。
- `set local role` 防的是「代码漏写条件」，不是「执行任意 SQL」：能注入 SQL 的攻击者可以 `reset role`。防注入靠的是全部查询都用参数化。
- 绕过 `withTenantTx` 直接用连接池查询的代码不受行级安全保护。约定是业务代码只用这两个入口；代码评审时检查。
