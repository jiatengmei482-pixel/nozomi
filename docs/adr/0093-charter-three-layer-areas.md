# ADR 0093：包车报价三层区域模型、商品匹配、各商品自选套餐比价、数据迁移

- 状态：草案（2026-11-14，待独立审查）。实施里程碑 M9P（第九节）。
- 依据（以它为准）：业主《NOZOMI 包车报价逻辑规格（开发版）》2026-11-14，`docs/requirements/charter-pricing-spec-2026-11-14.md`（PR #221，下称「规格」），以及 PR #221 描述里监工转达的 7 条决定。与 `docs/requirements/charter-airport-packages-2026-11-14.md`（PR #217，下称「旧需求文档」）冲突处以规格为准。
- **部分取代** ADR 0088：第 3 节第 3 条后半（经停点同时在商品区域和加价区域里时收加价区域的途经加价）、第 3 节第 5 条后半（「已因上 / 下车计价的区域不再加」及「选中区域的加价为 0 也算已计价」）、待确认第 1、2 条的推荐答复、第 3 节第 2 条「重叠取最高」（改为同层不允许重叠，第七节）。0088 其余（经停点、明细、订单 `waypoints` 列、补充 M9W-06 / M9W-10）不变。
- **部分取代** ADR 0089：第 1 节公式里的「超时费」（下单时不再收，规格第一节）、第 3 节「选套餐（服务层）」（改为各商品在引擎里自己选，第四节）。第 2 节 `routeUsage`、第 4 节路线、第 5 节订单不变。
- **修改** ADR 0073：第三部分第 1 节「落在几个区域里取最小」、M8-15 细节「基础定价用哪个区域的」（第五节改为「车型组 × 套餐」一次填写）、M8-38 口径「大运营区不能把小加价区盖成 0」（改为基础价区优先，第二节）。
- **修改** ADR 0075 / 0084 只在包车：包车不再按「上车点所在城市」筛商品（第三节）；接送机、点对点的城市规则（ADR 0069 第 4 条、0084）不变。
- **与 ADR 0091（PR #218，修订中）的关系**：0091 的 T、商品级三项配置、`packageCheck` / `lockedItinerary` 的「只由服务层传、不进快照」做法沿用；0091 的「按 T 收超时费」「退路 = 最长档 + 超时」「服务层逐档询价两轮」作废（第四节、第十二节）。0091 应按本篇修订后再合并。
- **与 ADR 0092（PR #219，已暂停）的关系**：方向相反——规格第四节第 3 条要求同一区域不能既是①又是③。0092 不采纳，#219 改做法（第七节第 3 小节）。
- 硬约束（PR #221 决定 5）：**只改包车报价；接送机、点对点报价结果完全不变**（`quote-compat.golden.json` 的接送机、点对点条目一字不改）；包车 golden 按规格更新，逐条列出期望值变化及原因（第六节第 4 小节）。

编号：main 上最大是 0090；0091（#218）、0092（#219）在未合并的分支上，这里用 0093。

## 一、三层区域模型

### 现状

| 现在的叫法 | 存在哪 | 报价里的作用 |
| --- | --- | --- |
| 服务区域（商品选的报价区域） | `product_areas` | 套餐价按「服务区域 × 车型组 × 套餐」填（`price_rules`，`pricing_model = 'charter_package'`，`area_id` 必填）；点在这里 → 这一端加 0（但同时落在有可用加价的加价区域里时收加价，M8-38） |
| 区域加价 | `price_rules`，`pricing_model = 'charter_area_surcharge'`，`params = { pickupSurchargeMinor, dropoffSurchargeMinor, waypointSurchargeMinor? }`，按「区域 × 车型组 × 套餐」 | 上车 / 下车 / 经停三种端点都从同一行取；任何一个有启用规则的区域都算「加价区域」（`surchargeAreaIds`），上车点、下车点落在里面就能匹配 |

问题（规格第五节）：经停和上下车共用一行，没法建「只管经停」的区域（#8）；上下车加价必填（#8）；服务区域与加价区域可以重叠、加价区域之间可以重叠取最高（#3、#4）。

### 新做法

| 层 | 规格名 | 后台位置 | 存储 | 判断用哪个点 | 金额 |
| --- | --- | --- | --- | --- | --- |
| ① | 基础价区域 | 基础信息 → 服务区域（现有） | `product_areas`（不变） | 上车点、下车点；经停点只用来「跳过」 | 不填加价；套餐价整单一次（第五节） |
| ② | 行程区域 | 价格规则 → **行程加价**（新） | `price_rules` 新价格方式 `charter_itinerary_surcharge`，`params = { surchargeMinor }` | 只看经停点（含第二节第 4 小节的「下车点当经停」） | 按车型组；`package_hours` 可空（空 = 所有套餐，见下） |
| ③ | 上下车加价区域 | 价格规则 → **上下车加价**（现有「区域加价」改名） | `price_rules` 现有 `charter_area_surcharge`，只用 `pickupSurchargeMinor`、`dropoffSurchargeMinor` | 只看上车点、下车点 | 上车 / 下车各一格，按车型组；`package_hours` 同② |

- ②③是两张独立的价格表：同一地理区域可以同时在两表里（金额各填），也可以用不同的区域（②画小景区如华严瀑布、河口湖，③按距离画大范围）。
- **空格 = 不报价**：②某车型组没填 → 经停在这里时这个车型组不报；③同理（规格第四节）。要不加钱必须明填 0（和 ADR 0088「没设 ≠ 0」同一口径）。
- 「表」的实现：②是 `price_rules` 里的一种新价格方式，后台显示为独立的「行程加价」表；不另建物理表（理由和比较见第十一节第 1 条）。
- **按车型组、套餐可空**：规格写「按车型组」。现有③（和途经加价）是按「车型组 × 套餐」存的。新规则的 `package_hours` 允许为空（= 这个车型组的所有套餐）；引擎找规则时同一区域 × 车型组先找套餐对得上的行、再找套餐为空的行。这样迁移可以把现有按套餐的值**原样搬过去**（不必合并、不丢信息），新填的只按车型组填一次。

### 对现有数据 / 报价的影响

- ①不动。③的数据不动（只是后台改名，`waypointSurchargeMinor` 迁走后对③变成只读的旧值，见第六节）。
- ②是新增的规则，迁移前为空——在迁移和引擎切换（第九节 M9P-05）之前，引擎照旧从③的 `waypointSurchargeMinor` 取途经加价（双读：有②规则的商品只看②）。
- 冲突检查的「价格方式分类」由 ADR 0073 M8-15 的两类（基础定价 / 加价）改为三类（套餐价 / 上下车加价 / 行程加价）：同一区域可以同时有③和②，不算冲突。

## 二、加价算法（规格步骤 4）

### 现状（`packages/domain/src/quote.ts` `quoteProduct` 第 840–870 行、`waypointSurcharges` 第 1049 行）

- 上 / 下车（`endCharge`）：点落在有可用加价的加价区域里就收（几个取最高，`prefer: "highest"`），哪怕也在服务区域里（M8-38）；加价区域都没可用规则时，在服务区域里算 0，否则不报。
- 经停：同上取 `waypointSurchargeMinor` 最高的区域；同一区域只加一次；**上车、下车各自选中的区域不再加**（`chargedAreaIds = [pickup.areaId, dropoff.areaId]`）——这就是 P0 #1「东京上车 → 河口湖经停 → 河口湖下车只收下车 11,000」的原因。
- 没有经停点的单：不收任何途经加价。

### 新做法

```
上下车加价(点, 方向)：
  点在商品任一① → 0（基础价优先）
  否则取点所在的③（同层不重叠，第七节保证只有一个；迁移过渡期仍有重叠时取最高，并记入迁移报告）
  ③不存在，或这个车型组 × 套餐在这个③没有可用规则 → 这个商品的这个车型组不报
  返回 ③.加价[方向]

行程加价：
  已收区域 = 空
  对每个经停点（按顺序）：
    在商品任一① → 跳过（市内经停不加价）
    取所在的②；不存在，或这个车型组没有可用规则 → 这个车型组不报（WAYPOINT_NOT_PRICED，带 stopSeq）
    ②不在已收区域里 → 加 ②.加价，记入已收区域（明细记下是第几个经停点）
  **不因为上车点或下车点也在这个②（或同名的③）就跳过**

总加价 = 上车加价 + 下车加价 + 行程加价
```

- 去掉 `waypointSurcharges` 的 `chargedAreaIds` 参数（P0 #1）。
- 「点在①」用 `locateInAreas(product.areas, …)`；①优先后，③画在①里的部分不再起作用（第七节禁止这种配置）。
- 规格四个标准场景（10h）用这套算法：东京往返富士山 = +10,000；东京上车 → 富士山下车 = +20,000（靠第 4 小节）；富士山上车 → 富士山游玩 → 富士山下车 = +30,000；富士山上车 → 箱根游玩 → 富士山下车 = 箱根行程 + 富士山上 + 下 = +30,000（不收富士山行程：行程只看经停点）。

### 第 4 小节：没有经停点的单把下车点所在②当作一个经停

- 商品级开关 `dropoffCountsAsStop`，**默认开启**，放在 `products.service_rules.charterItinerary`（和 ADR 0091 的三项同一个键；默认值不存键、PUT 不带键 = 保留原值，沿用 0091 / M9W-11 分支的做法）。**待业主确认**（规格写「待业务确认」，PR #221 决定 4）。
- 只在 `waypoints` 为空时生效；按客人自选时长（不按行程计价）的包车同样生效。
- 下车点在① → 跳过；下车点不在任何② → **跳过、不拒**（下车点已经靠①或③匹配上了，它不是客人填的经停点，拒掉会让「东京上车 → 镰仓③下车」这类单因为镰仓没画②而报不出）。这一点和真实经停点「不在②就不报」不同，**一并请业主确认**（第十三节第 2 条）。
- 明细写「行程加价（镰仓，下车点）」，`stopSeqs` 为空数组、另记 `fromDropoff: true`。

### 明细逐项（规格步骤 4 末）

结算价明细 `areaSurcharge` 改为：`pickup { areaId, priceRuleId, amountMinor }`（在①时 `areaId: null`）、`dropoff` 同、`itinerary: [{ areaId, priceRuleId, amountMinor, stopSeqs, fromDropoff? }]`（新键，取代 `waypoints`；旧单的 `waypoints` 照旧能读）。对外 `price_breakdown` 顺序：套餐、上车加价（区域名）、下车加价（区域名）、行程加价（区域名，第几个经停）、超公里费、调价、其他。

### 对现有数据 / 报价的影响（都是按规格的有意改动）

| 变化 | 例 | 归哪个任务 |
| --- | --- | --- |
| 经停区域和上 / 下车区域相同时多收行程加价 | P0 #1：+11,000（对外） | M9P-01 |
| 没有经停点、下车点在②里时多收一次行程加价 | 「东京上车 → 镰仓下车」+镰仓行程 | M9P-01（开关默认开） |
| 上 / 下车或经停在①里时不再收加价（①与③或②重叠处） | P1 #3：羽田∩横滨 3,300 → 0 | M9P-06 |
| 经停只看②：只有③没有②的区域里经停 → 不报 | 现在取③行里的途经加价，迁移后同值进②，结果不变；迁移前没填途经加价的区域本来就不报（M9W-10） | M9P-05 |

## 三、商品匹配（规格步骤 1）

### 现状

- 前端：新预订页按上车点找城市（`apps/web/src/pages/book/new/BookNewPage.tsx` 的 `charterCityOf` → `serviceCityOf`，城市中心约 80 公里范围内最近的能订包车的城市），找不到就不询价。
- 后端：`POST /site/v1/quotes` 必须带 `city_id`；候选商品只取这个城市的（`apps/api/src/repos/quotes.ts` `loadQuoteCandidates`：`where p.city_id = $1`）；能选的套餐也按城市（`apps/api/src/repos/site.ts` `listBookableCharterPackages`）。
- 引擎（`charterEnds`）本来就允许上车点只在加价区域里（ADR 0073 M8-15）。所以 P0 #2「河口湖上车暂时没有在线报价」不是引擎拒的：河口湖离东京中心超出城市范围，前端在选城市这一步就停了。
- 现在任何一个有启用区域加价的区域都能让上 / 下车点「匹配」——包括只为经停设的。

### 新做法

1. **匹配条件**（引擎 `charterEnds`）：上车点、下车点都落在这个商品的①或③里才参与；③只认有启用的上下车加价规则的区域（`charter_area_surcharge`），②（`charter_itinerary_surcharge`）不参与匹配。经停点不影响匹配，只影响行程加价（经停点不在任何①②里 → 这个商品不报，转人工，规格步骤 1）。
2. **不再按上车城市筛**（服务层）：包车询价的 `city_id` 改为可选；不给时服务器自己找城市：
   - 新的 repo 查询 `loadCharterCityCandidates`：渠道范围（`channel.scope.cityIds`）里所有已上架的包车商品，连同①的图形和③规则的区域图形；用 domain 新函数 `charterMatches(product, pickup, dropoff)`（和 `charterEnds` 共用同一段区域判断）挑出能匹配的商品，取它们的城市（`products.city_id`）。
   - 一个城市（今天日本只有东京有包车）→ 照现有流程按这个城市询价：候选、比价、询价日志（`quote_logs.city_id` 不可空，填这个城市）、快照全不改。
   - 多个城市 → 每个城市各询一次（各写各的日志），按车型组取对外价最低的那个报价返回。跨城市不并进同一个同价区间（中标排序的评分、区间规则只在一个城市的一次比价里用）。
   - 一个都没有 → `OUT_OF_SERVICE_AREA`，转人工；照 ADR 0075 第四部分记未覆盖需求（城市取上车点的 `serviceCityOf`，没有时不记，和点对点两端都不在城市时一致）。
   - 带 `city_id` 的旧请求照旧（兼容嵌入组件、旧页面），但服务器同样先按上一条找城市，`city_id` 只在匹配到多个城市时用来排序。
3. **前端**：去掉 `charterCityOf` 的「找不到城市就不询价」，包车询价不再带 `city_id`；套餐时长下拉（不按行程计价时）改调 `GET /site/v1/charter-packages?pickup=…&dropoff=…`（按匹配到的商品列套餐），旧的按城市的接口保留。
4. **多商品时同一车型取总价最低**：同一城市里沿用现有比价（`compareQuotes` → `rankCandidates`：同一租户只留最低；跨租户按平台既定的同价区间 + 评分排序，规格第五节「已确认正常：多商品同时报价展示最低价」）。各商品先各自选套餐再比（第四节）。
5. `/sales/v1`（渠道）：`city_id` 仍必填（不打断已接入的渠道）；匹配条件第 1 条同样生效（引擎改动）。渠道要不要也去掉城市，**另开任务**（M9P-02 的验收里不含）。

### 对现有数据 / 报价的影响

- 以前在城市范围外上车的询价（P0 #2 河口湖、镰仓站等）从「不询价」变成按东京包车报价（规格第六节第 4、5、8 条）。这类询价以前没有询价日志，回放比对看不到它们；由集成测试和测试站用例证明。
- 只为经停设的区域（只有途经加价、上下车加价是 0 的那种行）——迁移后进②，不再让上 / 下车点匹配；迁移报告列出「上下车加价两格都是 0、只有途经加价」的行，请运营确认是不是只想管经停（第六节第 3 小节）。
- 接送机、点对点：不走这条路，城市规则不变。

## 四、选套餐与比价（规格步骤 2、3；配合 ADR 0091 需求二的 T）

### 现状

- 服务层先统一定时长再比价（`apps/api/src/services/site.ts` `itineraryQuotes` 第 591–618 行）：取城市能选的所有档，先「能覆盖行驶 + 停留」的从短到长、再覆盖不了的从长到短，**逐档**调 `siteQuotes`，每个车型组取第一个报得出的档。结果：
  - 一档里只有含这一档的商品参加比价（P1 #5：特殊商品只有 8 / 10 / 12h，5h48m 被定为 6h，特殊商品不参与）；
  - 只按时长选（P1 #6：132 km 选 4h + 超公里 47,259，5h 只要 46,200）；
  - 超过最长档时最长档 + 超时费；
  - 每一档写一条询价日志、生成一批快照。
- 引擎在 `request.routeUsage` 给了时按 `basePrice` 的包车公式算超公里**和超时**（ADR 0089）。
- ADR 0091（未合并）加了 T 和 `packageCheck`，仍是服务层逐档。

### 新做法

1. **T**（规格步骤 2）：T = 行驶分钟 + Σ停留 + 经停数 × 每站默认占用 + 整单缓冲。直接用 M9W-11 分支（`origin/m9w-11-package-buffer`）的 `itineraryEstimate` 和 `service_rules.charterItinerary { stopOccupancyMinutes, bufferMinutes, minPackageHours }`。D = 全程米数。默认值沿用 0091（0 / 0 / 不限，行为不变），建议值由业主在后台填。
2. **候选**：这个商品这个车型组可用的套餐（启用、在生效期）里 **时长 ≥ T（且 ≥ 最低套餐）** 的全部；一档都没有时**只有最长那一档**（不收超时费）。
3. **取最低**：每个候选算 `套餐价 + max(0, D − 含公里) × 超公里单价`，取最小；一样时取短的。上下车加价、行程加价、调价不参与选择（旧需求文档第四节「区域加价和经停加价不影响选择」；②③即使按套餐细分也不参与）。
4. **超时费下单时不收**（规格第一节、PR #221 决定 2）：新口径下结算价明细 `itinerary.overtimeMinor = 0`、另记 `overtimeAtBooking: false`；`price_breakdown` 不再有 `overtime` 项。超时由供应商服务后提交（现有事后加收流程，基准 = 套餐时长）。0091 的「按 T 补收」作废。
5. **在引擎里按商品选**（`quoteProduct`）：`QuoteRequest` 加可选 `charterSelection: "auto"`——**进快照、进询价日志**（它决定价格，回放要能重现）；同时 `packageHours: null`、给 `routeUsage`。引擎对每个商品每个车型组按上面 2、3 选档，`VehicleOffer.packageHours` 记选中的档（这个字段现在就有）。没有 `charterSelection` 的请求（改期、救援、平台试算、旧日志回放、golden）和现在**逐字一样**——包括按行程计价旧单的超时费。
6. **客人手动升套餐**：`itinerary_pricing: true` 时允许带 `package_hours`（同 0091 第三节第 1 小节）；引擎收到 `charterSelection: "manual"` + `packageHours = H`：H × 60 ≥ T、或 H 是这个商品这个车型组最长的档 → 按 H 报（不收超时）；否则这个车型组 `PACKAGE_TOO_SHORT`（对外带 `min_package_hours`）。不能短于 T。
7. **比价**：同一车型组里各商品各自选了档、各自算出总价，再按现有 `rankCandidates` 比。`ComparisonGroup.packageHours`（现在 = `request.packageHours`）在 `auto` 时为 `null`，每个候选的档看 `offer.packageHours`；中标的档写进快照的 `winner.offer.packageHours` 和订单 `package_hours`（`orders.ts` 第 311 行本来就取 `winner.offer.packageHours`）。
8. **服务层**：`itineraryQuotes` 去掉逐档循环，改为**一次** `siteQuotes`（`charterSelection: "auto"`）；应答每个报价给 `estimated_minutes`（中标商品的 T）、`includes_buffer`、`auto_package_hours`（= 中标档；手动升档时给自动选出来的档）。「未覆盖需求」、报不出原因自然只有一次（0091 第四节第 3 小节那两项有意改动在这里不再需要「延后记 / 合并」，因为只询一次）。
9. **改期、救援**：从订单拿 `package_hours` 和快照 `request`，传 `charterSelection: "locked"`（引擎：按给定的 H 报、不判 T、不收超时费）；`rescues.ts` 第 399 行、`order-changes.ts` 第 266 行按 `packageHours` 找报价的逻辑不变（H 已固定）。部署前下的按行程计价单快照里没有 `charterSelection`，改期照旧收超时费（逐字不变）。
10. 不带经停点、客人自选时长的包车：不变（客人选 H，引擎不选档），只受最低套餐限制（0091 第六节第 6 条推荐「这次不改」，沿用）。

### 对询价日志、快照、回放（ADR 0086）的影响

- **询价日志**：按行程计价每次询价从「N 档 N 条」变成 1 条；`request` 多 `charter_selection`、没有 `package_hours`。`bids[].package_hours` 照旧记中标档。
- **快照**：`request.charterSelection`、`request.packageHours: null`；`winner.offer.packageHours` 是选中的档；`candidates` 里每个候选多记它自己的档（排序依据要能复算）。
- **回放**：`replay-digest.ts` 的 `offerParts` 不改（它本来就逐车型组记套餐、金额、规则编号）。新口径日志带 `charter_selection`，回放据此重现选档；旧日志不带，回放按旧口径重算（逐字不变）。切换前后的比对按第六节第 5 小节分类处理。
- 平台报价试算：加一个「按行程（新口径）」选项，默认按新口径，结果旁注明选了哪一档、T 是多少。

## 五、套餐价改为「车型组 × 套餐」一次填写

### 现状

套餐价规则 `charter_package` 按「服务区域 × 车型组 × 套餐」存（`price_rules.area_id not null`，迁移 0014）。引擎对上车点所在的服务区域取价（上车点只在加价区域时用下车点的，两端都不在时每个区域都算取最低，ADR 0073 M8-15）。P1 #7：服务区域没填套餐价 → 上车报不出、经停收 0。

### 新做法

- `price_rules.area_id` 对 `charter_package` 允许为空：**空 = 整个商品的套餐价**（规格「处处是东京市内价」）。迁移只放宽约束（加检查约束：`area_id is not null or pricing_model = 'charter_package'`），不改已有行。
- 引擎双读：商品有启用的「整商品套餐价」（`area_id is null`）时**只用它们**，不再按区域取价；没有时走旧逻辑（逐字不变，`quote-compat` 的包车样例、`charter-golden` 不受影响）。
- 冲突键：整商品套餐价按「车型组 × 套餐 × 生效日期」查重。上架检查「该有价格的组合」对有整商品套餐价的包车商品改为「每个车型组至少一档」，不再按服务区域查（P1 #7「上架拦下」）。
- **迁移**（第六节）：每个包车商品取一个「基础价来源区域」的套餐价复制成整商品套餐价——东京包车取「东京市内」服务区域；通用规则：取商品服务区域里排第一的（`product_areas` 的优先级），迁移报告写明取的是哪个区域，运营可以改。**其他服务区域与它不一致的组合逐条列进迁移报告**（区域、车型组、套餐、两边金额、含公里、超时 / 超公里单价）。
- **旧的按区域套餐价保留、只读**：后台价格页只显示「整商品套餐价」可编辑，旧行折叠在「旧的按区域套餐价（只读，迁移前的数据）」下面；导入导出只认新格式（旧模板导入给出明确提示）。验证通过后另开 M9P-12 清理。

### 对现有数据 / 报价的影响

- 迁移执行（只在测试站）之后：服务区域之间价格不一致的商品，原来在「非来源区域」上车的报价会变成来源区域的价。全部列入迁移报告；这是规格「套餐价整单只算一次（东京市内价）」的有意改动。
- 迁移前：无变化。

## 六、数据迁移方案

### 1. 原则

- **只做加法**：放宽 `price_rules.area_id` 约束、加检查约束、加价格方式 `charter_itinerary_surcharge`（改 `price_rules_model_check`、`price_rules_package_matches_model`：②③套餐可空）；不删列、不改旧行的值。
- **结构用迁移（`apps/api/migrations/04xx_*.sql`）建；数据搬迁用独立脚本** `pnpm charter:migrate-three-layer --dry-run | --apply`，通过只读接口同样的权限边界执行（ADR 0086 的做法：GitHub Actions 手动工作流 + 平台账号，不用 SSH）。脚本只在测试站执行；正式站另行决定。
- **不手改运营数据**：脚本只**新增**②规则和整商品套餐价，不改、不删任何现有规则；运营要改的（重叠、①上的③、不一致的价格）只列进报告。
- 脚本可重复执行（已迁过的跳过）；`--dry-run` 输出报告不写库。所有写入一个事务，写审计日志（对象 `price_rule`，操作 `migrate`）。

### 2. 搬什么

| 来源 | 去处 | 规则 |
| --- | --- | --- |
| ③行 `params.waypointSurchargeMinor`（途经加价） | ②规则：同租户、同商品、同 `area_id`、同车型组、同 `package_hours`、同生效日期和状态，`params = { surchargeMinor }` | 没设途经加价的行不搬（没设 = 不报，迁移后②没有 = 不报，一致） |
| 「基础价来源区域」的 `charter_package` 行 | 整商品套餐价（`area_id null`），其余字段照抄 | 来源区域见第五节 |

搬完后引擎对有②规则的商品只从②取行程加价（③的 `waypointSurchargeMinor` 不再读，后台不再显示「途经加价」列）。

### 3. 迁移报告（给运营，不含对外价）

1. 套餐价不一致：非来源服务区域与来源区域不同的组合。
2. ①上设了③（同一区域既是服务区域又有上下车加价规则）——规格第四节第 3 条禁止，列出请运营删掉其中一个。
3. 几何重叠：①①、②②、③③、①③重叠的区域对和重叠面积（`findAreaOverlaps`）。
4. 只有途经加价、上下车加价都是 0 的③行（可能本意只管经停，迁移后仍能让上 / 下车点匹配）。
5. 空格：②③表里某车型组没填的格（= 不报价）。
6. 城市热门景点清单（第七节第 4 小节）里不在任何区域的点——清单为空时这一项写「未配置」。

### 4. 包车 golden

- `quote-compat.golden.json` 的接送机、点对点条目**一字不改**；包车条目和 `charter-golden.json`、M9W-11 分支的 `itinerary-golden.json`（1,008 条，在原代码上生成）：**不带新参数（没有 `charterSelection`）、没有②规则、没有整商品套餐价**时逐字段不变——这一组证明旧单改期、旧日志回放不受影响。
- 新口径另建 `charter-spec-golden`（按规格第六节 15 个用例的数据 + 各任务的边界样例）；凡是因本 ADR 有意改变的旧 golden 条目，在实现 PR 里**新增**一份按新口径算的期望值，并在 PR 描述里逐条列表（不重新生成旧文件）：

| --- | --- | --- | --- | --- |

## 七、后台校验（规格第四节）

### 现状

- 价格页保存区域加价：区域不能是商品本身的服务区域（`apps/api/src/services/prices.ts` 第 365 行 `AREA_IS_PRODUCT_AREA`），批量保存时整批被拒，页面一直显示「有 N 条未保存」（业主报的 Bug，M8-46）。PR #219 / ADR 0092 的做法是放开这条。
- 区域重叠：只有区域页的软提醒（`packages/domain/src/area-overlap.ts` `findAreaOverlaps`、`findPricingOutsideOperating`）；同层重叠时报价取最高。
- 没有上架覆盖检查、没有空格提示。

### 新做法（保存和上架都在后端校验，前端在保存前就提示）

1. **同商品同层不重叠**（①①、②②、③③）：保存服务区域、②规则、③规则时，用 `findAreaOverlaps` 算这个商品同一层所有区域两两的重叠；有重叠 → 400 `AREA_LAYER_OVERLAP`，`details` 给两个区域名和重叠面积（km²，一位小数）。只有边界接触（面积 < 0.01 km²）不算。
2. **①与③不重叠**（几何）：同上，`AREA_BASE_SURCHARGE_OVERLAP`。①②、②③可以重叠。
3. **同一区域不能既是①又是③**：保留 `AREA_IS_PRODUCT_AREA`（ADR 0092 不采纳），文案改为「这个区域是商品的基础价区域（服务区域），在这里上下车不加价，不能再设上下车加价。」。**#219 的处理**：不放开；改为前端在保存前拦——区域下拉里服务区域灰掉并写「基础价区域，不能设上下车加价」；已经存在的「①上的③」行在表里标红、写同样的话、提供「删除这一行」按钮，**不计入「未保存」**；批量保存时这些行不提交，其余行照常保存，不再整批卡住。设②时服务区域可以选（①②可以重叠）。#219 里「保存卡在有 N 条未保存」的前端修复（计数、错误展示）可以复用，`AREA_IS_PRODUCT_AREA` 删除那部分撤回。
4. **上架覆盖检查**：「城市热门景点坐标清单」复用平台主数据 `places`（`type = 'poi'`，已挂城市、有坐标、运营后台维护），加一列 `charter_coverage boolean not null default false`（迁移，只加列）；运营在运营后台地点页勾选哪些地标进清单。**不预置任何数据**（规则 1），清单由运营在后台填。包车商品上架检查（`publish_check`）新增一项 `charter_coverage`：列出商品所在城市清单里不在这个商品任何①②③的地标——**提醒、不拦上架**（规格写「列出」）。清单为空时这一项不出现。
5. **加价表空格提示**：②③表里每个区域行，某车型组没填的格显示「空 = 不报价」的灰底提示；表头汇总「N 格没填」；上架检查同样列出（提醒）。
6. 重叠校验只对新保存生效；已有的重叠数据在迁移报告里列出（第六节第 3 小节），由运营处理，校验不回头锁死已有数据（否则运营改别的价格也存不了）。

### 后续（不在本篇实施范围，立任务 M9P-13）

区域编辑器建议：「从本区域减去另一个区域」切掉重叠；「在地图上看全部」按商品和层筛选、标红重叠；区域详情显示它在哪些商品里当①/②/③。

### 对现有数据的影响

不改数据。测试站「东京包车」若有①上的③、重叠区域，迁移报告列出，运营处理前报价按第二节①优先算（①上的③不起作用）。

## 九、实施顺序和任务拆分（新里程碑 M9P）

**为什么新开里程碑而不接在 M9W 后面**：M9W 的目标是「第一期从简，不填经停点时报价完全不变」（ADR 0088）；本规格有意改变包车报价、改数据结构，验收标准和回放判法都不同，放在一起会让 M9W 的「完全不变」失去意义。另外 PR #218 在 M9W 下立了 M9W-11～14（需求一～四），#218 还没合并，接着编号会撞号。M9W-07（受阻：最短覆盖套餐不一定最便宜）由 M9P-03 解决；#218 的 M9W-12～14 对应 M9P-09、M9P-03、M9P-10，#218 合并时应把它们标为「已移到 M9P」（#218 按新规格修订时一并处理）。

顺序（监工定）：P0 #1、#2 → 需求二 + #6 + #5 → #3 / #4 / #7 / #8 区域模型与后台校验 → 需求一机场套餐 → P2 #10、#11。

## 十、验收方法

1. 部署后在测试站（`/book/new`，包车，东京包车商品，经济 7 座）逐条跑规格第六节 15 个用例；前台价 = 结算价 × 1.1。
2. **测试站现有金额与规格表不同**（例：今天实测镰仓前台 9,900，即结算 9,000；规格表镰仓 8,000 × 1.1 = 8,800）：期望值按测试站当时的实际配置（套餐价、②③金额）用规格公式算，验证的是公式；验收报告另列「与规格表的金额差异」表交运营（区域、车型组、规格表金额、测试站金额），**不改运营数据**。
3. 第 2–6 条实际按预计用时自动选套餐，验收时可手动升到 10h 核对（规格原话）。
4. 第 14、15 条在测试供应商（ADR 0077）的商品上做，不动业主真实商品。
5. 截图、询价应答（结算价明细）写进验收报告 `docs/acceptance/M9P-11.md`。
