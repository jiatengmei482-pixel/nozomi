## 一、三层区域模型

### 现状

| 现在的叫法 | 存在哪 | 报价里的作用 |
| --- | --- | --- |
| 服务区域（商品选的报价区域） | `product_areas` | 套餐价按「服务区域 × 车型组 × 套餐」填（`price_rules`，`pricing_model = 'charter_package'`，`area_id` 必填）；点在这里 → 这一端加 0（但同时落在有可用加价的加价区域里时收加价，M8-38） |
| 区域加价 | `price_rules`，`pricing_model = 'charter_area_surcharge'`，`params = { pickupSurchargeMinor, dropoffSurchargeMinor, waypointSurchargeMinor? }`，按「区域 × 车型组 × 套餐」 | 上车 / 下车 / 经停三种端点都从同一行取；任何一个有启用规则的区域都算「加价区域」（`surchargeAreaIds`），上车点、下车点落在里面就能匹配 |

问题（规格第五节）：经停和上下车共用一行，没法建「只管经停」的区域（#8）；上下车加价必填（#8）；服务区域与加价区域可以重叠、加价区域之间可以重叠取最高（#3、#4）。

### 新做法

| 层 | 规格名 | 后台位置 | 存储 | 判断用哪个点 | 金额 |
| --- | --- | --- | --- | --- | --- |
| ① | 基础价区域 | 基础信息 → 服务区域（现有） | `product_areas`（不变） | 上车点、下车点；经停点只用来「跳过」 | 不填加价；套餐价整单一次（第五节） |
| ② | 行程区域 | 价格规则 → **行程加价**（新） | `price_rules` 新价格方式 `charter_itinerary_surcharge`，`params = { surchargeMinor }` | 只看经停点（含第二节第 4 小节的「下车点当经停」） | 按车型组；`package_hours` 可空（空 = 所有套餐，见下） |
| ③ | 上下车加价区域 | 价格规则 → **上下车加价**（现有「区域加价」改名） | `price_rules` 现有 `charter_area_surcharge`，只用 `pickupSurchargeMinor`、`dropoffSurchargeMinor` | 只看上车点、下车点 | 上车 / 下车各一格，按车型组；`package_hours` 同② |

- ②③是两张独立的价格表：同一地理区域可以同时在两表里（金额各填），也可以用不同的区域（②画小景区如华严瀑布、河口湖，③按距离画大范围）。
- **空格 = 不报价**：②某车型组没填 → 经停在这里时这个车型组不报；③同理（规格第四节）。要不加钱必须明填 0（和 ADR 0088「没设 ≠ 0」同一口径）。
- 「表」的实现：②是 `price_rules` 里的一种新价格方式，后台显示为独立的「行程加价」表；不另建物理表（理由和比较见第十一节第 1 条）。
- **按车型组、套餐可空**：规格写「按车型组」。现有③（和途经加价）是按「车型组 × 套餐」存的。新规则的 `package_hours` 允许为空（= 这个车型组的所有套餐）；引擎找规则时同一区域 × 车型组先找套餐对得上的行、再找套餐为空的行。这样迁移可以把现有按套餐的值**原样搬过去**（不必合并、不丢信息），新填的只按车型组填一次。

### 对现有数据 / 报价的影响

- ①不动。③的数据不动（只是后台改名，`waypointSurchargeMinor` 迁走后对③变成只读的旧值，见第六节）。
- ②是新增的规则，迁移前为空——在迁移（第九节 M9P-05 / M9P-08）之前，引擎照旧从③的 `waypointSurchargeMinor` 取途经加价。新旧表怎么切换见下一小节。

### 新旧表按「商品迁移过没有」切换（审查建议第 8 条，采纳这一种）

- 商品加一列 `products.charter_layout text null`（迁移只加列；`null` = 旧表，`'three_layer'` = 新表）。**只由迁移脚本（第六节）在把这个商品的②和整商品套餐价都建好的同一个事务里写**；供应商、运营的接口都不能改它（不在 PUT 字段里）。写的时候商品 `version` 加一、记审计。
- 引擎：`charter_layout = 'three_layer'` 的商品，经停只从②取、套餐价只用整商品套餐价；`null` 的商品**整套用旧表**（③行的途经加价、按服务区域的套餐价），不看②和整商品套餐价，即使有这类行也不读。
- 价格页、导入导出、价格接口：按同一个标志决定显示和接受哪一套表——没迁移过的商品照旧显示旧表（正式站部署后什么都不变），迁移过的显示三张新表、旧行折叠只读。没迁移过的商品**不能**新建②和整商品套餐价（接口 400 `CHARTER_LAYOUT_NOT_MIGRATED`），迁移过的不能再新建按区域套餐价和③的途经加价。
- 第二节的算法改动（M9P-01 去掉「上下车已计价不再加」、M9P-06 ①优先）**和这个标志无关**，对新旧表都生效；标志只决定「经停加价、套餐价从哪张表取」。
- 不采纳「按车型组 × 套餐逐格回退」：② 的「空 = 不报价」和逐格回退到③的旧途经加价互相矛盾（运营删掉一个②格，经停会悄悄按③的旧值收，而不是不报）；每一格可能来自不同的表，报价、明细、回放都很难说清。也不采纳上一稿的「有②规则就整体只看②」：正式站运营在新价格页填一行就让整个商品切换（审查建议第 8 条指出的问题）；改成显式标志后，切换只发生在迁移脚本里，一次切完。
- 冲突检查的「价格方式分类」由 ADR 0073 M8-15 的两类（基础定价 / 加价）改为三类（套餐价 / 上下车加价 / 行程加价）：同一区域可以同时有③和②，不算冲突。

## 二、加价算法（规格步骤 4）

### 现状（`packages/domain/src/quote.ts` `quoteProduct` 第 840–870 行、`waypointSurcharges` 第 1049 行）

- 上 / 下车（`endCharge`）：点落在有可用加价的加价区域里就收（几个取最高，`prefer: "highest"`），哪怕也在服务区域里（M8-38）；加价区域都没可用规则时，在服务区域里算 0，否则不报。
- 经停：同上取 `waypointSurchargeMinor` 最高的区域；同一区域只加一次；**上车、下车各自选中的区域不再加**（`chargedAreaIds = [pickup.areaId, dropoff.areaId]`）——这就是 P0 #1「东京上车 → 河口湖经停 → 河口湖下车只收下车 11,000」的原因。
- 没有经停点的单：不收任何途经加价。

### 新做法

```
上下车加价(点, 方向)：
  点在商品任一① → 0（基础价优先）
  否则取点所在的③（同层不重叠，第七节保证只有一个；迁移过渡期仍有重叠时取最高，并记入迁移报告）
  ③不存在，或这个车型组 × 套餐在这个③没有可用规则 → 这个商品的这个车型组不报
  返回 ③.加价[方向]

行程加价：
  已收区域 = 空
  对每个经停点（按顺序）：
    在商品任一① → 跳过（市内经停不加价）
    不在任何② → 这个商品不报（各车型组 WAYPOINT_NOT_PRICED，带 stopSeq；和现在「经停哪个区域都不在」同一个原因码）
    在②里但这个车型组没有可用规则 → 这个车型组不报，**沿用现有原因码**（NO_PRICE_RULE / PRICE_RULE_DISABLED / PRICE_NOT_IN_EFFECT，经 pickRefusal 选，带 stopSeq）
    ②不在已收区域里 → 加 ②.加价，记入已收区域（明细记下是第几个经停点）
  **不因为上车点或下车点也在这个②（或同名的③）就跳过**

总加价 = 上车加价 + 下车加价 + 行程加价
```

- 去掉 `waypointSurcharges` 的 `chargedAreaIds` 参数（P0 #1）。
- **原因码不变**（复审必改第 2 条）：现在 `quote.ts` 只在经停「哪个区域都不在」时报 `WAYPOINT_NOT_PRICED`（第 857 行），经停在加价区域里但没有可用规则时走 `pickRefusal` 带 `stopSeq`（第 866 行）。新算法照这个分法：不新增、不改原因码。这样回放摘要（`replay-digest.ts` 带着原因码）、M9W-10 前端按原因码转人工都不受影响，golden 里报不出的样例（`fujiOverlap→saitama→chiba`、`hachioji→chiba+kamakura→tokyo` 等）原因码也不变。
- 「点在①」用 `locateInAreas(product.areas, …)`；①优先后，③画在①里的部分不再起作用（第七节禁止这种配置）。
- 规格四个标准场景（10h）用这套算法：东京往返富士山 = +10,000；东京上车 → 富士山下车 = +20,000（靠第 4 小节）；富士山上车 → 富士山游玩 → 富士山下车 = +30,000；富士山上车 → 箱根游玩 → 富士山下车 = 箱根行程 + 富士山上 + 下 = +30,000（不收富士山行程：行程只看经停点）。

### 第 4 小节：没有经停点的单把下车点所在②当作一个经停

- 商品级开关 `dropoffCountsAsStop`，**默认开启**，放在 `products.service_rules.charterItinerary`（和 ADR 0091 的三项同一个键；默认值不存键、PUT 不带键 = 保留原值，沿用 0091 / M9W-11 分支的做法）。**待业主确认**（规格写「待业务确认」，PR #221 决定 4）。
- 只在 `waypoints` 为空时生效；按客人自选时长（不按行程计价）的包车同样生效。
- **查哪一层（审查必改第 3 条）**：`charter_layout = 'three_layer'` 的商品查②；没迁移过的商品（M9P-01 上线时所有商品都是，M9P-05 之前根本还没有②）查**下车点所在③行里的途经加价 `waypointSurchargeMinor`**。这一行没设途经加价（`waypointSurchargeMinor` 缺键）时**跳过、不拒单**——这和真实经停点不同（真实经停点落在没设途经加价的区域里照旧不报，M9W-10）。否则所有不带经停、在加价区域下车的包车都会报不出。
- 下车点在① → 跳过；下车点不在任何②（旧表：不在任何设了途经加价的③） → **跳过、不拒**（下车点已经靠①或③匹配上了，它不是客人填的经停点，拒掉会让「东京上车 → 镰仓③下车」这类单因为镰仓没画②而报不出）。这一点和真实经停点「不在②就不报」不同，**一并请业主确认**（第十三节第 2 条）。
- 明细写「行程加价（镰仓，下车点）」：`waypoints` 里的一条，`stopSeqs` 为空数组、另记 `fromDropoff: true`。

### 明细逐项（规格步骤 4 末）

结算价明细 `areaSurcharge` 的结构**不改键名**（复审必改第 3 条）：`pickup`、`dropoff` 照旧（在①时 `areaId: null`），行程加价仍记在现有的 `waypoints: [{ areaId, amountMinor, stopSeqs }]` 里；只在条目上加可选的 `fromDropoff: true`（下车点当经停的那一条，`stopSeqs: []`）。不改名的理由：`waypoints` 现在被 `routes/quotes.ts`（对外应答）、`order-views.ts`、`order-queries.ts`、`sales-quotes.ts`、`quote.ts`、`apps/web/src/lib/order-area-price-display.ts` 直接读，渠道应答形状也会跟着变；golden 的摘要按完整输出算，改名会让所有带经停的样例都变。只加可选键，旧单、对外接口、golden 都不用改（没有下车点当经停的样例不出现这个键）。OpenAPI 只加这个可选字段。对外 `price_breakdown` 顺序：套餐、上车加价（区域名）、下车加价（区域名）、行程加价（区域名，第几个经停）、超公里费、调价、其他。

### 对现有数据 / 报价的影响（都是按规格的有意改动）

| 变化 | 例 | 归哪个任务 |
| --- | --- | --- |
| 经停区域和上 / 下车区域相同时多收行程加价 | P0 #1：+11,000（对外） | M9P-01 |
| 没有经停点、下车点在②里时多收一次行程加价 | 「东京上车 → 镰仓下车」+镰仓行程 | M9P-01（开关默认开） |
| 上 / 下车或经停在①里时不再收加价（①与③或②重叠处） | P1 #3：羽田∩横滨 3,300 → 0 | M9P-06 |
| 经停只看②：只有③没有②的区域里经停 → 不报 | 现在取③行里的途经加价，迁移后同值进②，结果不变；迁移前没填途经加价的区域本来就不报（M9W-10） | M9P-05 |

**已下的单改期、救援（审查必改第 2 条）**：改期（`order-changes.ts` 第 265 行）、救援（`rescues.ts`）都是用快照里的 `request` 加**当前规则**调 `quoteProduct`。M9P-01、M9P-06 上线后，部署前下的单改期或救援时，上下车加价、行程加价按新算法重算，价格可能变（例：P0 #1 那种行程多收行程加价 11,000；①与③重叠处上车少收）。

- **改期——推荐：按当前规则重算**（保持现行行为）。和运营改价格、改区域后旧单改期的口径一致；`order-changes.ts` 只在改日期或时间时重新报价，客人会看到新价、多退少补，不会在不知情时被多收。不为算法版本另锁旧算法：那要在引擎里长期保留两套加价逻辑、按快照版本分支，M9P-12 也清不掉。
- **救援——影响不同，要分开定**。救援时客人付的钱不变，但「救援结算价（换到原结算币种）− 原结算价」会作为救援差价记成**原供应商的应扣款**（`rescues.ts` 头注释，为负记 0）。部署前的单在新算法下加价变高时（例：P0 #1 那种行程，新算法多出 11,000 的行程加价），救援供应商按新算法报价，原结算价却是旧算法算的，这 11,000 会整笔算进差价、记在原供应商头上——这部分是算法改出来的，不是原供应商违约造成的，等于把扣款放大了。两种做法：
  - A. 接受这个影响（运营可以按现有流程认定不可抗力，但那会把违约金一起免掉）；
  - B. **（推荐）** 部署前下的单（快照里没有 `charterSelection`）救援时，差价的基准不用原结算价，改用「原供应商这一单按当前规则重算的结算价」（和救援候选同一次重算，原供应商的商品报不出时退回原结算价）。这样算法造成的加价差两边都有、互相抵掉，原供应商只为自己违约造成的差价负责；不需要保留旧算法。
- 超时费、选档仍按第四节：旧快照没有 `charterSelection` → 照旧（预收过超时费的单照旧收）。
- 列为待业主确认第 8 条（改期、救援分开问）。
- 回放比对时，旧单改期 / 救援不进询价日志，不影响第六节第 5 小节的分类；集成测试加「部署前格式的订单改期按新加价算、超时费照旧」的用例（M9P-01）。

## 三、商品匹配（规格步骤 1）

### 现状

- 前端：新预订页按上车点找城市（`apps/web/src/pages/book/new/BookNewPage.tsx` 的 `charterCityOf` → `serviceCityOf`，城市中心约 80 公里范围内最近的能订包车的城市），找不到就不询价。
- 后端：`POST /site/v1/quotes` 必须带 `city_id`；候选商品只取这个城市的（`apps/api/src/repos/quotes.ts` `loadQuoteCandidates`：`where p.city_id = $1`）；能选的套餐也按城市（`apps/api/src/repos/site.ts` `listBookableCharterPackages`）。
- 引擎（`charterEnds`）本来就允许上车点只在加价区域里（ADR 0073 M8-15）。所以 P0 #2「河口湖上车暂时没有在线报价」不是引擎拒的：河口湖离东京中心超出城市范围，前端在选城市这一步就停了。
- 现在任何一个有启用区域加价的区域都能让上 / 下车点「匹配」——包括只为经停设的。

### 新做法

1. **匹配条件**（引擎 `charterEnds`）：上车点、下车点都落在这个商品的①或③里才参与；③只认有启用的上下车加价规则的区域（`charter_area_surcharge`），②（`charter_itinerary_surcharge`）不参与匹配。经停点不影响匹配，只影响行程加价（经停点不在任何①②里 → 这个商品不报，转人工，规格步骤 1）。
2. **不再按上车城市筛**（服务层）：包车询价的 `city_id` 改为可选；不给时服务器自己找城市：
   - 新的 repo 查询 `loadCharterCityCandidates`：渠道范围（`channel.scope.cityIds`）里所有已上架的包车商品，连同①的图形和③规则的区域图形；用 domain 新函数 `charterMatches(product, pickup, dropoff)`（和 `charterEnds` 共用同一段区域判断）挑出能匹配的商品，取它们的城市（`products.city_id`）。
   - 一个城市（今天日本只有东京有包车）→ 照现有流程按这个城市询价：候选、比价、询价日志（`quote_logs.city_id` 不可空，填这个城市）、快照全不改。
   - 多个城市（今天不会出现，审查建议第 9 条，采纳）→ **只取一个城市**：请求带了 `city_id` 且在匹配到的城市里就用它；否则取上车点的 `serviceCityOf`（在匹配到的城市里时）；都没有就取匹配到的城市里编号最小的一个。同时打一条警告日志（匹配到的城市、取了哪个），不做逐城询价合并。真的出现多城市包车时再另开任务做合并（快照、下单、救援都要跟着改）。
   - 一个都没有 → `OUT_OF_SERVICE_AREA`，转人工；照 ADR 0075 第四部分记未覆盖需求（城市取上车点的 `serviceCityOf`，没有时不记，和点对点两端都不在城市时一致）。
   - 带 `city_id` 的旧请求照旧（兼容嵌入组件、旧页面），但服务器同样先按上一条找城市，`city_id` 只在匹配到多个城市时用来挑。
3. **前端**：去掉 `charterCityOf` 的「找不到城市就不询价」，包车询价不再带 `city_id`；套餐时长下拉（不按行程计价时）改调 `GET /site/v1/charter-packages?pickup=…&dropoff=…`（按匹配到的商品列套餐），旧的按城市的接口保留。
4. **多商品时同一车型取总价最低**：规格步骤 1 字面是「展示同一车型下总价最低的一个」。现有比价（`compareQuotes` → `rankCandidates`，`packages/domain/src/quote.ts` 第 1322 行）不完全是这样：同一租户只留最低；跨租户时，对外价在最低价 × (1 + δ) 以内的都进「同价区间」，区间里**评分高的优先**（δ 默认 3%，渠道最多可配 5%；观察期租户还按对外价 × 1.05 排），所以中标的不一定最便宜，客人看到的可能比最低价高最多 3%（渠道配到 5% 时最多 5%）。规格第五节「已确认正常：多商品展示最低价」是业主实测同一供应商多个商品时的结果，没有碰到区间内评分翻转，不能算业主认可了这套排序。
   - **推荐：包车的同价区间设为 0（δ = 0，严格取最低价）**——包车询价调 `rankCandidates` 时 `bandBp` 传 0，不看渠道配置；价格完全相同时仍按评分、完成单数排。接送机、点对点不变。观察期租户的 × 1.05 排序是平台对新供应商的另一条规则，推荐保留（它让观察期供应商要便宜约 5% 以上才排在前面），一并请业主确认。
   - 请业主确认（第十三节第 5 条）；业主若同意保留评分优先，改回传渠道的 δ 即可。
   - 各商品先各自选套餐再比（第四节）。
5. `/sales/v1`（渠道）：`city_id` 仍必填（不打断已接入的渠道）；匹配条件第 1 条同样生效（引擎改动）。渠道要不要也去掉城市，**另开任务**（M9P-02 的验收里不含）。

### 对现有数据 / 报价的影响

- 以前在城市范围外上车的询价（P0 #2 河口湖、镰仓站等）从「不询价」变成按东京包车报价（规格第六节第 4、5、8 条）。这类询价以前没有询价日志，回放比对看不到它们；由集成测试和测试站用例证明。
- 只为经停设的区域（只有途经加价、上下车加价是 0 的那种行）——迁移把途经加价复制进②，但③行不删、仍是启用的上下车加价规则，**迁移后仍能让上 / 下车点匹配**；要等运营删掉或停用这一行以后才不再匹配。迁移报告列出「上下车加价两格都是 0、只有途经加价」的行，请运营确认是不是只想管经停（第六节第 3 小节）。
- 接送机、点对点：不走这条路，城市规则不变。

## 四、选套餐与比价（规格步骤 2、3；配合 ADR 0091 需求二的 T）

### 现状

- 服务层先统一定时长再比价（`apps/api/src/services/site.ts` `itineraryQuotes` 第 591–618 行）：取城市能选的所有档，先「能覆盖行驶 + 停留」的从短到长、再覆盖不了的从长到短，**逐档**调 `siteQuotes`，每个车型组取第一个报得出的档。结果：
  - 一档里只有含这一档的商品参加比价（P1 #5：特殊商品只有 8 / 10 / 12h，5h48m 被定为 6h，特殊商品不参与）；
  - 只按时长选（P1 #6：132 km 选 4h + 超公里 47,259，5h 只要 46,200）；
  - 超过最长档时最长档 + 超时费；
  - 每一档写一条询价日志、生成一批快照。
- 引擎在 `request.routeUsage` 给了时按 `basePrice` 的包车公式算超公里**和超时**（ADR 0089）。
- ADR 0091 第三稿（未合并）加了 T 和 `packageCheck`，仍是服务层逐档；这个做法被本节取代（0091 第四稿已收窄）。

### 新做法

1. **T**（规格步骤 2）：T 的定义和三项配置 `service_rules.charterItinerary { stopOccupancyMinutes, bufferMinutes, minPackageHours }` 以 ADR 0091 第四稿第一、二节为准；实现直接用 M9W-11 分支（`origin/m9w-11-package-buffer`）的 `itineraryEstimate` 和服务规则读写。D = 全程米数。默认值 0 / 0 / 不限（行为不变），建议值由业主在后台填。
2. **候选**（审查建议第 7 条，采纳）：这个商品这个车型组可用的套餐（启用、在生效期）里，**时长 ≥ T（且 ≥ 最低套餐）**、并且**这一档能报出**的全部——「能报出」指这一档的套餐价和这一单要用到的上下车加价、行程加价规则都齐全（加价规则按套餐细分时，缺这一档的格就不算候选）。一档都没有时**只有最长那一档**（不收超时费）；最长那一档也报不出 → 这个商品这个车型组不报（不退到更短的档）。
3. **取最低**：每个候选算 `套餐价 + max(0, D − 含公里) × 超公里单价`，取最小；一样时取短的。上下车加价、行程加价、调价（包括按套餐细分的调价规则，`quote.ts` 第 949 行）**不参与选择**（旧需求文档第四节「区域加价和经停加价不影响选择」，规格步骤 3 字面也只算这两项）。所以选出来的档不一定让总价最低——加价、调价按套餐细分时可能有别的档总价更低；这和规格字面一致，请业主确认（第十三节第 9 条）。
4. **超时费下单时不收**（规格第一节、PR #221 决定 2）：按 ADR 0091 第四稿第三节——带 `charterSelection` 的报价结算价明细 `itinerary.overtimeMinor = 0`、另记 `overtimeAtBooking: false`；对外 `price_breakdown` 的 `overtime` 项**只在超时费大于 0 时才写**（旧单订单页照旧显示，新报价没有这一项）；新订单的供应商 / 运营订单详情写「预计超出 X 分钟，未预收，服务后按实际提交」；平台试算同样不含超时费。超时由供应商服务后提交（现有事后加收流程，基准另定）。0091 第三稿的「按 T 补收」作废。
5. **在引擎里按商品选**（`quoteProduct`）：`QuoteRequest` 加可选 `charterSelection: "auto" | "manual" | "locked"`——**进快照、进询价日志**（它决定价格，回放要能重现）；`auto` 时 `packageHours: null`、给 `routeUsage`。引擎对每个商品每个车型组按上面 2、3 选档，`VehicleOffer.packageHours` 记选中的档（这个字段现在就有）。没有 `charterSelection` 的请求（部署前下的单改期、救援，旧日志回放，golden）**在选档和超时费上**和现在逐字一样——包括按行程计价旧单的超时费；但加价按第二节的新算法算（M9P-01、M9P-06 的改动对它们同样生效，第二节「已下的单改期、救援」、第六节第 4 小节）。
6. **`packageHours: null` 会碰到的现有代码**（审查建议第 11 条）：请求校验 `quote.ts` 第 136 行（包车必须带 `packageHours`）——`charterSelection: "auto"` 时允许为空；加价查找 `quote.ts` 第 848 行、调价时刻 `quote.ts` 第 949 行、套餐价查找 `pricing.ts` 第 480 行都直接用 `request.packageHours`——统一改为「按候选档 H 代入」（引擎对每个候选 H 用一份 `packageHours = H` 的请求副本算这一档）；`ComparisonGroup.packageHours`、`replay-digest.ts` 里读 `request.packageHours` 的地方改读 `offer.packageHours`。实现 PR 用 `grep packageHours` 逐处核对并在 PR 描述列出。
7. **客人手动升套餐**：`itinerary_pricing: true` 时允许带 `package_hours`（以前 400 `NOT_APPLICABLE`；放宽不影响任何现有请求）；引擎收到 `charterSelection: "manual"` + `packageHours = H`：H × 60 ≥ T 且 H ≥ 最低套餐、或 H 是这个商品这个车型组最长的档 → 按 H 报（不收超时）；否则这个商品这个车型组不报，原因 `PACKAGE_TOO_SHORT`（档 < 最低套餐时 `BELOW_MIN_PACKAGE`）。不能短于 T。
   - **对外口径**（`sales-quotes.ts` 的对外原因映射，不能落到 `NOT_AVAILABLE`）：`BELOW_MIN_PACKAGE`、`PACKAGE_TOO_SHORT` 对外都报 `PACKAGE_TOO_SHORT`，`unavailable` 里多给 `min_package_hours`（这个车型组里各商品能接受的最短档的最小值）。`/site/v1` 和 `/sales/v1`（渠道选了低于最低套餐的时长）同一个原因码和字段；只因这两个原因报不出时不记「未覆盖需求」（客人选短了，不是缺供应商）；OpenAPI 同步。
   - 页面（M9P-04）：带经停点时套餐下拉默认「自动（N 小时）」，只列 ≥ `auto_package_hours` 的档；不带经停点选了低于最低套餐的档，车型卡显示「这个车型最短 X 小时」和「改选 X 小时」。
8. **比价**：同一车型组里各商品各自选了档、各自算出总价，再按 `rankCandidates` 比（包车同价区间按第三节第 4 条）。`ComparisonGroup.packageHours`（现在 = `request.packageHours`）在 `auto` 时为 `null`，每个候选的档看 `offer.packageHours`；中标的档写进快照的 `winner.offer.packageHours` 和订单 `package_hours`（`orders.ts` 第 311 行本来就取 `winner.offer.packageHours`）。
9. **服务层**：`itineraryQuotes` 去掉逐档循环，改为**一次** `siteQuotes`（`charterSelection: "auto"`）；应答每个报价给 `estimated_minutes`（中标商品的 T）、`includes_buffer`、`auto_package_hours`（= 中标档；手动升档时给自动选出来的档）。「未覆盖需求」、报不出原因自然只有一次（0091 第三稿那两项「延后记 / 合并」的有意改动不再需要，因为只询一次）。
10. **超过 13 小时不能在线下单**（审查必改第 6 条，从 M9P-10 挪进 M9P-03）：T 超过商品的「在线下单上限」（商品级，`service_rules.charterItinerary.maxOnlineMinutes`，默认 780 分钟 = 13 小时，不存键 = 默认）时，这个商品这个车型组不报，原因 `ITINERARY_TOO_LONG`，对外同名，页面提示「行程较长，请联系客服定制」并给人工报价入口（记未覆盖需求）。和取消超时费同一个 PR 上线，否则从 M9P-03 上线到 M9P-10 之间，20 小时的行程会按 12 小时套餐价、不收超时费在线成交。M9P-10 只做「12 小时 / 360 公里提醒、可继续下单」和经停数上限。13 小时和「阈值商品级」直接来自规格步骤 5（「T>13h 不允许在线下单；阈值商品级」），不再问业主；和去超时费同一个 PR 上线是内部排期，写在给业主的说明里。
11. **改期、救援**：从订单拿 `package_hours` 和快照 `request`。新口径下的单（快照带 `charterSelection`）传 `charterSelection: "locked"`（引擎：按给定的 H 报、不判 T、不判最低套餐和 13 小时、不收超时费）；`rescues.ts` 第 399 行、`order-changes.ts` 第 266 行按 `packageHours` 找报价的逻辑不变（H 已固定）。**救援不直接调 `quoteProduct`**：`rescueCandidates` 调的是 `previewPlatformQuote`、逐个字段重拼入参，所以按 ADR 0091 第四稿第三节第 1 小节：`PlatformQuoteInput` 加可选 `charterSelection`，原样传给引擎、函数内部不设默认值；快照里有 `charterSelection` 时传 `locked` + `packageHours: order.packageHours`，没有时不传。部署前下的按行程计价单快照里没有 `charterSelection`，选档和超时费照旧（逐字不变；预收过超时费的单照旧收），加价按当前规则重算（第二节）。
12. 不带经停点、客人自选时长的包车：不变（客人选 H，引擎不选档），只受最低套餐限制（0091 第五节第 6 条推荐「这次不改」，沿用）。

### 对询价日志、快照、回放（ADR 0086）的影响

- **询价日志**：按行程计价每次询价从「N 档 N 条」变成 1 条；`request` 多 `charter_selection`、没有 `package_hours`。`bids[].package_hours` 照旧记中标档。
- **快照**：`request.charterSelection`、`request.packageHours: null`；`winner.offer.packageHours` 是选中的档；`candidates` 里每个候选多记它自己的档（排序依据要能复算）。
- **回放**：`replay-digest.ts` 的 `offerParts` 不改（它本来就逐车型组记套餐、金额、规则编号）。新口径日志带 `charter_selection`，回放据此重现选档；旧日志不带，回放按旧口径选档、算超时费（这两项逐字不变），加价按第二节新算法（第六节第 5 小节第 1、2、9、10 类）。
- **平台报价试算**：现在的试算路由（`routes/quotes.ts` 的 `previewInput`）不收经停点、路线用量，不能按行程计价，所以现在不传 `charterSelection`。以后试算路由开放按行程计价时，由**试算路由**传 `auto`（新口径，不含超时费，结果旁注明选了哪一档、T 是多少）。`previewPlatformQuote` / `PlatformQuoteInput` 里不设默认值——救援也走这个函数，靠默认值会把部署前的单救援当成新询价（不收超时费、重新选档、按订单的档找不到候选），见第 11 条和 ADR 0091 第三节第 1 小节。

## 五、套餐价改为「车型组 × 套餐」一次填写

### 现状

套餐价规则 `charter_package` 按「服务区域 × 车型组 × 套餐」存（`price_rules.area_id not null`，迁移 0014）。引擎对上车点所在的服务区域取价（上车点只在加价区域时用下车点的，两端都不在时每个区域都算取最低，ADR 0073 M8-15）。P1 #7：服务区域没填套餐价 → 上车报不出、经停收 0。

### 新做法

- `price_rules.area_id` 对 `charter_package` 允许为空：**空 = 整个商品的套餐价**（规格「处处是东京市内价」）。迁移只放宽约束（加检查约束：`area_id is not null or pricing_model = 'charter_package'`），不改已有行。
- 引擎按商品切换（第一节「新旧表按商品迁移过没有切换」）：`charter_layout = 'three_layer'` 的商品**只用整商品套餐价**（`area_id is null`），不再按区域取价；没迁移过的商品走旧逻辑（套餐价这一项逐字不变）。
- 冲突键：整商品套餐价按「车型组 × 套餐 × 生效日期」查重。上架检查「该有价格的组合」对迁移过的包车商品改为「每个车型组至少一档」，不再按服务区域查（P1 #7「上架拦下」）。
- **迁移**（第六节）：每个包车商品取一个「基础价来源区域」的套餐价复制成整商品套餐价——东京包车取「东京市内」服务区域；通用规则：取商品服务区域里排第一的（`product_areas` 的优先级），迁移报告写明取的是哪个区域，运营可以改。**其他服务区域与它不一致的组合逐条列进迁移报告**（区域、车型组、套餐、两边金额、含公里、超时 / 超公里单价）。
- **旧的按区域套餐价保留、只读**：迁移过的商品，后台价格页只显示「整商品套餐价」可编辑，旧行折叠在「旧的按区域套餐价（只读，迁移前的数据）」下面，导入导出只认新格式（旧模板导入给出明确提示）；**没迁移过的商品（正式站部署后全部是）价格页、导入导出照旧显示和接受旧表**，不受影响。验证通过后另开 M9P-12 清理。

### 对现有数据 / 报价的影响

- 迁移执行（只在测试站）之后：服务区域之间价格不一致的商品，原来在「非来源区域」上车的报价会变成来源区域的价。全部列入迁移报告；这是规格「套餐价整单只算一次（东京市内价）」的有意改动。
- 迁移前：无变化。

## 七、后台校验（规格第四节）

### 现状

- 价格页保存区域加价：区域不能是商品本身的服务区域（`apps/api/src/services/prices.ts` 第 365 行 `AREA_IS_PRODUCT_AREA`），批量保存时整批被拒，页面一直显示「有 N 条未保存」（业主报的 Bug，M8-46）。PR #219 / ADR 0092 的做法是放开这条。
- 区域重叠：只有区域页的软提醒（`packages/domain/src/area-overlap.ts` `findAreaOverlaps`、`findPricingOutsideOperating`）；同层重叠时报价取最高。
- 没有上架覆盖检查、没有空格提示。

### 新做法（保存和上架都在后端校验，前端在保存前就提示）

1. **同商品同层不重叠**（①①、②②、③③）：保存服务区域、②规则、③规则时，用 `findAreaOverlaps` 算这个商品同一层所有区域两两的重叠；有重叠 → 400 `AREA_LAYER_OVERLAP`，`details` 给两个区域名和重叠面积（km²，一位小数）。只有边界接触（面积 < 0.01 km²）不算。
2. **①与③不重叠**（几何）：同上，`AREA_BASE_SURCHARGE_OVERLAP`。①②、②③可以重叠。
3. **同一区域不能既是①又是③**：保留 `AREA_IS_PRODUCT_AREA`（ADR 0092 不采纳），文案改为「这个区域是商品的基础价区域（服务区域），在这里上下车不加价，不能再设上下车加价。」。**#219 的处理**：不放开；改为前端在保存前拦——区域下拉里服务区域灰掉并写「基础价区域，不能设上下车加价」；已经存在的「①上的③」行在表里标红、写同样的话、提供「删除这一行」按钮，**不计入「未保存」**；批量保存时这些行不提交，其余行照常保存，不再整批卡住。设②时服务区域可以选（①②可以重叠）。#219 里「保存卡在有 N 条未保存」的前端修复（计数、错误展示）可以复用，`AREA_IS_PRODUCT_AREA` 删除那部分撤回。
4. **上架覆盖检查**：「城市热门景点坐标清单」复用平台主数据 `places`（`type = 'poi'`，已挂城市、有坐标、运营后台维护），加一列 `charter_coverage boolean not null default false`（迁移，只加列）；运营在运营后台地点页勾选哪些地标进清单。**不预置任何数据**（规则 1），清单由运营在后台填。包车商品上架检查（`publish_check`）新增一项 `charter_coverage`：列出商品所在城市清单里不在这个商品任何①②③的地标——**提醒、不拦上架**（规格写「列出」）。清单为空时这一项不出现。
5. **加价表空格提示**：②③表里每个区域行，某车型组没填的格显示「空 = 不报价」的灰底提示；表头汇总「N 格没填」；上架检查同样列出（提醒）。
6. 重叠校验只对新保存生效；已有的重叠数据在迁移报告里列出（第六节第 3 小节），由运营处理，校验不回头锁死已有数据（否则运营改别的价格也存不了）。

### 后续（不在本篇实施范围，立任务 M9P-13）

区域编辑器建议：「从本区域减去另一个区域」切掉重叠；「在地图上看全部」按商品和层筛选、标红重叠；区域详情显示它在哪些商品里当①/②/③。

### 对现有数据的影响

不改数据。测试站「东京包车」若有①上的③、重叠区域，迁移报告列出，运营处理前报价按第二节①优先算（①上的③不起作用）。

## 十、验收方法

1. 部署后在测试站（`/book/new`，包车，东京包车商品，经济 7 座）逐条跑规格第六节 15 个用例；前台价 = 结算价 × 1.1。
2. **测试站现有金额与规格表不同**（例：今天实测镰仓前台 9,900，即结算 9,000；规格表镰仓 8,000 × 1.1 = 8,800）：期望值按测试站当时的实际配置（套餐价、②③金额）用规格公式算，验证的是公式；验收报告另列「与规格表的金额差异」表交运营（区域、车型组、规格表金额、测试站金额），**不改运营数据**。
3. 第 2–6 条实际按预计用时自动选套餐，验收时可手动升到 10h 核对（规格原话）。
4. 第 14、15 条在测试供应商（ADR 0077）的商品上做，不动业主真实商品。
5. 截图、询价应答（结算价明细）写进验收报告 `docs/acceptance/M9P-11.md`。

## 十三、待业主确认（未答复按推荐做，不停工）

| # | 问题 | 推荐 |
| --- | --- | --- |
| 1 | 没有经停点的单，是否把下车点所在的行程区域当作一个经停计入行程加价 | **是**，商品级开关、默认开启（规格的建议；否则客人不填经停就能少付） |
| 2 | 上一条里，下车点不在任何行程区域时（迁移前：下车点所在的上下车加价区域没设途经加价时） | **跳过、照常报价**（下车点已经靠基础价区域或上下车加价区域匹配上了；真实经停点不在行程区域才转人工） |
| 3 | 行程加价、上下车加价按车型组填一次，还是还要按套餐细分 | **按车型组填一次；保留「可按套餐细分」**（迁移把现有按套餐的值原样搬过去，不丢数据；以后新填的按车型组） |
| 4 | 套餐价统一取哪个服务区域的价 | **东京包车取「东京市内」**；其他商品取排第一的服务区域；不一致的逐条列给运营 |
| 5 | 规格写「展示同一车型下总价最低的一个」。平台现有排序在价差 3% 以内（渠道最多可配 5%）会优先评分高的供应商，所以中标的不一定最便宜，客人看到的可能比最低价高最多 3%（或 5%）。包车是否按规格严格取最低 | **严格取最低：包车的同价区间设为 0**（价格完全相同时才看评分）；接送机、点对点不变。观察期新供应商排序时按价格 × 1.05 的规则保留。业主若希望保留「价差 3% 内评分高的优先」，改回即可（第三节第 4 条） |
| 6 | 热门景点清单由谁维护 | **运营**在运营后台地点页勾选，不预置 |
| 7 | 渠道接口 `/sales/v1` 是否也去掉按城市选商品 | **这次不改**（不打断渠道），另开任务 |
| 8 | 部署前已下的单，**改期**和**救援**时上下车加价、行程加价按新规则（经停不被上下车抵消、基础价区域优先）重算。改期：客人看到新价、多退少补。救援：客人付的钱不变，但「救援结算价 − 原结算价」记成原供应商的应扣款，新规则多出的加价（例如 P0 #1 那种 11,000）会整笔算进原供应商的扣款 | **改期：按新规则重算**（保持现行行为，和运营改价后的改期一致）。**救援：推荐 B**——部署前的单救援时，差价基准改用「原供应商这一单按当前规则重算的结算价」，算法造成的加价差不算原供应商的；A 是接受这个影响。超时费、套餐时长两种情况都照旧（预收过超时费的单照旧收）（第二节） |
| 9 | 选套餐只比「套餐价 + 超公里费」（规格步骤 3 字面），不看加价、调价。加价或调价按套餐细分时，选出的档总价不一定最低 | **按规格字面**（只比这两项）；业主若希望按含加价、调价的总价最低选，需要另外说明 |

**给业主的说明（不需要决定）**：
- 超过 13 小时的行程不能在线下单（转客服），阈值商品级——这是规格步骤 5 的原话，照做，不再问；它和「下单不收超时费」放在同一次上线（M9P-03），否则中间会有一段时间 20 小时的行程按 12 小时套餐价、不收超时费在线成交。
- 规格「报价含高速费、停车费，服务后不再另收」已经由 ADR 0070 做了（2026-11-10 起下的包车单不能再加收高速费、停车费），这次不用改。
