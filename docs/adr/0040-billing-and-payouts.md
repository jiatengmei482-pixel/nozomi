# ADR 0040：供应商应付账单与付款批次——按月出账、供应商确认 / 异议、付款双人复核、次月 20 日付款批次

- 状态：已采纳（2026-10-26，M5-01）
- 补充 ADR 0023：双人复核登记一类 `statement.payout`（付款给租户）；`ApprovalKind` 加可选的 `unscopedOnly`（限定了数据范围的人看不到、审不了）。
- 补充 ADR 0030：菜单表加「财务结算」（查看 `statement.read`、编辑 `statement.manage`、审核 `statement.review`）；财务结算的接口一律不对限定了数据范围的人开放。
- 补充 ADR 0031：应扣款项（违约金、救援差价）在这里出账；「已扣」不另加状态，看它是否挂在一张有效账单的明细上（`statement_lines.source_key = deduction:<编号>`）。
- 编号说明：ADR 0040（0033–0039 可能被别的分支使用）；迁移 0070（0050–0069 留给别的分支）。

## 背景

需求：《平台运营端与渠道对接》「财务结算」（只有「已完成」「no-show 已审核」「有偿取消」的订单进入账单；服务日期在周期内且已结案；未结案的结案后在下一期补发；
租户应付账单：生成 → 租户确认（可提异议）→ 双人复核 → 付款；月结，次月 20 日付上月已结案订单；生成付款批次 → 双人复核 → 银行转账）、「一单的账务分录」、「敏感操作双人复核：付款给租户」；
《用车报价服务平台》「13. 对账结算」（按月生成账单：结算价、取消费、附加费用、no-show，租户确认后开票）；第三轮决策（月结、次月 20 日付款）、第五轮决策（租户退出：最后一期延后一个周期付款）。
roadmap 验收标准：次月 20 日付款批次。

### 出账口径

| 明细 | 金额（结算币种，应付给供应商的方向） | 什么时候出 |
| --- | --- | --- |
| `order` 已完成 | + 结算价 | 订单 `completed` |
| `no_show` 客人未出现 | + 结算价（全额） | 订单 `no_show`（审核通过）；`no_show_claimed` 还没结案 |
| `cancellation` 有偿取消 | + 供应商应得（结算价 × 扣款比例，ADR 0029 取消时已算好） | 订单 `cancelled` 且应得 > 0 |
| `extra_charge` 事后加收 | + 审核通过的金额（没审过是报的金额） | 加收 `charged`（已从客人那里扣到款）；异议期内、待审核、正在扣、扣款失败的还没结案 |
| `deduction` 违约金、救援差价 | − 金额 | 待扣、金额 > 0，订单在这家供应商那里已到终态（救援有了结论：原供应商那一行 `rescued` / `cancelled`） |
| `deduction_waiver` 免除退回 | + 金额 | 已经出过账的应扣款项之后被认定不可抗力 |
| `carry_forward` 上期结转 | − 上期合计 | 上期合计为负、复核后转入下期 |

- **切月按订单的服务日期**（`orders.service_date`，下单时按城市时区算好的当地日期）。需求写的是「服务日期在周期内」，没说按哪个时区：按城市当地日期最符合「服务日期」的字面意思，跨时区的城市各按各的（**待负责人确认**）。
- **「今天」、该出哪一期、付款日按东京日期**（`BILLING_RULES.timeZone`，和供应商每日检查同一个）：东京时间每月 1 日起出上个月的账。比东京晚的时区（如欧美城市）最后一天的单出账时可能还没结束，它们自然落到下一期（往期调整），不会漏也不会重。
- **来源键保证只出一次**：每笔应付一个来源键（`order:<编号>`、`extra_charge:<编号>`、`deduction:<编号>`、`deduction_waiver:<编号>`、`carry:<账单编号>`），唯一索引 `statement_lines_source_key`（一个供应商里，作废的不算）。出账时只取还没挂在有效账单上的；同一期同一币种只有一张有效账单（`statements_current_key`）。
  - 所以：出账可以反复运行；某一期出账后才结案的（加收扣到款、订单完成、违约金有了结论），进之后一期，明细标 `prior_period`（往期调整）——就是需求「账单生成后订单再有调整的进入下一期」「结案后在下一期补发」。
  - 同一家供应商的出账用 `pg_advisory_xact_lock` 排队（定时任务、手动出账、作废重出、几个实例同时到）；集成测试有并发两次只出一张。
- **币种**：一张账单一种币种。订单的结算价本来就是供应商的结算币种（商品子品牌的币种），**按原币出账、不换汇**；一家供应商有两种币种的商品就出两张。合同里的结算币种（ADR 0028）和商品币种不同时怎么办需求没写，现在按订单原币出（**待负责人确认**：是否要按快照汇率换成合同币种）。
- 钱只做整数加减（`sumMinor`，超出安全整数抛错），不取整、不换汇。

### 违约金免除与作废重出：扣一次、退一次（2026-10-26，M5-01 测试发现的缺陷）

问题：9 月扣了违约金，之后认定不可抗力，10 月出了一行「扣款免除」退回；再作废重出 9 月时，违约金已是「已免除」，重出的 9 月不再扣，10 月的退回却还在——供应商多拿一笔。

决定：
- 一笔应扣款项的扣款行和退回行成对出现：**有效的退回行必须有有效的扣款行**。
- 重出时，已免除的应扣款项如果在别的有效账单上已有退回行，重出的账单**照旧扣它**（`deductionBillable`：已免除、扣款行不在有效账单上、退回行在 → 扣），净额为 0。
- 反过来，作废含退回行的账单后重出：退回按来源键唯一（`statement_lines_source_key`），只要扣款行还在有效账单上，就只再退一次；扣款行也不在了，就既不扣也不退。
- 每次出账、作废重出结束前，在同一个事务里（同一家供应商排着队）核对这条不变式（`repos/billing.ts` 的 `unpairedWaivers`），不满足就整个回滚（409 `STATEMENT_LINES_INCONSISTENT`）。跨行的条件写成数据库约束要用触发器扫同一张表，和作废、新增在同一事务里的先后有关，所以放在事务末尾核对。

### 状态

`issued` 待确认 → `confirmed`（供应商确认，或 7 天确认期满系统视为确认）/ `disputed`（供应商提异议，原因必填）→ 平台答复回到 `issued`（重新给 7 天）→ 确认 → 财务发起付款复核 → 另一位财务批准：
合计 > 0 → `in_payout`（进付款批次）→ `paid`（M5-02）；= 0 → `settled`（无需付款）；< 0 → `carried`（转入下期）。待确认、有异议、待复核的可以 `void`（作废）。

- **作废并重出**：账单和明细一起作废（明细只能改「作废时间」，数据库触发器把关），同一个事务里按现在的数据重出这一期这家供应商的账单。账目有误的处理顺序：先在源头改（审核加收、更正订单），再作废重出。有待审核的付款复核时不能作废（409 `STATEMENT_REVIEW_PENDING`）。
- 手工调账（需求 `POST /adjustments`、「手工调账必须绑定工单」）不在本期：等工单（M4-02）合并后加一种明细。
- **确认期截止那一刻（含）起账单已视为确认**，不等定时任务（每小时一轮）：供应商这时提异议，同一个事务里先记为系统确认，再返回 409 `STATEMENT_CONFIRM_PERIOD_OVER`；确认接口照常成功（记为供应商确认）。（M5-01 测试发现的缺陷）
- **确认期 7 天**（`BILLING_RULES.confirmDays`，**待负责人确认**）：需求只写「租户确认（可提异议）」，没有说不确认怎么办。不设期限的话一家不点确认就永远付不了款；7 天让 1 日出的账在 8 日前确认，留出复核到 20 日付款的时间。有异议的不自动确认。
- 每一步写账单的经过（`statement_events`，供应商看得到，不含平台员工编号）和审计日志。

### 付款：双人复核和付款批次

- 复核放在**每张账单**上（`statement.payout`，「付款给租户」）：财务（`statement.manage`）发起，另一位有 `statement.review` 的财务批准（发起人不能批，机制本身保证）；批准时核对账单版本，变过 → `APPROVAL_STALE`。
- **付款批次**（`payout_batches`，平台表）：一个付款日一个批次。批准时从账单的应付日（周期的下一个月的合同付款日，默认 20 日）起，取第一个不早于今天、批次还开着的付款日；过了或那天的批次已锁定就顺延到下个月同一天。批次里多张账单、多种币种，合计按币种分开。
- 批次状态：`open` 收账单 → `closed` 财务锁定（之后批准的进下个月）→ `paid`（M5-02）。需求「生成付款批次 → 双人复核 → 银行转账」：复核在每张账单上做过了，锁定批次单人即可；如果负责人要求批次本身再复核一次，加一类复核即可（**待负责人确认**）。
- **已清退的供应商**最后一期的应付日延后一个月（第五轮决策），按出账时供应商的状态判断。
- 合计为负（违约金多于应付）：不付款，转入下一期，下一次这家供应商有新应付时带一行「上期结转」一起出；只有结转、没有新应付的不单独出账单。已清退的供应商的负数余额不会自动消失，由财务线下追讨（**待负责人确认**）。

### 权限

| 操作 | 谁有 |
| --- | --- |
| 平台 `statement.read`（看账单、批次） | 超级管理员、财务、只读 |
| 平台 `statement.manage`（手动出账、答复、作废重出、发起付款复核、锁定批次） | 超级管理员、财务 |
| 平台 `statement.review`（审核付款） | 超级管理员、财务（两位财务互审） |
| 租户 `statement.read` | 管理员、财务、只读 |
| 租户 `statement.confirm`（确认、提异议） | 管理员、财务 |

数据范围：一张账单含一家供应商在各城市、各渠道的订单，切不开——限定了任一维度的员工调用财务结算接口一律 403 `DATA_SCOPE_DENIED`，付款复核在待审核队列里也看不到（`unscopedOnly`）。

### 规则 2、规则 4

- 供应商接口的租户编号只来自令牌；列表、详情在租户事务里读（行级安全），确认、提异议在平台事务里按「令牌里的租户 + 编号」找，别的供应商的 404。三张租户表供应商只有 `select`。
- 明细里只有结算价一侧的数（结算价、供应商应得、加收报的 / 通过的金额、应扣款项和依据），没有对外价、加价比例、汇率；集成测试逐层扫描字段名。

### 接口（openapi 已同步，标签「财务结算」）

- 供应商：`GET /tenant/v1/statements`、`GET /tenant/v1/statements/{id}`、`POST …/{id}/confirm`、`POST …/{id}/dispute`。
- 运营后台：`GET /platform/v1/statements`、`POST /platform/v1/statements/generate`、`GET …/{id}`、`POST …/{id}/reply`、`POST …/{id}/void`、`POST …/{id}/payout-approval`（202，批准走 `/platform/v1/approvals/{id}/approve`）；
  `GET /platform/v1/payout-batches`、`GET …/{id}`、`POST …/{id}/close`。
- 需求写的 `:issue`、`:confirm`、`/payouts/{id}:approve`：本项目接口一律用斜杠；出账即发给供应商（没有草稿），付款复核走通用的复核接口。

### 定时任务

`BillingJobs`（和订单、供应商的定时任务一样跑在 API 进程里）：启动后 15 秒第一次，之后每小时一轮——给上个月（东京日期）出账（出过的不重复）；确认期满的视为确认。

## 待负责人确认（先按推荐做了）

| # | 问题 | 选的方案 | 理由 |
| --- | --- | --- | --- |
| 1 | 按哪个时区的日期切月 | 订单的服务日期（城市当地日期）；出账时机和付款日按东京日期 | 需求「服务日期在周期内」；城市当地日期就是客人和司机认的那一天 |
| 2 | 供应商不确认怎么办 | 出账（或答复异议）起 7 天视为确认；有异议的不自动确认 | 不设期限会卡住付款；7 天来得及 20 日付款 |
| 3 | 合同结算币种和商品币种不同 | 按订单原币出账，一种币种一张，不换汇 | 订单的结算价就是供应商报的币种，换汇会让供应商承担汇差 |
| 4 | 付款批次要不要再复核一次 | 复核在每张账单上做；锁定批次单人 | 需求的复核对象是「付款给租户」，每张账单批准一次就是每笔付款批准一次 |
| 5 | 合计为负 | 转入下一期，和新应付一起出；已清退的由财务线下追讨 | 需求没写；平台不向供应商收钱（第三轮决策：不收费），只能从以后的应付里扣 |
| 6 | 0 元的违约金 | 不出账（供应商「违约金与扣款」页里看得到） | 没有金额的行只增加对账负担 |
