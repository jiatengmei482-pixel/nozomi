# ADR 0016：商品——子品牌、基础信息、服务规则、商品详情、上架校验

- 状态：已采纳（2026-10-08，M1-03）
- 补上 ADR 0012、ADR 0015 留下的两处检查：平台主数据被已上架的商品用着时不能停用；区域被已上架的商品用着时不能删除、不能停用。

## 背景

M1-03 做商品的「① 基础信息、② 服务规则、⑤ 商品详情」和上架校验、上下架。价格规则（③，M1-04）、库存（④，M1-05）是后续任务。需求见《用车报价服务平台》「2. 商品」「3. 服务规则」「6. 上架」；页面规范见 `docs/design/pages/tenant-products.md`。下面是落地时定下的事，其中和需求文档写法不同的地方已由负责人（经协调人）接受。

## 决定

### 表

迁移 `0013_products.sql`，五张表都带 `tenant_id`、开行级安全、授权给租户角色 `nozomi_app`：

| 表 | 内容 |
| --- | --- |
| `brands` | 子品牌：名称（同一个供应商下不重名，不分大小写）、结算币种、状态、版本号 |
| `products` | 商品：编号、子品牌、城市、品类、接送点、状态、`service_rules`（jsonb）、`content`（jsonb）、版本号、最近上架时间 |
| `product_areas` | 商品选的区域和优先级；区域被删除时跟着删 |
| `product_vehicle_groups` | 商品选的车型组和「人数 / 行李数」组合 |
| `product_dispatchers` | 调度人（姓名、电话） |

- 子表的外键都带着 `tenant_id`（`(tenant_id, product_id)`、`(tenant_id, area_id)`）：即使绕过接口，也没法把别的供应商的区域接到自己的商品上。
- 商品编号 `PRD` + 创建时间（UTC 年月日时分秒）+ 至少 4 位流水号，流水号来自全平台一个序列 `product_code_seq`，编号全平台唯一。
- 平台角色 `nozomi_platform` 对 `products`、`product_vehicle_groups` 只有 SELECT（两条只读策略）：停用城市、地点、车型组、附加服务前要数「有几个已上架的商品在用」。其余三张表平台角色碰不到。平台看到的只是个数，接口不返回任何商品内容。
- 服务规则和商品详情做成 `products` 上的 jsonb 列，而不是拆成多张表：它们总是整体读、整体存，和商品共用一个版本号；报价引擎（M1-06）读一个商品就拿到全部规则。金额在 jsonb 里也是最小货币单位整数。

### 状态：三个

`draft`（草稿）→ `published`（已上架）⇄ `unpublished`（已下架）。需求文档写的是四个（草稿 → 未上架 → 已上架 → 已下架），但没有写草稿什么时候变成未上架；这里把「未上架」并进草稿：没上过架的都是草稿，上过架又停卖的是已下架。「配好了没有」看上架校验，列表项另带概况 `check`。

- 只有草稿可以删除（需求文档）。上过架的只能下架。
- 草稿不能下架（409 `PRODUCT_STATE_INVALID`）；已上架再上架、已下架再下架原样返回。

### 子品牌由供应商的管理员自己建

需求文档只写了「商品挂在子品牌下、子品牌决定币种」和 `GET /brands`，没写谁来建。这里是供应商的管理员自己建（权限 `brand.manage`，只有管理员有）：名称 + 结算币种。币种创建后不能改（409 `FIELD_LOCKED`）——它下面商品的所有金额都按这个币种的最小货币单位存。可以改名。本期没有停用子品牌的接口（`status` 列留着，永远是 `active`）。子品牌的 `rounding_unit`（取整单位）属于价格规则，M1-04 再加。

### 创建后不能改的四项

子品牌、城市、品类、接送点在新增时就要给全、之后不能改（PATCH 带了不同的值 → 409 `FIELD_LOCKED`）。它们决定了币种、时区、可选的区域和附加服务、免等的最低值，改了等于换一个商品。接送机商品必须有一个本城市的机场或车站；包车、点对点不能有接送点。

新增时引用的东西有问题，分两类：

- 写错了（不存在、别的供应商的、不在这个城市、类型不对）：400 `VALIDATION_FAILED`，每条带路径和原因代码。别的供应商的子品牌、区域和不存在的一模一样（`UNKNOWN_BRAND`、`UNKNOWN_AREA`）。
- 存在但已被平台停用（城市、接送点）：409 `MASTER_DATA_NOT_READY`，`details.reason` 是 `CITY_DISABLED` / `PICKUP_PLACE_DISABLED`。和新增区域（ADR 0015）一致：请求本身没写错，是主数据的状态不允许。两类同时有时先报 400。
- 例外：新选的区域、车型组已停用仍是 400（`AREA_DISABLED`、`VEHICLE_GROUP_DISABLED`）。它们是清单里的某一条，页面要靠路径（`/areas/2/area_id`）指到那一行；409 的 `details.reason` 指不到行。

### 分步保存，一个版本号

- 新增只要求上面四项，区域、车型组、调度人可以一起给也可以之后给。
- `PATCH /products/{id}` 保存区域（数组顺序 = 优先级）、车型组、调度人：带了的整体替换，没带的不动。
- `PUT …/service-rules`、`PUT …/content` 各自整体保存，可以只填一部分。
- 保存草稿、已下架的商品时只查「填了的写得对不对」，缺什么留到上架校验。
- 商品只有一个版本号：任何一部分变了都加一，所有修改接口用同一个 `If-Match`，应答里都带新的版本号。提交的内容和现有的一样时不加版本、不写日志。
- 已经选着的区域、车型组后来被停用，保存时不拒绝（上架校验会指出来）；新选的必须是启用中的。

### 区域、车型组、调度人

- 区域只能选本供应商、商品所在城市、业务类型和品类相同或「通用」的。一个商品最多 50 个区域、30 个车型组、10 个调度人。
- 优先级现在只是保存下来的显示顺序。已确认的决策是「一个位置落在多个区域时每个都算价、取最低」，顺序不影响价格。
- 车型组选的「人数 / 行李数」必须是平台给这个车型组定的可选组合之一；平台之后改了组合，上架校验会指出来（`VEHICLE_COMBO_NOT_OFFERED`）。
- 调度人上架前至少 1 个（需求文档只写了「姓名 + 电话，可多个」）。电话：数字，可带开头的 `+` 和中间的空格、横线，6 到 20 位数字。

### 服务规则

规则都在 `packages/domain/src/products.ts`（校验）和 `service-time.ts`（按城市时区的时间判断），浏览器填表用的是同一份。

- 金额（加急费、夜间费、附加服务单价、司机语言单价）是子品牌币种的最小货币单位整数，和全项目一致。需求文档接口示例里的 `{ amount: "12.00", currency }` 写法不采用；币种由子品牌决定，应答里单独给一个 `currency`。
- 下单有效期（`sale_from` / `sale_to`）看的是客人**下单那一天**（城市时区）在不在范围里，两端都含；不限制用车日期（那由价格规则的生效日期承担）。
- 服务时间是每天的一个时段，两端都含，可以跨午夜（`20:00`–`04:00`），全天写 `00:00`–`24:00`。（结束在午夜的写法见文末「修订」。）
- 提前预订时长按小时，0 到 720。加急阶梯的小时数不能超过提前预订时长，不能重复；落在多档时取小时数最小的那一档。
- 夏令时：本地时间不存在的（拨快的那一小时）按拨快后算，出现两次的取第一次。单元测试覆盖了这些边界。
- 免费等待的平台最低值：接机——国际线机场 90 分钟，国内线、国际国内都有或没标的 60 分钟，车站 30 分钟；送机 15 分钟；点对点 15 分钟（需求文档没写，比照送机）；包车 0。供应商填的不能低于它（`BELOW_PLATFORM_MINIMUM`，`detail.min` 给出最低值）。国际国内都有的机场，供应商填一个数（最少 60），国际航班不到 90 的按 90 算——这一条在报价时执行（M1-06）。
- 预订规则的备注是供应商自己的内部备忘（一种语言，最多 500 字），不给客人看。
- 附加服务必须是平台目录里的；开着的必须启用中、适用于这个品类；「首个免费」只有按个计费的（如儿童座椅）能设。（不适用时怎么处理见文末「修订」：不拒绝，当作没设。）
- 取消规则不在供应商的服务规则里：按第 5 轮决策由平台统一规定。平台侧的取消政策数据本期还不存在，所以服务规则的应答里没有 `cancel_policy`。

### 商品详情

按语言（ja / zh / en / ko）各一份：标题、简介、包含、不含、行程、接机指引。一种语言什么都没填就不存。标题同时是商品在列表里的名字。上架要求：至少一种语言有标题；接送机商品每一种有标题的语言都要有接机指引。

### 上架校验

`GET …/publish-check` 逐项给出通过 / 不通过和原因（路径 + 原因代码 + 中文说明）；判断是纯函数 `publishCheck(facts)`，接口层只负责把事实从库里取出来。校验看的是**现在**的情况，引用的区域、主数据后来被停用也会被指出来。

| 检查项 | 必须 | 内容 | 现在 |
| --- | --- | --- | --- |
| `basic_info` 基础信息 | 是 | 子品牌、城市、接送点启用中；至少 1 个区域、1 个车型组、1 个调度人；每个区域启用中、城市启用中、业务类型匹配；每个车型组启用中、组合仍可选 | 已实现 |
| `service_rules` 服务规则 | 是 | 服务时间、提前预订时长、这个品类该填的免等项都填了；填了的都合规；开着的附加服务启用中且适用 | 已实现 |
| `price_rules` 价格规则 | 是 | 至少一条启用且未过期的价格规则 | **功能没上线：固定不通过，原因 `FEATURE_NOT_AVAILABLE`**（M1-04 接上后变成真的检查，没有规则时是 `NO_ACTIVE_PRICE_RULE`） |
| `content` 商品详情 | 是 | 见上一节 | 已实现 |
| `adjust_rules` 调价规则 | 否 | 可以不设 | 固定通过（M1-04） |
| `inventory` 库存 | 否 | 可以不设 | 固定通过（M1-05） |

- 所以本期商品可以建、可以跑校验，但经接口上不了架：`POST …/publish` 返回 409 `PUBLISH_CHECK_FAILED`，`details.items` 和 `publish-check` 同一个结构。集成测试里需要「已上架的商品」的地方，用迁移账号直接改状态来摆数据。
- 已上架的商品可以直接改，但改完必须仍然通过上架校验，否则这次修改被拒绝（409 `PUBLISH_CHECK_FAILED`）、什么都不变。
- 上架、以及修改已上架的商品时，对它选的区域加共享锁，防止和「删除 / 停用区域」同时发生而漏判。（平台主数据的互斥见文末「修订」。）
- 资质认证没通过不能上架（需求文档）：资质模块是 M4-01，到时加一个检查项。
- 列表项带概况 `check { can_publish, failed_required, unavailable_required }`：后两个把没满足的必须项分成「自己能补的」和「功能还没上线的」。现在是逐个商品现算（每页最多 200 个）；商品多了变慢时再改成批量取数。

### 引用保护

- 区域：有已上架的商品在用时不能删除、不能停用（409 `AREA_IN_USE`，`details.published_product_count`）；只有草稿、已下架的商品在用时可以删，那些商品跟着少掉这个区域（商品的版本号不变）。有任何商品在用时不能改业务类型（409 `FIELD_LOCKED`）。区域的应答带 `usage { product_count, published_product_count }`，页面改图形前用它提示影响几个商品。
- 平台主数据：城市、地点、车型组、附加服务（商品里开着的）被已上架的商品用着时不能停用（409 `MASTER_DATA_IN_USE`，`details.active_count`）。只有草稿、已下架的商品在用时可以停用，那些商品的上架校验会指出来。

### 权限（需求文档 §11）

| 动作 | 管理员 | 商品价格 | 调度 | 财务 | 只读 |
| --- | --- | --- | --- | --- | --- |
| `product.read` | 有 | 有 | — | — | 有 |
| `product.manage` | 有 | 有 | — | — | — |
| `brand.manage` | 有 | — | — | — | — |

首页数量 `GET /tenant/v1/dashboard/summary` 加 `products { draft, published, unpublished }`，没有 `product.read` 的角色为 `null`。

### 接口路径

上架、下架用子路径 `POST …/publish`、`…/unpublish`，不用需求文档示例里的 `:publish` 写法，和已有的 `…/disable`、`…/enable` 一致。

### 地点列表按多个类型筛

`GET /tenant/v1/master/places` 和 `GET /platform/v1/master/places` 的 `type` 可以给多个，用逗号分隔（`type=airport,station`），给接送点的选项用。两侧写法一样。

### 修订：测试之后改的几处（M1-03 修复）

下面几条取代上文里对应的说法。

**服务规则只留一种写法、只留生效的内容。** 保存、读取、上架校验用的都是整理之后的同一份（`normalizeServiceRules`），所以三处的结论不会相反。

- 时段的结束在午夜：`24:00` 和 `00:00` 是同一个时刻（次日零点，算在时段里），`08:00–24:00` 和 `08:00–00:00` 判断完全一样。保存时统一成 `…–00:00`（页面上「到次日 00:00」的写法）；全天仍然只有 `00:00–24:00` 一种写法。只是换了写法的保存不算修改。
- 「首个免费」只对按个计费的附加服务有意义。别的计费方式下带了 `first_free: true` **不再拒绝**，当作没设保存。平台后来把一个附加服务从按个改成别的计费方式时，商品里原来勾着的「首个免费」不再生效：读取时返回 `false`、上架校验不算问题、报价不会用它，下一次保存服务规则时落库（那次保存会多一个版本号和一条日志）。平台改回按个计费不会自动恢复。
  - 为什么不让上架校验把它算成问题：这不是供应商能预先避免的，也没有危害（按次计费本来就没有「首个」）；算成必须项的问题会让已上架的商品此后的每次修改都被 `PUBLISH_CHECK_FAILED` 拒绝，直到供应商去存一次服务规则。
  - 为什么不保留拒绝：页面对不按个计费的附加服务不显示这个勾选框，供应商没有办法取消一个看不见的勾。
- 司机语言只能是平台支持的语言（`ja`、`zh`、`en`、`ko`，和商品详情的语言一致），不再接受任意两位字母。
- 每日加急库存是 1 到 10000，不限就留空；不再接受 0（等于开了加急却一单不接，要关就关掉加急）。
- 夏令时里不存在的用车时间：服务时间和提前预订时长用同一个时刻判断——都按拨快之后的钟面（纽约 02:30 不存在时按 03:30 去比服务时间）。

**下单有效期已经过去的商品能不能上架：能。** 需求文档的上架校验里，服务规则一项是「必填齐全」，下单有效期不是必填；写了「未过期」的只有价格规则。所以有效期已过不算上架校验的问题（它在报价时自然报不出价）。页面可以拿 `booking.sale_to` 和城市当地的今天比，给一句提醒；上架校验现在没有「提醒但不拦」的层级，要加需要新任务。

**上架校验补一个原因：`PICKUP_PLACE_OTHER_CITY`。** 接送点被平台改到别的城市之后，「基础信息」不通过（新建时这种组合是 400 `PLACE_OTHER_CITY`）。新建 / 修改时会被拒的引用问题，上架校验逐条都有对应：

| 新建 / 修改时 | 上架校验里 |
| --- | --- |
| 子品牌不存在 / 已停用 | `BRAND_DISABLED`（子品牌不能删除） |
| 城市不存在 / 已停用 | `CITY_DISABLED`（主数据不能删除） |
| 接送点没给、不是机场或车站、已停用、不在本城市 | `PICKUP_PLACE_MISSING`、`PICKUP_PLACE_DISABLED`、`PICKUP_PLACE_OTHER_CITY`（类型创建后不能改） |
| 区域不存在、已停用、业务类型不匹配、不在本城市 | 被删的区域自动从商品里去掉（没有区域时 `NO_AREA`）；`AREA_DISABLED`、`AREA_NOT_USABLE`、`AREA_CITY_DISABLED`（区域的城市创建后不能改） |
| 车型组不存在、已停用、组合不可选 | `VEHICLE_GROUP_DISABLED`、`VEHICLE_COMBO_NOT_OFFERED` |
| 调度人姓名、电话不合规 | 存下来的都是合规的；一个都没有时 `NO_DISPATCHER` |
| 服务规则填了的不合规（含免等低于平台最低值——机场航线范围被平台改了之后可能出现） | 上架校验重新查一遍，同一套原因代码 |
| 附加服务不存在、已停用、不适用 | `ADDON_DISABLED`、`ADDON_NOT_APPLICABLE`（只看开着的） |

**并发：上架和「停用它引用的东西」互斥。** 原来只对区域加了锁；现在对它引用的全部东西都互斥，结果只会是二选一：停用先完成则上架不通过，上架先完成则停用被拒。

- 区域（租户自己的表）：上架、修改已上架的商品时对它选的区域行加共享锁（原有）。
- 平台主数据（城市、接送点、车型组、开着的附加服务）：租户账号对这些表只有读权限，锁不了行，所以用按主数据编号算出来的事务级 advisory lock。上架、给已上架的商品换上新的车型组 / 开新的附加服务时，先取这些编号的**共享**锁，再读它们的状态；平台停用某一条时先取它的**排他**锁，再数有多少已上架的商品在用。
- 加锁顺序固定，不会互相等死：租户一边是「商品行 → 主数据的共享锁（按编号排序）→ 写入 → 区域行」；平台一边是「这一条的排他锁 → 主数据行」，每次只取一把排他锁，而且先于任何行锁。
- 子品牌现在没有停用的接口，所以没有对应的互斥；做停用子品牌时照区域的做法加。
- 集成测试经真实接口验证：把先到的请求停在「检查已通过、还没提交」的地方（测试锁住审计日志表），再发另一个请求，看它确实在等、等完之后被拒。区域、城市、接送点、车型组、附加服务都测了；平台主数据还测了反方向（停用先到，上架等它结束后不通过）。

**区域被删除后优先级重新排成连续的。** 草稿 / 已下架的商品少掉一个区域后，剩下的 `priority` 重新从 0 起连续排（先后不变）。

**平台修改（不是停用）主数据时不看有没有已上架的商品在用——现状和建议（这次没做）：**

| 平台的修改 | 对已上架商品的影响 | 建议 |
| --- | --- | --- |
| 去掉车型组的一个「人数 / 行李数」组合 | 选了这个组合的商品上架校验不通过（`VEHICLE_COMBO_NOT_OFFERED`），但它还在架上 | 有已上架的商品选着这个组合时拒绝（409 `MASTER_DATA_IN_USE`） |
| 去掉附加服务适用的一个品类 | 同上（`ADDON_NOT_APPLICABLE`） | 同上 |
| 把接送点改到别的城市 | 同上（`PICKUP_PLACE_OTHER_CITY`） | 同上 |
| 改附加服务的计费方式 | 商品里存的单价换了含义（每个 → 每次），「首个免费」失效 | 同上：单价含义变了不该悄悄发生 |
| 改机场的航线范围 | 接机免等的平台最低值可能变高，商品上架校验不通过（`BELOW_PLATFORM_MINIMUM`） | 不拦（报价时本来就取平台值和供应商值里较大的），但保存前告诉平台有几个已上架的商品受影响 |
