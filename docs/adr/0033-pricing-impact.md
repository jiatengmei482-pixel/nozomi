# ADR 0033：加价规则 / 渠道定价参数生效前的毛利试算

- 状态：已采纳（2026-10-26，M3-07）
- 实现 ADR 0023「本期不做」里的「复核生效前试算对近 30 天订单的毛利影响」和 ADR 0026「本期不做」里的「毛利试算」。
- 补充 ADR 0020 / 0023 的报价快照：每个候选多记它算对外价用的汇率和缓冲，渠道多记「渠道结算币种 → 客人支付币种」的汇率（见「快照里多记的两项」）。
- 补充 ADR 0023 的双人复核：复核记录加 `impact`（迁移 0050），改定价参数、加价规则的复核在发起时存一份试算。
- 编号说明：ADR 0030–0032、迁移 0034–0049 留给别的任务。

## 背景

需求：《平台运营端与渠道对接》「加价规则」——「修改加价规则需双人复核，生效前可用「试算」看对近 30 天订单的毛利影响」。
roadmap 的验收标准：发起加价规则或渠道定价参数的修改时，可以看到按近 30 天询价和订单重算的毛利变化；审核人在批准前能看到同样的试算结果。

## 决定

### 试算口径

| 项 | 怎么算 | 理由 |
| --- | --- | --- |
| 看哪些数据 | 这个渠道**近 30 天的报价**（`quotes`，每个车型组一个 `quote_id`，按询价时间）和**近 30 天下单、付过款的订单**（`order_sales` 的下单时间；`confirmed_at` 不为空） | 询价反映「新价格对报出去的价有多大影响」，订单反映「已经成交的毛利会差多少」，两者分开列。按用车日期取会把还没发生的单和很久以前问的价混进来 |
| 没付款的订单 | 不算（待支付、超时取消的） | 没有成交；它们的报价照样在「询价」里 |
| 付过款后取消的 | 有偿取消按**扣款比例**计入（对外价、结算价、毛利都 × 扣款比例，ADR 0029「按同一比例拆」）；免费取消的毛利是 0，不计入合计，单独计数 | 平台从这一单得到的就是加价 × 扣款比例 |
| 改前 | 按**现在生效的**定价参数和加价规则重算 | 只看这一次改动的影响。用历史实际成交价当改前，会把这 30 天里别的改动（之前批准过的规则）也算成这次的差 |
| 改后 | 按「现在的规则 + 这次的改动」重算：改定价参数是合并后的那一份；新增规则加进去；修改替换那一条；删除去掉那一条 | 和批准后实际生效的内容一致 |
| 中标 | **改前、改后都重新比价选中标**（`rankCandidates`：对外价、观察期 × 1.05、价格带、评分、单量、决胜规则都照旧） | 加价比例可以按租户不同，改了某个租户的比例中标就可能换人；客人付的是新中标者的对外价、平台付的是新中标者的结算价 |
| 候选 | 快照里的**全部候选**（报价那一刻报得出价的；它们的结算价、结算币种、评分、单量、观察期都按快照） | 快照（ADR 0020「全部候选的排序依据」）就是为复算存的。没进快照的（当时报不出价的）改了加价也报不出 |
| 对外价 | 每个候选按 `sellPrice` 重算：加价比例按五级匹配（用车日期按快照）、不低于下限、最低毛利、对外价取整，都用改前 / 改后那一套 | 和正式询价同一个函数 |
| 汇率 | **一律用快照里的**：候选的汇率和缓冲、最低毛利换币种和毛利换算用的渠道汇率，都是报价那一刻的；不看现在的汇率，也不再按 48 小时判断（当时能用） | 需求「汇率在报价快照里锁定」；试算看的是规则的差，不是汇率的差 |
| 毛利 | 对外价 − 结算价，两者都**按快照汇率换到渠道的结算币种**：对外价 ÷（渠道结算币种 → 客人支付币种）；结算价先 ×（结算币种 → 客人支付币种）再 ÷ 前者；同币种不换 | 渠道的账是按结算币种算的 |
| 取整 | 每一单（或每个报价）换算、按扣款比例折算后**四舍五入到最小单位**，再相加；毛利 = 取整后的对外价 − 取整后的结算价 | 和记账一致（每单入账都是整数），合计里对外价 − 结算价恰好等于毛利；也避免几万个不同分母的分数相加 |
| 差额 | 改后 − 改前（取整后的合计相减） | |
| 计数 | 中标会换人的个数；中标者要按最低毛利补价的个数（改前 / 改后各一个）；改前报得出、改后报不出的（如对外价超上限）；反过来的；快照缺汇率没法重算的 | 「会因低于最低毛利被拦的单数」：报价引擎对加价不足最低毛利的**不拦、补到最低毛利**（ADR 0023），所以数的是「要补价的」 |
| 估算 | 假定近 30 天的询价和订单照旧发生；客人面对新价格还会不会下单无法知道。页面上写明 | |

不算在里面的：服务后加收（按下单时的加价比例，ADR 0029，和以后的规则无关）、改期补收的差价（试算按下单时的报价算，改过期的单不另算）。

### 快照里多记的两项

- `QuoteSnapshot.candidates[]` 多了 `fx`（这个候选的结算币种 → 客人支付币种的中央汇率，同币种为 null）和 `fxBufferBp`。原来只有中标者的 `sell.fx`，候选的结算币种和中标者不同时就没法按快照汇率重算它的对外价。
- `StoredQuoteSnapshot.channel.settleFx`：渠道结算币种 → 客人支付币种的中央汇率。正式询价在客人支付币种和渠道结算币种不同时**总是**取这个汇率（原来只在设了最低毛利时取），取不到或过期为 null。只存进快照，不影响报价。
- **M3-07 之前的快照**：候选没有 `fx` 时，结算币种和中标者相同就用中标者的汇率，缓冲用中标者的（中标者同币种时用配置的 `FX_BUFFER_PERCENT`）；渠道汇率用最低毛利换币种时记下的，或结算币种正好是渠道结算币种的那个候选的汇率。还缺的这一条算「没法重算」，不计入合计、单独计数（`skipped`）。快照写坏了的同样。
- 渠道的结算币种改过的：快照里的渠道汇率对不上现在的结算币种，跨币种的那些报价同样算「没法重算」。

### 接口

| 接口 | 权限 | 做什么 |
| --- | --- | --- |
| `POST /platform/v1/channels/{id}/pricing-impact` | `channel.manage`（和发起这几类复核一样） | 入参 `{ kind, … }`：`kind` 是复核的类别（`channel.pricing` / `markup_rule.create` / `update` / `delete`），里面的 `change`、`rule` 和发起复核的请求体是同一个定义（openapi 里直接引用），`update`、`delete` 另给 `rule_id`。校验和发起一样（低于下限、日期重叠、调高下限时有规则低于新下限都拦），不查「和现在一样」、不查版本。只读 |
| 发起四类复核（`pricing-changes`、新增 / 修改 / 删除加价规则） | 同原来 | 发起之前按同样的口径试算一次，结果存进复核记录的 `impact`；`GET /platform/v1/approvals*` 都带 `impact`（别的类别为 null） |
| `POST /platform/v1/approvals/{id}/pricing-impact` | 看得到这一类（否则 404），且有这一类的审核**或**发起权限（`channel.review` / `channel.manage`，否则 403） | 按现在的规则和这条复核要做的改动、现在的近 30 天数据重算。只读，不改存下的那一份。不是这四类 409 `PRICING_IMPACT_NOT_APPLICABLE`；有结论了 409 `APPROVAL_NOT_PENDING`；要改的规则已被删 409 `APPROVAL_STALE` |

- 应答（也是存进复核记录的样子）：计算时间、窗口、结算币种；`quotes`、`orders` 各一份：总数、是否截断、计入数、没法重算数、改前 / 改后 / 差额（对外价、结算价、毛利，结算币种最小单位）、中标换人数、要补最低毛利的个数（改前 / 改后）、改后报不出 / 改后报得出的个数；订单另有有偿取消、免费取消的单数。没有任何供应商的名字和结算价明细。
- 只读：一个只读快照事务，不写库、不写审计（集成测试比对八张表试算前后的内容指纹）。
- 发起时的试算在发起的写事务**之前**、单独的只读事务里算：不让几秒的计算占着写事务。两者之间别人改了规则的极小窗口里，存下的试算按的是稍早一点的规则；审核人可以「再算一次」。

### 数据范围

`main` 上还没有自建角色和数据范围（M4-05 未开始）。现在按角色的操作权限控制；M4-05 做「只看某几个渠道」时，这两个接口和渠道详情一样，渠道范围外按不存在（404）处理。

### 性能

- 报价、订单各分批取（每批 5,000 行，按时间和编号的游标），每批只用 jsonb 取试算要的那几项（候选、汇率、用车日期；城市和品类在询价日志上），不读整份快照；每条语句都在连接的 10 秒 `statement_timeout` 之内。
- domain 的纯函数逐个累加（`pricingImpactAccumulator`），不把全部数据留在内存里。同一套规则下，加价比例按（租户、城市、品类、车型组、用车日期）、对外价按（结算价、币种、加价、汇率、缓冲）记下来，重复的不再算。
- **上限**：报价、订单各最多取最近的 100,000 个，超过时只算最近的这些，结果里标 `truncated` 和总数。
- 实测（`pricing-impact-benchmark.itest.ts`，开发机 2 核、机器负载约 8.7）：50,001 个报价 + 5,001 张订单约 **8.3 秒**（其中纯计算约 2 秒，其余是取数）；10,001 + 1,001 约 2 秒。需求的容量（自营官网起步）远在这之下。
  平时的检查只跑 10,000 + 1,000、只断言数字（造 50,000 行数据本身就要一分钟）；`PRICING_IMPACT_BENCH_ASSERT=1` 单独跑时按 50,000 + 5,000 并断言 ≤ 10 秒。

### 运营后台

- 渠道详情：「申请修改定价参数」「新增 / 修改加价规则」的对话框里有「试算近 30 天毛利影响」按钮，按现在填的内容试算；内容改了以后旧结果不再显示，提示重新试算（只改「给审核人的说明」不算改内容）；填得不对时按钮不可用。「申请删除加价规则」的对话框一打开就算。
- 结果：付过款的订单、询价各一张表（对外价合计、结算价合计、毛利的改前 / 改后 / 差额），下面列中标换人、要按最低毛利补价、改后报不出、没法重算、有偿 / 免费取消的个数，并写明「这是估算……」。
- 待审核：改定价参数、加价规则的复核显示「发起时的毛利试算」；待审核、能审核或撤回的人有「按现在的数据再算一次」，结果另外显示，存下的那一份不变。M3-07 之前发起的写明「没有保存」。

## 待定事项（需求没写清；先按推荐做了）

| # | 问题 | 选的方案 | 理由 |
| --- | --- | --- | --- |
| 1 | 「改前」用历史实际成交价，还是按现在的规则重算 | 按现在的规则重算 | 只反映这一次改动；这 30 天里别的改动不会混进差额 |
| 2 | 「近 30 天」按询价 / 下单时间，还是用车日期 | 询价时间、下单时间 | 是已经发生的询价和成交；按用车日期会混进还没发生的单 |
| 3 | 「低于最低毛利被拦」怎么数 | 数「中标者要补到最低毛利的」（改前 / 改后） | 引擎对加价不足最低毛利的是补价不是拦截（ADR 0023）；要改成真正拦下（报不出价）要另定 |
| 4 | 中标要不要重算 | 重算 | 加价按租户不同时中标会换人，不重算会把毛利算错 |
| 5 | 有偿取消、免费取消 | 有偿按扣款比例计入，免费只计数 | 平台从有偿取消得到加价 × 扣款比例（ADR 0029） |
| 6 | 数据量上限 | 报价、订单各最近 100,000 个 | 50,000 个约 8 秒；再多时最近的样本已经足够说明趋势，结果里标出截断 |
