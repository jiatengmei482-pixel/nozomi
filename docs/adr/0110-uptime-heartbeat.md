# ADR 0110：服务可用性检查和心跳提醒

- 状态：已采纳（2026-11-25，M12-05）
- 补充：ADR 0007「部署到自有 VPS」（入口模式、`bin/` 脚本、初始化脚本装定时任务）、ADR 0105 第 5 节「监控」（备份心跳 `BACKUP_HEARTBEAT_URL`）。两篇的其余内容不变。
- 依据：中文版上线前缺的开发项（#288，M12-05）：网站挂了没人知道。

## 背景

现在唯一的主动提醒是 ADR 0105 的备份心跳：备份全部正常时服务器每 15 分钟访问一次 `.env` 里的 `BACKUP_HEARTBEAT_URL`，监控服务收不到就发邮件。它能发现「整台服务器宕机」，但发现不了「服务器活着、网站打不开」或「网站开着、接口大量报错」：数据库正常、备份正常，API 起不来、反向代理挂了、证书过期、一个坏版本让下单接口一直 500，都不会有人知道，直到客人或供应商来说。

## 决定

### 1. 装法：和备份心跳一样，初始化脚本装的定时任务

`deploy/bootstrap.sh` 新装 `/etc/cron.d/nozomi-uptime-<环境>`：每 5 分钟以部署账号 `nozomi` 运行 `current/bin/uptime-check.sh`，输出进系统日志（标签 `nozomi-uptime`）。脚本随版本目录一起上传、一起回退，和 `pitr-status.sh` 同一个位置。

| 候选 | 结论 |
| --- | --- |
| 初始化脚本装的定时任务（选这个） | 和备份心跳同一种装法，不加新依赖（cron、curl、awk、flock、logger 初始化脚本本来就保证有）；脚本在宿主机上，能经正式入口访问、能读容器日志 |
| compose 里加一个常驻的小容器 | 要读反向代理的日志就得把 Docker 的套接字挂进去（等于给它整台机器的权限），或者让 Caddy 另写一份日志文件到共享卷；还多一个要升级、要监控的容器 |
| systemd timer | 和现有的 cron 两套并存，没有额外好处 |

已经初始化过的服务器要**重新运行一次「服务器初始化」**才装上（部署账号写不了 `/etc/cron.d`）；在那之前每次部署成功时，部署日志里会提示一句。

### 2. 查什么

1. **经正式入口访问 `/health`**：返回 200 且 `status` 是 `ok`（`/health` 本身就查了数据库和迁移，ADR 0007）。
   - standalone：`https://<域名>/health`，用 `--resolve` 连到本机 443。走的是客人用的同一个入口，证书也一起验了（证书过期、续期失败会被发现）；不经过 DNS 和外网。
   - behind-proxy：`http://<EDGE_LISTEN>/health`，和 `deploy.sh` 部署后的本机入口检查一样。外层代理（别人的 nginx）不在检查范围内。
2. **最近 5 分钟 API 的 5xx**：从反向代理（Caddy）的访问日志里数（`compose.sh logs --since 5m caddy`）。
   - 选 Caddy 的访问日志：每个经入口的请求都有一行 JSON（含状态码），不用加新服务、不用改 API；API 停了或超时时客人拿到的 502 / 504 也在这里（API 自己的日志里没有这些）。容器内部的健康检查（`:8081`、API 容器里的 `fetch`）不进这份日志，不会冲淡比例。
   - 只数归 API 的路径（`/health`、`/platform/v1` 等，和 `apps/web/src/lib/api-prefixes.ts` 同一张表，单元测试核对两边一致）：前端页面和静态文件的请求不算，免得把比例冲淡。
   - **阈值**：5 分钟内 5xx **至少 20 次并且占比至少 10%** 算异常。两个条件都要满足：夜里流量很少时三五次 5xx 不报，白天流量大时零星的 5xx 也不报。两个数放在 `.env`（`UPTIME_5XX_MIN_COUNT`、`UPTIME_5XX_MIN_PERCENT`），每次检查时现读，改了不用重启任何服务；填错了（不是整数、超出范围）算异常，不悄悄用默认值。
3. **都正常才访问 `.env` 里的 `UPTIME_HEARTBEAT_URL`**（超时 10 秒、重试 3 次）。有任何一项异常就不访问，由监控服务在超时后发邮件；服务器日志里逐条写明原因。没填这个地址时检查照做、只记日志，不算异常。

### 3. 心跳地址和日志

- `UPTIME_HEARTBEAT_URL` 是负责人在心跳服务（如 Healthchecks 免费版）里自己建的检查给的地址。它不是密钥，但知道它的人能冒充「一切正常」，所以和 `BACKUP_HEARTBEAT_URL` 一样只写在服务器的 `.env` 里，不进代码、不进日志：脚本不打印它，访问它时不用 `curl --show-error`（curl 的报错里可能带地址），失败只记 curl 的退出码。
- 只接受 `https://`。唯一的例外是本机回环地址上的 `http://127.0.0.1…`：只有 CI 冒烟的假接收端用，不出这台机器。
- 日志里只有计数、状态码和原因：不打印 `/health` 的响应内容、请求的地址、来源地址和任何请求内容。
- 两次检查不重叠（`flock`）；上一次还卡着（多半是 Docker 没响应）时这次直接算异常。读日志最多等 60 秒。

### 4. 心跳服务那边怎么设

周期 5 分钟、宽限 10 分钟：连续约 15 分钟没收到才发邮件。部署时容器重启那一两分钟、或者某一次检查碰巧没通过，都不会误报；真的挂了，15 分钟左右知道。

### 5. 为什么不在异常时主动报（`/fail`）

Healthchecks 等支持访问「地址 + `/fail`」立即报警，但各家写法不同；而「不访问」对所有心跳服务都通用，还能同时覆盖「服务器宕机、定时任务没跑」这类根本发不出请求的情况。代价是最多晚 10 分钟知道。以后需要更快时再加。

## 测试

- 单元测试（`apps/api/src/deploy-uptime.test.ts`，替身代替 docker 和 curl，真实执行脚本）：两种入口模式各自访问哪个地址；`/health` 503、连不上、200 但不是 ok；5xx 阈值的边界（正好 20 次 10%、19 次、占比不够）；只数 API 路径；`.env` 调阈值、填错阈值；读不到日志；心跳地址没填、不是 https、发送失败；检查重叠；输出里没有心跳地址、来源地址和路径；初始化脚本装的定时任务。
- 初始化脚本检查（`deploy/ci/bootstrap-check.sh`，Ubuntu 和 RHEL 系的容器）：定时任务文件的权限和内容，`.env` 里留好空位，重复运行不变。
- 部署冒烟（`deploy/ci/smoke.sh`，两种入口模式，真实镜像）：本机起一个假的心跳接收端；正常时访问一次；停掉 API 后不访问、写明 `/health` 不通；API 恢复后把阈值调低，用真实 Caddy 访问日志里刚才那几次 502 判为异常、不访问；阈值回到默认后再访问一次。

## 影响

- 需要负责人做的：在心跳服务里建一个检查（周期 5 分钟、宽限 10 分钟），把地址填进服务器 `.env` 的 `UPTIME_HEARTBEAT_URL`；已初始化过的服务器重新运行一次「服务器初始化」。见 `docs/deploy.md`「服务可用性提醒」。正式环境上线清单里加了这一项。
- 系统日志每 5 分钟多一行到几行（`journalctl -t nozomi-uptime`）。
- 每次检查经入口访问一次 `/health`，在访问日志里多一行。

## 已知限制

- 只从服务器本机查：域名解析错了、服务商的防火墙挡了、外层代理（behind-proxy）配错了，本机看是好的。需要「从外网看」时，在监控服务里另加一个 HTTP 检查（很多心跳服务的付费版、或 UptimeRobot 免费版都有），不在本 ADR 范围内。
- 只看 5xx，不看响应慢：接口很慢但没报错不会被发现。
- 第三方服务（Stripe、谷歌地图）出问题只有在它让我们的接口回 5xx 时才算。
