# ADR 0049：通知中心——事件发件箱、邮件模板、发送记录

- 状态：已采纳（2026-11-01，M4-08）；标了「待负责人确认」的是按推荐先做的决定，汇总在文末。
- 实现 ADR 0032、0035 留下的「确认邮件里带订单查看链接」，以及 0022、0025、0027、0028、0029、0031、0034 里写着「通知中心任务」的那几项（范围见「事件清单」和「不做」）。
- 补充 ADR 0048：发信一律经 `services/mail.ts` 的 `sendMail`；它留给本任务的「过一阵再发」「已送达」在这里定。
- 补充 ADR 0032：`site_order_links.issued_via` 多一个取值 `email`。
- 迁移 0140（0131–0139 留给别的任务）。

## 背景

需求《平台运营端与渠道对接》「通知中心」：所有对人的通知都从通知中心发出，统一模版、统一记录；模版按「事件 × 接收方 × 语言 × 通道」维护，变量用订单字段；接收方可设免打扰时段，紧急类（用车当天）不受限；每条发送记录状态（已发送 / 已送达 / 失败），可按订单查。「客人通知（不接短信）」规定了确认、派车、用车前 24 小时、司机已到达四个时间点；「服务后加收费用」规定提交后邮件通知客人。

现实约束：负责人还没填 SMTP，邮件现在发不出去；下单、付款、派车都不能因此受影响。

## 决定

### 总体：两张表、两段处理

```
业务事务 ──同一事务──▶ notification_events（发件箱：发生了什么）
                         │ 后台任务展开：按事件定接收方
                         ▼
                      notifications（发送记录：这一个人的这一封）
                         │ 后台任务发送：现取内容、渲染、sendMail、记结果
                         ▼
                        SMTP
```

**为什么分两张表**：派车、回传履约、提交加收都在**租户事务**里，而判断「这是不是官网的单」要读平台表 `site_order_links`、给平台员工发要读 `platform_users`，这些租户角色都读不到，也不该读到。业务事务只写一行「发生了什么」（租户角色对发件箱只有 `insert`，读不了），谁该收到由后台任务在平台事务里决定。发件箱和业务同生共死：业务回滚，事件就没有；业务提交，事件一定在。

后台任务 `NotificationJobs` 和 `WebhookJobs` 同一种写法（ADR 0022「定时任务和多实例」）：跑在 API 进程里，只有 `buildApp({ jobs: true })` 启动，启动后 5 秒第一次、之后每 5 秒一轮，`for update skip locked` 加租约，测试直接调 `tick()`。不引入队列框架。

### 事件清单

通道都是邮件，语言都是 `zh-CN`（见「模板」）。

| 事件 | 接收方 | 什么时候 | 依据 |
| --- | --- | --- | --- |
| `order.confirmed` | 客人、供应商 | 付款成功、订单确认 | 需求「支付后发确认邮件」「新订单」。客人那封带查看链接（ADR 0032） |
| `order.assigned` | 客人 | 派车、改派 | 需求「派车后发司机姓名、车牌、联系方式」「改派自动通知客人」 |
| `order.service_reminder` | 客人 | 用车前 24 小时（任务扫描） | 需求「用车前 24 小时发提醒」。下单时已不足 24 小时的不发（确认邮件就是提醒） |
| `order.driver_arrived` | 客人 | 司机点「已到达」 | 需求「司机点已到达时发邮件」 |
| `order.changed` | 客人、供应商 | 改单生效 | 需求「修改和取消」、ADR 0029 |
| `order.change_pending` | 供应商 | 改期等供应商确认 | 同上 |
| `order.change_declined` | 客人 | 改期被拒或超时没确认 | 同上（「改期结果」） |
| `order.cancelled` | 客人、供应商 | 付过款的单被取消 | 需求「修改和取消」。超时未付款、付款被取消的**不发**：客人没收到过确认，也没付钱 |
| `extra_charge.submitted` | 客人 | 供应商提交事后加收 | 需求「邮件通知客人，48 小时内可提异议」 |
| `ticket.guest_reply` | 客人 | 平台在工单里回复客人 | ADR 0034「工单的通知」。邮件只说「有新回复」，不抄内容，点链接看 |
| `order.rescue_assigned` | 供应商（新接单的那家） | 救援单转给它 | 需求「新订单」、ADR 0031 |
| `order.dispatch_overdue` | 供应商 | 过了派车截止时间仍未派车 | 需求「派车截止提醒」、ADR 0027 |
| `order.departure_overdue` | 供应商 | 用车前 1 小时仍未出发 | 需求「用车前 1 小时仍未已出发时提醒租户」 |
| `ticket.reply_requested` | 供应商 | 平台征求供应商意见 | 需求「工单」「24 小时内回复」 |
| `tenant.document_expiring`、`tenant.document_expired` | 供应商 | 每日检查发现资质快到期、已到期 | 需求「到期前 30 天、7 天提醒」、ADR 0028 |
| `tenant.observation_started`、`tenant.status_changed` | 供应商 | 进入观察期、状态变化（如暂停） | 需求「进入观察期（通知租户整改）」、ADR 0028 |
| `exception.opened` | 平台员工 | 异常队列新增一条 | 需求「平台员工：异常队列」 |
| `fx.alert` | 平台员工 | 汇率挂起、超过 48 小时未更新 | 需求「挂起并告警人工确认」、ADR 0022 |
| `site.lookup_ceiling` | 平台员工 | 官网找回订单同一订单号 24 小时失败满 100 次 | 需求「风控告警」、ADR 0032「告警以后由通知中心任务接」 |

### 发给谁

- **客人**：只有官网的单（需求「客人：由渠道发；自有官网由平台发邮件」）。判断方法：这张单有 `site_order_links`（官网下单必定有，其他渠道必定没有）。地址是订单现在的乘客邮箱。一个事件一封。
- **供应商**：这家在用（`active`）的管理员和调度，一人一封；一个都没有时发给企业信息里的联系邮箱；再没有就不产生发送记录，服务日志记一条 `notification.no_recipient`。
- **平台员工**：在用、且有对应权限的人，一人一封：异常发给有 `exception.manage` 的，汇率发给有 `fx.manage` 的，找回告警发给风控和超级管理员。自建角色按勾选的权限算。

### 模板

- **模板是代码常量**（`packages/domain/src/notifications.ts`），主键是「事件 × 接收方 × 语言 × 通道」，改模板走代码评审和测试。运营后台只读展示（`GET /platform/v1/notification-templates`）。**待负责人确认 1**：需求接口表写的是 `GET/PUT`；本期不做在线编辑（见「不做」）。
- **语言只有 `zh-CN`**：官网现在只有中文，订单也没记客人的语言，其他语言的模板写出来也选不到。加语言 = 加常量 + 记下客人语言。发送记录上存语言。**待负责人确认 2**。
- 只发纯文本（`text`），不发 `html`：没有 HTML 就没有 HTML 注入，也没有追踪像素、外链图片；链接由邮件客户端自动识别。
- 占位符写成 `{{order_no}}`。每个模板声明自己用到的变量，渲染只替换声明过的；缺变量不发（`RENDER_FAILED`，最终失败，属程序问题）。主题的变量去掉控制字符（防头注入；`sendMail` 还有一道）。
- **供应商模板的变量是白名单**（`TENANT_VARIABLES`）：**没有**对外价、加价比例、客人付款金额、退款金额、汇率（规则 4）。取数函数从不为供应商的通知读 `order_sales`。单元测试扫所有模板，集成测试把假 SMTP 收到的供应商邮件按真实金额比对。
- 内容只有行程和订单号：**不写结算价**（后台里有），也不写乘客的联系方式。

### 不存正文，发的时候现取

记录里没有主题和正文，只有事件、接收方、状态。每次发送时按**当前**的订单现取现渲染：

- 查看链接令牌不进库（库里只有 SHA-256）、不进日志、不进记录页；**没有可以泄露的存档**。
- 重试时内容是最新的：改过时间、换过司机的，不会发旧信息。
- 代价：事后看不到「当时发的原文」。排查时看事件、模板和订单流水。

### 查看链接

每次要发带链接的邮件时**新生成一个**（ADR 0032 的决定），`issued_via = 'email'`，有效期规则不变。失败的尝试留下的链接没有人拿得到（原文只在内存里），到期自然失效；最多多几行哈希。

### 状态和重试

| 状态 | 含义 |
| --- | --- |
| `pending` | 等待发送（包括等重试、等免打扰结束 `QUIET_HOURS`、等配置邮件 `NOT_CONFIGURED`） |
| `sending` | 正在发（有租约） |
| `sent` | **邮件服务器已接收**。不等于进了收件箱 |
| `failed` | 最终失败，页面看得到原因，可以手动重试 |
| `expired` | 不再发送：过了有效期（`EXPIRED`），或订单情况变了、发了只会误导（`ORDER_STATE_CHANGED`） |

发送结果按失败类型处理（domain 的 `notificationFailureAction`）：

| `sendMail` 的结果 | 处理 |
| --- | --- |
| `RECIPIENT_REJECTED`、`MESSAGE_INVALID` | 这封永远发不出去，直接最终失败 |
| `UNREACHABLE`、`TIMEOUT`、`SENDER_REJECTED`、`UNEXPECTED` | 退避重试：1 分钟、5 分钟、30 分钟、2 小时、6 小时；第 6 次仍失败就是最终失败，服务日志 `notification.failed`（错误级别） |
| `AUTH_FAILED`、`TLS_FAILED`、`TARGET_FORBIDDEN` | **配置问题**，和这封信无关：不算次数，5 分钟后再试，一直到这条的有效期；否则密码填错一晚上，所有通知都耗尽次数，改对了还要一条条手动重试 |
| `NOT_CONFIGURED` | 见下一节 |

### 邮件没配置时

- 业务完全不受影响：业务事务只写发件箱，不碰邮件；`sendMail` 只在后台任务里调用。
- 任务照常展开事件、产生记录；记录留在 `pending`，原因写 `NOT_CONFIGURED`，**不取走、不算次数**。
- 负责人填好后，下一轮（≤ 5 秒，密钥缓存见 ADR 0041）自动发还没过期的。
- 每条记录展开时算好**有效期**（domain 的 `notificationExpiresAt`），过了改为 `expired`，运营后台看得到。这样不会有「配置一填，几周前的通知一起砸给客人」：

| 事件 | 过期时间 |
| --- | --- |
| 确认、派车、提醒、新订单、救援单、改期待确认、派车和出发提醒 | 用车时间 |
| 司机已到达 | 事件后 1 小时 |
| 改单、改期结果、取消、工单回复、工单征求意见、供应商的资质和状态 | 事件后 7 天 |
| 事后加收 | 异议期结束 |
| 平台员工的告警 | 事件后 24 小时 |

- 发送前再看一次订单（domain 的 `notificationStale`）：确认、派车、提醒、到达在订单取消或结束后不再发；旧司机的派车通知在改派后不再发；提醒在改期后不再发（新时间有自己的提醒）；派车、出发提醒在已经派了车、已经出发后不再发。都记 `expired` + `ORDER_STATE_CHANGED`。

### 幂等和不重复

- **同一事件不重复入箱**：发件箱有唯一的 `dedupe_key`（如 `order.confirmed:<订单>`、`order.assigned:<派车记录>`、`order.service_reminder:<订单>:<用车时刻>`），写入 `on conflict do nothing`。Stripe 重发通知、任务重跑都只有一条。
- **同一事件同一人不重复展开**：`notifications` 上 `(event_id, audience, recipient)` 唯一。
- **发送**：取走时写租约令牌（60 秒，比发信时限 15 秒长得多），记结果时核对令牌，被接手的一方不记。
- **进程在发送中途死掉**（`sending` 且租约过期）：不知道发出去了没有，**不自动重发**，记最终失败 `OUTCOME_UNKNOWN`，页面说明「可能已发出」，由人决定要不要重试。
- 已知限制：`TIMEOUT`、`UNREACHABLE` 里有极少数是服务器已接收、应答丢了，这种自动重试会让收件人收到两封。这比漏发确认邮件好，而且发件方分不清；ADR 0048 的同一封内不重试不变。

### 免打扰

- 只有**供应商**能设（`PUT /tenant/v1/notification-settings`，`notification.manage`，归管理员）：一家一个时段，开始、结束是东京时间（`TENANT_RULES.timeZone`）的 `HH:mm`，可以跨午夜，整段留空就是不设。**待负责人确认 3**：需求写「接收方可设」；客人没有账号、平台员工的告警都是要马上看的，所以这两类不做。
- **用车当天（按订单城市当地日期）不受限**。没有订单的通知（资质、状态）受限。
- 免打扰时段里到期的，改到时段结束再发，不算次数。

### 运营后台

| 接口 | 权限 | 说明 |
| --- | --- | --- |
| `GET /platform/v1/notifications` | `notification.read` | 筛状态、事件、接收方类型、订单（编号或订单号）；带汇总：邮件配置了没有、等待发送多少条 |
| `POST /platform/v1/notifications/{id}/retry` | `notification.retry` | 手动重试 |
| `GET /platform/v1/notification-templates` | `notification.read` | 只读看模板 |

- `notification.read`、`notification.retry`：超级管理员、运营、客服（需求「通知中心：运营」；客服处理订单时要回答「客人收到没有」）。遵守数据范围（ADR 0030）：限定了范围的人只看范围内订单的记录，不属于订单的记录看不到。
- **手动重试**：`failed`、过了有效期的 `expired`（`EXPIRED`）能重试；`ORDER_STATE_CHANGED` 的不能（发了就是错的）；其余 409 `NOTIFICATION_NOT_RETRYABLE`。邮件没配置 409 `MAIL_NOT_CONFIGURED`。点了立刻发一次，失败回到 `failed`，不再自动重试。写审计日志（资源 `notification`、动作 `retry`；前后值只有状态、错误码、事件，没有收件人）。过了有效期的重试时，发送前的订单检查照做。
- **记录页展示**：事件、接收方类型、收件人（**打码**：`ab***@example.com`，domain 的 `maskEmail`）、状态、失败代码和我们自己写的一句话、次数、时间、订单号。**不展示**：正文（本来就没有）、令牌、完整邮箱、对外价。需要完整邮箱的客服去订单详情，那里有 `order.read` 把关。

### 供应商后台

| 接口 | 权限 | 说明 |
| --- | --- | --- |
| `GET /tenant/v1/notifications` | `notification.read`（管理员、调度、只读） | 发给**自己这家**的记录，可按订单筛。看不到发给客人的，也看不到别家的 |
| `GET`、`PUT /tenant/v1/notification-settings` | 看 `notification.read`；改 `notification.manage`（管理员） | 免打扰时段 |

### 隐私和日志

- 日志只写通知编号、事件、订单编号、错误码。**不写**邮箱（全文和打码都不写）、订单令牌、主题、正文。
- 错误信息只存 `sendMail` 返回的我们自己写的那句话（ADR 0048 已保证不带服务器原文）。
- `notifications.recipient` 存邮箱原文（发信要用），和订单的乘客邮箱同等保护：只有平台角色和这家供应商读得到，接口一律打码返回。
- 发件箱的 `data` 只放编号和枚举（如改了哪些字段名、原因码），不放邮箱、金额、令牌。

### 表（迁移 0140）

| 表 | 层级 | 内容 | 平台 | 租户 |
| --- | --- | --- | --- | --- |
| `notification_events` | 租户表，`tenant_id` 可空（和 `audit_logs` 一样：平台员工的告警不属于任何租户） | 发件箱：事件、订单、`dedupe_key`、`data`、发生时间、展开时间 | 读、写、改展开时间 | 只能追加自己的，读不了 |
| `notifications` | 同上；发给客人和平台员工的也带（发给客人的 `tenant_id` 是这单的供应商，方便查） | 发送记录 | 读、写、改 | 只能读 `audience = 'tenant'` 且是自己的 |
| `tenant_notification_settings` | 租户表 | 免打扰时段 | 只读 | 读、写 |

- 租户读 `notifications` 的策略同时限定 `tenant_id`（放行策略）和 `audience`（限制性策略）：发给客人的记录上虽然有这家的编号，供应商也读不到。
- **对 ADR 0009 的例外**（`schema-structure.itest.ts` 逐条登记）：这两张表 `tenant_id` 可空，主键是编号，外键 `notifications → notification_events` 不带 `tenant_id`。平台员工的告警不属于任何租户，又要和其他通知走同一条发送路径；发送记录只有平台角色写，这个外键指不到别家。
- 不写任何预置数据。

## 不做

| 内容 | 为什么 / 去向 |
| --- | --- |
| **「已送达」状态**（**待负责人确认 4**） | 通用 SMTP 只能知道「服务器接收了」，之后进没进收件箱要邮件服务商的回调或退信邮箱，负责人选定服务商后另开任务。**不用「已发送」冒充**。验收标准里的「已送达」本期达不到 |
| 模板在线编辑（`PUT /notification-templates`） | 见「模板」。在线改模板还要变量校验、版本和预览，等真有频繁改文案的需求再做 |
| 其他语言 | 见「模板」 |
| LINE、微信、即时通讯群 | 需求里是「可选」，要接外部服务和账号 |
| 后台消息（站内信） | 现有的是供应商后台的提醒（`tenant_notices`）、异常队列、记录页；不另做收件箱 |
| 集合点说明和照片（提醒邮件里） | 主数据还没有这项内容；有了以后加变量。**待负责人确认 5** |
| 客服热线写进邮件 | 同订单页：配置了 `SITE_SUPPORT_PHONE` 才有，本期邮件不写 |
| 其他渠道的客人通知 | 需求「由渠道发」 |
| 司机通知 | 需求「司机 H5 链接（由租户调度转发）」，不是邮件 |
| 最低价提醒 | 这项功能本身还没有 |
| 连接器故障告警 | 连接器还没有 |
| 司机驾照、车辆保险到期提醒 | 现在的代码没有这类提醒的任务，属于车队的任务 |
| 救援单发给候选供应商、原供应商「单被转走」的邮件 | 需求表没列；后台和 Webhook 都有 |
| 汇率锁定到期提醒（ADR 0025） | 需求没写，ADR 只是提到；审计和服务日志有 |
| 工单判定结果邮件 | 表里只要求「工单」；本期只发「需要你回复」这件有时限的事 |
| 退订 | 都是交易类通知，不是营销 |
