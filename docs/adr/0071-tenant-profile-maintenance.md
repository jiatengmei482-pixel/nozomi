# ADR 0071：供应商名称和企业信息的维护

- 状态：已采纳（2026-11-09，M4-34）
- 补充 ADR 0028：「企业信息只有申请中能改，之后锁住」改为下面的分法；「租户角色不能改 `tenants`」不变（名称的修改申请批准时在平台事务里写）。
- 补充 ADR 0023：双人复核新登记一类 `tenant.profile_change`（供应商改对外显示名称、法定名称、登记号）。
- 补充 ADR 0030：新操作 `tenant.edit`，算菜单「供应商」的「编辑」一格。
- 补充 ADR 0049：新事件 `tenant.profile_updated`、`tenant.profile_change_submitted`（发给平台员工）、`tenant.profile_change_approved`、`tenant.profile_change_rejected`（发给供应商管理员）。
- 补充 ADR 0010：迁移 0240——平台角色对 `tenant_profiles` 多了 `insert`、`update`；新表 `tenant_profile_changes`。
- 编号说明：0070 已被 M8-09 的分支占用，本文用 0071。

## 背景

- 对外显示名称（`tenants.name`）只在平台新建供应商时填，之后平台和供应商都改不了（`platform-tenants.md` 第 9 节第 5 条「修改供应商名称的接口」）。
- 企业信息（`tenant_profiles`：国家、法定名称、登记号、注册地址、联系人、电话、邮箱）只有「申请中」的供应商能改；审核通过以后谁都改不了，联系人换了也只能留着旧的。平台详情页不显示企业信息。
- 业主 2026-11-09 确认：**供应商改「对外显示名称」要平台审核通过后才生效**（审核期间客人仍看到旧名称），和法定名称、登记号一样走「企业信息变更」审核，平台另一位员工批准，提交的人不能自己批。顺序：先做平台侧（平台直接编辑、详情页企业信息卡片和入口），再做供应商侧的审核。
- 银行信息在收款账户（ADR 0051），不在这里，不重复造字段。

## 决定

### 字段和谁能怎么改

| 字段 | 平台（`tenant.edit`） | 供应商管理员：申请中 | 供应商管理员：审核通过以后（审核中、已签约、试运营、正式、暂停） |
| --- | --- | --- | --- |
| 对外显示名称（`tenants.name`） | 直接改 | 提交申请（名称不在企业信息里，ADR 0028 起就是平台建的） | 提交申请，平台复核通过后生效 |
| 法定名称、登记号 | 直接改 | 直接改 | 提交申请，平台复核通过后生效 |
| 所在国家 | 直接改 | 直接改 | 不能改（决定必交资质清单，改了会让已审的资质对不上），请联系平台 |
| 注册地址、联系人、电话、邮箱 | 直接改 | 直接改 | **直接改**，记审计，通知平台运营 |

- 已清退的供应商：`company.manage` 在鉴权这一步就 409 `TENANT_TERMINATED`（ADR 0028），只能看；平台仍能改（任何状态）。
- 供应商审核通过以后改企业信息，接口仍是整体替换的 `PUT /tenant/v1/company/profile`：和现在的值比，国家、法定名称、登记号有变化的 409 `PROFILE_FIELDS_LOCKED`（`details.fields`），什么都没变的不写、不通知。「申请中」的行为原样保留（每次保存都写一笔）。
  M4-01 之前就在运营、没有企业信息的供应商，可以直接补联系信息；法定名称、登记号要走申请。

### 平台直接改

- `PATCH /platform/v1/tenants/:id`：只收 `name`（多给字段 400）。**`If-Match` 用 `tenants.version`**：这一列 M4-01 就有了，状态变化（`applyTenantChange`）也会让它加一；每日检查记评分不加（`saveTenantEvaluation`）。和主数据、商品的乐观锁同一种做法（版本列 + `If-Match`，不一致 409 `VERSION_CONFLICT`，没带 428）。不用 `updated_at`：同一毫秒的两次改动分不出来。
  状态变化也会让名称的修改冲突，代价是偶尔要刷新一次；换来的是不用再加一列。
- `PUT /platform/v1/tenants/:id/company/profile`：和供应商的同一份请求体，整体替换；还没有企业信息时不带 `If-Match`，以后带企业信息的 `version`。
- 两者都是：和现在一样的不写、版本不变；写审计（名称：对象 `tenant`、动作 `update`、前后的名称；企业信息：对象 `tenant_profile`、`create` / `update`、前后七项），操作者是平台员工。直接生效、不走复核：平台员工本来就能看营业执照，改错了随时能再改，需求的复核清单里没有它。

### 供应商的修改申请（名称、法定名称、登记号）

- 表 `tenant_profile_changes`（租户表，带 `tenant_id`、行级安全；供应商只读自己的）：改哪几项（`fields`）、改成什么（`proposed`）、提交时的值（`previous`）、说明、状态（`pending` 等平台处理 → `approved` 已生效 / `rejected` 平台驳回 / `withdrawn` 供应商撤回）、提交人、批准的复核、驳回人和原因、版本。
- 提交、撤回在**平台事务**里做（租户编号只来自令牌，每条 SQL 带它），和收款账户（ADR 0051）同一做法：供应商角色对这张表只有 `select`，写不出「已生效」的申请；内容列平台也改不了（`reject_platform_column_update`），状态机和「已生效必须有属于它的已批准复核」由触发器兜底。
- 规则（domain `tenant-profile.ts`）：至少一项；每项不能为空、不超长（按字符数）、不能和现在一样（400 `VALIDATION_FAILED`）；一家同时只有一条等处理的（409 `PROFILE_CHANGE_PENDING_EXISTS`，要改先撤回）。
- **审核期间旧值照常用**：申请不碰 `tenants` 和 `tenant_profiles`，客人、渠道、账单看到的仍是原来的。
- **双人复核**：`approvals.requested_by` 必须是平台员工（ADR 0023 的约束），供应商不能直接当发起人。所以和收款账户一样分两步：
  1. 平台一位有 `tenant.review` 的同事（运营、招商、超级管理员）按营业执照、登记簿核对后**发起复核**（`POST …/profile-changes/:changeId/approval`，`kind = tenant.profile_change`，`base_version` = 申请的版本），或者直接**驳回**（原因必填，供应商看得到）；
  2. 另一位有 `tenant.approve` 的同事在「待审核」里批准。发起人不能批自己发起的（`APPROVAL_SELF_REVIEW`，数据库也有约束）；供应商本来就不是平台员工，碰不到复核接口。
- **批准时**（同一个事务）：锁申请、核对还是等处理且版本没变（撤回了就 `APPROVAL_STALE`）；锁供应商和企业信息，核对申请里每一项「提交时的值」和现在一样——审核期间平台直接改过这几项的也 `APPROVAL_STALE`，不能用旧申请盖掉平台的改动；然后改名称（版本加一）、改企业信息（版本加一），申请记为已生效。任何一步失败整个回滚，复核仍是待审核，审核人驳回即可。
  复核被驳回或撤回时，申请本身不变（仍等处理）：处理申请的同事可以重新发起或驳回申请。这和收款账户一样，复核的结论只针对「这次发起」，不替供应商的申请下结论。

### 审计

| 事 | 对象 | 动作 | 操作者 |
| --- | --- | --- | --- |
| 平台改名称 | `tenant` | `update`（前后 `name`） | 平台员工 |
| 平台、供应商改企业信息 | `tenant_profile` | `create` / `update`（前后七项） | 平台员工 / 供应商用户 |
| 提交、撤回申请 | `tenant_profile_change` | `submit`（前：提交时的值，后：改成什么）/ `withdraw` | 供应商用户 |
| 驳回申请 | `tenant_profile_change` | `reject`（带原因） | 平台员工 |
| 发起、批准、驳回、撤回复核 | `approval` | ADR 0023 的那四种 | 平台员工 |
| 批准生效 | `tenant`、`tenant_profile`（`after` 带 `approval_id`、`change_id`）；`tenant_profile_change` 的 `approve` | | 审核人 |

### 通知（ADR 0049 的通知中心）

| 事件 | 接收方 | 什么时候 | 内容 |
| --- | --- | --- | --- |
| `tenant.profile_updated` | 平台员工：有 `tenant.edit` 的 | 审核通过以后的供应商直接改了企业信息 | 哪家、改了哪几项（不抄值，值在审计日志） |
| `tenant.profile_change_submitted` | 平台员工：有 `tenant.review` 的 | 供应商提交修改申请 | 哪家、申请改哪几项；去供应商详情处理 |
| `tenant.profile_change_approved` | 供应商管理员 | 批准生效 | 改了哪几项；「不是你们提交的请联系平台」 |
| `tenant.profile_change_rejected` | 供应商管理员 | 平台驳回 | 改了哪几项、驳回原因 |

- 发给平台员工的两类事件带着供应商的 `tenant_id`（同一家去重），发送记录的 `tenant_id` 为空（ADR 0049「平台员工的记录」），供应商读不到。限定了数据范围的员工收不到（和别的不属于订单的通知一样）。
- 有效期按默认 7 天（「供应商的资质和状态」那一档）。发给供应商的只发管理员（和收款账户一样：账号被盗用时，管理员能从邮件发现异常的改名）。
- 平台员工的变量白名单多了 `tenant_name`、`changed_fields`。

### 权限

| 操作 | 角色 |
| --- | --- |
| `tenant.edit`（新）：直接改名称和企业信息 | 超级管理员、运营、招商（和新建供应商 `tenant.create` 同一批人；菜单表「供应商 · 编辑」） |
| `tenant.read`：看企业信息、修改申请 | 原有 |
| `tenant.review`：对修改申请发起复核、驳回 | 原有（超级管理员、运营、招商） |
| `tenant.approve`：批准 `tenant.profile_change` | 原有（运营、招商互审，只有一位时超级管理员审） |
| 供应商 `company.manage`：直接改联系信息、提交和撤回申请 | 管理员 |
| 供应商 `company.read`：看企业信息和申请 | 管理员、财务、只读 |

单独加 `tenant.edit`、不复用 `tenant.create`：已有的自建角色不会因此多出改名权；「勾了编辑」的自建角色照 ADR 0030 换算。

### 页面

- 运营后台供应商详情（`/platform/tenants/{id}`）：「基本信息」下面新卡片「企业信息」（对外显示名称、国家、法定名称、登记号、注册地址、联系人、电话、邮箱），标题行「编辑企业信息」（有 `tenant.edit` 才有）打开对话框，名称和企业信息一起改（分别带各自的版本）；有申请时下面一张「资料修改申请」：改前改后对照、「核对无误，发起复核」「驳回」（有 `tenant.review` 才有），已发起的指向「待审核」。
- 「待审核」页认识新类别：改前改后的表、去供应商详情的链接、批准的后果说明。
- 供应商后台：菜单「设置 › 企业信息」（`/settings/company`，`company.read`）：现在的企业信息；申请中每一项都能改（也可以在「企业资质」里改）；审核通过以后只能改注册地址和联系方式；「申请修改名称、法定名称、登记号」表单（只发改了的项）、等审核的申请和撤回、以前的申请和平台的意见。「企业资质」页的企业信息卡片指向这里。

## 待定事项（先按推荐做了）

| # | 问题 | 选的方案 | 理由 |
| --- | --- | --- | --- |
| 1 | 国家审核通过以后供应商能不能改 | 不能，只有平台改 | 国家决定必交资质清单，改了已审的资质对不上 |
| 2 | 联系信息直接改要不要复核 | 不要，事后通知平台运营 | 业主只要求名称、法定名称、登记号审核；联系人换了要马上能联系上 |
| 3 | 复核被驳回时申请怎么办 | 申请不变，处理的同事再驳回申请或重新发起 | 和收款账户一致；复核的结论针对一次发起 |
| 4 | 名称的乐观锁用哪个版本 | `tenants.version` | 已有的列；和主数据、商品一样的做法 |
