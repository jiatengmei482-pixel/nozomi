# ADR 0030：平台账号安全——两步验证、IP 白名单、自建角色与数据范围

- 状态：已采纳（2026-10-25，M4-05）
- 补充 ADR 0008：「本期只有邮箱 + 密码登录、两步验证不在本任务范围」一句由本文取代——平台员工登录现在是「密码 → 两步验证」；租户用户不变（仍只有密码）。
  「角色与权限」一节的「自建角色、数据范围留到 M4」由本文实现。
- 补充 ADR 0013：「必须先修改密码」的判断排在两步验证之后（见「登录的先后顺序」）。
- 补充 ADR 0023：双人复核多两类（`platform_role.update`、`staff.mfa_reset`）；渠道类的复核按数据范围过滤。
- 补充 ADR 0010：`platform_roles` 对平台角色开放读写删，`platform_sessions` 加「改」，新表 `platform_recovery_codes`。
- 数据加密密钥 `DATA_ENCRYPTION_KEY` 和 `SecretBox` 与 M3-02 分支（ADR 0027）是同一份实现（配置项、部署脚本自动生成、AES-256-GCM + HKDF 按用途派生）。
  本分支从 main 切出时 M3-02 还没合并，所以把那几处原样带了过来，只多一个用途名 `platform-totp-secret`；合并时两边是同一套代码，只需把两个用途名、两段说明合在一起。

## 背景

需求：《平台运营端与渠道对接》「平台账号、安全与审计」（必须两步验证；会话 8 小时过期；可设 IP 白名单；权限 = 角色 × 菜单 × 操作，可加数据范围，如只看某几个城市、某几个渠道），
「运营后台菜单与角色」（权限按「菜单 × 操作（查看 / 编辑 / 审核 / 导出）」配置，可自建角色），「敏感操作双人复核」。
roadmap 验收标准：平台员工必须开启两步验证才能登录；可按角色配置菜单 × 操作权限和数据范围。公司 SSO 是 M4-06（受阻），不在本文。

## 决定

### 两步验证：TOTP（RFC 6238）

- 算法：HMAC-SHA1、30 秒一个时间窗、6 位数字、T0 = 0——Google Authenticator、Microsoft Authenticator、1Password 等都支持的默认值。纯函数在 `packages/domain/src/totp.ts`（HMAC 由调用方传入，domain 不依赖 `node:crypto`），单元测试对照 RFC 4226 附录 D 和 RFC 6238 附录 B 的测试向量。
- 容忍前后各一个时间窗（手机时钟偏差、输入耗时），所以一个码最多在 90 秒里有效。
- **防重放**：账号上记「上次接受的时间窗编号」，接受的时间窗必须比它晚，写回的条件也是「比上次晚」（一条带条件的 `update`）。所以同一个码只能用一次；用了较晚的码之后较早时间窗的码也不再收；两个请求同时用同一个码只有一个成功。
- **限速**：输入动态码 / 恢复码和登录同一套机制（ADR 0008 的 `login_throttles`），单独一组计数（入口 `platform-mfa`）：同一邮箱 + 地址 15 分钟 5 次、同一邮箱 20 次、同一地址 50 次。6 位码猜中一次的概率是 3/10⁶，一天最多约 2000 次尝试。成功后清零。失败的尝试都写审计（`mfa_failed`，有限速，量有上限）。
- **密钥存储**：20 字节随机数（RFC 4226 推荐的长度），Base32 后用 `SecretBox` 加密存在 `platform_users.totp_secret`（AES-256-GCM，子密钥由 `DATA_ENCRYPTION_KEY` 按用途 `platform-totp-secret` 用 HKDF 派生；附加数据是员工编号，密文搬到别人的行里解不开）。原文只在「开始绑定」的那一次应答里出现。
  - 没配置 `DATA_ENCRYPTION_KEY` 时绑定、验证都返回 503 `MFA_ENCRYPTION_NOT_CONFIGURED`，也就是登录不了运营后台。production 必须配（配置校验）；服务器上初始化 / 部署脚本自动生成；本地开发要自己在 `.env` 里填一个（`.env.example` 有生成命令）。
  - 主密钥被换掉、库里的密文解不开时 503 `MFA_SECRET_UNAVAILABLE`，提示联系超级管理员重置。

### 绑定、恢复码

- **绑定要确认**：「开始绑定」只是生成一个待确认的新密钥（15 分钟有效）并返回密钥原文和 `otpauth://` 链接（页面显示成二维码，也显示密钥原文供手输）；输入一次用它算出的动态码才生效。
- **恢复码**：确认绑定时生成 10 个（16 个字符、去掉易混字符的 31 个字母数字，约 79 位随机；显示为 4 组），**只在这一次应答里出现**，库里只存 SHA-256（随机数熵足够，不需要慢哈希，和邀请令牌同一做法）。登录时可以用一个恢复码代替动态码，用一个少一个。登录后可以在个人页重新生成（要输入现在的动态码或一个恢复码），旧的整组作废。
- **换手机**（个人页的「更换验证器」）：已完成两步验证的会话，先输入现在的动态码或一个恢复码确认是本人，再走同样的「开始 → 确认」。确认之前旧的照常可用；确认后旧密钥作废、恢复码换成新的一组、**这个账号的其他会话全部失效**（换手机多半是因为旧手机丢了）。
- **不提供「自己关掉两步验证」**：两步验证是强制的，关掉等于下次登录又要绑定；需要的只是「换手机」和「别人帮我重置」。
- 只知道密码的人不能借「重新绑定」绕过：会话还没验证、账号已经绑定过时，「开始绑定」返回 409 `MFA_ALREADY_ENROLLED`。

### 登录的先后顺序

`密码 → 两步验证（第一次是绑定）→ 必须修改密码时先改密码 → 正常使用`，规则是 domain 的 `platformSessionRefusal`：

- 密码正确就建会话、发令牌（ADR 0013 的做法：令牌只是会话的凭证），但这个会话是「待验证」的：过期时间先是 15 分钟（够装好 App 并绑定；过了重新输密码）；完成两步验证后同一个令牌恢复正常，会话延长到令牌本身的过期时间（登录起 8 小时，ADR 0008 不变）。
- 登录应答和 `auth/me` 多一个 `second_factor.status`：`enrollment_required`（还没绑定，先绑定）/ `verify_required`（输入动态码）/ `verified`。
- 待验证的会话只能用：`auth/me`、`auth/logout`（用途 `self_service`）和两步验证本身（`auth/mfa/verify`、`auth/mfa/enrollment`、`auth/mfa/enrollment/confirm`，用途 `second_factor`）。其余一律 403 `MFA_REQUIRED`（`details.status` 告诉前端去绑定还是去输入动态码）。**修改密码也要先完成两步验证**——否则只知道密码的人能改掉密码把本人锁在门外。
- 完成两步验证后，账号必须先修改密码时（ADR 0013）照旧只放行 `self_service` 和 `auth/change-password`（用途 `password_change`）。
- 鉴权函数里的判断顺序：401 → 403 `IP_NOT_ALLOWED` → 403 `MFA_REQUIRED` → 403 `PASSWORD_CHANGE_REQUIRED` → 403 `FORBIDDEN` → 参数校验。新接口不用做任何事就默认被拦（`mfa-required.itest.ts` 遍历全部已注册的路由核对）。
- **为什么先两步验证再改密码**：用临时密码登录的人如果能先改密码，「拿到了终端回滚里的临时密码」就足以占住账号；先过两步验证，临时密码泄露的后果仍限于 ADR 0013 说的范围（第一次绑定前谁先登录谁绑定——见「已知限制」）。

### 上线时已有的员工、不能锁死最后一个超级管理员

- 迁移不改任何账号。上线后**已有的员工（包括负责人的超级管理员）下次登录时**，密码正确后页面引导绑定（扫码 → 输入一次动态码 → 保存恢复码），然后照常使用。已经开着的会话也一样：迁移后它们都是「待验证」的，下一个请求就被引导去绑定。
- 绑定只需要密码，所以任何在用的账号（含最后一个超级管理员）随时都能完成绑定，不会因为两步验证被锁死。
- 手机和恢复码都丢了：
  - 有另一位超级管理员：在后台对他发起「重置两步验证」，第三位（或这位之外的另一位）超级管理员批准（双人复核，见下）；
  - 只有一位超级管理员、或者丢了手机的就是唯一的那位：在服务器上运行 `pnpm admin:reset-2fa --email …`（新命令，见下）。
- 被 IP 白名单挡在门外：另一位超级管理员在后台改；没有的话在服务器上运行 `pnpm admin:clear-ip-allowlist --email …`。
- 改自己的 IP 白名单时，改完之后当前的地址必须还在名单里（409 `IP_ALLOWLIST_EXCLUDES_CURRENT`），不会一点保存就把自己锁在门外。
  （能改名单的只有超级管理员，超级管理员用的是内置角色、没有角色名单，所以不存在「改角色名单把自己锁在门外」的情况。）

### 重置别人的两步验证：双人复核

- `POST /platform/v1/staff/{id}/mfa-reset` 发起复核（类别 `staff.mfa_reset`；看 `staff.read`、发起和审核都是 `staff.manage`，即超级管理员）。批准后对方的密钥、恢复码作废，全部会话失效，下次登录重新绑定。不能对自己发起，也不能批准针对自己的（409 `MFA_RESET_SELF`）；复核机制本身保证发起人不能批准。
- **为什么要双人**：重置两步验证 + 发重置密码链接（单人就能发，ADR 0008）= 接管一个账号。只要一个超级管理员账号被盗，单人重置就能让攻击者拿下任何员工的账号；双人复核把它变成要两个人。
- 代价是只有一位超级管理员时后台做不了，用命令行；**建议负责人再建一个超级管理员账号**（见「需要负责人决定的事」）。
- **命令行 `pnpm admin:reset-2fa --email …`**：对任何在用的平台员工有效；清掉密钥和恢复码、全部会话失效；审计记为「系统 / 命令行」。和 `admin:reset-password` 一样只在服务器上能运行（能登录服务器的人本来就能改数据库）。`admin:reset-password` 本身不动两步验证：忘了密码和丢了手机是两件事，分开处理，各留一条审计。

### IP 白名单

- 按员工、按角色都能配：一组地址段（CIDR，IPv4 和 IPv6；只写地址 = 单个地址）。纯函数在 `packages/domain/src/ip-allowlist.ts`：
  - 规范写法存库（IPv6 按 RFC 5952 压缩）；主机位不为 0 的拒绝并给出正确写法（`10.1.2.3/8` → 提示 `10.0.0.0/8`）；重复的拒绝；每份最多 50 条。
  - **IPv4 映射的 IPv6 地址**（`::ffff:203.0.113.5`，双栈服务端常把 IPv4 来源写成这样）当作对应的 IPv4 地址，来源和名单两边都是。
- **生效的名单：员工自己的不空就用员工的，否则用角色的；都空 = 不限制。默认都是空的，所以上线后不影响任何人**。更具体的设置优先，可以给角色设办公室的地址段，再给个别人单独放开或收紧。
- 内置角色没有角色名单（内置角色只读，见下）；要给一组人设，建一个自建角色。
- 来源地址就是限速、审计用的那个（`request.ip`，遵循 `TRUST_PROXY_HOPS`，ADR 0008）：默认不看 `X-Forwarded-For`，伪造请求头绕不过名单。
- **在哪里检查**：登录时在密码正确之后（和「账号已停用」一样——不在名单里的人从应答上也分辨不出邮箱是否存在），不在名单里 403 `IP_NOT_ALLOWED`，审计记一条 `login_failed`（原因 `ip_not_allowed`）；**之后每个已登录的请求也检查**（令牌被拿到名单外用、或者名单刚改过，都立即生效）。每个请求本来就要查会话和账号，名单在同一条查询里带出来。

### 自建角色与「菜单 × 操作」

- 内置的 10 个角色（迁移 0001，来源需求文档）保留为**只读模板**：权限仍以代码里的表（`access.ts` 的 `PLATFORM_PERMISSIONS`）为准，原有的权限矩阵测试原样成立；库里的行加了触发器，改、删一律被数据库拒绝；接口返回 409 `ROLE_BUILTIN_READONLY`。
- 菜单表（`PLATFORM_MENUS`）是「菜单 → 查看 / 编辑 / 审核 / 导出 → 对应哪些接口操作」。只列已经有接口的格子：

  | 菜单 | 查看 | 编辑 | 审核 |
  | --- | --- | --- | --- |
  | 供应商 | `tenant.read` | `tenant.create`、`tenant.change_status` | |
  | 供应商商品 | `product.read` | | |
  | 报价试算 | `quote.preview` | | |
  | 渠道 | `channel.read` | `channel.manage` | `channel.review` |
  | 订单 | `order.read` | | |
  | 待审核 | `approval.read` | | |
  | 主数据与汇率 | `master_data.read` | `master_data.manage`、`fx.manage` | `fx.review` |
  | 平台账号 | `staff.read` | `staff.manage`（只归超级管理员） | |
  | 角色 | `role.read` | `role.manage`（只归超级管理员） | `role.review`（只归超级管理员） |
  | 审计日志 | `audit_log.read` | | |
  | 集成状态 | `integration.read` | | |

  「导出」列现在没有任何接口（订单、报表的导出在各自的任务里做），表里留着这一列，有了接口在这张表里加一格即可。汇率中心按需求文档放在主数据菜单里。
- 自建角色存勾选（`platform_roles.grants`，如 `channels:edit`），每个请求按菜单表换成接口操作；**勾了编辑 / 审核就必须也勾查看**（400 `ROLE_GRANTS_INVALID`）。内置角色在角色页上按同一张表显示成勾选表（`grantsOfActions`，单元测试保证换算前后一个不多一个不少），「从内置角色复制」就是拿这份勾选新建。
- **只归超级管理员、自建角色勾不了的三格**：平台账号的编辑、角色的编辑和审核。否则有「改角色」的人可以给自己的角色加任何权限、有「管账号」的人可以把自己改成超级管理员，双人复核也挡不住两人合谋。系统设置里的「查看」可以给自建角色。
- 新建角色：直接生效（新角色还没人用，不影响任何人；把人改成这个角色是另一件事）。修改：**双人复核**（`platform_role.update`；`role.manage` 发起、`role.review` 审核，即两位超级管理员），发起时给完整内容，批准时按那一刻的数据再校验并核对版本（`APPROVAL_STALE`）。删除：没有任何账号（含待激活、已停用）指着它时直接删（409 `ROLE_IN_USE`）。
- 改员工的角色（`PATCH /platform/v1/staff/{id}`）：超级管理员直接改、写审计（和发邀请时选角色一样）；不能改自己的角色（409 `OWN_ROLE_UNCHANGEABLE`）；最后一个在用的超级管理员不能改成别的角色（`LAST_ADMIN_REQUIRED`）。
- **不缓存**：鉴权本来每个请求都要按主键查会话和账号（ADR 0008），角色的勾选、数据范围、名单在同一条查询里 `join` 出来——每个请求不多一次查询，改了角色立即生效，没有缓存要失效。按菜单表换算是几十个字符串的内存操作。以后量大到这条查询成为瓶颈时，再加进程内缓存 + 按 `platform_roles.version` 失效（新增 ADR）。

### 数据范围

- 自建角色可以限定「城市」「渠道」两个维度（`scope_city_ids`、`scope_channel_ids`；null = 不限制，列表 = 只看这几个，各维度同时生效）。内置角色不限制。
- 现在管到的地方：

  | 维度 | 管到哪里 | 范围外的表现 |
  | --- | --- | --- |
  | 渠道 | 渠道列表、渠道详情及其下面的一切（加价规则、API 客户端、询价日志、改动、发起复核）；订单列表和详情；渠道类的复核（列表、详情、审核）；按渠道的报价试算 | 列表里没有；按编号访问和不存在一样（404） |
  | 城市 | 订单列表和详情 | 同上 |

  限定了渠道范围的人不能新建渠道（403 `DATA_SCOPE_DENIED`：新渠道不在任何人的范围里，建了自己也看不到）。
  渠道的 `/channels/:id…` 接口在一个地方统一检查（路由里的鉴权函数），以后在渠道下面加接口不用各自记得。
- **为什么是这两个维度**：需求原文的例子就是「某几个城市、某几个渠道」；它们在现有数据里都有明确的归属（订单有城市和渠道，渠道类的复核对象编号就是渠道编号）。
- **留给以后**（见「本期不做」）：按供应商（租户）的范围、城市范围管到供应商和商品（供应商没有单一城市，商品按区域覆盖多个城市，要先定口径）、报价试算按城市、审计日志按范围、首页统计按范围。

### 接口（openapi 已同步）

- 两步验证：`POST /platform/v1/auth/mfa/verify`（动态码或恢复码二选一）、`POST /platform/v1/auth/mfa/enrollment`（开始绑定；换手机时带现在的动态码或恢复码）、`POST /platform/v1/auth/mfa/enrollment/confirm`、`POST /platform/v1/auth/mfa/recovery-codes`（重新生成）。
- 员工：`GET /platform/v1/staff/{id}`、`PATCH /platform/v1/staff/{id}`（姓名、角色、IP 白名单）、`POST /platform/v1/staff/{id}/mfa-reset`（发起复核）。员工列表和详情多了 `mfa_enabled`、`mfa_enabled_at`、`ip_allowlist`；账号对象多了 `role_name`（自建角色的名字前端不认识）。
- 角色：`GET /platform/v1/roles`、`GET /platform/v1/roles/{key}`、`POST /platform/v1/roles`、`POST /platform/v1/roles/{key}/changes`（发起复核）、`DELETE /platform/v1/roles/{key}`。
- `auth/me` 的 `permissions` 按角色现查（自建角色按勾选），两步验证完成之前为空；多了 `data_scope`、`second_factor`（状态、绑定时间、剩余恢复码数）。
- 角色键：内置角色的键不变；自建角色是 `custom_` + 16 位十六进制（数据库约束），所以 `PlatformUser.role` 从枚举放宽成字符串。

### 运营后台页面（docs/design/pages/platform-security.md）

- 登录的第二步不改地址：两步验证完成之前，运营后台的任何地址都显示绑定 / 输入动态码的页面，完成后就是原来要去的页面；任何接口返回 403 `MFA_REQUIRED` 也回到这一页。
- 个人页「账号安全」（换手机、重新生成恢复码）、平台员工详情（改姓名、角色、IP 白名单，发起重置两步验证）、角色管理（菜单 × 操作的勾选表、数据范围、IP 白名单）。
- 前端判断显示什么：内置角色按 `@nozomi/domain` 的权限表（和后端同一份），自建角色按 `auth/me` 的 `permissions`。真正的检查都在后端。
- **新增运行时依赖 `qrcode-generator@2.0.4`**（MIT，无子依赖，版本写死）：把 `otpauth://` 链接画成二维码（页面上画成 SVG，颜色用设计令牌）。二维码编码（Reed–Solomon 纠错、掩码选择）自己写容易出错又难测（没有解码器可以对照），而这个库只做这一件事。扫不了时页面上同时有密钥原文可以手输。

### 审计

新动作：`mfa_enroll_start`、`mfa_enroll`、`mfa_verify`（方式；用恢复码时记剩余几个）、`mfa_failed`（哪一步、原因）、`mfa_recovery_codes`、`mfa_reset`（复核编号和发起人，或命令行）、`clear_ip_allowlist`（命令行，记清掉之前的名单）；对象 `platform_role` 的 `create` / `update` / `delete`；改员工角色记 `change_role`、改姓名或名单记 `update`（只记变了的字段的前后值）；`login_failed` 多一个原因 `ip_not_allowed`。审计里没有密钥、动态码、恢复码原文。

## 已知限制

- **第一次绑定之前，知道密码的人谁先登录谁绑定**：新员工接受邀请后、或者被重置之后，密码泄露的人可以抢先绑定自己的手机。本人会立刻发现（登录后要求输入动态码），超级管理员重置即可（有审计）。彻底解决要靠邀请链接本身带上绑定，或者公司 SSO（M4-06）。
- 恢复码只能整组重新生成，不能单独作废某一个。
- 待验证的会话 15 分钟过期，期间可以调 `auth/me`：它只返回本人信息，两步验证完成之前 `permissions` 为空。
- IP 白名单只看来源地址，前面的反向代理层数配错（`TRUST_PROXY_HOPS`）时会按代理的地址判断——和限速、审计是同一个前提（ADR 0008）。
- 改员工的角色是单人直接生效（和发邀请时选角色一致）；角色本身的修改才走复核。要把「把人改成超级管理员」也纳入复核，再登记一类即可。
- 时钟：服务器时间偏差超过 30 秒时动态码会对不上。服务器用系统的时间同步（Docker 主机默认开启）。
