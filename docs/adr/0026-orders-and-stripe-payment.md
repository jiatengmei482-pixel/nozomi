# ADR 0026：下单与 Stripe 付款——订单状态、库存预占、保存支付方式、Webhook 签名与幂等、超时取消

- 状态：已采纳（2026-10-18，M3-01）
- 由 ADR 0027 补充（2026-10-25，M3-02）：订单状态加「司机已出发」「司机已到达」「客人未出现（待审核）」「客人未出现」四个，转换表随之扩展；租户角色对订单加「改」（只许改派车和履约的列、只许在履约的范围里改状态）；付款确认时同一个事务里给中标供应商排 `order.confirmed` 推送。本文其余决定不变。
- 实现 ADR 0020「本期不做」里的「每日加急库存的已用量、下单预占」、ADR 0019 留给订单的「下单预占、付款扣减、超时释放」、ADR 0023 留给订单的 `quote_logs.ordered`。
- 补充 ADR 0005：Stripe 三个密钥的用法（`STRIPE_SECRET_KEY` 调接口、`STRIPE_PUBLISHABLE_KEY` 下发给前端、`STRIPE_WEBHOOK_SECRET` 验通知的签名）。
- 补充 ADR 0010：五张新表的授权；平台角色对 `inventory_days` 加「改」、对 `quote_logs` 加「改」。

- 编号说明：迁移 0022 留给 M1-15、0023 留给 M2-06，本任务用 0024。

## 背景

需求：《用车报价服务平台》「API · 销售端接口」（下单必须带 `quote_id` 和 `Idempotency-Key`、预占库存；订单状态；租户不能拒单；付款后才返回中标租户）、
「5. 商品 · ④ 库存」（下单时预占，支付确认后扣减，取消或超时未支付自动释放）、「8. 订单与履约」（支付后租户可见乘客姓名、电话、航班号；不显示对外价）、「数据模型」order / order_event、
「非功能需求」（下单 P95 ≤ 800 ms；乘客电话、邮箱加密存储，租户只在订单确认后可见）；
《平台运营端与渠道对接》「服务后加收费用」（客人付款时用 Stripe 保存支付方式，下单页明确告知并勾选同意）、「财务结算 · 收款与付款」（Stripe 的支付成功回调触发「支付确认 → 自动确认 → 推单给中标租户」）、
「订单中心」（订单详情含报价快照和全部参与比价的租户）、「客人通知」（可选填 WhatsApp / LINE / 微信 / KakaoTalk）。
文末决策：第一轮（默认自动确认，租户不能拒单）、第二轮（中标租户只在支付成功后显示）、第四轮（租户端不返回对外价和加价比例）、第五轮 ⑤（事后加收走 Stripe 保存的支付方式）。
roadmap 的验收标准：Stripe 测试卡真实付款成功；Webhook 签名校验。

负责人还没有提供 Stripe 账号和密钥。所以付款做成一个接口，真实实现是 Stripe，测试用替身；签名校验按 Stripe 的算法实现，用测试里现场生成的密钥验收。

### 订单状态

| 状态 | 含义 | 由谁进入 | 本任务 |
| --- | --- | --- | --- |
| `pending_payment` 待支付 | 已建单、已预占库存，等客人付款（30 分钟） | 渠道下单 | 是 |
| `confirmed` 已确认 | 付款成功即自动确认，租户不能拒单 | Stripe 通知 / 超时检查发现已付款 | 是 |
| `assigned` 已派车 | 填了司机和车辆 | 租户（M3-02） | 否 |
| `in_service` 服务中 | 司机接到客人 | 司机 / 租户（M3-02） | 否 |
| `completed` 已完成 | 服务完成，含实际时长和里程 | 租户（M3-02） | 否 |
| `cancelled` 已取消 | 付款前：超时、付款被取消；付款后的取消（按取消阶梯）在 M3-03 | 系统 / 收款服务 / 客人（M3-03） | 付款前的两种 |
| `rescue_pending` 救援改派中 | 4 种情形触发后，原租户不能再操作 | 系统 / 运营（M3-04） | 否 |

允许的转换（`orderTransitionAllowed`）：待支付 → 已确认 / 已取消；已确认 → 已派车 / 已取消 / 救援；已派车 → 服务中 / 已取消 / 救援；服务中 → 已完成；救援 → 已确认 / 已派车 / 已取消。已完成、已取消是终态。
没有「待确认」「已拒绝」（租户不能拒单，需求的 `order.rejected` 事件不使用）。no-show 审核通过后的结果、改单（M3-03）如果需要新状态，新增 ADR。

每次状态变化在 `order_events` 记一行（从什么到什么、谁、原因、时间，同一时刻的按写入序号排）——需求「所有订单状态变更可追溯」。订单的状态变化不另写审计日志：审计日志的操作者只有员工、租户用户、系统、匿名，渠道和收款服务不是其中之一，状态流水已经是完整的记录。

### 下单（`POST /sales/v1/orders`）

请求：`quote_id`、乘客（姓名、国际格式的电话、邮箱）、航班号、上下车点的地址、即时通讯（选填）、备注、渠道订单号、`save_payment_method`（必须为 true）；请求头 `Idempotency-Key`。

三步，外部调用不占着数据库事务：

1. **一个平台事务**：
   - 幂等键：同一个渠道里同一个键 + 同样的内容 → 返回那张单（应答头 `Idempotent-Replayed: true`）；内容不同 422 `IDEMPOTENCY_KEY_REUSED`。键存在 `order_sales` 上，同一个渠道里永久唯一（比需求的 24 小时更严：24 小时后重用同一个键也是 422，不会悄悄建出第二张单）。
   - 报价：本渠道的（别的渠道的和不存在一样，400 `UNKNOWN_QUOTE`）、在有效期里（410 `QUOTE_EXPIRED`）、没下过单（409 `QUOTE_ALREADY_ORDERED`，一个报价只能下一单，数据库唯一约束兜底）。
   - **金额以快照为准，不重新报价**：结算价和明细、对外价、加价比例、汇率和缓冲都从 `quotes.snapshot` 抄进订单。报价之后供应商改了价格不影响这一单。
   - 商品还在卖：被下架或供应商被暂停 409 `QUOTE_NO_LONGER_AVAILABLE`（车派不出去，不能收钱）。
   - 下单信息（domain 的 `orderDetailsIssues`）：接机（机场）要航班号、送机可填、接送站 / 点对点 / 包车不填；有坐标的那一端要填地址或酒店名；电话要带国家码；必须同意保存支付方式。
   - **加急名额**：走了加急、商品设了每日加急库存的，先拿「商品 + 用车日期」的事务级咨询锁，再数这一天走加急、没取消的单；用完 409 `SOLD_OUT`（`URGENT_SOLD_OUT`）。
   - **每日库存**（限量的商品）：一条条件更新 `held = held + 1 where total - held - sold >= 1` 预占；没占到 409 `SOLD_OUT`。判断和扣减在同一条语句里，并发下单不会超卖；`held + sold <= total` 的检查约束是最后一道防线（ADR 0019）。
   - 建订单（待支付，付款期限 = 下单时间 + 30 分钟）、销售端一侧、收款记录（`creating`）、状态流水，询价日志记「已下单」。
   - 同一个键（或同一个报价）同时来两次：后到的在唯一约束上等前一个提交，整体回滚后再走一遍——同一个键返回那张单，换了键是 409。
2. **事务之外**：在 Stripe 建付款（见下一节）。
3. **一个平台事务**：锁住订单和收款记录，记下 PaymentIntent 和 Customer 的编号。这时订单如果已经不是待支付、或收款记录已经是 `canceled`（建付款的那几秒里被超时取消了）：只记编号、收款记录**保持 `canceled`**（不改回「等客人付款」），再把刚建的付款在 Stripe 取消。

**过了付款期限不再建付款**：渠道很晚才用同一个键重试（订单还没被超时检查处理）时，不调 Stripe、不给 `client_secret`。还没建付款的单就地取消（`PAYMENT_TIMEOUT`）；已经建好付款的交给超时检查（先在 Stripe 取消再取消订单）。

第 2 步失败：订单留在待支付、收款记录还是 `creating`，应答 502 / 504（`PAYMENT_PROVIDER_*`，`details` 里有订单号和是否可以重试）。渠道用**同一个** `Idempotency-Key` 重试就接着建付款（Stripe 那边也带幂等键，不会建出第二笔）。没人重试的到期自动取消、释放库存。

应答：订单（行程、乘客、对外价、付款状态和期限；**没有结算价、加价比例**，付款前没有中标租户）和付款信息（`client_secret`、`publishable_key`）。`client_secret` 只交给客人的浏览器，平台不存、不写日志；重放时现查一次 Stripe 拿到。

Stripe 没配置（三个密钥没填，`config.stripe` 为 null）：下单和通知都 503 `PAYMENT_NOT_CONFIGURED`，和 `/health`、`pnpm config:check` 的「Stripe 支付：未配置，无法收款」是同一个判断。

**所有渠道都由平台用 Stripe 收款**。需求里「销售端收完款后调用 `:confirm-payment`」是给自己收款的渠道（OTA、预付余额 / 授信）用的；现在只有自营官网，那条路在接入第一个外部分销商时做（见「本期不做」）。

### Stripe：保存支付方式

- 每张单建一个 **Customer**（姓名、邮箱、电话、订单号），再建 **PaymentIntent**：
  - `amount` 是客人支付币种的最小货币单位整数——和平台的最小单位一致（日元、韩元就是元，人民币、美元、港币、新台币、泰铢是分）；`currency` 小写；
  - `customer` + **`setup_future_usage: "off_session"`**：付款成功后支付方式保存在这个 Customer 上，服务后加收（M3-03）用它离线扣款（第五轮决策 ⑤）；
  - 只收银行卡（`allowed_payment_method_types: ["card"]`：离线扣款要靠卡）；
  - `metadata` 里有订单编号和订单号，Stripe 后台能按订单号找到付款；
  - Customer 和 PaymentIntent 各带幂等键 `nozomi-order-<订单编号>-customer` / `-payment`。
- 客人在前端用 Stripe.js 确认付款（含 3DS 验证）；平台只认 Stripe 的通知（和超时检查主动去查），不认前端说的「付好了」。
- 下单页的「同意保存支付方式」由前端展示和勾选，接口要求 `save_payment_method: true`，收款记录里记下同意的时间（`save_consent_at`）。
- 官方库 `stripe`（v23）：每次请求最多 10 秒，网络错误、超时、409、429、5xx 自动重试 2 次（带幂等键，安全）；API 版本固定为这一版官方库对应的版本，升级官方库时一起升级、一起测。
- 错误码：`PAYMENT_PROVIDER_TIMEOUT`（504）、`PAYMENT_PROVIDER_UNAVAILABLE`、`PAYMENT_PROVIDER_RATE_LIMITED`、`PAYMENT_PROVIDER_AUTH_FAILED`、`PAYMENT_PROVIDER_REJECTED`（502）。原始异常不往外抛，日志里只有 Stripe 的错误代码。
- 卡号、CVC、`client_secret` 都不经过、不存在平台的库里；库里只有 PaymentIntent、Customer、PaymentMethod 的编号。

### Webhook（`POST /webhooks/stripe`）

- **签名**（`stripe-signature.ts`，按 Stripe 文档的算法自己实现，单元测试和官方库的 `generateTestHeaderString` / `constructEvent` 互相核对）：
  - 请求头 `Stripe-Signature: t=<秒>,v1=<签名>[,v1=…]`；签名 = HMAC-SHA256(整个 `whsec_…`, `${t}.${原始请求体}`) 的十六进制；先比十六进制字符串的长度（必须全是十六进制字符），再按字节定长等时比较（奇数长度解码会丢半个字节，不先比长度会把「正确签名 + 1 个字符」当成对的；官方库也拒绝）；
  - 几个 `v1` 任意一个对上即可（Stripe 轮换密钥期间同时带新旧两个），`v0` 不认；
  - 时间戳和现在相差超过 300 秒拒绝（防重放；比官方库多拒绝「太新」的）；先比签名再看时间；
  - 必须对**原始请求体**校验：这个接口按字节收请求体（256 KB 上限），不先解析成 JSON。
  - 不通过：400 `WEBHOOK_SIGNATURE_INVALID`（`details.reason`），什么都不记。
- **幂等**：`payment_events` 以 Stripe 的事件编号为主键。登记和处理在同一个事务里：处理失败整体回滚、回 500，Stripe 按它的节奏重发时再处理；同一个事件同时来两次，后到的在登记时等前一个事务结束，看到已登记、回 200（`duplicate: true`）。5 分钟之内的重放靠这一条挡住。
- **测试 / 正式模式**：事件的 `livemode` 和本环境的密钥对不上的不处理（`livemode_mismatch`）。
- **处理的事件**：

| 事件 | 做什么 |
| --- | --- |
| `payment_intent.succeeded` | 核对金额和币种（`paymentMatchesOrder`，对不上不确认、记 `mismatch` 和错误日志）→ 待支付的单**自动确认**、库存预占转已售、记下保存的支付方式；已确认的不动；已取消的不复活，收款记录标 `paid_after_cancel`、错误日志（财务核实退款，异常队列在 M4-02） |
| `payment_intent.payment_failed` | 记失败原因（代码、拒付代码、说明），订单仍待支付——付款期限内客人可以换一张卡再付 |
| `payment_intent.processing`、`requires_action` | 更新付款状态 |
| `payment_intent.canceled` | 待支付的单取消（`PAYMENT_CANCELED`）、释放库存 |
| `charge.refunded` | 核对币种（和这笔付款对不上：不记退款，记 `mismatch` 和错误日志，与付款成功的核对一致）；记已退金额（只增不减，乱序的旧通知不会少记）。退款流程在 M3-03 |
| `charge.dispute.created` | 标记拒付、错误日志（「支付异常」，异常队列在 M4-02） |
| 其余 | 记一条 `ignored`，回 200 |

  对不上平台付款的（同一个 Stripe 账户上别的系统建的付款）记 `unmatched`，回 200。付款状态只往前走：先到的「成功」不会被晚到的「失败」「处理中」改回去。
- 加锁顺序和超时取消一样（先订单、后收款记录），两边同时处理同一张单不会死锁。
- 通知原文不存（里面有客人的账单信息），只存事件编号、类型、对象编号、时间、处理结果和少量说明。

### 待支付超时自动取消

- **30 分钟**（需求没写；和报价有效期一样长：客人从询价到付款有完整的 30 分钟，3DS 验证也够用；库存不会被没付款的单占太久）。`ORDER_PAYMENT_RULES.paymentTimeoutMinutes`。
- 定时任务跑在 API 进程里（和汇率中心同一种做法，ADR 0022）：启动后 5 秒第一次，之后每 60 秒一轮，所以最晚在到期后约 1 分钟取消。只有服务进程启动它；测试直接调 `app.orderJobs.tick()`。
- 每一轮取到期的待支付单（最多 50 张，最早到期的在前），一张一张处理：
  处理每一张时**先锁住订单、重新读收款记录**再决定——列出之后到处理之间（前面几张要调 Stripe，可能要几十秒），渠道可能刚用同一个键重试、建好了付款，不能用列表时的旧值：
  1. 还没建好付款的：在这个事务里直接取消（下单第 3 步锁住订单后会看到已取消，把它刚建的付款取消掉）；
  2. 建好了的：**先在 Stripe 取消这笔付款**（事务之外），再看结果：已取消 → 取消订单、释放库存；其实已经付了（客人在最后一刻付款、通知还没到）→ 按付款成功确认订单；还在处理中 → 这一轮不动；Stripe 出错 → 下一轮再试。
  先取消付款再取消订单，保证不会出现「订单取消了，客人却还能付款」；万一还是发生了（取消付款和付款同时发生），由通知那一步标 `paid_after_cancel`。
- 多个实例同时跑：取消、确认都先锁住订单行再看状态，同一张单只处理一次；Stripe 那边重复取消也没关系（已取消的再取消，查出现在的状态）。

### 加急名额进报价

ADR 0020 里「每日加急库存的已用量按 0 算」改为：报价取数时（`loadQuoteFacts`）一并数出这一天走加急、没取消的单，交给 `quoteProduct` 的 `urgentUsed`。用完了的商品报 `URGENT_SOLD_OUT`（对渠道是 `SOLD_OUT`）。下单时在咨询锁里再数一次（询价和下单之间别人可能先下了）。

### 拿到 Stripe 测试密钥后的验证步骤（验收标准「Stripe 测试卡真实付款成功」）

现在做不了：负责人还没有 Stripe 账号。拿到之后（负责人自己把 `sk_test_` / `pk_test_` / `whsec_` 三项填进测试环境 VPS 的 `.env`，不发在聊天里）：

1. Stripe 控制台（Test mode）→ Developers → Webhooks → Add endpoint：网址 `https://<测试环境域名>/webhooks/stripe`，事件选 `payment_intent.succeeded`、`payment_intent.payment_failed`、`payment_intent.processing`、`payment_intent.requires_action`、`payment_intent.canceled`、`charge.refunded`、`charge.dispute.created`；复制 Signing secret 填进 `STRIPE_WEBHOOK_SECRET`。重新部署后 `/health` 的 Stripe 显示「已配置 · 测试模式」。
2. 运营后台建一个渠道、发 API 客户端；用它询价、下单，拿到 `client_secret` 和 `publishable_key`。
3. 用 Stripe.js（或 Stripe CLI：`stripe payment_intents confirm <pi_…> --payment-method pm_card_visa`）确认付款：
   - **4242 4242 4242 4242**（任意未来日期、任意 CVC）：付款成功 → 几秒内订单变成「已确认」，Stripe 后台这个 Customer 下保存了一张卡（`setup_future_usage=off_session`）；运营后台订单详情的「付款」是已付款、支付方式已保存，「收到的通知」里有 `payment_intent.succeeded: applied`。
   - **4000 0025 0000 3155**（需要 3DS 验证）：先是 `requires_action`，完成验证后成功、订单确认。
   - **4000 0000 0000 9995**（余额不足）：`payment_intent.payment_failed`，订单仍待支付、记下 `card_declined / insufficient_funds`；换 4242 再付成功。
   - 不付款等 30 分钟（或把定时任务的间隔看作 1 分钟，最晚 31 分钟）：订单自动取消、库存释放，Stripe 后台这笔 PaymentIntent 是 canceled。
4. Stripe 控制台对一笔事件点「Resend」：订单不变，通知记录里是重复（`duplicate`）。
5. 用 Stripe CLI `stripe trigger payment_intent.succeeded`（对不上平台付款）：记 `unmatched`，订单不受影响。
6. 核对 `allowed_payment_method_types` 在这一版 API 下只出现银行卡；如果 Stripe 账户的 API 版本和官方库固定的版本不同，以官方库固定的为准（请求头 `Stripe-Version`）。
