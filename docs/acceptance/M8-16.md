## 协调者的运行方式核对（检查项 9）

计划：本机生成 `~/.ssh/nozomi/qa-staging-tenant-password`（权限 600、末尾无换行），再运行
`ssh <staging> "docker exec -i -w /app nozomi-staging-api-1 node apps/api/src/cli/qa-tenant-ensure.ts --email <邮箱>" < 密码文件`。

- **可行**。`ssh` 的标准输入是文件，不会分配终端；`docker exec -i` 不带 `-t`，容器里 `process.stdin.isTTY` 为假，命令走「读完整个标准输入、只读一遍」的路径，不会进交互模式。末尾无换行和有换行都能正确读出（上面已核对）。容器里直接用 `node` 运行，环境变量（`APP_ENV=staging`、数据库地址）来自容器本身（`deploy/compose.yml` 要求必须有 `APP_ENV`）；镜像里有 `apps/api` 源码和工作目录 `/app`，和 `admin-create.ts` 在测试环境的用法一致。
- 提醒 1（**密码强度**）：平台规则要求至少 12 个字符、至少 3 类字符（小写 / 大写 / 数字 / 符号）、至少 6 个不同字符、不能包含邮箱 @ 前面的部分。`openssl rand -hex` 只有小写和数字两类，**会被拒**；`openssl rand -base64` 偶尔缺某一类。请用能保证三类以上的生成方式（例如生成后自己检查一遍再写文件）。被拒时命令不做任何改动，可以直接重来。
- 提醒 2：容器名 `nozomi-staging-api-1` 是按 compose 项目名推出来的，这次没有登录服务器核对；也可以用文档里的写法 `/opt/nozomi/staging/current/bin/compose.sh exec -T api node apps/api/src/cli/qa-tenant-ensure.ts --email <邮箱>`——**必须带 `-T`**，否则 compose 会分配终端，命令会进交互输入模式而读不到重定向的密码。
- 提醒 3：第一次成功输出「已建好 QA 测试供应商……」；建好以后可以不带密码再运行一次（`< /dev/null`），应输出「已经存在，没有做任何改动」和「核对通过」，退出码 0。邮箱写到 `~/.ssh/nozomi/qa-staging-tenant-email`。
